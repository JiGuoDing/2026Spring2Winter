## 1. 知识库基础与 RAG

### 1.1 知识库与不同类型的 RAG 有什么关系？请从知识组织方式、检索机制、生成链路和适用场景等角度，对比传统 RAG、混合检索 RAG、GraphRAG、Agentic RAG 与多模态 RAG。

知识库是被管理、可检索、可治理的知识资产及其服务能力，RAG (Retrieval-Augmented Generation，检索增强生成) 则是在生成答案前获取外部知识，并把证据提供给大模型的应用链路。可以简单理解为：**知识库解决“知识存在哪里、如何组织和治理”，RAG 解决“面对一个问题，如何找到并使用这些知识生成答案”。**

二者关系紧密，但并不等同：

- 知识库可以不接入大模型，例如企业文档搜索、知识图谱查询和 FAQ 系统。
- RAG 通常会消费某种外部知识源，但该知识源不一定是狭义的向量数据库，也可以是搜索引擎、知识图谱、关系数据库、业务 API、图片库或实时网页。
- 向量数据库只是知识库的一种索引或存储组件，不能代表完整知识库。完整知识库还应包含原始内容、元数据、权限、版本、质量、血缘和更新机制。
- RAG 的效果上限不仅取决于模型，也受知识质量、索引质量、检索质量和生成约束共同影响。

#### 一、先区分知识库、检索器与 RAG

一个完整系统通常可以拆成四层：

```text
知识源层
文档 / 网页 / 数据库 / 图片 / 音视频 / 知识图谱 / 业务 API
                         │
                         ▼
知识库层
解析清洗 / 切分 / 实体关系 / 元数据 / 权限 / 版本 / 原文与索引
                         │
                         ▼
检索层
关键词检索 / 向量检索 / 混合检索 / 图检索 / SQL / 工具调用
                         │
                         ▼
RAG 应用层
查询理解 / 路由 / 召回 / 重排 / 上下文构造 / 生成 / 引用 / 校验
```

各层职责如下：

| 层次 | 核心问题 | 典型能力 |
| --- | --- | --- |
| 知识源 | 原始事实来自哪里 | 文档、数据库、图像、音视频、API |
| 知识库 | 如何沉淀并治理知识 | 清洗、切分、结构化、权限、版本、质量管理 |
| 检索器 | 如何找到候选证据 | BM25、向量 ANN、图遍历、SQL、元数据过滤 |
| RAG | 如何基于证据完成回答 | 查询改写、检索编排、重排、生成、引用和拒答 |

因此，不能把“上传文档、生成 Embedding、存入向量数据库”当成完整的知识库建设。那只是知识索引链路的一部分。同样，RAG 也不能只理解为“向量 Top-K + 拼接 Prompt”，因为高级 RAG 还可能包含多路召回、图推理、工具调用和迭代验证。

#### 二、不同 RAG 名称并不处于同一分类维度

传统 RAG、混合检索 RAG、GraphRAG、Agentic RAG 和多模态 RAG 经常被并列介绍，但它们实际上回答的是不同问题：

| 类型 | 主要分类维度 | 回答的核心问题 |
| --- | --- | --- |
| 传统 RAG | 流程形态 | 是否采用固定的单次检索与生成管道 |
| 混合检索 RAG | 检索策略 | 如何融合关键词匹配与语义匹配 |
| GraphRAG | 知识表示与检索结构 | 如何利用实体、关系和社区结构获取关联知识 |
| Agentic RAG | 流程控制与决策方式 | 谁来决定查什么、查几次、调用哪个知识源 |
| 多模态 RAG | 知识模态 | 如何检索并理解文本之外的图像、音频或视频 |

它们不是互斥选项，而可以叠加组合。例如，一个企业知识助手可以同时是：

- 多模态 RAG：能够检索产品图片、PDF 图表和会议录音。
- 混合检索 RAG：同时使用 BM25 和向量检索召回文本。
- GraphRAG：利用产品、客户、合同和组织之间的关系做多跳查询。
- Agentic RAG：由 Agent 根据问题动态选择文档搜索、图查询或业务 API。

所以工程选型不应问“这些 RAG 只能选哪一个”，而应分别判断知识模态、组织结构、检索策略和流程复杂度。

#### 三、传统 RAG 与知识库的关系

传统 RAG 通常使用文档型或向量型知识库，流程相对固定：

```text
离线阶段：文档 → 解析 → 切分 → Embedding → 向量索引

在线阶段：问题 → Embedding → Top-K 检索 → 拼接上下文 → LLM 生成
```

它的知识组织单位通常是 Chunk。检索器根据问题与 Chunk 的向量相似度返回候选文本，再由大模型总结或回答。

**适用场景：**

- 产品手册、制度文档和 FAQ 问答。
- 单篇或少量文档即可回答的事实查询。
- 对成本、延迟和流程可控性要求较高的场景。

**主要优势：**

- 架构简单，容易实现和排查。
- 单次检索和生成，延迟与成本相对稳定。
- 证据可以保留原文出处，便于引用和审计。

**主要局限：**

- 相似度高不等于能够回答问题。
- 固定 Top-K 容易漏召回或引入噪声。
- Chunk 会切断跨段落、跨文档的实体关系。
- 对多跳推理、全局总结和复杂任务支持较弱。

#### 四、混合检索 RAG 与知识库的关系

混合检索 RAG (Hybrid Retrieval RAG) 通常要求知识库同时维护至少两类索引：

- 稀疏索引：基于倒排索引和 BM25，擅长匹配产品编号、人名、缩写、错误码和专业术语。
- 稠密索引：基于 Embedding 和近似最近邻搜索，擅长匹配同义表达和语义相近内容。

典型流程如下：

```text
                    ┌→ BM25 召回 ──┐
用户问题 → 查询处理                ├→ 融合排序 → Rerank → LLM
                    └→ 向量召回 ───┘
```

两路结果通常使用 RRF (Reciprocal Rank Fusion)、加权分数或学习排序进行融合，再使用 Cross-Encoder Reranker 精排。元数据过滤也经常参与检索，例如只查用户有权限访问且版本有效的文档。

**适用场景：**

- 企业知识库中既有自然语言描述，又有大量精确术语、代码和编号。
- 用户表达与文档措辞差异较大，纯关键词或纯向量检索都不稳定。
- 希望在不改变整体 RAG 流程的情况下提高召回率和准确率。

需要注意，混合检索首先是一种检索策略，并不必然构成独立的 RAG 架构。传统固定管道、GraphRAG 和 Agentic RAG 都可以把混合检索作为底层能力。

#### 五、GraphRAG 与知识库的关系

GraphRAG 将知识库从“孤立文本块集合”扩展为“实体、关系、文本证据和主题结构组成的图”。典型知识组织包括：

- 实体：客户、产品、组织、人物、技术概念等。
- 关系：隶属、依赖、交易、引用、影响、上下游等。
- 文本单元：实体和关系对应的原始证据。
- 社区或主题摘要：对图中相关子图进行聚类和概括。

典型流程为：

```text
文档 → 实体关系抽取 → 图谱构建 → 社区或层次组织
                                      │
问题 → 实体识别与意图分析 → 子图检索或社区检索 → 证据聚合 → LLM
```

与传统 RAG 主要查找“语义相似文本”不同，GraphRAG 更强调“沿关系找到与问题相关的知识链”。它适合以下场景：

- 多跳问题，例如先找到某产品的供应商，再查询供应商涉及的风险事件。
- 跨文档关系分析，例如人物、公司、项目和合同之间的关联。
- 全局性问题，例如总结整个知识库中的主要主题、群体和趋势。
- 对知识关系的可解释性要求较高的场景。

GraphRAG 的代价也更高：实体对齐、关系抽取、消歧、图更新和社区摘要都需要额外计算；错误关系还可能在图遍历中被放大。因此，只有当问题确实依赖关系或全局结构时，图结构的收益才更明显。简单 FAQ 不必为了使用 GraphRAG 而构建复杂知识图谱。

#### 六、Agentic RAG 与知识库的关系

Agentic RAG 不限定知识库必须采用哪种存储结构。它把关键词检索、向量检索、知识图谱、SQL、网页搜索和业务 API 都视为可调用工具，由 Agent 动态决定：

- 当前问题是否需要检索。
- 应该查询哪个知识源。
- 是否需要拆分成多个子问题。
- 检索结果是否充分、可信和相互一致。
- 是否需要改写 Query、扩大范围或再次检索。
- 何时停止检索并生成答案。

```text
问题 → 规划 → 选择知识源或工具 → 检索 → 评估证据
        ▲                                  │
        └──── 改写、补查、交叉验证 ────────┘
                                           │
                                           ▼
                                      生成与引用
```

**适用场景：**

- 复杂问题需要查询多个知识库或业务系统。
- 问题需要多轮探索、对比分析或事实交叉验证。
- 需要同时使用静态知识和库存、价格、工单等实时数据。
- 无法用一条固定检索链覆盖所有问题类型。

**主要代价：**

- 多轮模型调用和工具调用会增加延迟与成本。
- Agent 的路径具有动态性，测试和复现更困难。
- 必须设置工具权限、最大步数、超时、预算和终止条件。
- Agent 会规划并不代表底层知识可靠，仍需要权限过滤、来源引用和事实校验。

因此，Agentic RAG 是知识访问的动态编排层，不是知识库本身，也不会替代知识库的数据治理能力。

#### 七、多模态 RAG 与知识库的关系

多模态 RAG 将知识库中的知识形态从纯文本扩展到图片、表格、图表、音频和视频。其难点不只是“把图片存进去”，而是要同时保留：

- 原始媒体及其位置、时间戳、页码等元数据。
- OCR、ASR、图像描述和版面分析产生的文本表示。
- 图像、文本或音视频片段的向量表示。
- 不同模态之间的对应关系，例如图表与正文、视频帧与字幕。

常见检索路径包括：

```text
文本问题 → 跨模态 Embedding → 图片或视频片段召回
文本问题 → OCR/ASR 文本索引 → 对应原始媒体定位
图片问题 → 图像 Embedding → 相似图片与相关文本召回
```

**适用场景：**

- 产品图册、医学影像、设计素材和商品知识库。
- 包含复杂表格、架构图和业务图表的 PDF。
- 会议录音、培训视频和监控视频问答。

多模态 RAG 的关键风险是信息在模态转换中丢失。例如，只对图表做 OCR 可能识别出文字，却丢掉坐标、趋势和视觉关系。因此，系统通常需要结合版面解析、多模态 Embedding 和视觉语言模型，而不是简单把所有媒体转成文本。

#### 八、核心对比

| 维度 | 传统 RAG | 混合检索 RAG | GraphRAG | Agentic RAG | 多模态 RAG |
| --- | --- | --- | --- | --- | --- |
| 主要关注点 | 固定检索生成链路 | 多路检索互补 | 关系与全局结构 | 动态规划与工具编排 | 多种媒体知识 |
| 常见知识组织 | 文本 Chunk | Chunk + 稀疏/稠密索引 | 实体 + 关系 + 原文证据 | 多知识源和工具目录 | 文本 + 图片 + 音视频及跨模态关联 |
| 典型检索 | 向量 Top-K | BM25 + 向量 + Rerank | 子图、路径、社区或图向量检索 | Agent 动态选择并迭代检索 | 跨模态向量、OCR、ASR 和媒体定位 |
| 流程控制 | 固定单次管道 | 通常固定，可多路召回 | 通常按图检索流程执行 | 动态循环 | 可固定，也可与 Agent 结合 |
| 擅长问题 | 简单事实问答 | 术语与语义混合查询 | 多跳关系和全局总结 | 复杂任务和多源查询 | 图像、表格、音视频问答 |
| 主要成本 | 切分与向量索引 | 多索引、融合与重排 | 图构建、消歧与更新 | 多轮推理和工具调用 | 媒体解析、存储和多模态模型 |

#### 九、工程选型方法

实际建设时，可以依次回答四个问题：

1. **知识是什么形态？**
   - 纯文本为主，可以从文本 RAG 起步。
   - 图片、表格、音视频承载关键事实，需要多模态 RAG。
2. **问题是否依赖关系和全局结构？**
   - 单文档事实查询使用文档检索即可。
   - 多跳关系、跨文档关联或全局主题分析可以考虑 GraphRAG。
3. **检索需求是否同时包含精确匹配和语义匹配？**
   - 企业场景通常应优先验证 BM25 + 向量检索 + Rerank，而不是只用向量检索。
4. **流程是否需要动态决策？**
   - 固定链路能解决的问题，不必引入 Agent。
   - 只有当查询源、检索次数或任务步骤无法预先确定时，再考虑 Agentic RAG。

一个稳妥的演进路径通常是：

```text
文档 RAG
   → 增加元数据过滤、混合检索和 Rerank
   → 对关系密集场景增加图索引
   → 对图片、表格和音视频增加多模态索引
   → 对复杂多源任务增加 Agent 动态编排
```

这不是必须遵守的固定顺序，但体现了一个原则：先用评估数据确认瓶颈，再引入对应复杂度，不要先选一个热门 RAG 名称再寻找使用场景。

#### 十、共同的质量与治理要求

无论使用哪种 RAG，底层知识库都需要解决以下问题：

- **知识质量**：来源是否可信，内容是否完整，是否存在错误和冲突。
- **时效性**：新增、修改和删除是否能及时同步到所有索引。
- **权限一致性**：检索结果必须继承原始数据权限，不能在生成阶段才补救。
- **可追溯性**：答案应保留来源、版本、页码或记录 ID，支持引用和审计。
- **检索评估**：使用 Recall@K、MRR、NDCG 等指标衡量是否找到正确证据。
- **生成评估**：关注忠实度、答案相关性、引用准确性和拒答能力。
- **端到端可观测性**：记录查询改写、召回候选、排序分数、最终上下文、模型输出、耗时和成本。

如果知识本身过期、权限错误或缺少证据，再复杂的 RAG 也只是更快地使用错误知识。

#### 知识扩展

- **Naive RAG、Advanced RAG 与 Modular RAG**：这是从系统成熟度和模块化程度划分 RAG 的另一种方式，与本文按检索、结构、编排和模态划分的方法可以交叉组合。
- **Rerank 与 Context Compression**：召回之后还需要对候选证据精排和压缩，减少无关上下文对生成结果的干扰。
- **知识库增量更新**：文档、向量索引、倒排索引和图索引必须保持版本一致，否则会产生删除不彻底或新旧知识冲突。
- **Grounded Generation**：要求模型基于可验证证据回答，并在证据不足时拒答，是各类 RAG 控制幻觉的共同目标。
- **RAG 评估体系**：需要分别评估知识、检索和生成，不能只用最终答案正确率定位问题。

#### 面试中可以这样回答

知识库和 RAG 不是同一个概念。知识库负责知识的沉淀、组织、索引、权限、版本和质量治理，RAG 则是在用户提问时检索外部知识，并把证据交给大模型生成答案的应用链路。传统 RAG 一般对文档 Chunk 做单次向量检索，适合简单事实问答；混合检索 RAG 同时使用 BM25 和向量检索，解决精确词项与语义召回互补的问题；GraphRAG 把知识组织为实体和关系，适合多跳推理、跨文档关联和全局总结；Agentic RAG 让 Agent 动态选择知识源、改写查询并多轮检索，适合复杂的多源任务；多模态 RAG 则把图片、表格、音频和视频纳入知识库。需要注意，这些类型并不互斥，它们分别描述流程、检索策略、知识结构、编排方式和数据模态，可以组合使用。工程上应该先分析知识形态和问题类型，再根据评估结果逐步引入混合检索、图结构、多模态能力或 Agent，而不是为了使用某种 RAG 而增加不必要的复杂度。

### 1.2 如何让知识库检索同时做到低延迟和高准确率？请从数据与切分、查询理解、多路召回、索引选型、过滤与融合、重排序、缓存、分布式架构及评估监控等方面说明优化技术与工程取舍。

知识库检索要同时做到“快”和“准”，核心不是寻找一个万能算法，而是构建一条**分阶段、可降级、可评估的级联检索链路**：先用低成本方法快速缩小搜索空间并保证候选覆盖，再用高精度模型处理少量候选，最后只把最有用的证据交给下游。

典型链路可以概括为：

```text
Query 规范化与路由
        ↓
元数据与权限过滤
        ↓
BM25 / ANN / 图检索并行粗召回
        ↓
去重与融合
        ↓
轻量模型或 Cross-Encoder 精排
        ↓
证据选择、邻接补全与上下文压缩
```

其中，“快”主要由 P50、P95、P99 延迟、QPS、吞吐、资源消耗和超时率衡量；“准”主要由 Recall@K、Precision@K、MRR、NDCG、证据覆盖率和权限正确率衡量。最终还要观察答案忠实度、引用准确率和业务成功率，但不能只看最终答案，因为那样难以区分问题来自知识、检索还是生成。

#### 一、先定义“快”和“准”的验收标准

优化前应先建立带标注的查询集，并按真实流量划分查询类型，例如：

- 精确查询：产品编号、错误码、合同号和人名。
- 语义查询：用户表达与文档措辞不同，但含义接近。
- 多条件查询：带部门、时间、版本和权限范围。
- 多跳查询：答案依赖多个文档或实体关系。
- 无答案查询：知识库中不存在可靠证据，系统应拒答。

检索指标各自回答不同问题：

| 指标 | 关注点 | 典型用途 |
| --- | --- | --- |
| Recall@K | 相关证据是否被候选集覆盖 | 衡量粗召回是否漏掉关键材料 |
| Precision@K | Top-K 中有多少结果真正相关 | 衡量噪声水平和上下文利用率 |
| MRR | 第一个相关结果出现得多早 | 适合只取前几条结果的问答系统 |
| NDCG@K | 高相关结果是否排在前面 | 适合具有多级相关性标注的排序任务 |
| P95 / P99 延迟 | 高峰与长尾请求是否稳定 | 避免只看平均延迟掩盖慢请求 |
| QPS 与资源成本 | 单位资源能支撑多少请求 | 评估方案能否规模化部署 |

这些指标必须联合观察。例如，减小 ANN 搜索宽度可能降低延迟，却导致 Recall@K 下滑；盲目增大 Top-K 可能提高召回，却增加融合、精排和网络传输成本。工程目标通常是在业务给定的延迟和成本预算内最大化检索质量，而不是单独追求某个指标极值。

#### 二、数据质量和切分决定检索上限

如果原始知识重复、过期、缺少标题或被错误切分，后续再强的索引和模型也只能在低质量候选中排序。

##### 1. 数据清洗与去重

- 删除导航栏、页眉页脚、广告和模板噪声。
- 对完全重复和近重复内容做文档级、段落级去重。
- 保留来源、版本、生效时间、更新时间和权威等级。
- 对冲突内容标记版本与状态，不要静默覆盖。
- 删除文档时同步清理倒排、向量和缓存中的派生数据。

去重既能减少错误召回，也能缩小索引、降低内存和精排候选数量。

##### 2. 结构感知切分

优先按标题层级、自然段、合同条款、表格、代码函数等语义边界切分，而不是只按固定字符数截断。

- Chunk 太小：语义不完整，虽然匹配精确，但无法支撑答案。
- Chunk 太大：主题混杂，向量语义被稀释，传输和精排成本也更高。
- Overlap 太大：重复候选增多，索引和上下文成本上升。

常见补偿方式包括 Parent-Child Retrieval、Small-to-Big Retrieval 和邻接块扩展。可以用较小 Child Chunk 做精确匹配，命中后回填包含完整上下文的 Parent Chunk，从而兼顾召回粒度与证据完整性。

##### 3. 多粒度和多表示索引

同一份内容可以同时建立标题、摘要、段落、实体和原文 Chunk 等多种表示。查询先在文档或章节级快速定位范围，再在局部做细粒度检索，可以减少全库搜索成本。需要避免无控制地复制索引，因为多表示会增加存储、更新一致性和融合复杂度。

#### 三、查询理解决定系统找什么

真实用户 Query 常存在口语化、缩写、错别字、指代不清和上下文缺失。查询侧优化包括：

- **规范化**：统一大小写、全半角、日期、单位和领域别名。
- **拼写纠错与同义词扩展**：提高关键词检索覆盖率，但要防止错误扩展。
- **Query Rewrite**：将对话中的代词和省略信息补全为独立查询。
- **Query Expansion / Multi-Query**：生成多个检索表达并行召回，提高语义覆盖。
- **HyDE**：生成假设性文档再做向量检索，缓解短 Query 与长文档的表示差异。
- **Query Routing**：根据问题类型选择关键词、向量、SQL、图检索或多跳流程。

查询改写和扩展会增加模型调用延迟，因此不应对所有请求无条件启用。常见做法是使用规则或轻量分类器处理高频简单查询，只对低置信度、歧义或复杂查询调用大模型改写，并缓存稳定的改写结果。

#### 四、多路粗召回同时保证覆盖和速度

单一召回器通常无法覆盖所有查询类型，企业知识库常采用并行的混合召回：

```text
                   ┌→ BM25：术语、编号、精确词项 ───┐
Query → 路由与过滤 ├→ 向量 ANN：同义表达和语义匹配 ├→ 候选合并
                   └→ 图或结构化检索：关系与条件 ──┘
```

各路职责如下：

| 召回方式 | 优势 | 局限 |
| --- | --- | --- |
| BM25 / 倒排索引 | 查询快，对编号、专名和罕见词可靠 | 难以识别同义表达和深层语义 |
| 稠密向量检索 | 语义泛化能力强 | 可能漏掉精确词项，效果依赖 Embedding 模型 |
| 稀疏语义检索 | 保留词项可解释性并学习语义扩展 | 索引和模型复杂度高于传统 BM25 |
| 图检索 | 擅长实体关系和多跳关联 | 图构建与更新成本较高 |
| 结构化查询 | 精确处理时间、数值和业务条件 | 依赖稳定 Schema 和查询生成质量 |

实践中常见的是 BM25 与向量 ANN 并行召回，取各自较大的候选集，再进行融合和精排。召回阶段的目标是“候选不要漏”，不要求最终顺序完全正确；精度问题留给后续排序解决。

#### 五、选择并调优合适的索引

##### 1. 倒排索引

BM25 依赖倒排索引，可以通过分词器、停用词、同义词、字段权重和词项统计优化。标题、正文、标签不应简单拼成一个字段，而可以使用字段级检索与加权，让标题命中获得更高权重。

##### 2. HNSW

HNSW (Hierarchical Navigable Small World) 通过分层小世界图进行近似最近邻搜索，通常在高召回、低延迟场景中表现较好。关键参数包括：

- `M`：节点连接数。增大通常有利于召回，但会增加内存和构建成本。
- `efConstruction`：建索引时的候选宽度。增大可提高图质量，但构建更慢。
- `efSearch`：查询时的搜索宽度。增大通常提高召回，同时增加查询延迟。

固定索引后，`efSearch` 是常用的召回与延迟调节旋钮；但如果 `efConstruction` 过低导致索引质量不足，仅增大 `efSearch` 也不能完全补救。

##### 3. IVF 与 IVF-PQ

IVF (Inverted File Index) 先将向量划分到多个聚类，查询时只搜索与 Query 接近的部分聚类。`nprobe` 越大，搜索的聚类越多，召回通常越高，但延迟也越高。

PQ (Product Quantization) 用量化编码压缩向量，可以显著降低内存和磁盘 IO，适合超大规模或资源受限场景，但会带来距离估计误差。常见做法是用 IVF-PQ 快速召回，再对小候选集读取原始向量或使用精排模型重新打分。

##### 4. 索引选型原则

| 场景 | 候选方案 | 主要取舍 |
| --- | --- | --- |
| 小规模、高精度 | Flat 精确检索或简单索引 | 结果准确，但规模扩大后延迟线性增长 |
| 中大规模、高召回、内存充足 | HNSW | 查询快、召回高，但内存占用较大 |
| 超大规模、内存敏感 | IVF-PQ 或磁盘型 ANN | 更省资源，但需要接受近似误差和参数调优 |
| 高频更新 | 支持增量写入的索引与冷热分层 | 查询性能与更新可见性需要平衡 |

没有脱离数据规模、维度、硬件、更新频率和目标召回率的“最佳参数”。正确方法是以精确 KNN 结果为基准，在真实查询集上绘制 Recall-Latency-Cost 曲线，再选择满足业务 SLO 的参数组合。

#### 六、过滤策略既影响权限，也影响性能

元数据过滤可以按租户、部门、文档类型、时间、版本、语言和权限缩小搜索空间。过滤位置需要根据选择性和索引能力决定：

- **前置过滤**：先缩小候选范围再做向量搜索。适合过滤选择性高且底层索引支持高效过滤的场景。
- **后置过滤**：先做 ANN 搜索再过滤。实现简单，但可能过滤后不足 K 条，需要过度召回或补搜。
- **迭代过滤**：边搜索边校验过滤条件，直到结果足够或达到搜索预算。
- **分区或命名空间路由**：按租户、业务线或时间预先划分索引，减少无关分片访问。

权限过滤必须进入检索链路，不能先召回越权内容，再依赖大模型“不说出来”。同时也不能默认“前置过滤一定更快”，因为极小候选集可能破坏 ANN 图的连通性，具体行为取决于数据库实现和过滤选择性。

#### 七、融合、去重与精排提升最终准确率

##### 1. 多路结果融合

BM25 与向量检索的分数尺度不同，直接相加通常不稳。常见方法包括：

- 分数归一化后加权。
- RRF (Reciprocal Rank Fusion) 按各路名次融合，不依赖原始分数可比。
- 学习排序，根据点击或人工标注学习融合权重。

RRF 的常见形式为：

$$
RRF(d) = \sum_{i=1}^{n}\frac{1}{c + rank_i(d)}
$$

其中，$rank_i(d)$ 表示文档 $d$ 在第 $i$ 路召回中的名次，$c$ 是平滑常数。具体参数应通过验证集调优。

##### 2. 去重与多样性控制

重复 Chunk 会挤占 Top-K 和上下文窗口。可以按文档 ID、内容哈希和向量相似度去重，并使用 MMR (Maximum Marginal Relevance) 在相关性与多样性之间平衡。多样性不能过强，否则可能把真正相关的相近证据排除。

##### 3. 级联精排

推荐使用“粗召回多、精排少”的级联结构：

```text
多路召回数十到数百个候选
        ↓
规则或轻量模型初排
        ↓
Cross-Encoder 精排较小候选集
        ↓
选取少量证据供下游使用
```

Cross-Encoder 将 Query 与候选文本联合编码，能够捕捉细粒度交互，通常比独立向量相似度更准，但计算复杂度随候选数近似线性增长。因此它适合精排，不适合直接扫描全库。对延迟敏感时，可以使用更小的精排模型、批处理推理、模型量化或仅在低置信度请求上启用强精排。

#### 八、证据补全和压缩改善上下文可用性

检索准确不只代表“找到了某个 Chunk”，还要保证证据足以支持回答：

- **Neighbor Expansion**：命中后补充前后相邻块，修复边界截断。
- **Parent 回填**：用 Child 召回，用 Parent 提供完整语义。
- **Context Compression**：抽取与 Query 相关的句子，减少无关 Token。
- **去冗余与排序**：合并重复证据，并将高价值内容放在更显著的位置。
- **证据预算**：按相关性、来源权威性和覆盖度分配有限上下文窗口。

压缩模型也可能误删关键限定条件，因此应保留原始 Chunk ID 和文本位置，支持回溯，并评估压缩前后的证据覆盖率。

#### 九、缓存与预计算降低重复开销

缓存适合稳定、高频且重复度高的请求，但必须把租户、权限、知识版本和检索配置纳入 Cache Key。

常见缓存层包括：

- Query 规范化、Embedding 和改写结果缓存。
- BM25、向量召回和融合结果缓存。
- 热门文档、索引页和高频向量的内存缓存。
- 完全相同问题的最终结果缓存。
- 语义缓存，对相近 Query 复用结果，但需要更严格的相似度和权限校验。

缓存最大的风险不是命中率低，而是返回过期或越权结果。知识更新、权限变更和文档删除时必须进行版本切换或精准失效。对强时效查询，应缩短 TTL、绕过缓存或使用事件驱动失效。

#### 十、并行、分片与冷热分层提升系统吞吐

##### 1. 并行化与超时预算

- BM25、向量和图检索可并行执行，避免串行累加延迟。
- 对每一路设置独立超时和总体 Deadline。
- 使用有界并发、连接池和批量 Embedding，防止高峰期资源耗尽。
- 非关键召回器超时时允许降级，但必须记录降级路径和质量影响。

##### 2. 分片和路由

按租户、业务域、时间或数据哈希分片。优先通过元数据和查询路由减少 Fan-out，只访问相关分片；全分片广播虽然简单，但分片越多，长尾延迟和网络成本越明显。

##### 3. 副本与扩缩容

读多写少场景可增加查询副本；索引构建与在线查询应隔离资源，避免批量更新抢占在线 CPU、内存和 IO。扩缩容需要考虑索引加载和预热时间，实例启动不等于已经具备稳定查询能力。

##### 4. 冷热分层

高频、最新或高价值知识放入内存型高性能索引；低频历史数据使用压缩索引或磁盘索引。查询先访问热层，低置信度或需要历史证据时再访问冷层，从而减少常规请求成本。

#### 十一、用置信度门控和降级控制成本

不是每个请求都需要完整的 Query Rewrite、多路召回和强精排。可以根据查询类型、首轮分数、候选一致性和结果覆盖度选择路径：

```text
高置信度精确命中 → 直接返回精排结果
中等置信度       → 启用混合召回与 Rerank
低置信度或复杂题 → Query 改写、多查询或图检索
超时或过载       → 使用轻量召回、缓存或明确降级
无可靠证据       → 拒答或请求补充信息
```

门控策略必须通过标注数据校准，不能只凭一个未经校准的相似度阈值。不同索引和模型的分数通常不可直接比较。

#### 十二、评估、监控与定位优化

##### 1. 离线评估

- 建立 Query、相关文档、相关性等级和无答案标注。
- 按查询类型、业务域、语言、权限和时间切片统计指标。
- 使用精确检索或人工结果作为 ANN 召回基准。
- 对 Chunk、Embedding、索引参数、融合权重和 Reranker 做消融实验。
- 绘制 Recall@K 与 P95/P99 延迟、内存和成本之间的 Pareto 曲线。

##### 2. 在线评估

- 监控各阶段耗时，而不只监控端到端耗时。
- 记录候选来源、过滤数量、融合名次、精排分数和最终采用证据。
- 观察零结果率、补搜率、超时率、缓存命中率和降级率。
- 结合点击、引用打开、改问、人工反馈和任务完成率评估业务效果。
- 使用 A/B 测试或灰度发布验证优化，避免离线提升但线上退化。

##### 3. 分阶段定位

| 现象 | 优先检查 |
| --- | --- |
| 正确证据完全没出现 | 数据入库、切分、Query、召回器和 ANN 参数 |
| 正确证据出现但排名靠后 | 融合权重、Reranker、字段权重和去重逻辑 |
| 检索正确但答案错误 | 上下文构造、证据压缩、Prompt 和生成模型 |
| 平均快但 P99 很慢 | 分片 Fan-out、冷索引、缓存未命中和资源争用 |
| 更新后仍召回旧内容 | 多索引版本、缓存失效、删除传播和副本一致性 |
| 只在部分用户出错 | 权限过滤、租户路由和个性化配置 |

#### 十三、推荐的优化顺序

一个务实的优化顺序是：

1. 建立真实查询集、相关性标注和分阶段监控。
2. 修复数据清洗、版本、元数据和结构化切分问题。
3. 建立 BM25 与向量 ANN 的混合召回基线。
4. 加入权限与元数据过滤，并验证结果完整性。
5. 使用 RRF 或学习排序融合，再对小候选集做 Rerank。
6. 在真实数据上调优 HNSW、IVF、Top-K 和候选集大小。
7. 使用缓存、并行、路由、分片和冷热分层降低延迟与成本。
8. 仅对仍无法解决的复杂查询增加多查询、图检索或 Agentic 流程。

这个顺序的原则是先解决检索基础质量，再增加模型和系统复杂度。否则，复杂模块可能暂时掩盖脏数据和错误切分，却让问题更难定位。

#### 十四、常见误区

1. **只把 Top-K 调大**：可能提高候选覆盖，但也会增加噪声、精排延迟和上下文成本。
2. **只使用向量检索**：编号、专名、代码和罕见词通常更适合 BM25。
3. **只优化 ANN 参数**：Embedding、Chunk 和数据质量已经决定了向量空间的上限。
4. **直接用大模型扫描所有候选**：准确但成本和延迟不可控，应采用级联排序。
5. **只看平均延迟**：平均值无法反映分片广播、冷启动和资源争用造成的长尾。
6. **缓存不带权限和版本**：容易产生越权和过期结果，属于正确性问题而非单纯性能问题。
7. **盲目套用固定参数**：最佳配置依赖语料、硬件、流量和 SLO，必须通过基准测试确定。
8. **只看最终答案准确率**：无法判断错误来自知识、召回、排序、上下文还是生成。

#### 知识扩展

- **Approximate Nearest Neighbor**：HNSW、IVF 和 DiskANN 等算法通过牺牲少量精确性换取大规模向量检索性能，是速度与召回权衡的核心。
- **Learning to Rank**：当积累了足够的人工标注或用户行为数据后，可以学习多路召回特征的融合和排序权重。
- **Embedding 领域适配**：通用 Embedding 在专业术语或内部语义上可能失真，可通过模型选型、困难负样本和领域微调提升表示质量。
- **索引一致性**：倒排索引、向量索引、图索引和缓存必须共享文档版本与删除语义，否则会出现新旧知识混用。
- **容量规划**：向量数量、维度、索引开销、QPS、更新速率和副本数共同决定内存、磁盘与机器规模。

#### 面试中可以这样回答

要让知识库检索又快又准，我会先定义联合目标，而不是只调一个 Top-K。准确性用 Recall@K、MRR 和 NDCG 衡量，性能看 P95、P99、QPS 和资源成本，并建立覆盖精确查询、语义查询、多条件查询和无答案查询的标注集。链路上先保证数据清洗、版本和结构化切分正确，再做 BM25 与向量 ANN 的并行混合召回，用元数据和权限过滤缩小范围，通过 RRF 融合、去重和 Cross-Encoder 对小候选集精排，最后做 Parent 回填或上下文压缩。索引方面，HNSW 通过 `M`、`efConstruction` 和 `efSearch` 平衡内存、构建质量、召回与延迟；超大规模和内存敏感场景可以用 IVF-PQ，再对候选做精确重排。性能侧会使用 Query 路由、并行检索、缓存、分片、冷热分层和超时降级，但缓存必须绑定权限与知识版本。最后通过分阶段 Trace、离线消融和线上 A/B 测试持续调优。核心原则是“快速粗召回保证不漏，少量高成本精排保证排准”，并在业务延迟和成本预算内选择 Recall-Latency-Cost 曲线上的最佳点。
