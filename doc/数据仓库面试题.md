## 1. 数据仓库基础

### 1.1 什么是数据仓库？它和数据库、数据湖、湖仓一体有什么区别？

数据仓库 (Data Warehouse) 是面向分析场景的数据系统，它把来自业务数据库、日志系统、第三方系统等多个来源的数据进行集成、清洗、建模和沉淀，最终服务于报表分析、指标统计、经营决策、用户画像、数据产品等场景。

面试里可以先用一句话概括：数据仓库不是简单的数据存储，而是一套围绕分析决策构建的数据组织体系，它强调统一口径、历史沉淀、面向主题和高效查询。

#### 一、数据仓库的四个典型特征

##### 1. 面向主题 (Subject-Oriented)

业务数据库通常围绕业务流程设计，比如订单库、支付库、库存库。而数据仓库通常围绕分析主题组织，比如用户主题、商品主题、交易主题、流量主题。

例如，想分析“用户购买行为”，可能需要同时整合用户表、订单表、支付表、商品表和访问日志，这种跨系统分析就是数据仓库的典型价值。

##### 2. 集成 (Integrated)

数据仓库会把多个来源的数据统一编码、统一字段含义、统一时间格式、统一维度口径。

例如，不同系统中性别可能分别用 `M/F`、`1/0`、`男/女` 表示，进入数仓后需要统一成一套标准。

##### 3. 相对稳定 (Non-Volatile)

业务数据库中的数据会频繁增删改，而数仓更强调历史沉淀。数据进入数仓后，一般不会随意删除，而是通过分区、快照、拉链表等方式保留历史状态。

##### 4. 随时间变化 (Time-Variant)

数仓非常关注历史变化，通常会保留每天、每小时、每个版本的数据状态，用于趋势分析和同比环比分析。

#### 二、数据仓库和数据库的区别

数据库通常服务于 OLTP (Online Transaction Processing)，重点是高并发事务、增删改查、数据一致性和业务流程处理。

数据仓库通常服务于 OLAP (Online Analytical Processing)，重点是大规模数据分析、多维聚合、复杂查询和历史统计。

| 对比项 | 业务数据库 | 数据仓库 |
| --- | --- | --- |
| 核心场景 | 交易处理 | 分析决策 |
| 数据模型 | 范式化模型较多 | 维度建模较多 |
| 查询特点 | 单条或少量记录查询 | 大范围扫描和聚合 |
| 数据变化 | 高频增删改 | 批量写入、历史沉淀 |
| 典型系统 | MySQL、PostgreSQL | Hive、Spark、ClickHouse、Doris |

#### 三、数据仓库和数据湖的区别

数据湖 (Data Lake) 更像一个低成本、开放格式的大规模数据存储，可以保存结构化、半结构化、非结构化数据，比如数据库表、日志、图片、音视频、JSON 文件等。

数据仓库更强调建模、治理和分析效率。数据湖强调“先存下来”，数据仓库强调“整理好再用”。

#### 四、湖仓一体是什么

湖仓一体 (Lakehouse) 试图结合数据湖和数据仓库的优点：既保留数据湖低成本、开放格式、支持多类型数据的能力，又提供类似数仓的事务能力、元数据管理、数据治理和高性能分析。

常见技术包括 Delta Lake、Apache Iceberg、Apache Hudi、Apache Paimon 等。

#### 五、面试时可以怎么总结

可以这样回答：数据仓库是面向分析决策的数据系统，它会把多个业务系统的数据经过集成、清洗、建模和沉淀，形成统一、稳定、可复用的数据资产。它和业务数据库的区别在于，数据库主要服务在线交易，强调事务和实时写入；数据仓库主要服务分析查询，强调历史数据、多维聚合和统一口径。数据湖更偏原始数据存储，湖仓一体则是在数据湖基础上补充事务、治理和分析能力，让数据湖也具备数仓化使用能力。

#### 知识扩展

- OLTP 与 OLAP：理解数据库和数仓差异的基础
- 数据湖：偏原始数据存储，适合低成本保存多类型数据
- 湖仓一体：在数据湖上增强事务、元数据和分析能力
- 维度建模：数仓面向分析查询的核心建模方法
- 数据治理：保证数仓数据可信、可管、可复用

### 1.2 为什么要建设数据仓库？数据仓库解决了什么问题？

建设数据仓库的核心原因是：企业的数据通常分散在多个业务系统中，直接基于业务库做分析会遇到口径不统一、查询影响线上业务、历史数据不完整、重复开发严重等问题。数据仓库通过统一采集、统一建模、统一指标和统一服务，把分散的数据变成可复用的数据资产。

#### 一、解决数据分散问题

业务系统通常按功能拆分，比如用户系统、订单系统、支付系统、物流系统、营销系统。单个系统只能回答局部问题，无法直接回答跨业务问题。

例如，要分析“某次促销活动带来的新用户购买转化”，需要同时关联：

- 用户注册数据
- 活动曝光数据
- 商品浏览数据
- 下单数据
- 支付数据
- 退款数据

这些数据如果不进入数仓，很难形成完整链路。

#### 二、解决指标口径不一致问题

不同团队可能会各自写 SQL 计算 GMV、订单数、活跃用户，导致过滤条件、时间口径、退款处理方式都不一样，最终出现“同一个指标多个数字”。

数仓通过公共层和指标体系统一口径，让业务方复用同一套指标定义。

#### 三、降低对业务库的影响

分析查询通常会扫描大量数据，如果直接在业务库上做复杂 Join、Group By 和历史统计，容易影响线上交易性能。数仓会把分析负载从业务库中剥离出来，保护核心业务系统。

#### 四、沉淀历史数据

业务库通常只保存当前状态，或者为了性能和成本定期归档。但分析场景经常需要看历史趋势，比如过去 180 天的用户等级变化、商品价格变化、订单转化趋势。

数仓可以通过分区表、快照表、拉链表等方式保存历史状态。

#### 五、提升数据开发复用性

如果没有数仓，每个报表都从 ODS 或业务库重新清洗和关联，会产生大量重复 SQL。数仓通过 DWD、DWS、ADS 等分层，把通用明细和汇总能力沉淀下来，减少重复建设。

#### 六、面试时可以怎么总结

可以这样回答：建设数据仓库主要是为了解决企业数据分散、口径不统一、历史不可追溯、分析影响业务库以及数据开发重复的问题。数仓会把不同业务系统的数据统一接入，再经过清洗、建模、汇总和指标管理，形成稳定可复用的数据资产。这样业务分析、报表、BI、经营决策和数据产品都可以基于统一的数据底座来构建。

#### 知识扩展

- 指标体系：解决同一指标多个口径的问题
- 数仓分层：通过层次化加工提升复用性和可维护性
- 数据质量：保证进入报表和决策的数据可信
- 调度系统：保障数据链路按时、按依赖稳定产出
- 数据服务：把数仓结果以 API、报表或查询引擎形式提供出去

### 1.3 数据仓库常见分层有哪些？ODS、DWD、DWS、ADS 分别负责什么？

数仓分层是数据仓库设计中非常核心的思想。它的目的不是为了把链路变复杂，而是为了让数据从原始到可用、从明细到汇总、从通用到业务应用逐层沉淀，降低重复开发，提高数据质量和复用性。

常见离线数仓分层包括 ODS、DWD、DWS、ADS，有些公司还会增加 DIM、DM、TMP 等层。

#### 一、ODS 层：原始数据层

ODS (Operational Data Store) 主要保存从业务系统同步过来的原始数据，尽量保持和源系统一致。

特点：

1. 数据粒度最细，通常是一张业务表对应一张 ODS 表。
2. 尽量少做业务加工，只做必要的格式转换、字段补充和分区落地。
3. 便于数据追溯，当下游出现问题时可以回到 ODS 排查。

例如：

```sql
ods_order_info_di
ods_user_info_di
ods_payment_info_di
```

#### 二、DWD 层：明细数据层

DWD (Data Warehouse Detail) 是清洗后的明细层，通常会对 ODS 数据进行去重、过滤脏数据、字段标准化、维度退化、业务过程建模。

特点：

1. 仍然保持明细粒度。
2. 比 ODS 更干净、更规范。
3. 通常围绕业务过程建设事实明细表。

例如，订单明细表可以保留一行一笔订单或一行一个订单商品明细：

```sql
dwd_trade_order_detail_di
dwd_user_register_di
dwd_payment_success_di
```

#### 三、DWS 层：汇总数据层

DWS (Data Warehouse Summary) 是公共汇总层，面向主题域进行轻度或中度汇总，沉淀可复用的统计结果。

特点：

1. 通常按照用户、商品、店铺、地区、日期等维度汇总。
2. 服务多个 ADS 应用，强调公共复用。
3. 适合沉淀通用指标，比如用户近 7 日下单金额、商品日销售额。

例如：

```sql
dws_user_trade_1d
dws_product_trade_1d
dws_shop_trade_1d
```

#### 四、ADS 层：应用数据层

ADS (Application Data Service) 是面向具体业务场景或报表的数据层，通常直接服务 BI 看板、数据接口、运营报表、推荐系统特征等。

特点：

1. 面向具体应用，字段通常比较宽。
2. 查询性能要求高，常做预聚合和宽表设计。
3. 稳定性和口径一致性直接影响业务使用。

例如：

```sql
ads_sales_dashboard_1d
ads_user_growth_report_1d
ads_coupon_effect_analysis_1d
```

#### 五、订单链路示例

以订单数据为例：

1. ODS 层保存原始订单表 `ods_order_info_di`
2. DWD 层清洗出订单明细事实表 `dwd_trade_order_detail_di`
3. DWS 层按用户、商品、店铺汇总出公共统计表
4. ADS 层生成老板看板、运营活动分析、用户价值分析等应用表

#### 六、面试时可以怎么总结

可以这样回答：数仓分层的核心目的是提升复用性、可维护性和数据质量。ODS 层保存原始业务数据，便于追溯；DWD 层做清洗和明细建模，形成标准明细事实；DWS 层按主题进行公共汇总，沉淀可复用指标；ADS 层面向具体报表和应用，提供最终查询结果。分层之后，下游不需要反复从原始数据加工，可以复用公共明细和汇总数据。

#### 知识扩展

- DIM 层：存放公共维度表，例如用户维度、商品维度
- 事实表：DWD 层常围绕业务过程建设事实明细
- 公共汇总：DWS 层的价值在于减少重复指标计算
- 宽表：ADS 层常通过宽表提升查询效率
- 调度依赖：分层越清晰，任务依赖和故障定位越容易管理

### 1.4 什么是 ETL 和 ELT？两者有什么区别，分别适合什么场景？

ETL 和 ELT 都是数据集成和数据加工链路中的常见模式，区别在于 Transform (转换加工) 发生在数据加载到目标系统之前还是之后。

#### 一、ETL 是什么

ETL 指 Extract、Transform、Load，也就是先抽取数据，再在中间处理环节完成清洗转换，最后加载到目标数据仓库。

流程如下：

```plaintext
业务系统 -> 抽取 -> 清洗转换 -> 加载到数仓
```

ETL 更常见于传统数据仓库时代，因为传统数仓存储和计算成本较高，通常希望在进入数仓前就把数据清洗好。

#### 二、ELT 是什么

ELT 指 Extract、Load、Transform，也就是先把数据抽取并加载到数据湖或数据仓库，再利用目标平台的计算能力进行转换加工。

流程如下：

```plaintext
业务系统 -> 抽取 -> 加载到数据湖/数仓 -> 清洗转换
```

在大数据和湖仓场景下，ELT 更常见，因为 HDFS、对象存储、Hive、Spark、Flink、Trino 等系统可以低成本存储大量原始数据，并在后续按需加工。

#### 三、ETL 和 ELT 的核心区别

| 对比项 | ETL | ELT |
| --- | --- | --- |
| 转换时机 | 加载前转换 | 加载后转换 |
| 原始数据保留 | 可能不完整 | 通常完整保留 |
| 计算位置 | 中间 ETL 工具 | 目标数仓或数据湖 |
| 适合场景 | 传统数仓、强治理、入仓前标准化 | 大数据平台、湖仓、探索式分析 |
| 优点 | 入仓数据干净、质量可控 | 灵活、可追溯、适合大规模数据 |
| 缺点 | 原始细节可能丢失、扩展性较弱 | 对后续治理和存储管理要求更高 |

#### 四、典型场景选择

如果企业有强规范要求，比如金融报表、监管报送，可能更偏 ETL，因为入仓前就要完成严格校验和标准化。

如果企业的数据来源多、规模大、分析需求变化快，通常更适合 ELT，先把原始数据落到 ODS 或数据湖，再逐层加工。

#### 五、面试时可以怎么总结

可以这样回答：ETL 和 ELT 的区别主要在于数据转换发生的位置。ETL 是先抽取、再转换、最后加载，适合传统数仓和强治理场景；ELT 是先抽取并加载原始数据，再利用数仓或湖仓平台进行转换，适合大数据、数据湖和探索式分析场景。现在很多离线数仓会采用 ELT 思路，先把原始数据落到 ODS，再通过 DWD、DWS、ADS 分层加工。

#### 知识扩展

- ODS：ELT 模式下通常作为原始数据落地点
- 数据湖：天然适合先存储后加工的 ELT 模式
- 调度系统：负责串联抽取、加载、转换任务
- 数据质量：ETL 偏前置校验，ELT 偏入湖后分层校验
- CDC：增量抽取常用于 ETL/ELT 的数据接入环节

## 2. 数仓建模

### 2.1 什么是维度建模？为什么数仓里常用维度建模？

维度建模是一种面向分析查询的数据建模方法，它的核心思想是围绕业务过程构建事实表，再围绕分析视角构建维度表，让使用者可以从不同维度对事实指标进行统计分析。

面试里可以先说：维度建模不是为了减少数据冗余，而是为了让分析查询更直观、更高效、更贴近业务语言。

#### 一、维度建模的两个核心对象

##### 1. 事实表

事实表记录业务过程中发生的事件，通常包含度量值和维度外键。

例如订单事实表中，一笔订单就是一个业务事件，订单金额、支付金额、优惠金额就是度量。

##### 2. 维度表

维度表描述分析事实的角度，比如用户、商品、店铺、地区、时间。

例如分析订单金额时，可以按用户性别、商品类目、城市、日期等维度切分。

#### 二、为什么数仓常用维度建模

##### 1. 更适合 OLAP 查询

分析场景经常是按多个维度做聚合，比如“按城市和商品类目统计近 7 天销售额”。维度建模天然适合这种 Group By 和多维分析。

##### 2. 更容易被业务理解

事实和维度都来自业务语言，比高度范式化的数据库模型更容易解释。

##### 3. 查询链路更清晰

维度建模通常是事实表关联多个维度表，比复杂的三范式模型更适合报表开发和指标复用。

##### 4. 便于建设公共数据层

DWD 层可以沉淀标准事实表，DIM 层沉淀公共维度表，DWS 和 ADS 可以在此基础上复用加工。

#### 三、一个简单例子

```sql
-- 统计每天每个商品类目的支付金额
SELECT
    f.dt,
    p.category_name,
    SUM(f.pay_amount) AS pay_amount
FROM dwd_trade_order_detail_di f
LEFT JOIN dim_product_df p
    ON f.product_id = p.product_id
WHERE f.dt = '2026-06-10'
GROUP BY f.dt, p.category_name;
```

这里 `dwd_trade_order_detail_di` 是事实表，`dim_product_df` 是商品维度表，`pay_amount` 是度量，`category_name` 是分析维度。

#### 四、面试时可以怎么总结

可以这样回答：维度建模是数仓中面向分析场景的建模方法，它通过事实表记录业务过程，通过维度表描述分析角度。事实表负责回答发生了什么，维度表负责回答从哪些角度分析。数仓常用维度建模，是因为它更贴近 OLAP 查询模式，便于多维聚合、指标复用和业务理解。

#### 知识扩展

- 星型模型：事实表直接关联多个维度表，是维度建模最常见形态
- 雪花模型：维度进一步规范化拆分，减少冗余但增加 Join
- 总线矩阵：用于规划业务过程和公共维度
- 粒度：事实表设计中最关键的概念之一
- 指标体系：很多指标都基于事实表中的度量加工得到

### 2.2 事实表和维度表有什么区别？如何设计事实表和维度表？

事实表和维度表是维度建模中的两个核心概念。简单说，事实表记录业务事件和度量，维度表描述分析这些事件的角度。

#### 一、事实表是什么

事实表通常记录一个业务过程中的事实数据，比如下单、支付、退款、登录、浏览、点击。

事实表一般包含：

1. 业务主键或事件 ID
2. 维度外键，例如用户 ID、商品 ID、店铺 ID
3. 度量字段，例如订单金额、支付金额、浏览次数
4. 时间字段和分区字段

例如订单事实表：

```plaintext
order_id
user_id
product_id
shop_id
order_time
order_amount
pay_amount
dt
```

#### 二、维度表是什么

维度表用于描述事实发生时的上下文，比如用户是谁、商品属于哪个类目、店铺在哪个城市。

维度表一般包含：

1. 维度主键
2. 维度属性
3. 生效时间和失效时间 (如果需要保留历史)
4. 分区字段或版本字段

例如用户维度表：

```plaintext
user_id
gender
age_range
city
member_level
register_time
dt
```

#### 三、事实表和维度表的区别

| 对比项 | 事实表 | 维度表 |
| --- | --- | --- |
| 描述对象 | 业务事件 | 分析角度 |
| 数据特点 | 行数多、增长快 | 行数相对少、变化慢 |
| 核心字段 | 度量值、维度外键 | 维度属性 |
| 典型例子 | 订单事实、支付事实、浏览事实 | 用户维、商品维、地区维 |
| 主要问题 | 粒度设计、数据量、去重 | 历史变化、属性一致性 |

#### 四、如何设计事实表

设计事实表最重要的是确定粒度。粒度决定一行数据代表什么。

例如订单场景中：

1. 一行一笔订单：适合订单级统计
2. 一行一个订单商品明细：适合商品销售分析
3. 一行一次支付事件：适合支付成功率分析

事实表设计时要注意：

1. 粒度必须清晰，不能混合订单级和商品级字段。
2. 度量字段尽量保持可加性，比如金额、次数。
3. 保留必要的维度外键，方便后续关联维度表。
4. 对重复事件、撤销事件、退款事件要有明确处理逻辑。

#### 五、如何设计维度表

维度表设计时要关注属性完整性和历史变化。

常见方法：

1. 高频使用的维度属性可以冗余到同一张维表中，减少 Join。
2. 对会变化的属性，比如用户等级、商品价格，要考虑是否保留历史。
3. 公共维度要统一建设，避免多个团队重复维护用户维、商品维。
4. 敏感字段要考虑脱敏和权限控制。

#### 六、面试时可以怎么总结

可以这样回答：事实表记录业务过程中发生的事件，比如订单、支付、浏览，核心是粒度和度量；维度表描述分析事实的角度，比如用户、商品、地区，核心是维度属性和历史变化。设计事实表时最重要的是先确定一行数据代表什么，再选择度量字段和维度外键；设计维度表时要保证属性统一、可复用，并处理好缓慢变化维问题。

#### 知识扩展

- 粒度：事实表设计的第一原则
- 可加性度量：决定指标能否跨维度汇总
- 退化维度：某些维度值直接保存在事实表中
- SCD：解决维度属性变化的建模方法
- 宽表：常把事实和维度属性预先打平成应用表

### 2.3 什么是星型模型和雪花模型？它们的优缺点是什么？

星型模型和雪花模型都是维度建模中的常见组织方式，区别在于维度表是否继续拆分规范化。

#### 一、星型模型是什么

星型模型是以事实表为中心，事实表直接关联多个维度表。结构像一颗星，事实表在中间，维度表围绕在四周。

例如订单分析模型：

```plaintext
              dim_user
                 |
dim_product -- fact_order -- dim_shop
                 |
              dim_date
```

特点是结构简单，查询时 Join 路径短，适合 OLAP 分析。

#### 二、雪花模型是什么

雪花模型是在星型模型基础上，把维度表进一步拆分成更规范的多级维度。

例如商品维度拆成商品表、品牌表、类目表：

```plaintext
fact_order -> dim_product -> dim_category
                         -> dim_brand
```

它的结构比星型模型更规范，冗余更少，但 Join 链路更长。

#### 三、星型模型的优缺点

优点：

1. 查询简单，事实表直接关联维度表。
2. Join 次数少，查询性能通常更好。
3. 更符合分析人员的理解方式。
4. 适合 BI 报表和自助分析。

缺点：

1. 维度属性冗余较多。
2. 维度更新时可能需要维护较宽的维表。
3. 对维度一致性治理要求较高。

#### 四、雪花模型的优缺点

优点：

1. 数据冗余少。
2. 维度结构更规范。
3. 适合维度层级复杂且复用要求高的场景。

缺点：

1. Join 链路更长，查询性能可能下降。
2. 使用理解成本更高。
3. 报表开发 SQL 更复杂。

#### 五、如何选择

在数仓分析场景中，通常优先选择星型模型，因为分析系统更关注查询效率和易用性，而不是极致减少冗余。

如果某些维度层级非常复杂，比如行政区划、商品多级类目、组织架构，也可以局部使用雪花模型。

#### 六、面试时可以怎么总结

可以这样回答：星型模型是事实表直接关联多个维度表，结构简单、查询效率高、适合 OLAP 分析；雪花模型是把维度表继续拆分成更规范的层级结构，冗余更少，但 Join 更多、查询复杂度更高。实际数仓中通常优先使用星型模型，在维度层级复杂或复用要求很强的场景下局部采用雪花模型。

#### 知识扩展

- 维度退化：把部分维度字段放入事实表，减少 Join
- 宽表设计：进一步把事实和维度打平，提高查询效率
- 数据冗余：星型模型用冗余换查询效率
- BI 查询：星型模型对 BI 工具更友好
- 维度一致性：公共维度建设决定模型复用效果

### 2.4 什么是宽表？宽表有什么优缺点？

宽表是把多个相关表中的字段预先关联、清洗、展开到一张字段较多的表中，供下游报表、分析或数据服务直接使用。它本质上是一种用存储冗余换查询效率和使用便利性的设计。

#### 一、宽表为什么常见

在数仓里，如果每个报表都实时关联事实表、用户维表、商品维表、店铺维表、地区维表，SQL 会很复杂，查询性能也可能较差。

宽表会提前把常用字段打平，例如订单宽表中同时包含：

- 订单字段：订单 ID、下单时间、支付金额
- 用户字段：用户性别、城市、会员等级
- 商品字段：商品类目、品牌、价格
- 店铺字段：店铺类型、店铺城市

这样下游查询时可以直接过滤和聚合。

#### 二、宽表示例

```sql
SELECT
    dt,
    user_id,
    user_city,
    member_level,
    product_id,
    category_name,
    brand_name,
    shop_id,
    pay_amount
FROM ads_trade_order_wide_1d
WHERE dt = '2026-06-10';
```

业务方要按城市、类目、会员等级分析支付金额时，不需要再写复杂 Join。

#### 三、宽表的优点

1. 查询效率高，减少运行时 Join。
2. 使用门槛低，业务分析人员更容易理解。
3. 口径相对固化，适合稳定报表。
4. 对高频查询场景友好，可以直接服务 BI 或接口。

#### 四、宽表的缺点

1. 数据冗余大，存储成本更高。
2. 字段很多，维护成本高。
3. 需求变化时可能频繁加字段。
4. 如果上游维度口径变化，宽表需要重新加工或回刷。
5. 不适合所有探索式分析，因为它已经预设了字段范围。

#### 五、什么时候适合用宽表

适合：

1. 查询频率高的报表或看板。
2. 维度和指标相对稳定的分析场景。
3. 对响应速度要求较高的数据服务。
4. 多表 Join 成本很高且 Join 逻辑稳定的场景。

不适合：

1. 需求变化非常频繁的探索式分析。
2. 字段组合不稳定、口径还没沉淀的早期场景。
3. 上游维度变化频繁且历史口径复杂的场景。

#### 六、面试时可以怎么总结

可以这样回答：宽表是把事实表和常用维度表提前关联打平形成的一张大表，核心目的是减少下游 Join、提升查询效率、降低使用成本。它适合高频、稳定、面向报表或数据服务的场景。但宽表也会带来数据冗余、维护成本高、字段膨胀和口径固化的问题，所以一般放在 ADS 层或特定应用层，而不是替代整个数仓建模体系。

#### 知识扩展

- ADS 层：宽表最常出现的应用层
- 星型模型：宽表可以看作星型模型的预 Join 结果
- 指标口径：宽表字段越多，越需要清晰口径说明
- 数据回刷：维度属性修正后，宽表可能需要重算
- 列式存储：宽表通常配合 Parquet、ORC、ClickHouse 等列式存储提升查询性能

### 2.5 什么是缓慢变化维 (SCD)？常见的 SCD Type 1、Type 2 是什么？

缓慢变化维 (Slowly Changing Dimension, SCD) 用来处理维度属性随时间变化的问题。所谓“缓慢”，不是说一定变化很慢，而是相对于事实事件来说，维度属性不是每秒高频变化，但它的变化会影响历史分析口径。

典型例子是用户会员等级、用户所在城市、商品类目、店铺归属区域等。

#### 一、为什么需要 SCD

假设一个用户 1 月份是普通会员，3 月份升级为 VIP。如果分析 1 月份订单时，应该按当时的普通会员统计，还是按当前的 VIP 统计？

不同业务有不同需求：

1. 如果只关心当前状态，可以覆盖更新。
2. 如果要按历史状态分析，就必须保留维度变化历史。

SCD 就是为了解决这个问题。

#### 二、SCD Type 1：覆盖更新

Type 1 的做法是直接用新值覆盖旧值，不保留历史。

例如用户城市从杭州改成上海：

```plaintext
user_id = 1001, city = 杭州
```

更新后：

```plaintext
user_id = 1001, city = 上海
```

优点：

1. 实现简单。
2. 查询方便。
3. 存储成本低。

缺点：

1. 无法追溯历史状态。
2. 历史报表可能随维度更新而变化。

适合：手机号、昵称、当前状态类字段，或者业务只关心最新值的场景。

#### 三、SCD Type 2：保留历史

Type 2 的做法是新增一条版本记录，保留旧值和新值，并通过生效时间、失效时间或当前标识区分版本。

例如：

```plaintext
user_id | city | start_date | end_date   | is_current
1001    | 杭州 | 2026-01-01 | 2026-03-10 | 0
1001    | 上海 | 2026-03-11 | 9999-12-31 | 1
```

查询事实表时，需要根据事实发生时间关联当时有效的维度版本。

```sql
SELECT
    f.order_id,
    f.order_time,
    d.city,
    f.pay_amount
FROM dwd_order_fact f
LEFT JOIN dim_user_scd d
    ON f.user_id = d.user_id
   AND f.order_time >= d.start_date
   AND f.order_time < d.end_date;
```

优点：

1. 可以保留历史变化。
2. 历史分析口径更准确。
3. 适合回溯分析。

缺点：

1. 存储成本更高。
2. 查询和维护更复杂。
3. 需要处理时间区间、版本冲突等问题。

#### 四、拉链表和 SCD Type 2 的关系

拉链表是实现 SCD Type 2 的常见方式。它通过开始日期和结束日期记录每条维度记录的有效区间，既能保存历史，又能避免每天保存全量快照造成过大冗余。

#### 五、面试时可以怎么总结

可以这样回答：缓慢变化维是用来处理维度属性变化的建模方法。Type 1 是直接覆盖旧值，只保留最新状态，实现简单但不能追溯历史；Type 2 是新增版本记录，通过生效时间和失效时间保留历史状态，适合需要按当时维度分析历史事实的场景。数仓中常用拉链表来实现 Type 2，比如用户等级、城市、商品类目变化都可以这样处理。

#### 知识扩展

- 拉链表：SCD Type 2 在离线数仓中的常见实现
- 快照表：每天保留一份全量状态，查询简单但存储更大
- 事实发生时间：关联历史维度版本时非常关键
- 数据回刷：维度历史修正后可能影响历史事实分析
- 维度一致性：公共维度变化要影响所有使用方

## 3. 指标体系

### 3.1 什么是指标？原子指标、派生指标、复合指标有什么区别？

指标是对业务过程进行量化描述的统计结果。它不是简单的字段，而是由业务口径、统计范围、统计周期、计算逻辑和维度共同定义出来的结果。

例如 GMV 不是一个天然存在的字段，它通常需要明确：统计哪些订单、是否包含未支付订单、是否扣除退款、时间按下单时间还是支付时间计算。

#### 一、什么是原子指标

原子指标是基于某个业务过程形成的最基础度量，通常不能再拆分成更基础的业务指标。

例如：

- 支付金额
- 下单次数
- 支付用户数
- 退款金额

原子指标一般来自事实表中的度量字段或事件统计。

#### 二、什么是派生指标

派生指标是在原子指标基础上增加统计周期、业务限定、维度修饰后形成的指标。

例如：

```plaintext
近 7 日新用户支付金额
昨日 App 端支付用户数
本月华东地区退款金额
```

其中“支付金额”是原子指标，“近 7 日”“新用户”“App 端”“华东地区”都是修饰条件。

#### 三、什么是复合指标

复合指标是由多个指标经过计算组合得到的指标。

例如：

```plaintext
客单价 = 支付金额 / 支付订单数
转化率 = 支付用户数 / 访问用户数
退款率 = 退款金额 / 支付金额
```

复合指标通常需要特别注意分子、分母的口径是否一致。

#### 四、一个例子：GMV

如果定义“昨日支付 GMV”，它至少包括：

1. 业务过程：支付成功
2. 原子指标：支付金额
3. 统计周期：昨日
4. 时间口径：支付时间
5. 过滤条件：排除测试订单、排除风控订单
6. 维度：可按渠道、城市、商品类目拆分

#### 五、面试时可以怎么总结

可以这样回答：指标是对业务过程的量化统计，不能只看字段名，还要明确业务口径、统计周期、过滤条件和维度。原子指标是最基础的度量，比如支付金额、订单数；派生指标是在原子指标上增加时间周期和修饰条件，比如近 7 日新用户支付金额；复合指标是由多个指标计算得到的，比如客单价、转化率。指标体系建设的核心是保证定义清晰、口径统一、可复用。

#### 知识扩展

- 指标字典：记录指标名称、口径、负责人和计算逻辑
- 统计周期：日、周、月、近 7 日等会影响指标含义
- 修饰维度：渠道、地区、端类型等决定派生指标范围
- DWS 层：常沉淀可复用的公共指标
- 数据血缘：帮助追踪指标从哪些表和字段加工而来

### 3.2 如何设计一个可靠的指标体系？

设计指标体系的目标不是把所有数字都列出来，而是围绕业务目标建立一套分层、统一、可解释、可落地的度量体系，让不同团队看同一套数字、用同一种口径讨论问题。

#### 一、从业务目标出发

指标体系首先要回答业务要达成什么目标。

例如电商业务可能关注：

1. 用户增长
2. 交易规模
3. 转化效率
4. 履约体验
5. 复购留存

不同目标对应不同指标树。

#### 二、拆解核心指标和过程指标

核心指标用于衡量最终结果，过程指标用于解释核心指标为什么变化。

例如 GMV 可以拆解为：

```plaintext
GMV = 访问用户数 * 下单转化率 * 支付转化率 * 客单价
```

这样当 GMV 下降时，可以进一步排查是流量减少、转化变差，还是客单价下降。

#### 三、明确指标口径

每个指标都要明确：

1. 指标名称
2. 业务含义
3. 计算公式
4. 数据来源
5. 统计周期
6. 过滤条件
7. 维度范围
8. 负责人

如果这些不明确，后续一定会出现口径争议。

#### 四、建设公共指标层

可靠的指标体系不能只停留在文档里，还要落到数仓模型和数据服务中。

常见做法是：

1. DWD 层沉淀标准明细事实。
2. DWS 层沉淀公共汇总指标。
3. ADS 层面向具体报表和应用。
4. 指标平台或指标字典管理口径。

#### 五、设计指标治理机制

指标上线后还需要治理：

1. 指标命名规范
2. 指标审批和变更流程
3. 指标下线机制
4. 指标血缘追踪
5. 数据质量监控
6. 权限和敏感数据管理

#### 六、面试时可以怎么总结

可以这样回答：设计可靠的指标体系要从业务目标出发，先确定核心指标，再拆解过程指标，形成指标树。每个指标都要定义清楚业务含义、计算公式、统计周期、过滤条件、数据来源和负责人。技术上要把指标沉淀到 DWD、DWS、ADS 等公共数据层中，而不是让每个报表重复计算。最后还要配合指标字典、血缘、质量校验和变更流程，保证指标长期可信。

#### 知识扩展

- 指标树：用于拆解核心指标和驱动因素
- One Metric That Matters：某阶段最关键的北极星指标
- 公共汇总层：指标复用的主要承载位置
- 指标平台：统一管理指标定义和服务
- 数据质量监控：保障指标结果稳定可信

### 3.3 为什么会出现指标口径不一致？如何治理？

指标口径不一致是数仓和数据平台中非常常见的问题，本质原因是不同团队在不同数据源、不同过滤条件、不同时间口径、不同业务理解下重复计算同一个指标。

#### 一、常见原因

##### 1. 数据来源不同

例如订单数可以来自订单表，也可以来自支付表，还可以来自埋点日志。如果没有统一定义，不同来源算出来的结果可能不同。

##### 2. 时间口径不同

同一个 GMV，有人按下单时间统计，有人按支付时间统计，有人按订单完成时间统计，结果一定不同。

##### 3. 过滤条件不同

是否排除测试订单、是否排除取消订单、是否扣除退款、是否包含内部用户，都会影响指标结果。

##### 4. 维度口径不同

例如“新用户”可以指注册新用户、首访新用户、首单新用户，业务含义不同。

##### 5. 重复开发

如果每个报表都自己写 SQL，指标逻辑散落在各个任务里，就很难保证一致。

#### 二、如何治理

##### 1. 建立统一指标字典

指标字典需要记录指标名称、业务解释、计算公式、数据来源、统计周期、过滤条件、负责人和变更记录。

##### 2. 建设公共数据层

将核心指标沉淀到 DWS 或指标层中，下游报表尽量复用公共结果，而不是重复从明细层计算。

##### 3. 统一维度和业务口径

例如统一用户、商品、渠道、地区等公共维度，避免同一个字段在不同主题中含义不同。

##### 4. 建立指标审批和变更机制

新增或修改核心指标时，需要经过业务和数据团队共同评审，避免随意定义。

##### 5. 做血缘和质量监控

通过血缘知道某个指标依赖哪些表和任务，通过质量监控发现指标异常波动。

#### 三、一个例子

“支付 GMV”的统一口径可以定义为：

```plaintext
统计对象：支付成功订单
时间口径：支付成功时间
金额口径：订单实付金额
过滤条件：排除测试订单、风控订单
退款处理：不实时扣减退款，退款金额单独统计
```

定义清楚后，下游所有报表都应复用该指标，而不是各自解释。

#### 四、面试时可以怎么总结

可以这样回答：指标口径不一致通常来自数据源不同、时间口径不同、过滤条件不同、维度定义不同以及重复开发。治理时不能只靠口头约定，而要建立指标字典，明确指标定义和负责人；同时在数仓公共层沉淀统一指标，推动下游复用；再配合血缘、质量监控和变更审批，保证指标从定义到计算再到使用都是统一的。

#### 知识扩展

- 指标字典：口径治理的基础
- 公共维度：保证维度拆分结果一致
- 数据血缘：帮助定位指标差异来源
- 数据质量：监控指标异常波动
- 语义层：把指标口径封装成统一查询服务

## 4. 数据质量与治理

### 4.1 数据仓库中常见的数据质量问题有哪些？如何保障数据质量？

数据质量是数据仓库可信的基础。如果数据不准确、不完整、不及时，即使模型设计再好，最终报表和决策也不可靠。

#### 一、常见数据质量问题

##### 1. 完整性问题

数据缺失、分区未产出、字段为空、上游同步不完整。

例如某天 `ods_order_info_di` 分区没有数据，导致下游订单报表为 0。

##### 2. 准确性问题

字段值不符合真实业务含义，或者计算逻辑错误。

例如支付金额使用了订单原价，而不是实付金额。

##### 3. 一致性问题

不同表、不同系统、不同报表中的同一指标结果不一致。

##### 4. 唯一性问题

主键重复、事件重复上报、增量同步重复写入。

##### 5. 及时性问题

数据延迟产出，导致报表不能按时刷新。

##### 6. 合法性问题

字段值超出合理范围，比如年龄为负数、订单金额小于 0、日期格式错误。

#### 二、如何保障数据质量

##### 1. 接入层校验

在 ODS 层检查数据是否按时到达、分区是否存在、记录数是否异常。

##### 2. 明细层校验

在 DWD 层检查主键唯一性、字段非空、枚举值合法性、金额范围等。

##### 3. 汇总层校验

在 DWS 和 ADS 层检查指标波动、上下游汇总一致性、环比同比异常。

##### 4. 任务调度监控

监控任务是否失败、是否延迟、是否依赖未完成。

##### 5. 告警和阻断机制

核心数据质量规则失败时，可以阻断下游任务或发送告警，避免错误数据继续扩散。

#### 三、常见质量规则示例

```sql
-- 检查订单明细表是否存在重复订单
SELECT
    order_id,
    COUNT(*) AS cnt
FROM dwd_trade_order_detail_di
WHERE dt = '2026-06-10'
GROUP BY order_id
HAVING COUNT(*) > 1;
```

如果结果不为空，说明订单粒度可能存在重复。

#### 四、面试时可以怎么总结

可以这样回答：数仓常见的数据质量问题包括完整性、准确性、一致性、唯一性、及时性和合法性。保障数据质量需要分层治理：ODS 层关注数据是否按时完整接入，DWD 层关注主键、空值、枚举和明细准确性，DWS/ADS 层关注指标波动和汇总一致性。同时要结合调度监控、质量规则、告警和阻断机制，避免问题数据扩散到报表和业务决策中。

#### 知识扩展

- 数据质量规则：非空、唯一、范围、波动、表间一致性
- 调度系统：质量校验通常嵌入任务依赖链路
- 数据血缘：质量问题发生后用于影响分析
- SLA：衡量数据是否按时产出的服务承诺
- 数据治理平台：统一管理规则、告警、血缘和权限

### 4.2 什么是元数据？技术元数据、业务元数据、操作元数据分别是什么？

元数据就是描述数据的数据。它不一定直接参与业务分析，但它描述了数据在哪里、是什么含义、怎么产生、谁在使用、运行是否正常。

在数据仓库中，元数据管理非常重要，因为数仓表多、字段多、任务多、依赖复杂，没有元数据就很难治理。

#### 一、技术元数据

技术元数据描述数据的技术结构。

常见内容包括：

1. 库名、表名、字段名、字段类型
2. 分区信息
3. 存储位置
4. 文件格式
5. 表大小、行数
6. 表之间的血缘依赖

例如：

```plaintext
表名：dwd_trade_order_detail_di
字段：order_id string, user_id string, pay_amount decimal
分区：dt
存储格式：Parquet
```

#### 二、业务元数据

业务元数据描述数据的业务含义。

常见内容包括：

1. 表的业务说明
2. 字段含义
3. 指标口径
4. 业务负责人
5. 数据使用场景
6. 敏感等级

例如 `pay_amount` 字段的业务定义是“用户实际支付金额，不包含退款扣减”，这就属于业务元数据。

#### 三、操作元数据

操作元数据描述数据生产和使用过程中的运行信息。

常见内容包括：

1. 任务运行状态
2. 开始时间、结束时间、耗时
3. 失败原因
4. 数据产出时间
5. 数据访问记录
6. 资源消耗

例如某个 ADS 任务今天运行失败、耗时 40 分钟、依赖 DWS 表未产出，这些都属于操作元数据。

#### 四、元数据有什么作用

1. 帮助开发者查找和理解表。
2. 支持数据血缘分析。
3. 支持影响分析和故障定位。
4. 支持权限治理和敏感数据管理。
5. 支持成本治理，识别长期无人使用的表。

#### 五、面试时可以怎么总结

可以这样回答：元数据是描述数据的数据。技术元数据描述表结构、字段类型、分区、存储位置和血缘；业务元数据描述字段含义、指标口径、业务负责人和使用场景；操作元数据描述任务运行状态、产出时间、失败原因和访问记录。元数据管理是数据治理的基础，它能帮助我们做数据查找、血缘分析、质量排查、权限控制和成本治理。

#### 知识扩展

- 数据目录：基于元数据帮助用户查找数据
- 血缘分析：依赖技术元数据和任务解析
- 指标平台：大量依赖业务元数据
- 权限治理：需要字段敏感等级和访问记录
- 数据资产管理：通过元数据衡量数据价值和使用情况

### 4.3 什么是数据血缘？它有什么作用？

数据血缘描述数据从哪里来、经过哪些加工、最终流向哪里。它记录了表、字段、任务、指标、报表之间的依赖关系。

简单说，血缘就是数据链路地图。

#### 一、数据血缘包括什么

常见血缘层次包括：

1. 表级血缘：表 A 生成表 B
2. 字段级血缘：字段 B.x 来自字段 A.y
3. 任务级血缘：某个调度任务依赖哪些上游任务
4. 指标血缘：某个指标依赖哪些表、字段和计算逻辑
5. 报表血缘：某个看板依赖哪些 ADS 表

#### 二、数据血缘有什么作用

##### 1. 故障定位

如果某个报表数据异常，可以沿着血缘向上追溯，找到是 ADS、DWS、DWD 还是 ODS 层出现问题。

##### 2. 影响分析

如果要修改某张 DWD 表的字段，可以通过血缘查看哪些下游任务、指标和报表会受影响。

##### 3. 数据质量治理

当上游质量规则失败时，可以通过血缘判断需要阻断哪些下游任务。

##### 4. 权限和审计

敏感字段如果从 ODS 流向 ADS 或报表，血缘可以帮助追踪它的传播路径。

##### 5. 成本治理

通过血缘和访问记录，可以识别无人使用但仍在生产的中间表。

#### 三、一个简单例子

```plaintext
ods_order_info_di
    -> dwd_trade_order_detail_di
        -> dws_user_trade_1d
            -> ads_user_value_report_1d
                -> 用户价值看板
```

如果用户价值看板数据异常，可以顺着这条链路逐层排查。

#### 四、血缘如何生成

常见方式包括：

1. 解析 SQL，识别输入表、输出表和字段表达式。
2. 从调度系统获取任务依赖。
3. 从数据集成工具获取同步链路。
4. 从 BI 系统获取报表和数据集关系。
5. 人工补充复杂逻辑或外部系统血缘。

#### 五、面试时可以怎么总结

可以这样回答：数据血缘描述数据从源头到最终应用的流转关系，包括表级、字段级、任务级、指标级和报表级血缘。它的主要作用是故障定位、影响分析、质量治理、权限审计和成本治理。比如某个报表异常时，可以沿着血缘从 ADS 一直追到 ODS，逐层定位问题；修改上游字段前，也可以通过血缘评估影响范围。

#### 知识扩展

- SQL 解析：自动生成字段级血缘的重要手段
- 调度依赖：任务级血缘的重要来源
- 元数据管理：血缘属于核心元数据
- 数据质量：血缘帮助定位质量问题影响范围
- 数据资产治理：血缘帮助识别核心表和无用表

### 4.4 数据权限治理一般怎么做？

数据权限治理的目标是在保证数据可用的同时，控制数据访问风险，尤其是涉及个人信息、经营敏感数据、财务数据时，需要做到最小权限、可审计、可追溯。

#### 一、常见权限粒度

##### 1. 库表权限

控制用户能否访问某个库或某张表。

例如普通运营人员只能访问 ADS 报表表，不能直接访问 ODS 原始用户表。

##### 2. 字段权限

控制用户能否访问某些敏感字段。

例如手机号、身份证号、银行卡号、详细地址等字段需要单独授权或脱敏。

##### 3. 行级权限

控制用户只能访问符合条件的数据行。

例如区域经理只能查看自己负责区域的数据。

##### 4. 操作权限

区分查询、写入、删除、导出、授权等操作。

#### 二、敏感数据治理

敏感字段通常需要分级分类，例如：

1. 公开数据
2. 内部数据
3. 敏感数据
4. 高敏数据

对高敏字段可以采用脱敏、加密、访问审批、导出限制等策略。

常见脱敏方式：

```plaintext
手机号：138****5678
身份证：110101********1234
姓名：张*
```

#### 三、权限申请和审批

生产环境中通常不会让用户随意访问所有数据，而是通过权限申请流程说明：

1. 申请人
2. 申请表和字段
3. 使用原因
4. 使用期限
5. 审批人
6. 是否允许导出

#### 四、审计与回收

权限治理不只是授权，还要能审计和回收。

需要记录：

1. 谁访问了什么数据
2. 什么时候访问
3. 查询了哪些字段
4. 是否导出
5. 是否访问敏感数据

长期未使用的权限应该定期回收。

#### 五、面试时可以怎么总结

可以这样回答：数据权限治理一般从库表、字段、行级和操作权限几个粒度来做。对手机号、身份证、地址等敏感字段，需要做分级分类、脱敏、审批和审计。实际落地时，要建立权限申请审批流程，控制访问期限和使用范围，同时记录访问日志，支持事后审计和定期权限回收。核心原则是最小权限、按需授权、可审计和可追溯。

#### 知识扩展

- 数据分级分类：权限治理的前置基础
- 字段脱敏：保护敏感信息的常见方式
- 行级权限：多区域、多租户场景非常常见
- 审计日志：用于安全追踪和合规检查
- 数据血缘：帮助追踪敏感字段流向

## 5. 离线数仓链路

### 5.1 一个离线数仓任务从数据接入到报表产出，完整链路是怎样的？

一个典型离线数仓链路通常包括数据接入、ODS 落地、DWD 清洗建模、DWS 汇总、ADS 应用层产出、数据质量校验、调度依赖和报表展示。

#### 一、完整链路

```plaintext
业务库/日志/第三方数据
        -> 数据接入
        -> ODS 原始层
        -> DWD 明细层
        -> DWS 汇总层
        -> ADS 应用层
        -> BI 报表/数据服务
```

#### 二、数据接入

数据来源可能包括：

1. MySQL 业务库
2. 日志埋点
3. Kafka 消息
4. 第三方接口
5. 文件上传

常见接入方式包括全量同步、增量同步、CDC、日志采集等。

#### 三、ODS 落地

ODS 层尽量保存原始数据，按日期或小时分区，方便追溯和重跑。

例如：

```plaintext
ods_order_info_di
ods_user_info_di
ods_app_log_di
```

#### 四、DWD 清洗建模

DWD 层会做去重、过滤、字段标准化、主键处理、业务过程建模。

例如：

```plaintext
dwd_trade_order_detail_di
dwd_user_register_di
dwd_page_view_di
```

#### 五、DWS 公共汇总

DWS 层按主题沉淀公共指标。

例如：

```plaintext
dws_user_trade_1d
dws_product_trade_1d
dws_channel_traffic_1d
```

#### 六、ADS 应用层

ADS 层面向具体报表或业务应用。

例如：

```plaintext
ads_boss_trade_dashboard_1d
ads_user_growth_dashboard_1d
```

#### 七、质量校验和调度

离线链路通常由调度系统按依赖顺序执行。每一层都可以设置质量校验，比如分区是否产出、数据量是否异常、关键字段是否为空、指标波动是否超阈值。

#### 八、面试时可以怎么总结

可以这样回答：一个离线数仓任务通常从业务库、日志或第三方系统接入数据，先落到 ODS 保留原始数据，再在 DWD 层做清洗和明细建模，然后在 DWS 层按主题做公共汇总，最后在 ADS 层生成面向报表或业务应用的数据。整个链路会由调度系统管理依赖，并配合数据质量校验和告警，保证数据按时、准确、可追溯地产出。

#### 知识扩展

- 数据接入：包括全量、增量、CDC、日志采集
- 数仓分层：离线链路的核心组织方式
- 调度系统：负责按依赖运行任务
- 数据质量：保障链路产出可信
- BI 工具：通常消费 ADS 层数据

### 5.2 全量同步和增量同步有什么区别？如何选择？

全量同步和增量同步是数据接入中的两种基本方式。全量同步每次同步完整数据集，增量同步只同步新增或变化的数据。

#### 一、全量同步是什么

全量同步是每次把源表当前全部数据同步到目标表。

适合：

1. 数据量较小的维度表。
2. 没有可靠更新时间字段的表。
3. 需要完整快照的场景。
4. 历史数据可能被修改但无法捕获增量的场景。

优点：

1. 逻辑简单。
2. 不容易漏数据。
3. 目标表和源表当前状态一致。

缺点：

1. 数据量大时成本高。
2. 同步时间长。
3. 对源库压力较大。

#### 二、增量同步是什么

增量同步只同步上次同步后新增或变化的数据。

常见方式：

1. 基于更新时间字段，例如 `update_time`
2. 基于自增 ID
3. 基于 binlog 或 CDC
4. 基于消息队列

适合：

1. 数据量大且每天变化比例较小的事实表。
2. 需要频繁同步的表。
3. 对源库压力敏感的场景。

优点：

1. 同步数据量小。
2. 效率高。
3. 对源库压力小。

缺点：

1. 实现复杂。
2. 可能漏掉物理删除或无更新时间的更新。
3. 需要处理重复、乱序和迟到变更。

#### 三、如何选择

一般原则：

1. 小表、维表、变化不大，可以全量同步。
2. 大表、事实表、持续增长表，优先增量同步。
3. 需要保留历史变化，可以用增量加拉链表。
4. 如果源表更新逻辑复杂，优先考虑 binlog CDC。

#### 四、订单表示例

订单表数据量很大，如果每天全量同步成本很高，通常会用增量同步：

```sql
SELECT *
FROM order_info
WHERE update_time >= '${last_sync_time}'
  AND update_time < '${current_sync_time}';
```

但要注意，如果源表存在物理删除，而 `update_time` 无法体现删除，就可能漏掉删除事件，此时 CDC 更可靠。

#### 五、面试时可以怎么总结

可以这样回答：全量同步是每次同步整张表，逻辑简单但成本高，适合小表、维表和快照场景；增量同步只同步新增或变化数据，效率高但实现更复杂，适合大表和事实表。选择时主要看数据量、变化比例、是否需要历史追踪、源表是否有可靠更新时间字段，以及是否能通过 binlog 或 CDC 捕获所有变更。

#### 知识扩展

- CDC：通过变更日志捕获插入、更新和删除
- 拉链表：常用增量数据维护维度历史
- 分区覆盖：离线同步中常用于按天重刷
- 幂等写入：增量同步必须考虑重复执行结果一致
- 数据校验：全量和增量都需要记录数、金额等对账

### 5.3 什么是分区表？为什么数仓中大量使用分区？

分区表是把一张逻辑表按照某些字段拆分成多个物理或逻辑分区存储的表。数仓中最常见的是按日期分区，比如 `dt`、`hour`。

#### 一、分区表的基本概念

例如订单明细表按日期分区：

```plaintext
dwd_trade_order_detail_di
  dt=2026-06-08
  dt=2026-06-09
  dt=2026-06-10
```

查询某一天数据时，只需要扫描对应分区，而不需要扫描整张表。

#### 二、为什么数仓大量使用分区

##### 1. 减少扫描数据量

大多数离线分析都带时间条件。按日期分区后，可以利用分区裁剪减少扫描范围。

```sql
SELECT
    SUM(pay_amount)
FROM dwd_trade_order_detail_di
WHERE dt = '2026-06-10';
```

这个查询只扫描 `dt=2026-06-10` 分区。

##### 2. 便于数据重跑和修复

如果某天数据错误，可以只重刷这一天分区，而不是重算整张表。

##### 3. 便于生命周期管理

可以按分区删除历史数据，例如只保留最近 2 年数据。

##### 4. 适合调度产出

离线任务通常每天产出一个分区，天然和调度周期匹配。

#### 三、常见分区方式

1. 按天分区：`dt`
2. 按小时分区：`dt` + `hour`
3. 按业务域分区：地区、渠道、租户
4. 多级分区：日期 + 小时 + 地区

最常见的是日期分区，因为时间是分析和调度中最稳定的边界。

#### 四、分区设计注意点

1. 分区字段要高频出现在查询条件中。
2. 分区粒度不能过细，否则会产生大量小文件。
3. 分区粒度不能过粗，否则分区裁剪效果差。
4. 不要把高基数字段随意作为分区字段，例如用户 ID。
5. 查询时必须带分区条件，否则容易全表扫描。

#### 五、面试时可以怎么总结

可以这样回答：分区表是按照某些字段把数据拆分到不同分区中存储，数仓中最常见的是按日期分区。使用分区的主要目的包括减少查询扫描量、提升性能、方便按天重跑修复、支持生命周期管理，并且和离线调度周期天然匹配。设计分区时要选择高频过滤字段，常见是 `dt`，同时避免分区过细导致小文件过多。

#### 知识扩展

- 分区裁剪：查询引擎根据分区条件跳过无关数据
- 小文件问题：分区过细或写入过散会导致性能下降
- 动态分区：批量写入多个分区时常用
- 生命周期管理：按分区删除过期数据
- Hive/Spark SQL：分区表是离线数仓最基础的表设计

### 5.4 Hive/Spark SQL 中如何进行常见的数仓性能优化？

Hive/Spark SQL 性能优化的核心思路是减少扫描数据量、减少 Shuffle、减少 Join 成本、避免数据倾斜，并让存储格式和执行引擎更好地配合。

#### 一、分区裁剪

查询时尽量带上分区条件，避免全表扫描。

```sql
SELECT
    SUM(pay_amount)
FROM dwd_trade_order_detail_di
WHERE dt = '2026-06-10';
```

如果不带 `dt`，可能会扫描整张历史表。

#### 二、列裁剪

只查询需要的字段，避免 `SELECT *`。

```sql
SELECT
    user_id,
    pay_amount
FROM dwd_trade_order_detail_di
WHERE dt = '2026-06-10';
```

对于 Parquet、ORC 这类列式存储，列裁剪可以显著减少 IO。

#### 三、选择合适的文件格式

数仓分析通常优先选择列式格式，比如 Parquet 或 ORC。

优点：

1. 支持列裁剪。
2. 压缩效果好。
3. 适合聚合查询。
4. 支持谓词下推。

#### 四、优化 Join

常见策略：

1. 小表广播 Join，避免大表 Shuffle。
2. 大表 Join 前先过滤无关分区和字段。
3. 避免多张大表直接 Join。
4. 预先建设宽表或汇总表。
5. 保证 Join Key 类型一致，避免隐式转换。

#### 五、处理数据倾斜

数据倾斜常见于热点 Key，例如某个默认值、未知城市、超级大客户。

优化方式：

1. 过滤异常热点值。
2. 对热点 Key 单独处理。
3. 加盐打散热点 Key。
4. 使用两阶段聚合。
5. 调整 Shuffle 分区数。

#### 六、小文件治理

小文件过多会导致 NameNode 压力、任务启动开销和读取开销增加。

常见治理方式：

1. 合并小文件。
2. 控制任务并行度。
3. 使用合理的分区粒度。
4. 写入后做 compact。

#### 七、减少重复计算

如果某些复杂逻辑被多个报表复用，应沉淀到 DWS 或 ADS 层，而不是每个报表都重复计算。

#### 八、面试时可以怎么总结

可以这样回答：Hive/Spark SQL 的数仓性能优化可以从几个方向入手：首先通过分区裁剪和列裁剪减少扫描数据量；其次使用 Parquet、ORC 等列式存储提升 IO 效率；然后优化 Join，比如小表广播、大表先过滤、必要时建设宽表；再处理数据倾斜，比如热点 Key 拆分、加盐和两阶段聚合；最后治理小文件和重复计算。核心目标是减少 IO、减少 Shuffle、减少 Join 成本。

#### 知识扩展

- Parquet/ORC：列式存储对 OLAP 查询非常重要
- Broadcast Join：小表 Join 大表的常见优化
- Shuffle：Spark SQL 性能瓶颈常来自 Shuffle
- 数据倾斜：聚合和 Join 中最常见的性能问题之一
- DWS/ADS：通过预聚合和宽表减少重复计算
