## 1. 数据仓库基础

### 1.1 什么是数据仓库？它和数据库、数据湖、湖仓一体有什么区别？

数据仓库 (Data Warehouse) 是面向分析场景的数据系统，它把来自业务数据库、日志系统、第三方系统等多个来源的数据进行集成、清洗、建模和沉淀，最终服务于报表分析、指标统计、经营决策、用户画像、数据产品等场景。

面试里可以先用一句话概括：数据仓库不是简单的数据存储，而是一套围绕分析决策构建的数据组织体系，它强调统一口径、历史沉淀、面向主题和高效查询。

#### 一、数据仓库的四个典型特征

##### 1. 面向主题 (Subject-Oriented)

业务数据库通常围绕业务流程设计，比如订单库、支付库、库存库。而数据仓库通常围绕分析主题组织，比如用户主题、商品主题、交易主题、流量主题。

例如，想分析“用户购买行为”，可能需要同时整合用户表、订单表、支付表、商品表和访问日志，这种跨系统分析就是数据仓库的典型价值。

##### 2. 集成 (Integrated)

数据仓库会把多个来源的数据统一编码、统一字段含义、统一时间格式、统一维度口径。

例如，不同系统中性别可能分别用 `M/F`、`1/0`、`男/女` 表示，进入数仓后需要统一成一套标准。

##### 3. 相对稳定 (Non-Volatile)

业务数据库中的数据会频繁增删改，而数仓更强调历史沉淀。数据进入数仓后，一般不会随意删除，而是通过分区、快照、拉链表等方式保留历史状态。

##### 4. 随时间变化 (Time-Variant)

数仓非常关注历史变化，通常会保留每天、每小时、每个版本的数据状态，用于趋势分析和同比环比分析。

#### 二、数据仓库和数据库的区别

数据库通常服务于 OLTP (Online Transaction Processing)，重点是高并发事务、增删改查、数据一致性和业务流程处理。

数据仓库通常服务于 OLAP (Online Analytical Processing)，重点是大规模数据分析、多维聚合、复杂查询和历史统计。

| 对比项  | 业务数据库            | 数据仓库                        |
| ---- | ---------------- | --------------------------- |
| 核心场景 | 交易处理             | 分析决策                        |
| 数据模型 | 范式化模型较多          | 维度建模较多                      |
| 查询特点 | 单条或少量记录查询        | 大范围扫描和聚合                    |
| 数据变化 | 高频增删改            | 批量写入、历史沉淀                   |
| 典型系统 | MySQL、PostgreSQL | Hive、Spark、ClickHouse、Doris |

#### 三、数据仓库和数据湖的区别

数据湖 (Data Lake) 更像一个低成本、开放格式的大规模数据存储，可以保存结构化、半结构化、非结构化数据，比如数据库表、日志、图片、音视频、JSON 文件等。

数据仓库更强调建模、治理和分析效率。数据湖强调“先存下来”，数据仓库强调“整理好再用”。

#### 四、湖仓一体是什么

湖仓一体 (Lakehouse) 试图结合数据湖和数据仓库的优点：既保留数据湖低成本、开放格式、支持多类型数据的能力，又提供类似数仓的事务能力、元数据管理、数据治理和高性能分析。

常见技术包括 Delta Lake、Apache Iceberg、Apache Hudi、Apache Paimon 等。

#### 五、面试时可以怎么总结

可以这样回答：数据仓库是面向分析决策的数据系统，它会把多个业务系统的数据经过集成、清洗、建模和沉淀，形成统一、稳定、可复用的数据资产。它和业务数据库的区别在于，数据库主要服务在线交易，强调事务和实时写入；数据仓库主要服务分析查询，强调历史数据、多维聚合和统一口径。数据湖更偏原始数据存储，湖仓一体则是在数据湖基础上补充事务、治理和分析能力，让数据湖也具备数仓化使用能力。

#### 知识扩展

- OLTP 与 OLAP：理解数据库和数仓差异的基础
- 数据湖：偏原始数据存储，适合低成本保存多类型数据
- 湖仓一体：在数据湖上增强事务、元数据和分析能力
- 维度建模：数仓面向分析查询的核心建模方法
- 数据治理：保证数仓数据可信、可管、可复用

### 1.2 为什么要建设数据仓库？数据仓库解决了什么问题？

建设数据仓库的核心原因是：企业的数据通常分散在多个业务系统中，直接基于业务库做分析会遇到口径不统一、查询影响线上业务、历史数据不完整、重复开发严重等问题。数据仓库通过统一采集、统一建模、统一指标和统一服务，把分散的数据变成可复用的数据资产。

#### 一、解决数据分散问题

业务系统通常按功能拆分，比如用户系统、订单系统、支付系统、物流系统、营销系统。单个系统只能回答局部问题，无法直接回答跨业务问题。

例如，要分析“某次促销活动带来的新用户购买转化”，需要同时关联：

- 用户注册数据
- 活动曝光数据
- 商品浏览数据
- 下单数据
- 支付数据
- 退款数据

这些数据如果不进入数仓，很难形成完整链路。

#### 二、解决指标口径不一致问题

不同团队可能会各自写 SQL 计算 GMV、订单数、活跃用户，导致过滤条件、时间口径、退款处理方式都不一样，最终出现“同一个指标多个数字”。

数仓通过公共层和指标体系统一口径，让业务方复用同一套指标定义。

#### 三、降低对业务库的影响

分析查询通常会扫描大量数据，如果直接在业务库上做复杂 Join、Group By 和历史统计，容易影响线上交易性能。数仓会把分析负载从业务库中剥离出来，保护核心业务系统。

#### 四、沉淀历史数据

业务库通常只保存当前状态，或者为了性能和成本定期归档。但分析场景经常需要看历史趋势，比如过去 180 天的用户等级变化、商品价格变化、订单转化趋势。

数仓可以通过分区表、快照表、拉链表等方式保存历史状态。

#### 五、提升数据开发复用性

如果没有数仓，每个报表都从 ODS 或业务库重新清洗和关联，会产生大量重复 SQL。数仓通过 DWD、DWS、ADS 等分层，把通用明细和汇总能力沉淀下来，减少重复建设。

#### 六、面试时可以怎么总结

可以这样回答：建设数据仓库主要是为了解决企业数据分散、口径不统一、历史不可追溯、分析影响业务库以及数据开发重复的问题。数仓会把不同业务系统的数据统一接入，再经过清洗、建模、汇总和指标管理，形成稳定可复用的数据资产。这样业务分析、报表、BI、经营决策和数据产品都可以基于统一的数据底座来构建。

#### 知识扩展

- 指标体系：解决同一指标多个口径的问题
- 数仓分层：通过层次化加工提升复用性和可维护性
- 数据质量：保证进入报表和决策的数据可信
- 调度系统：保障数据链路按时、按依赖稳定产出
- 数据服务：把数仓结果以 API、报表或查询引擎形式提供出去

### 1.3 数据仓库常见分层有哪些？ODS、DWD、DWS、ADS 分别负责什么？

数仓分层是数据仓库设计中非常核心的思想。它的目的不是为了把链路变复杂，而是为了让数据从原始到可用、从明细到汇总、从通用到业务应用逐层沉淀，降低重复开发，提高数据质量和复用性。

常见离线数仓分层包括 ODS、DWD、DWS、ADS，有些公司还会增加 DIM、DM、TMP 等层。

#### 一、ODS 层：原始数据层

ODS (Operational Data Store) 主要保存从业务系统同步过来的原始数据，尽量保持和源系统一致。

特点：

1. 数据粒度最细，通常是一张业务表对应一张 ODS 表。
2. 尽量少做业务加工，只做必要的格式转换、字段补充和分区落地。
3. 便于数据追溯，当下游出现问题时可以回到 ODS 排查。

例如：

```sql
ods_order_info_di
ods_user_info_di
ods_payment_info_di
```

#### 二、DWD 层：明细数据层

DWD (Data Warehouse Detail) 是清洗后的明细层，通常会对 ODS 数据进行去重、过滤脏数据、字段标准化、维度退化、统一口径、业务过程建模。

特点：

1. 仍然保持明细粒度。
2. 比 ODS 更干净、更规范。
3. 把维度表 join 进来，让下游不用再频繁 join 维度表
4. 通常围绕业务过程建设事实明细表。

例如，订单明细表可以保留一行一笔订单或一行一个订单商品明细：

```sql
dwd_trade_order_detail_di
dwd_user_register_di
dwd_payment_success_di
```

#### 三、DWS 层：汇总数据层

DWS (Data Warehouse Summary) 是公共汇总层，面向主题域进行轻度或中度汇总，沉淀可复用的统计结果。按照"主题 + 统计粒度"做轻度聚合，一般是 宽表，服务于多个报表复用。

特点：

1. 通常按照用户、商品、店铺、地区、日期等维度汇总。
2. 服务多个 ADS 应用，强调公共复用。
3. 适合沉淀通用指标，比如用户近 7 日下单金额、商品日销售额。
4. 这层是"通用积木"，不是给某一张报表用的，而是"用户维度""商品维度""地区维度"各自沉淀一张宽表，后面 ADS 层可以随意拼装，避免重复计算。

例如：

```sql
dws_user_trade_1d
dws_product_trade_1d
dws_shop_trade_1d
```

#### 四、ADS 层：应用数据层

ADS (Application Data Service) 是面向具体业务场景或报表的数据层，通常直接服务 BI 看板、数据接口、运营报表、推荐系统特征等。直接面向"某个具体报表/大屏/API"的强定制表

特点：

1. 面向具体应用，字段通常比较宽。
2. 查询性能要求高，常做预聚合和宽表设计。
3. 稳定性和口径一致性直接影响业务使用。
4. 直接从多张 DWS 宽表汇总 / 拼接得到，不再需要回头去查 DWD 甚至 ODS

例如：

```sql
ads_sales_dashboard_1d
ads_user_growth_report_1d
ads_coupon_effect_analysis_1d
```

#### 五、订单链路示例

以订单数据为例：

1. ODS 层保存原始订单表 `ods_order_info_di`
2. DWD 层清洗出订单明细事实表 `dwd_trade_order_detail_di`
3. DWS 层按用户、商品、店铺汇总出公共统计表
4. ADS 层生成老板看板、运营活动分析、用户价值分析等应用表

#### 六、面试时可以怎么总结

可以这样回答：数仓分层的核心目的是提升复用性、可维护性和数据质量。ODS 层保存原始业务数据，便于追溯；DWD 层做清洗和明细建模，形成标准明细事实；DWS 层按主题进行公共汇总，沉淀可复用指标；ADS 层面向具体报表和应用，提供最终查询结果。分层之后，下游不需要反复从原始数据加工，可以复用公共明细和汇总数据。

#### 知识扩展

- DIM 层：存放公共维度表，例如用户维度、商品维度
- 事实表：DWD 层常围绕业务过程建设事实明细
- 公共汇总：DWS 层的价值在于减少重复指标计算
- 宽表：ADS 层常通过宽表提升查询效率
- 调度依赖：分层越清晰，任务依赖和故障定位越容易管理
- DWS 和 ADS 的边界怎么划分：DWS 是"通用可复用的中间汇总"，ADS 是"为某个具体应用定制的最终结果"，如果一张 DWS 表只被一个报表用，那它其实该算 ADS

### 1.4 什么是 ETL 和 ELT？两者有什么区别，分别适合什么场景？

ETL 和 ELT 都是数据集成和数据加工链路中的常见模式，区别在于 Transform (转换加工) 发生在数据加载到目标系统之前还是之后。

#### 一、ETL 是什么

ETL 指 Extract、Transform、Load，也就是先抽取数据，再在中间处理环节完成清洗转换，最后加载到目标数据仓库。

流程如下：

```plaintext
业务系统 -> 抽取 -> 清洗转换 -> 加载到数仓
```

ETL 更常见于传统数据仓库时代，因为传统数仓存储和计算成本较高，通常希望在进入数仓前就把数据清洗好。

#### 二、ELT 是什么

ELT 指 Extract、Load、Transform，也就是先把数据抽取并加载到数据湖或数据仓库，再利用目标平台的计算能力进行转换加工。

流程如下：

```plaintext
业务系统 -> 抽取 -> 加载到数据湖/数仓 -> 清洗转换
```

在大数据和湖仓场景下，ELT 更常见，因为 HDFS、对象存储、Hive、Spark、Flink、Trino 等系统可以低成本存储大量原始数据，并在后续按需加工。

#### 三、ETL 和 ELT 的核心区别

| 对比项    | ETL             | ELT            |
| ------ | --------------- | -------------- |
| 转换时机   | 加载前转换           | 加载后转换          |
| 原始数据保留 | 可能不完整           | 通常完整保留         |
| 计算位置   | 中间 ETL 工具       | 目标数仓或数据湖       |
| 适合场景   | 传统数仓、强治理、入仓前标准化 | 大数据平台、湖仓、探索式分析 |
| 优点     | 入仓数据干净、质量可控     | 灵活、可追溯、适合大规模数据 |
| 缺点     | 原始细节可能丢失、扩展性较弱  | 对后续治理和存储管理要求更高 |

#### 四、典型场景选择

如果企业有强规范要求，比如金融报表、监管报送，可能更偏 ETL，因为入仓前就要完成严格校验和标准化。

如果企业的数据来源多、规模大、分析需求变化快，通常更适合 ELT，先把原始数据落到 ODS 或数据湖，再逐层加工。

#### 五、面试时可以怎么总结

可以这样回答：ETL 和 ELT 的区别主要在于数据转换发生的位置。ETL 是先抽取、再转换、最后加载，适合传统数仓和强治理场景；ELT 是先抽取并加载原始数据，再利用数仓或湖仓平台进行转换，适合大数据、数据湖和探索式分析场景。现在很多离线数仓会采用 ELT 思路，先把原始数据落到 ODS，再通过 DWD、DWS、ADS 分层加工。

#### 知识扩展

- ODS：ELT 模式下通常作为原始数据落地点
- 数据湖：天然适合先存储后加工的 ELT 模式
- 调度系统：负责串联抽取、加载、转换任务
- 数据质量：ETL 偏前置校验，ELT 偏入湖后分层校验
- CDC：增量抽取常用于 ETL/ELT 的数据接入环节

## 2. 数仓建模

### 2.1 什么是维度建模？为什么数仓里常用维度建模？

维度建模是一种面向分析查询的数据建模方法，它的核心思想是围绕业务过程构建事实表，再围绕分析视角构建维度表，让使用者可以从不同维度对事实指标进行统计分析。

面试里可以先说：维度建模不是为了减少数据冗余，而是为了让分析查询更直观、更高效、更贴近业务语言。

#### 一、维度建模的两个核心对象

##### 1. 事实表

事实表记录业务过程中发生的事件，通常包含度量值和维度外键。

例如订单事实表中，一笔订单就是一个业务事件，订单金额、支付金额、优惠金额就是度量。

##### 2. 维度表

维度表描述分析事实的角度，比如用户、商品、店铺、地区、时间。

例如分析订单金额时，可以按用户性别、商品类目、城市、日期等维度切分。

#### 二、为什么数仓常用维度建模

##### 1. 更适合 OLAP 查询

分析场景经常是按多个维度做聚合，比如“按城市和商品类目统计近 7 天销售额”。维度建模天然适合这种 Group By 和多维分析。

##### 2. 更容易被业务理解

事实和维度都来自业务语言，比高度范式化的数据库模型更容易解释。

##### 3. 查询链路更清晰

维度建模通常是事实表关联多个维度表，比复杂的三范式模型更适合报表开发和指标复用。

##### 4. 便于建设公共数据层

DWD 层可以沉淀标准事实表，DIM 层沉淀公共维度表，DWS 和 ADS 可以在此基础上复用加工。

#### 三、一个简单例子

```sql
-- 统计每天每个商品类目的支付金额
SELECT
    f.dt,
    p.category_name,
    SUM(f.pay_amount) AS pay_amount
FROM dwd_trade_order_detail_di f
LEFT JOIN dim_product_df p
    ON f.product_id = p.product_id
WHERE f.dt = '2026-06-10'
GROUP BY f.dt, p.category_name;
```

这里 `dwd_trade_order_detail_di` 是事实表，`dim_product_df` 是商品维度表，`pay_amount` 是度量，`category_name` 是分析维度。

#### 四、面试时可以怎么总结

可以这样回答：维度建模是数仓中面向分析场景的建模方法，它通过事实表记录业务过程，通过维度表描述分析角度。事实表负责回答发生了什么，维度表负责回答从哪些角度分析。数仓常用维度建模，是因为它更贴近 OLAP 查询模式，便于多维聚合、指标复用和业务理解。

#### 知识扩展

- 星型模型：事实表直接关联多个维度表，是维度建模最常见形态
- 雪花模型：维度进一步规范化拆分，减少冗余但增加 Join
- 总线矩阵：用于规划业务过程和公共维度
- 粒度：事实表设计中最关键的概念之一
- 指标体系：很多指标都基于事实表中的度量加工得到

### 2.2 事实表和维度表有什么区别？如何设计事实表和维度表？

事实表和维度表是维度建模中的两个核心概念。简单说，事实表记录业务事件和度量，维度表描述分析这些事件的角度。

#### 一、事实表是什么

事实表通常记录一个业务过程中的事实数据，比如下单、支付、退款、登录、浏览、点击。

事实表一般包含：

1. 业务主键或事件 ID
2. 维度外键，例如用户 ID、商品 ID、店铺 ID
3. 度量字段，例如订单金额、支付金额、浏览次数
4. 时间字段和分区字段

例如订单事实表：

```plaintext
order_id
user_id
product_id
shop_id
order_time
order_amount
pay_amount
dt
```

#### 二、维度表是什么

维度表用于描述事实发生时的上下文，比如用户是谁、商品属于哪个类目、店铺在哪个城市。

维度表一般包含：

1. 维度主键
2. 维度属性
3. 生效时间和失效时间 (如果需要保留历史)
4. 分区字段或版本字段

例如用户维度表：

```plaintext
user_id
gender
age_range
city
member_level
register_time
dt
```

#### 三、事实表和维度表的区别

| 对比项  | 事实表            | 维度表         |
| ---- | -------------- | ----------- |
| 描述对象 | 业务事件           | 分析角度        |
| 数据特点 | 行数多、增长快        | 行数相对少、变化慢   |
| 核心字段 | 度量值、维度外键       | 维度属性        |
| 典型例子 | 订单事实、支付事实、浏览事实 | 用户维、商品维、地区维 |
| 主要问题 | 粒度设计、数据量、去重    | 历史变化、属性一致性  |

#### 四、如何设计事实表

设计事实表最重要的是确定粒度。粒度决定一行数据代表什么。

例如订单场景中：

1. 一行一笔订单：适合订单级统计
2. 一行一个订单商品明细：适合商品销售分析
3. 一行一次支付事件：适合支付成功率分析

事实表设计时要注意：

1. 粒度必须清晰，不能混合订单级和商品级字段。
2. 度量字段尽量保持可加性，比如金额、次数。
3. 保留必要的维度外键，方便后续关联维度表。
4. 对重复事件、撤销事件、退款事件要有明确处理逻辑。

#### 五、如何设计维度表

维度表设计时要关注属性完整性和历史变化。

常见方法：

1. 高频使用的维度属性可以冗余到同一张维表中，减少 Join。
2. 对会变化的属性，比如用户等级、商品价格，要考虑是否保留历史。
3. 公共维度要统一建设，避免多个团队重复维护用户维、商品维。
4. 敏感字段要考虑脱敏和权限控制。

#### 六、面试时可以怎么总结

可以这样回答：事实表记录业务过程中发生的事件，比如订单、支付、浏览，核心是粒度和度量；维度表描述分析事实的角度，比如用户、商品、地区，核心是维度属性和历史变化。设计事实表时最重要的是先确定一行数据代表什么，再选择度量字段和维度外键；设计维度表时要保证属性统一、可复用，并处理好缓慢变化维问题。

#### 知识扩展

- 粒度：事实表设计的第一原则
- 可加性度量：决定指标能否跨维度汇总
- 退化维度：某些维度值直接保存在事实表中
- SCD：解决维度属性变化的建模方法
- 宽表：常把事实和维度属性预先打平成应用表

### 2.3 什么是星型模型和雪花模型？它们的优缺点是什么？

星型模型和雪花模型都是维度建模中的常见组织方式，区别在于维度表是否继续拆分规范化。

#### 一、星型模型是什么

星型模型是以事实表为中心，事实表直接关联多个维度表。结构像一颗星，事实表在中间，维度表围绕在四周。

例如订单分析模型：

```plaintext
              dim_user
                 |
dim_product -- fact_order -- dim_shop
                 |
              dim_date
```

特点是结构简单，查询时 Join 路径短，适合 OLAP 分析。

#### 二、雪花模型是什么

雪花模型是在星型模型基础上，把维度表进一步拆分成更规范的多级维度。

例如商品维度拆成商品表、品牌表、类目表：

```plaintext
fact_order -> dim_product -> dim_category
                         -> dim_brand
```

它的结构比星型模型更规范，冗余更少，但 Join 链路更长。

#### 三、星型模型的优缺点

优点：

1. 查询简单，事实表直接关联维度表。
2. Join 次数少，查询性能通常更好。
3. 更符合分析人员的理解方式。
4. 适合 BI 报表和自助分析。

缺点：

1. 维度属性冗余较多。
2. 维度更新时可能需要维护较宽的维表。
3. 对维度一致性治理要求较高。

#### 四、雪花模型的优缺点

优点：

1. 数据冗余少。
2. 维度结构更规范。
3. 适合维度层级复杂且复用要求高的场景。

缺点：

1. Join 链路更长，查询性能可能下降。
2. 使用理解成本更高。
3. 报表开发 SQL 更复杂。

#### 五、如何选择

在数仓分析场景中，通常优先选择星型模型，因为分析系统更关注查询效率和易用性，而不是极致减少冗余。

如果某些维度层级非常复杂，比如行政区划、商品多级类目、组织架构，也可以局部使用雪花模型。

#### 六、面试时可以怎么总结

可以这样回答：星型模型是事实表直接关联多个维度表，结构简单、查询效率高、适合 OLAP 分析；雪花模型是把维度表继续拆分成更规范的层级结构，冗余更少，但 Join 更多、查询复杂度更高。实际数仓中通常优先使用星型模型，在维度层级复杂或复用要求很强的场景下局部采用雪花模型。

#### 知识扩展

- 维度退化：把部分维度字段放入事实表，减少 Join
- 宽表设计：进一步把事实和维度打平，提高查询效率
- 数据冗余：星型模型用冗余换查询效率
- BI 查询：星型模型对 BI 工具更友好
- 维度一致性：公共维度建设决定模型复用效果

### 2.4 什么是宽表？宽表有什么优缺点？

宽表是把多个相关表中的字段预先关联、清洗、展开到一张字段较多的表中，供下游报表、分析或数据服务直接使用。它本质上是一种用存储冗余换查询效率和使用便利性的设计。

#### 一、宽表为什么常见

在数仓里，如果每个报表都实时关联事实表、用户维表、商品维表、店铺维表、地区维表，SQL 会很复杂，查询性能也可能较差。

宽表会提前把常用字段打平，例如订单宽表中同时包含：

- 订单字段：订单 ID、下单时间、支付金额
- 用户字段：用户性别、城市、会员等级
- 商品字段：商品类目、品牌、价格
- 店铺字段：店铺类型、店铺城市

这样下游查询时可以直接过滤和聚合。

#### 二、宽表示例

```sql
SELECT
    dt,
    user_id,
    user_city,
    member_level,
    product_id,
    category_name,
    brand_name,
    shop_id,
    pay_amount
FROM ads_trade_order_wide_1d
WHERE dt = '2026-06-10';
```

业务方要按城市、类目、会员等级分析支付金额时，不需要再写复杂 Join。

#### 三、宽表的优点

1. 查询效率高，减少运行时 Join。
2. 使用门槛低，业务分析人员更容易理解。
3. 口径相对固化，适合稳定报表。
4. 对高频查询场景友好，可以直接服务 BI 或接口。

#### 四、宽表的缺点

1. 数据冗余大，存储成本更高。
2. 字段很多，维护成本高。
3. 需求变化时可能频繁加字段。
4. 如果上游维度口径变化，宽表需要重新加工或回刷。
5. 不适合所有探索式分析，因为它已经预设了字段范围。

#### 五、什么时候适合用宽表

适合：

1. 查询频率高的报表或看板。
2. 维度和指标相对稳定的分析场景。
3. 对响应速度要求较高的数据服务。
4. 多表 Join 成本很高且 Join 逻辑稳定的场景。

不适合：

1. 需求变化非常频繁的探索式分析。
2. 字段组合不稳定、口径还没沉淀的早期场景。
3. 上游维度变化频繁且历史口径复杂的场景。

#### 六、面试时可以怎么总结

可以这样回答：宽表是把事实表和常用维度表提前关联打平形成的一张大表，核心目的是减少下游 Join、提升查询效率、降低使用成本。它适合高频、稳定、面向报表或数据服务的场景。但宽表也会带来数据冗余、维护成本高、字段膨胀和口径固化的问题，所以一般放在 ADS 层或特定应用层，而不是替代整个数仓建模体系。

#### 知识扩展

- ADS 层：宽表最常出现的应用层
- 星型模型：宽表可以看作星型模型的预 Join 结果
- 指标口径：宽表字段越多，越需要清晰口径说明
- 数据回刷：维度属性修正后，宽表可能需要重算
- 列式存储：宽表通常配合 Parquet、ORC、ClickHouse 等列式存储提升查询性能

### 2.5 什么是缓慢变化维 (SCD)？常见的 SCD Type 1、Type 2 是什么？

缓慢变化维 (Slowly Changing Dimension, SCD) 用来处理维度属性随时间变化的问题。所谓“缓慢”，不是说一定变化很慢，而是相对于事实事件来说，维度属性不是每秒高频变化，但它的变化会影响历史分析口径。

典型例子是用户会员等级、用户所在城市、商品类目、店铺归属区域等。

#### 一、为什么需要 SCD

假设一个用户 1 月份是普通会员，3 月份升级为 VIP。如果分析 1 月份订单时，应该按当时的普通会员统计，还是按当前的 VIP 统计？

不同业务有不同需求：

1. 如果只关心当前状态，可以覆盖更新。
2. 如果要按历史状态分析，就必须保留维度变化历史。

SCD 就是为了解决这个问题。

#### 二、SCD Type 1：覆盖更新

Type 1 的做法是直接用新值覆盖旧值，不保留历史。

例如用户城市从杭州改成上海：

```plaintext
user_id = 1001, city = 杭州
```

更新后：

```plaintext
user_id = 1001, city = 上海
```

优点：

1. 实现简单。
2. 查询方便。
3. 存储成本低。

缺点：

1. 无法追溯历史状态。
2. 历史报表可能随维度更新而变化。

适合：手机号、昵称、当前状态类字段，或者业务只关心最新值的场景。

#### 三、SCD Type 2：保留历史

Type 2 的做法是新增一条版本记录，保留旧值和新值，并通过生效时间、失效时间或当前标识区分版本。

例如：

```plaintext
user_id | city | start_date | end_date   | is_current
1001    | 杭州 | 2026-01-01 | 2026-03-10 | 0
1001    | 上海 | 2026-03-11 | 9999-12-31 | 1
```

查询事实表时，需要根据事实发生时间关联当时有效的维度版本。

```sql
SELECT
    f.order_id,
    f.order_time,
    d.city,
    f.pay_amount
FROM dwd_order_fact f
LEFT JOIN dim_user_scd d
    ON f.user_id = d.user_id
   AND f.order_time >= d.start_date
   AND f.order_time < d.end_date;
```

优点：

1. 可以保留历史变化。
2. 历史分析口径更准确。
3. 适合回溯分析。

缺点：

1. 存储成本更高。
2. 查询和维护更复杂。
3. 需要处理时间区间、版本冲突等问题。

#### 四、拉链表和 SCD Type 2 的关系

拉链表是实现 SCD Type 2 的常见方式。它通过开始日期和结束日期记录每条维度记录的有效区间，既能保存历史，又能避免每天保存全量快照造成过大冗余。

#### 五、面试时可以怎么总结

可以这样回答：缓慢变化维是用来处理维度属性变化的建模方法。Type 1 是直接覆盖旧值，只保留最新状态，实现简单但不能追溯历史；Type 2 是新增版本记录，通过生效时间和失效时间保留历史状态，适合需要按当时维度分析历史事实的场景。数仓中常用拉链表来实现 Type 2，比如用户等级、城市、商品类目变化都可以这样处理。

#### 知识扩展

- 拉链表：SCD Type 2 在离线数仓中的常见实现
- 快照表：每天保留一份全量状态，查询简单但存储更大
- 事实发生时间：关联历史维度版本时非常关键
- 数据回刷：维度历史修正后可能影响历史事实分析
- 维度一致性：公共维度变化要影响所有使用方

## 3. 指标体系

### 3.1 什么是指标？原子指标、派生指标、复合指标有什么区别？

指标是对业务过程进行量化描述的统计结果。它不是简单的字段，而是由业务口径、统计范围、统计周期、计算逻辑和维度共同定义出来的结果。

例如 GMV 不是一个天然存在的字段，它通常需要明确：统计哪些订单、是否包含未支付订单、是否扣除退款、时间按下单时间还是支付时间计算。

#### 一、什么是原子指标

原子指标是基于某个业务过程形成的最基础度量，通常不能再拆分成更基础的业务指标。

例如：

- 支付金额
- 下单次数
- 支付用户数
- 退款金额

原子指标一般来自事实表中的度量字段或事件统计。

#### 二、什么是派生指标

派生指标是在原子指标基础上增加统计周期、业务限定、维度修饰后形成的指标。

例如：

```plaintext
近 7 日新用户支付金额
昨日 App 端支付用户数
本月华东地区退款金额
```

其中“支付金额”是原子指标，“近 7 日”“新用户”“App 端”“华东地区”都是修饰条件。

#### 三、什么是复合指标

复合指标是由多个指标经过计算组合得到的指标。

例如：

```plaintext
客单价 = 支付金额 / 支付订单数
转化率 = 支付用户数 / 访问用户数
退款率 = 退款金额 / 支付金额
```

复合指标通常需要特别注意分子、分母的口径是否一致。

#### 四、一个例子：GMV

如果定义“昨日支付 GMV”，它至少包括：

1. 业务过程：支付成功
2. 原子指标：支付金额
3. 统计周期：昨日
4. 时间口径：支付时间
5. 过滤条件：排除测试订单、排除风控订单
6. 维度：可按渠道、城市、商品类目拆分

#### 五、面试时可以怎么总结

可以这样回答：指标是对业务过程的量化统计，不能只看字段名，还要明确业务口径、统计周期、过滤条件和维度。原子指标是最基础的度量，比如支付金额、订单数；派生指标是在原子指标上增加时间周期和修饰条件，比如近 7 日新用户支付金额；复合指标是由多个指标计算得到的，比如客单价、转化率。指标体系建设的核心是保证定义清晰、口径统一、可复用。

#### 知识扩展

- 指标字典：记录指标名称、口径、负责人和计算逻辑
- 统计周期：日、周、月、近 7 日等会影响指标含义
- 修饰维度：渠道、地区、端类型等决定派生指标范围
- DWS 层：常沉淀可复用的公共指标
- 数据血缘：帮助追踪指标从哪些表和字段加工而来

### 3.2 如何设计一个可靠的指标体系？

设计指标体系的目标不是把所有数字都列出来，而是围绕业务目标建立一套分层、统一、可解释、可落地的度量体系，让不同团队看同一套数字、用同一种口径讨论问题。

#### 一、从业务目标出发

指标体系首先要回答业务要达成什么目标。

例如电商业务可能关注：

1. 用户增长
2. 交易规模
3. 转化效率
4. 履约体验
5. 复购留存

不同目标对应不同指标树。

#### 二、拆解核心指标和过程指标

核心指标用于衡量最终结果，过程指标用于解释核心指标为什么变化。

例如 GMV 可以拆解为：

```plaintext
GMV = 访问用户数 * 下单转化率 * 支付转化率 * 客单价
```

这样当 GMV 下降时，可以进一步排查是流量减少、转化变差，还是客单价下降。

#### 三、明确指标口径

每个指标都要明确：

1. 指标名称
2. 业务含义
3. 计算公式
4. 数据来源
5. 统计周期
6. 过滤条件
7. 维度范围
8. 负责人

如果这些不明确，后续一定会出现口径争议。

#### 四、建设公共指标层

可靠的指标体系不能只停留在文档里，还要落到数仓模型和数据服务中。

常见做法是：

1. DWD 层沉淀标准明细事实。
2. DWS 层沉淀公共汇总指标。
3. ADS 层面向具体报表和应用。
4. 指标平台或指标字典管理口径。

#### 五、设计指标治理机制

指标上线后还需要治理：

1. 指标命名规范
2. 指标审批和变更流程
3. 指标下线机制
4. 指标血缘追踪
5. 数据质量监控
6. 权限和敏感数据管理

#### 六、面试时可以怎么总结

可以这样回答：设计可靠的指标体系要从业务目标出发，先确定核心指标，再拆解过程指标，形成指标树。每个指标都要定义清楚业务含义、计算公式、统计周期、过滤条件、数据来源和负责人。技术上要把指标沉淀到 DWD、DWS、ADS 等公共数据层中，而不是让每个报表重复计算。最后还要配合指标字典、血缘、质量校验和变更流程，保证指标长期可信。

#### 知识扩展

- 指标树：用于拆解核心指标和驱动因素
- One Metric That Matters：某阶段最关键的北极星指标
- 公共汇总层：指标复用的主要承载位置
- 指标平台：统一管理指标定义和服务
- 数据质量监控：保障指标结果稳定可信

### 3.3 为什么会出现指标口径不一致？如何治理？

指标口径不一致是数仓和数据平台中非常常见的问题，本质原因是不同团队在不同数据源、不同过滤条件、不同时间口径、不同业务理解下重复计算同一个指标。

#### 一、常见原因

##### 1. 数据来源不同

例如订单数可以来自订单表，也可以来自支付表，还可以来自埋点日志。如果没有统一定义，不同来源算出来的结果可能不同。

##### 2. 时间口径不同

同一个 GMV，有人按下单时间统计，有人按支付时间统计，有人按订单完成时间统计，结果一定不同。

##### 3. 过滤条件不同

是否排除测试订单、是否排除取消订单、是否扣除退款、是否包含内部用户，都会影响指标结果。

##### 4. 维度口径不同

例如“新用户”可以指注册新用户、首访新用户、首单新用户，业务含义不同。

##### 5. 重复开发

如果每个报表都自己写 SQL，指标逻辑散落在各个任务里，就很难保证一致。

#### 二、如何治理

##### 1. 建立统一指标字典

指标字典需要记录指标名称、业务解释、计算公式、数据来源、统计周期、过滤条件、负责人和变更记录。

##### 2. 建设公共数据层

将核心指标沉淀到 DWS 或指标层中，下游报表尽量复用公共结果，而不是重复从明细层计算。

##### 3. 统一维度和业务口径

例如统一用户、商品、渠道、地区等公共维度，避免同一个字段在不同主题中含义不同。

##### 4. 建立指标审批和变更机制

新增或修改核心指标时，需要经过业务和数据团队共同评审，避免随意定义。

##### 5. 做血缘和质量监控

通过血缘知道某个指标依赖哪些表和任务，通过质量监控发现指标异常波动。

#### 三、一个例子

“支付 GMV”的统一口径可以定义为：

```plaintext
统计对象：支付成功订单
时间口径：支付成功时间
金额口径：订单实付金额
过滤条件：排除测试订单、风控订单
退款处理：不实时扣减退款，退款金额单独统计
```

定义清楚后，下游所有报表都应复用该指标，而不是各自解释。

#### 四、面试时可以怎么总结

可以这样回答：指标口径不一致通常来自数据源不同、时间口径不同、过滤条件不同、维度定义不同以及重复开发。治理时不能只靠口头约定，而要建立指标字典，明确指标定义和负责人；同时在数仓公共层沉淀统一指标，推动下游复用；再配合血缘、质量监控和变更审批，保证指标从定义到计算再到使用都是统一的。

#### 知识扩展

- 指标字典：口径治理的基础
- 公共维度：保证维度拆分结果一致
- 数据血缘：帮助定位指标差异来源
- 数据质量：监控指标异常波动
- 语义层：把指标口径封装成统一查询服务

## 4. 数据质量与治理

### 4.1 数据仓库中常见的数据质量问题有哪些？如何保障数据质量？

数据质量是数据仓库可信的基础。如果数据不准确、不完整、不及时，即使模型设计再好，最终报表和决策也不可靠。

#### 一、常见数据质量问题

##### 1. 完整性问题

数据缺失、分区未产出、字段为空、上游同步不完整。

例如某天 `ods_order_info_di` 分区没有数据，导致下游订单报表为 0。

##### 2. 准确性问题

字段值不符合真实业务含义，或者计算逻辑错误。

例如支付金额使用了订单原价，而不是实付金额。

##### 3. 一致性问题

不同表、不同系统、不同报表中的同一指标结果不一致。

##### 4. 唯一性问题

主键重复、事件重复上报、增量同步重复写入。

##### 5. 及时性问题

数据延迟产出，导致报表不能按时刷新。

##### 6. 合法性问题

字段值超出合理范围，比如年龄为负数、订单金额小于 0、日期格式错误。

#### 二、如何保障数据质量

##### 1. 接入层校验

在 ODS 层检查数据是否按时到达、分区是否存在、记录数是否异常。

##### 2. 明细层校验

在 DWD 层检查主键唯一性、字段非空、枚举值合法性、金额范围等。

##### 3. 汇总层校验

在 DWS 和 ADS 层检查指标波动、上下游汇总一致性、环比同比异常。

##### 4. 任务调度监控

监控任务是否失败、是否延迟、是否依赖未完成。

##### 5. 告警和阻断机制

核心数据质量规则失败时，可以阻断下游任务或发送告警，避免错误数据继续扩散。

#### 三、常见质量规则示例

```sql
-- 检查订单明细表是否存在重复订单
SELECT
    order_id,
    COUNT(*) AS cnt
FROM dwd_trade_order_detail_di
WHERE dt = '2026-06-10'
GROUP BY order_id
HAVING COUNT(*) > 1;
```

如果结果不为空，说明订单粒度可能存在重复。

#### 四、面试时可以怎么总结

可以这样回答：数仓常见的数据质量问题包括完整性、准确性、一致性、唯一性、及时性和合法性。保障数据质量需要分层治理：ODS 层关注数据是否按时完整接入，DWD 层关注主键、空值、枚举和明细准确性，DWS/ADS 层关注指标波动和汇总一致性。同时要结合调度监控、质量规则、告警和阻断机制，避免问题数据扩散到报表和业务决策中。

#### 知识扩展

- 数据质量规则：非空、唯一、范围、波动、表间一致性
- 调度系统：质量校验通常嵌入任务依赖链路
- 数据血缘：质量问题发生后用于影响分析
- SLA：衡量数据是否按时产出的服务承诺
- 数据治理平台：统一管理规则、告警、血缘和权限

### 4.2 什么是元数据？技术元数据、业务元数据、操作元数据分别是什么？

元数据就是描述数据的数据。它不一定直接参与业务分析，但它描述了数据在哪里、是什么含义、怎么产生、谁在使用、运行是否正常。

在数据仓库中，元数据管理非常重要，因为数仓表多、字段多、任务多、依赖复杂，没有元数据就很难治理。

#### 一、技术元数据

技术元数据描述数据的技术结构。

常见内容包括：

1. 库名、表名、字段名、字段类型
2. 分区信息
3. 存储位置
4. 文件格式
5. 表大小、行数
6. 表之间的血缘依赖

例如：

```plaintext
表名：dwd_trade_order_detail_di
字段：order_id string, user_id string, pay_amount decimal
分区：dt
存储格式：Parquet
```

#### 二、业务元数据

业务元数据描述数据的业务含义。

常见内容包括：

1. 表的业务说明
2. 字段含义
3. 指标口径
4. 业务负责人
5. 数据使用场景
6. 敏感等级

例如 `pay_amount` 字段的业务定义是“用户实际支付金额，不包含退款扣减”，这就属于业务元数据。

#### 三、操作元数据

操作元数据描述数据生产和使用过程中的运行信息。

常见内容包括：

1. 任务运行状态
2. 开始时间、结束时间、耗时
3. 失败原因
4. 数据产出时间
5. 数据访问记录
6. 资源消耗

例如某个 ADS 任务今天运行失败、耗时 40 分钟、依赖 DWS 表未产出，这些都属于操作元数据。

#### 四、元数据有什么作用

1. 帮助开发者查找和理解表。
2. 支持数据血缘分析。
3. 支持影响分析和故障定位。
4. 支持权限治理和敏感数据管理。
5. 支持成本治理，识别长期无人使用的表。

#### 五、面试时可以怎么总结

可以这样回答：元数据是描述数据的数据。技术元数据描述表结构、字段类型、分区、存储位置和血缘；业务元数据描述字段含义、指标口径、业务负责人和使用场景；操作元数据描述任务运行状态、产出时间、失败原因和访问记录。元数据管理是数据治理的基础，它能帮助我们做数据查找、血缘分析、质量排查、权限控制和成本治理。

#### 知识扩展

- 数据目录：基于元数据帮助用户查找数据
- 血缘分析：依赖技术元数据和任务解析
- 指标平台：大量依赖业务元数据
- 权限治理：需要字段敏感等级和访问记录
- 数据资产管理：通过元数据衡量数据价值和使用情况

### 4.3 什么是数据血缘？它有什么作用？

数据血缘描述数据从哪里来、经过哪些加工、最终流向哪里。它记录了表、字段、任务、指标、报表之间的依赖关系。

简单说，血缘就是数据链路地图。

#### 一、数据血缘包括什么

常见血缘层次包括：

1. 表级血缘：表 A 生成表 B
2. 字段级血缘：字段 B.x 来自字段 A.y
3. 任务级血缘：某个调度任务依赖哪些上游任务
4. 指标血缘：某个指标依赖哪些表、字段和计算逻辑
5. 报表血缘：某个看板依赖哪些 ADS 表

#### 二、数据血缘有什么作用

##### 1. 故障定位

如果某个报表数据异常，可以沿着血缘向上追溯，找到是 ADS、DWS、DWD 还是 ODS 层出现问题。

##### 2. 影响分析

如果要修改某张 DWD 表的字段，可以通过血缘查看哪些下游任务、指标和报表会受影响。

##### 3. 数据质量治理

当上游质量规则失败时，可以通过血缘判断需要阻断哪些下游任务。

##### 4. 权限和审计

敏感字段如果从 ODS 流向 ADS 或报表，血缘可以帮助追踪它的传播路径。

##### 5. 成本治理

通过血缘和访问记录，可以识别无人使用但仍在生产的中间表。

#### 三、一个简单例子

```plaintext
ods_order_info_di
    -> dwd_trade_order_detail_di
        -> dws_user_trade_1d
            -> ads_user_value_report_1d
                -> 用户价值看板
```

如果用户价值看板数据异常，可以顺着这条链路逐层排查。

#### 四、血缘如何生成

常见方式包括：

1. 解析 SQL，识别输入表、输出表和字段表达式。
2. 从调度系统获取任务依赖。
3. 从数据集成工具获取同步链路。
4. 从 BI 系统获取报表和数据集关系。
5. 人工补充复杂逻辑或外部系统血缘。

#### 五、面试时可以怎么总结

可以这样回答：数据血缘描述数据从源头到最终应用的流转关系，包括表级、字段级、任务级、指标级和报表级血缘。它的主要作用是故障定位、影响分析、质量治理、权限审计和成本治理。比如某个报表异常时，可以沿着血缘从 ADS 一直追到 ODS，逐层定位问题；修改上游字段前，也可以通过血缘评估影响范围。

#### 知识扩展

- SQL 解析：自动生成字段级血缘的重要手段
- 调度依赖：任务级血缘的重要来源
- 元数据管理：血缘属于核心元数据
- 数据质量：血缘帮助定位质量问题影响范围
- 数据资产治理：血缘帮助识别核心表和无用表

### 4.4 数据权限治理一般怎么做？

数据权限治理的目标是在保证数据可用的同时，控制数据访问风险，尤其是涉及个人信息、经营敏感数据、财务数据时，需要做到最小权限、可审计、可追溯。

#### 一、常见权限粒度

##### 1. 库表权限

控制用户能否访问某个库或某张表。

例如普通运营人员只能访问 ADS 报表表，不能直接访问 ODS 原始用户表。

##### 2. 字段权限

控制用户能否访问某些敏感字段。

例如手机号、身份证号、银行卡号、详细地址等字段需要单独授权或脱敏。

##### 3. 行级权限

控制用户只能访问符合条件的数据行。

例如区域经理只能查看自己负责区域的数据。

##### 4. 操作权限

区分查询、写入、删除、导出、授权等操作。

#### 二、敏感数据治理

敏感字段通常需要分级分类，例如：

1. 公开数据
2. 内部数据
3. 敏感数据
4. 高敏数据

对高敏字段可以采用脱敏、加密、访问审批、导出限制等策略。

常见脱敏方式：

```plaintext
手机号：138****5678
身份证：110101********1234
姓名：张*
```

#### 三、权限申请和审批

生产环境中通常不会让用户随意访问所有数据，而是通过权限申请流程说明：

1. 申请人
2. 申请表和字段
3. 使用原因
4. 使用期限
5. 审批人
6. 是否允许导出

#### 四、审计与回收

权限治理不只是授权，还要能审计和回收。

需要记录：

1. 谁访问了什么数据
2. 什么时候访问
3. 查询了哪些字段
4. 是否导出
5. 是否访问敏感数据

长期未使用的权限应该定期回收。

#### 五、面试时可以怎么总结

可以这样回答：数据权限治理一般从库表、字段、行级和操作权限几个粒度来做。对手机号、身份证、地址等敏感字段，需要做分级分类、脱敏、审批和审计。实际落地时，要建立权限申请审批流程，控制访问期限和使用范围，同时记录访问日志，支持事后审计和定期权限回收。核心原则是最小权限、按需授权、可审计和可追溯。

#### 知识扩展

- 数据分级分类：权限治理的前置基础
- 字段脱敏：保护敏感信息的常见方式
- 行级权限：多区域、多租户场景非常常见
- 审计日志：用于安全追踪和合规检查
- 数据血缘：帮助追踪敏感字段流向

## 5. 离线数仓链路

### 5.1 一个离线数仓任务从数据接入到报表产出，完整链路是怎样的？

一个典型离线数仓链路通常包括数据接入、ODS 落地、DWD 清洗建模、DWS 汇总、ADS 应用层产出、数据质量校验、调度依赖和报表展示。

#### 一、完整链路

```plaintext
业务库/日志/第三方数据
        -> 数据接入
        -> ODS 原始层
        -> DWD 明细层
        -> DWS 汇总层
        -> ADS 应用层
        -> BI 报表/数据服务
```

#### 二、数据接入

数据来源可能包括：

1. MySQL 业务库
2. 日志埋点
3. Kafka 消息
4. 第三方接口
5. 文件上传

常见接入方式包括全量同步、增量同步、CDC、日志采集等。

#### 三、ODS 落地

ODS 层尽量保存原始数据，按日期或小时分区，方便追溯和重跑。

例如：

```plaintext
ods_order_info_di
ods_user_info_di
ods_app_log_di
```

#### 四、DWD 清洗建模

DWD 层会做去重、过滤、字段标准化、主键处理、业务过程建模。

例如：

```plaintext
dwd_trade_order_detail_di
dwd_user_register_di
dwd_page_view_di
```

#### 五、DWS 公共汇总

DWS 层按主题沉淀公共指标。

例如：

```plaintext
dws_user_trade_1d
dws_product_trade_1d
dws_channel_traffic_1d
```

#### 六、ADS 应用层

ADS 层面向具体报表或业务应用。

例如：

```plaintext
ads_boss_trade_dashboard_1d
ads_user_growth_dashboard_1d
```

#### 七、质量校验和调度

离线链路通常由调度系统按依赖顺序执行。每一层都可以设置质量校验，比如分区是否产出、数据量是否异常、关键字段是否为空、指标波动是否超阈值。

#### 八、面试时可以怎么总结

可以这样回答：一个离线数仓任务通常从业务库、日志或第三方系统接入数据，先落到 ODS 保留原始数据，再在 DWD 层做清洗和明细建模，然后在 DWS 层按主题做公共汇总，最后在 ADS 层生成面向报表或业务应用的数据。整个链路会由调度系统管理依赖，并配合数据质量校验和告警，保证数据按时、准确、可追溯地产出。

#### 知识扩展

- 数据接入：包括全量、增量、CDC、日志采集
- 数仓分层：离线链路的核心组织方式
- 调度系统：负责按依赖运行任务
- 数据质量：保障链路产出可信
- BI 工具：通常消费 ADS 层数据

### 5.2 全量同步和增量同步有什么区别？如何选择？

全量同步和增量同步是数据接入中的两种基本方式。全量同步每次同步完整数据集，增量同步只同步新增或变化的数据。

#### 一、全量同步是什么

全量同步是每次把源表当前全部数据同步到目标表。

适合：

1. 数据量较小的维度表。
2. 没有可靠更新时间字段的表。
3. 需要完整快照的场景。
4. 历史数据可能被修改但无法捕获增量的场景。

优点：

1. 逻辑简单。
2. 不容易漏数据。
3. 目标表和源表当前状态一致。

缺点：

1. 数据量大时成本高。
2. 同步时间长。
3. 对源库压力较大。

#### 二、增量同步是什么

增量同步只同步上次同步后新增或变化的数据。

常见方式：

1. 基于更新时间字段，例如 `update_time`
2. 基于自增 ID
3. 基于 binlog 或 CDC
4. 基于消息队列

适合：

1. 数据量大且每天变化比例较小的事实表。
2. 需要频繁同步的表。
3. 对源库压力敏感的场景。

优点：

1. 同步数据量小。
2. 效率高。
3. 对源库压力小。

缺点：

1. 实现复杂。
2. 可能漏掉物理删除或无更新时间的更新。
3. 需要处理重复、乱序和迟到变更。

#### 三、如何选择

一般原则：

1. 小表、维表、变化不大，可以全量同步。
2. 大表、事实表、持续增长表，优先增量同步。
3. 需要保留历史变化，可以用增量加拉链表。
4. 如果源表更新逻辑复杂，优先考虑 binlog CDC。

#### 四、订单表示例

订单表数据量很大，如果每天全量同步成本很高，通常会用增量同步：

```sql
SELECT *
FROM order_info
WHERE update_time >= '${last_sync_time}'
  AND update_time < '${current_sync_time}';
```

但要注意，如果源表存在物理删除，而 `update_time` 无法体现删除，就可能漏掉删除事件，此时 CDC 更可靠。

#### 五、面试时可以怎么总结

可以这样回答：全量同步是每次同步整张表，逻辑简单但成本高，适合小表、维表和快照场景；增量同步只同步新增或变化数据，效率高但实现更复杂，适合大表和事实表。选择时主要看数据量、变化比例、是否需要历史追踪、源表是否有可靠更新时间字段，以及是否能通过 binlog 或 CDC 捕获所有变更。

#### 知识扩展

- CDC：通过变更日志捕获插入、更新和删除
- 拉链表：常用增量数据维护维度历史
- 分区覆盖：离线同步中常用于按天重刷
- 幂等写入：增量同步必须考虑重复执行结果一致
- 数据校验：全量和增量都需要记录数、金额等对账

### 5.3 什么是分区表？为什么数仓中大量使用分区？

分区表是把一张逻辑表按照某些字段拆分成多个物理或逻辑分区存储的表。数仓中最常见的是按日期分区，比如 `dt`、`hour`。

#### 一、分区表的基本概念

例如订单明细表按日期分区：

```plaintext
dwd_trade_order_detail_di
  dt=2026-06-08
  dt=2026-06-09
  dt=2026-06-10
```

查询某一天数据时，只需要扫描对应分区，而不需要扫描整张表。

#### 二、为什么数仓大量使用分区

##### 1. 减少扫描数据量

大多数离线分析都带时间条件。按日期分区后，可以利用分区裁剪减少扫描范围。

```sql
SELECT
    SUM(pay_amount)
FROM dwd_trade_order_detail_di
WHERE dt = '2026-06-10';
```

这个查询只扫描 `dt=2026-06-10` 分区。

##### 2. 便于数据重跑和修复

如果某天数据错误，可以只重刷这一天分区，而不是重算整张表。

##### 3. 便于生命周期管理

可以按分区删除历史数据，例如只保留最近 2 年数据。

##### 4. 适合调度产出

离线任务通常每天产出一个分区，天然和调度周期匹配。

#### 三、常见分区方式

1. 按天分区：`dt`
2. 按小时分区：`dt` + `hour`
3. 按业务域分区：地区、渠道、租户
4. 多级分区：日期 + 小时 + 地区

最常见的是日期分区，因为时间是分析和调度中最稳定的边界。

#### 四、分区设计注意点

1. 分区字段要高频出现在查询条件中。
2. 分区粒度不能过细，否则会产生大量小文件。
3. 分区粒度不能过粗，否则分区裁剪效果差。
4. 不要把高基数字段随意作为分区字段，例如用户 ID。
5. 查询时必须带分区条件，否则容易全表扫描。

#### 五、面试时可以怎么总结

可以这样回答：分区表是按照某些字段把数据拆分到不同分区中存储，数仓中最常见的是按日期分区。使用分区的主要目的包括减少查询扫描量、提升性能、方便按天重跑修复、支持生命周期管理，并且和离线调度周期天然匹配。设计分区时要选择高频过滤字段，常见是 `dt`，同时避免分区过细导致小文件过多。

#### 知识扩展

- 分区裁剪：查询引擎根据分区条件跳过无关数据
- 小文件问题：分区过细或写入过散会导致性能下降
- 动态分区：批量写入多个分区时常用
- 生命周期管理：按分区删除过期数据
- Hive/Spark SQL：分区表是离线数仓最基础的表设计
- 分桶 (Bucket)：分区之外另一种拆表方式，和分区有本质区别 (详见 5.7)

### 5.4 Hive/Spark SQL 中如何进行常见的数仓性能优化？

Hive/Spark SQL 性能优化的核心思路是减少扫描数据量、减少 Shuffle、减少 Join 成本、避免数据倾斜，并让存储格式和执行引擎更好地配合。

#### 一、分区裁剪

查询时尽量带上分区条件，避免全表扫描。

```sql
SELECT
    SUM(pay_amount)
FROM dwd_trade_order_detail_di
WHERE dt = '2026-06-10';
```

如果不带 `dt`，可能会扫描整张历史表。

#### 二、列裁剪

只查询需要的字段，避免 `SELECT *`。

```sql
SELECT
    user_id,
    pay_amount
FROM dwd_trade_order_detail_di
WHERE dt = '2026-06-10';
```

对于 Parquet、ORC 这类列式存储，列裁剪可以显著减少 IO。

#### 三、选择合适的文件格式

数仓分析通常优先选择列式格式，比如 Parquet 或 ORC。

优点：

1. 支持列裁剪。
2. 压缩效果好。
3. 适合聚合查询。
4. 支持谓词下推。

#### 四、优化 Join

常见策略：

1. 小表广播 Join，避免大表 Shuffle。
2. 大表 Join 前先过滤无关分区和字段。
3. 避免多张大表直接 Join。
4. 预先建设宽表或汇总表。
5. 保证 Join Key 类型一致，避免隐式转换。

#### 五、处理数据倾斜

数据倾斜常见于热点 Key，例如某个默认值、未知城市、超级大客户。

优化方式：

1. 过滤异常热点值。
2. 对热点 Key 单独处理。
3. 加盐打散热点 Key。
4. 使用两阶段聚合。
5. 调整 Shuffle 分区数。

#### 六、小文件治理

小文件过多会导致 NameNode 压力、任务启动开销和读取开销增加。

常见治理方式：

1. 合并小文件。
2. 控制任务并行度。
3. 使用合理的分区粒度。
4. 写入后做 compact。

#### 七、减少重复计算

如果某些复杂逻辑被多个报表复用，应沉淀到 DWS 或 ADS 层，而不是每个报表都重复计算。

#### 八、面试时可以怎么总结

可以这样回答：Hive/Spark SQL 的数仓性能优化可以从几个方向入手：首先通过分区裁剪和列裁剪减少扫描数据量；其次使用 Parquet、ORC 等列式存储提升 IO 效率；然后优化 Join，比如小表广播、大表先过滤、必要时建设宽表；再处理数据倾斜，比如热点 Key 拆分、加盐和两阶段聚合；最后治理小文件和重复计算。核心目标是减少 IO、减少 Shuffle、减少 Join 成本。

#### 知识扩展

- Parquet/ORC：列式存储对 OLAP 查询非常重要
- Broadcast Join：小表 Join 大表的常见优化
- Shuffle：Spark SQL 性能瓶颈常来自 Shuffle
- 数据倾斜：聚合和 Join 中最常见的性能问题之一
- DWS/ADS：通过预聚合和宽表减少重复计算

### 5.5 Hive SQL 的执行流程是怎样的？一条 SQL 从提交到结果产出经历哪些阶段？

Hive 本身不存储数据，也不直接执行计算，它更像一个"SQL 翻译器"：把用户写的 SQL 翻译成底层计算引擎 (MapReduce、Tez、Spark) 能执行的分布式任务。一条 Hive SQL 从提交到产出结果，通常会经历提交、编译、优化、执行、返回五个大阶段，其中编译和优化是最核心也最容易被面试追问的部分。

#### 一、Hive 的核心组件

先看 Hive 的几个关键角色，理解了它们再看执行流程会非常清晰：

| 组件               | 职责                                    |
| ---------------- | ------------------------------------- |
| Driver           | 驱动器，接收用户提交的 SQL，协调编译、优化和执行的全流程        |
| Compiler         | 编译器，负责 SQL 解析、语义分析、生成和优化执行计划          |
| Metastore        | 元数据服务，存储库名、表名、字段、分区、存储位置等信息           |
| Execution Engine | 执行引擎，实际运行任务，可以是 MapReduce、Tez 或 Spark |

#### 二、完整执行流程

```plaintext
用户提交 SQL (CLI / JDBC / Beeline)
        │
        ▼
   ┌─────────┐
   │ Driver  │  接收 SQL，发起编译
   └────┬────┘
        ▼
┌─────────────────────────────────────────────┐
│              Compiler 编译器                  │
│                                             │
│  1. Parser (Antlr)       → AST (抽象语法树)  │
│  2. Semantic Analyzer    → QueryBlock        │
│     (查 Metastore 校验表名/字段/类型)        │
│  3. 生成 Logical Plan     → Operator Tree    │
│  4. Logical Optimizer    (谓词下推、列裁剪等) │
│  5. 生成 Physical Plan    → Task Tree        │
│  6. Physical Optimizer    (Join 顺序、Join 方式) │
└────┬────────────────────────────────────────┘
        ▼
┌──────────────────────────┐
│   Execution Engine        │  MapReduce / Tez / Spark
│   (提交 DAG 到集群执行)   │
└────┬─────────────────────┘
        ▼
   返回结果给用户
```

#### 三、各阶段详解

##### 1. 提交 SQL

用户通过 Hive CLI、Beeline、JDBC 等方式把 SQL 发给 Driver。Driver 是整个流程的入口和协调者。

##### 2. 解析 (Parse)：SQL → AST

Compiler 首先用 Antlr 定义的语法规则把 SQL 字符串解析成一棵抽象语法树 (AST)。这个阶段只关心语法是否正确，不关心表和字段是否真实存在。

例如 `SELECT` 后面跟的是列名还是函数、`FROM` 后面是不是一个表名、`WHERE` 条件结构是否合法，都在这一步判断。

##### 3. 语义分析 (Semantic Analysis)：AST → QueryBlock

这一步会结合 Metastore 中的元数据做校验：

1. 表是否存在
2. 字段是否存在
3. 字段类型是否匹配
4. 函数是否存在、参数是否合法
5. 分区字段是否被正确使用

语义分析后，AST 被转换成 QueryBlock，它是更接近执行语义的逻辑块。这一步也是 Hive 和 Metastore 交互最频繁的阶段——如果元数据校验不通过，SQL 在这里就会直接报错，而不是到集群上才失败。

##### 4. 生成逻辑计划 (Logical Plan)：QueryBlock → Operator Tree

Compiler 把 QueryBlock 翻译成一棵由 Operator (操作符) 组成的逻辑执行树。每个 Operator 代表一个基本操作，例如：

- TableScanOperator：扫描表
- SelectOperator：选取字段
- FilterOperator：过滤条件
- GroupByOperator：分组聚合
- JoinOperator：表关联
- ReduceSinkOperator：Shuffle 边界，决定按什么 Key 分区发送到 Reducer

注意 ReduceSinkOperator 非常关键——它标记了 Map 和 Reduce 阶段的分界点，一个 SQL 有几个 ReduceSinkOperator 基本就对应几次 Shuffle。

##### 5. 逻辑优化 (Logical Optimization)

逻辑计划生成后，优化器会对 Operator Tree 做一系列基于规则的变换 (RBO)，常见优化包括：

1. 谓词下推 (Predicate Pushdown)：把过滤条件尽可能推到 TableScan 附近，提前减少数据量
2. 列裁剪 (Column Pruning)：只保留下游真正需要的字段
3. 常量折叠 (Constant Folding)：`1+1` 直接算成 `2`
4. MapJoin 转换：小表 Join 大表时，把小表广播到所有 Map 端，避免 Shuffle
5. 分区裁剪 (Partition Pruning)：根据分区条件跳过无关分区

##### 6. 生成物理计划 (Physical Plan)：Operator Tree → Task Tree

逻辑计划描述的是"做什么"，物理计划描述的是"怎么在分布式环境下做"。Compiler 会把 Operator Tree 拆分成一个个 Task，并根据执行引擎组装成 DAG (有向无环图)。

例如一个带 Group By 和 Join 的 SQL，通常会被拆成多个 MapReduce (或 Tez/Spark) 阶段，阶段之间通过 Shuffle 衔接。

##### 7. 物理优化 (Physical Optimization)

物理计划层面会做更偏执行层面的优化：

1. Join 顺序调整，让小表先参与 Join
2. Join 方式选择 (MapJoin、SMB Join、Bucket Map Join)
3. Shuffle 分区数调整
4. 排序优化、合并小文件等

##### 8. 执行 (Execution)

物理计划生成后，Driver 把任务 DAG 提交给执行引擎。如果底层是 MapReduce，会提交到 Hadoop YARN；如果是 Tez 或 Spark，则提交到对应引擎的集群。执行过程中会真正读取 HDFS 上的数据，完成 Map、Shuffle、Reduce 各阶段计算。

##### 9. 返回结果

任务执行完成后，结果会写入 HDFS，Driver 把结果读取并返回给用户，或者直接写入目标表。

#### 四、一个例子：从 SQL 看执行计划

```sql
-- 统计 2026-06-10 每个商品类目的支付金额
SELECT
    p.category_name,
    SUM(f.pay_amount) AS pay_amount
FROM dwd_trade_order_detail_di f
JOIN dim_product_df p
    ON f.product_id = p.product_id
WHERE f.dt = '2026-06-10'
GROUP BY p.category_name;
```

用 `EXPLAIN` 可以看到 Hive 生成的执行计划，大致会包含：

```plaintext
-- Stage 1: Map 阶段
--   扫描 dwd_trade_order_detail_di (只读 dt=2026-06-10 分区，列裁剪 product_id/pay_amount)
--   扫描 dim_product_df
--   Map 端 Join (若 dim_product_df 足够小，走 MapJoin)
--   按 category_name 分区 Shuffle
-- Stage 2: Reduce 阶段
--   按 category_name 做 SUM 聚合
--   结果写入 HDFS
```

从这个例子可以看出：分区裁剪发生在逻辑优化阶段，MapJoin 选择发生在物理优化阶段，而 Shuffle 的边界由 ReduceSinkOperator 决定。

#### 五、面试时可以怎么总结

可以这样回答：Hive 本身不存储和计算数据，它是一个把 SQL 翻译成分布式任务的系统。一条 SQL 提交后，Driver 把它交给 Compiler：先用 Antlr 解析成 AST，再结合 Metastore 做语义分析，校验表和字段；然后生成由各种 Operator 组成的逻辑计划，并做谓词下推、列裁剪、MapJoin 等逻辑优化；接着生成物理执行计划，拆成 MapReduce 或 Tez/Spark 的 DAG，做 Join 顺序和方式等物理优化；最后提交到集群执行，结果写回 HDFS 再返回给用户。整个过程最关键的是编译和优化阶段，它决定了 SQL 最终跑得对不对、快不快。

#### 知识扩展

- 执行引擎：MapReduce、Tez、Spark，Tez 因 DAG 复用和减少中间落盘通常比 MR 快 (详见 5.6)
- ReduceSinkOperator：标记 Shuffle 边界，是理解 Hive 执行计划的关键
- 谓词下推：把过滤推到数据源附近，减少后续处理数据量
- MapJoin：小表广播到 Map 端，避免昂贵 Shuffle
- EXPLAIN：查看执行计划是排查 Hive SQL 性能问题的第一步

### 5.6 Hive 的执行引擎：MapReduce、Tez、Spark 有什么区别？

Hive 本身只负责把 SQL 编译成逻辑和物理执行计划 (见 5.5)，真正跑任务的是底层执行引擎。Hive 历史上支持三种执行引擎：MapReduce、Tez 和 Spark (即 Hive on Spark)。三种引擎跑的是同一份物理计划，但运行时模型差异很大，直接决定了中间结果怎么流转、任务怎么申请资源、整体跑得快不快。

可以先记住一个核心区别：MapReduce 把多阶段任务拆成多个独立 Job、中间结果反复落盘 HDFS；Tez 和 Spark 都用 DAG 串联多个阶段、中间结果尽量走内存，所以都比 MapReduce 快很多；而 Spark 比 Tez 更激进地用内存、生态更强，但调优更复杂。

#### 一、三种引擎总览

| 引擎                    | 执行模型                             | 中间结果              | 典型定位               |
| --------------------- | -------------------------------- | ----------------- | ------------------ |
| MapReduce             | 多个独立 MR Job，每个 Job 固定 Map→Reduce | 落盘到 HDFS          | Hive 最早期引擎，稳定但慢    |
| Tez                   | 单个 DAG，多个 Vertex 串联              | DAG 内流转，不落 HDFS   | Hive 原生加速引擎，现代默认选项 |
| Spark (Hive on Spark) | 单个 DAG，多个 Stage + 内存流水线          | 内存为主，宽依赖处 Shuffle | 性能最强，适合已有 Spark 栈  |

#### 二、MapReduce 执行模型

MapReduce 是 Hive 最早的执行引擎。一条复杂 SQL 往往会被拆成多个 MR Job，每个 Job 有固定的 Map 和 Reduce 阶段。

```plaintext
SQL (Join + Group By)
   │
   ├── MR Job 1: Map(读表、Join、Map 端聚合) → Shuffle → Reduce(局部聚合)
   │        └── 输出落盘 HDFS
   │
   └── MR Job 2: Map(读 HDFS 中间结果) → Shuffle → Reduce(全局聚合)
            └── 最终结果落盘 HDFS
```

它的核心特点：

1. 每个 MR Job 相互独立，前一个 Job 的输出写入 HDFS，后一个 Job 再从 HDFS 读，中间结果反复落盘。
2. 每个 Task 启动一个独立 JVM，启动开销大，资源申请和释放频繁。
3. 编程模型简单固定 (Map→Shuffle→Reduce)，容错成熟，单个 Task 失败可以直接重跑。

最大的问题是慢：多个 Job 之间的 HDFS 往返和 JVM 启动开销，让 MR 引擎不适合任何近交互场景。

#### 三、Tez 执行模型

Tez 把原本需要多个 MR Job 才能完成的逻辑，表达成一个 DAG (有向无环图)。一个 Tez Job 包含多个 Vertex (对应阶段) 和连接它们的 Edge。

```plaintext
SQL (Join + Group By)
   │
   └── Tez DAG:
         Vertex1 (读表 + Join) ──edge──► Vertex2 (Shuffle + 聚合) ──► 结果
         │                              │
         └── 中间数据在 Application 内流转，不落 HDFS
```

和 MR 相比，Tez 的关键优势：

1. 中间结果不落 HDFS，而是在同一个 Application 内通过 edge 流转，省掉大量磁盘 IO。
2. 同一个 DAG 内的多个 Vertex 复用 Container，避免每个阶段重新申请资源。
3. 因为减少了落盘和资源申请，通常比 MR 快数倍。

Tez 是 Hive 2.x 之后推荐的默认引擎，配合 LLAP (Live Long And Process) 还能进一步做内存缓存和常驻进程，接近交互式查询。

#### 四、Spark 执行模型 (Hive on Spark)

Hive on Spark 是把 Hive 编译出的物理计划翻译成 Spark 的 RDD/DataFrame DAG，提交到 Spark 集群执行。

```plaintext
SQL (Join + Group By)
   │
   └── Spark Job:
         Stage 0 (读表 + Map 端 Join) ──宽依赖 Shuffle──► Stage 1 (全局聚合) ──► 结果
         │                                              │
         └── Executor 常驻，数据尽量驻留内存
```

Spark 的特点：

1. 基于内存的计算流水线，窄依赖可以在一个 Stage 内 pipeline，只有宽依赖 (如 Shuffle) 才切分 Stage。
2. Executor 常驻，Task 复用 Executor 线程，启动开销远小于 MR。
3. 容错基于 RDD 血缘 (lineage)，分区丢失时按血缘重算，而不是像 MR 那样靠任务重跑。
4. 通常性能最强，但内存消耗大，Shuffle、内存管理和 GC 调优比较复杂。

#### 五、核心差异对比

| 对比项       | MapReduce     | Tez               | Spark                 |
| --------- | ------------- | ----------------- | --------------------- |
| 执行单元      | 每 Task 一个 JVM | Container 内进程，可复用 | Executor 常驻，Task 复用线程 |
| 中间结果      | 反复落盘 HDFS     | DAG 内流转，不落 HDFS   | 内存为主，必要时落盘            |
| DAG 能力    | 弱，多 Job 串联    | 强，单 DAG 多 Vertex  | 强，单 DAG 多 Stage       |
| 启动开销      | 大             | 中                 | 小                     |
| 性能        | 最慢            | 比 MR 快数倍          | 通常最快                  |
| 容错机制      | Task 级重跑      | Task 级重跑          | RDD 血缘重算              |
| 调优难度      | 简单            | 中等                | 复杂 (内存/Shuffle/GC)    |
| 与 Hive 集成 | 原生            | 原生，默认推荐           | 需额外配置                 |
| 适用场景      | 超大规模离线批、极致稳定  | Hive 原生加速、近交互     | 高性能、已有 Spark 生态       |

#### 六、同一个 SQL 在三种引擎上的差异

拿 5.5 里那个例子：

```sql
SELECT
    p.category_name,
    SUM(f.pay_amount) AS pay_amount
FROM dwd_trade_order_detail_di f
JOIN dim_product_df p
    ON f.product_id = p.product_id
WHERE f.dt = '2026-06-10'
GROUP BY p.category_name;
```

三种引擎的执行差异：

```plaintext
MapReduce: 2 个独立 MR Job，中间结果写 HDFS，启动 2 轮 JVM
Tez:       1 个 Tez DAG，Vertex 间数据内存流转，Container 复用
Spark:     1 个 Spark Job，2 个 Stage，Shuffle 处切分，Executor 常驻
```

虽然三种引擎的物理计划在"做什么"上基本一致 (都是 Join → 按 category\_name Shuffle → 聚合)，但"中间结果怎么走"完全不同，这正是性能差距的根源。

#### 七、如何选择执行引擎

1. 新建 Hive 集群默认选 Tez，改动最小、加速明显，是 Hive 原生引擎。
2. 对性能要求很高，或者公司已经有成熟的 Spark 平台，选 Hive on Spark，甚至直接用 Spark SQL。
3. MapReduce 基本只在老旧环境、或者对稳定性要求极高且能接受慢的场景下保留。
4. 如果追求交互式 ad-hoc 查询，更主流的做法是用 Trino/Presto 这类 MPP 引擎，而不是在 Hive 里换引擎。

#### 面试时可以怎么总结

可以这样回答：Hive 本身不执行计算，它把 SQL 编译成物理计划后交给执行引擎。历史上主要有三种引擎：MapReduce 把任务拆成多个独立 Job，中间结果反复落盘 HDFS，稳定但慢；Tez 用一个 DAG 把多个阶段串起来，中间结果在 Application 内流转不落 HDFS，通常比 MR 快数倍，是 Hive 现在推荐的默认引擎；Spark 把计划翻译成 Spark 的 DAG，全内存流水线、Executor 常驻，性能最强但调优更复杂。三者的核心差异在于中间结果怎么流转、资源怎么复用，选择上新建集群优先 Tez，追求极致性能或已有 Spark 栈选 Hive on Spark，交互式查询则更推荐 Trino 这类 MPP 引擎。

#### 知识扩展

- Hive 执行流程：三种引擎共享同一套编译和优化流程，差异只在执行阶段 (见 5.5)
- LLAP：Tez 之上的常驻进程和内存缓存，进一步接近交互式查询
- Spark SQL：可直接替代 Hive on Spark，生态更完整
- Trino/Presto：MPP 架构的交互式查询引擎，和 Hive 引擎定位不同
- DAG：理解 Tez 和 Spark 性能优势的关键，区别于 MR 的多 Job 串联

### 5.7 Hive 的分区和分桶有什么区别？

分区 (Partition) 和分桶 (Bucket) 都是 Hive 里把一张大表拆成更小单元的手段，目的都是让查询少扫数据、让计算更高效，但它们的拆分依据、物理形态和主要用途完全不同。一句话概括：分区是按字段值把数据拆到不同 HDFS 目录，面向查询裁剪和数据管理；分桶是按某列的 hash 值把数据拆到目录下的多个文件，面向 Join 优化、数据抽样和均匀分布。

面试时最常见的混淆点是：以为分桶和分区一样能靠查询条件自动裁剪。实际上普通查询带分桶列过滤并不会自动只扫一个桶，分桶的核心价值在 Join 和抽样，而不是单表过滤。

#### 一、分区的本质 (回顾)

分区是把表按某个字段的值拆成多个 HDFS 目录，查询时带分区条件就能只读对应目录。数仓中最常见的是按日期分区。

```plaintext
dwd_trade_order_detail_di
  /dt=2026-06-08/
  /dt=2026-06-09/
  /dt=2026-06-10/     ← 查询 WHERE dt='2026-06-10' 只读这个目录
```

分区的详细作用、设计原则在 5.3 已经讲过，这里不重复，重点看分桶。

#### 二、分桶的本质

分桶是按某个列的 hash 值对桶数取模，把数据拆到目录下的多个文件里。每个桶对应一个文件 (或一组文件)，数据按分桶列的 hash 均匀分布。

```plaintext
dwd_trade_user_bucket
  /dt=2026-06-10/
      bucket_00000    ← hash(user_id) % 16 == 0 的行
      bucket_00001
      ...
      bucket_00015
```

建表语法：

```sql
-- 按 user_id 分 16 个桶
CREATE TABLE dwd_trade_user_bucket (
    order_id    STRING,
    user_id     STRING,
    pay_amount  DECIMAL(10,2)
)
PARTITIONED BY (dt STRING)       -- 先按日期分区
CLUSTERED BY (user_id)           -- 再按 user_id 分桶
SORTED BY (user_id)              -- 桶内排序 (可选，配合 SMB Join)
INTO 16 BUCKETS
STORED AS ORC;
```

分桶的核心作用：

1. **优化 Join**：两张表都按同一个 key 分桶，且桶数相同或成倍数，就可以做 Bucket Map Join 或 SMB Join，避免昂贵的全量 Shuffle。
2. **数据抽样**：用 `TABLESAMPLE` 可以快速抽取固定比例的数据做验证分析，而不需要全表扫描。
3. **数据均匀分布**：hash 取模天然让数据均匀打散，缓解按某列值倾斜的问题。
4. **控制文件数量**：桶数决定了每个分区下的文件数，合理的桶数能同时避免小文件过多和单文件过大。

#### 三、分区和分桶的核心区别

| 对比项  | 分区 (Partition)     | 分桶 (Bucket)                          |
| ---- | ------------------ | ------------------------------------ |
| 拆分依据 | 字段值直接对应            | 分桶列 hash 对桶数取模                       |
| 物理形态 | HDFS 目录            | 目录下的多个文件                             |
| 粒度   | 粗，按业务值 (如日期、地区)    | 细，按 hash 均匀打散                        |
| 查询裁剪 | 带分区条件即可裁剪目录        | 普通查询默认不能只扫一个桶                        |
| 数据分布 | 可能不均 (某天数据量特别大)    | 理论上均匀                                |
| 主要目的 | 减少扫描、按维度管理、重跑修复    | Join 优化、抽样、数据均匀                      |
| 多层能力 | 支持多级分区             | 单维分桶 (可指定多列，但通常一列)                   |
| 适合字段 | 低基数、高频过滤字段 (dt、城市) | 高基数、Join key 字段 (user\_id、order\_id) |

最关键的一行是"查询裁剪"：分区靠值直接命中目录，所以 `WHERE dt='2026-06-10'` 能立刻裁剪；而分桶靠 hash 规则，`WHERE user_id='u1001'` 理论上能算出它在哪个桶，但普通 Hive 查询默认不会做这种桶级裁剪，所以分桶的收益主要不在单表查询，而在 Join 和抽样。

#### 四、分区和分桶能否一起用

可以，而且生产中很常见。典型做法是先按时间分区，再在每个分区下按 user\_id 分桶：

```plaintext
表: dwd_trade_user_bucket
  /dt=2026-06-10/
      bucket_00000 ... bucket_00015
  /dt=2026-06-11/
      bucket_00000 ... bucket_00015
```

分区负责按时间裁剪，分桶负责让每个时间分区内的大表能高效 Join 和抽样，两者互补。

#### 五、分桶的设计要点和坑

1. **桶数要和数据量匹配**：桶太少会导致单桶文件过大、并行度低；桶太多会产生大量小文件。经验上是让每个桶的数据量在几百 MB 到 1GB 左右。
2. **分桶列优先选 Join key**：分桶最大的价值是 Join 优化，所以分桶列通常就是和其他大表关联的字段，比如 user\_id。
3. **桶数等于写入时的 Reducer 数**：写分桶表时每个桶通常对应一个 Reducer，所以桶数也决定了这一步的并行度。
4. **两表 Bucket Join 要求桶数一致或成倍数**：否则桶和桶对不上，无法做 Map 端 Join，只能退化成普通 Shuffle Join。
5. **分桶数定下来后很难改**：改桶数等于重新分布全部数据，通常需要重建表并回刷历史，所以初期设计就要想好。

#### 六、一个例子：Join 优化和数据抽样

两张大表都按 user\_id 分 16 桶：

```sql
-- 抽样：只读 16 个桶里的 1 个，约 1/16 数据
SELECT COUNT(*)
FROM dwd_trade_user_bucket
TABLESAMPLE(BUCKET 1 OUT OF 16 ON user_id);

-- Join 优化：两表同 key 同桶数，可走 Bucket Map Join，避免 Shuffle
SELECT /*+ MAPJOIN(b) */ a.user_id, b.member_level
FROM dwd_trade_user_bucket a
JOIN dim_user_bucket b
    ON a.user_id = b.user_id;
```

抽样在大数据量下做快速验证特别有用，而 Bucket Map Join 则是分桶最核心的性能收益场景。

#### 面试时可以怎么总结

可以这样回答：分区和分桶都是把大表拆小的手段，但原理和目的不同。分区是按字段值把数据拆到不同 HDFS 目录，查询带分区条件就能裁剪，主要用来减少扫描和按维度管理数据，比如按日期分区；分桶是按某列 hash 取模把数据拆到目录下的多个文件，主要用来优化 Join、支持数据抽样和让数据均匀分布。两者可以组合使用，常见的做法是先按日期分区，再按 user\_id 分桶。分桶设计时要注意桶数和数据量匹配、分桶列尽量选 Join key、两表做 Bucket Join 要保证桶数一致或成倍数，而且桶数一旦确定就很难修改。

#### 知识扩展

- 分区表：分区的详细作用和设计原则见 5.3
- SMB Join：Sort Merge Bucket Join，分桶表间最高效的 Join 方式
- TABLESAMPLE：分桶表的数据抽样语法
- Bucket Map Join：分桶大表间的 Map 端 Join，避免 Shuffle
- 数据倾斜：分桶的 hash 打散能缓解按值倾斜

### 5.8 在 Hive 中如何创建分桶表？分桶表相比普通表有哪些优势？

分桶表 (Bucketed Table) 是在普通表基础上，按某一列的 hash 值对桶数取模，把每个分区 (或整表) 的数据进一步拆成固定数量的桶文件。和普通表相比，分桶表的数据在物理上被"预先按规则组织"过，这种组织方式换来了 Join 提速、高效抽样和数据均匀分布等收益，但同时也对建表设计和数据写入方式提出了约束。

5.7 讨论的是"分区和分桶有什么区别"，本节聚焦分桶表本身：怎么把它建出来、数据怎么正确导入，以及它相对普通表到底好在哪。

#### 一、创建分桶表：完整语法

分桶表的核心建表语法是 `CLUSTERED BY ... [SORTED BY ...] INTO N BUCKETS`：

```sql
CREATE TABLE dwd_trade_user_bucket (
    order_id    STRING,
    user_id     STRING,
    pay_amount  DECIMAL(10,2),
    order_time  TIMESTAMP
)
PARTITIONED BY (dt STRING)        -- 先按日期分区
CLUSTERED BY (user_id)            -- 按 user_id 的 hash 值分桶
SORTED BY (user_id)               -- 每个桶内按 user_id 排序 (可选)
INTO 16 BUCKETS                   -- 分成 16 个桶
STORED AS ORC;                    -- 分桶表通常配合列式存储
```

关键字含义：

1. `CLUSTERED BY (col)`：指定分桶列，Hive 用 `hash(col) % N` 决定一行数据落到哪个桶。分桶列通常选高频 Join key，例如 `user_id`、`order_id`。
2. `SORTED BY (col)`：可选，要求每个桶内部按指定列有序。它本身不带来单表查询加速 (Hive 普通查询不会利用桶内排序做二分查找)，但配合 Sort Merge Bucket Join 时是必要条件。
3. `INTO N BUCKETS`：桶数 N，决定每个分区下的物理文件数。N 一旦定下就很难修改，改 N 等于重新分布全部历史数据。
4. `STORED AS ORC/PARQUET`：分桶表几乎总是配合列式存储，因为 Join 和抽样场景下都要靠列裁剪进一步减少 IO。

物理上，每个桶对应一个文件，命名形如 `000000_0`、`000001_0` ... `000015_0`：

```plaintext
dwd_trade_user_bucket
  /dt=2026-06-10/
      000000_0   ← hash(user_id) % 16 == 0 的所有行
      000001_0
      ...
      000015_0
```

#### 二、数据导入的正确姿势 (最容易踩的坑)

很多人建好了分桶表却没拿到分桶收益，问题几乎都出在数据导入上。

##### 1. 必须用 INSERT ... SELECT，不能用 LOAD

分桶表写入数据的正确方式是通过 MR/Spark 任务重新分布：

```sql
-- 正确：走分布式任务，按 user_id hash 写入对应桶
INSERT OVERWRITE TABLE dwd_trade_user_bucket PARTITION (dt='2026-06-10')
SELECT order_id, user_id, pay_amount, order_time
FROM ods_order_info_di
WHERE dt = '2026-06-10';
```

而 `LOAD DATA INPATH ...` 只是把 HDFS 文件原封不动地搬到表目录下，不会做 hash 分桶，也不会拆成 N 个桶文件。用 LOAD 导入的"分桶表"，每行数据的实际归属和所在桶号毫无关系，后续的 Bucket Map Join、TABLESAMPLE 都会得到错误结果。

##### 2. 桶数等于写入时的 Reducer 数

写入分桶表时，Hive 会让 Reducer 个数等于桶数 N，每个 Reducer 按 `hash(key) % N` 只处理对应的那一个桶，输出一个桶文件。这也意味着 N 同时决定了写入阶段的并行度——N 太小写入慢，N 太大又容易产生小文件。

##### 3. hive.enforce.bucketing

老版本 Hive (3.0 之前) 需要显式开启 `set hive.enforce.bucketing=true;`，让 Hive 自动根据桶数设置 Reducer 数并正确分桶；否则要手动把 `mapreduce.job.reduces` 设成桶数。Hive 3.x 之后这个推断变成自动的，但在脚本里显式开启仍是稳妥做法。

#### 三、分桶表相比普通表的优势

普通表 (非分桶表) 的数据只是按分区写到目录下，文件内部没有按任何 key 组织。分桶表多了一层"按 hash 预分布"，由此带来几个维度的收益：

| 对比维度    | 普通表                   | 分桶表                                               |
| ------- | --------------------- | ------------------------------------------------- |
| 文件内数据组织 | 无 key 规律              | 按 hash(key) 均匀分布到 N 个桶                            |
| Join 大表 | 必须全量 Shuffle，代价大      | 同 key 同桶数可走 Bucket Map Join / SMB Join，避免 Shuffle |
| 数据抽样    | 只能随机采样或全表扫，慢且不固定      | `TABLESAMPLE` 直接读指定桶，快且比例固定                       |
| 数据倾斜    | 按 key 聚合/Join 时热点严重   | hash 取模天然把热点 key 打散到不同桶                           |
| 并行度     | 取决于文件数和切片大小           | 桶数即天然的并行单元，可控                                     |
| 写入约束    | 任意方式 (LOAD/INSERT) 均可 | 必须 INSERT ... SELECT 走分布式任务                       |
| 修改成本    | 改分区/重算较灵活             | 桶数一旦定下基本不可改                                       |

其中最核心、最常被追问的是 Join 优化和抽样：

##### 1. Join 优化：把 Shuffle Join 降级成 Map Join

两张大表都按 `user_id` 分相同数量的桶时，左表第 i 个桶和右表第 i 个桶里，hash 值落在同一编号的行一定只出现在同号桶里 (因为 hash 函数和桶数都相同)。这样 Join 时不需要全局 Shuffle，只需把同号桶拉到一起做 Map 端 Join。这是分桶表最大的性能价值，5.7 也提到了这一点。

##### 2. 高效且确定性的抽样

普通表做抽样要么随机采样 (代价大、每次结果不同)，要么全表扫后 LIMIT。分桶表因为按 hash 均匀分布，读第 i 个桶就约等于读了 1/N 的数据，而且每次抽到的样本集合是稳定的：

```sql
-- 抽取约 1/16 的数据做快速验证
SELECT COUNT(*), SUM(pay_amount)
FROM dwd_trade_user_bucket
TABLESAMPLE(BUCKET 1 OUT OF 16 ON user_id)
WHERE dt = '2026-06-10';
```

在大数据量下做指标验证、SQL 调试时，这种固定比例的抽样非常实用。

#### 四、什么场景值得用分桶表，代价是什么

适合用分桶表的场景：

1. 两张大表频繁按同一个 key Join，例如交易明细表和用户维表都按 `user_id` 关联。
2. 经常需要按固定比例抽样做快速验证或数据探查。
3. 某张表按 Join key 严重倾斜，需要靠 hash 预打散。

不适合或需要权衡的地方：

1. 桶数一旦确定几乎不可改，重建需要回刷全部历史分区，所以必须在建表初期就根据数据量规划好 (经验上让每个桶几百 MB 到 1GB)。
2. 写入必须走 MR/Spark 任务，不能用 LOAD，数据生产链路约束更强。
3. 如果只是单表 ad-hoc 查询、没有大表 Join 需求，分桶收益很有限，普通表加好分区往往就够了。
4. 普通查询带分桶列过滤并不会自动只扫一个桶 (详见 5.7)，所以不要指望分桶能像分区那样做查询裁剪。

一句话原则：分桶是为了 Join 和抽样，不是为了单表查询过滤。

#### 五、完整例子：建表、导入、Join 优化

```sql
-- 1. 建两张按 user_id 分 16 桶的表
CREATE TABLE dwd_trade_user_bucket (
    order_id   STRING,
    user_id    STRING,
    pay_amount DECIMAL(10,2)
)
PARTITIONED BY (dt STRING)
CLUSTERED BY (user_id) SORTED BY (user_id) INTO 16 BUCKETS
STORED AS ORC;

CREATE TABLE dim_user_bucket (
    user_id      STRING,
    member_level STRING
)
CLUSTERED BY (user_id) SORTED BY (user_id) INTO 16 BUCKETS
STORED AS ORC;

-- 2. 正确导入：INSERT ... SELECT，走分布式任务分桶
INSERT OVERWRITE TABLE dwd_trade_user_bucket PARTITION (dt='2026-06-10')
SELECT order_id, user_id, pay_amount
FROM ods_order_info_di
WHERE dt = '2026-06-10';

-- 3. 两表同 key、同桶数、桶内排序，可走 SMB Join，避免 Shuffle
set hive.optimize.bucketmapjoin=true;
set hive.auto.convert.sortmerge.join=true;

SELECT /*+ MAPJOIN(b) */ a.user_id, b.member_level, a.pay_amount
FROM dwd_trade_user_bucket a
JOIN dim_user_bucket b
    ON a.user_id = b.user_id
WHERE a.dt = '2026-06-10';
```

两张表桶数成倍数 (如 16 和 32) 时也能做 Bucket Map Join；只有桶数完全一致且桶内排序时，才能进一步走 SMB Join，性能最好。

#### 面试时可以怎么总结

可以这样回答：分桶表是在普通表基础上，按某列的 hash 值对桶数取模，把数据预先拆成固定数量的桶文件。创建时用 `CLUSTERED BY (col) [SORTED BY (col)] INTO N BUCKETS`，通常配合 ORC/Parquet 列式存储。导入数据时必须用 `INSERT ... SELECT` 走分布式任务，不能用 LOAD，因为 LOAD 只搬文件不做 hash 分桶，会导致桶文件号和实际数据归属不一致；写入时 Reducer 数也等于桶数。分桶表相比普通表的核心优势有三点：一是两张同 key 同桶数的大表 Join 可以走 Bucket Map Join 或 SMB Join，避免全量 Shuffle；二是可以用 `TABLESAMPLE` 做固定比例的高效抽样；三是 hash 取模能把数据均匀打散，缓解倾斜。但分桶也有代价：桶数定下后几乎不可改、写入约束更强、且对单表查询过滤没有裁剪效果。所以分桶主要服务于 Join 和抽样场景，不是为了单表查询加速。

#### 知识扩展

- 分区 vs 分桶：两者都是拆表手段，但原理和目的不同，详见 5.7
- SMB Join：Sort Merge Bucket Join，分桶表间最高效的 Join 方式，要求同 key、同桶数、桶内排序
- Bucket Map Join：分桶大表间的 Map 端 Join，桶数相同或成倍数即可
- TABLESAMPLE：基于分桶的确定性抽样语法，适合大数据量下的快速验证
- 数据倾斜：分桶的 hash 打散是缓解 Join/聚合倾斜的预处理手段

### 5.9 Hive 的元数据存储在哪里？如何管理 Hive 元数据？

Hive 本身既不存储业务数据，也不执行计算，甚至连"有哪些库、表长什么样、数据存在 HDFS 哪个目录"这类结构信息也不是 Hive 自己记录的，而是交给一个独立组件 **Hive Metastore (HMS)** 统一管理。它的核心设计是：业务数据存在 HDFS，元数据存在关系数据库，中间用 Metastore 服务把两者解耦。理解 Metastore 的存储结构和管理方式，是排查 Hive 表"看不见""分区缺失""统计信息不准"等问题的基础。

注意和 4.2 的区别：4.2 讲的是数仓层面"技术/业务/操作元数据"的分类概念，本节讲 Hive 这个具体组件怎么落地存储和管理元数据。

#### 一、Metastore 的架构：数据 + 服务两层

Hive 的元数据管理分成两层：底层是关系数据库，上层是 Metastore 服务。

```plaintext
Hive 客户端 (CLI / Beeline / HiveServer2 / Spark / Trino)
              │  Thrift (默认端口 9083)
              ▼
      ┌──────────────────┐
      │  Metastore 服务   │  独立 JVM 进程，可多实例做高可用
      │  (HMS Thrift API) │  封装所有元数据读写逻辑
      └────────┬─────────┘
               │  JDBC (DataNucleus / JDO)
               ▼
      ┌──────────────────┐
      │   关系数据库       │  MySQL / PostgreSQL / SQL Server
      │   (元数据表)       │  DBS / TBLS / PARTITIONS / COLUMNS_V2 / SDS ...
      └──────────────────┘
```

为什么要分两层，而不是让每个客户端直连数据库：

1. **解耦和统一**：所有客户端 (Hive、Spark、Trino、Presto) 通过同一套 Thrift API 访问元数据，不必每个引擎都直连数据库。
2. **安全和可控**：数据库账号不暴露给业务方，权限和并发控制集中在 HMS。
3. **可扩展**：HMS 可以独立扩容、做多实例高可用，而底层 DB 可以单独做主从。

底层关系数据库里有一百多张元数据表，最核心的几张：

| 元数据表                                | 记录内容                                                            |
| ----------------------------------- | --------------------------------------------------------------- |
| `DBS`                               | 数据库 (DB\_ID、库名、HDFS 路径、所有者)                                     |
| `TBLS`                              | 表 (TBL\_NAME、所属 DB\_ID、表类型 MANAGED\_TABLE/EXTERNAL\_TABLE/VIEW) |
| `COLUMNS_V2`                        | 字段定义 (字段名、类型 STRING/DECIMAL、注释、顺序)                              |
| `PARTITION_KEYS`                    | 分区字段 (分区列名、类型)                                                  |
| `PARTITIONS`                        | 具体分区值 (PART\_KEY、对应 SDS)                                        |
| `SDS`                               | 存储描述 (SerDe、InputFormat、OutputFormat、HDFS LOCATION)             |
| `TABLE_PARAMS` / `PARTITION_PARAMS` | 表/分区属性 (numRows、numFiles、totalSize 等统计)                         |
| `TAB_COL_STATS` / `PART_COL_STATS`  | 列级统计 (min、max、ndv、null\_count，供 CBO 使用)                         |
| `SCHEMA_VERSION`                    | 元数据 schema 版本 (升级时核对)                                           |

`SDS` 这张表尤其关键：Hive 表名和 HDFS 物理目录的映射关系就存在这里。如果元数据丢了，即便 HDFS 上的数据文件还在，Hive 里这张表也会"看不见"——这也是元数据必须备份的根本原因。

#### 二、Metastore 的三种部署模式

根据 Metastore 服务和元数据库的位置关系，Hive 提供三种部署模式：

| 模式            | 元数据库     | Metastore 服务 | 连接方式               | 适用场景      |
| ------------- | -------- | ------------ | ------------------ | --------- |
| Embedded (内嵌) | 内置 Derby | 和客户端同进程      | 零配置                | 单机测试、单元测试 |
| Local (本地)    | 独立 RDBMS | 嵌在客户端 JVM 内  | 客户端直连 DB           | 小规模、开发环境  |
| Remote (远程)   | 独立 RDBMS | 独立 JVM 进程    | 客户端通过 Thrift 连 HMS | 生产环境标配    |

Embedded 模式用自带的 Derby，启动 Hive CLI 时自动创建，但同一时刻只允许一个客户端访问，完全不能用于生产。

Local 模式把元数据库换成了独立的 MySQL，但 Metastore 逻辑仍然跑在每个客户端进程里，每个客户端都独立连 DB，连接数和一致性压力较大，适合开发和小规模环境。

Remote 模式才是生产标配：HMS 作为独立进程部署，所有客户端 (HiveServer2、Spark、Trino) 通过 Thrift 连到 HMS，再由 HMS 统一访问数据库。客户端只需要指向 HMS 地址：

```xml
<!-- Remote 模式：客户端只配 Metastore 服务地址，多实例用逗号分隔做高可用 -->
<property>
  <name>hive.metastore.uris</name>
  <value>thrift://hms-host-01:9083,thrift://hms-host-02:9083</value>
</property>
```

对比之下，Local/Embedded 模式要直接配数据库连接：

```xml
<property>
  <name>javax.jdo.option.ConnectionURL</name>
  <value>jdbc:mysql://mysql-host:3306/hive_metastore</value>
</property>
<property>
  <name>javax.jdo.option.ConnectionDriverName</name>
  <value>com.mysql.cj.jdbc.Driver</value>
</property>
```

#### 三、如何管理 Hive 元数据

##### 1. schema 初始化与升级：schematool

元数据库需要先建好 schema (表结构) 才能用，Hive 提供 `schematool` 工具：

```bash
# 首次部署：初始化元数据库 schema
schematool -dbType mysql -initSchema

# Hive 版本升级时：同步升级元数据 schema
schematool -dbType mysql -upgradeSchema
```

schema 版本记录在 `SCHEMA_VERSION` 表里，Hive 启动时会核对版本是否匹配，不一致会直接报错——这是防止元数据和 Hive 二进制版本不兼容导致脏数据。升级时通常要按版本顺序走，不能跳级。

##### 2. 备份与恢复

元数据是 Hive 的命脉，必须和 HDFS 数据一起备份：

1. 定期用 `mysqldump` 备份元数据库。
2. HMS 关键表 (`DBS` / `TBLS` / `SDS` / `PARTITIONS`) 重点保护。
3. 恢复时元数据和 HDFS 数据要对齐，否则会出现"元数据指向的目录 HDFS 上没有"或"数据在但表看不见"。
4. 误删表后，如果及时备份了元数据库还能恢复；若只备份了 HDFS 数据，重建表结构和分区映射的成本很高。

##### 3. 通过 HMS API 操作，不要直连改库

所有元数据变更都应该走 HMS 的 Thrift API 或 DDL 语句 (`CREATE` / `ALTER` / `DROP` / `MSCK REPAIR`)，而不是直接到数据库里改表。直接改元数据库很容易绕过 HMS 的一致性校验，造成表和分区、表和存储位置之间不一致，排查极其困难。

常用元数据维护命令：

```sql
-- 分区是手动 put 到 HDFS 的场景，用 MSCK 同步元数据
MSCK REPAIR TABLE dwd_trade_order_detail_di;

-- 重新统计表/分区的行数、文件数，写入 TABLE_PARAMS
ANALYZE TABLE dwd_trade_order_detail_di PARTITION(dt='2026-06-10')
COMPUTE STATISTICS;

-- 收集列级统计，供 CBO 选择 Join 顺序
ANALYZE TABLE dwd_trade_order_detail_di
COMPUTE STATISTICS FOR COLUMNS user_id, pay_amount;
```

##### 4. 高可用与权限治理

1. **高可用**：HMS 部署多实例，客户端通过 `hive.metastore.uris` 配多个地址自动故障转移；底层 DB 用主从或集群。
2. **权限**：Hive 自带授权较简单，生产环境一般接 Apache Ranger 或 Sentry，做库/表/列级权限和脱敏，Ranger 的策略往往也基于 HMS 的元数据做匹配。
3. **外部数据目录**：Atlas、Amundsen、DataHub 这类数据目录工具，通常订阅 HMS 的事件 (Metastore Listener) 或调 HMS API 来构建数据目录和血缘。

#### 四、一个例子：建表时元数据怎么落

执行一条建表语句：

```sql
CREATE TABLE dwd_trade_order_detail_di (
    order_id   STRING,
    user_id    STRING,
    pay_amount DECIMAL(10,2)
)
PARTITIONED BY (dt STRING)
STORED AS ORC
LOCATION '/warehouse/dwd/dwd_trade_order_detail_di';
```

HMS 在元数据库里大致会这样写入：

```plaintext
DBS              ← 找到/确认 dwd 库 (DB_ID)
TBLS             ← 新增一行: TBL_NAME=dwd_trade_order_detail_di, TBL_TYPE=MANAGED_TABLE
COLUMNS_V2       ← 写入 order_id:STRING, user_id:STRING, pay_amount:DECIMAL(10,2)
PARTITION_KEYS   ← 写入分区字段 dt:STRING
SDS              ← 写入 ORC 的 InputFormat/OutputFormat/SerDe 和 LOCATION
TABLE_PARAMS     ← 写入表属性 (transient_lastDdlTime 等)
```

之后每次 `ALTER TABLE` / `ADD PARTITION` / `INSERT OVERWRITE`，HMS 都会更新对应元数据。这也是为什么 5.5 里讲 Hive 执行流程时，Compiler 在语义分析阶段必须频繁查 Metastore——表存不存在、字段类型、分区位置全靠它提供。

#### 面试时可以怎么总结

可以这样回答：Hive 的元数据由独立的 Hive Metastore (HMS) 统一管理，架构上分两层：底层是关系数据库 (MySQL/PostgreSQL)，存储 `DBS`、`TBLS`、`COLUMNS_V2`、`PARTITIONS`、`SDS` 等一百多张元数据表；上层是 Metastore 服务，对外通过 Thrift (默认 9083) 提供统一 API，Hive、Spark、Trino 都通过它访问元数据，而不是直连数据库。部署上有 Embedded (Derby 内嵌，仅测试)、Local (DB 独立但 HMS 嵌在客户端)、Remote (HMS 独立进程) 三种模式，生产环境用 Remote，客户端只配 `hive.metastore.uris`。管理上：用 `schematool` 初始化和升级 schema；元数据库必须和 HDFS 数据一起备份，丢了元数据等于表全部看不见；元数据变更必须走 HMS API 或 DDL，不能直连改库；高可用靠 HMS 多实例 + DB 主从；权限和血缘通常接 Ranger、Atlas。核心要记住的一点是：Hive 的数据在 HDFS、元数据在 RDBMS，两者靠 SDS 表里的 LOCATION 映射。

#### 知识扩展

- 元数据分类：技术/业务/操作元数据的概念见 4.2，本节是它们在 Hive 里的具体落地
- Hive 执行流程：Compiler 在语义分析阶段频繁查 Metastore 校验表和字段，见 5.5
- HMS Thrift API：Hive、Spark、Trino 共用的元数据访问入口
- CBO：`TAB_COL_STATS` 里的列级统计是代价优化器选 Join 顺序的基础
- 数据目录：Atlas/DataHub 等通过 Metastore Listener 或 API 构建数据目录和血缘
- 湖仓元数据：Iceberg/Hudi/Paimon 各有独立元数据管理，常挂载到 Hive Catalog 统一访问

### 5.10 Hive 中如何实现多表连接？不同 JOIN 策略的性能差异是怎样的？

多表连接是数仓里最高频的操作，Hive 支持标准 SQL 的各种 JOIN 写法。但同样是 JOIN，底层可以走完全不同的物理执行策略，性能差距能到几倍甚至几十倍。所以这道题要分两层回答：先看 Hive 怎么实现多表 JOIN (逻辑写法 + 物理执行模型)，再看底层有哪些 Join 策略、哪种最快。

#### 一、Hive 的逻辑 JOIN 类型

先区分一个前提：SQL 里写的 `INNER/LEFT` 这些叫**逻辑 Join 类型**，决定"哪些行保留、怎么匹配"；而后面讲的 Map Join / SMB Join 叫**物理 Join 策略**，决定"用什么算法执行"。同一个 `INNER JOIN` 在不同数据规模下可以走完全不同的物理策略。

Hive 支持的逻辑 Join 类型：

| 类型               | 语义                    | 典型场景           |
| ---------------- | --------------------- | -------------- |
| INNER JOIN       | 只保留两表都匹配的行            | 默认关联           |
| LEFT OUTER JOIN  | 左表全保留，右表不匹配填 NULL     | 事实关联维度         |
| RIGHT OUTER JOIN | 右表全保留                 | 较少用            |
| FULL OUTER JOIN  | 两表都全保留，互不匹配填 NULL     | 差异比对           |
| LEFT SEMI JOIN   | 左表行在右表存在即输出，每行左表只输出一次 | 替代 IN / EXISTS |
| CROSS JOIN       | 笛卡尔积                  | 极少用，性能差        |

其中 **LEFT SEMI JOIN** 是 Hive 比较有特色的一个，面试常被追问：

```sql
-- 找出"下单过的用户"，等价于 user_id IN (SELECT user_id FROM order_info)
SELECT u.user_id, u.user_name
FROM dim_user u
LEFT SEMI JOIN dwd_trade_order_detail_di o
    ON u.user_id = o.user_id;
```

它的特点：

1. 语义是"半连接"：右表只要匹配到一行，左表这条就输出并停止扫描右表，效率比写出全量 JOIN 再去重高。
2. 右表字段**只能出现在 ON 条件里**，不能在 SELECT / WHERE 引用，因为它并不真正参与输出。
3. 早期 Hive 子查询支持差，LEFT SEMI JOIN 是替代 IN / EXISTS 的标准写法。

#### 二、多表连接的物理执行模型：左深树和 stage 切分

写多个表 `A JOIN B JOIN C JOIN D` 时，Hive 默认生成**左深树** (left-deep tree)：从左到右两两 Join，前一个 Join 的结果作为下一个 Join 的输入。

```plaintext
A JOIN B JOIN C
   =>   ((A ⋈ B) ⋈ C)        左深树
            │
   stage1: A ⋈ B   ── Shuffle ──► Reduce (输出中间结果)
            │
   stage2: result ⋈ C ── Shuffle ──► Reduce
```

几个关键点：

1. 5.5 讲过，每个 `ReduceSinkOperator` 标记一次 Shuffle 边界。多表 Join 时，每两个非 Map Join 的表关联就会切出一个 stage、多一次 Shuffle。
2. N 个表做 Common Join，最坏要 N-1 次 Shuffle，中间结果会反复落盘。
3. 中间结果可能远大于输入 (尤其笛卡尔积或一对多关联)，所以**多表 Join 的顺序和执行计划影响巨大**。
4. Hive 2.x 之后的 CBO (Cost Based Optimizer) 可以基于列统计重排 Join 顺序，甚至生成 bushy tree (多路并行 Join)，前提是收集过统计信息 (见 5.9 的 ANALYZE)。

#### 三、Hive 的物理 Join 策略与性能差异

这是本题最核心的部分。Hive 的 Join 在物理执行时主要有五种策略，核心区别是**要不要 Shuffle**：

##### 1. Common Join (Reduce Join / Shuffle Join)

默认策略：两表都按 Join key 做 Shuffle 发到 Reducer，在 Reduce 端排序匹配。

```plaintext
Map (读表+打标) ──按 Join key Shuffle──► Reduce (排序+匹配)
```

最通用，但每次 Join 都要 Shuffle，慢且容易倾斜。大表 Join 大表且无法分桶时只能走它。

##### 2. Map Join (小表广播)

把小表整个读进内存广播到每个 Map 任务，大表在 Map 端直接匹配，**完全不 Shuffle、不 Reduce**。

```plaintext
小表广播到每个 Mapper
Map (读大表 + 内存匹配小表) ──直接输出──► 结果
```

触发条件：小表能放进内存 (由 `hive.auto.convert.join.noconditionaltask.size` 控制，默认约 25MB)。开启 `hive.auto.convert.join=true` 后 Hive 自动判断转换，也可以用 `/*+ MAPJOIN(小表) */` 强制指定。这是日常最快的 Join，**小表 Join 大表必走它**。

##### 3. Bucket Map Join

两表都按 Join key 分桶，桶数相同或成倍数。广播的是小表的"每个桶"而不是整表，因此能处理比普通 Map Join 更大的表，仍不 Shuffle。前提是两表都按 Join key 分好桶 (详见 5.8)。

##### 4. SMB Join (Sort Merge Bucket Join)

两表按 Join key 分桶 + 桶内排序 + 桶数相同，每个 Mapper 只 Join 对应的同号桶，借桶内有序做归并匹配，**不 Shuffle**。这是**大表 Join 大表最快的策略**，但要求最高——必须提前按规则建好分桶表并正确导入 (详见 5.8)。

##### 5. Skew Join (倾斜优化)

运行时检测某个 Join key 数据量超过阈值 (`hive.skewjoin.key`)，把它判定为倾斜 key，这部分单独走 Map Join，其余正常 Common Join。它的目标不是"最快"，而是**避免某个 Reducer 被热点 key 拖垮**。

五种策略对比：

| 策略              | 是否 Shuffle | 触发条件                  | 适合场景              | 性能  |
| --------------- | ---------- | --------------------- | ----------------- | --- |
| Map Join        | 否          | 小表能进内存                | 小表 Join 大表        | 最快  |
| SMB Join        | 否          | 同 key 分桶 + 桶内有序 + 同桶数 | 大表 Join 大表 (分桶)   | 极快  |
| Bucket Map Join | 否          | 同 key 分桶 + 桶数成倍数      | 中等表 Join 中等表 (分桶) | 快   |
| Skew Join       | 部分         | 倾斜 key 超阈值            | 倾斜场景              | 治倾斜 |
| Common Join     | 是          | 默认兜底                  | 任意                | 最慢  |

一句话：**能不能消灭 Shuffle 决定了 Join 快不快**。Map Join、Bucket Map Join、SMB Join 都是在想方设法把 Reduce 端 Join 提前到 Map 端，从而省掉 Shuffle。

#### 四、多表 Join 的实践优化要点

落到日常开发，多表 Join 优化可以总结为几条：

1. **小表用 Map Join**：开启自动转换或写 `/*+ MAPJOIN(b) */`，消灭 Shuffle。
2. **先过滤再 Join**：把 WHERE 条件尽量下推到子查询里，减少参与 Join 的行数 (谓词下推，见 5.4)。
3. **Join key 类型必须一致**：一边 STRING 一边 BIGINT 会触发隐式转换，导致无法正确 Shuffle 甚至全表扫。
4. **多表 Join 小表放左边**：左深树下左边先加载，配合 Map Join 让小表尽早参与。
5. **大表 Join 大表考虑分桶走 SMB Join**：建表阶段就按 Join key 分桶，长期收益 (见 5.8)。
6. **倾斜 key 单独处理**：加盐打散、两阶段聚合，或开 Skew Join (见 5.4)。
7. **避免笛卡尔积**：CROSS JOIN 或漏写 ON 条件会产生海量中间结果。

一个多表 Join 优化示例：

```sql
-- 优化前：四表关联，未控制 Join 顺序和过滤
SELECT a.user_id, b.city, c.category_name, d.pay_amount
FROM fact_order a
JOIN dim_user b      ON a.user_id = b.user_id
JOIN dim_product c   ON a.product_id = c.product_id
JOIN fact_pay d      ON a.order_id = d.order_id;

-- 优化后：先过滤、小表广播、大表分桶对齐
SELECT /*+ MAPJOIN(b, c) */ a.user_id, b.city, c.category_name, d.pay_amount
FROM (
    -- 先把大表过滤到需要的那天，减少参与 Join 的数据量
    SELECT user_id, product_id, order_id
    FROM fact_order
    WHERE dt = '2026-06-10'
) a
JOIN dim_user b    ON a.user_id = b.user_id          -- 维表小，走 Map Join
JOIN dim_product c ON a.product_id = c.product_id    -- 维表小，走 Map Join
JOIN dim_pay_bucket d ON a.order_id = d.order_id;    -- 若两表按 order_id 分桶，可走 SMB Join
```

#### 面试时可以怎么总结

可以这样回答：Hive 的多表连接要分逻辑和物理两层看。逻辑层面支持 INNER、LEFT/RIGHT/FULL OUTER、LEFT SEMI、CROSS 等 JOIN，其中 LEFT SEMI JOIN 是 Hive 比较特别的，等价于 IN/EXISTS，右表匹配到一行就停止，效率高。物理层面，多表 Join 默认生成左深树，每两个非 Map Join 表关联就切一个 stage、多一次 Shuffle，所以 Join 顺序影响很大。性能上关键看用哪种物理策略：Map Join 把小表广播到 Map 端、不 Shuffle，小表 Join 大表最快；SMB Join 要求两表同 key 分桶且桶内有序，大表 Join 大表最快；Bucket Map Join 介于两者之间；Skew Join 专门治倾斜；Common Join 是默认的 Shuffle Join，最慢。优化的核心思路就是尽量消灭 Shuffle：小表用 Map Join、大表预先分桶走 SMB Join、先过滤再 Join、Join key 类型一致、倾斜 key 单独处理。

#### 知识扩展

- Join 优化要点：小表广播、先过滤等见 5.4
- ReduceSinkOperator：理解多表 Join 切 stage 的关键，见 5.5
- 分桶表与 SMB Join：大表 Join 大表最优解的落地方式，见 5.8
- CBO：基于列统计自动重排 Join 顺序，依赖 ANALYZE 收集统计，见 5.9
- 数据倾斜：Join 和聚合最常见的性能杀手，倾斜 key 需单独处理

### 5.11 Hive 如何处理大数据量的排序？实际应用中如何优化排序操作？

排序是数仓里的常见操作，比如按金额取 Top-N、按时间倒序、每个分组取前几名。但在分布式环境下，"全局排序"和单机排序完全不同——它要求所有数据最终汇聚到一个 Reducer 做归并，这在大数据量下是性能灾难。所以做排序优化的前提，是先分清 Hive 四种排序语法在底层的本质区别。

#### 一、Hive 的四种排序语法

这是面试最容易被追问、也最容易混淆的点。四种语法对应不同的并行度和有序范围。

##### 1. ORDER BY：全局排序

`ORDER BY` 保证全表最终有序。为了做到跨所有数据有序，Hive 会把**全部数据 Shuffle 到单个 Reducer** 做最终归并排序。

为什么必须是单 Reducer：全局有序需要一个汇总点做跨分片归并，多个 Reducer 各排各的无法保证 Reducer 之间的顺序。代价就是这个 Reducer 要处理全量数据，数据量大时极易 OOM 和超时。

##### 2. SORT BY：局部排序

`SORT BY` 只保证**每个 Reducer 内部有序**，Reducer 之间不保证顺序。因为是多 Reducer 并行排序，并行度高，但结果不是全局有序。

##### 3. DISTRIBUTE BY：只控制分发

`DISTRIBUTE BY` 决定数据按某列的 hash 分发到哪个 Reducer，**本身不做排序**。它常和 `SORT BY` 配合：先用 `DISTRIBUTE BY` 决定哪些行进入同一 Reducer，再用 `SORT BY` 在 Reducer 内排序。

典型场景：按 `user_id` 分发，保证同一用户的数据进同一 Reducer，再在该 Reducer 内按 `order_time` 排序。

##### 4. CLUSTER BY：分发 + 排序同一列

`CLUSTER BY (col)` 等价于 `DISTRIBUTE BY (col) + SORT BY (col)`，且**只能升序**，不能指定 DESC。当分发列和排序列是同一个字段时，用它写法更简洁。

四种语法对比：

| 语法            | 有序范围        | Reducer 数 | 全局有序 | 能否指定 DESC | 典型场景            |
| ------------- | ----------- | --------- | ---- | --------- | --------------- |
| ORDER BY      | 全局          | 1 个 (强制)  | 是    | 能         | 必须全局有序、配合 LIMIT |
| SORT BY       | 单 Reducer 内 | 多个        | 否    | 能         | 局部有序、并行排序       |
| DISTRIBUTE BY | 不排序         | 多个        | 否    | —         | 控制分发，搭配 SORT BY |
| CLUSTER BY    | 单 Reducer 内 | 多个        | 否    | 否 (只能升序)  | 同列分发+排序的简写      |

一个直观例子，对比同样"按金额排序"在不同语法下的行为：

```sql
-- (1) 全局有序：所有数据进 1 个 Reducer，慢
SELECT order_id, pay_amount FROM fact_order WHERE dt='2026-06-10'
ORDER BY pay_amount DESC;

-- (2) 局部有序：多 Reducer 并行，每个 Reducer 内有序，但全局不一定
SELECT order_id, pay_amount FROM fact_order WHERE dt='2026-06-10'
SORT BY pay_amount DESC;

-- (3) 分发+排序：先按 user_id 分发，每个 Reducer 内按 user_id 升序
SELECT user_id, order_id, pay_amount FROM fact_order WHERE dt='2026-06-10'
CLUSTER BY user_id;

-- (4) 精确控制：按 user_id 分发，Reducer 内按 pay_amount 降序 (CLUSTER BY 做不到 DESC)
SELECT user_id, order_id, pay_amount FROM fact_order WHERE dt='2026-06-10'
DISTRIBUTE BY user_id SORT BY pay_amount DESC;
```

#### 二、大数据量排序为什么慢

排序的代价集中在两点：Shuffle 和单 Reducer 归并。

1. **ORDER BY 的单 Reducer 瓶颈**：全表数据都要经 Shuffle 汇聚到这一个 Reducer，由它串行完成归并排序。单节点处理全量数据，内存压力大 (易 OOM)、耗时长、完全无法并行，数据量到几亿行时基本跑不出来。
2. **Shuffle 成本**：即便用 `SORT BY` 多 Reducer 并行排序，数据仍要从 Map 端经网络 Shuffle 到 Reduce 端，这部分 IO 是排序的主要开销。
3. **分发倾斜**：`DISTRIBUTE BY` 按 hash 分发，如果某列存在热点 key (例如大量 user\_id 为默认值)，对应 Reducer 数据量远超其他，拖慢整体。

#### 三、实际优化手段

##### 1. 能用 SORT BY 就别用 ORDER BY

很多"全局有序"其实是伪需求。如果下游能接受局部有序 (比如分区表内每天各自有序，或配合二次处理)，用 `SORT BY` 多 Reducer 并行，性能能好一个数量级。只在真正需要全表有序时才用 `ORDER BY`。

##### 2. Top-N 用两阶段聚合

经典场景：取全天支付金额前 10 的订单。

错误做法是直接 `ORDER BY ... LIMIT 10`——单 Reducer 全量排序后再取 10 条，前面绝大部分排序都白做了。

优化思路是两阶段：每个 Reducer 先各自局部排序、各取前若干，再汇总到单 Reducer 做一次小数据量的全局排序：

```sql
-- 两阶段 Top-N：取全天支付金额前 10 的订单
SELECT order_id, pay_amount
FROM (
    -- 第一阶段：每个 Reducer 内局部排序后各取前 100
    -- Hive 中 SORT BY + LIMIT 的 LIMIT 是 per-Reducer 生效的
    SELECT order_id, pay_amount
    FROM fact_order
    WHERE dt = '2026-06-10'
    SORT BY pay_amount DESC
    LIMIT 100
) t
-- 第二阶段：单 Reducer 只处理 (Reducer 数 × 100) 条数据，很快
ORDER BY pay_amount DESC
LIMIT 10;
```

如果有 200 个 Reducer，第二阶段单 Reducer 只需对 20000 条数据排序，而不是全表的几亿条。

##### 3. 利用分桶表的 SORTED BY

建分桶表时声明 `SORTED BY (col)`，数据在导入时桶内就有序 (见 5.8)，后续查询可以直接复用这个有序性，避免运行时再排。这也是 SMB Join 的前提条件。

##### 4. 排序前先把数据量降下来

1. **分区裁剪**：排序前先 `WHERE dt=...` 缩小到必要范围。
2. **列裁剪**：只 SELECT 需要的列，配合列式存储减少 IO。
3. **谓词下推**：把过滤条件尽可能推到数据源附近 (见 5.4)。

##### 5. 控制 Reducer 数和防倾斜

`SORT BY` 的并行度由 Reducer 数决定 (`mapreduce.job.reduces` 或 `hive.exec.reducers.byte.per.reducer`)：太少排序慢，太多产生小文件。`DISTRIBUTE BY` 的列尽量选分布均匀的，避免热点 key 让某个 Reducer 数据量爆炸，必要时对热点 key 加盐打散。

#### 四、分组 Top-N：窗口函数的排序

数仓里更常见的是"每个分组取前 N"，比如每个商品类目销售额前 3 的商品，通常用窗口函数：

```sql
-- 每个类目支付金额前 3 的商品
SELECT product_id, category_id, pay_amount
FROM (
    SELECT
        product_id,
        category_id,
        pay_amount,
        ROW_NUMBER() OVER (
            PARTITION BY category_id             -- 按 category 分组 (内部会按 category Shuffle 分发)
            ORDER BY pay_amount DESC             -- 组内按金额降序
        ) AS rn
    FROM dwd_trade_order_detail_di
    WHERE dt = '2026-06-10'
) t
WHERE rn <= 3;
```

注意窗口函数 `PARTITION BY` 在底层也会按分区列做一次 Shuffle (类似 `DISTRIBUTE BY`)，数据量大时同样是性能瓶颈，同样适用"先过滤、分桶预排序、控制并行度"的优化思路。

#### 面试时可以怎么总结

可以这样回答：Hive 的排序要先分清四种语法的底层差异。ORDER BY 是全局排序，为了保证跨所有数据有序，会把全部数据强制 Shuffle 到单个 Reducer 归并，大数据量下极慢、易 OOM；SORT BY 只保证每个 Reducer 内有序、多 Reducer 并行，但不全局有序；DISTRIBUTE BY 只控制数据按某列 hash 分发到 Reducer，不排序，常和 SORT BY 配合；CLUSTER BY 等价于 DISTRIBUTE BY + SORT BY 同列，且只能升序。排序慢的根本原因是 Shuffle 和单 Reducer 归并，优化时：能用 SORT BY 就别用 ORDER BY；Top-N 用两阶段聚合，每个 Reducer 先局部取 N 条，再单 Reducer 全局取 N 条；大表可以建分桶表声明 SORTED BY 让数据导入时就有序，查询时复用；排序前先做分区裁剪和列裁剪减少数据量；最后合理控制 Reducer 数、注意分发倾斜。分组 Top-N 用 ROW\_NUMBER 窗口函数，它底层也要按分区列 Shuffle，同样适用这些优化。

#### 知识扩展

- Shuffle 与 ReduceSink：排序的本质开销在 Shuffle 和 Reduce 归并，见 5.5
- 通用性能优化：分区裁剪、列裁剪、谓词下推见 5.4
- 分桶表 SORTED BY：让数据导入时桶内有序，排序与 SMB Join 复用，见 5.8
- 窗口函数：ROW\_NUMBER / RANK 用于分组 Top-N，底层依赖按分区列 Shuffle
- 两阶段聚合：Top-N、distinct 计数等场景的经典优化思路

### 5.12 Hive 中如何优化 GROUP BY 查询的性能？常见优化策略有哪些？

GROUP BY 是数仓里最高频的聚合操作，几乎所有 DWS/ADS 指标都靠它汇总，它的性能直接决定任务产出速度。GROUP BY 在 Hive 里本质上是一个"按 group key 分发 + 聚合"的过程，瓶颈几乎都来自两个地方：Shuffle 数据量和 group key 倾斜。所以优化的核心思路就是——**尽量在 Map 端提前聚合减少 Shuffle，并处理好 group key 倾斜**。

#### 一、GROUP BY 的执行原理与瓶颈

##### 1. 两阶段聚合模型

GROUP BY 默认走 MapReduce 的两阶段聚合：

```plaintext
Map (局部聚合) ──按 group key Shuffle──► Reduce (全局聚合)
```

1. **Map 端**：读取数据，按 group key 输出。如果开了 Map 端聚合，Map 端会先用 hash table 缓存做局部聚合，再把局部结果 Shuffle 出去。
2. **Shuffle**：按 group key 的 hash 把数据分发到 Reducer，相同 key 必须落到同一 Reducer。
3. **Reduce 端**：对同一 key 的所有数据做最终聚合 (SUM / COUNT / MAX 等)。

##### 2. 两个核心瓶颈

1. **Shuffle 成本**：所有数据都要按 group key 经网络传到 Reducer，Shuffle 数据量越大越慢。
2. **group key 倾斜**：如果某个 key 的数据量远超其他 (例如按城市聚合，一线城市的数据是其他城市的几十倍)，对应 Reducer 处理时间远超其他，整个任务被这一个 Reducer 拖垮，这是 GROUP BY 最常见的性能杀手。

#### 二、核心优化策略

##### 1. Map 端聚合 (最重要的一项)

原理：Map 端用一个 hash table 缓存已聚合的中间结果，相同 key 在 Map 端就先合并，真正 Shuffle 出去的只是局部聚合后的少量结果，而不是原始明细。

```sql
-- 开启 Map 端聚合 (Hive 默认就是 true，生产环境务必确认)
set hive.map.aggr=true;
-- 控制 hash table 可占用的 Map 端内存比例
set hive.map.aggr.hash.percentmemory=0.5;
```

它适合 group key 基数适中、聚合函数可合并的场景 (SUM / COUNT / MIN / MAX 都可合并)。局限是 hash table 占内存，key 基数特别大时会频繁 flush 到磁盘，效果下降。

##### 2. 倾斜自动处理 (hive.groupby.skewindata)

Hive 提供了自动应对倾斜的开关，把一个 GROUP BY 拆成两个 MR Job：

```sql
set hive.groupby.skewindata=true;
```

- **Job 1**：Map 输出时给 key 加随机前缀，按随机前缀 Shuffle，每个 Reducer 做局部聚合。这样原本集中在某个 Reducer 的倾斜 key 被均匀打散到多个 Reducer。
- **Job 2**：去掉随机前缀，按真正的 key Shuffle 做全局聚合。

注意它会多跑一轮 MR，非倾斜场景反而变慢，所以要判断确实存在倾斜再开。

##### 3. 手动加盐两阶段聚合 (倾斜 key 的经典解法)

当自动开关不够灵活，或已经知道具体倾斜 key 时，手动写两阶段聚合更可控。这是 Join 倾斜加盐 (见 5.10) 在 GROUP BY 上的对应做法：

```sql
-- 第一阶段：给倾斜 key 加随机后缀打散，在打散后的 key 上做局部聚合
SELECT
    real_city,
    SUM(partial_cnt) AS cnt
FROM (
    SELECT
        -- 加 0-99 的随机后缀，同一城市被拆成 100 份散到不同 Reducer
        concat(city, '_', CAST(floor(rand() * 100) AS STRING)) AS salted_key,
        city AS real_city,
        COUNT(1) AS partial_cnt
    FROM fact_order
    WHERE dt = '2026-06-10'
    GROUP BY
        concat(city, '_', CAST(floor(rand() * 100) AS STRING)),
        city
) t
-- 第二阶段：按真实 city 全局聚合
GROUP BY real_city;
```

原理：第一阶段用 (随机后缀 + key) 作为新分发键，原本集中的"北京"被拆成 100 份，均匀分布到多个 Reducer 各自 count；第二阶段再去掉后缀按真实 city 汇总。这样既绕开了单 Reducer 倾斜，又保证了最终结果正确。

##### 4. COUNT(DISTINCT) 改写

`COUNT(DISTINCT col)` 为了正确去重，无法像 SUM/COUNT 那样在 Map 端简单合并，往往集中到少数甚至单个 Reducer 处理，数据量大时是严重瓶颈。

```sql
-- 慢：COUNT(DISTINCT) 容易集中到单 Reducer
SELECT city, COUNT(DISTINCT user_id) AS uv
FROM fact_order
WHERE dt = '2026-06-10'
GROUP BY city;

-- 快：先用 GROUP BY 去重走多 Reducer，外层再 SUM
SELECT city, SUM(cnt) AS uv
FROM (
    SELECT city, user_id, 1 AS cnt
    FROM fact_order
    WHERE dt = '2026-06-10'
    GROUP BY city, user_id        -- 先把 (city, user_id) 去重，分散到多 Reducer
) t
GROUP BY city;                    -- 再按 city 汇总，得到每个城市的 uv
```

如果业务允许近似值，可以用 `APPROX_COUNT_DISTINCT` (基于 HyperLogLog)，速度更快、内存更省。

##### 5. 通用减量与并行度优化

1. **减小 group key 基数**：去掉不必要的列，key 基数越小 Map 端 hash table 效率越高。
2. **列裁剪 + 分区裁剪 + 谓词下推**：先过滤到必要范围再聚合 (见 5.4)。
3. **合理 Reducer 数**：由 `hive.exec.reducers.byte.per.reducer` 控制，太少聚合慢，太多小文件多。
4. **倾斜 key 单独拎出来**：把极端热点 key 过滤后单独处理，其余正常聚合再 union。

各策略适用场景对比：

| 策略                 | 解决的问题                 | 代价 / 限制       |
| ------------------ | --------------------- | ------------- |
| Map 端聚合            | Shuffle 数据量大          | key 基数过大时效果下降 |
| skewindata         | 未知的 group key 倾斜      | 多一轮 MR，非倾斜时变慢 |
| 手动加盐两阶段            | 已知的明显倾斜 key           | SQL 更复杂       |
| COUNT(DISTINCT) 改写 | distinct 集中到单 Reducer | 多一层子查询        |
| 减量 + 并行度           | 通用基础优化                | 无             |

#### 面试时可以怎么总结

可以这样回答：优化 Hive 的 GROUP BY 要先理解它的执行模型——Map 端局部聚合，按 group key Shuffle，Reduce 端全局聚合，瓶颈在 Shuffle 数据量和 group key 倾斜。最常用的优化是 Map 端聚合，开 `hive.map.aggr=true`，让 Map 端用 hash table 先合并，大幅减少 Shuffle 数据量。遇到倾斜时，可以开 `hive.groupby.skewindata=true` 让 Hive 自动拆成两个 MR 打散倾斜 key；也可以手动写两阶段聚合，给倾斜 key 加随机后缀先局部聚合、再去掉后缀全局聚合。另外 `COUNT(DISTINCT)` 往往集中到单 Reducer，可以改写成先 GROUP BY 去重再 SUM，分散到多 Reducer，或者用 APPROX\_COUNT\_DISTINCT 做近似计数。最后配合分区裁剪、列裁剪、减小 group key 基数和合理 Reducer 数等通用优化一起做。

#### 知识扩展

- 通用性能优化：分区/列裁剪、谓词下推、Reducer 数调整见 5.4
- Join 倾斜加盐：GROUP BY 加盐两阶段聚合的对应做法，见 5.10
- 两阶段聚合：倾斜、Top-N、distinct 计数等场景的通用思路，见 5.11
- HyperLogLog：APPROX\_COUNT\_DISTINCT 的底层算法，用极少内存做基数近似估计
- Shuffle：GROUP BY 性能开销的本质来源，理解它有助于判断该用哪种优化


## 6. 实时数仓架构

### 6.1 什么是 Lambda 架构，什么是 Kappa 架构？二者有什么异同点和优缺点？

Lambda 架构和 Kappa 架构都是面向大数据实时分析场景的架构设计思想，核心目标都是解决一个问题：既要保证数据结果准确可靠，又要尽可能降低数据产出的延迟。

在面试中，这道题通常不是只考概念定义，而是考你是否理解实时数仓从“离线批处理 + 实时流处理”到“流批一体”的架构演进，以及你是否能从数据一致性、开发维护成本、延迟、容错、历史数据重算等角度做技术权衡。

#### 一、什么是 Lambda 架构

Lambda 架构是一种同时保留批处理链路和流处理链路的大数据架构。它通常把数据处理拆成三层：Batch Layer、Speed Layer 和 Serving Layer。

Batch Layer 负责离线批处理，通常基于 Hive、Spark、MapReduce 等引擎，对全量历史数据进行周期性计算，产出准确、完整、可重算的结果。Speed Layer 负责实时流处理，通常基于 Kafka、Flink、Storm、Spark Streaming 等组件，对最新增量数据进行低延迟计算。Serving Layer 负责对外查询服务，把批处理结果和实时结果合并后提供给报表、BI、接口或数据应用。

可以用一个简化链路理解：

```text
数据源
  ├── 离线链路：ODS / 日志归档 → Hive / Spark 批处理 → 离线结果表
  └── 实时链路：Kafka → Flink 实时计算 → 实时结果表

查询服务：离线结果 + 实时增量结果 → 对外提供统一指标
```

例如要计算“当天实时 GMV”，Lambda 架构可能会这样做：T-1 及更早的数据由离线任务每天定时计算，今天 0 点之后的数据由 Flink 实时计算，查询时把离线历史结果和当天实时增量结果合并。

#### 二、为什么会出现 Lambda 架构

Lambda 架构出现的背景是：早期大数据体系中，批处理系统比较成熟，结果准确、吞吐高、容错能力强，但延迟高；流处理系统延迟低，但早期在一致性、容错、状态管理、Exactly Once、历史回放等方面不够成熟。

所以 Lambda 架构选择“两条链路互补”：离线链路兜底准确性，实时链路提供低延迟。实时结果可以先快速给业务使用，等离线批处理结果产出后，再用离线结果修正或覆盖实时结果。

它本质上是一种用系统复杂度换取“准确性 + 实时性”的折中方案。

#### 三、Lambda 架构的优点

##### 1. 结果准确性高

离线批处理链路可以基于全量数据重新计算，适合做最终一致、口径校准和历史修正。如果实时链路因为乱序、延迟、数据丢失、状态异常导致短期结果不准确，离线链路可以在后续修正。

##### 2. 容错和重算能力强

只要原始数据被完整保存在 HDFS、对象存储、数据湖或 Hive ODS 层中，就可以通过批处理链路重新跑历史数据，适合处理口径变更、代码 Bug 修复、历史数据回补等场景。

##### 3. 适合复杂历史分析

离线链路天然适合大规模全量 Join、多维聚合、复杂窗口、长周期统计等任务，比如月活、留存、复购、归因分析、用户分层等。

##### 4. 技术风险相对可控

对于强依赖准确性的核心指标，Lambda 架构可以用离线结果作为最终结果，实时结果只是提前预估或临时展示，因此整体风险较低。

#### 四、Lambda 架构的缺点

##### 1. 开发和维护成本高

同一个指标通常要写两套逻辑：一套离线 SQL / Spark 任务，一套实时 Flink 任务。两套代码、两套调度、两套存储、两套监控都会增加维护成本。

##### 2. 口径一致性难保证

离线链路和实时链路使用的计算引擎、时间语义、维表关联方式、去重逻辑、窗口边界可能不同，很容易出现“同一个指标，离线和实时结果对不上”的问题。

例如离线任务按 `dt` 分区统计自然日订单，而实时任务按事件时间窗口统计，如果迟到数据处理策略不同，GMV 就可能不一致。

##### 3. 架构复杂度高

查询层需要合并离线结果和实时结果，还要处理数据覆盖、去重、补偿、延迟到达、重复消费等问题。链路越长，排查问题越困难。

##### 4. 资源成本较高

同一份数据可能既要进入离线存储，又要进入实时链路；同一个指标可能既要跑批任务，又要跑流任务，会带来额外的计算和存储成本。

#### 五、什么是 Kappa 架构

Kappa 架构是 Jay Kreps 提出的简化实时数据处理架构。它的核心思想是：取消独立的批处理链路，只保留一条流处理链路，用流处理系统同时处理实时数据和历史数据。

在 Kappa 架构中，所有数据都被看作事件流。实时数据是不断到来的新事件，历史数据则是可以从 Kafka、日志系统、数据湖或其他可回放存储中重新回放的旧事件。当需要重算历史数据时，不再启动一套独立的批处理任务，而是让流处理作业从更早的 offset 或历史数据源重新消费。

简化链路如下：

```text
数据源 → Kafka / 可回放日志 → Flink / 流处理作业 → 实时结果表 / OLAP 存储 → 查询服务

历史重算：从旧 offset 或历史事件重新回放 → 同一套流处理逻辑重新计算
```

例如计算实时 UV，Kappa 架构中只维护一套 Flink 作业。实时计算时消费最新 Kafka 数据；如果指标口径变了，则从 Kafka 保留的历史消息、日志归档或数据湖中的历史事件重新回放，用同一套逻辑重新生成结果。

#### 六、为什么会出现 Kappa 架构

Kappa 架构出现的背景是流处理技术逐渐成熟，比如 Kafka 提供可持久化、可回放的日志存储，Flink 提供状态管理、Checkpoint、Savepoint、事件时间、水位线、Exactly Once 语义等能力。

当流处理系统已经能承担较高准确性和较强容错能力时，就没有必要为了同一个指标长期维护两套计算链路。Kappa 架构希望用“一套代码、一条链路”降低系统复杂度。

它本质上是一种用更强的流处理能力换取架构简化的方案。

#### 七、Kappa 架构的优点

##### 1. 架构更简单

Kappa 架构只有一条流处理链路，不需要同时维护离线批处理和实时流处理两套系统，整体链路更短，组件更少。

##### 2. 口径一致性更容易保证

因为实时计算和历史重算使用同一套代码逻辑，所以不会出现离线 SQL 和实时 Flink 逻辑不一致的问题。

##### 3. 延迟低

Kappa 架构天然面向实时处理，适合秒级、分钟级指标产出，比如实时大盘、实时风控、实时推荐特征、实时告警等场景。

##### 4. 运维和开发成本较低

只需要维护一套作业、一套状态、一套监控和一套数据链路，开发迭代效率更高。

#### 八、Kappa 架构的缺点

##### 1. 对消息系统和流处理能力要求高

Kappa 架构依赖数据可长期保留和可回放。如果 Kafka 数据保留时间较短，或者历史数据无法完整回放，历史重算就会受限。

##### 2. 大规模历史重算成本高

虽然 Kappa 理论上可以通过事件回放完成重算，但如果要重放半年或一年的海量数据，流处理作业可能需要跑很久，而且会占用大量资源。对于超大规模全量重算，批处理往往更高效。

##### 3. 不适合所有复杂离线分析

一些复杂的历史分析任务，比如多表大宽表构建、复杂维度建模、长周期留存、全量用户分群、复杂归因分析，用纯流处理实现会比较困难，开发复杂度可能反而更高。

##### 4. 状态管理复杂

流处理中的状态可能非常大，涉及 Checkpoint、State Backend、状态 TTL、状态迁移、Savepoint 恢复等问题。一旦状态设计不合理，可能出现 Checkpoint 慢、恢复慢、状态膨胀等问题。

#### 九、Lambda 架构和 Kappa 架构的相同点

Lambda 和 Kappa 都服务于大数据实时分析场景，目标都是在低延迟和高准确性之间取得平衡。二者通常都会使用消息队列承接实时数据，比如 Kafka；都会强调原始数据可追溯、可回放；都会面临乱序、迟到、重复数据、幂等写入、状态管理、数据质量监控等问题。

从数仓角度看，它们都不是单纯的技术组件堆叠，而是数据链路设计方法。真正落地时都需要考虑 ODS 原始层保留、DWD 明细层清洗、DWS 汇总层聚合、ADS 应用层服务，以及元数据、血缘、监控、告警、权限和质量校验。

#### 十、Lambda 架构和 Kappa 架构的核心区别

| 对比项 | Lambda 架构 | Kappa 架构 |
| --- | --- | --- |
| 核心思想 | 批处理 + 流处理双链路 | 只保留流处理单链路 |
| 计算逻辑 | 离线一套逻辑，实时一套逻辑 | 实时和重算共用一套逻辑 |
| 准确性保障 | 离线批处理结果兜底和修正 | 依赖流处理 Exactly Once、状态和回放能力 |
| 实时性 | 实时链路低延迟，离线链路高延迟 | 整体低延迟 |
| 历史重算 | 批处理全量重算，成熟稳定 | 通过事件回放重算，依赖数据保留和流处理能力 |
| 开发维护成本 | 高，需要维护两套链路 | 低，主要维护一套链路 |
| 口径一致性 | 较难，双链路容易不一致 | 较好，同一套代码复用 |
| 资源成本 | 较高，批流两套资源 | 较低，但大规模回放时成本可能很高 |
| 适用场景 | 核心指标、复杂历史分析、强准确性场景 | 实时监控、实时特征、实时风控、链路较简单的实时指标 |

#### 十一、怎么选择 Lambda 还是 Kappa

如果业务既要求实时展示，又要求最终结果高度准确，并且有大量复杂离线分析、历史回溯、口径修正需求，Lambda 架构更稳妥。典型场景包括公司级核心经营指标、财务口径指标、复杂用户分析、长周期留存分析等。

如果业务更关注低延迟，计算逻辑相对清晰，数据可以通过 Kafka 或日志系统完整回放，团队的 Flink / Kafka / 状态管理能力比较成熟，那么 Kappa 架构更合适。典型场景包括实时风控、实时推荐特征、实时告警、实时看板、实时用户行为分析等。

在真实公司里，并不是非黑即白。很多团队会采用混合架构：核心离线数仓仍然保留批处理链路，实时指标和实时特征使用流处理链路；部分实时指标用 Kappa 思路统一代码逻辑，重要财务或经营指标仍然用 Lambda 思路由离线链路兜底。

#### 十二、面试官想考察什么

这道题表面上是在问两个架构定义，实际主要考察四类能力。

第一，是否理解实时数仓的基本架构。你不能只说“Lambda 是两条链路，Kappa 是一条链路”，还要能说明为什么需要两条链路，以及一条链路为什么可行。

第二，是否理解工程权衡。Lambda 的问题是复杂，Kappa 的问题是重算和状态压力。面试官希望看到你能结合业务场景做选择，而不是简单说哪个更先进。

第三，是否理解数据一致性。实时数仓最容易被追问的是口径一致、迟到数据、乱序、Exactly Once、幂等写入、历史回补等问题。

第四，是否理解架构演进。早期因为流处理不成熟，所以 Lambda 更常见；后来 Kafka、Flink、湖仓一体和流批一体能力增强，Kappa 和流批统一思想逐渐更受关注。

#### 十三、常见追问

##### 1. Lambda 架构中离线和实时结果不一致怎么办？

可以从四个角度回答：统一指标口径和元数据管理；统一维表版本和时间语义；实时链路支持迟到数据修正；最终以离线批处理结果做校准或覆盖。同时要建设数据质量校验，比如实时结果和离线结果按小时、按天做差异对账。

##### 2. Kappa 架构如何支持历史数据重算？

关键是原始事件必须可回放。可以通过 Kafka 长时间保留、日志归档、数据湖存储原始事件等方式保存数据。重算时使用同一套流处理逻辑，从指定 offset、时间点或历史事件文件重新消费，重新写出结果表。落地时要注意新旧结果隔离、幂等写入、状态初始化和资源隔离。

##### 3. Kappa 架构是不是一定比 Lambda 架构更好？

不是。Kappa 更简单，但前提是流处理系统足够成熟，且历史回放成本可接受。如果业务有大量复杂离线分析或全量重算需求，批处理仍然有优势。架构选择要看业务目标、数据规模、团队能力和一致性要求。

##### 4. Flink 流批一体是不是等于 Kappa 架构？

不完全等同。Flink 流批一体是一种计算引擎能力，表示同一个引擎可以处理有界数据和无界数据。Kappa 架构是一种系统架构思想，强调用一条流处理链路承接实时处理和历史重算。Flink 可以帮助实现 Kappa，但不能简单划等号。

#### 面试时可以怎么总结

可以这样回答：Lambda 架构是一种批流双链路架构，离线批处理负责全量、准确和可重算，实时流处理负责低延迟，查询层再把离线结果和实时增量合并。它的优点是准确性高、容错和历史重算能力强，适合核心指标和复杂历史分析；缺点是要维护两套逻辑，开发运维成本高，离线和实时口径容易不一致。Kappa 架构则取消独立批处理链路，把所有数据都看成事件流，用一套流处理逻辑同时处理实时数据和历史回放数据。它的优点是架构简单、口径更一致、延迟低，适合实时风控、实时看板、实时特征等场景；缺点是强依赖消息回放和流处理状态能力，大规模历史重算成本可能较高，也不一定适合复杂离线分析。实际选型时不能简单说谁更先进，而要看业务对实时性、准确性、重算能力、数据规模和团队技术能力的要求。

#### 知识扩展

- 实时数仓分层：实时链路也可以设计 ODS、DWD、DWS、ADS 分层，分别承接原始数据、清洗明细、聚合汇总和应用服务。
- Exactly Once：Kappa 架构尤其依赖端到端一致性，包括 Kafka 消费、Flink 状态、Checkpoint 和下游幂等写入。
- 事件时间和水位线：实时统计中要处理乱序和迟到数据，Watermark 决定窗口什么时候触发以及迟到数据如何处理。
- 维表关联：实时链路常见维表 Join 方式包括预加载维表、异步 IO 查询、广播维表、Temporal Join 等。
- 湖仓一体和流批一体：现代架构中，Iceberg、Hudi、Delta Lake、Flink、Spark 等技术正在弱化传统批流边界，让实时与离线的数据管理逐渐统一。
