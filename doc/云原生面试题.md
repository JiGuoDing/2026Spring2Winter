## 1. Kubernetes 基础面试题

### 1.1 描述如何在 Kubernetes 中创建一个 Pod，并给出示例配置文件

这道题建议从四个层次回答：资源定义、提交流程、控制面与节点面执行链路、以及可观测与排障。

核心结论：

- 在 Kubernetes 中创建 Pod 的本质是向 API Server 提交一个声明式对象 (Pod YAML)
- 后续由控制平面和节点组件协同把“期望状态”收敛为“实际运行状态”
- 面试里不要只说 `kubectl apply -f`，要讲清 Scheduler、Kubelet、CRI、CNI 的协作路径

#### 一、创建 Pod 的标准步骤

1. 编写 Pod 资源清单 (YAML)
2. 使用 `kubectl apply -f` 提交到 API Server
3. API Server 完成认证、鉴权、准入控制后写入 etcd
4. Scheduler 监听到 Pending Pod，为其选择 Node 并回写 `spec.nodeName`
5. 目标节点上的 Kubelet 通过 CRI (containerd/runc) 拉镜像并启动容器
6. Kubelet 调用 CNI 插件完成网络配置 (veth、网桥/overlay、IP 分配)
7. Pod 进入 Running，`kubectl get pod -o wide` 可看到节点与 IP

#### 二、可落地示例 (Pod YAML)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-demo
  namespace: default
  labels:
    app: nginx-demo
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      imagePullPolicy: IfNotPresent
      ports:
        - containerPort: 80
          name: http
      resources:
        requests:
          cpu: "100m"
          memory: "128Mi"
        limits:
          cpu: "500m"
          memory: "256Mi"
  restartPolicy: Always
```

说明：

- `requests/limits` 会影响调度和 cgroups 配额，是面试高频点
- 单独创建 Pod 常用于学习与调试，生产通常用 Deployment 管理副本与滚动升级

#### 三、常用命令行操作 (创建 + 验证 + 调试)

```bash
# 1) 创建 Pod
kubectl apply -f nginx-pod.yaml

# 2) 查看调度和运行状态
kubectl get pod nginx-demo -o wide

# 3) 查看事件 (调度失败、拉镜像失败等最先看这里)
kubectl describe pod nginx-demo

# 4) 进入容器验证进程
kubectl exec -it nginx-demo -- sh

# 5) 查看日志
kubectl logs nginx-demo
```

#### 四、底层机制 (面试加分点)

1. 为什么 Pod 会先 Pending

- Pod 刚写入 etcd 时还没有绑定节点，直到 Scheduler 完成打分与绑定才会进入下一阶段

2. Kubelet 如何创建容器

- Kubelet 不直接操作 runc，而是调用 CRI Runtime (常见 containerd)
- containerd 再调用 runc 按 OCI 规范创建容器 namespace 与 cgroups

3. 网络是何时完成的

- 容器进程创建前后，Kubelet 通过 CNI `ADD` 动作为 Pod 创建网络命名空间接口
- 常见实现会创建 veth pair 并挂到主机侧网桥或 overlay 设备

4. 为什么 Pod IP 在重建后会变

- Pod 是短生命周期对象，删除重建后通常会获得新 IP
- 稳定访问应通过 Service 提供虚拟 IP 与负载均衡

#### 五、常见问题与排障路径

- `ImagePullBackOff`:
  - 原因常见于镜像名错误、仓库鉴权失败、节点无法访问镜像仓库
  - 先查 `kubectl describe pod` 的 Events，再查节点网络与镜像拉取凭据
- `Pending` 长时间不调度:
  - 常见于资源不足、NodeSelector/Taint 不匹配、PVC 未绑定
  - 重点看调度事件中的 predicate/filter 失败原因
- `CrashLoopBackOff`:
  - 容器启动后反复退出，常见于启动命令错误、配置缺失、探针配置不合理
  - 结合 `kubectl logs --previous` 与 `describe` 事件定位

#### 六、面试收束模板

可以这样总结：

- 创建 Pod 是一次声明式提交，真正落地依赖 API Server、Scheduler、Kubelet、CRI、CNI 的控制闭环
- YAML 负责表达期望状态，控制器与节点组件负责持续逼近期望
- 线上问题优先看事件流与状态流转，而不是只看容器日志

知识扩展：
Pod 创建流程与 Deployment/ReplicaSet 强相关，因为生产环境通常不用裸 Pod 管理生命周期；与 Service 强相关，因为 Pod IP 不稳定需要稳定服务发现；与 NetworkPolicy 强相关，因为连通性故障常出在 CNI 策略与策略生效链路。

### 1.2 Scheduler 在决定调度 Pod 到哪个节点时，是如何为节点打分的？请具体说明打分的依据及逻辑

这道题建议按"调度框架架构 -> 过滤阶段 -> 打分阶段 -> 插件机制 -> 实战调优"回答，不要只说"选择资源最多的节点"。面试要体现你对 Kubernetes 调度器插件化架构和评分算法的具体理解。

核心结论：

- Kubernetes Scheduler 的打分是一个多维度评分过程，通过 Filter 阶段筛选出候选节点后，在 Score 阶段由多个评分插件对每个候选节点进行加权打分
- 最终选择得分最高的节点作为调度目标，分数相同时按节点名称排序保证确定性
- 调度器插件化设计允许自定义评分策略，这是实现高级调度需求（如亲和性、拓扑感知、碎片化整理）的关键

#### 一、调度框架架构概览

Kubernetes Scheduler 采用插件化架构，核心调度流程分为以下几个阶段：

1. **Queue sorting** (队列排序)：决定 Pending Pod 的调度顺序
2. **Pre-filter** (预过滤)：预处理 Pod 和节点信息，减少后续阶段开销
3. **Filter** (过滤)：剔除不满足基本条件的节点
4. **Post-filter** (后过滤)：在 Filter 之后执行一些补充逻辑
5. **Pre-score** (预打分)：生成打分所需的共享状态
6. **Score** (打分)：调用各评分插件对候选节点打分
7. **Normalize score** (分数归一化)：将各插件分数归一化到 [0, 100] 区间
8. **Reserve** (预留)：预留资源，锁定调度结果
9. **Permit** (许可)：允许或拒绝调度
10. **Pre-bind** (预绑定)：执行绑定前的准备工作
11. **Bind** (绑定)：将 Pod 绑定到节点
12. **Post-bind** (后绑定)：绑定完成后的清理工作

其中与打分直接相关的是 **Score** 和 **Normalize score** 阶段。

#### 二、过滤阶段 (Filter) 为打分做准备

在打分之前，Scheduler 会先通过 Filter 阶段进行节点筛选，只有通过所有 Filter 插件的节点才会进入打分阶段。

常见 Filter 条件包括：

- **PodFitsResources**：节点资源是否满足 Pod 的 requests (CPU、内存、临时存储、巨大页等)
- **PodFitsHost**：是否匹配 `spec.nodeName`
- **PodFitsHostPorts**：节点端口是否冲突
- **PodMatchNodeSelector**：是否匹配 `nodeSelector`、`nodeAffinity`
- **NoVolumeZoneConflict**：PV 的可用区是否与节点匹配
- **CheckNodeMemoryPressure**：内存压力节点是否允许调度
- **CheckNodeDiskPressure**：磁盘压力节点是否允许调度
- **TaintToleration**：是否容忍节点的污点

#### 三、打分阶段 (Score) 插件与评分逻辑

通过 Filter 阶段的节点会进入 Score 阶段，由多个评分插件进行加权打分。默认启用的评分插件及其评分逻辑如下：

##### 1. LeastAllocated (默认启用，权重 1)

**评分依据**：节点已分配资源越少，得分越高

**计算公式**：
```
score = (100 - (allocatedResources / allocatableResources) * 100) * weight
```

- 这里的资源通常指 CPU 和内存
- 目标是选择资源利用率最低的节点，实现"打散"效果

```go
// 伪代码：LeastAllocated 评分逻辑
func LeastAllocated(pod *v1.Pod, nodeName string) (int, error) {
    nodeInfo, _ := cache.GetNodeInfo(nodeName)
    cpuAllocated := nodeInfo.AllocatedCPU()
    memAllocated := nodeInfo.AllocatedMemory()
    cpuCapacity := nodeInfo.CapacityCPU()
    memCapacity := nodeInfo.CapacityMemory()

    cpuScore := 100 * (1 - float64(cpuAllocated)/float64(cpuCapacity))
    memScore := 100 * (1 - float64(memAllocated)/float64(memCapacity))

    return int((cpuScore+memScore)/2), nil
}
```

##### 2. MostAllocated (默认禁用，可通过配置启用)

**评分依据**：节点已分配资源越多，得分越高

**使用场景**：适合"堆积"场景，希望把 Pod 集中调度到少数节点，留出更多空闲节点用于后续大规模批处理任务

##### 3. BalancedAllocation (默认启用，权重 1)

**评分依据**：CPU 和内存资源使用率越均衡，得分越高

**计算公式**：
```
score = 100 - abs(cpuScore - memScore)
```

- 避免出现 CPU 几乎用完但内存还有很多，或反之的情况
- 与 LeastAllocated 配合使用，实现"打散且均衡"

##### 4. NodeAffinity (默认启用，权重 1)

**评分依据**：满足 nodeAffinity 软策略 (preferredDuringSchedulingIgnoredDuringExecution) 的程度

**评分逻辑**：
- 匹配 requiredDuringSchedulingIgnoredDuringExecution：节点直接通过 Filter，不参与打分
- 匹配 preferredDuringSchedulingIgnoredDuringExecution：每个匹配的 term 加分，权重由 `weight` 字段指定

```yaml
# Pod 示例：使用 nodeAffinity 软策略
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 60
          preference:
            matchExpressions:
              - key: disktype
                operator: In
                values:
                  - ssd
        - weight: 40
          preference:
            matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values:
                  - zone-a
```

##### 5. PodAffinity / PodAntiAffinity (默认启用，权重 1)

**评分依据**：满足 Pod 亲和性/反亲和性规则的程度

**评分逻辑**：
- PodAffinity：希望与某些 Pod 调度到同一拓扑域（如同节点、同 Zone、同 Region）
- PodAntiAffinity：希望与某些 Pod 调度到不同拓扑域

```yaml
# Pod 示例：使用 PodAntiAffinity 实现反亲和
spec:
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchLabels:
                app: web
            topologyKey: kubernetes.io/hostname
```

##### 6. TaintToleration (默认启用，权重 1)

**评分依据**：Pod 对节点污点的容忍程度

**评分逻辑**：
- 容忍越多污点，得分越高
- 匹配 `effect: NoSchedule` 的污点不参与评分，只在 Filter 阶段生效
- 匹配 `effect: PreferNoSchedule` 的污点参与评分

##### 7. ImageLocality (默认启用，权重 1)

**评分依据**：节点上是否已存在 Pod 所需的镜像

**评分逻辑**：
- 节点有所需镜像：得分 100 * 镜像存在数量 / 所需镜像总数
- 节点无所需镜像：得分 0
- 目标：优先调度到已有镜像的节点，减少镜像拉取时间

##### 8. NodeResources (默认启用，权重 1)

**评分依据**：与 LeastAllocated 类似，但支持自定义资源类型

**支持资源**：CPU、内存、存储、巨大页、GPU 等

##### 9. RequestedToCapacityRatio (默认禁用)

**评分依据**：自定义的资源分配比例评分函数

**可配置**：通过 `scoreConfig` 自定义资源权重和函数形状

#### 四、分数归一化与最终选择

各插件返回原始分数后，Scheduler 会进行归一化处理：

1. **Normalize score**：将所有分数映射到 [0, 100] 区间
2. **Weight and sum**：各插件分数乘以权重后求和
3. **最终得分** = Σ (pluginScore × pluginWeight)

```go
// 伪代码：最终分数计算
func calculateFinalScore(nodeScores map[string]map[string]int, weights map[string]int) map[string]int {
    finalScores := make(map[string]int)

    for nodeName, pluginScores := range nodeScores {
        var totalScore float64
        for pluginName, score := range pluginScores {
            weight := weights[pluginName]
            totalScore += float64(score) * float64(weight)
        }
        finalScores[nodeName] = int(totalScore)
    }

    // 选择得分最高的节点
    // 得分相同时按节点名称排序，保证确定性
    return finalScores
}
```

#### 五、自定义评分插件与高级调度场景

Kubernetes 调度器支持自定义评分插件，通过编写 Scheduler Framework 插件实现高级调度策略。

常见自定义场景：

1. **拓扑感知调度**：优先调度到同一拓扑域的节点，减少跨域网络开销
2. **资源碎片化整理**：优先调度到资源碎片最少的节点
3. **负载感知调度**：根据节点实时负载 (非静态资源分配) 进行调度
4. **成本优化**：在多可用区集群中优先调度到低成本区域

```go
// 自定义评分插件伪代码示例
package myschedulerplugin

import (
    "k8s.io/kubernetes/pkg/scheduler/framework"
)

type MyScorePlugin struct{}

func (pl *MyScorePlugin) Score(ctx context.Context, state *framework.CycleState, pod *v1.Pod, nodeName string) (int64, *framework.Status) {
    nodeInfo, _ := pl.handle.SnapshotSharedLister().NodeInfos().Get(nodeName)

    // 自定义评分逻辑：例如基于节点标签打分
    score := int64(0)
    if nodeInfo.Node().Labels["my-custom-label"] == "preferred" {
        score = 100
    }

    return score, nil
}

func (pl *MyScorePlugin) ScoreExtensions() framework.ScoreExtensions {
    return pl
}
```

#### 七、常见面试追问与排障视角

1. **为什么 Pod 调度到了资源更少的节点而不是更多的节点**

- 可能原因：各评分插件权重配置、BalancedAllocation 插件影响、亲和性/反亲和性规则
- 排查：查看调度器日志中的打分详情

2. **如何实现"尽量打散"或"尽量堆积"**

- 打散：启用 LeastAllocated + BalancedAllocation，禁用 MostAllocated
- 堆积：启用 MostAllocated，禁用 LeastAllocated

3. **调度器性能问题如何排查**

- 大量 Pending Pod 时，检查调度周期耗时
- 调优：调整 Filter 插件顺序、启用预过滤、使用 Score 插件缓存

4. **自定义调度策略如何落地**

- 方案一：编写自定义 Scheduler Framework 插件
- 方案二：使用 KubeSchedulerConfiguration 配置内置插件
- 方案三：使用 Descheduler 进行调度重平衡

知识扩展：
Scheduler 打分与 Pod 亲和性/反亲和性强相关，因为这是影响评分的重要因素；与 Descheduler 强相关，因为调度结果需要定期重平衡；与 Scheduler Framework 强相关，因为自定义调度逻辑通过插件机制扩展；与资源配额 (ResourceQuota) 强相关，因为调度时需要考虑 namespace 级别的资源限制。

### 1.3 解释什么是 Kubernetes，并描述其主要组件及其作用

这道题不要只回答"容器编排平台"。面试里建议按四层结构展开：定义与设计目标、控制平面组件、节点组件、以及一次完整请求如何在组件间流转。

核心结论：

- Kubernetes (K8s) 是一个面向容器化应用的声明式集群操作系统
- 它通过 API + 控制器模式，把用户声明的期望状态持续收敛为实际状态
- 其本质不是“启动容器工具”，而是一套分布式控制平面 + 节点执行平面的协同系统

#### 一、什么是 Kubernetes (本质与设计思想)

Kubernetes 最核心的思想有三点：

1. 声明式 API
   用户提交的是“我要什么” (Desired State)，不是“每一步怎么做”。
2. 控制器闭环
   Controller 通过 Watch 监听对象变化，持续 Reconcile (对齐期望与现实)。
3. 最终一致性
   分布式系统里不追求强同步一步到位，而是通过不断重试和状态收敛达到稳定结果。

可以把 K8s 理解为：

- etcd 存储“系统真相”
- API Server 提供统一入口与准入治理
- 各控制器和节点代理不断把现实世界拉回声明目标

#### 二、主要组件与作用 (控制平面)

##### 1. kube-apiserver

作用：集群唯一权威入口，负责认证、鉴权、准入控制、对象校验、版本化 API 输出。

关键点：

- 所有组件几乎都通过它读写状态 (而不是直接写 etcd)
- 通过 Watch 机制向控制器和客户端推送资源变化
- 典型高频问题包括 QPS 限流、缓存命中、长连接 Watch 中断

##### 2. etcd

作用：存储集群全量元数据与状态的分布式 KV 数据库。

关键点：

- 基于 Raft 共识保证一致性
- 保存 Pod、Deployment、ConfigMap、Lease 等关键对象
- 面试排障会涉及 compaction、defrag、snapshot、成员健康度

`etcdctl` 示例 (只读健康检查)：

```bash
# 需要在控制平面节点或具备证书环境执行
ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/peer.crt \
  --key=/etc/kubernetes/pki/etcd/peer.key \
  endpoint health
```

##### 3. kube-scheduler

作用：为未绑定节点的 Pod 选择最合适 Node。

核心流程：

- 过滤 (Filter)：剔除不满足资源/亲和性/污点容忍的节点
- 打分 (Score)：对候选节点按策略打分
- 绑定 (Bind)：把 `spec.nodeName` 回写到 Pod

关键点：

- 调度失败不是“容器问题”，而是调度约束问题
- 排障优先看 Pod Events 中的 `FailedScheduling`

##### 4. kube-controller-manager

作用：运行一组控制器，负责系统对象的持续对账。

常见控制器：

- Deployment/ReplicaSet Controller (副本数收敛)
- Node Controller (节点心跳与驱逐)
- EndpointSlice Controller (服务后端维护)
- Job/CronJob Controller (批任务编排)

本质：控制器 = Watch -> Diff -> Act，失败后按重试队列继续收敛。

#### 三、主要组件与作用 (节点平面)

##### 1. kubelet

作用：节点代理，负责把 PodSpec 转成真实运行容器。

关键职责：

- 监听分配到本节点的 Pod
- 调用 CRI 启停容器
- 调用 CNI 配网
- 调用 CSI 挂载存储
- 上报 Node/POD 状态与探针结果

##### 2. container runtime (containerd/runc)

作用：真正创建容器进程与隔离环境。

关键点：

- containerd 负责镜像与容器生命周期管理
- runc 按 OCI 规范创建 namespace 与 cgroups

##### 3. kube-proxy

作用：实现 Service 的四层转发能力。

关键点：

- iptables 模式：写 NAT 规则完成后端分发
- IPVS 模式：使用内核虚拟服务，规则规模大时性能更稳

##### 4. CNI 插件 (如 Calico/Cilium/Flannel)

作用：为 Pod 分配 IP 并打通跨节点网络连通性。

关键点：

- Pod 创建时执行 CNI `ADD`
- Pod 删除时执行 CNI `DEL`
- NetworkPolicy 生效也依赖 CNI 数据面实现 (iptables/eBPF)

这个链路说明了一个关键面试点：K8s 是“控制平面驱动的数据面执行系统”，每个组件都在闭环中有明确职责。

#### 五、常见面试追问与排障视角

1. 为什么 API Server 负载高会影响全局

- 因为它是唯一控制入口，控制器、调度器、kubelet 都依赖它

2. 为什么 etcd 抖动会导致集群异常

- 状态持久化与读取延迟上升，控制循环会整体变慢甚至失败

3. 为什么 Pod 运行慢不一定是镜像问题

4. 为什么 kube-proxy 问题会表现为“服务偶发不通”

- Service 转发表不一致、规则未及时刷新、后端健康状态波动都可能导致间歇故障

#### 六、面试收束模板

可以这样总结：

- Kubernetes 是声明式容器编排与集群控制系统，核心是“API + 控制器 + 最终一致性”
- 控制平面负责决策和状态收敛 (API Server、etcd、Scheduler、Controller Manager)
- 节点平面负责执行和上报 (kubelet、runtime、kube-proxy、CNI)
- 生产排障应按“提交 -> 持久化 -> 调度 -> 启动 -> 网络/存储 -> 服务转发”的链路逐段定位

知识扩展：
Kubernetes 组件协作与 Operator 模式强相关，因为 Operator 本质是定制 Controller 扩展控制平面能力；与 Service Mesh 强相关，因为流量治理会叠加在 kube-proxy/CNI 之上；与可观测体系强相关，因为控制环路问题需要通过 metrics、events、logs、traces 联合定位。

### 1.4 K8s 的 HPA 机制的底层原理是怎样的？请深入浅出地说明

这道题建议从 HPA 的设计思想与定位切入，然后拆解核心算法公式、Metrics 采集管道、Controller 控制回路、扩缩容决策流程，最后深入到冷却窗口、多指标合并策略等生产级细节。

核心结论：

- HPA 本质是一个控制回路 (Control Loop)，周期性比较"当前指标值"与"期望目标值"，通过 `desiredReplicas = ceil[currentReplicas * (currentMetricValue / desiredMetricValue)]` 公式计算目标副本数
- HPA 本身不采集指标——它从聚合 API (metrics.k8s.io / custom.metrics.k8s.io / external.metrics.k8s.io) 拉取数据，Metrics Server/Prometheus Adapter 负责指标生产和暴露
- 扩容与缩容并非对称操作：扩容有默认 3 分钟的冷却期（防止误报），缩容有默认 5 分钟的冷却期（防止抖动）
- 多个指标同时存在时，HPA 取"需要最多副本"的那个指标计算结果 (max policy)，确保弹性覆盖最苛刻的资源需求

#### 一、HPA 在 K8s 弹性体系中的定位

Kubernetes 弹性体系分为三层，HPA 处于中间层：

```
┌─────────────────────────────────────────────┐
│  Cluster Autoscaler (CA)                    │  ← 节点层弹性：根据 Pending Pod 增减 Node
├─────────────────────────────────────────────┤
│  Horizontal Pod Autoscaler (HPA)            │  ← Pod 层弹性：根据 CPU/Memory/自定义指标 增减 Pod 副本
├─────────────────────────────────────────────┤
│  Vertical Pod Autoscaler (VPA)              │  ← 资源层弹性：根据历史用量调整 Pod 的 Request/Limit
└─────────────────────────────────────────────┘
```

HPA 不负责决定 Pod 调度到哪台机器、也不负责修改 Pod 资源配置——它只做一件事：**根据指标计算应该有多少个 Pod 副本**，然后更新 Deployment/StatefulSet 的 `spec.replicas` 字段。

#### 二、核心算法公式

HPA 的核心是一个按比率缩放的比例控制器 (Proportional Controller)：

```
desiredReplicas = ceil[ currentReplicas × ( currentMetricValue / desiredMetricValue ) ]
```

**逐项拆解：**

| 变量 | 含义 | 来源 |
|------|------|------|
| `currentReplicas` | 当前运行的 Pod 副本数 | 从目标资源 (Deployment/RS) 的 `spec.replicas` 读取 |
| `currentMetricValue` | 当前所有 Pod 的指标平均值 | 从 Metrics API 拉取各 Pod 指标，汇总后取平均 |
| `desiredMetricValue` | 用户设定的目标值 (target) | HPA YAML 中 `targetAverageUtilization` 或 `targetAverageValue` |
| `ceil` | 向上取整 | 保证副本数至少能覆盖需求 |

**场景演算示例：**

假设有 3 个 Pod，目标 CPU 利用率为 50%，当前各 Pod CPU 分别为 80%、60%、70%：

```
currentMetricValue = (80% + 60% + 70%) / 3 = 70%
desiredReplicas = ceil[ 3 × (70% / 50%) ] = ceil[ 3 × 1.4 ] = ceil[4.2] = 5
// 需要扩容到 5 个 Pod
```

**防抖保护 (Tolerance)：**

HPA 不会对微小的指标波动做出反应。默认容忍度是 ±10%——只有当比例偏离 1.0 超过 10% 时才触发扩缩容：

```
ratio = currentMetricValue / desiredMetricValue
if 0.9 ≤ ratio ≤ 1.1:  // 不做任何操作
if ratio > 1.1:         // 触发扩容
if ratio < 0.9:         // 触发缩容
```

#### 三、Metrics 采集管道 —— 从 Pod 到 HPA 的数据链路

这是面试中最容易被追问的环节。HPA 本身不采集指标，它依赖三层 API：

```
Pod (cAdvisor)  ──►  Metrics Server  ──►  metrics.k8s.io API        ──► HPA Controller (Resource Metrics)
                                                                      │
Prometheus      ──►  Prometheus Adapter  ──►  custom.metrics.k8s.io  ──► HPA Controller (Custom Metrics)
                                                                      │
外部系统 (云监控) ──►  External Adapter    ──►  external.metrics.k8s.io ──► HPA Controller (External Metrics)
```

**三种指标类型对比如下：**

| 指标类型 | API Group | 数据来源 | 典型场景 | 示例 |
|----------|-----------|----------|----------|------|
| Resource Metrics | `metrics.k8s.io` | Metrics Server (Heapster 已废弃) | CPU/内存 基础资源 | Pod CPU 平均使用率 50% |
| Custom Metrics | `custom.metrics.k8s.io` | Prometheus Adapter / Datadog 等 | 应用自定义指标 | HTTP 请求 QPS、队列长度 |
| External Metrics | `external.metrics.k8s.io` | 云厂商监控 (AWS CloudWatch 等) | 集群外部指标 | SQS 队列深度、GCP Pub/Sub 积压 |

**核心技术细节：**

1. **Metrics Server** 是一个 `APIService` 聚合层，通过 kubelet 的 `/metrics/resource` 端点采集每个节点上 cAdvisor 暴露的容器资源数据，内存缓存后通过 API 对外提供。它不是 etcd 持久化的，每次重启数据丢失。
2. **聚合 API (Aggregated API)** 将自定义指标注册为 K8s API 资源，HPA Controller 通过标准的 REST 调用拉取——这意味着新指标源只需实现对应 API Service 即可无缝接入。
3. 指标采集有延迟 (默认 15s 采集间隔)，加上指标聚合和冷却窗口，HPA 对突发流量有约 1-2 分钟的反应延迟——**这是设计取舍而非缺陷**。

#### 四、HPA Controller 控制回路 —— 从指标拉取到副本更新

HPA Controller 是 kube-controller-manager 中的一个控制循环，默认每 15 秒执行一次 `reconcile()`。其核心伪代码如下：

```go
// HPA Controller reconcile 伪代码 (Go 语义)
func (a *HorizontalController) reconcile(hpa *autoscalingv2.HorizontalPodAutoscaler) error {
    // 1. 获取目标 Scale 对象 (Deployment/RS/StatefulSet)
    scale, targetRef := a.scaleForResourceMappings(hpa.Spec.ScaleTargetRef)
    
    // 2. 遍历 HPA 中定义的所有指标规格
    for _, metricSpec := range hpa.Spec.Metrics {
        switch metricSpec.Type {
        case autoscalingv2.ResourceMetricSourceType:
            // 从 metrics.k8s.io 拉取 Pod 级别的资源指标
            podMetrics, _ := a.metricsClient.GetResourceMetric(
                metricSpec.Resource.Name,       // "cpu" / "memory"
                hpa.Namespace,
                targetRef,
            )
            // 计算所有 Pod 的平均值
            currentValue = average(podMetrics)
            desiredValue = metricSpec.Resource.Target.AverageUtilization
        
        case autoscalingv2.PodMetricSourceType:
            // 从 custom.metrics.k8s.io 拉取 Pod 级别的自定义指标
            podMetrics, _ := a.customMetricsClient.GetMetric(
                metricSpec.Pods.Metric.Name,    // 例如 "http_requests_per_second"
                hpa.Namespace,
                targetRef,
            )
        
        case autoscalingv2.ObjectMetricSourceType:
            // 从 custom.metrics.k8s.io 拉取 Object 级别指标 (Ingress/Service)
            objMetric, _ := a.customMetricsClient.GetObjectMetric(...)
        
        case autoscalingv2.ExternalMetricSourceType:
            // 从 external.metrics.k8s.io 拉取集群外部指标
            extMetric, _ := a.externalMetricsClient.GetExternalMetric(...)
        }
        
        // 3. 应用公式计算该指标的建议副本数
        replicaCountProposal = ceil[ currentReplicas × (currentValue / desiredValue) ]
        
        // 4. 多个指标取最大值 (max policy)
        if replicaCountProposal > desiredReplicas {
            desiredReplicas = replicaCountProposal
        }
    }
    
    // 5. 稳定化窗口检查 — 缩容敏感保护
    if desiredReplicas < scale.Spec.Replicas {
        // 检查距上一次缩容是否超过 stabilizationWindowSeconds
        // 在稳定窗口内，HPA 会取窗口期内"最高"的建议值作为真实缩容目标
        // 这样可以避免指标短暂下降就立刻缩容
        desiredReplicas = a.normalizeDesiredReplicas(hpa, desiredReplicas, scale)
    }
    
    // 6. 冷却窗口检查
    if desiredReplicas > scale.Spec.Replicas &&
       time.Since(hpa.Status.LastScaleTime) < scaleUpCooldown {  // 默认 3min
        desiredReplicas = scale.Spec.Replicas  // 保持现状
    }
    if desiredReplicas < scale.Spec.Replicas &&
       time.Since(hpa.Status.LastScaleTime) < scaleDownCooldown {  // 默认 5min
        desiredReplicas = scale.Spec.Replicas  // 保持现状
    }
    
    // 7. 边界裁剪
    if hpa.Spec.MinReplicas != nil && desiredReplicas < *hpa.Spec.MinReplicas {
        desiredReplicas = *hpa.Spec.MinReplicas
    }
    if desiredReplicas > hpa.Spec.MaxReplicas {
        desiredReplicas = hpa.Spec.MaxReplicas
    }
    
    // 8. 更新目标资源的 spec.replicas
    if desiredReplicas != scale.Spec.Replicas {
        scale.Spec.Replicas = desiredReplicas
        a.scaleUpdater.Update(hpa.Namespace, scale)
    }
    
    return nil
}
```

#### 五、稳定化窗口 (Stabilization Window) 详解

这是 Kubernetes 1.18+ 引入的关键机制，专门解决缩容抖动问题。

**问题场景：** 流量在 1 分钟内剧烈波动 (10 QPS → 100 QPS → 10 QPS → 100 QPS)，如果没有稳定窗口，HPA 会反复扩容缩容，造成系统抖动。

**解决机制：** 在缩容时，HPA 会回溯稳定化窗口 (默认 300s) 内的所有历史推荐值，取**最大值**作为实际缩容目标：

```yaml
# HPA v2 behavior 配置
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300  # 缩容稳定化窗口：5分钟
    policies:
    - type: Percent
      value: 10                       # 每次缩容不超过当前副本数的 10%
      periodSeconds: 60               # 在 60 秒内
    selectPolicy: Min                 # 选择幅度最小的策略 (Chage 最小)
```

```
时间线:  T0       T+60       T+120      T+180      T+240      T+300 (当前)
推荐值:  5        8 (峰值)   3          4          6          2

真实缩容目标 = max(5, 8, 3, 4, 6, 2) = 8
// 即使当前推荐只有 2 个，实际也只缩容到 8 个——因为窗口内有过 8 个的建议
```

**扩容策略控制 (scaleUp behavior) 和缩容策略控制 (scaleDown behavior) 可独立配置：**

| 配置项 | 默认值 | 含义 |
|--------|--------|------|
| `stabilizationWindowSeconds` (扩容) | 0s | 扩容不做稳定化，立刻响应 |
| `stabilizationWindowSeconds` (缩容) | 300s | 缩容需看窗口期最大值 |
| `scaleUp cool-down` | 3min | 两次扩容间隔至少 3 分钟 |
| `scaleDown cool-down` | 5min | 两次缩容间隔至少 5 分钟 |
| `tolerance` | 0.1 | 指标比率 ±10% 以内不触发扩缩 |

```yaml
      - type: Percent
        value: 100                   # 最多翻倍 (增加 100% = 翻倍)
        periodSeconds: 60            # 每 60 秒内
      - type: Pods
        value: 4                     # 或者最多增加 4 个 Pod
        periodSeconds: 60
      selectPolicy: Max              # 取两种策略中扩容幅度大的 (更激进地应对流量)
    scaleDown:
      stabilizationWindowSeconds: 600 # 缩容稳定化窗口 10 分钟——保守缩容
      policies:
      - type: Percent
        value: 10                    # 每 60 秒最多缩容 10%
        periodSeconds: 60
      selectPolicy: Min              # 取幅度最小的策略 (Chage 最小的)
```

#### 八、常见面试追问与排障视角

**Q1: HPA 为什么扩容了但 Pod 状态还是 Pending？**

检查链路：HPA 更新了 Deployment `spec.replicas` → 新 Pod 被创建 → Scheduler 调度失败 (资源不足/亲和性不满足) → 状态 Pending。如果节点资源不足，需要 Cluster Autoscaler 配合——这就是 HPA + CA 的经典组合。

**Q2: HPA 与 VPA 能同时使用吗？**

不能直接同时作用于同一个 Workload。两者都会修改 `spec.replicas`/`resources`，同时启用会产生冲突 (K8s 1.18+ 有 basic protection 但非完全隔离)。推荐方案：对同一工作负载之使用 HPA 或 VPA 中的一个；如果需要两者效果，使用 VPA 的 `Off` 模式 (仅建议，不自动执行) + HPA 自动扩缩容。

**Q3: 为什么 CPU 使用率很低但 HPA 显示当前值很高？**

常见原因：(a) `targetAverageUtilization` 计算的是已用/请求比例，如果 Pod 的 `resources.requests.cpu` 设得过低，分母小导致百分比很高；(b) Metrics Server 有 1-2 分钟的延迟，看的是过去的指标；(c) 检查是否是多容器 Pod，HPA 聚合的是所有容器使用量之和。

**Q4: 内存为什么不适合做 HPA 的指标？**

因为内存是"黏性资源"——一旦分配就不会释放 (不像 CPU 会随任务完成而释放)，基于内存的 HPA 扩容后内存不会自动下降，导致持续扩容直到 `maxReplicas`。K8s 官方文档也建议慎用内存 HPA。如果一定需要，应配合 `AverageValue` 模式而非 `AverageUtilization`。

**Q5: HPA v1 和 v2 有什么区别？**

| 特性 | v1 (autoscaling/v1) | v2 (autoscaling/v2) |
|------|---------------------|---------------------|
| 支持指标 | 仅 CPU | CPU + Memory + Custom + External |
| 扩缩容行为控制 | 不支持 | 支持 `behavior` 字段精细控制 |
| 多指标 | 不支持 | 支持，取 max 策略 |
| 推荐使用 | 已被淘汰 | 当前主流，v2beta2 已废弃，用 v2 |

#### 九、面试收束模板

可以这样总结：

- HPA 本质是 K8s 内置的一个比例控制器 (Proportional Controller)，周期性地从 Metrics 聚合 API 拉取 Pod 指标，通过 `desiredReplicas = ceil[currentReplicas × (currentMetricValue / desiredMetricValue)]` 计算目标副本数
- 核心组件联动关系：Metrics Server (数据采集) → Aggregated API (数据暴露) → HPA Controller (计算与决策) → Scale Subresource (副本更新) → Scheduler (Pod 调度) → Kubelet (容器启动)
- 生产级 HPA 配置需关注三个关键参数：冷却窗口 (避免抖动)、稳定化窗口 (缩容保护)、容忍度 (避免过于敏感)
- 多指标并存时取 max 策略确保覆盖最苛刻的资源需求；扩缩容行为可通过 `behavior` 字段独立精细控制
- 排查 HPA 问题遵循"链路定位法"：指标源是否正常 → API 是否能拉取到数据 → Controller Log 中推荐值是否正确 → 冷却窗口是否在生效 → 目标资源是否被正确更新

知识扩展：
HPA 与 Cluster Autoscaler (CA) 强相关，因为 HPA 扩容出的 Pod 若因节点资源不足而 Pending，需要 CA 自动添加节点完成调度；与 KEDA (Kubernetes Event-Driven Autoscaling) 强相关，因为 KEDA 是 HPA 的超集 (可缩容到零、支持事件源触发)；与 VPA (Vertical Pod Autoscaler) 强相关，因为水平弹性 (增加副本) 与垂直弹性 (增大单 Pod 资源) 从不同维度优化资源利用率；与 Prometheus + Prometheus Adapter 强相关，因为生产环境中自定义指标 HPA 几乎都依赖 Prometheus 作为数据源；与 ResourceQuota 和 LimitRange 强相关，因为 HPA 的扩容上限受集群资源配额约束。

### 1.5 具体说说什么是潮汐调度

这道题建议按"概念定义与核心思想 -> 与被动式弹性的本质区别 -> 技术实现架构 -> 可落地方案 -> 生产细节与追问"回答，不能只说"根据时间段扩缩容"。

核心结论：

- 潮汐调度 (Tidal Scheduling) 是一种基于业务流量的时间变化规律，**预判性**地对集群资源 (Pod 副本数、节点规模) 进行定时扩缩容的资源管理策略
- 它的核心不是"看指标响应"，而是"看趋势预测"——在流量高峰到来**之前**完成扩容，在低谷到来**之前**完成缩容
- 本质是对 HPA 等被动式弹性机制的时间维度补充，解决的是"流量变化可预测但变化速率超过响应速度"的场景

#### 一、潮汐调度的背景与价值

互联网业务流量通常呈现明显的日周期规律：

```
流量
 ▲
 │          ┌──午高峰──┐     ┌──晚高峰──┐
 │         ╱            ╲   ╱            ╲
 │        ╱              ╲ ╱              ╲
 │   ┌──╱                 V                ╲──┐
 │  ╱                                          ╲
 │ ╱ 早高峰                                     ╲ 夜间低谷
 ├────┬────┬────┬────┬────┬────┬────┬────┬────┬───► 时间
 0    3    6    9    12   15   18   21   24
```

面对这种规律性流量波动，有三种资源管理策略：

| 策略 | 做法 | 优势 | 劣势 |
|------|------|------|------|
| 峰值预置 | 始终按最高峰配置资源 | 响应最快 | 成本最高，夜间浪费 60-70% |
| 被动弹性 (HPA) | 指标超阈值后触发扩容 | 按需分配 | 有 1-2 分钟延迟，高峰初期可能过载 |
| 潮汐调度 | 按时间表预判性扩缩容 | 成本低且提前就绪 | 依赖流量可预测性，突发流量需兜底 |

**潮汐调度的核心价值**：在流量可预测的前提下，实现"提前就绪 + 成本最优"的平衡——高峰前扩容避免过载，低谷前缩容避免浪费。

#### 二、潮汐调度与其他弹性机制的关系

潮汐调度不是替代 HPA/CA，而是与它们协同构成完整的弹性体系：

```
┌─────────────────────────────────────────────────────────────┐
│                     弹性决策层                                │
│  ┌──────────────┐  ┌──────────────┐  ┌───────────────────┐  │
│  │  潮汐调度     │  │  HPA         │  │  Cluster          │  │
│  │  (时间维度)   │  │  (指标维度)   │  │  Autoscaler       │  │
│  │  预判性       │  │  响应式       │  │  (节点维度)        │  │
│  └──────┬───────┘  └──────┬───────┘  └────────┬──────────┘  │
│         │                 │                    │              │
│         ▼                 ▼                    ▼              │
│  定时修改 HPA         根据实时指标         根据 Pending Pod    │
│  的 min/max           调整 replicas        增减节点            │
└─────────────────────────────────────────────────────────────┘
```

**协作逻辑**：

- 潮汐调度在 T-30min 设置 HPA 的 `minReplicas`/`maxReplicas` 上下界
- HPA 在上下界之内根据实时指标做细粒度弹性
- CA 根据 HPA 扩容后的 Pending Pod 做节点增减
- 三者各司其职：潮汐管"天花板和地板"，HPA 管"区间内的微调"，CA 管"地基够不够"

##### 方案一：CronJob 定时修改 HPA 配置 (最常用)

通过 Kubernetes CronJob 周期性地 patch HPA 的 `minReplicas` 和 `maxReplicas`，让 HPA 在不同时段拥有不同的弹性边界。

```yaml

metadata:
  name: tidal-scale-up-morning
  namespace: production
spec:
  schedule: "0 7 * * *"           # 每天 07:00 执行 (早高峰前 1 小时)

  concurrencyPolicy: Forbid        # 禁止并发执行，防止重复扩容
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3

    spec:
      backoffLimit: 2              # 失败重试 2 次
      template:
        spec:
          serviceAccountName: tidal-scheduler-sa
          restartPolicy: OnFailure
          containers:
          - name: patch-hpa
            image: bitnami/kubectl:1.30
            command:
            - /bin/sh
            - -c
            - |
              # 扩容 HPA 上限：为 8-9 点早高峰做准备
              kubectl patch hpa api-gateway-hpa -n production --type='merge' -p '{
                "spec": {
                  "minReplicas": 10,
                  "maxReplicas": 30,
                  "metrics": [{
                    "type": "Resource",
                    "resource": {
                      "name": "cpu",
                      "target": {
                        "type": "Utilization",
                        "averageUtilization": 60
                      }
                    }
                  }]
                }
              }'
              echo "$(date) Tidal scale-up (morning peak) applied: min=10, max=30"
```

#### 五、高级机制：潮汐调度与渐进式扩容

直接一次性将副本数拉到目标值可能造成瞬间资源压力，生产级方案通常采用渐进式扩容：

```python
# 渐进式潮汐扩容伪代码
import time

def gradual_tidal_scale(hpa_name, namespace, target_min, target_max, steps=3, interval_sec=300):
    """
    分步扩容：在 steps 次操作中逐步将 HPA 调整到目标配置
    避免一次性大规模扩容对集群和应用的冲击
    """
    current_hpa = get_hpa(hpa_name, namespace)
    current_min = current_hpa.spec.minReplicas
    current_max = current_hpa.spec.maxReplicas

    min_step = (target_min - current_min) // steps
    max_step = (target_max - current_max) // steps

    for i in range(steps):
        new_min = current_min + min_step * (i + 1)
        new_max = current_max + max_step * (i + 1)

        patch_hpa(hpa_name, namespace, minReplicas=new_min, maxReplicas=new_max)
        log.info(f"Step {i+1}/{steps}: HPA min={new_min}, max={new_max}")

        if i < steps - 1:
            time.sleep(interval_sec)  # 等待 HPA 和集群稳定
```

#### 六、常见面试追问

**Q1: 潮汐调度和 HPA 的核心区别是什么？**

| 维度 | 潮汐调度 | HPA |
|------|---------|-----|
| 驱动因素 | 时间计划 (Schedule) | 实时指标 (Metrics) |
| 响应方式 | 预判性，提前扩容 | 响应式，事后调整 |
| 变更对象 | HPA 的 min/max 边界 | Deployment 的 replicas |
| 适用场景 | 流量有明显时间规律 | 流量不可预测或变化剧烈 |
| 互相依赖 | 依赖 HPA 在边界内做微调 | 依赖潮汐调度设置合理边界 |

**Q2: 潮汐调度怎么处理突发流量？**

潮汐调度负责"地板"和"天花板"，突发流量由 HPA 在边界内响应。如果突发流量超过潮汐调度设置的 `maxReplicas`，有两条保底路径：(a) 潮汐调度的 `maxReplicas` 留有足够余量（通常按历史峰值的 1.5-2 倍设置）；(b) Cluster Autoscaler 作为最终兜底，当 Pod Pending 时自动添加节点。

**Q3: 有状态服务能做潮汐调度吗？**

有状态服务的潮汐调度更复杂，需要考虑：(a) StatefulSet 扩缩容是有序的，不能像 Deployment 一样瞬间拉起；(b) 缩容时需要确保数据已持久化或完成主从切换；(c) 需要配合 PDB (PodDisruptionBudget) 保证最低可用副本数。因此有状态服务的潮汐调度通常只做节点级潮汐（预置节点资源），不做 Pod 级潮汐。

#### 七、面试收束模板

可以这样总结：

- 潮汐调度是一种基于时间规律的预测性资源管理策略，核心思想是"在高峰到来前扩容，在低谷到来前缩容"
- 实现上通常通过 CronJob 定时 patch HPA 的 min/max 边界，让 HPA 在不同时段拥有不同的弹性空间
- 它与 HPA、CA 协同工作：潮汐管边界，HPA 管区间微调，CA 管节点供给
- 生产落地需关注渐进式扩容、配置回滚、兜底策略，以及有状态服务的特殊处理

知识扩展：
潮汐调度与 HPA 强相关，因为潮汐调度通过修改 HPA 配置实现扩缩容边界控制，HPA 在边界内做实时弹性；与 Cluster Autoscaler 强相关，因为 Pod 级潮汐扩容可能引发节点不足，需要 CA 配合添加节点；与 KEDA 强相关，因为 KEDA 的 Cron Scaler 原生支持基于 Cron 表达式的预测性伸缩，可直接替代手动 CronJob 方案；与 Karpenter 强相关，因为 Karpenter 的 NodePool 支持时间感知的节点供应策略，是节点级潮汐调度的更优实现；与 Prometheus 强相关，因为历史流量数据是制定潮汐调度时间表的数据基础，需要 Prometheus 提供长期指标存储与分析能力。

## 2. Docker 基础面试题

### 2.1 请解释 Docker 的基本概念及其核心组件

这道题建议按“概念 -> 组件 -> 内核机制 -> 执行链路 -> 排障视角”回答，不要只停留在“Docker 是容器工具”。

核心结论：

- Docker 是一个围绕 OCI 规范构建的容器打包、分发、运行平台
- 它通过镜像分层、容器运行时和宿主机内核隔离机制，把应用及依赖标准化交付
- 容器不是轻量虚拟机，本质是宿主机上的受限进程 (受 Namespace/Cgroups/Capabilities 等约束)

#### 一、Docker 的基本概念

##### 1. 镜像 (Image)

- 镜像是只读模板，包含应用代码、运行时依赖、启动命令等
- 镜像采用分层结构 (Layer)，复用层可显著降低构建与分发成本
- 常见格式符合 OCI Image 规范

##### 2. 容器 (Container)

- 容器是镜像的运行实例
- 运行时在镜像只读层之上叠加可写层 (Writable Layer)
- 容器生命周期短、可重建，配置和数据应尽量外置 (Volume/Config/Secret)

##### 3. 仓库 (Registry)

- Registry 用于存储和分发镜像 (如 Docker Hub、Harbor)
- 企业场景通常需要私有仓库、镜像签名、漏洞扫描与准入拦截

##### 4. Dockerfile

- Dockerfile 是镜像构建脚本，描述“如何从基础镜像构建业务镜像”
- 面试高频点是多阶段构建 (multi-stage build) 和最小化镜像

#### 二、Docker 核心组件与作用

##### 1. Docker CLI

作用：用户入口，用于执行 `docker build/run/pull/push/exec/logs` 等命令。

##### 2. Docker Engine (dockerd)

作用：守护进程，负责镜像管理、容器生命周期、网络与存储编排。

关键点：

- 对上接收 CLI/API 请求
- 对下调用 containerd/runc 执行容器
- 管理本地镜像层、容器元数据、网络与卷

##### 3. containerd

作用：容器生命周期管理器，负责镜像拉取、快照管理、任务管理。

关键点：

- 通过 snapshotter 管理镜像层与可写层
- 调用低层运行时 (通常 runc) 创建容器进程

##### 4. runc

作用：OCI Runtime 实现，真正执行 `clone/unshare/setns/cgroup` 等系统调用创建受限进程。

关键点：

- runc 本身不管理集群，也不做镜像分发
- 它负责把 OCI bundle 变成一个运行中的容器进程

##### 5. Registry + Distribution

作用：完成镜像分发链路，包括层上传、层下载、Manifest 管理与标签解析。

#### 三、底层 Linux 内核机制 (面试加分点)

Docker 的隔离与限制主要依赖以下内核能力：

1. Namespace (隔离视图)

- `pid`：隔离进程号空间
- `net`：隔离网络栈 (网卡、路由、iptables 视图)
- `mnt`：隔离挂载点
- `uts`：隔离主机名
- `ipc`：隔离进程间通信对象
- `user`：隔离用户与权限映射

2. Cgroups (资源配额)

- CPU 配额与权重
- 内存上限与 OOM 行为
- I/O 限速
- PIDs 数量限制

3. UnionFS / OverlayFS (分层文件系统)

- 下层只读镜像层 + 上层可写层合并为容器视图
- Copy-on-Write 降低磁盘占用与构建成本

4. Capabilities + Seccomp + LSM

- Capabilities：细粒度拆分 root 权限
- Seccomp：限制可调用系统调用集合
- AppArmor/SELinux：强制访问控制

#### 四、一次 `docker run` 的执行链路

```plaintext
docker run nginx:1.27
  ↓
CLI 调用 Docker Engine API
  ↓
dockerd 检查本地镜像，不存在则从 Registry 拉取
  ↓
containerd 创建容器元数据与快照层
  ↓
runc 创建 Namespace/Cgroups 并启动容器主进程
  ↓
Docker 网络驱动配置 veth/bridge/NAT
  ↓
容器进入 Running，stdout/stderr 接入日志驱动
```

这个链路可以很好回答“Docker 到底做了什么”而不是只说“起了一个容器”。

#### 五、可落地示例

##### 1. 多阶段 Dockerfile 示例

```dockerfile
# Stage 1: 构建阶段
FROM golang:1.22 AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o app ./cmd/server

# Stage 2: 运行阶段 (最小化镜像)

WORKDIR /app
COPY --from=builder /src/app /app/app
USER nonroot:nonroot
ENTRYPOINT ["/app/app"]
```

说明：

- 多阶段构建可显著减小镜像体积
- distroless 减少攻击面，适合生产环境

##### 2. 常用命令与排障命令

```bash
# 构建镜像
docker build -t demo/app:1.0.0 .

# 启动容器并映射端口
docker run -d --name app -p 8080:8080 demo/app:1.0.0

# 查看容器进程与资源限制
docker inspect app

# 查看日志
docker logs -f app

# 进入容器排障
docker exec -it app sh

# 查看实时资源使用

```

#### 六、常见误区与排障视角

1. 误区：容器和虚拟机是同一层隔离

- 不准确。容器共享宿主机内核，隔离边界弱于硬件虚拟化

2. 误区：镜像越小越好

- 不完整。应在“体积、安全、可观测、可调试”之间平衡

3. 误区：容器内数据天然可靠

- 错误。可写层随容器销毁而丢失，持久化必须依赖 Volume

4. 常见故障排障顺序

- 启动失败：先看 `docker logs`，再看 `docker inspect` 的 entrypoint/cmd
- 资源问题：看 `docker stats` 和 cgroup 限制
- 网络问题：看端口映射、bridge 网络、宿主机防火墙/NAT 规则

#### 七、面试收束模板

可以这样总结：

- Docker 的本质是基于 OCI 标准的容器交付与运行平台
- 核心组件是 CLI、dockerd、containerd、runc 与 Registry
- 关键内核机制是 Namespace、Cgroups、OverlayFS 与安全策略
- 生产落地要关注镜像治理、运行时安全、资源限制与可观测排障链路

知识扩展：
Docker 与 Kubernetes 强相关，因为 K8s 的 Pod 运行最终依赖 CRI 运行时和同一套内核隔离机制；与镜像供应链安全强相关，因为镜像签名、SBOM、漏洞扫描直接影响生产风险；与 Service Mesh 强相关，因为容器网络与 sidecar 注入都建立在容器网络命名空间和 CNI 数据面之上。

### 2.2 Docker 是如何进行容器间的资源隔离的？并且请具体描述分析其底层逻辑

这道题建议按"隔离维度 -> 底层内核机制 -> 系统调用链路 -> 实战验证 -> 排障视角"回答，不要只停留在"用 Namespace 和 Cgroups"。面试要体现你对 Linux 内核系统调用、数据结构和运行时行为的具体理解。

核心结论：

- Docker 的容器隔离不是单一机制，而是 Namespace (视图隔离) + Cgroups (资源限制) + UnionFS (文件系统隔离) + 安全机制 (Capabilities/Seccomp/LSM) 的协同
- 底层由 runc 通过 `clone/unshare/setns` 等系统调用完成内核对象的创建与绑定
- 理解隔离的边界很重要：容器共享宿主机内核，属于逻辑隔离而非硬件级虚拟化

#### 一、Namespace：隔离视图 (What you can see)

Namespace 是 Linux 内核提供的资源视图隔离机制，让进程只能看到属于自己的一组资源。

| Namespace | 系统调用参数      | 隔离资源                         |
| --------- | ----------------- | -------------------------------- |
| PID       | `CLONE_NEWPID`    | 进程号空间                       |
| Network   | `CLONE_NEWNET`    | 网络设备、端口、路由表、iptables |
| Mount     | `CLONE_NEWNS`     | 挂载点                           |
| UTS       | `CLONE_NEWUTS`    | 主机名与域名                     |
| IPC       | `CLONE_NEWIPC`    | 信号量、消息队列、共享内存       |
| User      | `CLONE_NEWUSER`   | UID/GID 映射                     |
| Cgroup    | `CLONE_NEWCGROUP` | Cgroup 根目录视图 (Linux 4.6+)   |
| Time      | `CLONE_NEWTIME`   | 容器独立时钟 (Linux 5.6+)        |

底层实现逻辑：

- 内核为每个 Namespace 维护独立的数据结构 (如 `struct pid_namespace`、`struct net`)
- `clone()` 创建新进程时通过 flags 指定要独立的 Namespace
- `unshare()` 让已有进程脱离当前 Namespace 并进入新 Namespace
- `setns()` 让进程加入一个已存在的 Namespace

实战验证命令：

```bash
# 查看某容器进程所属的 Namespace
# 以容器内 PID 1 为例 (替换 <container_pid> 为实际宿主机 PID)
ls -l /proc/<container_pid>/ns
# 输出示例：
# lrwxrwxrwx 1 root root 0 Apr 26 10:00 cgroup -> cgroup:[4026531835]
# lrwxrwxrwx 1 root root 0 Apr 26 10:00 ipc -> ipc:[4026532892]
# lrwxrwxrwx 1 root root 0 Apr 26 10:00 mnt -> mnt:[4026532890]
# lrwxrwxrwx 1 root root 0 Apr 26 10:00 net -> net:[4026532895]
# lrwxrwxrwx 1 root root 0 Apr 26 10:00 pid -> pid:[4026532893]
# lrwxrwxrwx 1 root root 0 Apr 26 10:00 uts -> uts:[4026532891]
```

```bash
# 进入容器的 Network Namespace 排障
nsenter -t <container_pid> -n ip addr
nsenter -t <container_pid> -n iptables -t nat -L -n -v

# 进入容器的 PID Namespace 排障 (可看到容器内进程视图)
nsenter -t <container_pid> -p -r ps aux
```

关键面试点：

- 两个容器可以拥有相同的 PID 1，因为它们处于不同的 PID Namespace
- 容器内 `lo` 网卡和 `eth0` 是独立的，因为 Network Namespace 隔离了内核协议栈
- User Namespace 允许容器内 root (UID 0) 映射到宿主机普通用户 (如 UID 100000)，降低特权逃逸风险

#### 二、Cgroups：限制资源 (What you can use)

Cgroups (Control Groups) 是 Linux 内核的资源限制与统计机制，Docker 通过它限制容器的 CPU、内存、IO 等资源使用。

底层架构：

- Cgroups v1：按子系统独立挂载 (cpu、memory、blkio 等)，路径 `/sys/fs/cgroup/<subsystem>/docker/<container_id>`
- Cgroups v2：统一层级，路径 `/sys/fs/cgroup/docker/<container_id>`，使用 BPF 和 eBPF 增强
- 内核通过 `cgroup_subsys_state` 结构将进程与资源限制策略关联

核心子系统与面试要点：

##### 1. CPU 子系统

- `cpu.shares`：相对权重 (默认 1024)，用于 CPU 时间片竞争
- `cpu.cfs_quota_us` / `cpu.cfs_period_us`：硬限制 (如配额 100000/周期 100000 = 1 核)
- `cpuset.cpus`：绑定到特定物理 CPU 核心

```bash
# 查看容器的 CPU Cgroup 限制 (Docker Cgroups v1 路径示例)
cat /sys/fs/cgroup/cpu/docker/<container_id>/cpu.cfs_quota_us
cat /sys/fs/cgroup/cpu/docker/<container_id>/cpu.cfs_period_us
# 若 quota = 50000, period = 100000，表示限制使用 0.5 核
```

##### 2. Memory 子系统

- `memory.limit_in_bytes`：内存硬上限
- `memory.soft_limit_in_bytes`：软限制 (不强制 OOM，但系统紧张时优先回收)
- `memory.kmem.limit_in_bytes`：内核内存限制 (防止内核级 OOM)
- OOM Killer 行为：当容器内存超过 limit，内核会杀死容器内评分最高的进程 (通常是占用内存最多的)

```bash
# 查看容器的内存限制
cat /sys/fs/cgroup/memory/docker/<container_id>/memory.limit_in_bytes

# 查看容器是否发生过 OOM
cat /sys/fs/cgroup/memory/docker/<container_id>/memory.oom_control
cat /sys/fs/cgroup/memory/docker/<container_id>/memory.failcnt
```

##### 3. Pids 子系统

- `pids.max`：限制容器内进程/线程数，防止 fork 炸弹

```bash
# 查看容器的 PID 限制
cat /sys/fs/cgroup/pids/docker/<container_id>/pids.max
cat /sys/fs/cgroup/pids/docker/<container_id>/pids.current
```

Docker 运行时的资源限制示例：

```bash
# 启动一个资源受限的容器
docker run -d \
  --name limited-app \
  --cpus="1.5" \
  --memory="512m" \
  --memory-swap="512m" \
  --pids-limit=100 \
  --blkio-weight=300 \
  nginx:1.27

# --cpus="1.5" 底层映射为 cpu.cfs_quota_us=150000 / cpu.cfs_period_us=100000
# --memory="512m" 底层映射为 memory.limit_in_bytes=536870912
# --pids-limit=100 底层映射为 pids.max=100
```

#### 三、文件系统隔离：OverlayFS 与 Rootfs

容器需要独立的文件系统视图，但又要避免镜像层被修改。

底层逻辑：

- Docker 使用 OverlayFS (或 aufs/zfs/btrfs) 实现联合挂载
- 容器启动时，内核将多个只读层 (lowerdir) 和一个可写层 (upperdir) 合并为统一视图 (merged)
- 写操作触发 Copy-on-Write：修改只读层文件时，内核将其复制到可写层再修改

挂载结构：

```plaintext
lowerdir=/var/lib/docker/overlay2/l/XXX:/var/lib/docker/overlay2/l/YYY  (镜像层)
upperdir=/var/lib/docker/overlay2/<container_id>/diff                   (容器可写层)
workdir=/var/lib/docker/overlay2/<container_id>/work                    (工作目录)
merged=/var/lib/docker/overlay2/<container_id>/merged                   (容器根目录视图)
```

验证命令：

```bash
# 查看容器的 OverlayFS 挂载详情
docker inspect -f '{{.GraphDriver.Data}}' <container_id>

# 查看宿主机上的挂载点
mount | grep overlay | grep <container_id>

# 直接查看容器在宿主机上的可写层文件
ls /var/lib/docker/overlay2/<container_id>/diff
```

面试要点：

- OverlayFS 让容器看似拥有完整文件系统，实际数据可能分散在多个层
- 大量写操作会导致 Copy-on-Write 放大，影响 IO 性能 (数据库类应用建议用 Volume)
- 容器删除后，upperdir (可写层) 也会被清理，因此重要数据必须外挂 Volume

#### 四、安全加固机制：Capabilities + Seccomp + LSM

隔离不等于安全，Docker 还通过以下机制缩小攻击面：

##### 1. Linux Capabilities

- 传统 root 权限被拆分为多个细粒度 Capability (如 `CAP_NET_ADMIN`、`CAP_SYS_PTRACE`)
- 默认 Docker 容器会丢弃大部分危险 Capability，只保留 14 个安全的基础 Capability
- 可通过 `--cap-add` 和 `--cap-drop` 精细控制

```bash
# 查看容器当前的 Capability
docker inspect -f '{{.HostConfig.CapAdd}} {{.HostConfig.CapDrop}}' <container_id>

# 启动一个禁用所有 Capability 的容器 (最严格)
docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE nginx:1.27

# 查看进程的 Capability 位图 (宿主机视角)
cat /proc/<container_pid>/status | grep Cap
# CapInh: 继承的 Capability
# CapPrm: 允许的 Capability
# CapEff: 生效的 Capability
# CapBnd: 边界 Capability (上限)
```

##### 2. Seccomp (Secure Computing Mode)

- 通过 BPF 过滤器限制容器进程可发起的系统调用
- Docker 默认启用 seccomp profile，禁止约 44 个危险系统调用 (如 `mount`、`umount2`、`pivot_root` 等)
- 可通过 `--security-opt seccomp=profile.json` 自定义

```bash
# 查看容器的 seccomp 状态
docker inspect -f '{{.HostConfig.SecurityOpt}}' <container_id>

# 以无 seccomp 限制运行 (不推荐生产环境)
docker run --security-opt seccomp=unconfined nginx:1.27
```

##### 3. LSM (Linux Security Modules)：AppArmor / SELinux

- AppArmor (Ubuntu/Debian 默认)：基于路径的强制访问控制
- SELinux (RHEL/CentOS 默认)：基于标签 (label) 的强制访问控制
- Docker 默认启用 AppArmor profile `docker-default`，限制容器对宿主机文件的访问

```bash
# 查看容器的 AppArmor 策略
docker inspect -f '{{.AppArmorProfile}}' <container_id>

# 查看进程的 AppArmor 状态
cat /proc/<container_pid>/attr/current
# 输出示例：docker-default (enforce) 表示正在强制执行 docker-default 策略
```

#### 五、一次容器启动时的隔离链路 (runc 视角)

当 `docker run` 执行时，runc 通过以下步骤建立完整隔离环境：

```plaintext
runc create <container-id>
  ↓
1. 创建 Namespace：调用 unshare(CLONE_NEWNS|CLONE_NEWPID|CLONE_NEWNET|...)
  ↓
2. 设置 Cgroups：向 /sys/fs/cgroup/ 各子系统写入限制参数，并将容器 PID 加入 tasks 文件
  ↓
3. 挂载 Rootfs：通过 mount(MS_BIND|MS_REC, ...) 挂载 OverlayFS 到容器根目录
  ↓
4. 写入 UID/GID 映射：配置 /proc/<pid>/uid_map 和 gid_map (User Namespace)
  ↓
5. 应用 Seccomp 过滤器：通过 prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, ...) 加载 BPF 规则
  ↓
6. 应用 Capabilities：通过 capset() 系统调用设置进程的 Capability 位图
  ↓
7. pivot_root 切换根目录：将容器根目录切换为 merged 层，旧根挂载到 /.pivot_root 后卸载
  ↓
8. execve() 启动用户进程：容器主进程开始执行 entrypoint/cmd
```

面试要点：

- `pivot_root` 与 `chroot` 的区别：`pivot_root` 更安全，它改变了进程的根挂载点和当前工作目录，而 `chroot` 只是改变了根目录查找路径
- 容器内执行 `ps aux` 只能看到 PID Namespace 内的进程，是因为 `/proc` 挂载在新的 PID Namespace 下

#### 六、常见问题与排障路径

1. 资源限制未生效：
   - 检查 Cgroups v1/v2 混合环境是否导致配置路径错误
   - 检查宿主机内核是否编译了对应的 Cgroup 子系统 (`grep CGROUP /boot/config-$(uname -r)`)

2. 容器内存 OOM：
   - 先看 `docker stats` 确认是否达到 limit
   - 再看宿主机 `dmesg -T | grep -i "killed process"` 找到 OOM Killer 日志
   - 若 `memory.failcnt` 持续增长，说明频繁触发限制

3. 网络不通但端口已映射：
   - 进入容器 Network Namespace：`nsenter -t <pid> -n`
   - 检查容器内 iptables、路由表、网卡状态
   - 检查宿主机是否开启 ip_forward：`cat /proc/sys/net/ipv4/ip_forward`

4. 权限不足 (Permission denied)：
   - 检查 Capabilities：`cat /proc/<pid>/status | grep Cap`
   - 检查 AppArmor/SELinux 日志：`dmesg | grep -i apparmor`
   - 检查文件系统挂载选项是否包含 `noexec`

5. 容器内看到宿主机进程：
   - 说明 PID Namespace 未正确创建，常见于特权模式 (`--privileged`) 或 `hostPID: true` 的 Pod

#### 七、面试收束模板

可以这样总结：

- Docker 的资源隔离是 Namespace (视图隔离) + Cgroups (资源限制) + OverlayFS (文件系统隔离) + 安全机制 (Capabilities/Seccomp/LSM) 的组合拳
- Namespace 通过内核数据结构复制实现视图分离，Cgroups 通过内核调度器与资源计数器实现硬限制
- runc 通过 `clone/unshare/setns`、`mount`、`pivot_root`、`prctl` 等系统调用完成这些隔离的落地
- 容器隔离是逻辑隔离，共享宿主机内核，与虚拟机有本质区别
- 排障时应按 Namespace -> Cgroups -> 文件系统挂载 -> 安全策略的层次逐层定位

知识扩展：
Docker 容器隔离与 Kubernetes 强相关，因为 K8s 通过 SecurityContext 将 Namespace/Capabilities/SELinux 等配置下发到 Pod；与 CRI 运行时强相关，因为 containerd/runc 才是实际执行隔离系统调用的组件；与 eBPF 可观测强相关，因为内核级排障工具 (如 bcc、bpftrace) 可以穿透 Namespace 边界观察容器内行为；与云安全强相关，因为容器逃逸 (Container Escape) 的本质就是突破 Namespace/Cgroups 边界获取宿主机权限。
