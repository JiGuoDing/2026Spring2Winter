# 数据仓库学习 Roadmap

> 适用对象：具备 Flink 基础且熟悉 Flink，了解 Ray，但 SQL 薄弱、即将进入数据开发工程师实习岗位的学习者。
>
> 默认假设：距离入职还有 2 到 4 周；每天可投入 2 到 3 小时；岗位以离线数仓为主，可能接触实时数仓；技术栈以 Hive SQL、Spark SQL、Flink SQL、Kafka、调度系统和 OLAP 引擎为主；当前目标是先能在实习中干活，再逐步进阶。

## 一、你的当前基础与学习策略

### 1. 当前优势

你已经具备 Flink 基础，而且特别熟悉 Flink，这是进入实时数仓方向的明显优势：

- 你理解事件时间、Watermark、窗口、状态、Checkpoint、Exactly-once，这些都是实时数仓的核心概念。
- 你更容易理解 Kafka + Flink + OLAP Sink 的实时链路。
- 你能从计算引擎角度理解任务运行、状态恢复、延迟、吞吐和容错。

你也具备 Ray 基础，这有助于理解分布式计算、任务调度、资源管理、机器学习数据处理和未来 AI Agent 后端。但在当前数仓入门阶段，Ray 不是主线，不应抢占 SQL、建模、调度、质量这些基础能力。

### 2. 当前最大短板

当前最需要补齐的是 SQL。对数据开发来说，SQL 不是简单 CRUD，而是数据加工、维度关联、指标计算、数据清洗、分层沉淀和质量校验的核心语言。

入职后高频工作不会只是写 `select * from table`，而是：

- 从 ODS 清洗明细数据到 DWD。
- 使用 JOIN 关联业务表、维表和事实表。
- 使用 GROUP BY、窗口函数、日期函数计算指标。
- 写 Hive SQL、Spark SQL、Flink SQL。
- 排查为什么某个指标和业务口径不一致。
- 处理分区、重跑、补数、数据倾斜和调度依赖。

### 3. 总体学习策略

学习顺序应该是：

1. 先补 SQL，尤其是 JOIN、聚合、窗口函数、日期处理、留存、漏斗、TopN、同比环比。
2. 再理解数仓分层和核心概念，知道 ODS、DWD、DWS、ADS、DIM 各自负责什么。
3. 然后练离线数仓，因为大多数数据开发实习岗位首先接触离线链路。
4. 再迁移到实时数仓，用你的 Flink 优势形成差异化。
5. 同步学习维度建模、指标体系、调度、数据质量和治理。
6. 最后把 Agent 作为长期扩展方向，围绕元数据、指标口径、SQL Copilot 和质量诊断做探索。

你需要从“写计算任务”的视角，逐步转向“建设数据资产”的视角。数仓不只是让任务跑起来，还要让数据稳定、准确、可复用、可追溯、可治理。

## 三、阶段 1：SQL 快速补齐

### 学习目标

本阶段目标是让 SQL 从“能写简单查询”提升到“能完成数仓日常开发”。你至少要能独立完成清洗、关联、聚合、窗口计算、分区处理、留存、漏斗、TopN、同比环比和拉链表相关 SQL。

| 必须马上掌握 | INNER JOIN、LEFT JOIN、RIGHT JOIN、FULL JOIN | 数仓中经常要关联事实表、维表、明细表 |

| 必须马上掌握 | UNION、UNION ALL、子查询、CTE | 拆解复杂逻辑，提升 SQL 可读性 |
| 入职后高频使用 | ROW_NUMBER、RANK、DENSE_RANK | 去重、排序、TopN、取最新记录 |
| 入职后高频使用 | LAG、LEAD | 环比、前后状态对比、行为路径分析 |
| 入职后高频使用 | SUM OVER、COUNT OVER | 累计指标、分组内统计、滑动分析 |
| 入职后高频使用 | 分区字段、分区过滤、动态分区 | Hive/Spark SQL 日常开发核心 |
| 后续进阶掌握 | 留存、漏斗、同比、环比、拉链表 SQL | 从基础开发进入指标和模型建设 |

### 推荐练习内容

1. 基础查询练习
   - 从订单表中筛选最近 7 天订单。
   - 按天统计订单数、支付用户数、GMV。
   - 使用 `CASE WHEN` 统计不同订单状态数量。

2. JOIN 练习
   - 订单表 JOIN 用户表，统计不同城市的订单金额。
   - 订单明细表 JOIN 商品维表，统计类目 GMV。
   - 使用 LEFT JOIN 找出有访问但无下单的用户。

3. 窗口函数练习
   - 使用 `ROW_NUMBER()` 取每个用户最近一笔订单。
   - 使用 `RANK()` 和 `DENSE_RANK()` 做类目销售 TopN。
   - 使用 `LAG()` 计算用户两次下单间隔。
   - 使用 `SUM() OVER` 计算用户累计消费金额。

4. 数仓指标练习
   - 日活跃用户 DAU。
   - 新增用户数。
   - 次日留存率。
   - 商品详情页到支付成功的漏斗转化率。
   - GMV 日环比和周同比。

5. 拉链表练习
   - 根据用户状态变更日志生成 SCD Type 2 风格的历史表。
   - 维护 `start_date`、`end_date`、`is_current` 字段。

### 简短 SQL 示例

取每个用户最近一笔订单：

```sql
WITH ranked_order AS (
  SELECT
    user_id,
    order_id,
    pay_time,
    amount,
    ROW_NUMBER() OVER (
      PARTITION BY user_id
      ORDER BY pay_time DESC
    ) AS rn
  FROM dwd_order_detail
  WHERE dt = '${bizdate}'
)
SELECT
  user_id,
  order_id,
  pay_time,
  amount
FROM ranked_order
WHERE rn = 1;
```

计算每日 GMV 和环比：

```sql
WITH daily_gmv AS (
  SELECT
    dt,
    SUM(pay_amount) AS gmv
  FROM dwd_order_detail
  WHERE dt BETWEEN '${start_date}' AND '${end_date}'
  GROUP BY dt
)
SELECT
  dt,
  gmv,
  LAG(gmv) OVER (ORDER BY dt) AS prev_day_gmv,
  (gmv - LAG(gmv) OVER (ORDER BY dt)) / LAG(gmv) OVER (ORDER BY dt) AS day_over_day_rate
FROM daily_gmv;
```

### Hive SQL、Spark SQL、Flink SQL 的差异

| 维度 | Hive SQL | Spark SQL | Flink SQL |
| --- | --- | --- | --- |
| 常见场景 | 离线批处理、T+1 数仓 | 离线和准实时批处理 | 实时流处理、实时数仓 |
| 执行特点 | 适合大规模离线任务 | 执行效率较高，生态丰富 | 面向无界流、状态和事件时间 |
| 时间处理 | 多用于分区日期和批处理时间 | 多用于批任务时间计算 | 重点关注事件时间、Watermark |
| JOIN | 离线大表 JOIN、MapJoin | Broadcast Join、Shuffle Join | 流流 JOIN、维表 JOIN、Temporal Join |
| 结果写入 | Hive 表、HDFS | Hive、湖格式、OLAP | Kafka、Doris、ClickHouse、StarRocks、Iceberg、Hudi |

## 四、阶段 2：数据仓库基础概念

### 学习目标

本阶段目标是建立数仓全局认知。你要知道数据为什么要分层，ODS、DWD、DWS、ADS、DIM 分别解决什么问题，为什么不能所有需求都直接查 ODS，以及指标口径为什么必须统一。

### 核心知识

| 概念 | 你需要理解的重点 |
| --- | --- |
| 数据仓库 | 面向分析、主题集成、相对稳定、反映历史变化的数据系统 |
| OLTP | 面向交易系统，如下单、支付、库存扣减，强调高并发写入和事务 |
| OLAP | 面向分析系统，如报表、看板、指标分析，强调复杂查询和聚合 |
| 数据仓库和数据库 | 数据库服务业务交易，数据仓库服务分析决策 |
| 数据湖 | 存储原始、多格式、大规模数据，结构可后置 |
| 湖仓一体 | 结合数据湖灵活性和数据仓库治理能力 |
| ETL | 先抽取、转换，再加载到目标系统 |
| ELT | 先加载，再在目标系统内转换 |
| 批处理 | 固定周期处理有界数据，如每天凌晨跑 T+1 |
| 流处理 | 持续处理无界数据，如实时订单 GMV |
| 离线数仓 | 强调稳定、准确、成本可控，常用于报表和经营分析 |
| 实时数仓 | 强调低延迟、状态处理、实时指标和一致性 |

### 数仓分层

| 层级 | 全称 | 主要职责 | 数据粒度 |
| --- | --- | --- | --- |
| ODS | Operational Data Store | 原始数据接入层，尽量保持业务系统原貌 | 与源系统接近，粒度最细 |
| DWD | Data Warehouse Detail | 明细数据层，完成清洗、标准化、轻度建模 | 明细粒度，面向业务过程 |
| DIM | Dimension | 维度层，沉淀用户、商品、店铺、地区等维度 | 一行一个维度对象或维度状态 |
| DWS | Data Warehouse Summary | 汇总层，按主题、维度、周期聚合公共指标 | 中间汇总粒度 |
| ADS | Application Data Service | 应用层，面向报表、看板、接口和具体需求 | 面向应用，粒度最贴近使用方 |

### 为什么数仓要分层

数仓分层的本质是降低复杂度、提升复用性、统一口径、便于治理。

- ODS 保留原始数据，方便追溯。
- DWD 清洗和标准化，避免每个需求都重复处理脏数据。
- DIM 统一维度信息，避免用户、商品、地区等解释不一致。
- DWS 沉淀公共汇总，避免重复计算。
- ADS 面向具体业务场景，保证报表和应用查询简单稳定。

如果所有需求都直接查 ODS，会出现几个问题：

- 每个需求都重复写清洗逻辑。
- 同一个指标不同人算出来不一致。
- SQL 复杂、慢、难维护。
- 数据质量问题很难定位。
- 上游字段变化会直接影响所有下游报表。

### 指标口径为什么重要

指标口径决定“这个数到底怎么算”。例如“支付用户数”可能有多种口径：

- 按支付成功时间统计。
- 按订单创建时间统计。
- 是否排除退款订单。
- 是否排除测试账号。
- 是否按自然日、业务日或时区统计。

如果口径不统一，业务会议里就会出现“两个部门都说自己是对的”的问题。数仓的价值之一，就是把指标定义、维度、时间周期、过滤条件和数据来源沉淀下来。

### 典型电商离线链路

假设业务库有三张 MySQL 表：

- `order_info`：订单主表。
- `user_info`：用户表。
- `product_info`：商品表。

进入数仓后可以这样设计：

| 层级 | 示例表 | 说明 |
| --- | --- | --- |
| ODS | `ods_order_info_di` | 每日增量同步订单原始数据 |
| ODS | `ods_user_info_df` | 每日全量或快照同步用户数据 |
| ODS | `ods_product_info_df` | 商品原始快照数据 |
| DWD | `dwd_trade_order_detail_di` | 清洗订单明细，处理金额、状态、时间字段 |
| DIM | `dim_user_df` | 用户维表，统一性别、年龄段、城市等维度 |
| DIM | `dim_product_df` | 商品维表，统一类目、品牌、上下架状态 |
| DWS | `dws_user_trade_1d` | 按用户汇总每日交易行为 |
| DWS | `dws_product_trade_1d` | 按商品汇总每日交易表现 |
| ADS | `ads_trade_dashboard_1d` | 面向看板的 GMV、订单数、支付用户数等指标 |

链路示例：

1. MySQL 订单表、用户表、商品表同步到 ODS。
2. ODS 经过字段清洗、去重、状态映射进入 DWD。
3. DWD 关联 DIM，生成面向分析的明细宽表或汇总表。
4. DWS 按用户、商品、类目、地区、日期汇总。
5. ADS 面向报表、看板、接口输出指标。

### 离线开发必须理解的几个问题

#### 1. 分区表为什么重要

离线数仓数据量通常很大，按日期分区可以让任务只扫描目标日期数据。例如查询某天订单时只扫 `dt='2026-06-08'`，而不是全表扫描。

#### 2. 小文件问题是什么

大量小文件会增加 NameNode 压力，也会让 Spark/Hive 启动大量小任务，拖慢查询。常见处理方式包括合并小文件、控制任务并发、合理设置输出文件大小。

#### 3. 数据倾斜是什么

当某些 key 的数据量特别大时，少数 reducer 或 task 会处理远多于其他节点的数据，导致任务长尾。常见处理方式包括过滤异常 key、加盐、拆分热点 key、MapJoin/Broadcast Join。

#### 4. 幂等为什么重要

同一个任务同一个业务日期重复跑多次，结果应该一致。常见方式是先删除目标分区再写入，或使用覆盖写入。

### Flink 背景如何迁移到数仓

你的 Flink 背景会帮助你快速理解：

- 为什么实时指标需要事件时间，而不是简单用处理时间。
- 为什么 Watermark 决定窗口何时触发。
- 为什么状态大小会影响任务稳定性。
- 为什么 Checkpoint 和 Exactly-once 影响数据一致性。
- 为什么维表 Join、Upsert Sink、乱序和迟到数据是实时数仓高频问题。

但需要注意：实时数仓不是简单写 Flink 任务。数仓场景更关注数据模型、指标口径、分层复用、链路稳定性、数据质量和离线实时一致性。

### 实时数仓分层示例

| 层级 | 示例 | 说明 |
| --- | --- | --- |
| 实时 ODS | MySQL Binlog 进入 Kafka | 原始变更事件，尽量保留源数据 |

| 实时 ADS | 实时大屏 GMV、订单数、转化率 | 面向看板或接口 |

### 离线实时一致性

实时指标常用于“现在发生了什么”，离线指标常用于“最终准确结果”。两者口径必须尽量一致：

- 使用同一套指标定义。
- 使用一致的过滤条件。
- 明确实时链路是否包含退款、取消、延迟到达数据。
- 明确实时结果是否会被离线 T+1 修正。
- 对业务说明实时数据是预估、准实时还是最终值。

## 七、阶段 5：维度建模与指标体系

### 学习目标

本阶段目标是从“会写 SQL”升级到“会设计数仓模型”。你要理解事实表、维度表、粒度、业务过程、指标口径、一致性维度和一致性事实。

### 核心知识

| 模块 | 需要掌握的内容 |
| --- | --- |
| 建模思想 | Kimball 维度建模、Inmon 范式建模 |
| 模型形态 | 星型模型、雪花模型 |
| 事实表 | 事务事实表、周期快照事实表、累积快照事实表 |
| 维度表 | 用户维、商品维、地区维、时间维、渠道维 |
| 特殊维度 | 退化维度、缓慢变化维 |
| SCD | SCD Type 1 覆盖更新、SCD Type 2 保存历史 |
| 粒度 | 一张表每一行代表什么 |
| 主键与业务键 | 技术唯一标识和业务标识的区别 |
| 指标 | 原子指标、派生指标、复合指标 |
| 指标组成 | 维度、修饰词、时间周期、统计口径 |
| 一致性 | 一致性维度、一致性事实、统一口径 |

### 建模的本质

建模的本质是服务分析，而不是简单搬运数据。一个好的模型应该让业务问题更容易回答：

- 用户每天买了多少？
- 哪些类目增长最快？
- 新用户留存如何？
- 退款率为什么上升？
- 某个渠道的转化漏斗在哪里掉得最多？

事实表设计最重要的是确定业务过程和数据粒度。例如订单支付事实表的粒度可以是“一行代表一个支付成功的订单明细”。如果粒度说不清，后面的指标就容易重复计算或漏算。

### 指标体系示例

| 指标类型 | 示例 | 说明 |
| --- | --- | --- |
| 原子指标 | 支付金额、支付订单数、支付用户数 | 不可再拆的基础度量 |
| 派生指标 | 最近 7 天 GMV、类目日支付用户数 | 原子指标 + 维度 + 时间周期 + 修饰词 |
| 复合指标 | 客单价、转化率、退款率 | 由多个指标计算得出 |

客单价示例：

- 指标名称：客单价。
- 口径：支付金额 / 支付订单数。
- 时间周期：按天、按周、按月。
- 过滤条件：支付成功订单，排除测试订单。
- 维度：渠道、类目、城市、用户类型。

### 推荐练习内容

- 设计订单支付事务事实表。

- 明细粒度是什么？
- 需要哪些维度？
- 指标口径是什么？
- 该沉淀在 DWS 还是 ADS？
- 是否已有公共模型可以复用？

## 九、阶段 7：性能优化与工程化

### 学习目标

本阶段目标是让你写出的任务不仅能跑，还要跑得稳、跑得快、可维护、可恢复。优化不是只调参数，首先要理解数据分布、表结构、SQL 逻辑和执行计划。

### 核心知识

| 模块 | 需要掌握的内容 |
| --- | --- |
| SQL 优化 | 避免全表扫描、减少重复计算、合理拆分 CTE |
| 扫描优化 | 分区裁剪、列裁剪、谓词下推 |
| Join 优化 | 小表广播、MapJoin/Broadcast Join、Join 顺序 |
| 倾斜处理 | 热点 key 拆分、加盐、两阶段聚合、异常值过滤 |
| 文件优化 | 小文件合并、合理控制输出文件大小 |
| Spark 优化 | Shuffle 分区数、缓存、Broadcast、执行计划 |
| Flink 优化 | 状态大小、State TTL、Checkpoint 间隔、反压排查 |
| 表设计优化 | 存储格式、分区、桶表、主键模型、排序键 |
| 资源调优 | Executor、Memory、CPU、并行度 |
| 稳定性 | 幂等、数据回溯、灰度发布、版本管理 |
| 代码规范 | SQL 命名、字段注释、任务参数、提交规范 |

### 优化思路

推荐按照这个顺序思考：

1. 是否扫了不该扫的数据，例如忘记加分区过滤。
2. 是否读取了不需要的字段。
3. Join 的表大小和 key 分布是否合理。
4. 是否存在数据倾斜。
5. 是否有重复计算或可以复用的中间结果。
6. 存储格式和压缩是否合适。
7. 资源参数是否明显不合理。
8. 是否能通过模型层沉淀减少 ADS 重复计算。

### 工程化能力

数据开发工程化能力包括：

- 可维护性：SQL 清晰、命名规范、字段注释完整。
- 可观测性：有日志、质量规则、任务状态和告警。
- 可恢复性：支持补数、重跑、回滚和幂等写入。
- 可协作性：口径文档、表说明、代码版本管理清楚。

某电商平台需要建设订单交易分析数仓，支持运营看板和实时大屏。业务关心：

- `dws_category_trade_1d`：类目粒度每日交易汇总。
- `dws_channel_trade_1d`：渠道粒度每日交易汇总。
- `dws_user_behavior_funnel_1d`：用户行为漏斗汇总。

DWS 要沉淀公共复用指标，避免 ADS 重复计算。

### ADS 层设计

- `ads_trade_overview_1d`：交易总览看板。
- `ads_category_rank_1d`：类目销售排行。
- `ads_channel_conversion_1d`：渠道转化分析。
- `ads_user_retention_1d`：用户留存分析。
- `ads_refund_monitor_1d`：退款监控。
- `ads_realtime_trade_dashboard`：实时交易大屏。

ADS 面向具体应用，字段命名和粒度应该贴近业务使用。

### 指标体系设计

| 指标 | 口径 |
| --- | --- |
| GMV | 支付成功订单的支付金额汇总，排除测试订单 |
| 支付订单数 | 支付成功订单去重计数 |
| 支付用户数 | 支付成功订单的用户去重计数 |
| 客单价 | GMV / 支付订单数 |
| 人均消费 | GMV / 支付用户数 |
| 退款金额 | 退款成功金额汇总 |
| 退款率 | 退款订单数 / 支付订单数 |
| 加购到支付转化率 | 支付用户数 / 加购用户数 |
| 次日留存率 | D 日新增用户中 D+1 日仍活跃用户占比 |

### 离线链路

1. 每日凌晨从 MySQL 同步前一日增量到 ODS。
2. ODS 清洗去重后写入 DWD。
3. DWD 关联 DIM 生成用户、商品、类目、渠道汇总。
4. DWS 形成公共汇总表。
5. ADS 输出看板指标。
6. 调度系统配置 T+1 DAG 和失败告警。

### 实时链路

1. MySQL Binlog 或业务埋点写入 Kafka。
2. Flink SQL 读取 Kafka 构建实时 ODS。
3. 清洗支付成功事件进入实时 DWD。
4. 关联商品、类目、渠道维表。
5. 按分钟窗口聚合 GMV、订单数、支付用户数。
6. 写入 Doris、ClickHouse、StarRocks 或 Kafka。
7. 支持实时大屏查询。

### 调度设计

调度 DAG 示例：

```text
ods_order_info_di
  -> dwd_trade_order_detail_di
  -> dws_user_trade_1d
  -> ads_trade_overview_1d

ods_product_info_df
  -> dim_product_df
  -> dws_product_trade_1d
  -> ads_category_rank_1d
```

关键要求：

- ODS 先于 DWD。
- DIM 先于需要关联维度的 DWS。
- DWS 先于 ADS。
- 所有任务支持按 `dt` 参数补数。
- ADS 任务失败时优先检查上游 DWS/DWD/ODS 分区。

### 数据质量校验

- ODS 分区数据量不为 0。
- DWD 订单主键不重复。
- 支付成功记录 `pay_time` 不为空。
- 订单金额不能小于 0。
- DWD 支付成功订单数不能大于 ODS 订单数异常阈值。
- GMV 日环比波动超过阈值时告警。
- ADS 指标表必须产出目标日期分区。

### 可视化或查询服务

可以使用任一方式完成：

- Superset、Metabase、DataEase 等 BI 工具。
- Doris、ClickHouse、StarRocks 查询服务。
- 简单 Web Dashboard。
- Notebook 或 SQL 查询报告。

### 可选 Agent 扩展

项目完成后可以做一个小型数仓问答 Agent：

- 输入：“GMV 是怎么计算的？”
- 返回指标口径、来源表、过滤条件和示例 SQL。
- 输入：“`ads_trade_overview_1d` 依赖哪些表？”
- 返回上游血缘。
- 输入：“今天 GMV 为什么下降？”
- 返回质量检查、调度状态、上游数据量和可能原因。

### 项目最终产出

- 表结构设计文档。
- ODS、DWD、DIM、DWS、ADS SQL 脚本。
- Flink SQL 实时任务。
- 调度 DAG 图。
- 数据质量规则。
- 指标口径文档。
- 实时与离线指标一致性说明。
- 项目复盘文档。

## 十一、Agent 赋能数仓的长期方向

### 先明确主次

入职初期应该先做好 SQL、建模、调度和数据质量。Agent 可以作为个人差异化能力和长期研究方向，但不建议一开始脱离数仓本职去做泛 AI 项目。

Agent 与数仓结合的正确路线是：先掌握数仓核心知识，再把元数据、指标口径、数据质量规则和调度日志结构化，最后让 Agent 基于这些可信上下文工作。

### 1. Text-to-SQL Agent

用户用自然语言提问，Agent 结合表结构、字段解释、指标口径和权限信息生成 SQL，可用于业务自助分析。

典型流程：

1. 用户提问：“最近 7 天各类目 GMV 是多少？”
2. Agent 检索指标口径和表结构。
3. Agent 选择合适的 DWS 或 ADS 表。
4. Agent 生成 SQL。
5. 系统做权限、成本和语法检查。
6. 返回结果或图表。

风险提醒：

- SQL 可能生成错误。
- 指标口径可能误用。
- 用户可能无权访问敏感字段。
- 大查询可能消耗过多资源。
- Agent 需要知道优先查 ADS/DWS，而不是乱查 ODS。

### 2. 指标问答 Agent

基于指标字典、口径文档、维度信息进行问答，帮助业务理解指标定义。

示例问题：

- “GMV 是否包含退款？”
- “支付用户数按订单创建时间还是支付时间统计？”
- “客单价和人均消费有什么区别？”

### 3. 元数据 Agent

基于表结构、字段、血缘、负责人、任务信息进行问答。

示例问题：

- “这个 ADS 表依赖哪些上游表？”
- “这个字段来自哪里？”
- “哪个任务负责产出 `dws_user_trade_1d`？”
- “这张表的负责人是谁？”

### 4. 数据质量诊断 Agent

结合数据质量规则、调度日志、数据波动、血缘信息，辅助定位异常。

示例：

- 某个指标突降时，Agent 判断是上游延迟、口径变更、任务失败还是数据源异常。
- 某个分区数据量为 0 时，Agent 自动检查调度依赖和 ODS 分区。
- 某个字段空值率升高时，Agent 追踪字段来源和最近变更。

### 5. 数仓运维 Agent

辅助排查调度失败、SQL 报错、任务超时、数据倾斜、小文件等问题。

可结合：

- 调度日志检索。
- SQL 错误规则库。
- 历史故障案例。
- 执行计划分析。
- 表分区和文件数量信息。

### 6. SQL Copilot

SQL Copilot 可以辅助：

- 生成 Hive SQL、Spark SQL、Flink SQL。
- 解释复杂 SQL。
- 重构复杂 SQL。
- 生成测试数据。
- 生成数据质量规则。
- 对比 Hive/Spark/Flink SQL 差异。

但 SQL Copilot 不能替代你理解指标口径。你必须能判断它生成的 SQL 是否符合业务语义。

### 长期学习路线

1. 先掌握 SQL、分层、建模、调度、质量。
2. 整理元数据、指标口径、数据质量规则和血缘关系。
3. 学习 RAG、Tool Calling、Function Calling。
4. 做一个小型数仓问答 Agent。
5. 扩展到 Text-to-SQL。
6. 增加 SQL 安全检查、权限控制和成本控制。
7. 扩展到质量诊断和任务运维。
8. 结合 Ray 做分布式推理、批量分析或 Agent 后端编排。

## 十六、总结

你的短期主线非常明确：先把 SQL 补到能工作的水平，再理解数仓分层，接着掌握离线数仓开发、调度和数据质量。入职初期，不要急着追求复杂架构，先做到能看懂表、看懂 DAG、看懂 SQL、能改任务、能补数、能排查简单数据问题。

你的中期目标是掌握维度建模和指标体系。能写 SQL 是基础，能设计事实表、维度表和统一指标口径，才是真正进入数仓开发核心。

你的长期优势在实时数仓和 AI 数据平台。Flink 能帮助你在实时链路、状态管理、Exactly-once、Watermark 和实时指标上形成优势；Ray 可以作为未来机器学习数据处理、分布式推理和 Agent 后端方向的储备。但当前不要让 Agent 抢占数仓主线，最好的路线是先把数仓知识学扎实，再用 Agent 去增强元数据问答、指标解释、SQL Copilot、数据质量诊断和任务运维。

最终你应该形成这样一套能力结构：

- SQL 能写复杂分析和指标计算。
- 数仓分层能讲清楚，也能落到表设计。
- 离线链路能开发、调度、补数和排查。
- 实时链路能结合 Flink 做清洗、聚合和一致性处理。
- 建模能围绕业务过程、粒度、事实和维度展开。
- 治理能覆盖质量、元数据、血缘、权限和成本。
- Agent 能作为长期差异化方向，服务数仓本职，而不是偏离数仓本职。
