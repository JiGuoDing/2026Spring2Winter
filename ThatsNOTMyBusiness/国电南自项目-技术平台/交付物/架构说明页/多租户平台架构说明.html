01 目标

一套平台，管住约 900 个租户的四件事

不看架构图也能理解：这套平台最终要同时做到「开得出、隔得开、管得住、查得清」。

开得出模板化开通六类配置一次选完，从审批到可登录 ≤ 10 分钟。
隔得开按档隔离四档强度由打分决定，越权请求 100% 拦下。
管得住配额有牙齿三层执行点，超限被拒，存量业务不中断。
查得清全程留痕审计五元组完整，平台方操作对租户可见。

1.1六个可以验收的数字

目标不写成形容词，写成能测的指标。下表的每一项都在后面的步骤里有对应的动作。

≤ 10 min模板化开通时长从审批通过到租户管理员可登录
100%越权请求拦截含 API 越权、数据越权、控制面越权
3 层配额执行点K8s、准入、网关各管一段
45%–55%资源当量以「全量 L2 方案」为 100%
≤ 5 个L3 独立集群成本太高，必须设上限
≈ 109.5人月，分三期43.5 + 34.0 + 32.0，测试占 24%
一句话目标不是「上多租户」，是让隔离、配额、访问的每一次判定都有依据、有执行点、有记录。
02 问题

平台跑得很好，但三件事没有答案

现状不是「没做」，是「做了但缺后手」。缺口集中在治理层，不在数据面。

31省级区域
≈700在场站运行
7能力板块已上线
8独立数据库实例
≈900规划租户数

2.1三个缺口，一个比一个难补

G1

建得出租户，说不出为什么这么建

六类配置模板齐备，容器、中间件、数据库、功能、安全、通知都能选。但「这个厂站为什么给独立集群、给多少资源」没有判定准则，每次都要开会拍。

后果900 个租户就要开 900 次会；档位一旦拍错，事后无法复核。
G2

有资源监控，没有配额体系

已有 Prometheus + Grafana 与低代码埋点，但 15 项配额的上限与分档默认值没有定义，K8s / 准入 / 网关三层执行点也没落地，用量不回传。

后果没有配额就没有上限。超了只能事后从监控里发现，无法在写入前拦住。
G3

有统一身份，没有跨租户边界

支持 SSO 集成与跨租户认证，但令牌里不带租户、服务端采信前端传的租户号、数据层不强制过滤，租户视角的审计视图也没有。

后果能认人，拦不住越界。跨租户访问只能靠制度和自觉。
为什么现在动900 个租户 × 15 项配额，边际人工操作必须为 0。靠人盯的治理，在第一个月就会失效。
03 框架

三步定框架：先划红线，再定档，最后定重心

顺序不能换。红线决定能不能做，档位决定做多重，重心决定钱花在哪。

第一步 · 划红线

全部资源只落安全Ⅲ区

含 L3 独立集群也不跨区。生产控制区数据经单向隔离装置进入平台，平台不回写任何控制类指令。这不是选型偏好，是法规前提。

→ 排除「部署到Ⅰ/Ⅱ区」这条诉求
第二步 · 定档

四维打分，定四档隔离

业务类型、数据敏感度、监管要求、SLA 各打 1–5 分，合计 4–20 分；另设五条一票否决，触发即最高档。

→ 约 80% 的二级租户落在 L1，不必一刀切
第三步 · 定重心

改控制面，不动数据面

数据面已是每类能力独立实例，不重构。改造集中在控制面六个模块，层间只认四条契约。

→ 工作量比「共享库改独立库」低约 30%

3.1红线：数据只能单向进来

所有平台资源（含为高隔离租户单独起的集群）都在管理信息区。生产控制区的数据经电力专用横向单向安全隔离装置进入，反向通道不存在——图中红色 ✕ 标的就是那条不存在的路径。

3.2重心：四层结构，改造压在 L2

层与层之间只走四条契约，每条都要显式定义、可校验，否则分层会退化成示意图。绕过任何一条，后面就有一条结论失效。

04 步骤

七步落地，每一步都有可交付的产出

七步不是七个模块，是一条有先后的链路：先有模型，才谈得上接身份、开租户、落隔离、装配额。跳步做，后面都要返工。

S1

立模型：把四类事实收到一处

租户、配额、落档、授权四类事实以控制面为唯一来源，绕过控制面直接改库一律按违规变更处理。在客户既有的「租户—组织—员工—用户—角色—权限—资源域—订购」模型上补四个扩展实体：租户层级、租户成员、隔离等级、资源域配额。

产出租户元数据模型 + 生命周期状态机 + 命名规范
S2

接身份：4A 做权威，平台只做联邦

集团 4A 是唯一权威源，平台侧做 SP，不自建主身份库。OIDC 与 SAML 2.0 双栈并行——客户子系统多、历史长，只做一种协议大概率在第一个系统上就卡住。令牌必须带「当前激活租户」，切换租户重签。外部厂商不进 4A，另立账号域：强制 MFA、有效期 ≤ 90 天、到期自动禁用。

产出联邦桥接（OIDC + SAML2 + CAS 兼容层）+ 外部账号域 + 令牌租户声明
S3

建开通流水线：把「配置驱动」变成「一键下发」

申请、审批、落档、资源创建、验收五个环节串成一条流水线，六类配置全部模板化。落档与配额必须联动——隔离升级若没有对应资源支撑，等于只改了标签。

产出开通流水线 + 生命周期状态机（申请 → 审批 → 开通中 → 运行，另有变更中 / 冻结 / 注销中 / 数据处置）
S4

落隔离基线：每档一套清单，不是一个开关

L1 用命名空间 + 配额 + Pod 安全准入 + 网络策略，加 Capsule 的 Tenant 对象做治理层；L2 在此之上加节点池与独立实例；L3 走 vCluster 或独立集群。第三方开发商一律按 B 类处理，不留在共享命名空间里。

产出L0–L3 四套基线清单 + A/B 两类租户的判定表
S5

装三层配额：越靠右越软，也越能看见真实用量

K8s 管资源、准入管对象、网关管调用。三层口径一致、执行时机不同。P0 的第一个里程碑必须是 API 网关改造——有一批配额在 K8s 层根本看不见，网关不改，配额、计量、跨租户留痕三件事同时落空。

产出三层各自可验证的拦截证据 + 计量流水
S6

改子系统：必改 5、轻改 3、不动 2

多租户管理、统一身份接入、API 网关、低代码平台、集成平台必改；统一门户、待办中心、时序库适配轻改；大数据平台与大模型工具链本期不动，只在网关接计量。判断标准是「有没有租户边界」，不是「重不重要」。

产出适配清单与逐项工作量
S7

验收：拿一个真实场景跑通六步

选「某二级租户从申请到上线一个低代码检修应用」作为验证场景，它是最小完整链路，但覆盖全部控制面能力。六步依次是：环境准备与基线导入 → 全流程走通 → 构造 20 组越权用例 → 三层配额分别触发 → 故障注入 → 审计回溯。

产出六个可复测的产出示证，其中越权与审计两份同时作为等保举证材料
05 结果

做完之后，三件事会变，六个指标能测

定性看变化，定量看验收。两者都能在原型环境里当场复现，不靠口头承诺。

判据可复核

任一租户的档位能追到四项分数与否决项，不用再开会。
「为什么这个厂给独立集群」有台账可查。

执行点可验证

三层配额分别有拦截证据，20 组越权用例全部拦下并告警。
「配了但没生效」能被 24 小时比对发现。

边界可审计

「用户 + 激活租户 + 动作 + 对象 + 时间」五元组完整。
平台方进数据面的每一步，租户都看得见。

5.1六项验收指标

编号指标怎么测目标值
V-1开通时长从审批通过，到租户管理员可以登录≤ 10 分钟（模板化）
V-2隔离有效性从租户 A 尝试访问租户 B 的工作负载、服务、数据、密钥，逐项记录100% 拒绝并留痕
V-3配额生效提交超限资源申请、超量接口调用、超 Token 调用三层各自拒绝，可分别举证
V-4越权拦截率构造 20 组越权用例：改租户号、跨租户引用、跨租户取数、越权导出100% 拦截并告警
V-5故障影响面在租户 A 注入 CPU/内存打满、Pod 崩溃、网络抖动租户 B 无感知
V-6审计完整性校验五元组是否完整，平台操作是否对租户可见100% 可回溯

5.2三期节奏与代价

分期依据不是「功能多少」，是「依赖顺序与可验证性」。凡需要跨集群、跨环境或客户财务口径的，一律推到后两期——这样 P0 结束时能拿出可演示、可复测的完整链路，而不是一堆「已开发未联调」的模块。

代价要说清约 109.5 人月里，测试占 24%（约 26.7 人月），高于常规的 15%——隔离有效性、越权拦截率、配额生效这三项只能测出来，看代码看不出来。三个最不确定项带区间提交：身份 ±50%、子系统适配 ±40%、隔离 ±30%。

5.3现在需要客户回的 5 件事

这五项决定方案能不能落地成可施工的图纸，其余问题都可以并行推进。

编号要确认什么不回复的后果
T01集团 4A 的技术规格：支持哪些协议、有无属性扩展、能否增量同步、有无测试环境P0 关键路径无法开工，身份联邦无法设计
T09一级 / 二级租户的实际数量与层级清单配额默认值与容量规划的分母失效
T10各租户现有应用的部署方式、数据库模式、中间件模式若多数仍是共享库共享表，工作量上浮 30%，估算失效
T12等保测评现状：是否已过三级、本次是否扩建、上次整改项条款映射只能停在控制点级，举证清单定不了
T20本期预算量级与交付形态：设计方案 / 设计+原型 / 含实施三期范围与人力承诺没有锚点

5.4还缺一块：实测证据

上表的数字目前是经验值与目标值，不是实测值。三个最不确定项要带区间提交，等原型环境跑出来再回填。

回到起点三个缺口都不是技术选型问题。补上判据、执行点与边界，这套平台才算从「能建租户」走到「能管租户」。
