## 摘要

### 一、这份文档要达成什么

把设计方案从“图纸”落到“能施工”。全文给出一套可直接执行的实现路径：**27 个组件的锁定版本**（含 EOL 与许可证）、**三套环境拓扑**、**九个模块的逐项实现要点**、**四组跨模块契约**、**十二项验收指标**、**十二周周计划**，以及**五项必须在开工前两周拿到结论的实测**。

判断合格的标准只有一条：一个没参与过设计的工程师，照着本文能在干净的信创环境上把 P0 装出来，并在第 12 周通过验收。

### 二、调研推翻了四条旧结论

这一轮做了组件版本与上游状态的实地核验，结果不是“确认原方案可行”，而是发现了四处必须修正：

**其一，对象存储的 MinIO 已经不能用了。** 社区版 2025-05 移除管理控制台，2025-10 起只发源码不发二进制，2026-02-12 声明“不再维护”，**2026-04-25 仓库归档**，2026-09 Docker Hub 镜像下架、官方下载站返回 410。设计方案表 10-3/10-7 把 MinIO 列为轨一，现在意味着“部署即背一个不再有安全补丁的组件”——这直接冲撞等保对漏洞修补的要求。处置：主轨改 **Ceph RGW**，过渡轨 **RustFS**，MinIO 移除。

**其二，vCluster 不能锁 0.38。** v0.38.0（2026-11-18）被官方定位为 limited availability，只推荐新部署，存量应留在 0.37（LTS）。处置：锁 **v0.37.7**。

**其三，Kyverno 策略必须从第一行就写在 CEL 类型上。** 1.19（2026-08）实现新旧类型功能对等后正式弃用 `ClusterPolicy`，**1.20 移除**；补丁支持是 “main + 1”（约三个月）。按网上大量教程写成 `kind: ClusterPolicy`，交付物半年内即过期。处置：一律用 `ValidatingPolicy`/`MutatingPolicy`/`GeneratingPolicy`/`ImageValidatingPolicy`/`DeletingPolicy`。

**其四，K8s 版本成了隔离强度的一部分。** 1.34 已于 2026-10-27 EOL；而 **CVE-2026-2270**（StatefulSet 控制器混淆代理，CVSS 5.9）允许持有 StatefulSet + ControllerRevision 写权限者把 Pod 送进他人命名空间，只在 1.35.9/1.36.5/1.37.1+ 修复。这个漏洞的形状，正是设计方案“L1 只挡误操作”所担心的越界——它不是理论风险，是已经发生的 CVE。处置：生产基线 **≥ 1.36，推荐 1.37.3**，不接受 1.34。

### 三、最要紧的不是写完文档，是这五件实测

设计方案里有几处“未验证假设”，实现阶段必须变成结论。按紧急度排：

1. **达梦 RLS 的会话上下文作用域** —— 若只支持会话级（无 `SET LOCAL` 等价物），共享连接池下必然存在串租户窗口。这一条决定 L1 数据隔离是“共享池 + 重置”还是“每租户独立池”，两者容量规划差一个量级。
2. Capsule 0.15.2 在鲲鹏 + 麒麟 V11 上能否跑（arm64 镜像、webhook 证书链）。
3. vCluster 0.37.7 private nodes 模式在信创节点上的网络栈。
4. Cilium 1.20 在麒麟 V11 内核 6.6 上的 eBPF 可用性（国产内核有大量自研补丁）。
5. APISIX 在国产 CPU 上的限流性能与精度。

再补一条不是实测但同样卡住整体的：**客户既有容器云是否允许安装 CRD 与 admission webhook**（【待确认-T33】）。不允许，则 Capsule 路线整体不成立，方案形态要改为新建集群。

### 四、预期效果与定位

按 CNCF 2026-09 发布的《Platform Engineering Maturity Model v1》五维四级模型，本方案 P0 结束时的定位是：**Interfaces 到 Level 2（Standard Tooling）、Operations 到 Level 2、Measurement 停在 Level 1**。Measurement 卡在 L1 的原因是成本分摊机制未定（【待确认-T08】），不是技术问题。

这个定位要提前说。说“P0 结束平台建成”会在验收时变成争议，说“P0 结束达到 Interfaces L2、Measurement L1，P1 冲 L3”是可核对的承诺。

## 0. 这份文档解决什么问题

### 0.1 与设计方案的分工

设计方案回答“做什么、为什么这样做”，本文回答“用什么做、怎么装上、怎么证明它做成了”。

同样是“L1 隔离”，设计方案写的是“L1 = 命名空间 + 配额 + 默认拒绝 + PSA restricted，只承诺挡误操作，不承诺防恶意”；本文要写的是“Capsule v0.15.2 的 Tenant CR 怎么配、PSA 用哪个 label 值、默认拒绝策略用上游 ClusterNetworkPolicy 还是 CiliumNetworkPolicy、跨命名空间引用靠哪两个引擎交叉校验、装完之后用哪 20 组用例证明它真的拒绝了”。

判断本文是否合格只有一条标准：**一个没参与过设计的实施工程师，照着本文能在一套干净的信创环境上把 P0 装出来，并且在第 12 周通过验收。**

### 0.2 三条写作约束

**其一，所有版本号都带核验日期。** 云原生组件半年一变，不带日期的版本号等于没写。本文全部锁定到 2026-11-28 可查证的具体版本，并标注 EOL 日期。

**其二，凡属厂商声明值，一律标注，不当事实用。** 例如“RustFS 通过 455 项标准 S3 测试”是厂商自述，本文写成“厂商声明”，不进验收判据。

**其三，凡本文推翻了设计方案的地方，单独列节并说明原因。** 见第 2 章。设计与实现之间有出入不是问题，藏着不说才是问题。

## 第 1 章 实现基线：版本锁定与信创矩阵

### 1.1 为什么版本锁定是第一章

多租户平台的隔离强度，有一半不在自己的代码里，在底座版本里。举一个已经发生的例子：

**CVE-2026-2270**（CVSS 5.9，StatefulSet 控制器混淆代理）。持有某命名空间内 StatefulSet 与 ControllerRevision 写权限的用户，可以借控制器把 Pod 恢复进**另一个命名空间**。修复版本是 kube-controller-manager 1.34.12 / 1.35.9 / 1.36.5 / 1.37.1。

这个漏洞的形状，恰好就是本方案“L1 只挡误操作”所担心的那类越界：它不需要租户有恶意，只需要租户有正常的 StatefulSet 写权限，配置稍一组合就出去了。而 1.34 分支已于 2026-10-27 结束生命周期（EOL），此后不再有回补。

结论：**版本不是偏好问题，是隔离强度的一部分。** 所以放在第一章。

### 1.4 一个容易被忽略的合规点：AGPL

Grafana 13.3、Loki 3.7、Tempo 3.1 均为 **AGPL-3.0**。Prometheus、Thanos、VictoriaMetrics、Jaeger、OTel Collector 为 Apache-2.0。

对本项目意味着什么：内部自用、不修改源码、不对外提供服务，AGPL 义务不触发。但有两种情形需要法务提前评估：①平台作为产品交付给客户后由客户再对外运营；②我方对 Grafana/Loki 做定制后随平台分发。

给出可执行的处置：**监控与仪表盘层保持“可替换”**——指标走 Prometheus/Thanos（Apache-2.0），Grafana 只作展示层，不写入业务逻辑；日志若客户要求全栈宽松许可，Loki 可换 OpenSearch（Apache-2.0）。这条写进技术选型记录，避免交付后被动。

## 第 2 章 必须修正的四条设计结论

本章四条，都是本轮调研发现的事实变化，与设计方案原文冲突。不修正的话，实施阶段会在第 1 周就撞上。

### 2.1 对象存储：MinIO 已归档，不能再用

**设计方案原文**（表 10-3、表 10-7）：对象存储轨一为“MinIO / 国产 Ceph 发行版”。

**现在的事实**（时间线可逐条核验）：

| 时间 | 事件 |
|---|---|
| 2025-05 | 社区版移除内嵌管理控制台；LDAP/OIDC 外部身份登录移出社区版 |
| 2025-10-15 | 最后一个安全版本发布，**不含二进制与镜像**，只发源码 |
| 2025-12-03 | README 标注“维护模式”，不接受 PR，安全问题“视情况评估” |
| 2026-02-12 | README 改为“THIS REPOSITORY IS NO LONGER MAINTAINED” |
| 2026-04-25 | GitHub 仓库**归档**（只读）；mc 客户端仓库 2026-07-14 归档 |
| 2026-09 | Docker Hub 上 `minio/minio`、`minio/mc` 镜像消失；`dl.min.io` 对社区版返回 **410 Gone** |

**为什么必须改而不是“继续用旧版本”**：本平台要过等保三级，等保要求“及时发现并修补漏洞”。一个上游明确声明“不提供安全公告与安全更新”的组件，无法通过这一条。继续用等于把这一条写进整改项。

**替代方案与取舍**：

| 候选 | 许可证 | 状态 | 优点 | 不选/选的理由 |
|---|---|---|---|---|
| **Ceph RGW** | LGPL-2.1/3 | 活跃 15 年+ | 对象/块/文件一套底座；S3 官方特性表覆盖 lifecycle、versioning、tagging、bucket policy、storage class | **主轨**。代价是运维极重（MON 每实例 5 GB+ 内存、每 OSD 4 GB 起、RGW 建议 6–8 核 / 32–64 GB），必须有存储运维团队。注意 bucket replication 官方标注为“Partial”，仅限 zone 之间 |
| **RustFS** 1.0.1 | Apache-2.0 | 2026-09 发 1.0，2026-10-03 更新 | 形态与 MinIO 同构（9000/9001 端口），迁移摩擦最小；内置控制台 | **过渡轨/边缘轨**。短板是年轻，生产年限不足三年；厂商声明的 455 项 S3 测试不作验收判据，必须自测 |
| **SeaweedFS** 4.47 | Apache-2.0 | 活跃 12 年 | 海量小文件性能好；支持 POSIX 挂载 | 海量小文件场景备选。S3 只是其入口之一，部分高级语义需走 filer API |
| pgsty/silo | AGPL-3.0 | 社区维护 | MinIO 源码 fork，兼容环境变量、路由、磁盘格式 | **不推荐用于关基**。单一维护者，且 AGPL |
| MinIO AIStor | 商业 | 活跃 | 官方维护版本 | 备选。按容量计价，许可到期后部署不可访问，需评估长期成本 |

**修正后的结论**：对象存储 **主轨 = Ceph RGW**，**过渡/边缘轨 = RustFS**，MinIO 从选型表移除并注明移除原因（上游归档、无安全补丁）。实施时先用 rclone 做一次“应用真实场景对象集”的读写基准，再定最终形态。

### 2.2 vCluster 锁 0.37.x，不锁 0.38

**设计方案原文**：“vCluster 约 11,300 stars / 160+ contributors；配置格式曾发生不兼容变更”。

**现在的事实**：v0.38.0 发布于 2026-11-18，官方明确定位为 **limited availability**——“仅推荐用于新部署”，存量集群应留在 v0.37 与 Platform v4.12（当前 LTS）。同时 0.38 弃用了 Istio 集成，移除了 shared secrets，资源代理开始强制校验 admission policy 与 webhook。

**修正**：实现路径锁定 **v0.37.7**。0.38 列入 P2 评估项，不在 P0/P1 触碰。理由不是“新版不好”，是“一个被上游标为 limited availability 的版本，不该承载第三方开发商的隔离边界”。

### 2.3 Kyverno 策略必须从第一行就写在 CEL 类型上

**设计方案原文**：准入控制“Kyverno + Gatekeeper 双引擎”，未指定策略类型。

**现在的事实**：Kyverno 1.19（2026-08）实现了 CEL 策略类型与旧类型的**功能对等**，同时**正式弃用** `ClusterPolicy`、`Policy`、`CleanupPolicy`、`ClusterCleanupPolicy`、旧版 `PolicyException`；这些资源在 **1.20（2026-11 起）被移除**。

**为什么这条最要紧**：如果实施团队按网上大量教程写成 `kind: ClusterPolicy`，代码在 1.19 上能跑，升到 1.20 就整体失效。而 1.19 的补丁支持是 “main + 1” 模型，约三个月。也就是说，**按旧写法交付，交付物在半年内过期**。

**修正**：策略全部使用 `policies.kyverno.io` API 组下的独立类型：

| 旧类型 | 新类型 | 本方案用途 |
|---|---|---|
| validate rules | `ValidatingPolicy` | 禁止 privileged/hostPath/hostNetwork、禁止 NodePort、必须带租户标签 |
| mutate rules | `MutatingPolicy` | 注入租户标签、注入 LimitRange 默认值 |
| generate rules | `GeneratingPolicy` | 新命名空间自动生成 NetworkPolicy/ResourceQuota |
| verifyImages rules | `ImageValidatingPolicy` | 镜像必须来自 Harbor 且签名有效 |
| CleanupPolicy | `DeletingPolicy` | 过期临时命名空间回收 |

命名空间级策略用对应的 `Namespaced*` 变体。1.19 起 CRD 通过独立 `kyverno-api` chart 管理，`crds.install` 控制，升级时要注意这一点。

### 2.4 K8s 生产基线 ≥ 1.36，推荐 1.37

已在 §1.1 说明 CVE-2026-2270。补充两条：

**其一，1.34 不是“旧一点但能用”**。2026-10-27 之后，1.34 分支不再接收任何 CVE 回补、依赖刷新与核心修复。对于一个要过等保、要通过渗透测试的平台底座，这条是硬约束。

**其二，版本还受 Capsule 反向约束**。Capsule 0.15.x 明确要求 K8s ≥ 1.36，且官方只支持最新一个小版本，向后兼容由厂商提供。所以“客户集群是 1.34，我们上车 Capsule 0.15”这条路不存在。如果客户既有集群无法升级，可选路径只有两条：降 Capsule 版本（但要评估其 2026 年 CVE 覆盖），或改走 vCluster/独立集群（放弃 L1 的轻量路线）。

**这条要写进 P0 启动前置条件**，与设计方案 §11.5 的清单合并。

## 第 4 章 逐模块实现路径

本章对应设计方案第 4–9 章与 §11.2 的十个模块。每个模块给出四件事：**技术方案 → 关键实现点 → 交付物 → 验收判据**。技术方案说“用什么”，关键实现点说“哪里会翻车”，后两项用来验收。

### 4.1 M1 租户模型与生命周期

#### 技术方案

**结论：租户本体自研 CRD + 自研 Operator，不把 Capsule 的 Tenant 当业务档案。**

理由：Capsule 的 `Tenant` 是“命名空间组 + 配额继承”的执行体，字段围绕 RBAC、配额、网络策略、镜像仓库展开。而本方案需要的租户档案是：十位租户编码、行政层级（一级/二级/基层）、信任等级（A/B）、四维打分（B/D/R/S）与总分、对应隔离档（L0–L3）、配额模板、计费口径、生命周期事件。这些字段 Capsule 不认识，硬塞进 annotations 会让“谁是真源”变成事故源。

所以做**两层**：

```
PlatformTenant（本方案 CRD，业务档案，真源在关系库）
        │  tenant-operator 投影（幂等）
        ├─→ Capsule Tenant（执行体：命名空间组 + 配额继承 + RBAC）
        ├─→ ResourceQuota / LimitRange（配额实例化）
        ├─→ NetworkPolicy + ClusterNetworkPolicy 标签选择（网络边界）
        ├─→ Keycloak Group `/t/{code}/{role}`（身份侧投影）
        ├─→ Harbor Project `t-{code}`（镜像侧投影）
        └─→ 对象存储 bucket `t-{code}-{purpose}` + 前缀策略（数据侧投影）
```

**为什么用 CRD 而不是“数据库表 + 脚本”**：因为要幂等。租户开通失败后重试、平台组件重启后状态收敛、有人手工删了命名空间——这些都要靠 reconcile 拉回来，而不是靠人重跑脚本。CRD 是让“期望态”可声明、可 diff、可自动修复的最小载体。

**为什么还要关系库**：CRD 存 `status` 与执行态合适，存“审批单、打分台账、变更历史”不合适——etcd 不适合当业务流水库。所以采用“关系库存档案 + CRD 存声明 + Operator 做对账”的三段式。真源唯一：**关系库**；etcd 里的 CRD 是可重建的执行态。

#### 关键实现点

**其一，`PlatformTenant` 的 spec 只放期望态，不放进度。**

```yaml
apiVersion: platform.nz.local/v1alpha1
kind: PlatformTenant
metadata:
  name: t-0102030405            # 十位租户编码，全局唯一，不可改
  labels:
    platform.nz.local/trust-level: A       # A 内部可信 / B 第三方
    platform.nz.local/tier: L1             # 打分结果的隔离档
    platform.nz.local/org-level: L2        # 行政层级：L1 集团 / L2 二级 / L3 基层
spec:
  displayName: 某某水电厂
  parentCode: "0102030000"                 # 上级租户，一级租户为空
  trustLevel: A
  isolationTier: L1
  score:                                   # 四维打分留档，便于复核
    business: 3
    data: 3
    regulation: 2
    share: 1
    total: 9
  quotaTemplate: standard-l1               # 引用配额模板，不内联 15 项
  owner:
    adminSubject: "emp:10023871"           # 指向 4A 主体，不存姓名
    contact: "ops@example.com"
  costCenter: "CC-3301"
status:
  phase: Active                            # Pending/Provisioning/Active/Suspended/Terminating/Terminated
  conditions: [...]                        # 每类投影一条 condition
  projections:                             # 每类投影的实际对象引用，便于排障
    capsuleTenant: t-0102030405
    namespaces: [t-0102030405-app, t-0102030405-data]
    keycloakGroup: /t/0102030405
  observedGeneration: 7
```

三条硬约束：

1. **`metadata.name` 就是租户编码**，不允许另存一个 `code` 字段——两个唯一键必然不同步。
2. **配额走模板引用，不内联**。15 项配额内联在 CR 里，改一次默认值要改 900 个对象。
3. **`status.projections` 必须记录实际创建的每个对象**。这是“删租户能不能删干净”的唯一依据，也是等保“剩余信息保护”的举证材料。

**其二，状态机用 phase + conditions，不用 finalizer 做业务等待。**

finalizer 只做一件事：确保数据处置完成前对象不被删除。业务等待（等审批、等资源就绪）用 `phase` 表达。混用会导致“卡在 Terminating 的租户无法排查”——这类故障在生产上极难定位。

**其三，开通 ≤ 10 min 靠并行 + 预生成，不靠“脚本跑得快”。**

时间预算拆解：

| 步骤 | 预算 | 说明 |
|---|---|---|
| 审批通过 → CR 创建 | < 5 s | 同步 API 调用 |
| 命名空间 + 配额 + 网络策略 | < 30 s | 一次 apply 批量创建 |
| Capsule Tenant 就绪 | < 60 s | 依赖 Capsule 控制器 reconcile |
| Keycloak group + 角色 | < 30 s | Admin API 批量调用 |
| Harbor project + robot 账号 | < 60 s | 预建模板可降到 10 s |
| 对象存储 bucket + 策略 | < 60 s | Ceph RGW 建 bucket 是秒级 |
| 门户可见 + 欢迎页 | < 30 s | — |
| **合计（串行）** | **≈ 4.5 min** | 余量 5.5 min 用于重试 |
| **合计（并行后）** | **≈ 1.5 min** | 六项投影并行 |

10 分钟的目标是有余量的。真正的风险不是慢，是**部分成功**——Capsule 成了、Keycloak 失败，租户看到半开通状态。所以要求：任一投影失败 → `phase=Provisioning` + condition 标记失败项 + 自动重试 3 次（指数退避）→ 仍失败则回滚已建对象并置 `phase=Pending`，不留给人工猜。

#### 交付物

- `PlatformTenant` CRD（含 OpenAPI schema 与 CEL 校验规则）
- `tenant-operator`（Go，controller-runtime；含 6 个投影 reconciler）
- 关系库 DDL：`platform_tenant`、`tenant_score`、`tenant_quota`、`tenant_lifecycle_event`、`tenant_approval`
- 配额模板库（L0–L3 × 3 档规格 = 12 套 YAML）
- 开通流水线时序图与失败回滚矩阵

#### 验收判据

| # | 判据 | 测量方法 |
|---|---|---|
| A-1 | 申请到可登录 ≤ 10 min | 从审批通过时间戳到租户管理员首次成功登录日志，取 10 次样本的 P95 |
| A-2 | 幂等：同一 CR 重复 reconcile 10 次，无对象漂移 | reconcile 前后 `kubectl get -o yaml` 全量 diff 为空 |
| A-3 | 部分失败可回滚 | 人为让 Keycloak 不可用，验证已建对象被清理、phase 回 Pending |
| A-4 | 租户编码唯一且不可变 | 尝试 patch `metadata.name` 被 API Server 拒绝；重复创建同名返回 409 |

### 4.2 M2 统一身份与权限

#### 技术方案

**结论：一个平台 Realm + Group 层级映射租户，不用“每租户一 Realm”。**

设计方案 §10.3 已定“4A 为权威源、Keycloak 作联邦层、自研用户中心保留为主体”。实现层面要回答的是 Realm 怎么划。

**为什么不用每租户一 Realm**：Realm 之间不共享用户与组，跨 Realm 管人必须走 Admin API 逐 Realm 操作；而 Keycloak 的多 Realm 共享同一进程与数据库，Realm 数量上去后启动加载、缓存、连接池、配置漂移全部成为瓶颈。900 个租户 = 900 个 Realm，这条路在规模上不成立。

**采用结构**：

```
Realm: platform（唯一）
├─ Identity Provider: corp-4a（SAML2 或 OIDC，SP 侧发起）
├─ Group 树
│   └─ /t
│       ├─ /0102030405
│       │   ├─ /admin      → 租户管理员
│       │   ├─ /dev        → 开发/运维
│       │   ├─ /viewer     → 只读
│       │   └─ /auditor    → 审计（只读审计日志，不含业务数据）
│       └─ /0102030406/...
├─ Client: platform-portal（public, PKCE）
├─ Client: platform-api（bearer-only）
├─ Client: tenant-provisioner（service account，仅 Admin API 权限）
└─ Roles: 平台级（platform-admin / platform-auditor / platform-operator）
          租户级（tenant-admin / tenant-dev / tenant-viewer / tenant-auditor）
```

**角色映射规则**：4A 断言里的组织编码 → 平台租户编码（通过 `org_code` 映射表，一对多时需要客户确认归属规则【待确认-T34：一人多单位时租户归属判定】）；4A 岗位/角色 → 平台角色（映射表配置化，不硬编码）。

#### 关键实现点

**其一，不做 JIT 建号（Just-In-Time provisioning）。**

4A 断言里出现未知用户时，默认行为是**拒绝登录并告警**，不是自动建号。JIT 在多租户场景下会造出“幽灵账号”：人已离职，4A 已停用，但平台侧账号还在，且带着历史租户授权。等保“应及时删除多余、过期账户”这一条会直接挂。

**其二，租户上下文必须服务端签发，不能前端传。**

Token 里放 `active_tenant` 声明。切换租户 = 走一次 token exchange 换新 token，不是前端改 header。原因：如果“当前租户”可以由请求头决定，那么任何一个有合法 token 的人都能通过改 header 读到别人的数据——这正是设计方案 §5.4“三道闸”要防的第一类越权。

网关侧动作（APISIX）：

```yaml
# 认证后注入，覆盖客户端传入的任何同名头
- plugin: proxy-rewrite
  conf:
    headers:
      set:
        X-Tenant-Id: "$jwt_active_tenant"      # 来自已验签 token，非客户端输入
        X-Subject-Id: "$jwt_sub"
      remove: ["X-Tenant-Id-Client-Supplied"]  # 显式移除可疑头
```

注意：APISIX 的 header 变量来自已验签的 JWT 才可信。若用 `$http_x_tenant_id` 直接取值，等于把租户选择权交给调用方。

**其三，三道闸的落点要写死。**

| 闸 | 落点 | 强制手段 | 绕过的后果 |
|---|---|---|---|
| 第一道 | 网关 | 验签 + 注入 `X-Tenant-Id` | 未认证请求进不来 |
| 第二道 | 服务框架 | 拦截器把 `X-Tenant-Id` 写入 ThreadLocal/Reactor Context；DAO 层强制拼接 `tenant_id` 条件 | 业务代码无法手写绕过 |
| 第三道 | 数据层 | 达梦 RLS 策略 / 金仓 RLS / 视图 | 即使 SQL 被注入，行级过滤仍在 |

第二道闸的实现要求：**禁止业务代码直接持有 DataSource**，只能注入 `TenantAwareDataSource`。这条用编译期检查（ArchUnit 规则）或代码扫描强制，不靠 code review 自觉。

**其四，共用/值班账号用主从映射，不禁止。**

### 4.3 M3 隔离等级落地

#### 技术方案

三层分别对应三种实现，不要用一套配置打三档。

**L1（八成的租户在这里）**

| 能力 | 实现 | 组件 |
|---|---|---|
| 命名空间组 | Capsule `Tenant` | capsule v0.15.2 |
| 配额继承 | Capsule `Tenant.spec.resourceQuotas` + 默认 `ResourceQuota` | capsule |
| Pod 安全 | PSA `restricted`（命名空间 label `pod-security.kubernetes.io/enforce: restricted`） | K8s 内置 |
| 网络默认拒绝 | 命名空间内 `NetworkPolicy` deny-all + 白名单放行 | K8s 内置 |
| 集群级护栏 | 上游 `ClusterNetworkPolicy`（Admin 层级） | Cilium 1.20 实现 |
| 准入 | Kyverno `ValidatingPolicy` + Gatekeeper `ConstraintTemplate` 双引擎 | kyverno 1.19.1 / gatekeeper 3.23.1 |
| 镜像 | Harbor project 隔离 + `ImageValidatingPolicy` 验签 | harbor 2.15.2 |

**用上游 `ClusterNetworkPolicy` 而不是 `CiliumNetworkPolicy` 做护栏，是这一层最值得写下的一个决定。** 理由：`CiliumNetworkPolicy` 能表达 FQDN 出站、L7 规则、集群范围作用域，表达力更强；但它把安全态势绑在 CNI 上，换 CNI 就要重写全部策略。而 Cilium 1.20 已实现上游 `ClusterNetworkPolicy`（Admin/Baseline 两个层级），标的选择器、命名空间选择器的表达力足够覆盖“禁止任何命名空间削弱集群级默认拒绝”这个需求。

取舍写成一句话：**集群级护栏用可移植 API 写，租户级细粒度策略用 Cilium 原生 CRD 写。** 前者保替换性，后者保表达力。

**L2**

在 L1 基础上加三件事：

1. **独占节点池**：Capsule `Tenant.spec.nodeSelector` 注入 `pool=dedicated` + `tenant={code}`；节点打对应 label 与 taint；调度器保证不越池。
2. **独立中间件实例**：Redis/Kafka 独立实例而非共享逻辑库（共享实例的侧信道风险见设计方案 [G-02]）。
3. **独立数据库 schema 或独立实例**：schema 级隔离 + 独立 DB 用户 + RLS 双保险；对数据敏感度高的租户直接给实例。

**L3**

两条路，按信任来源选：

- 第三方开发商 → **vCluster 0.37.7**，`private nodes` 模式（租户独占工作节点，控制面在宿主集群）
- 外部主体/等级保护要求独立 → **独立集群**（CAPI 纳管），配 OCM 做多集群视图

#### 关键实现点

**其一，Capsule 的 2026 年 CVE 说明“双引擎”不是冗余，是必需。**

Capsule 在 2026 年修复的安全问题里，有多条是**准入 webhook 被绕过**类型：

| 编号 | 问题 | 影响 |
|---|---|---|
| GHSA-jr6p-8pjj-mfx6 | `TenantResource` 的 RawItems/Generators 可创建集群级资源（跨租户提权） | 中危，0.13.8 修复 |
| GHSA-gjw4-v3v3-rqxg | `ForbiddenListSpec.ExactMatch` 大小写排序问题，租户 owner 可绕过禁止标签/注解强制 | **高危**，0.13.7 修复 |
| GHSA-gxjc-74v5-3vx3 | 畸形 `ForbiddenAnnotations.Regex` 可绕过租户校验并触发命名空间准入 panic | 中危 |
| GHSA-f94q-w3w8-cj67 | `hostnameRegexHandler` 在 update 时校验旧值，非法正则绕过 webhook | 中危 |

这些不是 Capsule 独有的问题——**任何单一准入 webhook 都是单点**。所以要求：Capsule 锁 ≥ 0.15.2；同时 Kyverno 与 Gatekeeper 各自独立实现同一组关键约束，任一引擎拒绝即拒绝。两个引擎都写、都生效，不是“选一个用”。

**其二，PSA 的 `restricted` 会打挂一批存量应用。**

`restricted` 要求：非 root、禁止特权、禁止 hostPath/hostNetwork/hostPID、必须设 seccomp、capabilities 只能 drop ALL。客户既有应用（尤其是有 agent 的老应用）大概率不符合。

处置：L1 默认 `restricted`，但**提供“降级到 baseline 需审批”的通道**，且降级必须留痕并在门户可见。不要默认给 `baseline`——那等于把最容易出事的特权容器放进来，而且事后没人知道哪些是例外。降级例外本身是治理数据，要能统计。

**其三，跨命名空间引用的白名单要双向。**

Kyverno 策略拦截“服务 A 引用了别的租户的 ConfigMap/Secret”时，不能只看引用方。要求：**引用方与被引用方都在白名单里才放行**，白名单以“租户 A ↔ 租户 B 的某个具体资源”为粒度，不是“租户 A ↔ 租户 B”整体授权。

**其四，L1 的诚实边界要写进产品文案。**

门户上 L1 租户的隔离说明，写“防止误操作与配置越界，不防御恶意攻击”，不要写“完全隔离”。这句话不是免责，是让租户知道该在哪一层加强——避免出现“我们以为平台隔离了，所以应用侧没做鉴权”这种事故链。

#### 交付物

- Capsule 部署 values 与 `Tenant` 模板（L0–L3 四套）
- Kyverno `ValidatingPolicy` / `MutatingPolicy` / `GeneratingPolicy` / `ImageValidatingPolicy` 共 12 条
- Gatekeeper `ConstraintTemplate` + `Constraint` 共 6 条（与 Kyverno 交叉覆盖关键项）
- `ClusterNetworkPolicy`（Admin 层级）基线 3 条
- 命名空间基线清单（PSA label、quota、netpol、limitrange 四件套）
- 例外审批流程与台账

### 4.4 M4 配额三层强制执行

#### 技术方案

设计方案 §6.6 定了 15 项配额、三层执行点。实现上三层分别落在不同组件，缺一层就有配额看不见。

**表 4-1 三层执行点与配额项对应**

| 层 | 组件 | 管得住什么 | 管不住什么 |
|---|---|---|---|
| 第一层：K8s 配额 | `ResourceQuota` + `LimitRange` | CPU/内存 requests·limits、Pod 数、PVC 容量、Service 数、LoadBalancer 数、ConfigMap/Secret 数 | API 调用次数、外发流量、调用第三方次数 |
| 第二层：准入 | Kyverno `ValidatingPolicy`（CEL）+ Gatekeeper | 创建时校验“这套配置是否超出租户档位”，可引用外部数据（租户档位 ConfigMap） | 运行时累计量 |
| 第三层：网关 | APISIX `limit-count` / `limit-conn` | API 调用频次、并发连接、Token 消耗 | 集群内服务间调用（除非全走网关） |

**第三层是最容易被跳过、也最不能跳过的一层。** 设计方案 §11.1 已写“P0 第一个里程碑必须是 API 网关改造”，原因是 Q-07/Q-08/Q-09 三项配额在 K8s 层根本不可见。实现上第三层的具体形态：

```yaml
# APISIX 3.16+：一租户一端点独立计数桶
plugins:
  limit-count:
    policy: redis
    redis_host: redis.quota.svc
    redis_port: 6379
    rules:
      - count: 1000            # 每租户每端点每分钟
        time_window: 60
        key: "$http_x_tenant_id $uri"
        header_prefix: "tenant"
      - count: 50000           # 全平台兜底
        time_window: 60
        key: "global"
        header_prefix: "global"
    rejected_code: 429
    allow_degradation: false   # 配额必须故障关闭
```

#### 关键实现点

**其一，APISIX 的默认 key 是 `remote_addr`，不显式设就是“每 IP 一份配额”。**

这是最典型的实现事故：配置看上去有 `limit-count`，压测也能触发 429，但线上发现“同一租户从不同出口 IP 发起请求时配额翻倍”。根因是 `key_type` 默认 `var`、`key` 默认 `remote_addr`。所以配置评审时把“是否显式设置 `key`”列为必检项。

**其二，`allow_degradation` 的选择要按配额类别分，不能统一。**

配额类（Q-01…Q-09）必须 `false`——Redis 挂了就拒绝，因为放行意味着可以无限调用。观测/分析类可以 `true`——少一条埋点不影响业务。混设的后果是“要么 Redis 一抖全站 5xx，要么限流形同虚设”。

**其三，配额变更必须走“申请 → 审批 → 落档 → 生效 → 可回滚”。**

突破配额的流程不是“运维改个数”，而是：
1. 租户在门户提交（含理由、期限、期望值）
2. 一级管理员审批（一级代管的体现）
3. 落档到 `tenant_quota` 表（含审批单号、生效期、失效期）
4. Operator 同步到 `ResourceQuota` 与网关配置（GitOps 提交，有 diff 可审）
5. 到期自动回收，回收前 7 天通知

**“到期自动回收”是这条流程里最容易漏的一环**，漏了就会累积成一堆永久临时配额，年底一统计发现配额总和是物理容量的三倍。

**其四，配额与容量要对账。**

`Σ ResourceQuota.requests ≤ 集群可分配容量 × 超卖比`。这个校验做成每日巡检任务，超了就告警。没有这一步，配额表会变成“账面数字”，实际调度时大面积 Pending。

#### 交付物

- 15 项配额定义表（含单位、默认值、上限、是否可申请突破）
- 12 套配额模板（L0–L3 × 3 档规格）
- 配额突破审批流配置
- APISIX 限流插件配置模板（按租户档位生成）
- 每日配额-容量对账任务

#### 验收判据

| # | 判据 | 测量方法 |
|---|---|---|
| D-1 | 三层各自可验证 | V-3：分别触发 K8s 拒绝、准入拒绝、网关 429，三份独立证据 |
| D-2 | 配额超限后存量不中断 | 提交超限申请被拒，已在跑的业务容器不被驱逐 |
| D-3 | 网关配额按租户而非按 IP | 同一租户从两个 IP 发起，合计计数；两个租户合计不串 |
| D-4 | 临时配额到期回收 | 构造到期场景，验证次日配额回落且通知已发 |
| D-5 | 配额总和 ≤ 容量 × 超卖比 | 对账任务输出通过 |

### 4.5 M5 计量与 Showback

#### 技术方案

**链路**：OTel Collector 采集 → Prometheus 短期存储 → Thanos 长期存储（对象存储）→ OpenCost 计算 → 账单聚合任务 → 门户展示。

**表 4-2 计量数据流与责任**

| 环节 | 组件 | 关键配置 | 可能的失真点 |
|---|---|---|---|
| 采集 | OTel Collector（DaemonSet + Gateway） | 保留 `namespace`、`pod`、`node` 维度标签 | 标签被 relabel 丢掉，导致无法归租户 |
| 聚合 | Prometheus 3.16 + 记录规则 | `tenant_id` 从命名空间标签映射 | 映射表变更导致历史数据归错租户 |
| 长期 | Thanos 0.42（sidecar + 对象存储） | 保留 ≥ 13 个月（覆盖一个完整预算年） | 对象存储单价表丢失，历史无法重算 |
| 成本 | OpenCost（CNCF Incubating） | 私有化环境用自定义单价表 ConfigMap | 单价为估算值，与财务口径有差 |
| 输出 | 自研账单聚合 | 租户 × 资源类型 × 周期 + 未分配 + 共享池 | 未分配成本处理规则不明，账不平 |

#### 关键实现点

**其一，计量口径用 `max(request, usage)`，不用“实际用量”。**

OpenCost 规范对 CPU、GPU 这类可分配资源的定义是 `max(request, usage)`。原因很实在：一个申请 2 核、实际只用 200m 的 Pod，仍然占着别人调不到的调度容量。用“实际用量”计量，会让“申请了不释放”变成免费行为，配额管理立刻失效。

这一条要在门户上解释清楚，否则租户会说“我明明只用了 0.2 核，为什么算我 2 核”。

**其二，`tenant_id` 标签必须打在 Pod template 上。**

只打在 Deployment 的 `metadata.labels` 上是无效的——分配成本是从运行中的 Pod 算的，Pod 上没有标签就归不到租户。所以 `MutatingPolicy` 要能“从命名空间标签推导并注入 Pod 标签”，并且这条策略的失败要阻断创建（不是只告警）。

**其三，私有化环境的单价表要纳入备份。**

与公有云不同，私有化部署没有账单可对，单价靠配置。如果只备份了指标而丢了单价 ConfigMap，历史样本还在，但重算的金额与当初报出去的对不上。备份范围必须包含：Prometheus TSDB 快照、Thanos 对象存储桶、OpenCost 单价 ConfigMap、租户映射表。恢复演练的验收标准写成“**账单能回到同一时间点且金额一致**”，不是“进程起来了、页面能打开”。

**其四，未分配成本（Idle）必须有明确规则并公开。**

集群空闲成本 = 集群资产成本 − 工作负载成本。这部分钱是真实花掉的，谁都不认领。三种处理方式（单独列示 / 按比例分摊 / 平均分摊）都成立，但必须**在第一次出报表前和租户约定**。一个团队从报表里第一次学到一个分摊规则，会把它当成乱收费。

本方案建议：**单独列示 + 按申请比例分摊两套视图并存**。单独列示用于解释“为什么总账不等于各租户之和”，按比例分摊用于推动资源瘦身。

**其五，本期只做 Showback，不做 Chargeback。**

设计方案 F.5 已定。实现上要防止“顺手把扣款也做了”——Showback 出错是数字不准，Chargeback 出错是真金白银，追责路径完全不同。所以账单模块只出“用量 + 折算金额”，不带扣款动作、不带预算冻结。

#### 交付物

- OTel Collector 配置（含租户标签处理器）
- Prometheus 记录规则集（10 条核心指标）
- OpenCost 部署配置 + 单价表 ConfigMap
- 账单聚合任务（日批 + 月批）
- Showback 报表模板（租户 × 资源 × 周期 + Idle + 共享池）
- 备份与恢复演练脚本

#### 验收判据

| # | 判据 | 测量方法 |
|---|---|---|
| E-1 | 租户级用量可查可导出 | 门户查询 + 导出 CSV，与 PromQL 直查结果一致（误差 ≤ 1%） |
| E-2 | `max(request, usage)` 口径生效 | 构造“申请 2 核用 0.2 核”的 Pod，验证计入 2 核 |
| E-3 | 账单可重算 | 从备份恢复后重算同一天账单，金额一致 |
| E-4 | Idle 与共享池可解释 | 各租户金额之和 + Idle + 共享池 = 集群总成本（误差 ≤ 0.5%） |

### 4.6 M6 门户与服务台

#### 技术方案

**结论：自研轻门户，不引 Backstage。**

理由：本方案门户只需要五类页面——租户申请、配额与用量、审计查询、工单、文档入口。Backstage 是开发者门户框架，核心价值在软件目录（Software Catalog）与脚手架（Scaffolder），要它发挥作用需要 Node/React 深度二次开发，且中文生态与信创适配无公开证据。为五个页面背一个框架，性价比不成立。

**但保留一个例外**：P2 若要做“服务目录 + 模板市场”（自助申请数据库、缓存、消息队列），届时重新评估 Backstage 或 Crossplane 的 `CompositeResourceDefinition` 直接对租户暴露。评估触发条件写清楚，避免到时候凭感觉决定。

#### 关键实现点

**门户不能是唯一入口。** 所有门户能力必须有对应的 API，且 API 是权威接口。原因：租户里的自动化脚本、CI 流水线、批量操作都走 API，门户只是其中一种客户端。若把业务逻辑写在门户里，API 就成了二次封装，两边必然不同步。

**审计查询要给租户看，但不能给全量。** 租户能看“与自己相关的操作”（含平台对其的操作），不能看其他租户、不能看平台内部运维细节。这条与等保“平台操作可被客户审计”对应，实现上是审计存储按 `tenant_id` 分片或加行级过滤，不是查询时过滤。

#### 交付物

- 门户前端（5 个模块）
- Platform API（OpenAPI 3.1 描述，含 12 个端点）
- 审计查询接口（租户范围过滤）

#### 验收判据

| # | 判据 | 测量方法 |
|---|---|---|
| F-1 | API 可独立完成门户全部动作 | 用 curl 走通五类页面各自的核心动作 |
| F-2 | 租户审计视图不外泄 | 以租户身份查询，返回结果中他人 `tenant_id` 为 0 条 |

### 4.7 M7 子系统适配：四组接口抽象

#### 技术方案

设计方案 §10.4.4 定了四组抽象（消息、缓存、对象存储、数据源），并要求“P0 交付接口，不一定全部实现”。实现层面给出接口签名与强制约束。

```java
// 租户上下文由框架注入，业务代码不可见
public interface TenantAwareMessageProducer {
    void send(String topic, Object payload, Map<String, String> headers);
    // 实现内强制：实际 topic = "t/" + TenantContext.require() + "/" + topic
    // headers 自动补 tenant_id、trace_id、producer_app
}

public interface TenantAwareCache {
    <T> Optional<T> get(String key, Class<T> type);
    void put(String key, T value, Duration ttl);
    // 实现内强制：实际 key = "t:" + TenantContext.require() + ":" + key
    // 显式不提供 eval/Stream 直通方法——国产 KV 常只支持命令子集
}

public interface TenantAwareObjectStorage {
    PresignedUrl presignPut(String bucket, String objectKey, Duration ttl);
    // ttl 上限 15 分钟，超出抛异常
    // 实际 bucket = "t-" + TenantContext.require() + "-" + bucket
}

public interface TenantAwareDataSource {
    Connection getConnection();   // 返回前已 SET 租户上下文
    // 业务代码不得直接注入框架 DataSource，ArchUnit 规则强制
}
```

#### 关键实现点

**其一，前缀注入必须发生在抽象层，业务代码不可见。**

“业务代码自己拼 `t/{tenant}/`”这种设计一定会出错——总有一个人忘了拼。所以前缀在实现类里拼，接口签名里根本没有“租户”这个参数。这样即使业务代码写错，也不可能写出跨租户的 key。

**其二，缓存显式禁止裸 Lua 与 Stream。**

国内容器化 KV 产品常只支持 Redis 命令子集，Lua 脚本、Stream、部分复杂结构可能不支持。接口层不暴露这些方法，等于在编译期就挡住了“用了之后换产品才发现不支持”的情况。

**其三，消息的延迟/事务语义不能靠抽象层抹平。**

Kafka 原生不支持延迟消息与完整事务，RocketMQ 支持。抽象层能统一的是“发送”这个动作，统一不了语义。所以接口上要显式区分：`send()` 与 `sendDelayed()`、`sendInTransaction()`，且后者在 Kafka 实现里抛 `UnsupportedOperationException`。**让差异显式失败，比让差异静默降级安全。**

**其四，对象存储的预签名 URL 有效期设硬上限。**

15 分钟上限不是性能考虑，是控制共享范围。一个 7 天有效的预签名 URL 等于一个不受租户鉴权约束的后门链接。上限在接口层硬编码，不开放配置。

#### 交付物

- 四组接口定义（Java 接口 + Javadoc 写清租户语义）
- 四组实现（Redis/Kafka/RocketMQ/对象存储各一套）
- ArchUnit 规则集（禁止直连 DataSource、禁止直用框架 Cache 客户端）
- 契约测试（每组 8 个用例，覆盖租户隔离、边界、降级）

#### 验收判据

| # | 判据 | 测量方法 |
|---|---|---|
| G-1 | 业务代码无法构造跨租户 key | 代码扫描：全仓库无 `"t/" +`、`"t:" +` 形式的字符串拼接 |
| G-2 | 换实现不改业务代码 | 用 testcontainers 跑两套实现，同一业务用例均通过 |
| G-3 | 不支持的语义显式失败 | 调用 Kafka 实现的 `sendDelayed`，抛 `UnsupportedOperationException` 而非静默立即发送 |
| G-4 | 预签名 URL 超 15 分钟被拒 | 传 30 分钟 ttl，抛异常 |

### 4.8 M8 治理与 GitOps

#### 技术方案

**三仓分离**：

| 仓库 | 内容 | 谁能改 | 保护 |
|---|---|---|---|
| `platform-infra` | 裸金属/虚拟机/网络/存储底座、集群生命周期 | 平台团队 | 需 2 人 review + 变更窗口 |
| `platform-config` | 平台组件 Helm values、CRD、准入策略、网络基线 | 平台团队 | 需 2 人 review；策略变更需安全评审 |
| `tenant-config` | 各租户的 `PlatformTenant` 声明与业务配置 | 平台团队（代管）+ 租户（自管目录） | 按目录 CODEOWNERS 分权 |

**为什么租户配置也要进 Git**：租户的配额、命名空间、白名单都是“应可审计的声明”。放进 Git 后，每一次变更有 diff、有提交人、有审批记录，直接对应等保“变更可追溯”。相反，如果租户配置只能通过门户点点点，出事后无法还原“当时是什么配置”。

#### 关键实现点

**其一，Argo CD 的 AppProject 是租户边界的执行点。**

每租户一个 `AppProject`，限制：可用的 Git 仓库与路径、可部署的目标命名空间、可创建的资源类型（禁止 `ClusterRole`、`CustomResourceDefinition`、`Namespace`）、可用的集群。没有这一层，一个租户的 Application 可以指向别人的命名空间。

**其二，漂移检测要能区分“人工热修”与“控制器写入”。**

`ResourceQuota` 的 `status`、HPA 改的 `replicas`、Capsule 注入的 label——这些是合法漂移。Argo CD 的 `ignoreDifferences` 要精确到字段路径，不能整类忽略。忽略过宽的结果是“真漂移看不出来”。

**其三，策略即代码要有测试。**

Kyverno 提供 `kyverno test` 与 CLI，可以对策略跑用例。要求：每条策略至少 2 个正向 + 2 个反向用例，进 CI。策略改错的代价是“全平台无法创建 Pod”，比应用发布失败严重得多。

#### 交付物

- 三仓目录结构与 CODEOWNERS
- Argo CD AppProject 模板（按租户生成）
- 漂移忽略规则清单（字段级）
- 策略测试用例集（12 条策略 × 4 用例）
- 变更审批流程配置

#### 验收判据

| # | 判据 | 测量方法 |
|---|---|---|
| H-1 | 租户无法跨 AppProject 部署 | 构造指向他人命名空间的 Application，验证被拒 |
| H-2 | 人工删改被自动拉回 | 手工删 `ResourceQuota`，5 分钟内被 reconcile 恢复 |
| H-3 | 策略变更经测试门禁 | 故意交一条错误策略，CI 拒绝合并 |

### 4.9 M9 原型验证环境

#### 技术方案

按设计方案 §11.3 的六步推进，实现层面补三项：

1. **用例化**：六项指标各自对应可执行脚本，不靠人手工点。20 组越权用例做成参数化测试集，可重复跑。
2. **证据化**：每次运行自动产出证据包（截图、日志、API 响应、审计记录），直接可作为等保举证材料。
3. **环境快照**：验证前打一次快照，验证后恢复。避免“跑完一轮环境脏了，第二轮结果不可比”。

#### 关键实现点

**故障注入用 Chaos Mesh，不用人肉 kill Pod。** 原因是可重复：人肉操作每次的影响面不一样，数据没法对比。Chaos Mesh 的 `PodChaos`、`NetworkChaos`、`StressChaos` 三类够用。

**越权用例要覆盖“组合”而不只是“单项”。** 单项越权（改 `tenant_id`）大多数框架能挡；组合越权（合法 token + 合法角色 + 他人对象 ID + 合法 API）才是真风险。所以用例设计里至少一半是组合场景。

- 六项验证脚本 + 证据包模板
- 20 组越权用例（参数化，可 CI 跑）
- Chaos Mesh 实验清单
- 环境快照与恢复脚本

#### 验收判据

即设计方案 V-1…V-6，扩展版见 §7.1。

## 第 5 章 关键契约

契约先定，实现后做。这一章的四组契约一旦定下，后续多个模块可以并行开发而不互相踩。

### 5.1 标签规范

标签是多租户平台的连通组织。计量、策略、网络、账单全靠它，一旦不统一，每个模块各认一套，对不上账。

**表 5-1 强制标签清单**

| 标签 | 值 | 打在哪 | 谁打 | 缺失后果 |
|---|---|---|---|---|
| `platform.nz.local/tenant-id` | 十位租户编码 | Namespace、Pod template、PVC、Service | MutatingPolicy 注入 | 计量归不到租户 |
| `platform.nz.local/trust-level` | `A` / `B` | Namespace | Operator 投影 | 策略无法按信任等级分派 |
| `platform.nz.local/tier` | `L0`–`L3` | Namespace | Operator 投影 | 隔离策略无法分层 |
| `platform.nz.local/pool` | `infra`/`tenant-shared`/`tenant-core`/`dedicated`/`virt-host` | Node | 运维 | 调度与隔离失效 |
| `platform.nz.local/cost-center` | 成本中心编码 | Namespace、Pod template | MutatingPolicy | Showback 无法按成本中心归集 |
| `platform.nz.local/env` | `dev`/`test`/`prod` | Namespace | Operator 投影 | 环境混布，故障互相影响 |
| `platform.nz.local/managed-by` | `tenant-operator` | 所有投影对象 | Operator | 无法区分平台托管对象与租户自建对象 |

**命名约束**：域名前缀统一用 `platform.nz.local`（K8s 标签键的 DNS 前缀规则），不用下划线、不用中文。

**从命名空间标签推导 Pod 标签的规则**（`MutatingPolicy` 实现）：

```
Namespace 有 platform.nz.local/tenant-id=N
  → Pod template 缺该标签时自动补 N
  → Pod template 已有但值不等于 N 时，按策略分支：
      默认拒绝（严格档）
      或 覆盖并告警（过渡档，仅限存量应用迁移期）
```

### 5.2 审计事件格式

等保三级要求“平台操作可被客户审计”。能否实现，取决于审计事件里有没有租户维度。

```json
{
  "event_id": "01JQ8Z3K7M2N5P9R4S6T8V0W2X",
  "occurred_at": "2026-11-28T10:15:33.421+08:00",
  "actor": {
    "subject_id": "emp:10023871",
    "display_name": "张某",
    "login_account": "zhangsan",
    "shared_account": null,
    "source_ip": "10.20.31.44",
    "auth_method": "saml2"
  },
  "scope": {
    "active_tenant": "0102030405",
    "acting_as": "tenant-admin",
    "on_behalf_of": null
  },
  "action": {
    "verb": "update",
    "object_type": "PlatformTenant",
    "object_id": "t-0102030405",
    "fields_changed": ["spec.quotaTemplate"],
    "old_value": "standard-l1",
    "new_value": "standard-l1-plus"
  },
  "result": { "status": "success", "http_code": 200 },
  "trace": { "trace_id": "4bf92f...", "span_id": "00f067..." },
  "integrity": { "prev_hash": "sha256:...", "hash": "sha256:..." }
}
```

**五元组是底线**：`actor.subject_id + scope.active_tenant + action.verb + action.object_id + occurred_at`。少任一项，等保“审计记录应包含事件的日期、时间、类型、主体标识、客体标识和结果”就过不了。

**三个设计选择要说明**：

- `shared_account` 与 `subject_id` 并存，是为了 R-14 的“共用/值班账号”场景——既要归因到实名主体，也要保留公共账号标识。
- `on_behalf_of` 用于一级代管：一级管理员代二级租户操作时，`scope.active_tenant` 是被代管租户，`on_behalf_of` 是代管关系标识。这样被代管租户查审计时能看到“谁替我做了什么”。
- `integrity` 用链式哈希（前一条的 hash 进当前条），防篡改。这不是等保硬性要求，但 GA/T 2347-2025 对 SaaS 模式强调“审计记录可向客户提供”，能自证未篡改会让举证轻松很多。

### 5.3 数据层租户隔离的实现约束（本章最要紧的一节）

这一节单独拎出来，因为它是全平台最容易出**数据泄漏级事故**的地方，而且很多方案会漏掉。

#### 问题：达梦 RLS 依赖会话上下文，连接池会串租户

达梦 DM8 的行级安全（RLS）实现方式是谓词注入：通过 `DBMS_RLS` 创建策略，策略函数返回 `WHERE` 条件，数据库在 SQL 执行前自动追加。开启方式：

```sql
-- 静态参数，需重启实例
SP_SET_PARA_VALUE(2, 'ENABLE_RLS', 1);
-- 初始化 RLS 系统包
SP_INIT_RLS_SYS(1);
```

策略函数通常读取**会话级上下文**（如 `SYS_CONTEXT('USERENV', ...)` 或自定义上下文）来决定返回哪个租户的谓词。

于是问题来了：如果平台使用共享连接池（HikariCP/Druid 默认行为），租户 A 的请求用完连接归还池中，租户 B 的服务**复用了同一个物理会话**。若 A 设置的会话上下文没有被显式清除，B 的查询就会拿到 A 的谓词——**B 看到 A 的数据**。

这不是理论风险。类似问题在 PostgreSQL 的 RLS 上同样存在（`SET` 与 `SET LOCAL` 的区别），只是 PG 的 `set_config(..., true)` 提供了事务级作用域来规避。

#### 三种处置方案与取舍

| 方案 | 做法 | 隔离强度 | 代价 | 适用 |
|---|---|---|---|---|
| **A. 每租户独立数据库用户 + 独立连接池** | `t_0102030405_app` 用户，策略按 `USER` 判定；每租户一个小连接池 | 最强：会话上下文不共享，池也分开 | 连接数 = 租户数 × 池大小，900 租户下连接数爆掉 | L2/L3 租户、数据敏感租户 |
| **B. 共享池 + 请求级上下文重置** | 借出连接先 `RESET CONTEXT`，归还前再清；上下文用 `SET LOCAL` 等事务级机制 | 中：依赖“清理一定执行” | 少一次清理就漏；异常路径易漏 | L1 租户（需配合 C 兜底） |
| **C. 应用层强制行过滤 + 数据库权限收紧** | 视图按租户过滤、授予列权限、禁用裸表访问；数据库账号只能访问视图 | 中高：不依赖会话 | 视图数量多、维护成本高 | 全部租户，作为兜底 |

**本方案要求 B + C 组合用于 L1，A + C 用于 L2/L3。** 单独用 B 不够——“清理一定执行”这个假设在异常、超时、连接被强杀时都不成立；单独用 C 也不够——视图绕过（如通过存储过程、动态 SQL）仍需数据库侧兜底。

#### 实现硬约束（写进编码规范）

1. **禁止业务代码直接注入 `DataSource`**，只能用 `TenantAwareDataSource`。ArchUnit 规则强制，CI 检查。
2. **连接借出与归还都必须重置上下文**，且用 `try-finally` 而非 AOP 环绕——AOP 在异常路径上的行为依赖代理链，不够确定。
3. **`TenantContext` 必须支持“无租户”状态并显式失败**，不允许 `null` 被当作“全部租户”。这个默认值设计错了，后果是平台后台任务误读全表。
4. **RLS 策略覆盖全部业务表**，新表上线前必须登记；用一个元数据表维护“已登记表清单”，巡检任务比对实际表与清单，缺一个就告警。
5. **每季度做一次“串租户”回归测试**：并发两租户压测，交叉校验返回结果集中 `tenant_id` 是否单一。

#### 待验证项

**【待确认-T36：达梦 RLS 是否支持事务级（`SET LOCAL` 等价）上下文作用域】** 这一条决定方案 B 是否可行。若达梦只支持会话级上下文，则 L1 必须降级为“每租户连接池”或“全部走视图”，容量规划要重算。**这是 P0 第一周就要在 E3 环境上验证的事，不是设计阶段能拍板的。**

| 性能测试 | k6 / JMeter | 网关配额、开通时长、并发 | 见 §7.3 门禁 | 15% |
| 安全测试 | Trivy + kube-bench + 渗透 | 镜像、基线、越权 | 无高危；渗透无跨租户 | 5% |

**测试占比 24% 的构成**（承接设计方案 §11.2 的口径）：越权测试 20% + 混沌 10% + 性能 15% 里的大部分，都是“只能测出来、看不出来”的部分。这三个数不是拍脑袋，是三个核心验收指标（隔离有效性、越权拦截率、配额生效）各自必须有独立测试手段。

### 6.3 CI/CD 流水线

```
提交 → 静态检查（golangci-lint / spotbugs / ArchUnit）
     → 单元测试
     → 策略测试（策略文件变更时必跑）
     → 镜像构建 + Trivy 扫描 + Cosign 签名
     → 推送 Harbor（租户项目 or 平台项目）
     → 更新 platform-config 仓的镜像 tag（GitOps PR）
     → Argo CD 同步到集成环境
     → 越权用例集 + 契约测试
     → 人工审批 → 生产
```

**镜像必须签名**，因为 `ImageValidatingPolicy` 要验签。签名这一步不做，准入策略就得降级成“只校验镜像来源域名”，防护强度差一个量级。

### 6.4 可观测性最小集

平台自己也要被观测，否则“租户说慢”时无法自证。

| 维度 | 指标 | 告警阈值 |
|---|---|---|
| 开通 | `tenant_provision_duration_seconds`（P95） | > 600 s |
| 投影 | `tenant_projection_failures_total` | 5 分钟内 > 3 |
| 准入 | `kyverno_admission_latency_seconds`（P99） | > 200 ms |
| 准入 | `gatekeeper_audit_duration_seconds` | > 300 s |
| 网关 | `apisix_http_status{class=429}` 按租户 | 单租户 5 分钟内 > 配额 10% |
| 配额 | `quota_utilization_ratio{tenant}` | > 0.9 持续 30 分钟 |
| 隔离 | `cross_tenant_access_attempts_total` | > 0（任何一次都告警） |
| 审计 | `audit_ingest_lag_seconds` | > 60 s |

`cross_tenant_access_attempts_total > 0` 就告警，看起来会吵。但这正是要的——跨租户访问尝试要么是攻击，要么是我们自己的 bug，两者都不能静默。

本章回答“这个实现路径是否符合行业标准”。分四个尺子：等保、电力监控安全防护、平台工程成熟度、信创测评。

另外要引用 **GA/T 2347-2025《网络安全等级保护云计算测评指引》**，它比标准原文更明确地要求：SaaS 模式三级测评须验证“导入导出、报表下载、附件存储、备份恢复、日志查看、接口调用”六个场景无跨租户泄漏。这六个场景直接对应 §7.2 用例集里的“越权导出”与“间接访问”两类，覆盖率要对齐。

### 8.2 电力监控系统安全防护（27 号令）

本平台不进生产控制区，所以 27 号令对本方案的约束主要是三条：

1. **分区不得跨越**：平台部署在管理信息区，与生产控制区之间只能经安全接入区、单向或经隔离装置。
2. **横向隔离装置两侧不做协议穿透**：采集代理只做数据落地，不做协议代理。
3. **安全 Ⅰ/Ⅱ 区内部不引入本平台组件**（含 agent）。

实现上要落实一条：**Cilium 的 DaemonSet 不部署到生产控制区节点**。这听起来是细节，但它是 27 号令“不得改变生产控制区网络结构”的直接要求——一个 CNI agent 会在节点上加网络规则，属于改变网络结构。

### 8.3 CNCF 平台工程成熟度模型（2026-09 发布 v1）

这是本轮调研发现的、最合适用来给本方案定位的行业尺子。CNCF Platform Engineering TCG 于 2026-09-01 发布 v1，定义了五个维度（Investment、Adoption、Interfaces、Operations、Measurement），每个维度独立评四级（Provisional、Operational、Scalable、Optimizing），并明确“各维度不必同步前进”。

**用它对本方案做定位，比自称“先进”有说服力**：

| 维度 | P0 结束 | P1 结束 | 说明 |
|---|---|---|---|
| Interfaces | **L2 Standard Tooling** | **L3 Self-Service** | 有 golden path 与模板，但例外仍需平台团队处理（L2）；租户可一键开通、常规变更不找人（L3） |
| Operations | L2 | L2→L3 | 平台自身可观测、有 SLO；跨租户故障隔离靠测出来 |
| Measurement | **L1 Provisional** | L2 | P0 只有基础指标与 Showback 雏形；成本口径要等 T08 |
| Investment | L2 | L2 | 有专职团队与预算，未到“平台即产品”的完整产品化 |
| Adoption | L2 | L3 | 首批租户按批次迁移，覆盖率逐步到 80% |

**这个定位的三个用处**：

1. **管理预期**：P0 结束不是“平台建成”，是 Interfaces 到 L2。这个话提前说，比验收时解释强。
2. **指出短板**：Measurement 停在 L1，因为成本分摊机制未定（【待确认-T08】）。这不是技术问题，是客户财务口径问题——用外部标准说这件事，比我们说自己缺更有效。
3. **给出下一步**：L3 到 L4 的关键是“能力透明嵌入既有工作流”，对应到本方案就是“租户不用打开门户就能用平台”（IDE 插件、CLI、CI 集成），这是 P2 的事。

### 8.4 信创测评口径

三个层次要分清，不要混用（设计方案 §10.4.3 的 G-5 门禁已经要求区分）：

| 口径 | 含义 | 本方案可引用的 | 不能声称的 |
|---|---|---|---|
| 安全可靠测评 | 中国信息安全测评中心评定等级 | 银河麒麟 V11 SP1 于 2026-09 通过 II 级 | 不能说“麒麟 V11 通过等保” |
| 互认/兼容性认证 | 厂商之间的适配互认证书 | 需逐组件取得编号 | 不能说“某开源组件通过信创认证”（多数没有） |
| 等保测评 | 系统级测评结论 | 达梦 DM8 通过等保四级认证 | 不能说“平台已过等保”（要实测） |

**对 Capsule / vCluster / Kyverno 这类开源组件，本方案的处理是：不声称任何信创认证，只声称“在麒麟 V11 + 鲲鹏环境上实测通过（附报告）”。** 实测报告的证明力低于认证，但它是真的——这比贴一个查不到的证书编号安全得多。

**其二，网关改造必须有独立验收。** 它不是“平台联调的一部分”，它是 Q-07/Q-08/Q-09 三项配额、计量埋点、跨租户留痕三个能力的共同前提。混在大联调里，一旦延期就没人知道是哪一环拖的。

**其三，测试时间不能用来换进度。** 24% 的测试占比不是保守，是三个核心验收指标只能测出来。历史上“压缩测试换进度”的项目，最后都在生产上把时间还回去了。

## 第 10 章 必须先实测的五件事

这一章是本文最该被认真读的一节。以下五项，在设计阶段无法定论，在实施阶段决定方案成败。P0 前两周必须全部有结论。

### 10.1 达梦 RLS 的会话上下文作用域（最关键）

**问题**：达梦 RLS 是否支持事务级（等价 `SET LOCAL`）上下文？若不支持，共享连接池下必然存在串租户窗口。

**验证方法**：E3 环境建两张表、两个用户、两条策略；用共享池（HikariCP，池大小 1）交替以两个租户身份查询，验证是否出现交叉可见。

**若不通过**：L1 从“共享池 + 重置”改为“每租户独立 DB 用户 + 小连接池”，或全部走视图。前者连接数上升，后者维护成本上升。**这条会改容量规划，所以必须最早知道。**

### 10.2 Capsule 0.15.2 在鲲鹏 + 麒麟 V11 上能否运行

**问题**：arm64 镜像是否存在、webhook 证书链是否正常、CRD 是否兼容 K8s 1.36/1.37。

**若不通过**：A 类租户失去轻量治理层，只能退到“原生 NS + RBAC + 自研控制器”，等于 M1/M3 的工作量翻倍。

### 10.3 vCluster 0.37.7 的 private nodes 模式在信创节点上的网络栈

**问题**：private nodes 模式要求租户自带 CNI/CSI，且控制面与数据面同步依赖网络连通。麒麟 V11 上的 CNI 选型与 kube-proxy 模式需要验证。

**若不通过**：B 类租户退回“独立集群”档，运维成本上升但方案不破。

### 10.4 Cilium 1.20 在麒麟 V11 内核 6.6 上的 eBPF 可用性

**问题**：内核 6.6 满足 Cilium ≥5.10 的要求，但国产内核有大量自研补丁（麒麟自研 KYSEC、eBPF 工具集），需验证 eBPF 程序加载、tc/XDP 钩子、Hubble 流量采集是否正常。

**若不通过**：换 Calico（eBPF 模式或 iptables 模式），代价是失去 `ClusterNetworkPolicy` 的可移植护栏与 Hubble 的流量可见，L1 的网络边界要重写。

### 10.5 APISIX 在国产 CPU 上的限流性能与精度

**问题**：APISIX 基于 NGINX + Lua，在鲲鹏/飞腾上的吞吐与 Redis 计数精度需实测。

**若不通过**：网关层配额的精度无法保证，Q-07…Q-09 要改为“近似配额”并在合同里说明，或换其他网关。

### 10.6 五项之外的第六件：客户既有容器云的 CRD 与 webhook 支持

严格说这不算“实测”，算“确认”，但它卡住整个方案落地：如果客户既有“基于 K8s 增强的资源管理运行平台”不允许安装 CRD、不允许注册 admission webhook，那么 Capsule、Kyverno、Gatekeeper 全部装不上，方案要整体改为“新建独立集群”。这一条对应【待确认-T33】，必须前置。
