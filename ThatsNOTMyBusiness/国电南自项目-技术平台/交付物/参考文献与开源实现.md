## 1. 最值得引用的 5 项

这五项覆盖了方案最容易被打的三个点：**为什么必须分档、租户模型凭什么这么切、共享资源凭什么敢给 900 个租户。** 建议摘要与第 3、4 章各引一处，全文不超过 5 次引用同一条。

### ① Kubernetes 官方文档《多租户》

- **链接**：https://kubernetes.io/zh-cn/docs/concepts/security/multi-tenancy/ （英文：https://kubernetes.io/docs/concepts/security/multi-tenancy/）
- **来源与维护**：Kubernetes SIG Security 维护，随版本持续更新 ✅
- **主要贡献**：官方明确把多租户分成两类场景（多团队 / 多客户），并把隔离定义为 **soft multi-tenancy 与 hard multi-tenancy 构成的谱系，而不是二元开关**；同时指出数据平面的攻击面远大于控制面，`namespace` 只是命名、配额与 RBAC 边界，**不构成天然的安全边界**。
- **与本方案的关联点**：这是 L0–L3 四档隔离最有力的合法性来源。方案不是"自创分级"，而是把官方承认的谱系在企业场景下**具体化为可判定、可计价的四档**。
- **可用于论证的具体主张**：
  - 「隔离强度是谱系而非开关」——直接对应"不对所有业态用一套隔离强度"的设计前提；
  - 「多团队 = 共享信任，多客户 = 强隔离」——正好映射本方案的 A 类（内部单位）/ B 类（第三方开发商）两类信任模型；
  - 「数据平面攻击面更大」——支撑"L0/L1 可共享控制面，但网络与存储必须单独设策略"的分层判断。

### ② Capsule（CNCF Sandbox）

- **链接**：https://github.com/clastix/capsule ｜ https://projectcapsule.dev/
- **来源与维护**：Clastix 发起，CNCF Sandbox 项目，Apache-2.0，约 2.3k stars，持续活跃 ✅
- **主要贡献**：引入 **Tenant CRD**，把"一组 Namespace"聚合成租户这一等公民；租户级的 ResourceQuota、LimitRange、RBAC、NetworkPolicy **自动被租户内所有 Namespace 继承**；提供 BYOD（Bring Your Own Device）把租户绑定到专属节点池；由准入 webhook 在 API Server 侧强制边界。
- **与本方案的关联点**：这就是本方案租户模型的工业级参照实现——"租户 = 一组命名空间 + 一套继承下去的配额与策略"，而不是"一个 namespace 就是一个租户"。
- **可用于论证的具体主张**：
  - 「租户应当是配额的继承单位，而不是命名空间的同义词」——支撑 15 项配额按租户模板下发、由子命名空间继承的设计；
  - 「配额必须有 API Server 侧的执行点」——支撑"准入控制是配额强制点之一"的判断；
  - 「同一套抽象可以通过 BYOD 升级为专属资源池」——支撑 L2/L3 不必另起一套模型，只是同一模型的不同参数。

### ③ Cross-Tenant Side-Channel Attacks in PaaS Clouds（CCS 2014）

- **链接**：https://dl.acm.org/doi/10.1145/2660267.2660356
- **来源与维护**：ACM CCS 2014，Zhang / Juels / Reiter / Ristenpart ○
- **主要贡献**：在真实 PaaS 环境中演示了**跨租户侧信道攻击**——攻击者利用共享 CPU 缓存与调度行为，从同一物理宿主机上的其他租户进程中提取信息。结论是：**只要共享同一内核与同一物理资源，逻辑隔离不足以阻止信息泄漏。**
- **与本方案的关联点**：这是"为什么 L0/L1 只能给可信租户、不可信租户必须上 L2/L3"的学术硬证据。睿思本身就是 PaaS 形态，这条比任何厂商白皮书都有说服力。
- **可用于论证的具体主张**：
  - 「容器级隔离的性能收益伴随可被利用的共享面，因此隔离等级必须与租户信任等级挂钩」；
  - 「B 类（第三方开发商）租户不得与内部租户共宿主机」——为 L3 独立资源池的成本增加提供了正当性论证；
  - 反向用法：说明本方案并未夸大隔离能力，而是**如实承认 L0/L1 的边界**，这在评审中比"我们全都能隔离"更可信。

### ④ Dominant Resource Fairness（NSDI 2011）

- **链接**：https://www.usenix.org/conference/nsdi11/technical-sessions/presentation/ghodsi
- **来源与维护**：USENIX NSDI 2011，Ghodsi / Zaharia / Hindman / Konwinski / Shenker / Stoica ○
- **主要贡献**：解决**多资源类型**下的公平分配问题——当作业对 CPU、内存、I/O 的需求比例各不相同时，单一维度的配额会产生严重的不公平。DRF 用"主导份额"定义公平，成为 YARN、Mesos 等调度器的配额理论基础。
- **与本方案的关联点**：直接支撑"配额不能只给一个数字"这一核心判断。方案的 15 项配额不是拍脑袋列长，而是因为**单资源配额在多资源场景下必然失效**。
- **可用于论证的具体主张**：
  - 「多资源配额必须成套定义，且需明确各维度的相对权重」——支撑 15 项配额的成组设计与默认值推导；
  - 「公平性依赖于对主导资源的识别」——支撑"按业态设不同主导资源"（水电=存储与写入、煤电=算力、新能源=实例数）的分档逻辑。

### ⑤ Large-scale Cluster Management at Google with Borg（EuroSys 2015，最佳论文）

- **链接**：https://dl.acm.org/doi/10.1145/2741948.2741964
- **来源与维护**：ACM EuroSys 2015，Verma / Pedrosa / Korupolu / Oppenheimer / Tune / Wilkes ○
- **主要贡献**：公开 Google 内部集群管理器 Borg 的设计与十年运行经验：**数万台机器、数十万个作业共享同一批 cell**，靠 quota/limit、优先级与抢占、以及"把隔离失效当作常态来设计"来维持稳定。
- **与本方案的关联点**：这是"共享集群承载海量租户"在超大规模下可行的最强工程证据。评审若质疑"900 个租户共用一套底座是否会互相拖垮"，这条是标准答案。
- **可用于论证的具体主张**：
  - 「共享 + 配额 + 优先级是超大规模下的主流做法，专用集群是例外而非默认」——支撑"共享为主、独立为例外"的总体策略；
  - 「必须预设隔离会失效，因此要有降级与抢占机制」——支撑方案中故障隔离与降级设计的必要性；
  - 「配额上限与优先级是治理工具，不只是计费工具」——支撑配额体系同时服务于公平与稳定两个目标。

## 6. 不建议引用的类型

写在这里是为了防止后续有人"补文献"时把清单撑虚：

- **厂商产品白皮书里未经第三方验证的性能数字。** 例如"某平台支持万级租户、性能提升 300%"。这类数字没有测试条件，评审一问就塌；本方案已建立的规矩是**厂商声明值不作承诺**，文献清单同样适用。
- **与技术决策无关的通用云原生科普。** "什么是 Kubernetes""云原生十二要素"这类内容不支撑任何设计判断，只会让附录显得凑数。
- **已被归档或停止维护的项目。** 例如 HNC；引用一个归档项目来论证"这条路可行"，反而自证调研不深。
- **同一条主张引三份来源。** 一个判断有官方文档 + 一份学术证据就够了；第三条开始是冗余。
- **无法定位到具体段落的二手解读。** 只能引到"某文章说"，不能引到原文页码或章节的，不进正式附录。

## 附：一句话总结

这套架构的可信度不来自"引了多少篇"，而来自**每一条引用都咬在一个具体设计决策上**：官方文档证明分档合法，CNCF 项目证明租户抽象可行，CCS 论文证明隔离不能省，DRF 与 YARN 证明配额必须成套且继承，Borg 证明共享集群能扛住规模。五项各管一段，没有一项是装饰。
