## 摘要

### 一、现状

华电睿思数智底座已在集团 31 个省级区域、近 700 个场站投运。平台建起七大能力板块：应用构建、应用集成、数据集成、时序数据、大数据、大模型工具链、多租户管理，另有统一门户、统一待办、统一身份与用户中心配套。就多租户这一项，客户已能做到“配置驱动的租户创建”：容器、中间件、数据库、功能模板、安全、通知六类配置模板齐备（P146），一级/二级租户的概念模型完整（P143），“多租户共享或分离”的部署形态也已可选（P151）。数据面的底子是好的——每类能力各自对应独立数据库实例（统一用户中心库、生产环境库、业务库、融合集成库、Doris 库、IoTDB 库、智能计算库、工具链库共 8 个），消息队列、缓存、任务调度这些中间件同样是独立实例。

**但现状是“配置驱动”，不是“治理驱动”**：创建能做，判定准则没有；资源能分配，配额与计量没有；身份中心有了，跨租户权限边界仍是空白。

### 二、三个核心缺口

**表 0-1 三个核心缺口**

| # | 核心缺口 | 具体表现 | 后果 |
|---|---|---|---|
| 1 | **隔离等级缺判定准则与代价模型** | 客户材料表述为“根据配置可以实现多个租户共享或者分离”（P151，未提供验证证据），但未给出“什么业务该共享、什么业务该独立”的判据，也未给出各档隔离的资源与运维代价 | 隔离档位取决于人工经验与博弈，评审无法复核；极端情况下所有租户都要求独立部署，平台退化为资源转售 |
| 2 | **配额与计量缺强制执行点** | 已有 Prometheus + Grafana 资源监控并可按租户层级上报（P152），但仅覆盖 CPU/内存/磁盘/网络 IO；API 调用量、大模型 Token、并发会话三项在 K8s 层完全不可见，且无配额上限、无审批流、无成本可见性 | 单租户可挤占共享资源；算力（GPU/NPU）与 Token 无约束；无法回答“某租户占用了多少”这一最基本问题 |
| 3 | **统一身份贯通与跨租户权限边界未打通** | 已支持第三方身份认证 / IAM / SSO 集成 / 跨租户身份认证（P144），但现状采用“每个租户同步全量组织架构与用户信息”（P148）；集团 4A 接口规格完全未知【待确认-T01】 | 存储与一致性成本随租户数增长而放大，组织可见范围形同虚设；无 4A 联邦则 P0 无法开工 |

剩下三项属于治理件缺口：应用自治与集团统管的权责划分、多环境与租户级运维视角、命名/接入/变更/审计治理规范，分别放在 §7.4、§8、§4.5 处理。

### 三、建议架构（一句话）

**以“安全分区为第一约束、以信任等级定隔离强度、以控制面为改造重心”的分级多租户架构**：全部平台资源（含 L3 独立集群）只部署在管理信息区（安全Ⅲ区）；生产控制区数据只经电力专用横向单向安全隔离装置单向进入平台，平台不回写控制类指令。租户按 L0–L3 四级隔离，用“业务类型 + 数据敏感度 + 监管要求 + SLA”四维 1–5 分打分定档，另设 5 条一票否决。A 类内部租户走 K8s 原生命名空间加 Capsule 的 Tenant CR 作治理层，B 类第三方开发商强制 vCluster 或独立集群。身份以集团 4A 为权威源，平台侧只做联邦（SP）；组织与用户改为“按可见范围同步 + 增量同步 + 冲突仲裁”。

## 第 1 章 项目背景与设计目标

### 1.1 集团管控模式与业务格局

中国华电集团实行总部—区域/省公司—基层企业三级管控。落到多租户平台，第一位的影响不是“要不要隔离”，而是“租户边界和组织边界不一致”：一个区域公司是一级租户的管理主体，同时还管着水电、新能源、煤电三类业态的若干厂站；一个厂站是二级租户，站上人员却可能被授权访问集团级应用。租户模型因此得表达“人—组织—租户”的多对多关系（§4.2、§5.1）。表达不了，一人多租户就退化成多套账号。

三类业态信息化差异不小，配额模板与落档打分因此要分开做，一个模板套不了全集团：

| 业态 | 信息化重心 | 数据特征 | 对平台的要求 |
|---|---|---|---|
| 水电 | 全过程监控、集中调度、径流预测、大坝安全 | 单站测点多、维度丰富、跨省分布、OT/IT 融合深 | 时序写入能力与保留策略；模型推理按租户隔离 |
| 新能源（风光储） | 功率预测、无人值守、场站海量接入 | 场站数量多（近 700 个场站的主要构成）、单站数据量小、接入协议杂 | 轻量租户模板（配额小、数量大）；边缘采集与区域汇聚 |
| 煤电/燃机 | 性能计算、集控分析、环保与可靠性 | 单机数据密度高、实时性要求高、与 DCS/SIS 边界敏感 | 只读汇聚；严禁把控制类业务纳入平台（§9.2） |

这三类差异不停留在业务描述上，都落到了具体设计参数。**配额模板**按业态分：水电重存储与时序写入，新能源重租户数量与轻量配额，煤电重计算资源与只读汇聚。**落档打分**里，新能源场站的数据源自场站监控系统，R 值因此偏高（判例 C-3）。**子系统适配优先级**也按业态排：新能源先做场站接入与边缘采集，水电先做时序保留策略与大坝安全类应用的隔离，煤电只做只读汇聚，不碰控制类业务。不分业态做模板，就会出现“给一个只有两名信息化人员的风电场站配 32 核配额”这种结果，既不经济，也没法运维。

两条与业务格局直接相关的事实口径得先说清，否则后续容量与覆盖率的讨论会用错：

1. “接入睿思底座的装机容量 8000 万千瓦”（2025-12 口径）与“集团发电总装机 2.86 亿千瓦”（2026-09 口径）**分母不同，不可相互折算**。本方案的容量设计不据此作任何覆盖率推算。
2. 集团“十五五”目标为装机超 4 亿千瓦、新能源装机倍增、清洁能源占比超 70%，租户数量与场站接入规模还会涨。因此本方案的容量设计按“可线性扩容的模板化下发”来做，不做“一次性精确容量”；绝对容量参数以【待确认-T09】【待确认-T10】为准。

三态标注不是文字游戏，它直接决定验收口径。标“已落地”的项，我方设计时可以假定机制存在，只做接口对接。标“蓝图”的项，我方必须在 P0 第一周做现场实测盘点；实测不通过的部分，按“新建”计工作量。时序数据是个例子：客户材料表述支持 600 万测点同时写入，这属于能力声明。本方案不据此推算容量，而是在【待确认-T04】里要求给出实际测点规模与写入峰值。原因很简单，一旦按声明值做容量设计，实际写入量达到声明值的三分之一就可能击穿存储规划。同理，“混合租户”在材料里是“物理共享 + 逻辑隔离与独立部署并存”，它准确描述了现状的**结果**，没描述**判据**。本方案要补的第一个缺口，就是这个判据。

### 1.3 现状差距分析

客户已有“配置驱动的租户创建”能力（容器、中间件、数据库、功能模板、安全、通知六类配置，P146），也有“共享或分离”的初步设想（P151）。缺的是把配置能力转成可复核治理的六个环节，逐项编号如下。

| 编号 | 差距 | 现状（含证据） | 目标状态 | 承接章节 |
|---|---|---|---|---|
| GAP-01 | 隔离等级判定准则 | 客户材料表述为“根据配置可以实现多个租户共享或者分离”（P151，未提供验证证据），无判据 | 四维打分 + 一票否决 + 降档成本 | §6.1 |

| GAP-04 | 配额强制执行点 | 无网关侧计量与限流 | 三层执行点（K8s / 准入 / 网关） | §6.6 |

| GAP-12 | 安全分区边界显式化 | 平台设计文档未显式表达与生产控制区的边界 | 分区约束写入架构与选型硬门槛 | §3.2、§9.2 |

### 1.4 设计目标、范围与不在范围

**目标**：给出可评审、可施工、可验收的多租户架构设计。在不推翻既有容器云平台（KubeSphere / Rancher / OpenShift 类平台一律“拿机制不拿平台”）、不新建域名体系（沿用 `*.zhsc.chd.com` 泛域名 + 出口 IP 分集群 A/B/C）、不重构数据面的前提下，让客户拿到隔离分级、配额治理、身份贯通、应用自治四项治理能力。

**在范围内**：租户模型与治理模型；统一身份与权限；资源隔离与配额；应用自治与集团统管；与运行保障体系的衔接；安全合规映射；技术选型建议；三期路线与原型验证方案；待确认清单。

**不在范围内**：生产落地实施与具体代码改造；硬件采购与机房建设；安全接入区建设；等保测评实施；运行保障方案（由并行方案承接，§8.1）；商业报价（【待确认-I06】）。

### 1.5 设计原则

| # | 原则（结论） | 理由 |
|---|---|---|
| P1 | 控制面与数据面分离 | 控制面故障不得影响已开通租户运行；控制面是租户与配额的事实源，必须独立演进 |
| P2 | 租户无感升级 | 二级租户无人运维是既定事实，升级不能要求租户配合 |
| P3 | 隔离按需分级而非一刀切 | 全 L2 的资源当量是 L1 的 2.5–3 倍；全 L1 则无法承载主数据供给与外部开发商 |
| P4 | 最小权限与默认拒绝 | 跨租户访问必须是“显式授权 + 留痕”，网络策略默认 deny、准入默认拒绝 |
| P5 | 信创优先且可双轨 | 单一供应商锁定会在性能与适配任一环节失守时无退路（§10.4） |
| P6 | 二级租户不自管但不锁死 | 不自管有同业背书，但必须保留可升级开关，否则架构无法应对业务变化 |
| P7 | 配额内自治、配额外审批 | 无自治则平台成为瓶颈；无审批则配额形同虚设 |
| P8 | 一切可计量、可审计 | 不能计量的资源无法治理，不能审计的操作无法追责 |

## 第 2 章 需求分析

### 2.1 干系人与角色

**表 2-1 角色—关注点—权限边界**

| 角色 | 关注点 | 权限边界（不可逾越） | 关键诉求 |
|---|---|---|---|
| 集团信息化主管部门 | 统一标准、投资效益、合规 | 不进入租户数据面做业务操作 | 一套框架管控多业态；可量化考核 |
| 区域/省公司平台管理员 | 本区域租户开通与代管 | 不得跨区域操作；不得设定超过集团上限的配额 | 批量开通、模板下发、代登录可审计 |
| 厂级租户管理员 | 本租户用户与角色 | 不得修改平台级策略；不得申请超出本租户上限配额 | 自助建应用、自助分配权限 |
| 厂级业务人员 | 低代码配置、报表 | 不得发布到生产环境（需审批）；不得跨租户取数 | 表单/流程/报表自助 |
| 专业开发人员 | 微服务、集成、算力 | 禁止直连平台库；不得创建集群级资源（CRD/ClusterRole） | 受配额约束的自助部署 |
| 平台运维人员 | 稳定性、容量 | 进入租户数据面属高危动作（限时 + 双人 + 录屏） | 统一视图、快速定位 |
| 安全审计员 | 合规举证 | 只可读、不可改审计配置；不得兼任平台管理员 | 全量审计、租户可见审计 |

**特权三角色必须互斥**。平台管理员、租户管理员、安全审计员一旦由同一人兼任，租户冻结/注销、审计配置变更这些控制就全部失效。客户侧因此至少要三个岗位编制：集团侧的平台管理员组、审计组，以及各租户的管理员。具体人力见【待确认-T16】。

七个角色跟客户实际岗位对不上，汇报时得说明映射。集团信息化主管部门对应集团数字化管理部门。区域/省公司的平台管理员，多数区域是“信息化专责 + 少量外包”的组合。厂级租户管理员在厂站通常由信息班组长兼任，不是专职岗位。安全审计员在集团侧最可能由审计或纪检岗位兼任，但**不能由平台管理员兼任**。这层映射的现实含义是：本方案的操作步骤必须按“兼职人员、每周只有几个小时处理平台事务”来设计。凡是需要连续操作或敲专业命令行的流程，都要做成批量或模板化，否则规则会因为没人执行而失效。

还有一类“共用账号”必须单列。场站值班多人共用一个操作账号，在电力行业是常态。不设“主从账号映射授权”（把公共账号与多个实名登录账号建立映射，实现实名审计），审计链就在值班环节断了（§5.2、R-14）。

### 2.2 典型场景

**S1 集团新设区域公司，一天内开通一级租户并带上默认子系统**
集团信息化主管部门在服务台提交租户申请，选业态（水电/新能源/煤电）、层级（一级）、配额模板和默认子系统包。系统按四维打分预填档位（无跨租户数据供给时为 L1）；平台管理员审批后触发开通流水线：创建租户元数据 → 创建命名空间与配额 → 初始化独立 schema → 按模板下发子系统配置 → 绑定域名与证书 → 生成租户管理员账号。涉及的设计点有租户生命周期状态机（§4.4）、模板化开通（§7.1）、配额默认值（§6.6）、域名沿用（§6.5）。

**S2 某水电厂作为二级租户上线一套检修管理应用（低代码 + 流程 + 报表）**
厂级业务人员在设计态沙箱里配置表单、流程、报表与字典，提交发布申请。租户管理员审批通过，发布到本租户运行态；流程实例自动带上 tenant_id 标签，待办推送到一级租户门户的流程中心。全程不写代码，也不碰跨租户数据。该场景四维打分 9 分，落 L1（§6.1 判例 C-1），是本方案的默认路径，也是原型验证场景（§11.3）。涉及的设计点：低代码成熟度 M2、设计态沙箱、租户上下文注入、待办隔离校验。

**S3 新能源场站侧边缘节点接入集团时序数据平台，数据只在租户内可见**
场站侧按轻量模板开通二级租户。采集侧通过 OPC/MQTT/104 等协议接入，数据经区域汇聚节点写入时序库。写入路径强制注入 tenant_id 标签；查询侧由数据层过滤，保证只在本租户可见。该场景监管要求维度为 4（数据源自场站监控系统），一票否决后至少 L2，且需独立时序实例，避免写入争抢（判例 C-3）。涉及的设计点：时序租户标签与保留策略（§6.3）、边缘节点不缓存重要数据（§9.2）、带宽配额（§6.6 Q-11）。

**S4 两个租户之间需要共享一份主数据（供应商/设备台账）**
数据所有方租户（如某水电厂）提出共享申请，与消费方租户、平台方三方确认共享对象、字段、有效期（≤ 90 天）。平台开通“受控通道”，走数据服务 API 而非数据库直连；双向授权，全程留痕，到期自动复审。这个场景会触发落档升级：供给方一旦成为“重要数据”提供方，数据敏感度从 2 抬到 4，总分 11，落 L2（判例 C-2）。涉及的设计点：跨租户数据共享授权（§5.4）、数据集成受控通道（§7.2）、数据分级（§9.4）。

**S5 专业开发人员在租户内自建微服务并接入 API 网关，受配额约束**
开发人员在本租户命名空间内部署微服务，镜像只能来自白名单仓库，工作负载须过基线准入。服务注册到网关时申请租户路由与限流策略，网关按租户维度累计 API 调用量，与配额比对。超过上限触发审批流，而不是直接把存量流量掐掉。涉及的设计点：准入双引擎（§6.2）、网关计量点（§6.6）、配额突破审批（§6.6）。

**S6 大模型工具链按租户计量 Token 与算力，超额需审批**
租户调用平台托管的模型服务，模型网关按请求记录输入/输出 Token，归集到租户。GPU/NPU 按卡·小时计量，受队列配额约束；超额时拒绝新请求，并提示申请突破。模型与智能体本身不按租户隔离，共享是收益最大化的路径，只做可见性与配额。涉及的设计点：Token 输入/输出分开计量（§6.7）、算力配额（§6.6 Q-10）、大模型成熟度 M3（§7.2）。

**S7 某租户发生故障或算力挤占，不得影响其他租户**
单个租户的工作负载出异常，先靠限流与熔断收住爆炸半径。若引起节点级资源争抢，关键租户因处于独立节点池而不受影响；平台侧再用 QoS 分级（关键/普通/批处理）和节点池物理分组进一步限制影响面。事后由隔离策略漂移检测确认隔离真的生效了。涉及的设计点：故障隔离与降级（§8.3）、节点池分级（§6.2）、漂移检测（§6.2）。

**S8 租户注销/合并时的数据归档、导出与彻底清除**
租户申请注销后先进入冻结态（保留只读 N 天），期间完成数据导出（按租户级导出清单，覆盖 8 类独立库）、归档与交接确认。冷静期（≥ 30 天）过后才执行销毁：PVC 擦除、对象存储级联删除、备份副本联动删除，审计日志按规定留存，不随租户数据一起销毁。销毁动作由平台、租户、审计三方复核。涉及的设计点：生命周期状态机（§4.4）、剩余信息保护（§9.5）、高危动作 H-06（§5.4）。

八个场景不是八个孤立用例，它们拼成一张覆盖矩阵。S1/S2 覆盖租户生命周期与低代码路径（控制面 + 应用构建）；S3/S4 覆盖数据隔离与跨租户数据流转（数据面 + 数据集成）；S5/S6 覆盖配额与计量（网关 + 模型网关，即三项 K8s 层看不见的配额）；S7 覆盖故障隔离与爆炸半径；S8 覆盖退出机制与数据交还。八个场景都落在“设计可验证”的范围内：每个都能在原型环境里用可观测指标判定通过与否（§11.3）。反过来，某个需求要是映射不到这八个场景中的任何一个，它大概率属于运行保障方案，不在本方案范围内（§8.1）。

## 第 3 章 总体架构

### 3.1 分层架构

平台分四层。层与层之间只暴露契约，不允许跨层直连：

**L1 基础设施与资源池**：信创服务器（鲲鹏/飞腾/海光）、虚拟化或裸金属、容器运行时、存储（块/对象/文件）、网络（VPC/子网/负载均衡/防火墙）。这一层承载客户既有的“资源管理运行平台（基于 K8s 增强）”。本方案不替换它，只在上面加一层租户治理。

**L2 多租户管控面**：租户管理、身份联邦与授权、配额与准入、模板与开通编排、计量采集与聚合、审计与合规。改造重心就在这里（§7.2）。租户、配额、落档、授权四类事实以管控面为唯一来源；绕过管控面直接改库，一律按违规变更处理。

**L3 平台服务层**：七大能力板块（应用构建、应用集成、数据集成、时序数据、大数据、大模型工具链、多租户管理中的服务实例部分）与中间件（缓存、消息、对象存储、调度）。某个租户在这一层用共享实例还是独立实例，由它的落档结果决定。

**L4 应用与门户层**：统一门户、统一待办、租户自建应用、外部厂商应用。一级租户有独立门户；二级租户的应用聚合到所属一级门户（沿用客户现状定义，P148）。

层间契约只有四条，每条都得显式定义、可校验，否则分层会退化成示意图。L2→L1 是“配额下发与准入拦截”：配额以声明式对象下发，准入在写入前拦截。L2→L3 是“租户上下文注入”：服务实例不采信调用方自报的租户身份。L3→L2 是“状态上报与计量流水”：实际用量与策略生效状态回传，供对账与漂移检测。L4→L3 是“仅经网关调用”：应用不得直连服务实例，这是跨租户留痕的前提。其中任何一条被绕过，都会直接破坏本章后续的一个具体结论。绕过配额下发，§6.6 失效；绕过上下文注入，§5.4 失效；绕过状态上报，NFR-10 的漂移检测失效；绕过网关，Q-07~Q-09 的计量失效。

### 3.2 部署架构与安全分区边界

**这是全方案的第一位约束，任何性能、成本、便利性理由都不构成突破它的依据。** 依据是《电力监控系统安全防护规定》（2024 年第 27 号令，2025-01-01 施行，2014 年第 14 号令已废止）：

1. 平台全部资源，包括 L3 物理隔离的独立集群，只能部署在**管理信息区（安全Ⅲ区）**。L3 的“物理隔离”指独立集群、独立资源池、独立控制面，**但仍不跨区**。
2. 生产控制区（安全Ⅰ区实时控制、安全Ⅱ区非实时）的数据只能经**电力专用横向单向安全隔离装置**单向进入安全Ⅲ区，再进平台。平台**不向安全Ⅰ/Ⅱ区回写任何控制类指令**（第九条、第十五条）。
3. **安全接入区**不得存储重要数据（第十四条），还得具备通信代理与端到端身份认证能力。场站边缘节点因此只能缓存非重要数据，原始数据一律直传。
4. 生产控制区禁止选用带无线通信功能的产品（第十三条）；重要业务优先采用可信验证（第十三条）；投运前须完成安全加固（第十六条）；基于内置探针的监测告警要同步送调度机构（第十七条）。
5. 禁止任何穿越生产控制区、管理信息区、安全接入区三者边界的通用网络服务（第十五条）。

由此得出一条要写进正文的结论：**任何“用 L3 把租户部署到生产控制区”的诉求，本方案明确不支持。** 合规依据为第九条、第十三条、第十四条、第十五条。业务方确有控制类系统建设需求的，须独立建设并单独通过电力监控安全防护测评，不在集团统一多租户平台内解决。

### 3.3 控制面与数据面分离

控制面承载租户元数据、配额、落档、授权、模板、计量配置、审计策略；数据面承载业务流量与业务数据。分离到什么程度，看下面几条：

1. **故障域独立**：控制面不可用时，已开通租户的业务流量照最后一次下发的配置继续跑；控制面恢复后按期望状态收敛（声明式 + 定期对账）。
2. **网络路径独立**：管理流量与业务流量物理或逻辑隔离（独立管理网/VPC），管理面不向租户网络开放。
3. **权限路径独立**：平台管理员对控制面有管理权；要进数据面，走高危动作流程（限时 + 双人 + 录屏 + 租户可见，§5.4 H-01/H-02）。
4. **变更节奏独立**：控制面变更视同生产发布（双人复核、灰度、可回滚）。一次错误配置会同时打到大量租户（§6.2 爆炸半径）。
5. **对账机制**：控制面记录期望状态，数据面定期上报实际状态，差异超过阈值就告警。隔离策略的漂移检测也靠这套机制实现（NFR-10）。

这个分离不是为了“架构上好看”。控制面承载两类高影响动作：配额下发与准入策略下发。一次错误下发能同时影响数百个租户，而一次数据面故障通常只影响一个租户。把两类风险放进同一个故障域、同一个变更节奏，等于拿“单租户级”的运维纪律去管“全平台级”的变更。分开之后，控制面按生产发布标准管（双人复核、灰度、可回滚），数据面按租户维度做灰度与降级，两者的责任人和节奏可以不同。§8.4 “平台组件变更视同生产发布”的制度前提，就是这条。

## 第 4 章 租户模型与治理模型

### 4.1 租户定义与分级

租户是资源、配额、身份、账单、审计五类事实的归属单元，分两级：

- **一级租户**：集团总部租户、区域/省公司租户。有独立门户、独立 SSO 能力、独立租户管理员，可代管下属二级租户。
- **二级租户**：业态租户（集团水电、集团新能源、集团煤电等）与厂站租户（电厂、场站）。**不含门户能力、不具备 SSO 能力**；应用聚合到所属一级租户的统一门户，由一级租户管理员代管（沿用客户现状定义，P148）。

“二级不自管”这个说法得写准，否则会被读成“二级被降级”。二级租户**不单独部署门户、不单独运维平台、不自建 IdP**，但**保留完整的租户内自治权**：自助建低代码应用、自助配置角色与数据权限、自助申请配额（不超上限）、自助查看本租户用量与审计。代管只是说“平台侧的运维与开通动作由一级租户管理员执行”，不是“业务权限被一级收走”。

一级租户的职责边界同样要写清，不然“一级代管”会滑成“一级包办”。一级租户管理员负责二级租户的开通申请、配额分配（不超上限）、模板下发、代登录审计；**不负责**二级租户内部的用户与角色维护、不负责二级应用的业务配置、不负责二级数据的导出审批。这三项归二级租户自己，由厂级租户管理员执行。划清这条的实际价值在于：区域公司通常只有 1–2 名信息化人员。代管范围一旦扩到业务配置，一级就成了全区域所有厂站变更的排队点，多租户的价值被流程吃掉。

同时留一个**可升级为自管**的配置开关，免得架构被锁死。开关的边界如下：

| 项 | 可升级 | 不可升级（永远继承平台） |
|---|---|---|
| 独立门户（品牌、导航、登录主题） | ✅ 配置化开通 | — |
| 独立 MFA / 密码策略 | ✅ 按 tenant_level 下发 | 不可低于平台基线 |
| 独立域名子域 | ✅ 沿用泛域名，不新建体系 | 不可脱离 `*.zhsc.chd.com` |
| 独立 IdP | ❌ 不提供 | 必须接入统一身份与统一审计 |
| 独立运维（自有 K8s 集群纳管） | ❌ 不提供 | 不进入平台运维体系 |

升级要集团审批、约定成本承担，且**升级后仍需接入统一身份与统一审计**。这条边界的作用是让“自管”停在有限能力的配置项上，不至于变成架构分叉（R-09）。

### 4.2 领域模型

以下沿用客户的概念模型（租户 1—* 用户；租户 1—* 组织；组织 1—* 员工；租户 1—* 角色；用户 *—* 角色；角色—权限；租户 1—* 订购的解决方案；解决方案 1—* 订购的产品；产品—运行/存储/中间件资源；租户 1—* 资源域，P143），另补四个扩展实体：

1. **资源域（Resource Pool）**：把“一组可分配的资源”显式建模，属性含域类型（集群/节点池/中间件实例/数据库实例/存储池）、所属分区（固定为安全Ⅲ区）、容量、已分配、落档下限。资源域既是 L2/L3 的实现载体，也是配额扣减的对象。
2. **配额（Quota）**：按 15 项指标建模，每项含默认值、上限、已用、告警阈值和生效范围（租户/子系统）。
3. **计量记录（Metering Record）**：小时采样、日汇总，字段含 tenant_id、子系统、资源类型、用量、采集来源。
4. **隔离等级（Isolation Level）**：记录档位、四维打分明细、一票否决命中项、生效时间、复核时间与降档审批记录。

1. **租户级导出清单必须在数据模型阶段就设计**。客户现有 8 类独立库（统一用户中心库、生产环境库、业务库、融合集成库、Doris 库、IoTDB 库、智能计算库、工具链库）；等到测评前再想“一键导出”，几乎做不出来。做法是给每类库登记导出器（表清单 + 导出顺序 + 依赖 + 校验和），由 metering/export 服务编排（NFR-16）。
2. **审计日志与业务数据分离存储**；租户注销时，审计日志不随业务数据销毁（法定留存）。
3. **所有表必须带 tenant_id 且不可为空**。平台侧跨租户查询走独立视图并留痕；业务代码不得直接跨租户 join。

| 定时任务 | `t-{tenant_id}-{job}` | `t-T000123-daily-report` | 防调度器被单租户打满 |

命名规范的实际作用是三件事，且都要在平台里做成强制，不能只当约定。**第一，故障定位**：平台侧看到告警时能从命名空间名直接判断是哪个租户的哪个子系统，不必再查台账。这是 NFR-14（单租户故障定位 ≤ 30 min）能否达成的前提。**第二，越权识别的第一道信号**：跨租户引用的对象名往往“看起来不属于自己”，命名规范让异常命名在审计日志里一眼可见。**第三，计量归集**：M-01~M-08 的聚合口径全依赖标签与命名的一致性；命名一随意，计量数据就归不到租户头上。三件事有个共同点，都是事后才能发现问题的场景。所以命名只能由准入控制强制（§6.2 补偿控制①），靠开发规范文档不行。

## 第 5 章 统一身份与权限

### 5.1 身份体系与对接

**一句话结论**：集团 4A 是权威源，平台只做身份联邦（SP），不做主身份库。平台侧 Keycloak 承担三件事：“协议适配 + 联邦桥接 + 外部账号域”。

依据有三条。一是“连接而非替换”是集团化 IAM 的主流取向。二是等保要求平台提供“云租户账号体系 + 主子账号 + 平台方访问可被租户审计”，这三件 4A 不会替平台做。三是责任不转移：系统上云后，安全管理责任主体与数据归属不随上云而转移。

四种对接方式的适用条件与字段映射，见下表。

**表 5-1 身份对接方式对比与字段映射（T-11）**

| 协议 | 适用条件 | 我方角色 | 必备字段映射 | 已知坑 | 定位 |
|---|---|---|---|---|---|
| OIDC | 现代 Web / 移动应用；4A 若支持则首选 | SP（Relying Party） | `sub` → `external_id`（唯一主键，禁用 email）；自定义 claim：`tenant_id`/`org_id`/`employee_no`/`roles`/`tenant_level`；`iss`+`sub` 组合唯一 | claim 体积过大导致 header 溢出；`sub` 在不同 IdP 语义不一；令牌短寿命 + Refresh 轮换必须配好 | **主协议** |
| SAML 2.0 | 传统集团 4A 极可能只支持 SAML | SP | `NameID` 格式必须协商为 **persistent**；`AttributeStatement` 承载 tenant/org/role；`SessionIndex` 用于单点登出 | 传统企业用户“90% 要求 SAML”；元数据交换与证书轮换是运维负担；多方联邦下 SLO 常不完整 | **必须并行支持（双栈）** |
| CAS | 存量子系统多、历史长 | SP 或 CAS Server | `ticket` → 校验 → `principal` + 自定义 attributes；**须在 attributes 显式带 tenant_id**（CAS 原生无租户概念） | 无标准属性规范，各家实现不一致；票据校验需内网可达 | 兼容层，只为存量系统保留 |
| LDAP | 服务账号、向下游子系统供给、非 Web 系统 | LDAP Client（读）/ 对外提供 LDAP | `uid`/`mail`/`departmentNumber`/`employeeNumber` → 平台字段；目录树层级映射到 org 树 | **目录树不做租户隔离**，多租户共用目录时必须靠 OU 分组 | 仅用于向下游供给与服务账号认证 |

**OIDC + SAML 双栈是硬要求，不能只做 OIDC。** 客户子系统数量多、历史长，第一次对接就卡在协议上的概率很高。

**对客户现状的明确纠偏：组织与用户同步模型必须改。** 客户材料表述为“每个租户都同步全量组织架构和用户信息”（P148，未提供验证证据）。本方案改成三项组合：

1. **按可见范围同步**：租户只拉本租户可见范围内的组织与人员（visible_scope），不拉全量。
2. **增量同步**：以 4A 为权威，平台侧只存只读镜像，按变更流水增量拉取。4A 若给不出增量接口，平台侧就用“全量快照 + 差异比对”实现等效增量（对应 T01 的默认假设）。
3. **冲突仲裁规则**：4A 是唯一权威，平台侧字段只读。租户本地扩展字段（如岗位、值班标记）单独放扩展表，不回写 4A。同一 employee_no 在多个租户内的角色冲突，由租户边界消解，不跨租户合并。

同时**保留租户本地副本**。客户明确诉求“独立门户断网可用”（P148），断网期间得能凭本地副本完成认证与授权判定。副本的有效期与刷新策略要在设计里给出，建议副本 TTL 与增量周期保持一致。

**表 5-2 三类特殊场景处理结论（T-12）**

| 场景 | 结论 | 理由 | 代价 / 风险 |
|---|---|---|---|
| 一人多租户（集团专家跨厂支持） | 4A `sub` → 平台唯一 user；`user 1—* tenant_membership(tenant_id, 默认标记, 有效期)`；登录后“确认租户身份 → 选择租户”（客户现状已具备此交互） | 三级管控的必然产物，靠“多账号”绕开会造成审计主体不清 | 令牌须携带“当前激活 tenant_id”，网关每次校验；切换租户重签令牌；审计记“用户 + 激活租户”二元组 |
| 二级租户复用一级 SSO | 可行，且保持“二级不具备 SSO 能力”的现状定义：二级不建 IdP、不建独立登录页，全部走一级域名与 Realm；二级身份边界由令牌 claim 中的 tenant_id 与网关校验保证 | 同业背书（区域不要求强开发能力、集中开发 + 镜像分发）；客户现状明确定义 | 二级无法独立定制 MFA/登录主题/密码策略 → 用“按 tenant_level 下发平台级策略”折中；若强要求独立 MFA，须升级为自管二级 |
| 外部厂商临时账号 | **不得进入集团 4A**（4A 覆盖内部员工）。平台自建“外部账号域”：强制 MFA + 有效期 ≤ 90 天 + 绑定具体项目/租户 + 强制操作录屏 + 到期自动禁用 + 不可自助改密；且必须映射到 vCluster/L3 边界内 | 外部主体是 L3 一票否决触发者；混入 4A 会污染权威源，权限生命周期失控 | 需额外账号台账与到期任务调度；录屏存储成本；与“一人多租户”并存时须明确“外部账号不得同时是多租户成员” |

**Keycloak 的边界必须写清**。能做的：原生 Realm 多租户、身份联邦、细粒度授权下沉、SCIM、审计事件。做不到的：**Realm 共享同一进程与数据库，不提供独立计算、独立数据库或独立故障域**，单个 Realm 高负载会拖慢其他 Realm 的延迟。所以本方案从不说“每租户一 Realm 等于每租户隔离”。Realm 只与一级租户 1:1 映射，二级租户在父 Realm 下用 Group 表达。

### 5.2 认证

1. **单点登录**：一级租户走集团 4A 联邦。租户内应用统一由平台侧网关做令牌校验，不各自对接 4A。
2. **租户隔离登录页**：二级租户复用一级门户与登录页，不开独立登录入口。一级租户可按品牌配置主题，认证流程不动。
3. **MFA 策略**：平台管理员、租户管理员、安全审计员强制 MFA；普通用户按业务敏感度分级，D ≥ 3 的租户强制。策略按 tenant_level 与 isolation_level 下发；租户不得自行降低。
4. **会话与令牌**：访问令牌短寿命（建议 ≤ 15 min），配 Refresh 轮换。令牌必须携带 `tenant_id`、`roles`、`tenant_level`。网关每次校验令牌里的 tenant_id 与目标路由的租户归属是否一致，不一致直接拒绝并告警（§5.4 第一道闸）。
5. **外部供应商/厂商账号**：走独立身份域（§5.1 表 5-2），不与内部账号合并，也不授予平台级角色。
6. **共用账号处理**：场站值班等场景采用主从账号映射，公共账号绑定多个实名登录账号，操作日志记“实际登录人 + 功能账号”，实现实名审计。值班环节的审计链靠这一条才不断（R-14）。

**图 5-1 认证与鉴权链路时序（待绘制）**

### 5.3 授权模型

三层叠加：**RBAC（角色=权限集合）+ 数据权限（行级 org_id/tenant_id、列级敏感字段）+ 场景级授权（按功能模板授权）**。

矩阵的设计原则是“能力靠角色给，风险靠动作控”。三类人员乘六类资源，解决“他能干什么”；§5.4 的高危动作清单，解决“他干这件事时怎么被看住”。只做前者会漏掉一件事：平台管理员本身就是最大的风险源。所以矩阵里刻意留了两处“—”：平台管理员不得直接修改租户内用户，专业开发人员不得创建集群级资源。这两处不是权限收窄的善意，是技术事实。前者会让“租户管理员负责本租户人员”这条审计链断裂；后者会在共享集群内引发 CRD 版本冲突，并跨租户扩散（§6.2 维度 3）。

### 5.4 越权与高危操作防护

跨租户访问设三道闸，缺一不可：

1. **令牌租户校验**：网关校验令牌 `tenant_id` 与目标路由/资源归属是否一致，不一致就拒绝并告警。
2. **服务端租户上下文强制注入**：服务端不采信前端传入的 tenant_id，以网关注入的可信上下文为准。业务代码不得自行解析租户。
3. **数据层租户过滤**：数据访问框架强制拼上 `tenant_id` 条件（或依赖数据库行级安全），不许业务手写。平台侧跨租户查询走独立视图，并留痕。

**平台运维人员进入租户数据面的机制**：授权（工单 + 租户知情）→ 审批（双人）→ 限时（exec ≤ 4 h、数据库 ≤ 2 h，到期自动回收）→ 录屏 + 命令全量审计 → 租户可见。这不是加分项，是刚性要求。等保三级明确平台方对租户系统和数据的访问操作须可被租户审计，所以平台必须真做出**租户视角审计视图**这个功能，不能只在方案里写“留痕”。

**批量导出与数据脱敏**：导出超过 1000 行须申请。导出内容按列级敏感字段自动脱敏（手机号、身份证、银行账号、精确地址）；导出行为记入审计并通知租户管理员；导出文件带有效期与水印标识。

## 第 6 章 资源隔离与配额治理

### 6.0 本章的两个前置判断

**判断一：安全分区是架构第一约束，优先级高于任何隔离等级设计。** 不管 L0 还是 L3，全部资源都在管理信息区（安全Ⅲ区）内。L3 的物理隔离指“独立集群 + 独立资源池 + 独立控制面”，不等于可以跨入生产控制区。生产控制区（安全Ⅰ区/安全Ⅱ区）的数据只能经电力专用横向单向安全隔离装置单向进入，平台不回写任何控制类指令。所以本章讨论的隔离档位，全部在“同一分区内”。

**判断二：隔离维度必须从三维扩到五维。** 同业六家的公开口径普遍是“资源 / 数据 / 应用”三维。本方案补两个：**网络带宽**（K8s ResourceQuota 不约束带宽，这个问题已被核心期刊立项研究，大数据与 AI 训练租户会把带宽打满）与**安全分区**（27 号令的分区要求）。五维是 L0–L3 矩阵的横向骨架。

### 6.1 隔离等级模型 L0–L3

**表 6-1 隔离等级矩阵（等级 × 隔离对象 × 实现手段）（T-03）**

| 等级 | 定义 | 计算隔离 | 网络隔离 | 数据隔离 | 中间件隔离 | 存储隔离 | 网关/入口 |
|---|---|---|---|---|---|---|---|
| **L0** | 共享实例共享数据，仅配置隔离 | 同命名空间共享 Deployment，靠配置/字典隔离 | 同 Service、同 Ingress，无差异化策略 | 共享库共享表 + `tenant_id` 行级过滤 | 同实例、同库、key/topic 前缀 | 同 bucket 前缀隔离（**不建议**） | 同路由，靠 header/路径分流 |
| **L1** | 逻辑隔离（默认档） | 独立 Namespace + ResourceQuota + LimitRange + **PSA restricted** + 默认拒绝的 NetworkPolicy + CoreDNS 限制跨 ns 解析 | 独立 Ingress 主机名 + 默认 deny（ingress + egress） | **共享实例独立 schema** + 行级安全（RLS）；或共享库 `tenant_id` + 强制拦截器 | 缓存独立逻辑库 + key 前缀；MQ 独立 vhost 或 topic 前缀 + ACL；对象存储独立 bucket | 独立 PVC/独立 bucket + 独立配额 | 独立 route + 独立限流/熔断 |

| **L3** | 物理隔离 | **独立 K8s 集群**（或 vCluster + 独立节点组）+ 独立资源池 + 独立控制面 | 独立网络平面 + 独立防火墙策略 | 独立数据库集群 + 独立备份域 | 独立中间件集群 | 独立存储池 | 独立入口链路（可独立出口 IP） |

**L3 仍不得跨分区**：全部资源都部署在安全Ⅲ区内，依据 27 号令第九、十三、十五条。

**落档规则**：总分 `T = B + D + R + S`（区间 4–20）。`T ≤ 6` → L0（仅非生产，登记例外，季度复核）；`7 ≤ T ≤ 9` → L1；`10 ≤ T ≤ 13` → L2；`T ≥ 14` → L3。

**一票否决升级条款（优先级高于总分，硬编码在平台准入校验里，不交人工判定）**：

1. `B = 5`（含控制指令下发）→ **不得进入集团统一多租户平台**，须独立建设并单独过电力监控安全防护测评；
2. `R = 5` 或 `D = 5` → 至少 L3；
3. `R = 4` → 至少 L2，且入平台前须完成安全接入方案评审；
4. `S ≥ 4` 且 `B ≥ 3` → 至少 L2；
5. 租户主体是**外部开发商/集成商**（非集团员工）→ 至少 L3（vCluster 起步），与打分无关。

**降档条款**：只能经集团信息化主管部门书面批准，最多降一档，且必须补三项补偿控制（独立审计流、独立限流、季度安全复核），记录进 ADR 台账，可在附录 E 检索。不给降档定成本，规则会立刻失效。

| C-5 | 中电金信、南京圣唯思等第三方基于底座开发 | 2 | 2 | 3 | 2 | **9** | **L3（外部主体一票否决）** | 打分只到 L1，但外部主体条款强制 L3。**这是本方案唯一“打分与落档脱钩”的场景** |
| C-6 | 集团级人力/财务等经营管理核心 | 4 | 3 | 3 | 4 | **14** | **L3** | 经营决策类 + 敏感数据 + 高 SLA 叠加自然到 L3；可讨论降档至 L2，须补三项补偿控制 |

**本节结论，也是本方案最重要的成本判断**：既不做“一刀切硬多租户”，也不做“一刀切软多租户”。L1 覆盖约 80% 的二级租户（厂站级）；L2 只给区域核心与主数据供给方；L3 只给外部开发商与涉密场景，目标 ≤ 5 个集群。**资源当量约为“全 L2”方案的 45%–55%**（估算值【待确认-I06】），隔离强度仍然满足分级要求。

另外三条附加判断，必须同时成立：

- 判定要“可打分、可复核、可申诉”。四维打分的意义不在精确，而在于把评审现场那句“我觉得这个得独立部署”换成“你的 D 为什么不是 4”。代价是要维护一份租户—打分—落档台账，并接受季度复核。
- 打分表最大的风险是被业务方人为压低，低报 D 和 R 就能省资源。因此一票否决条款**不能进打分**，得由平台判定，不交人工。
- 降档必须有成本：只允许降一档，加三项补偿控制，再加季度复核。

### 6.2 计算与容器隔离

**表 6-5 软隔离的九维边界：能做到 / 做不到 / 补偿控制（T-08）**

| # | 隔离维度 | 原生 Namespace 模型能做到 | 做不到的事实 | 我方补偿控制 |
|---|---|---|---|---|
| 1 | API 资源命名 | 对象名可跨 ns 重名 | — | 命名规范强制“见名知租户”（§4.5）；ns 名全集群唯一 |

| 6 | 东西向网络 | NetworkPolicy 默认 deny + CoreDNS 限制跨 ns 查询 | ❌ **CNI 不真正执行策略时策略形同虚设**（最常见的“看起来配了”） | ①CNI 能力验证进 POC 门禁；②策略漂移检测（周期 ≤ 24 h）；③跨租户调用**必须走网关并留痕** |
| 7 | 数据面/内核 | PSA restricted + 每 workload 独立 SA + 关闭自动挂载令牌 | ❌ **默认共享节点与宿主机内核**；取得节点权限后，该节点上所有租户的 Secret/ConfigMap/挂载卷均可见 | ①L2 以上用基于 VM 的容器沙箱（Kata 等）；②节点池按租户等级物理分组；③节点访问纳入高危动作清单 |
| 8 | 爆炸半径 | 准入控制事前拦截 | ❌ 策略错误配置导致的爆炸半径不可控；虚拟控制面能降低“策略错配的爆炸半径”，但**不能解决数据面隔离** | ①策略 GitOps 管理 + 变更双人复核；②准入策略分“阻断/告警”两档灰度上线；③平台组件变更视同生产发布（H-11） |
| 9 | 成本归集与计量 | 命名空间标签 + Prometheus 采集 | ❌ **无原生计价/Showback 能力**，需自建 | 自建计量流水线：标签 → 小时采样 → 租户聚合 → 日汇总（§6.7） |

四道补偿控制都要逐条落到可验收的动作上，否则“补偿”只是措辞。①**准入控制双引擎**：Kyverno 与 Gatekeeper 同时生效，前者负责命名规范与标签强制，后者负责跨命名空间引用与镜像来源校验；两者交叉校验，单引擎策略被绕过也拦得住。②**跨 ns 引用白名单 + 双向授权**：把“允许引用哪些跨租户对象”写成白名单资源，而不是散落在各 CR 的 Annotation 里；引用方与被引用方都要显式授权，授权带有效期。③**平台自身组件先过“恶意租户”测试**：把 Operator/Controller/Webhook/ServiceMesh 一律当作“可能被恶意租户诱导的组件”来测，用例包括在自有 ns 内构造指向他人资源的 spec、伪造 OwnerReference、注入异常 Annotation、诱导 Webhook 做全集群扫描。④**B 类强制隔离**：外部主体的越权尝试进不了共享控制面，从物理上掐掉 Confused Deputy 的可达路径。这四条缺任何一条，“软隔离”的底线（挡误操作、不挡故意）就不成立。

|---|---|---|---|---|---|---|

**为什么按 A/B 类分而不是按数量分，这一点要写实**：客户现状里“中电金信、南京圣唯思等第三方基于底座开发”是已经发生的事实（P153 及集团生态大会公开信息），不是假设。**L3 档不是为未来设计的，是为已经存在的第三方接入场景设计的。** 而 Namespace 的底线就是“挡误操作、不挡故意”：A 类属“内部分环境”，B 类属“多客户 SaaS”，这就是分类的技术依据。

**关于 HNC**：本方案不推荐把 HNC 作主线。理由不是“项目已死”，是两条站得住的判断。其一，Capsule 的 Tenant CR 已覆盖同一诉求，即单集群内多命名空间的租户治理。其二，HNC 的维护状态未核实【待确认-I01】，且它本身的定位是“命名空间组织与策略传播组件”，不是租户模型。**方案的结论不依赖任何过期项目的状态。** 即便核实为活跃，也只作 Capsule 的补充。

**必须承认的代价**：选 Capsule，就等于放弃“租户自定义 CRD”。将来任何租户提出“我要装一个 Operator”，都会触发升级到 L3。这条得写进 §7.4 的统管清单，成为明规则，否则会被反复挑战。

### 6.3 数据隔离

数据库三种模式怎么取舍：

| 模式 | 适用档 | 优点 | 风险 | 本方案判定 |
|---|---|---|---|---|
| 共享库共享表 + `tenant_id` 行级过滤 | L0、部分 L1 | 资源利用率最高、运维最简单 | 漏一个 where 条件即跨租户泄露；低代码元数据表多，行级过滤极易漏 | **仅用于 L0 与配置类字典表，不作业务数据默认** |
| 共享实例独立 schema + RLS | **L1 默认** | 隔离与成本的平衡点；备份按 schema 粒度可行；客户现状已具备（8 类独立库） | schema 数量随租户线性增长，需连接池与元数据管理；跨 schema 查询需显式授权 | **L1 标准做法** |
| 独立实例 | L2、L3 | 资源与故障域独立；备份恢复按实例 | 成本 2.5–3 倍；实例台账与版本管理负担 | **L2 标准做法** |

国产数据库（达梦、人大金仓）在 schema、行级安全、资源隔离上的能力存在实现差异，**具体支持度须以现场验证为准，方案不预设结论**【待确认-T19】。要验三件事：①RLS 能不能强制生效，连管理员也绕不过去；②单实例的 schema 数量上限与连接数上限；③单租户备份与单租户恢复是否可行，注意不是全库恢复。

**备份恢复的租户粒度是硬要求**：L2/L3 必须具备“单租户恢复”能力，L1 至少具备“按 schema 恢复”。跨租户备份恢复（把 A 的备份恢复到 B）列为 H-12 高危动作，双人复核加租户可见。

**时序数据**：写入路径强制注入 tenant_id 标签，保留策略分级，原始精度建议留 30 天、分钟级 1 年、小时级 3 年（**建议值，非客户基线**【待确认-T04】）。跨租户的时序查询须走白名单；共享查询接口里不许开放租户维度聚合。

**大模型与算力**：模型与智能体天生适合共享，“一个厂出问题、全集团一起排查”正是这类能力的价值来源。所以本方案**不做隔离重构**，只做三件事：Token 按租户计量、算力按租户配额、模型与智能体按租户控制可见性。

### 6.4 中间件隔离

| 中间件 | 隔离手段（L1） | 强化（L2 及以上） | 必须验证的点 |
|---|---|---|---|
| 分布式缓存 | 独立逻辑库（db index）+ key 前缀强制注入 + ACL | 独立实例 | 国产缓存产品常只支持 Redis 命令子集，Lua/Stream/复杂结构需逐项验证；集群模式差异 |
| 消息队列 | 独立 vhost（支持时）或 topic 前缀 + ACL；消费组名租户化 | 独立集群 | Kafka 原生无 vhost；原生不支持延迟/定时消息，事务仅简单事务——两票/工单类业务需 RocketMQ 或应用层补偿 |
| 对象存储 | 独立 bucket + prefix + bucket 配额 + 预签名 URL（≤ 15 min） | 独立存储池 + BYOK | S3 接口兼容度必须用真实上传/下载/预览验证，不看文档；大文件分片与断点续传行为差异 |
| API 网关 | 独立 route + 独立限流/熔断 + 租户维度计量 | 独立网关实例 + 独立证书 + 独立 WAF 策略 | 租户维度计量的准确性（网关是 Q-07/Q-08/Q-09 的唯一计量点） |

**接口抽象是双轨策略能否成立的前提**：P0 阶段必须定下四组抽象接口，即 MessageProducer/Consumer、Cache、ObjectStorage、DataSource，并在抽象层里封装租户语义（topic 前缀、key 前缀、bucket 前缀、tenant_id 强制拼接）。不做抽象，“换供应商”就等于一次应用重构。

### 6.5 网络与域名

**沿用客户既有机制，不另建域名体系。** 客户现状是泛域名 `*.zhsc.chd.com` 绑出口容器，之后创建的租户自动绑定，租户访问形如 `tenantIdA.zhsc.chd.com`；不同租户绑不同出口 IP（示例 10.12.9.1 / 10.12.9.2 / 10.12.9.3），对应生产环境的容器集群 A/B/C（P153）。这实际上已经形成“按集群分租户”的事实隔离。

在这个基础上，本方案只加三件事：

1. **租户上下文校验**：网关校验域名归属的租户与令牌 tenant_id 是否一致。
2. **出口 IP 与落档绑定**：L1 租户默认共享集群入口，L2/L3 租户分配独立入口 IP 或独立入口链路（对应表 6-1 的网关列）。
3. **证书管理**：沿用泛域名证书，只为一级租户申请子域证书，不新增第二套证书体系【待确认-T11】。

沿用而不新建，除了“不推翻客户现状”，还有一笔运维成本要算。泛域名证书只有一张，或少数几张，续期与部署都是一处操作。若给每个租户申请独立证书，900 个租户就是 900 次续期；按单次 10 分钟人工算，一年超过 150 人时。而证书过期导致的全租户不可用，正是典型的高影响低概率事故。所以本方案明确：**证书体系不扩张，租户身份靠令牌与路由校验，不靠证书区分**。客户后续若要求租户级证书（例如外部开发商要独立证书），只对 L2/L3 租户开放，并约定证书生命周期由租户自管，平台只做有效性校验。

**东西向**：同租户内调用默认放行（白名单）；**跨租户调用必须走网关并留痕**，禁止 Pod 之间直连，且需双向授权（调用方申请 + 被调用方同意）。南北向入口统一收敛到网关，管理面入口与业务入口分开。

**Q-10 与 Q-11 是本表相对通用配额模板的两个必要增量**。AI 租户的算力配额与普通业务租户是两套模型（训推共池、断点续训、跨域调度）；而 ResourceQuota 只约束 CPU/内存，不约束网络带宽，大数据与 AI 训练租户会把带宽打满。客户有新能源功率预测、径流预测、设备预警等大量 AI 场景，**不补这两项，配额治理在本客户场景下就是不完整的**。

### 7.1 应用全生命周期

**图 7-1 应用生命周期流程（待绘制）**
图示结构说明：横向五阶段泳道，“模板化开通 → 租户定制 → 版本升级 → 运行运营 → 下线归档”；四条泳道分别为“平台侧 / 一级租户管理员 / 二级租户 / 安全审计”。关键门点用菱形标出：模板选择（服务目录准入）、发布审批（租户管理员）、生产发布（双人复核）、升级窗口（租户通知）、下线确认（数据归档）。图中在“版本升级”处标注“租户无感：蓝绿/灰度 + 数据库变更前置校验”。

四个环节的机制要点：

1. **模板化开通**：以客户六类配置（容器/中间件/数据库/功能模板/安全/通知，P146）为输入，配合子系统模板与功能模板，拼出“业态 × 层级 × 落档”三维模板矩阵。开通是一条可重入的流水线，任一步失败就回滚到上一个一致状态。
2. **租户定制**：配置级（表单、流程、报表、字典）自助完成；代码级走沙箱与审核。租户不得直连平台库。定制内容与模板版本解耦，模板升级不覆盖租户定制。
3. **版本升级**：租户无感是硬要求。二级租户没人运维，升级就不能要求租户配合。做法是蓝绿/灰度发布 + 数据库变更前置校验 + 失败自动回退 + 升级窗口与租户通知（≥ 5 工作日，与等保“变更告知”一致）。
4. **下线与归档**：下线之前先做完数据导出（租户级导出清单）、归档与交接，再进注销流程（§4.4）。

四个环节里最容易被跳过的，是“模板版本与租户定制的解耦”。做法是：租户定制内容单独存进租户扩展表，并带上模板版本号；模板升级只替换平台侧定义，不覆盖租户扩展。升级时做一次“字段级兼容性校验”，不通过就暂缓该租户的升级并告警，而不是全量回滚。这么处理的原因还是二级租户无人配合：升级若要求租户逐个确认，窗口会被无限拉长。

成熟度定级要克制，本表只给 1 个子系统定 M4，其余最多 M3/M2。客户现状混合了二级（可配置、独立实例）与三级（共享实例 + tenantInfo）特征，成熟度落在 2–3 级之间，未达 4 级【待确认-T10 建议作为客户访谈确认项】。一次改造跨两级（2→4）不现实；本方案的目标只是“2/3 → 3/4 的治理层”，数据面不动。

### 7.5 租户自助服务台

服务台在 500 个以上租户的规模下是必要件，不是可选项。核心功能：服务目录（可选子系统与模板）、工单与审批流（开通、变更、配额突破、跨租户共享、自管升级）、开通时长承诺与失败回滚、用量与配额自查、审计视图入口。

**R-02 的缓解件在这里落地**。二级租户不自管带来的响应瓶颈，靠三件事缓解：一级租户管理员的批量操作（批量开租户、批量下发模板、批量调配额）、模板化下发（减少人工填写）、代登录全程审计（提效率，也不失控）。同业事实可以用来做预期管理：华能“区域侧不要求很强开发能力、集中在集团开发再以容器镜像分发”，二级单位做信息化的人可能只有一到两个人（2021 年单场演讲、单一来源，引用须注明口径）。这不是劝客户接受低服务，是让“二级不自管”的设计意图被正确理解。

### 8.2 多租户可观测

三条硬要求：

1. **指标、日志、链路统一打 tenant_id 与 subapp_id 标签**，标签由平台侧注入，不能靠应用自报：应用自报必然缺失或造假。
2. **租户视角大盘**：租户管理员看本租户的资源、配额、用量、SLA、告警；平台管理员看全平台汇总；**默认不做跨租户排行**。历史数据没有 tenant_id 的无法回溯，所以标签体系必须从 P0 第一天起生效。
3. **数据隔离下的日志查询权限**：租户只查本租户日志；平台运维跨租户检索日志属 H-03 高危动作。

有个实话要提前说。客户现有的 Prometheus + Grafana 三级分析（单租户 / 一级租户含下属 / 全平台）已经能回答“某租户用了多少资源”，但回答不了“某租户的某接口在什么时间被谁调用了多少次”。前者是资源可观测，后者是行为可观测；数据源不同（指标 vs 访问日志），采集成本也不同，后者量级高两个数量级。本方案的分工是：资源可观测复用现状，行为可观测只在网关侧做聚合计数与采样明细，**不做全量日志长期留存**。否则仅访问日志一项，就会超过业务数据的存储量。这也是 M-06 的明细“按月滚动”而非长期保存的原因。

### 8.3 故障隔离与降级

四层控制，逐层收窄爆炸半径：

| 层 | 机制 | 参数（建议值） | 说明 |
|---|---|---|---|
| 流量层 | 网关租户级限流与熔断 | 单租户并发/调用量按 Q-07/Q-09；熔断阈值按错误率 50% / 10 s | 先挡住异常流量的横向扩散 |
| 调度层 | 节点池隔离 + QoS 分级 | 关键/普通/批处理三级；关键租户 Guaranteed QoS | 防“嘈杂邻居”导致关键租户被驱逐 |
| 存储层 | 连接池与 IO 上限 | 单租户连接数上限、单租户 IOPS 上限 | 防单租户打满数据库连接 |
| 治理层 | 隔离策略漂移检测 | 全量比对周期 ≤ 24 h | 防“看起来配了但没生效” |

降级顺序是先限流，再熔断非关键租户，实在不行才考虑迁移工作负载。**任何降级动作必须记录 tenant_id 并通知受影响租户**，否则会变成“平台偷偷降级某租户”的争议源。

### 8.4 变更发布

1. **租户级灰度**：模板与平台组件升级先在 1–2 个试点租户上验证，再按业态分批；灰度期 7 天。
2. **租户级回滚**：模板版本必须能回滚到上一版；数据库变更须有可逆脚本或前置备份。
3. **升级窗口与通知**：计划内升级提前 ≥ 5 工作日通知（与等保“变更告知”一致）；升级过程不得要求租户配合，P2 要达到租户无感。
4. **平台组件变更视同生产发布**：准入策略、Operator、Webhook、CNI 策略的变更走 H-11（双人复核 + 灰度）。

### 9.2 电力监控系统安全防护

分区与边界要求已在 §3.2 列明，本节只给结论与适用边界。

| 约束 | 内容 | 对方案的直接影响 |
|---|---|---|
| 平台落位 | 全部资源在管理信息区（安全Ⅲ区）；**L3 也不跨区** | 任何“用 L3 把租户部署到生产控制区”的诉求，明确不支持 |
| 数据流向 | 生产控制区（安全Ⅰ/Ⅱ区）数据经**电力专用横向单向安全隔离装置**单向进入Ⅲ区；平台不回写控制类指令 | 所有涉及实时控制的业务不得入平台；只读汇聚类业务按 R = 4 落 L2 |
| 边界穿越 | 禁止任何穿越生产控制区/管理信息区/安全接入区三者边界的通用网络服务 | 平台不提供跨区代理、不提供跨区数据库连接、不提供跨区消息通道 |
| 安全接入区 | **不得存储重要数据**；须具备通信代理与端到端身份认证 | 场站边缘节点只缓存非重要数据，原始数据直传 |
| 无线与可信 | 生产控制区禁选无线通信功能产品；重要业务优先可信验证；投运前安全加固 | 选型硬约束写入 §10.1 评分（隔离强度项） |
| 监测告警 | 基于内置探针的监测，告警**同步送调度机构** | 平台安全采集点须支持对接调度机构告警通道 |

“禁止任何穿越三者边界的通用网络服务”这一条落到工程上，是三个具体的事，评审时通常会被问到。**第一，平台不能提供跨区数据库连接**：即使只读，也必须由隔离装置侧的应用代理转发，不能出现从安全Ⅲ区直连安全Ⅰ/Ⅱ区数据库的连接串。**第二，平台不能提供跨区消息通道**：不允许在平台内建一个“从生产控制区接收消息”的 MQ 主题并让租户直接订阅，必须由隔离装置侧的采集程序落成文件或数据表，再单向传输。**第三，平台不能提供跨区反向代理**：不提供任何“临时开通一条链路”的口子，运维手动开启也不行，因为这本身就属于通用网络服务穿越边界。这三条写进方案，就能挡住后续实施阶段最常见的一类“临时方案”。

**哪些租户/子系统不得进入平台，这里给明确清单**：含控制指令下发的系统（DCS/TCS/水电监控/风电主控等）；实时闭环控制与保护类系统；安全Ⅰ区、安全Ⅱ区内的任何业务系统；涉密系统（另有涉密网要求，不并入）。这些系统须独立建设，并单独过电力监控安全防护测评。

| 中间件 | 国产商业（东方通/宝兰德/金蝶天燕等）与开源发行版 | 材料表述“国产中间件优先、兼容开源生态”（P142） | 多租户隔离机制无公开文档；默认配置性能差距 | §10.4 八项 POC 门禁 |
| 容器多租户组件 | Capsule / vCluster | 无 | **信创环境零公开实测数据** | P0 前 6 周实测【待确认-I03】，不通过则切独立集群 |
| 时序库 | ThunderDB / IoTDB | 材料表述 IoTDB 底层、支持国产 CPU/OS | 自研组件的合规路径；开源组件的发行版要求 | 【待确认-I04】 |
| 浏览器/办公套件 | 国产浏览器与办公套件 | 【待确认-T19】 | 前端兼容性 | 关键页面兼容性测试清单 |

适配工作有个顺序问题必须提前排定：先 CPU/OS，再数据库，最后中间件。越靠下层的问题暴露越早，修复成本也越低。反过来，若先做中间件适配，等 CPU/OS 层出问题时，前面所有压测数据都要重做。顺序定了，各层的工作量归属也要明确。CPU/OS 适配属基础设施方（含客户既有云平台运维）；数据库适配由数据库厂商与应用方共同承担；中间件适配由我方与厂商共同承担；**应用代码层适配是各子系统开发方的责任，不在本方案工作量内**（这也是 §11.2 中“子系统适配”只计我方投入部分的原因）。这条不写清，实施阶段会出现“信创适配谁来做”的反复扯皮。

三条纪律。①**证据分层**：“互认证书”“信创目录”“安全可靠测评”是三种不同证据，不可混用；任何型号一律标【待核验-V02】，方案中不写“已通过信创认证”。②**不使用兼容层作为长期方案**：名义上替换了，实际还在兼容层跑原应用，会出现“名录证明在册、适配证明能跑、但无法证明真用起来”（替而不用）。③国产化率的计算分母须客户明确【待确认-T17】，方案不自行计算。

### 9.4 数据安全

**表 9-4 数据分级与管控措施**

| 级别 | 判定 | 典型数据 | 平台管控 | 跨租户流转 |
|---|---|---|---|---|
| L-公开 | 可对外 | 公开制度、新闻 | 无特殊限制 | 允许 |
| L-内部 | 企业内部一般 | 检修工单、两票、缺陷台账 | 租户内行级过滤；导出限额 | 需授权 + 留痕 |
| L-敏感 | 企业敏感 | 财务、人事、合同、客户信息 | 列级脱敏；导出需审批；强制 MFA | 双向授权 + ≤ 90 天 + 审计 |
| L-重要 | 集团重要数据 | 设备主数据、生产统计、涉网参数 | 独立实例或独立集群；BYOK；导出双人复核 | 严格受限，须数据所有者书面授权 |
| L-核心/涉密 | 国家核心数据/涉密 | 不纳入本平台 | 独立建设 | 禁止 |

数据安全法义务怎么落地：平台只提供工具，“标签 + 流转留痕 + 导出管控”三样；**定级判定权在客户数据管理方**，平台不做定级判定【待确认-T18】。跨租户流转一律走受控通道（数据服务 API），禁止库级直连。没有授权机制的“共享”属重大违规（R-06）。

数据安全有三个常见误判，要在方案里提前纠正。**一是把“加密”当成隔离**：存储加密解决的是介质失窃，不解决“同集群内另一租户能否读到”，两者不能互相替代。**二是把“脱敏”当成一次性动作**：列级脱敏必须在导出、查询、API 返回三个出口同时生效，只在导出时脱敏等于没做。**三是把“授权”当成永久**：跨租户共享一旦授权就长期有效，是本客户最可能出现的合规漏洞。所以本方案把有效期 ≤ 90 天与到期复审写成硬约束（H-04），不是建议。

### 9.5 审计

**审计的最低要求是一条三元组**：谁、在什么时间、对哪个租户做了什么。落地要求如下：

1. **审计日志独立存储、只追加、不可篡改**，与业务数据物理或逻辑分离。平台管理员没有删除权限；仅审计员可配置归档，且走 H-08 双人复核。
2. **租户视角审计视图**是功能，不是制度：租户要能查到平台方对本租户资源的所有访问（H-01/H-02/H-03/H-12）。
3. **留存期限**：平台侧在线 ≥ 6 个月，归档 ≥ 3 年（建议值，以客户制度为准【待确认-T12】）；审计日志不随租户注销而销毁。
4. **审计的审计**：审计配置的变更本身也要被记录、要双人复核，防的是“审计者被审计掉”。

选“原生 + Capsule”而不是“直接上 KubeSphere 企业空间”或“直接上 Rancher Project”，理由是后两者在能力上都能覆盖租户分组，但都要求平台把资源管理权交给它们的产品模型。客户已有基于 K8s 增强的资源管理运行平台与三级监控，再引入第三方 PaaS，就会形成两套资源视图、两套权限模型，还要叠加其信创认证状态未知这一重风险。Capsule 的价值在于它只加一层“Tenant CR + 准入 webhook + 代理”，不动客户既有的资源视图。代价是功能朴素：没有 UI、没有自服务模板、没有休眠能力，这些都要平台侧自建，计入 §11.2 模块 1 与模块 8。

**推荐组合（结论）**：A 类内部可信租户 = 原生 NS + Capsule + 准入双引擎；B 类第三方 = vCluster 或独立集群。**不推荐整平台替换客户现有容器云**。客户已有基于 K8s 增强的资源管理运行平台与三级监控，引入第三方 PaaS 会与既有资源管理冲突，且其信创认证状态未检索到。但**拿两个机制**：KubeSphere 的 Node Group（企业空间绑定节点组，适配“核心场站业务 vs 一般业务”分级）与 Rancher 的跨集群 RBAC 继承（集团定义角色一次、下发到所有下游集群，适配三级管控）。**这是“拿机制不拿平台”，成本远低于替换。**

| G-5 | 信创证据 | ①itsec 公告核对记录；②厂商互认证书**编号**；③明确区分“互认/目录/安全可靠测评” | — |
| G-6 | 故障注入 | 节点宕机、网络抖动、主备切换：恢复 ≤ 5 min，无数据丢失 | — |
| G-7 | 国产 OS/CPU 实测 | 在麒麟/统信 + 鲲鹏/飞腾上完成同 G-1~G-3 | 真实信创环境 |
| G-8 | 驱动/连接池兼容 | 与选定国产数据库版本组合验证：连接超时、事务回滚、批量写入 | 版本矩阵 |

门禁的核心是“× 3.6”这个数字，不是“跑个压测”。它来自真实失败案例：生产并发 = 测试 3.6 倍 → 上线即崩。这条门禁把“我们的测试不可信”这个常见失败模式提前封堵。

**必须承认的最大缺口**：国产商业中间件的多租户隔离机制（vhost/topic 前缀/ACL/独立 schema）几乎没有公开技术文档。方案里凡涉及“国产中间件支持某级多租户隔离”的表述，一律改成“**待厂商书面确认 + POC 验证（G-4）**”。宁可写“待验证”，不作断言【待确认-T06】。

#### 10.4.4 双轨能否成立取决于接口抽象

**表 10-6 四组接口抽象与租户语义（T-28 摘要）**

| 抽象接口 | 必须在抽象层内封装的租户语义 | 换产品时会踩的坑 |
|---|---|---|
| MessageProducer / Consumer | topic 前缀强制注入 `t/{tenant_id}/`；headers 携带 tenant_id、trace_id；消费组名租户化 | 延迟消息语义差异；事务消息实现不同；位点重置与重试/DLQ 行为不一 |

行业共性可以提炼成三条共识：**①逻辑统一、物理分散；②区域能力弱、人力少，必须集中开发 + 模板化下发；③隔离必须覆盖资源/数据/应用三维，并补网络带宽与安全分区两个维度。** 第三条是本方案相对同业的增量。同业普遍只说三维，但核心期刊已证明网络带宽不被 Quota 约束，27 号令要求分区约束，两者都靠三维矩阵表达不了。

验证按六步推进，每步都有明确产出。①环境准备与租户基线数据导入（产出：两个测试租户 + 打分台账）。②S2 全流程走通（产出：V-1 开通时长记录）。③构造越权用例 20 组（产出：V-4 拦截清单与告警记录）。④三层配额分别触发（产出：V-3 三层拦截证据）。⑤故障注入（产出：V-5 影响面数据）。⑥审计回溯（产出：V-6 五元组完整性报告）。六个产出里，③与⑥同时作为等保举证材料，①与②作为客户验收的可视化演示。

验证环境要求：一套独立集群（3 节点起）、一个 4A 测试账号源（或临时本地账号域）、一套信创环境用于 V-2/V-3 的兼容性复核。验证结论直接构成等保举证的一部分：V-2 对应“隔离失效告警”，V-6 对应“平台操作可被租户审计”。这是原型验证除技术验证之外的第二个用途。

| 安全Ⅰ区 | 生产控制区内实时控制子区 | 不得写作“控制区”“安全区Ⅰ” |
| 安全Ⅲ区 | 管理信息区内生产管理/办公子区 | **本方案全部资源的唯一落位** |
| 电力专用横向单向安全隔离装置 | 跨生产控制区与管理信息区边界的法定装置 | 不得写作“物理隔离装置”“网闸” |
| 电力专用纵向加密认证装置 | 同级或上下级之间的加密认证装置 | 27 号令增列“加密认证网关” |
| 等保 2.0 三级 | 网络安全等级保护第三级 | 首次出现须写全称 |
| 一票否决 | 优先级高于总分的强制升级/排除条款（5 条） | 由平台硬编码判定，不由人工判 |
| 四维打分 | 业务类型 B / 数据敏感度 D / 监管要求 R / SLA S，各 1–5 分 | T = B+D+R+S，区间 4–20 |
| 资源当量 | 以 L0 = 1.0 为基准的相对资源成本，非报价 | 仅用于横向比较 |
| 降档 | 经书面批准下调一档隔离等级 | 须补三项补偿控制 + 季度复核 |
| Confused Deputy | 高权限组件被低权限方诱导代为执行越权操作的攻击模式 | K8s 场景表现为跨 ns 引用 |
| 准入控制双引擎 | Kyverno 与 Gatekeeper 同时生效的策略拦截层 | 写入 etcd 前拦截，防单点失效 |
| vCluster | 虚拟集群方案，提供独立 API Server 与独立 CRD 视图 | 共享工作节点，不解决数据面隔离 |
| Capsule | 单集群内多命名空间租户治理层（Tenant CR） | 不提供租户自定义 CRD 能力 |
| HNC | 命名空间层次与策略传播组件 | 不是租户模型，本方案不列为主线 |
| 策略漂移 | 期望策略与实际生效状态不一致 | 由定期对账检测 |
| Showback | 用量可见（不出账、不排名） | 与 Chargeback 区分 |
| Chargeback | 内部结算/出账 | 需客户财务口径，本期只做评估 |
| 主张从账号映射 | 公共账号绑定多个实名登录账号以实现实名审计 | 场站值班场景必需 |
| 租户级导出清单 | 覆盖 8 类独立库的导出编排（表清单、顺序、依赖、校验和） | 等保“可迁出/可交还”的落地件 |
| 旁路隔离 | 通过独立集群/独立实例实现隔离，不依赖共享集群策略 | L3 的本质 |

**术语对照说明（旧词 → 新词）**：客户历史文档里的“生产控制大区”“管理信息大区”“控制区”“非控制区”“安全区Ⅰ/Ⅱ/Ⅲ”都是 2014 年第 14 号令的术语，该号令已于 2024 年被 27 号令取代。本方案统一按现行法规表述为“生产控制区/管理信息区/安全接入区”与“安全Ⅰ/Ⅱ/Ⅲ/Ⅳ区”；引用客户材料原文时加注“客户材料原文如此”。
