命名规范的实际作用是三件事，都要在平台里做成强制而非约定：**第一，故障定位**——平台侧看到告警时能从命名空间名直接判断是哪个租户的哪个子系统，不需要再查台账，这是 NFR-14（单租户故障定位 ≤ 30 min）能否达成的前提；**第二，越权识别的第一道信号**——跨租户引用的对象名往往"看起来不属于自己"，命名规范让异常命名在审计日志里一眼可见；**第三，计量归集**——M-01~M-08 的聚合口径全部依赖标签与命名的一致性，命名一旦随意，计量数据就无法按租户汇总。三件事的共同点是：它们都是事后才能发现问题的场景，因此命名必须由准入控制强制（§6.2 补偿控制①），不能靠开发规范文档。

@@P097@@
依据三条：一是"连接而非替换"是集团化 IAM 的主流取向；二是等保要求平台提供"云租户账号体系 + 主子账号 + 平台方访问可被租户审计"，这三件 4A 不会替平台做；三是责任不转移——系统上云后安全管理责任主体与数据归属不随上云而转移。

四种对接方式的适用条件与字段映射如下。

@@P099@@
**OIDC + SAML 双栈是硬要求，不能只做 OIDC。** 客户子系统数量多、历史长，第一次对接就卡在协议上的风险极高。

@@P100@@
**对客户现状的明确纠偏：组织与用户同步模型必须改。** 客户材料表述为"每个租户都同步全量组织架构和用户信息"（P148，未提供验证证据），本方案改为三项组合：

@@P101@@
1. **按可见范围同步**：租户只拉取本租户可见范围内的组织与人员（visible_scope），不拉全量。

@@P102@@
2. **增量同步**：以 4A 为权威、平台侧只读镜像，按变更流水增量拉取；4A 若不能提供增量接口，平台侧以"全量快照 + 差异比对"实现等效增量（对应 T01 的默认假设）。

@@P103@@
3. **冲突仲裁规则**：4A 为唯一权威；平台侧字段只读；租户本地扩展字段（如岗位、值班标记）单独存放于扩展表，不回写 4A；同一 employee_no 在多个租户内的角色冲突由租户边界消解，不跨租户合并。

@@P104@@
同时**保留租户本地副本**——客户明确诉求"独立门户断网可用"（P148），断网期间须能凭本地副本完成认证与授权判定，副本有效期与刷新策略须在设计中给出（建议副本 TTL 与增量周期一致）。

@@P105@@
**Keycloak 的边界必须写清**：能——原生 Realm 多租户、身份联邦、细粒度授权下沉、SCIM、审计事件；不能——**Realm 共享同一进程与数据库，不提供独立计算、独立数据库或独立故障域**，单 Realm 高负载会影响其他 Realm 延迟。因此本方案从不说"每租户一 Realm 等于每租户隔离"；Realm 只与一级租户 1:1 映射，二级租户在父 Realm 下用 Group 表达。

@@P106@@
1. **单点登录**：一级租户走集团 4A 联邦；租户内应用统一由平台侧网关做令牌校验，不各自对接 4A。

@@P107@@
2. **租户隔离登录页**：二级租户复用一级门户与登录页，不提供独立登录入口；一级租户可按品牌配置主题，但不改变认证流程。

@@P108@@
3. **MFA 策略**：平台管理员、租户管理员、安全审计员强制 MFA；普通用户按业务敏感度分级（D ≥ 3 的租户强制）。策略按 tenant_level 与 isolation_level 下发，不允许租户自行降低。

@@P109@@
4. **会话与令牌**：访问令牌短寿命（建议 ≤ 15 min）+ Refresh 轮换；令牌必须携带 `tenant_id`、`roles`、`tenant_level`；网关每次校验令牌中的 tenant_id 与目标路由的租户归属一致，不一致直接拒绝并告警（§5.4 第一道闸）。

@@P110@@
5. **外部供应商/厂商账号**：独立身份域（§5.1 表 5-2），不得与内部账号合并，不得授予平台级角色。

@@P111@@
6. **共用账号处理**：场站值班等场景采用主从账号映射——公共账号绑定多个实名登录账号，操作日志记"实际登录人 + 功能账号"，实现实名审计。这是审计链在值班环节不断裂的唯一手段（R-14）。

@@P114@@
三层叠加：**RBAC（角色=权限集合）+ 数据权限（行级 org_id/tenant_id、列级敏感字段）+ 场景级授权（按功能模板授权）**。

@@P115@@
矩阵的设计原则是"能力靠角色给，风险靠动作控"：三类人员 × 六类资源解决"他能干什么"，§5.4 的高危动作清单解决"他干这件事时怎么被看住"。只做前者会漏掉一个事实——平台管理员本身就是最大风险源。因此矩阵里刻意出现了两处"—"：平台管理员不得直接修改租户内用户，专业开发人员不得创建集群级资源。这两处不是权限收窄的善意，而是技术事实：前者会让"租户管理员负责本租户人员"这条审计链断裂，后者会在共享集群内引发 CRD 版本冲突并跨租户扩散（§6.2 维度 3）。

@@P116@@
> ● 完全可用（自助）｜◐ 受限可用（需审批/沙箱/受配额约束）｜○ 只读｜— 无权限

@@P117@@
**"专业开发人员禁止直连平台库"必须靠架构实现，不能靠文档约束**：网络策略隔离 + 只发应用账号不发 DBA 账号 + 数据库侧连接来源白名单，三条同时生效。

@@P118@@
跨租户访问设三道闸，缺一不可：

@@P119@@
1. **令牌租户校验**：网关校验令牌 `tenant_id` 与目标路由/资源归属一致，不一致拒绝并告警。

@@P120@@
2. **服务端租户上下文强制注入**：服务端不得信任前端传入的 tenant_id，由网关注入的可信上下文决定；业务代码禁止自行解析租户。

@@P121@@
3. **数据层租户过滤**：数据访问框架强制拼接 `tenant_id` 条件（或依赖数据库行级安全），禁止业务手写；平台侧跨租户查询走独立视图并留痕。

@@P122@@
**平台运维人员进入租户数据面的机制**：授权（工单 + 租户知情）→ 审批（双人）→ 限时（exec ≤ 4 h、数据库 ≤ 2 h，到期自动回收）→ 录屏 + 命令全量审计 → 租户可见。这不是加分项而是刚性要求：等保三级明确平台方对租户系统和数据的访问操作须可被租户审计，因此平台必须提供**租户视角审计视图**这个功能，不能只在方案里写"留痕"。

@@P123@@
**批量导出与数据脱敏**：导出 > 1000 行须申请；导出内容按列级敏感字段自动脱敏（手机号、身份证、银行账号、精确地址）；导出行为记入审计并通知租户管理员；导出文件带有效期与水印标识。

@@P124@@
设计逻辑是"能力靠角色给，风险靠动作控"：权限矩阵解决"他能干什么"，高危动作清单解决"他干这件事时怎么被看住"。只做前者会漏掉"平台管理员本身就是最大风险源"这一事实。

@@P125@@
**判断一：安全分区是架构第一约束，优先级高于任何隔离等级设计。** 无论 L0 还是 L3，全部资源都在管理信息区（安全Ⅲ区）内；L3 的物理隔离指"独立集群 + 独立资源池 + 独立控制面"，不等于可以跨入生产控制区。生产控制区（安全Ⅰ区/安全Ⅱ区）数据只能经电力专用横向单向安全隔离装置单向进入，平台不回写任何控制类指令。因此本章所有隔离档位都在"同一分区内"讨论。

@@P126@@
**判断二：隔离维度必须从三维扩到五维。** 同业六家的公开口径普遍是"资源 / 数据 / 应用"三维。本方案补两个维度：**网络带宽**（K8s ResourceQuota 不约束带宽，此问题已被核心期刊立项研究，大数据与 AI 训练租户会打满带宽）与**安全分区**（27 号令的分区要求）。五维是 L0–L3 矩阵的横向骨架。
