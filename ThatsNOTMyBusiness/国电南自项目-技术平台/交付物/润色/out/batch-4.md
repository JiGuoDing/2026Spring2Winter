@@P127@@
**L3 仍不得跨分区**：全部资源都部署在安全Ⅲ区内，依据 27 号令第九、十三、十五条。

@@P128@@
成本当量是按资源占用与人力投入做的经验估算，只用于横向比较；绝对值与报价见【待确认-I06】。开通时长的目标需客户确认 SLA【待确认-T14】。

@@P129@@
**落档规则**：总分 `T = B + D + R + S`（区间 4–20）。`T ≤ 6` → L0（仅非生产，登记例外，季度复核）；`7 ≤ T ≤ 9` → L1；`10 ≤ T ≤ 13` → L2；`T ≥ 14` → L3。

@@P130@@
**一票否决升级条款（优先级高于总分，硬编码在平台准入校验里，不交人工判定）**：

@@P131@@
1. `B = 5`（含控制指令下发）→ **不得进入集团统一多租户平台**，须独立建设并单独过电力监控安全防护测评；

@@P132@@
2. `R = 5` 或 `D = 5` → 至少 L3；

@@P133@@
3. `R = 4` → 至少 L2，且入平台前须完成安全接入方案评审；

@@P134@@
4. `S ≥ 4` 且 `B ≥ 3` → 至少 L2；

@@P135@@
5. 租户主体是**外部开发商/集成商**（非集团员工）→ 至少 L3（vCluster 起步），与打分无关。

@@P136@@
**降档条款**：只能经集团信息化主管部门书面批准，最多降一档，且必须补三项补偿控制（独立审计流、独立限流、季度安全复核），记录进 ADR 台账，可在附录 E 检索。不给降档定成本，规则会立刻失效。

@@P137@@
**本节结论，也是本方案最重要的成本判断**：既不做"一刀切硬多租户"，也不做"一刀切软多租户"。L1 覆盖约 80% 的二级租户（厂站级）；L2 只给区域核心与主数据供给方；L3 只给外部开发商与涉密场景，目标 ≤ 5 个集群。**资源当量约为"全 L2"方案的 45%–55%**（估算值【待确认-I06】），隔离强度仍然满足分级要求。

@@P138@@
另外三条附加判断，必须同时成立：

@@P139@@
- 判定要"可打分、可复核、可申诉"。四维打分的意义不在精确，而在于把评审现场那句"我觉得这个得独立部署"换成"你的 D 为什么不是 4"。代价是要维护一份租户—打分—落档台账，并接受季度复核。

@@P140@@
- 打分表最大的风险是被业务方人为压低，低报 D 和 R 就能省资源。因此一票否决条款**不能进打分**，得由平台判定，不交人工。

@@P141@@
- 降档必须有成本：只允许降一档，加三项补偿控制，再加季度复核。

@@P142@@
四道补偿控制都要逐条落到可验收的动作上，否则"补偿"只是措辞。①**准入控制双引擎**：Kyverno 与 Gatekeeper 同时生效，前者负责命名规范与标签强制，后者负责跨命名空间引用与镜像来源校验；两者交叉校验，单引擎策略被绕过也拦得住。②**跨 ns 引用白名单 + 双向授权**：把"允许引用哪些跨租户对象"写成白名单资源，而不是散落在各 CR 的 Annotation 里；引用方与被引用方都要显式授权，授权带有效期。③**平台自身组件先过"恶意租户"测试**：把 Operator/Controller/Webhook/ServiceMesh 一律当作"可能被恶意租户诱导的组件"来测，用例包括在自有 ns 内构造指向他人资源的 spec、伪造 OwnerReference、注入异常 Annotation、诱导 Webhook 做全集群扫描。④**B 类强制隔离**：外部主体的越权尝试进不了共享控制面，从物理上掐掉 Confused Deputy 的可达路径。这四条缺任何一条，"软隔离"的底线（挡误操作、不挡故意）就不成立。

@@P143@@
**为什么按 A/B 类分而不是按数量分，这一点要写实**：客户现状里"中电金信、南京圣唯思等第三方基于底座开发"是已经发生的事实（P153 及集团生态大会公开信息），不是假设。**L3 档不是为未来设计的，是为已经存在的第三方接入场景设计的。** 而 Namespace 的底线就是"挡误操作、不挡故意"：A 类属"内部分环境"，B 类属"多客户 SaaS"，这就是分类的技术依据。

@@P144@@
**关于 HNC**：本方案不推荐把 HNC 作主线。理由不是"项目已死"，是两条站得住的判断。其一，Capsule 的 Tenant CR 已覆盖同一诉求，即单集群内多命名空间的租户治理。其二，HNC 的维护状态未核实【待确认-I01】，且它本身的定位是"命名空间组织与策略传播组件"，不是租户模型。**方案的结论不依赖任何过期项目的状态。** 即便核实为活跃，也只作 Capsule 的补充。

@@P145@@
**必须承认的代价**：选 Capsule，就等于放弃"租户自定义 CRD"。将来任何租户提出"我要装一个 Operator"，都会触发升级到 L3。这条得写进 §7.4 的统管清单，成为明规则，否则会被反复挑战。

@@P146@@
数据库三种模式怎么取舍：

@@P147@@
国产数据库（达梦、人大金仓）在 schema、行级安全、资源隔离上的能力存在实现差异，**具体支持度须以现场验证为准，方案不预设结论**【待确认-T19】。要验三件事：①RLS 能不能强制生效，连管理员也绕不过去；②单实例的 schema 数量上限与连接数上限；③单租户备份与单租户恢复是否可行，注意不是全库恢复。

@@P148@@
**备份恢复的租户粒度是硬要求**：L2/L3 必须具备"单租户恢复"能力，L1 至少具备"按 schema 恢复"。跨租户备份恢复（把 A 的备份恢复到 B）列为 H-12 高危动作，双人复核加租户可见。

@@P149@@
**时序数据**：写入路径强制注入 tenant_id 标签，保留策略分级，原始精度建议留 30 天、分钟级 1 年、小时级 3 年（**建议值，非客户基线**【待确认-T04】）。跨租户的时序查询须走白名单；共享查询接口里不许开放租户维度聚合。

@@P150@@
**大模型与算力**：模型与智能体天生适合共享，"一个厂出问题、全集团一起排查"正是这类能力的价值来源。所以本方案**不做隔离重构**，只做三件事：Token 按租户计量、算力按租户配额、模型与智能体按租户控制可见性。

@@P151@@
**接口抽象是双轨策略能否成立的前提**：P0 阶段必须定下四组抽象接口，即 MessageProducer/Consumer、Cache、ObjectStorage、DataSource，并在抽象层里封装租户语义（topic 前缀、key 前缀、bucket 前缀、tenant_id 强制拼接）。不做抽象，"换供应商"就等于一次应用重构。

@@P152@@
**沿用客户既有机制，不另建域名体系。** 客户现状是泛域名 `*.zhsc.chd.com` 绑出口容器，之后创建的租户自动绑定，租户访问形如 `tenantIdA.zhsc.chd.com`；不同租户绑不同出口 IP（示例 10.12.9.1 / 10.12.9.2 / 10.12.9.3），对应生产环境的容器集群 A/B/C（P153）。这实际上已经形成"按集群分租户"的事实隔离。

@@P153@@
在这个基础上，本方案只加三件事：

@@P154@@
1. **租户上下文校验**：网关校验域名归属的租户与令牌 tenant_id 是否一致。

@@P155@@
2. **出口 IP 与落档绑定**：L1 租户默认共享集群入口，L2/L3 租户分配独立入口 IP 或独立入口链路（对应表 6-1 的网关列）。

@@P156@@
3. **证书管理**：沿用泛域名证书，只为一级租户申请子域证书，不新增第二套证书体系【待确认-T11】。

@@P157@@
沿用而不新建，除了"不推翻客户现状"，还有一笔运维成本要算。泛域名证书只有一张，或少数几张，续期与部署都是一处操作。若给每个租户申请独立证书，900 个租户就是 900 次续期；按单次 10 分钟人工算，一年超过 150 人时。而证书过期导致的全租户不可用，正是典型的高影响低概率事故。所以本方案明确：**证书体系不扩张，租户身份靠令牌与路由校验，不靠证书区分**。客户后续若要求租户级证书（例如外部开发商要独立证书），只对 L2/L3 租户开放，并约定证书生命周期由租户自管，平台只做有效性校验。

@@P158@@
**东西向**：同租户内调用默认放行（白名单）；**跨租户调用必须走网关并留痕**，禁止 Pod 之间直连，且需双向授权（调用方申请 + 被调用方同意）。南北向入口统一收敛到网关，管理面入口与业务入口分开。

@@P159@@
> 全部默认值都是**假设值**（无客户基线数据）【待确认-T10】。上限 = 默认值 × 倍数，超过上限走"配额突破审批"（H-05）。强制执行点分三层：**①K8s ResourceQuota/LimitRange（硬）→ ②平台准入校验（准硬）→ ③网关限流 + 计量后置告警（软）**，三层缺一，配额必然被绕过。

@@P160@@
**Q-10 与 Q-11 是本表相对通用配额模板的两个必要增量**。AI 租户的算力配额与普通业务租户是两套模型（训推共池、断点续训、跨域调度）；而 ResourceQuota 只约束 CPU/内存，不约束网络带宽，大数据与 AI 训练租户会把带宽打满。客户有新能源功率预测、径流预测、设备预警等大量 AI 场景，**不补这两项，配额治理在本客户场景下就是不完整的**。

@@P162@@
图示结构说明：从左到右三列，"申请/变更入口（服务台）"→"三层执行点"→"计量与告警"。中间列自上而下三个方框：①K8s 层（ResourceQuota/LimitRange，标注"硬拦截、秒级生效、覆盖 Q-01~Q-06"）；②平台准入层（开通/变更时校验，标注"准硬、覆盖 Q-04/Q-06/Q-12~Q-15"）；③网关层（限流 + 计数，标注"软、覆盖 Q-07~Q-09，唯一可计量点"）。右侧列画计量流水线（采样 → 聚合 → 比对 → 告警 → 审批）。图中用红色标出"绕过任一层 = 配额失效"。

@@P163@@
**本节结论**：配额必须有"分档 + 倍数 + 审批"三件套，只给一个数字不行。只给默认值，人人都来要突破；只给上限，小租户被大配额浪费。900 租户 × 15 项 = 13500 个配额对象，人工维护不可行，必须模板化下发，变更走 GitOps。

@@P164@@
**API 网关的定位要在本章说定**：**网关不是集成工具，是配额治理的强制执行点。** Q-07（API 调用量）、Q-08（Token）、Q-09（并发）这三项在 K8s 层完全看不见，只能靠网关与模型网关。所以 §7.2 把"应用集成（API 网关）"列为本期必改，§11.1 把网关改造列为 P0 的第一个里程碑。

@@P165@@
**计量是"补齐而非重建"，这也是本方案成本最低、说服力最强的一块**：客户已有 Prometheus + Grafana 三级资源监控（可按单租户/一级租户含下属/全平台三级分析），低代码也有统一埋点，M-01/02/03/11 四类数据在采。方案只需补"标签体系（tenant_id/subapp_id 强制标签）+ 聚合口径 + 计量库 + 展示"，**不新建监控体系**。

@@P166@@
**分期节奏上有一条重要判断**：P0 只出"用量"，P1 才出"当量"，P2 再谈"钱"。不建议在 P0 引入折算系数，一旦公布就会被当价格用，后面再调整必然起争议。另外，计量数据带商业敏感（用量高等于系统臃肿），**默认只做"本租户可见 + 平台侧汇总"，不做跨租户排行**，客户明确要求除外。
