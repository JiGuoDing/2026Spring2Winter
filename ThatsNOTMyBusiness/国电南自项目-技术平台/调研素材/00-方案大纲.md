## 0. 文档定位与写作要求（给撰写人）

- **文档性质**：架构设计方案（Design Document），不是产品宣传册，也不是实施施工图。本阶段只交"图纸 + 规范 + 原型验证方案"，不承诺上线。
- **必须适配客户**：所有章节都要落在"华电集团三级管控 + 水电/新能源/煤电/燃机多业态 + 睿思数智底座七大能力板块 + 信创 + 等保 2.0 三级 + 电力监控系统安全防护"这些具体约束上。凡是可以原样套用到任何一家企业的通用段落，一律重写或删除。
- **现状与蓝图必须分开**：客户材料中存在"已落地 / 仅设想"混排。凡涉及客户现状，必须标注证据（引用客户材料页码，如 P142–P152）或标注【待确认-Txx】。
- **占位符规则**：不确定的事实、待客户确认的口径、需现场勘测的参数，一律写成 `【待确认-Txx：具体问题】`，并在第 12 章与附录 E 中登记，编号唯一、可全文检索。
- **篇幅**：正文 1.8 万–2.4 万字；表格不少于 18 张；示意图清单见各章"图表"栏（图以图题 + 结构描述 + 待绘制标记呈现，最终由设计人出图）。
- **术语**：统一使用"租户 / 一级租户 / 二级租户 / 租户管理员 / 平台管理员 / 资源域 / 配额 / 隔离等级（L0–L3）/ 服务目录 / 子系统"。

### 第 1 章 项目背景与设计目标（约 2500 字）
1.1 集团管控模式与业务格局：总部—区域/省公司—基层企业三级；水电、新能源（风光储）、煤电/燃机三类业态的信息化差异（生产实时 vs 经营管理）。
1.2 客户平台现状盘点：睿思数智底座七大能力板块（应用构建、应用集成、数据集成、时序数据、大数据、大模型工具链、多租户管理）+ 统一门户/统一待办/统一身份/用户中心；用一张"能力—状态—证据"表（附录 A 的摘要版）。
1.3 现状差距分析：客户已具备"配置驱动的租户创建"（容器/中间件/数据库/功能模板/安全/通知六类配置，见 P146）与"共享或分离"的初步设想，但缺：①隔离等级的判定准则与代价模型；②配额与计量；③统一身份贯通与跨租户权限边界；④应用自治与集团统管的权责划分；⑤多环境与租户级运维视角；⑥治理规范（命名、接入、变更、审计）。
1.4 设计目标、范围与不在范围（明确"不做落地实施、不做具体代码改造"）。
1.5 设计原则（8 条，每条一句结论 + 一句理由）：控制面与数据面分离 / 租户无感升级 / 隔离按需分级而非一刀切 / 最小权限与默认拒绝 / 信创优先且可双轨 / 二级租户不自管但不锁死 / 配额内自治、配额外审批 / 一切可计量、可审计。
1.6 读者指引与术语表（术语表放附录 C）。

### 第 2 章 需求分析（约 2500 字）
2.1 干系人与角色：集团信息化主管部门、区域/省公司平台管理员、厂级租户管理员、厂级业务人员、专业开发人员、平台运维人员、安全审计员；一张角色—关注点—权限边界表。
2.2 典型场景（8 个，每个 150–250 字，写成"谁—在什么条件下—要做什么—系统如何响应—涉及哪些设计点"）：
  S1 集团新设区域公司，一天内开通一级租户并带上默认子系统；
  S2 某水电厂作为二级租户上线一套检修管理应用（低代码 + 流程 + 报表）；
  S3 新能源场站侧边缘节点接入集团时序数据平台，数据只在租户内可见；
  S4 两个租户之间需要共享一份主数据（供应商/设备台账）——跨租户数据授权；
  S5 专业开发人员在租户内自建微服务并接入 API 网关，受配额约束；
  S6 大模型工具链按租户计量 Token 与算力，超额需审批；
  S7 某租户发生故障或算力挤占，不得影响其他租户（故障隔离与降级）；
  S8 租户注销/合并时的数据归档、导出与彻底清除。
2.3 功能需求：FR-01…FR-36，按"租户管理 / 身份权限 / 资源配额 / 应用与子系统 / 运维运营 / 安全审计"六组编号，每条含"需求描述 + 验收要点"。
2.4 非功能需求 NFR-01…NFR-16：容量（租户数、并发、纳管节点数）、性能（登录、开通时长、网关时延）、可用性（99.9%/99.95%）、RTO/RPO、隔离强度、合规、可扩展、可运维。

### 第 3 章 总体架构（约 3000 字）
3.1 分层架构：L1 基础设施与资源池（信创服务器/虚拟化/容器/存储/网络）→ L2 多租户管控面（租户、身份、授权、配额、模板、计量、审计）→ L3 平台服务层（七大板块与中间件）→ L4 应用与门户层（统一门户、统一待办、租户自建应用）。
3.2 逻辑架构图（图 3-1）与部署架构图（图 3-2）：集团中心云 + 区域节点 + 场站边缘三级部署；管理信息大区与生产控制大区的边界（引用电力监控系统安全防护要求，正/反向隔离装置位置）。
3.3 控制面 / 数据面分离：控制面（租户与配额的事实源）与数据面（业务流量与数据）分离，控制面故障不影响已开通租户运行。
3.4 关键设计决策 ADR-01…ADR-08：每条"决策 / 备选 / 理由 / 代价 / 复审条件"。至少覆盖：软多租户 vs 硬多租户、单集群多命名空间 vs 多集群、统一身份用集团 4A 还是平台自建、数据隔离用 schema 还是实例、子系统"共享实例"还是"独立实例"、二级租户是否给独立门户、配额强制执行点放在哪、计量数据从哪采集。
3.5 与客户现有架构的映射：说明本方案哪些是"沿用"（客户已有概念模型与配置体系）、哪些是"增强"（隔离等级、配额、计量、身份贯通）、哪些是"新增"。

### 第 4 章 租户模型与治理模型（约 2800 字）
4.1 租户定义与分级：一级（集团总部、区域/省公司）、二级（基层电厂/场站）。明确"二级不自管"的准确含义：不单独部署门户、不单独运维平台、由一级租户管理员代管；但保留"可升级为自管"的开关（配置项 + 升级路径），避免架构锁死。
4.2 领域模型：租户—组织—员工—用户—角色—权限—资源域—订购（沿用客户 P143 概念模型，补充"资源域/配额/计量/隔离等级"四个扩展实体）。用 ER 关系描述（mermaid 或表结构说明）。
4.3 数据模型：核心表设计（tenant、tenant_quota、org、employee、user、role、permission、policy、subscription、resource_pool、metering_record、audit_log），字段级说明 + 关键索引与唯一约束。
4.4 租户生命周期：申请 → 审批 → 开通（模板化）→ 变更（扩缩容/加子系统）→ 冻结（欠费/违规）→ 注销 → 数据处置；状态机图 + 每个状态的准入准出条件 + 责任角色。
4.5 编码与命名规范：租户码规则（集团-区域-厂站-序号）、K8s 命名空间、数据库 schema、Redis key 前缀、Kafka topic、对象存储 bucket/prefix、域名；一张"命名规范表"，要求"见名知租户"。
4.6 治理权责矩阵（RACI）：集团 / 区域 / 厂站 / 平台运维 / 安全审计 五方在 12 项治理事项上的权责。
- **图表**：图 4-1 租户领域模型、图 4-2 生命周期状态机、表 4-1 核心表清单、表 4-2 命名规范、表 4-3 RACI。

### 第 5 章 统一身份与权限（约 2500 字）
5.1 身份体系与对接：集团统一身份/4A 为权威源，平台侧做身份联邦（OIDC / SAML 2.0 / CAS / LDAP 四种对接方式的适用条件与字段映射表）；账号唯一标识、租户归属、一人多租户（集团专家跨厂支持）的处理。
5.2 认证：单点登录、租户隔离登录页（二级租户复用一级门户）、MFA 策略（管理员强制）、会话与令牌（令牌中携带 tenant_id 与角色，网关校验）、外部供应商/厂商临时账号。
5.3 授权模型：RBAC（角色=权限集合）+ 数据权限（行级：org_id/tenant_id；列级：敏感字段）+ 场景级（按功能模板授权）。给出"三类人员（普通用户/业务人员/专业开发人员）× 六类资源"的权限矩阵。
5.4 越权与高危操作防护：跨租户访问的三道闸（令牌租户校验、服务端租户上下文强制注入、数据层租户过滤）；平台运维人员进入租户的"授权—审批—录屏/审计—限时"机制；批量导出与数据脱敏策略。
- **图表**：表 5-1 身份对接方式对比、表 5-2 权限矩阵、图 5-1 认证与鉴权链路时序。

### 第 6 章 资源隔离与配额治理（约 3500 字，全文重点）
6.1 隔离等级模型 L0–L3：L0 共享实例共享数据（仅配置隔离）、L1 逻辑隔离（命名空间/独立 schema/独立 vhost）、L2 强化隔离（独立节点池/独立中间件实例/独立网关路由）、L3 物理隔离（独立集群/独立资源池，仅限生产控制相关与特例）。给出"等级—隔离对象—实现手段—代价（成本/运维/性能）—适用业务"五列矩阵，并给出**判定准则**（按业务类型、数据敏感度、监管要求、SLA 等级打分选档）。
6.2 计算与容器隔离：Namespace + ResourceQuota + LimitRange + NetworkPolicy + Pod Security Admission + 镜像白名单 + 节点池/污点与亲和；明确软多租户的**已知局限**（共享内核、CRD/Operator 冲突、集群级资源争抢、DaemonSet 影响面），并给出补偿控制。
6.3 数据隔离：数据库三种模式（共享库共享表 + tenant_id 行级过滤 / 共享实例独立 schema / 独立实例）；国产数据库（达梦、人大金仓）在 schema、行级安全、资源隔离上的能力差异；备份恢复的租户粒度（单租户恢复是否可行）；时序数据的租户标签与保留策略。
6.4 中间件隔离：分布式缓存（逻辑库/前缀/独立实例/ACL）、消息队列（vhost/topic 前缀/ACL/独立集群）、对象存储（bucket/prefix/租户配额/预签名 URL）、API 网关（租户路由、限流、配额）。
6.5 网络与域名：租户域名规范、南北向入口、东西向调用白名单、跨租户调用必须走网关并留痕。
6.6 配额模型与治理：配额项清单（vCPU/内存/存储/实例数/命名空间数/API 调用量/Token 数/并发数）、默认配额与上限、审批流、超配与回收、配额告警阈值（70/90/100%）；配额强制执行点（K8s ResourceQuota + 平台侧准入校验 + 网关限流三层）。
6.7 计量与成本分摊：计量采集点（容器/中间件/存储/AI Token）、计量粒度（小时/日）、账单维度（租户/子系统/资源类型）、成本展示与内部结算建议。

### 第 7 章 应用自治与集团统管（约 2200 字）

### 第 11 章 实施路径与原型验证（约 2200 字）

## 2. 写作红线
1. 不许出现"赋能、抓手、闭环、数智化转型新范式"这类空话；每段必须能落到具体机制、参数、角色或流程。
2. 所有对比必须给判断，不能只罗列；给判断必须给理由和代价。
3. 所有数字（租户数、节点数、配额值、时延、人月）若无来源，必须写成占位符并给"建议默认值 + 依据"。
4. 不承诺落地时间与效果，只承诺"设计 + 验证方案"。
5. 涉密与敏感：不写客户未公开的具体系统名与内网地址，用"某水电厂""某区域公司"表述。
