**可用于方案的关键事实（分区与隔离要求，直接决定多租户平台不能跨区部署）**
1. **分区体系（新口径）**：生产控制区、管理信息区、安全接入区。生产控制区含**安全Ⅰ区**、**安全Ⅱ区**；管理信息区含**安全Ⅲ区**、**安全Ⅳ区**。
2. **第九条**：生产控制区与管理信息区、安全接入区之间的联接处**应当设置电力专用横向单向安全隔离装置**。
3. **第十条**：安全Ⅰ区与安全Ⅱ区之间、安全Ⅲ区与安全Ⅳ区之间、安全接入区与终端之间**应当设置具有访问控制功能的设备、防火墙或者相当功能的逻辑隔离设施**。
4. **第十一条**：生产控制区与电力监控专用网络广域网联接处**应当设置电力专用纵向加密认证装置或者加密认证网关**。
5. **第十二条**：生产控制区处理重要业务过程中**应当采用应用层端到端加密认证机制**；与电力调度机构交互业务数据应纳入电力调度认证机制。
6. **第十三条**：生产控制区**禁止采用安全风险高的通用网络服务功能，禁止选用具有无线通信功能的产品**，应当对外设接入行为进行管控；重要业务**应当优先采用可信验证措施实现安全免疫**。
7. **第十四条**：安全接入区应设通信代理模块，业务模块与终端间传输控制指令等**重要数据时应与终端进行端到端身份认证**；安全接入区**禁止存储重要数据**。
8. **第十五条**：禁止任何**穿越**生产控制区与管理信息区、安全接入区之间边界的**通用网络服务**。
9. **第十六条**：电力监控系统**优先选用安全可信的产品和服务**；不得选用存在已知安全缺陷、漏洞等风险但未采取有效补救措施的产品和服务；投运前应进行**安全加固**。
10. **第十七条**：运营者应建立网络安全监测预警机制，**建设基于内置探针的网络安全监测手段**；与调度数据网相连的系统，告警信息应**同步传送至相应电力调度机构**。
11. 电力监控专用网络应**在物理层面**与运营者其他数据网及外部公用数据网安全隔离；划分为**逻辑隔离**的实时子网和非实时子网，分别连接安全Ⅰ区和安全Ⅱ区。

# C. Kubernetes 多租户技术路线

## C-1 Kubernetes 官方文档《多租户》（中文）
- **类型**：开源项目官方文档 | **发布方**：Kubernetes / CNCF | **时间**：持续更新（对应 v1.3x） | **通道**：通用检索
- **链接**：https://kubernetes.io/zh-cn/docs/concepts/security/multi-tenancy/
- **可信度**：**高**（官方权威定义）

**可用于方案的关键事实**
1. 官方明确：「**硬性（hard）**」与「**柔性（soft）**」多租户**没有统一定义能适用所有用户**，应按「硬度谱系（spectrum of hardness）」理解，并可按需在每个租户上叠加多种技术。
2. 官方给出的最极端方案：「彻底放弃所有集群级别共享并为每个租户分配专用集群」；若认为虚拟机安全边界仍不足，「甚至可以在专用硬件上运行」——**必须评估更强隔离带来的多集群管理成本与复杂度**。
3. 控制面隔离的两个维度：**命名空间隔离**（单集群内 API 资源分组）与**虚拟控制面/独立控制面**。
4. **命名空间隔离的关键局限（原文明确）**：「它可能很难配置，而且**不适用于非命名空间作用域的 Kubernetes 资源，例如自定义资源定义（CRD）、存储类和 Webhook 等**」。
5. **控制面虚拟化的代价（原文明确）**：「控制面虚拟化允许以**更高的资源使用率和更困难的跨租户共享**为代价，隔离非命名空间作用域的资源」。
6. 推荐实践：**即使同一租户的多个工作负载，也应每个工作负载独立命名空间**，确保每个工作负载有自己的身份并可套用适当安全策略。
7. **Operator 在多租户下的强制要求（原文，直接可用于我方平台规范）**：Operator 应 ①支持在不同租户命名空间内创建资源，而非仅在部署 Operator 的命名空间内；②确保 Pod 配置了资源 request/limit 以保证调度与公平；③支持节点隔离、沙箱容器等数据面隔离技术的 Pod 配置。
8. 网络隔离：默认 deny 的 NetworkPolicy；DNS 层面应限制跨命名空间的 DNS 查找（CoreDNS 可基于 Kubernetes 元数据限制查询）。
9. 名称唯一性最佳实践：「**为每个命名空间赋予在集群机队范围内（即使它们在单独集群中）唯一的名字**」，以便未来在专用集群与共享集群间灵活切换。

**可用于**：第 5 章 5.1（技术路线选型的权威依据）、第 5 章 5.2（隔离边界与局限）、第 4 章 4.4（隔离矩阵）、第 7 章 7.2（Operator 规范）

## C-2 CNCF 官方：《Kubernetes 的三种租户模型》
- **类型**：官方译文（Kubernetes 多租户工作组成员署名） | **发布方**：CNCF 官微（原作者 Ryan Bezdicek/Medtronic、Jim Bugwadia/Nirmata、Tasha Drew/VMware、Fei Guo/阿里巴巴、Adrian Ludwin/Google） | **时间**：2021 前后 | **通道**：通用检索
- **链接**：http://mp.weixin.qq.com/s?__biz=MzI5ODk5ODI4Nw==&mid=2247500640&idx=1&sn=32b3bd0c0ce39aa8f80b407c30979288
- **可信度**：**高**（SIG 工作组署名定义）

**可用于方案的关键事实（这是"三模型"最权威的原始定义）**
1. **命名空间即服务（Namespace as a Service）**：租户共享集群，工作负载限制在分配给租户的一组命名空间内；集群控制面资源（API Server、调度器）与工作节点资源（CPU、内存）**可供所有租户使用**。每命名空间必须控制：**RoleBinding（访问控制）、NetworkPolicy（阻止跨租户流量）、ResourceQuota（限制资源、保证公平）**。
2. **命名空间即服务的固有限制（原文）**：租户共享集群范围资源，例如 **ClusterRoles 和 CRD**，因此**不能创建或更新这些集群范围资源**。
3. **集群即服务（Cluster as a Service）**：每租户独立集群，允许租户拥有**集群范围资源的不同版本（如 CRD）**，提供对 Kubernetes 控制面的**完全隔离**；可用 Cluster API（CAPI）创建；但成本更高。
4. **控制面即服务（Control Plane as a Service / CPaaS）**：租户拥有专用虚拟控制面，**共享工作节点**；虚拟集群用户认为与真实集群无显著差异；用户可管理自己的集群范围资源。
5. **安全底线（原文，可直接写入方案的安全基线章节）**：①**镜像扫描**；②**RBAC**（Namespace-as-a-Service 场景必须在每个命名空间级别正确配置）；③**NetworkPolicy**（建议默认拒绝所有入口和出口）；④**Pod Security Standards 采用 Restricted 策略作为默认**；⑤**Kubernetes CIS 基准**；⑥策略引擎（只允许受信任的镜像仓库）；⑦运行时扫描器；⑧基于 VM 的容器沙箱增强数据面隔离。
6. 官方警告（原文）：「**新的社区上游 Kubernetes 集群的默认安装是不安全的，你需要投资对其进行加固**」。
7. 相关工作组成员项目：**HNC（层次命名空间控制器）、Virtual Cluster / CAPI Nested、MTB（多租户基准测试）**。
8. 落地建议：多数企业会**同时使用多种租户模型**处理不同用例；遵循安全与治理最佳实践（如使用 Pod 安全标准、不使用 default 命名空间）可**更容易从一种模型切换到另一种**。

**可用于**：第 5 章 5.1/5.2（核心依据）、第 4 章 4.4、第 9 章 9.1（安全基线）

## C-4 多租户工具分层地图（Stakater MTO 文档）
- **类型**：厂商技术文档 | **发布方**：Stakater | **时间**：2026 | **通道**：通用检索
- **链接**：https://stakater.github.io/mto-docs/renovate-main-npm-minimatch-vulnerability/learn/kubernetes-multi-tenancy-tools.html
- **可信度**：**中高**（厂商立场，但**工具分层框架本身极有价值**，是本项目做选型矩阵的最佳骨架）

**可用于方案的关键事实（强烈建议采用此框架组织选型章节）**
1. **核心洞察（原文）**：几乎所有关于这些工具的争论都源于混淆了两个问题 ——
   - **隔离（Isolation）**：租户之间有多分离？命名空间 → 虚拟集群 → 托管控制面 → 专用集群，**强度与成本依次递增**。
   - **运营模型（Operating model）**：谁拥有什么、谁可以访问、可以消耗什么、满足什么标准、成本多少、集群周边工具如何。
2. **关键论断（原文）**：「一个拥有 30 个虚拟集群的平台，其运营模型问题与拥有 30 个命名空间的平台完全一样。**隔离工具不回答运营模型问题，治理工具也不提供控制面隔离**。」—— 这句话直接支撑本项目"多租户治理体系"独立成章的必要性。
3. **工具分层归类**：
   | 工具 | 类别 | 解决的层 |
   |---|---|---|
   | Multi-Tenant Operator (MTO) | 多支柱商业平台 | 集群内治理 + 模板 + FinOps + 休眠 + 生态集成 + 控制台 |
   | Capsule | 租户运营模型 | 集群内治理 |
   | HNC | 命名空间组织 | 集群内策略传播 |
   | vCluster | 虚拟集群 | 控制面隔离 |
   | vCluster Platform / Loft | 商业平台 | 虚拟集群与命名空间的统一管理 |
   | Kamaji | 托管控制面 | 控制面隔离 |
   | Hypershift | 托管控制面 | 控制面隔离（OpenShift） |
   | KCP | 逻辑控制面 | **API 多租户，而非工作负载隔离**（重要区分） |
4. **Capsule 定位**：CNCF Sandbox 项目；引入 **Tenant CR**，把命名空间归组到 Tenant 下，对命名空间、配额、网络策略、准入执行**按租户策略**；**capsule-proxy** 组件让租户用户用普通 kubectl 只列出自己租户内资源。
5. **HNC 定位（原文，重要）**：「**它不是一个租户模型** —— 没有成员、分配、成本或生命周期概念 —— 通常是平台的一个组件，而不是平台本身。」HNC 只解决"在一组相关命名空间间保持策略一致"这一个具体而真实的问题。
6. **vCluster 定位**：在宿主集群的一个命名空间里运行虚拟 Kubernetes 控制面；每虚拟集群有自己的 API Server 和自己的 CRD；工作负载同步到宿主节点。**隔离强于命名空间，但每租户需运行和维护一个控制面；它自身不提供租户治理模型。**
7. **MTO 六能力领域（可作为我方多租户平台功能清单的对照基准）**：多租户（命名空间、来自 IdP 组的 RBAC、租户范围配额、准入护栏、网络隔离，持续 reconcile）、模板（参数化环境，可强制到租户或全集群）、FinOps（按命名空间采样用量、聚合到租户、计价、历史、容量规划）、休眠（空闲工作负载定时或按需睡眠/唤醒）、扩展（把租户边界带入 ArgoCD、OpenBao/Vault 与开发工具）、控制台（对 API 暴露的同一批对象的权限感知界面）。

**可用于**：第 5 章 5.1（选型矩阵骨架）、第 4 章 4.2（生命周期/休眠/配额）、第 4 章 4.3（计量与 FinOps）、第 11 章（能力演进清单）

## C-5 Capsule vs vCluster 工程对比（2026）
- **类型**：技术媒体对比 | **发布方**：FAUN.dev | **时间**：2026-09 | **通道**：通用检索
- **链接**：https://faun.dev/toolbox/capsule-vs-vcluster
- **可信度**：**中高**（含具体数字，但为第三方评测口径）

**可用于方案的关键事实（含可用数字，建议方案引用时标注"第三方 2026 年评测）**
1. **每租户资源开销**：Capsule 租户只是一个把命名空间归组的 CR，**新增一个租户对集群几乎无成本**，所有租户共享一个控制器（评分 90 分档）；vCluster **每租户消耗一组控制面 Pod 及其数据存储，静态内存几百 MB**（评分 45 分档）—— 远低于独立集群，但跑上百个租户时会叠加。
2. **版本与成熟度**：Capsule 2020-06 公开，2022-12 进入 CNCF Sandbox，2026-09 版本 v0.14.6，**API 仍低于 1.0**；vCluster 2021-04 公开，2026-09 版本 v0.37.1，**有商业公司支持并通过 Kubernetes 一致性认证**，但**配置格式在 2024 年变过形态，升级需谨慎阅读**。
3. **社区规模**：Capsule 约 **2,200 GitHub stars / 75 contributors**；vCluster 约 **11,300 stars / 160+ contributors**（2026-09 数据）。
4. **隔离强度评分**：Capsule 54 分档 —— 「准入 webhook 在 RBAC 与网络策略之上拦截租户规则外的对象；**但租户仍共享一个 API Server 和一组节点，且不能有自己的 CRD**」；vCluster 90 分档（控制面隔离）。
5. **可移植性**：Capsule 写入命名空间的是标准 Kubernetes 对象（RoleBinding、Quota），**移除控制器后仍保留**，但 Tenant 资源及其策略字段是 Capsule 私有，换工具需重写；vCluster 为 Apache-2.0，租户看到的是标准 Kubernetes，manifest 可原样迁到真实集群，但同步配置与平台特性带不走。
6. **自服务能力**：Capsule 由 tenants owner 在命名空间配额内自建命名空间，租户规则自动复制到每个命名空间；allowed ingress classes、storage classes、registries、node selectors 的规则都在一处集中设置。vCluster 开源自建版**无自服务模板创建、休眠模式、UI**（这些在商业平台）。

**可用于**：第 5 章 5.1（对比矩阵数据源）、第 5 章 5.2（风险）、第 11 章（TCO 与运维成本）

## C-6 隔离谱系与决策矩阵（Namespace → Capsule → vCluster → 独立集群）
- **类型**：技术博客（2026 企业实践） | **发布方**：lucaberton.com | **时间**：2026 | **通道**：通用检索
- **链接**：https://lucaberton.com/blog/kubernetes-multi-tenancy-patterns-enterprise-2026
- **可信度**：**中**（个人深度技术博客，模型清晰可借用）

**可用于方案的关键事实（可直接做成方案的"隔离谱系图"）**
1. **隔离谱系（从左到右隔离递增，成本递增）**：
   `Namespace-per-tenant（RBAC+Quota，软隔离，成本低）` → `Capsule / HNC（策略引擎，中隔离，成本低）` → `vCluster（虚拟集群，强隔离，成本中）` → `独立集群（物理隔离，全隔离，成本高）`
2. **自服务命名空间能力对比**：Namespace 模型 ❌（需管理员开 ns，租户无法自服务）；Capsule ✅；vCluster ✅；独立集群 ✅。
3. **租户需要自定义 CRD / cluster-admin**：Namespace ❌❌；Capsule ❌❌；vCluster ✅✅；独立集群 ✅✅。
4. **合规隔离（compliance isolation）**：Namespace ❌；Capsule ⚠️；vCluster ✅；独立集群 ✅（最佳）。
5. **经验阈值建议（原文）**：**10 个团队以下** → Namespace-per-tenant + NetworkPolicy + ResourceQuota；**10–50 个团队** → Capsule 做自服务命名空间管理；**受监管/合规场景** → vCluster 在无物理集群前提下提供强隔离；**需要不同 K8s 版本** → 独立集群（或用 vCluster 做版本锁定）。
6. **成本效率**：Namespace 最佳；Capsule 最佳；vCluster ⚠️；独立集群 ❌。

**可用于**：第 5 章 5.1（选型结论的量化依据）、第 4 章 4.4

## C-7 namespace 不是安全边界：控制面/数据面/网络三层隔离边界
- **类型**：技术媒体深度文章（多篇交叉印证） | **发布方**：oryoy.com 等 | **时间**：2026 | **通道**：通用检索
- **链接**：https://www.oryoy.com/news/kubernetes-duo-zu-hu-bie-zhi-hui-kai-namespace-le-hnc-jin-dang-an-guan-hou-2026-nian-zhe-dao-ti-huan.html ；https://www.oryoy.com/news/yi-ge-ji-qun-zhu-er-shi-ge-tuan-dui-kubernetes-duo-zu-hu-zhe-men-he-zu-sheng-yi-dao-di-gai-zen-me-ta.html
- **可信度**：**中**（技术媒体，但引用了 Kubernetes 官方与阿里云 ACK 文档）

**可用于方案的关键事实（第 5.2 节"隔离边界与局限"的主要弹药）**
1. **核心论断**：「Kubernetes 到现在也没有一个原生对象叫 tenant。你手里那些 namespace、RBAC、ResourceQuota、NetworkPolicy，拼起来才叫'多租户'。」
2. **官方口径转述**：namespace 是**命名、配额和 RBAC 边界，不是天然安全边界**。
3. **共享清单（同集群内所有 namespace 仍共享的 6 项）**：**API Server、etcd、CRD、admission webhook，默认还共享节点和宿主机内核**。
4. **两个典型翻车场景（原文）**：
   - 租户 A 装了一个 operator，**CRD 版本跟租户 B 撞了**，大家一起看 controller 报错；
   - 租户 C 的控制器疯狂刷 API Server，**API Priority and Fairness 能缓一下，但不能把 noisy neighbor 变没**。
5. **HNC 状态变化重要提示**：2026 年讨论"**HNC 进档案馆（归档）**" —— 说明 HNC 已不推荐作为主线方案，**选型时须核实 HNC 的维护状态**（⚠️ 本条为二手转述，**须以 kubernetes-sigs/kubernetes-namespace 项目仓库现状核实**）。
6. **隔离边界三层模型（Sysdig 口径）**：控制面 / 节点·Pod / 网络；**namespace 只覆盖第一层的一小块，下面两层基本裸奔**。
7. **数据面风险的实证描述**：「攻击者一旦摸到节点权限，这台机器上**所有租户的 Secret、ConfigMap、挂载卷就是"开卷考试"**——它们都是节点级可见的」。
8. **行业共识一句话（可直接引用为方案结论）**：「**Namespace 能挡住误操作，挡不住故意搞事**。对内部分环境、dev/test 混用，够了；对外卖资源、跑多客户 SaaS，不够。」
9. **多租户底线配置清单（原文，建议原样纳入我方平台基线规范）**：
   - 每个 namespace 默认 **deny ingress/egress 的 NetworkPolicy**，**CNI 必须真正执行策略**（否则策略形同虚设）；
   - **Pod Security Admission 直接上 restricted**；
   - **ResourceQuota 和 LimitRange 一个都不能少**；
   - **租户零 cluster-admin**；
   - 每个 workload 一个 **ServiceAccount**，默认 `automountServiceAccountToken: false`。
10. **三种形态的取舍**：Namespace as a Service（资源利用率高、开通快，但**租户用不了集群级 API，想装 CRD 都得找管理员**）；节点/集群隔离（安全最硬，成本高、开通慢，CNCF 报告将资源利用率列为"低到中"）；虚拟集群（折中，独立 API Server + 自己的 CRD 视图）。

**可用于**：第 5 章 5.2（核心依据）、第 9 章 9.1（安全基线）、第 4 章 4.4（隔离矩阵的"边界"列）

## C-8 Black Hat USA 2026：Kubernetes 多租户隔离为何反复失效（Confused Deputy）
- **类型**：国际安全会议议题笔记 | **发布方**：Black Hat USA 2026（讲者 Lorin Lehawany、Sven Nobis），中文笔记见 cn-sec | **时间**：2026 | **通道**：通用检索
- **链接**：https://cn-sec.com/archives/5442513.html ；https://cn-sec.com/archives/5395111.html
- **可信度**：**高**（国际顶级安全会议议题，有明确讲者与方法论）

**可用于方案的关键事实（这是"硬多租户 vs 软多租户"结论最有力的实证支撑）**
1. **核心结论**：**Namespace 仅提供名称作用域（name scoping），而非安全边界**；RBAC、NetworkPolicy、Pod Security Standards、Admission Controller、镜像扫描、ResourceQuota **全部必要，但都不能自动保证 Namespace 隔离**。
2. **根因（Confused Deputy / 混淆代理）**：Kubernetes 生态中**大量 Namespaced Resource 会被高权限 Controller 解释，并影响其他 Namespace、共享入口、整个 Service Mesh，甚至集群外部系统**。租户只能在自己 Namespace 中创建对象，却能**在对象字段或 Annotation 中引用其他租户的资源**；Controller 以更高权限解析引用并更新全局配置 —— **原本正确的 RBAC 因而成为 Confused Deputy 的入口**。
3. **三类实证案例**：**Kubeflow、Traefik、Istio** —— 覆盖控制平面、数据平面、身份平面及集群外部的跨租户影响。
4. **非漏洞类攻击（架构性弱点）——「Notebook 钓鱼」**：攻击者在共享 namespace 创建一个自定义镜像的 Notebook（镜像内含凭证窃取逻辑），然后**授权受害用户访问**；诱使受害者点击链接并交互，恶意镜像即拿到受害者凭证。**结论：当一个租户能在共享空间创建"看起来正常"的资源并诱骗他人交互时，隔离假设本身就不成立。**
5. **可复用的三步方法论（强烈建议写入我方平台的多租户安全评审流程）**：
   - **识别**：哪些资源在租户控制之下？哪些控制面交互和数据面流量跨越 namespace 边界？**特别检查 CR 的 spec 里有没有引用其他 namespace 的字段、Annotation 里有没有跨 namespace 引用**。
   - **评估**：对已识别的交叉引用评估影响（信息泄露 / 权限提升 / DoS / 数据面劫持）；提问方式是「**如果这个租户是恶意的，他能不能影响到其他 namespace？**」，而不是假设所有租户都按文档使用平台。
   - **修复**：优先级从低到高 —— 部署厂商补丁 → 使用已有 admission policy 集合（**Kyverno / Gatekeeper**）→ 定义自定义策略。
6. **关键防御论断（原文）**：「**Admission Control 在资源被持久化到 etcd 之前拦截，这是 Kubernetes 安全模型中最有效但最被低估的防御层。**」
7. **安全引用要求（原文）**：**双向授权**（引用方与被引用方都同意）、**限制跨 namespace 引用**、**审计间接资源**。

**可用于**：第 5 章 5.2（核心依据）、第 9 章 9.1（准入控制与策略引擎要求）、第 12 章（风险 R-01：软多租户被绕过）

## D-2 超大型建筑集团统一身份认证架构（中建类集团）
- **类型**：行业分析文章 | **发布方**：TrueSight | **时间**：2025—2026 | **通道**：通用检索
- **链接**：https://tsight.io/articles/20182429
- **可信度**：**中**

**可用于方案的关键事实**
1. 组织复杂度刻画（与我方场景高度同构）：「总部、分局、项目部及众多下属企业」→ 传统碎片化认证模式既增加员工操作成本，更在**安全审计与权限管控**上留下治理漏洞。
2. IAM 定位升级：从"登录工具"升华为「**企业治理的数字底座**」与「数字通行证」，核心目标是构建**中心化身份源（Identity Source）**，实现"一次认证，全网通行"。
3. 架构定位：认证系统处于所有业务平台**上游**，扮演"流量调度员"与"权限校验官"，通过 **SAML 2.0 / OAuth 2.0 / OIDC** 把底层身份数据与上层业务应用**解耦**。

## D-6 Keycloak 多租户 IAM 架构：Realm 隔离模式与真实边界
- **类型**：技术文档（IDaaS Book） | **发布方**：idaas.xlabs.club | **时间**：2025—2026 | **通道**：通用检索
- **链接**：https://idaas.xlabs.club/docs/advanced-topics/multi-tenant-iam
- **可信度**：**中高**（技术文档，观点克制且有明确边界声明）

**可用于方案的关键事实（这是评估 Keycloak 能否承载集团级多租户的核心依据）**
1. **三种隔离模式**：①每租户一个 **Realm**（隔离强度高，配置/用户/会话边界独立）；②高隔离要求下每 Realm 独立数据库 schema 或独立 Keycloak 实例；③所有租户共享一个 Realm，通过 Group/Role 隔离（省资源）。
2. **Realm 模式的优点**：一个 Realm 的配置错误不影响其他 Realm；每租户可**独立定制登录主题、MFA 策略、Session/Token 超时、密码策略**；**性能隔离**（一个租户高负载不会拖垮其他）；**可按租户粒度做备份/恢复/导出**。
3. **Realm 模式的缺点（原文，方案必须写明的代价）**：运维成本显著增加（100 个 Realm = 100 套配置要维护）；新增租户需创建 Realm、配客户端、设策略，**自动化要求高**；**升级需确保所有 Realm 兼容**（版本升级可能涉及每个 Realm 的迁移）；Realm 数量增大后，**启动时间、管理操作、缓存占用、数据库连接与配置漂移**都可能成为瓶颈。
4. **关键边界（原文，务必写入方案的风险栏）**：「Keycloak 的 Realm **共享同一服务进程和数据库**，Realm 隔离了配置、用户和会话边界，但**不会自动提供独立的计算、数据库或故障域**。」—— 即 **Realm ≠ 性能隔离，也 ≠ 故障域隔离**（与第 1 点的"性能隔离"表述需区分：配置层面隔离 vs 资源层面隔离）。
5. **容量验证要求（原文，建议直接采纳为我方验收标准）**：生产前至少记录 —— 启动/滚动升级耗时、登录 **P95/P99**、数据库 CPU 与连接数、缓存命中率、**单租户噪声对其他租户的影响**、单 Realm 导出/恢复耗时。
6. 「不要把某个 Realm 数字写成通用阈值」—— 反对拍脑袋定容量上限。

**可用于**：第 6 章 6.1（IAM 选型：Keycloak 的可行性与代价）、第 6 章 6.3（租户隔离模式）、第 12 章（风险：IAM 成为单点瓶颈）

## D-7 Keycloak 工程架构与选型边界（源码级尽调）
- **类型**：技术深度分析 | **发布方**：稀土掘金（个人作者，源码级） | **时间**：2025—2026 | **通道**：通用检索
- **链接**：https://juejin.cn/post/7685332147724369930 ；https://quant67.com/post/iam/16-keycloak-internals/keycloak-internals.html
- **可信度**：**中**（个人深度分析，技术判断可采信，结论需自验）

**可用于方案的关键事实**
1. **支持**：云原生友好（内置 Quarkus 运行时、**K8s Operator**、原生容器部署与水平扩展）；密码与安全逻辑集中在独立 crypto 模块；RedHat 官方长期维护。
2. **原生局限（原文）**：**代码库体量巨大（9k+ 源码文件）**，二次修改与深度定制门槛高；**核心链路为同步模型**，高并发认证场景需仔细评估吞吐量；大量分支用于**协议兼容**，每个分支都是潜在安全面，需完整回归测试；**网络 I/O 较多**（外部身份联邦、SAML 回调、元数据拉取依赖外部网络），**网络抖动会直接影响认证流程**。
3. **「谨慎或替换」场景（原文，可用于我方的风险论证）**：超高并发/毫秒级低延迟认证场景；仅需简单 JWT 签发的极简场景；**安全合规要求极高、不允许庞大代码库带来大面积安全审计工作量**；资源受限边缘环境（无法承载 Java 应用内存开销）。
4. **Realm 性能陷阱（原文）**：「**所有 Realm 共享同一个数据库连接池和 JVM 堆**。一个大 Realm 的高负载（如某企业客户在上班高峰期的集中登录）会影响其他 Realm 的延迟。」
5. **生产落地硬建议（可直接写入我方 IAM 部署规范）**：数据库**锁死 PostgreSQL**（远离 Dev 模式 H2）；连接池与 schema 迁移（Liquibase）纳入发布流程；集群先想清楚 **Infinispan 拓扑**（单站点与跨站点是两套配置）；会话数量直接消耗堆内存，**JVM 堆与 off-heap 要提前压测**；密钥不得明文存库，用 **vault SPI 接 KMS/HSM**；自研 SPI 要锁定版本（**升级时二进制兼容性没有保证**）；**Access Token 短、Refresh Token 轮换**；前端走授权码 + PKCE。
6. **综合评价**：「**跨数据中心与会话一致性被普遍低估，小规模跑得顺，一上多区域就出问题**」—— 直接命中我方"集团—省公司—场站"多区域部署场景。
7. **能力亮点**：Realm **原生多租户**；**Identity Brokering**（把 AD、另一个 Keycloak Realm 注册为 IdP 做身份联邦）；细粒度授权可下沉到**资源实例级**（多数竞品只到"角色"层）；**Token Exchange（RFC 8693）**；FAPI、PKCE、**SCIM 同步**、完整审计事件。

**可用于**：第 6 章 6.1（选型与代价）、第 6 章 6.3（跨区域会话一致性）、第 12 章（风险）

## D-8 开源 IAM 横向对比（Keycloak / Casdoor / Zitadel / Authentik）
- **类型**：技术文档 | **发布方**：IDaaS Book | **时间**：2025—2026 | **通道**：通用检索
- **链接**：https://idaas.xlabs.club/docs/advanced-topics/opensource-iam-comparison
- **可信度**：**中高**

**可用于方案的关键事实**

5. **区域间数据交互两种方式（可直接借鉴）**：①集团数据官网平台的**数据目录**，让二级单位**订阅**财务报表、指标类数据；②**基于 Alluxio 与集团大数据湖构建数据高速通道**，区域各自有数据湖，通过**集群到集群**方式调用数据。**结论：API 方式只适合小批量或已深度治理的指标类数据；一旦是 1PB–2GB 级别的明细数据，API 调用无法实现，必须用高速通道。**
6. **开发能力的集中与分发模式（重要设计模式）**：「区域侧部署的底座，**我们不要求区域有很强的开发能力，不需要有很多开发工具，完全集中在集团上面开发**，使用 Alluxio 调取数据后通过现有开发工具，**再用容器镜像分发下去，达到云边协同**。使得开发的所有业务集团都可感知、并能共享，方便大批量推广。」
   → **这与我方"二级租户不自管、不带门户"的约束完全一致，是"集团集中开发 + 镜像分发到二级"模式的公开同业范例。**
7. **⚠️ 二级单位信息化人力现实（对方案第 11 章的运维模式设计是决定性依据）**：「传统央企、能源央企里边存在一个很大的问题是人员。**二级单位做信息化的人可能只有一到两个人**，对于他们来说建立一个云平台管控机房都会非常累。要建立一个统一的 **PaaS 运维管理**，相当于把他们的业务分发给我们专业化的信息公司，让信息公司去**接管所有 PaaS 运维的内容**，帮忙监管应用、资源、做版本升级、统一内容分发…你只需要管好硬件基础设施。」
8. **为什么二级单位不统一建的四条原因（原文）**：①**体量不同**（山东 16 家电厂 vs 贵州 2 个风电厂）；②**业务模式不同**（有的靠现货只做电力交易，有的靠传统火电，有的靠物资检修运输）；③**投资规模差异大**（大的二级单位投几千万，小的只有三百多万预算）；④结论：「很难用一套特别标准化的东西把所有东西固定到一起，**只能提供一套技术框架，制定一套标准保证集团整个技术体系的统一性**。」
   → **这句话是方案"统一技术框架 + 差异化配置"总体策略的最佳同业背书。**
9. **数据平台四层**：IaaS → PaaS（数据集成、传统 ETL、实时数据库、大数据环境含 Alluxio 数据编排与 HDFS 体系、数仓、数据治理）→ **DaaS**（敏捷化开发报表体系，主要为 BI；含数据目录、发布、订阅、权限）→ SaaS。

3. **安全审计（双重要求）**：①「应支持对云服务商和云租户远程管理时执行的**特权命令**进行审计」；②「应支持**租户收集和查看与本租户资源相关的审计信息，保证云服务商对云租户系统和数据的访问操作可被租户审计**。」
   → **第②条是"平台方必须向租户开放审计视图"的强制要求**，方案中多租户管理平台的"应用分析/资源监控"模块必须能还原"平台管理员对某租户做过什么"。
4. **入侵防范**：「应能检测到**虚拟机对宿主机物理资源**的异常访问」；「应支持对云租户进行**行为监控**，对云租户发起的恶意攻击或恶意对外连接进行检测和告警」。
5. **数据保密性**：「应提供重要业务数据加密服务，**加密密钥由租户自行管理**」；「应提供加密服务，保证虚拟机在**迁移过程中**重要数据的保密性。」→ **密钥租户自管（BYOK）是刚性要求**。
6. **数据备份与恢复**：应采取冗余或分布式架构；应支持**数据多副本存储**；应支持**通用接口**确保云租户可以将业务系统及数据**迁移到其他云计算平台和本地系统**（可移植性）。
7. **第四级的额外要求（可预判客户未来升级需求）**：「为第四级业务应用系统**划分独立的资源池**」；「对虚拟资源的主体和客体设置**安全标记**的能力」。
8. **网络架构**：应实现**不同云服务客户虚拟网络之间的隔离**（通常通过 VPC 技术实现，同 VPC 内默认互通，不同 VPC 默认不通）；建设策略可参考「**VPC 网络在租户数据传输过程中进行 VXLAN 封装实现租户隔离**」。

**可用于**：第 9 章 9.1（条款级对照）、第 6 章 6.3（主子账号）、第 4 章 4.4、第 8 章（密钥与数据可移植）

## F-12 等保 2.0 云计算扩展要求的学理分析（公安部第三研究所，核心期刊）
- **类型**：**核心期刊论文**《网络空间安全》第 10 卷第 7 期 | **发布方**：赖静、韦湘、陈妍（**公安部第三研究所**） | **时间**：2019-07 | **通道**：通用检索
- **链接**：http://mp.weixin.qq.com/s?__biz=MzU3MTU0NDQ1Ng==&mid=2247484932&idx=2&sn=ecbbed267675971c519651db9f9b30ee
- **可信度**：**高**（公安部三所为等保标准起草与测评主管机构）

**可用于方案的关键事实**
1. 等保 2.0（GB/T 22239-2019）相比 2008 版三大变化：①名称与《网络安全法》对齐；②**由一个基本要求变为"安全通用要求 + 4 个安全扩展要求"**（云计算、移动互联、物联网、工业控制）；③基于「**一个中心，三重防御**」思想重组为 **10 个安全类**（安全物理环境、安全通信网络、安全区域边界、安全计算环境、安全管理中心、安全管理制度、安全管理机构、安全管理人员、安全建设管理、安全运维管理）。
2. **测评方式（重要）**：云计算系统测评内容为 **1+N 模式**，依据包括「**安全通用要求 + 云计算安全扩展要求**」两部分。
3. **多租户风险的原始表述（可直接引用）**：「云租户在享受云计算技术带来便利的同时，也面临着云计算共享技术带来的一系列风险，如**租户间资源的隔离、租户间数据的非法访问**，此外**云服务商对云计算平台拥有过大的权限**。」
4. **测评实际发现的三类问题（方案第 12 章的合规风险可直接引用）**：
   - **重技术、轻管理**：责任主体倾向通过技术手段（防火墙、防毒墙、IDS/IPS、WAF、加密、冗余）保障安全，**安全管理约束缺失**；
   - **责任划分不明确**：云服务商与云租户对 IaaS/PaaS/SaaS 三种模式下的控制范围与责任范围划分不清，租户「不主动承担己方应有的安全责任」；
   - **云租户备份容灾意识不强**：过度依赖云平台。
   → **解决路径（原文）**：建设系统前**了解清楚自身使用的云服务模式与各自控制范围、责任范围**，并通过**签订有效协议明确各自职责**。
5. 明确 GA/T 1346-2017《信息安全技术 云操作系统安全技术要求》可作为剩余信息保护能力的测评参考。

**可用于**：第 9 章 9.1（学理与测评实践）、第 12 章（合规风险与责任划分）

## F-13 《中华人民共和国数据安全法》（2021）

- **链接**：https://www.cac.gov.cn/2021-06/11/c_1624994566919140.htm
- **可信度**：**高**

**可用于方案的关键事实**
1. **第 3 条（定义）**：数据 = 任何以电子或者其他方式对信息的记录；**数据处理**包括收集、存储、使用、加工、传输、提供、公开等；**数据安全** = 通过采取必要措施，确保数据处于**有效保护和合法利用**的状态，以及具备保障**持续安全状态**的能力。

4. **第 22–23 条**：建立数据安全**风险评估、报告、信息共享、监测预警**机制；建立数据安全**应急处置**机制。

## F-15 SaaS 成熟度四级模型（学术来源）
- **类型**：**学术期刊论文**《重庆大学学报（自然科学版）》 | **发布方**：重庆大学期刊社 | **时间**：2014 | **通道**：通用检索
- **链接**：http://qks.cqu.edu.cn/html/cqdxzrcn/2014/2/201402004.htm
- **可信度**：**高**（学术来源，模型为业界通行）

**可用于方案的关键事实（第 4 章评估我方多租户成熟度的标尺）**
1. **四级模型定义（原文）**：
   - **第一级：定制开发，多次开发多次部署**。每个用户独占一个独立的数据库实例和应用服务器实例（与 ASP 基本一致）。
   - **第二级：可配置，一次开发多次部署**。开发通用型产品并提供可配置功能，每个用户仍独占实例，但运行同一份代码。
   - **第三级：高性能的多租户框架，开发和部署各一次**。**多用户共享一个实例**；由于共享实例，「**用户数据安全和数据隔离就显得十分重要**」；随之而来的是**集中式数据性能成为瓶颈**。
   - **第四级：可伸缩性多租户框架，一次开发无限次扩展**。核心是**水平扩展性**：在不更改应用架构的情况下，仅通过添加硬件设备缓解访问压力（通过负载均衡分散压力）。
2. **第三级的关键工程手法**（可用于评估我方现状）：增加 **Tenant 表**描述租户信息；在**大部分与租户有关的数据表中增加 `tenant_id` 字段**；业务数据查询过滤时**都增加 `tenant_id=?` 过滤条件**。
3. **⚠️ 与我方现状的对照判断（我方分析，非原文）**：从 A-9 本地材料看，睿思底座的现状是「**每类能力对应独立数据库实例（PRD）+ 支持多租户共享容器或独立容器部署**」，混合了**二级（可配置、独立实例）**与**三级（共享实例 + tenantInfo）**的特征 —— 即**成熟度在 2–3 级之间，尚未达到 4 级（可伸缩多租户）**。**这一判断建议列为客户访谈确认项。**

**可用于**：第 2 章 2.2（现状成熟度评估）、第 4 章 4.1（演进目标定级）、第 11 章（演进路径 2→3→4 级）

- **类型**：学术论文 / 科技成果 | **发布方**：南瑞集团、国网浙江、北京邮电大学；山东电科院、中国电科院 | **时间**：2015—2020 | **通道**：通用检索

## ①-2 隔离强度的"看得见"与"看不见"原始事实

| 隔离维度 | Namespace 模型能做到 | Namespace 模型做不到（事实描述） | 来源 |
|---|---|---|---|
| API 资源命名 | 对象名可跨命名空间重名 | — | C-1 |
| 授权 | RBAC Role/RoleBinding 命名空间作用域 | 无法阻止**高权限 Controller 解析跨命名空间引用**（Confused Deputy） | C-8 |
| 集群级资源 | 租户**不能创建或更新** ClusterRoles、CRD、StorageClass、Webhook | 租户**无法安装自己的 CRD**；CRD 版本冲突会**跨租户互相影响** | C-1, C-2, C-7 |
| 调度公平 | ResourceQuota + LimitRange + API Priority and Fairness | **噪声邻居无法消除**；**Quota 不约束网络带宽**（K8s 原生无网络配额） | C-7, F-2 |
| 网络 | NetworkPolicy（默认 deny）+ CoreDNS 限制跨 ns 查询 | **CNI 不真正执行策略时策略形同虚设** | C-1, C-7 |
| 数据面/内核 | Pod Security Admission restricted + 基于 VM 的容器沙箱 | **默认共享节点与宿主机内核**；节点权限被拿到后**所有租户 Secret/ConfigMap/挂载卷节点级可见** | C-2, C-7 |
| 爆炸半径 | 准入控制（Kyverno/Gatekeeper）事前拦截 | 策略错误配置导致的爆炸半径**不可控** | C-1, C-3, C-8 |
| 成本归集 | 命名空间标签 + Prometheus 采集 | 无原生计价/Showback 能力（需 MTO 类平台或自建） | C-4, A-9 |
| 性能隔离 | — | 共享 API Server / etcd / JVM / 数据库连接池（IAM 场景） | C-7, D-6, D-7 |

## ①-3 可直接引用的三个"分界线"论断（原文）
1. **官方**：「namespace 是命名、配额和 RBAC 边界，**不是天然安全边界**」[C-1/C-7]
2. **SIG 工作组**：命名空间即服务模型下「租户共享集群范围资源，例如 **ClusterRoles 和 CRD，因此不能创建或更新这些集群范围资源**」[C-2]
3. **安全研究**：「**Admission Control 在资源被持久化到 etcd 之前拦截，这是 Kubernetes 安全模型中最有效但最被低估的防御层**」[C-8]

## 三、三条最关键的发现（对方案走向有决定性影响）

### 发现一 ⚠️ 方案引用的核心法规已更新：14 号令已被 27 号令取代
- **事实**：《电力监控系统安全防护规定》已由 **发改委 2014 年第 14 号令**更新为 **2024 年第 27 号令**（国家发改委官方解读明确"取代原 2014 年 14 号令"）[B-1]。
- **术语也变了**：14 号令是「生产控制**大区**（控制区/非控制区）+ 管理信息**大区**」；27 号令是「**生产控制区（安全Ⅰ/Ⅱ区）+ 管理信息区（安全Ⅲ/Ⅳ区）+ 安全接入区**」[B-2, B-3]。
- **影响**：如果方案沿用旧术语和旧条款编号（业内模板极常见），会在专家评审时被直接挑错。**必须全量替换。**
- **额外提醒**：14 号令核心内容已固化为 **GB/T 36572-2018**，并于 2022 年泛化为 **GB/Z 41288-2022** —— 方案可以引标准号，比引旧号令更稳妥 [B-1]。

### 发现二 ✅ "二级租户不自管、无门户、无 SSO"的选择有强同业背书，但"软多租户"存在已被实证的安全边界
- **背书面**：中国华能明确表述"**区域侧不要求有很强的开发能力，完全集中在集团开发，再用容器镜像分发下去**"；且"**二级单位做信息化的人可能只有一到两个人**""大的投几千万、小的三百万"——与我方"二级租户不自管、不带门户"的约束**完全同构** [F-4]。国网云、南网云、国家能源、三峡五家均为"逻辑统一、物理分散"的集团+区域节点架构 [F-1, F-5, F-6, F-7, F-8]。
- **风险面**：Black Hat USA 2026 的实证研究证明 —— **Namespace 只提供"名称作用域"，不是安全边界**；即使 RBAC、NetworkPolicy、PSA、准入控制全部到位，**大量 Namespaced Resource 仍会被高权限 Controller 解释，并在对象字段/Annotation 中跨命名空间引用，形成 Confused Deputy**（已知受影响：Kubeflow、Traefik、Istio）；甚至存在不依赖漏洞的「**Notebook 钓鱼**」——恶意租户在共享空间投放看似正常的资源，诱使他人交互即窃取凭证 [C-8]。
- **对方案的直接结论**：
  1. 我方的"一级租户 = 集团/省公司"（可信度高、数量少）与"二级租户 = 场站业态"（可信度较高、数量多）**本身不是不可信租户** → **纯 Namespace 软多租户在业务上可接受**；
  2. 但**必须叠加四道硬约束**：①准入控制双引擎（Kyverno/Gatekeeper）在 etcd 写入前拦截跨 ns 引用；②**CR 的 spec/Annotation 跨 ns 引用白名单化 + 双向授权**；③**平台自身组件（Operator、Controller、Webhook、ServiceMesh）必须首先通过"恶意租户"测试**（依据 C-8 的三步方法论）；④**对"外部应用开发商"这一类真正不可信的接入方，必须隔离到 vCluster 或独立集群** —— 这条对现状中"中电金信、南京圣唯思等第三方基于底座开发"的场景（A-5）**是刚性要求**。
  3. 这与官方文档的"谱系"结论一致：**租户信任等级决定隔离强度，而不是租户数量决定隔离强度** [C-1, C-6]。

### 发现三 ⚠️ "东方通实测效果不行"在公开渠道几乎无法举证，但可以换成更站得住的论证路径
- **检索结论**：**未检索到任何公开、具名、可复核的东方通负面测评或权威通报**（详见 E-13.1 的六方向检索表）。直接说"东方通不行"在方案评审中**无法举证，且存在合规风险**（对供应商的无据贬损）。
- **但找到了三条可公开引用、且论证力更强的替代证据**：
  1. **横向数据**：中国信通院 2025-06 基准中，宝兰德 BES 10.0（TPS 25,200 / P99 8.2ms）**优于** TongWeb 7.0（23,800 / 10.5ms）[E-4，需回溯]；
  2. **默认配置与最优配置差距极大**：某国家级政务平台需 **近 400 项参数调优**才把响应时间从 1200ms 降到 280ms [E-4] → **"开箱即用体验差"是行业已知现象，可公开引用**；
  3. **行业故障率**：信创替代中**中间件适配问题占应用故障的 27%**，仅次于数据库 32%（中国信通院 2025）[E-4]；且有"测试环境 OK、上线后高峰期线程池耗尽与连接泄漏，因**生产并发是测试的 3.6 倍**"的真实案例 [E-4]。
- **由此推出的、评审站得住的双轨策略**：
  - **轨一（主）**：**开源组件 + 国产 OS/CPU 上的发行版验证**（Kafka/RocketMQ/Redis/MinIO/Nginx 在麒麟/统信 + 鲲鹏/飞腾上做适配），依据官方口径"开源组件通常不强制替换，但需国产云厂商托管版本或信创认证发行版" [E-9, E-12]；
  - **轨二（辅/合规兜底）**：中间件层引入**第二家国产供应商**（宝兰德 BES / 金蝶天燕 Apusic / 中创 InforSuite），**不做单一供应商锁定** —— 依据是 2026 年中央国家机关框采中 Web 中间件有 5 家、消息中间件有 6 家可选 [E-4]；
  - **技术落点**：代码层**抽象 Producer/Consumer、Cache、ObjectStorage 接口**，保留跨产品迁移能力 [E-9, E-10]；
  - **门禁**：**测试环境压力 ≥ 生产峰值 × 3.6**，所有中间件必须通过我方场景化基准测试才能进生产 [E-4]；
  - **措辞**：我方结论写成"**在我方特定业务场景与参数配置下的 POC 实测未达要求**"，而非"产品不行" [E-13.2]。
