## B 它做对了什么

### B.1 核心洞察是对的

这份设计最重要的句子，不是“做四类缓存”，而是：

> 缓存价值不是对象的静态属性，而是对象、请求、动作、依赖状态和系统负载的函数。

这直接拒绝了三个常见但薄弱的假设：命中率高就是收益高；相似度高就是可复用；验证是免费的安全动作。

```flow LR
(请求) -> [候选/硬门]
[候选/硬门] -> [三动作]
[三动作] -> [生命周期]
[生命周期] -> [反馈]
```

### B.2 几个必须保留的工程边界

| 设计点 | 为什么值得保留 |
|---|---|
| 把 VERIFY 作为一等动作 | 验证有成本，也有残余风险；不能默认“先判官再复用”。 |
| 权限、模型 revision、依赖版本做硬门 | 这些不是可被概率平均掉的风险。 |
| 只承诺“相对已记录依赖”的一致性 | 避免把缺失依赖或延迟事件说成已被解决。 |
| 记录后台验证、刷新、失效和恢复成本 | 防止把在线延迟下降误报成系统净收益。 |
| 设计负结果和降级路径 | 比只写“预期提升”更符合答辩要求。 |
| 使用现有 Flink Jobs 工程作为试验台 | 已有 user-scoped state、exact-match cache、TTL、短期记忆和 checkpoint。 |

`flink-jobs` 中的 `CustomerSupportAgentJob` 已经是一个可运行的真实 Agent 链：`userId` keyed state、exact-match response cache、TTL、短期会话记忆、vLLM Chat Completions 和 checkpoint。

`PlanActSupportJob` 已有 plan/tool 执行状态，但没有响应缓存。

2026-11-16 重新运行该工程测试：44 tests，0 failures，0 errors。这是工程底座测试，不是缓存收益实验。

最现实的落地是扩展现有 customer-support job。把售后政策文档和订单数据版本化，复现一次政策更新对证据与回答缓存的影响。

这降低了“从零搭 Flink 平台”的工程量。当前章节应明确把它作为实现底座，而不是把 Flink 本身当成创新。

## C 为什么当前还不是完整证据链

### C.1 范围前后不一致

| 位置 | 现在的说法 | 冲突 |
|---|---|---|
| 初稿 15 行 | “Agent 的各个中间结果都纳入缓存对象” | 四类对象并不等于所有中间结果；ctx 还被排除。 |
| 初稿 21–33 行 | 列出 resp / rag / act / plan 四类 | 初稿 35 行紧接着写“以下三类对象”。 |
| 初稿 212 行 | 主要实现与实验只做 resp / rag | 设计稿又说四类对象同等研究地位。 |
| 初稿 298–300 行 | 实验只围绕 resp / rag | 不能据此外推四类对象的同等结论。 |

这不是文字小错，而是论文主张的范围问题。**“统一接口可承载四类对象”不等于“四类对象都得到了同等实证”。**

### C.2 统一的动作名，隐藏了四种不同语义

| 对象 | 直接复用实际是什么 | 验证实际是什么 | 重算实际是什么 |
|---|---|---|---|
| resp | 返回完整回答 | LLM judge 或规则检查答案可接受性 | 重新生成 |
| rag | 复用证据集合，可能还要补检 | 检查权限、版本、证据覆盖和补检 | 重新检索与加工 |
| act | 返回只读工具结果 | 检查工具、参数、环境与外部状态 | 重新调用工具 |
| plan | 绑定参数或使用计划片段 | 检查阶段、前置条件、工具和可执行性；可能修复 | 重新规划 |

rag 的“复用有效证据 + 只补检缺失部分”和 plan 的“适配 + 验证 + 局部修复”都是复合动作。

如果主表只有 REUSE / VERIFY_THEN_REUSE / RECOMPUTE，这些复合动作会被伪装成一个单一动作。

### C.3 数学上最容易被追问的六处

| 问题 | 现在的风险 | 最低修复 |
|---|---|---|
| 动作基线 | W 写成了对象属性；C_l 是否共同成本不清 | 用请求级路径成本 C_M(r) 与 C_a(r) 比较。 |
| 覆盖价值 | N_i(H) × S_i 会把重叠条目重复相加 | 改为相对于当前集合的边际安全覆盖 ΔN_i(H|M)。 |
| 管理价值 | D_i=V_i/s_i 不含扇出、失效域和风险暴露 | 管理价值加入下游扇出/风险，或明确它只是局部启发式。 |
| 刷新级联 | m_j(H) × C_rebuild(j) 可能把一次性重建按每次命中重复计费 | 区分一次性重建与每请求重算。 |
| 风险约束 | q_UCB ≤ δ_remaining 与窗口风险预算不是同一单位 | 拆成单次返回门 + 窗口/域预算。 |
| 硬门与软风险 | q_auth/q_model 既出现在风险向量，又被当作硬门 | 明确硬门失败不进入可交易风险预算。 |
| 单步决策 | NV 只比较当前动作成本，不计验证对后续信念和生命周期的影响 | 若保留 VERIFY，加入决策边界价值信息；否则明确它是 myopic heuristic。 |
| 负载价格 | λ 来自第二章，第一章的复用又改变第二章负载 | 外生化负载档位，或给出固定点/双层控制条件。 |

```callout err 一个具体反例
若一个请求既可被 resp 命中，也可被 rag + 生成服务，则不能同时把“整次生成节省”和“检索节省”相加。

一个请求最终只走一条服务路径。跨层价值必须相对于整条路径定义，不能按层独立求和。
```

### C.4 系统不变量没有真正落地

| 问题 | 证据 | 后果 |
|---|---|---|
| 淘汰与失效混用 | 初稿 246 行正确区分“删除缓存副本”和“底层事实变化”；设计稿 1363–1369 行又说淘汰上游会让下游失效 | 容量压力被误当成逻辑事实变化。 |
| 读、版本和后台完成跨 key | 设计稿先把请求按 tenant key、版本按 dep key、完成按 item key 路由 | Flink 只保证单 key 串行，不自动保证跨 key 原子性。 |
| 权限过滤晚于 ANN | 设计稿 725 行要求权限先行；请求伪代码 1407–1411 行却是先 ANN 后 auth | 候选存在性、相似度和日志可能形成侧信道。 |
| version_vector 名不副实 | 实际是构建时的依赖版本快照，不是分布式版本向量 | 版本分支、同号不同内容和乱序事件无法正确处理。 |
| 全局预算放在 tenant-keyed state | 约束是全局的，状态却是按租户保存 | 严格全局预算难以原子执行，可能持续超支。 |
| EVICT 删除元数据 | 删除后还需要反向索引做级联 | 后续版本事件找不到下游条目。 |

若管理价值最终只用 D_i=V_i/s_i 排序，它在结构上已接近 GDSF 和 FinCacheServe 的 U/size。要么加入扇出、更新风险和失效域，要么明确它只是基线。

命题 1–3 目前主要是期望成本的代数移项和线性阈值。它们可以作为引理或验收条件，但不宜作为本章的主理论贡献。

初稿 35 行说动作价值可先统一采用端到端耗时；238 行又说不把风险和时延直接相加。两条口径不能同时做主表。主表应采用风险约束口径，Q·L 只放敏感性分析。

对未登记依赖，不要只报“未登记率”。做注入式审计：改一个未登记依赖，检查是否被错误复用；安全性结论只覆盖已审计依赖集。

这部分应作为**实现前的阻断项**，不是“后续工程优化”。

### C.5 实验还只是目录

当前 1.4 有正确的指标方向，但没有把主张、对照、主指标、门槛和失败条件绑定。

| 现在缺什么 | 为什么重要 |
|---|---|
| P0 复用经济学测量 | 若复用率低或验证税高于节省，后面的复杂模型没有意义。 |
| Oracle 与人工/执行标签 | 没有可信标签，决策后悔和风险预算没有分母。 |
| 固定 matcher 的 2×2 实验 | 不能把“联合系统的收益”误归因于更好的匹配器或更多调参。 |
| 总成本账本 | 候选签名、embedding、ANN、judge、回放、刷新、存储和恢复都要计入。 |
| 漏复用与假阴性指标 | 只报告“错复用少”会奖励过度保守的缓存。 |
| 冷启动与时间切分 | 会话相关、非平稳，不能按独立请求随机切分。 |
| 域级尾部风险 | 期望错误率达标不代表没有热租户连续出错。 |

引用清理也要做：RAGCache 的 TOCS 年份口径不一致；Pensieve 是 KV/上下文旁证，正文未实际引用；AgenticCache、GenCache、IC-Cache、SmartCache 等出现在表中，却没有完整参考文献。

## D 文献撞击：不能再说“这些都是新点”

截至 **2026-11-16**，至少以下工作已经直接或邻近覆盖了当前设计的一部分。

| 工作 | 状态 | 已覆盖 | 当前设计还剩什么 |
|---|---|---|---|
| [SafeCache](https://arxiv.org/abs/2611.10418)，arXiv:2611.10418 | 预印本 | 直接复用、选择性验证、重生成的 routing；验证调用预算与 unsafe-reuse 目标 | 只能保留跨对象依赖与生命周期，不能再把单层动作选择作为首创。 |
| [GroundedCache](https://arxiv.org/abs/2605.27494)，arXiv:2605.27494 | 预印本 | query、证据重叠、来源版本、答案支持四门联合判断 RAG 答案复用 | 只能保留部分证据复用、回答修复和预算控制。 |
| [Multi-Turn Semantic Caching](https://arxiv.org/abs/2611.01077)，arXiv:2611.01077 | 预印本 | 多轮 reuse risk、预算化缓存集合、离线/在线学习 | 通用“风险 + 集合”新颖性很弱。 |

| [GenCache](https://arxiv.org/abs/2511.17565) | NeurIPS 2025 | 结构化生成程序、先验证再复用、负反馈删除/重生成 | 结构化程序缓存和验证复用已有正式基线。 |

**在本次抽查中，最有价值且尚未发现直接同构工作的空位**，是这些机制的交汇：

```callout ok 最值得保留的差异
上游证据或工具版本变化后，刷新会同时降低陈旧暴露，并使多个下游回答/计划命中失效。

在共享验证/刷新预算下，对刷新级联、下游重建和命中损失计价，并做合并调度。
```

这只说明“本次检索未发现直接同构工作”，不是穷尽性新颖性证明。它仍比“四类对象共享一个接口”更像一个可被实验证伪的新问题。

## E 我建议的重新定位

### E.1 一句话主张

> **面向版本化 RAG 的证据—回答可修复复用。**
>
> 目标是在最终答案风险预算与有限验证/刷新预算下，联合选择证据动作和回答动作。

它不是“统一四类对象的完整系统”，而是一个窄的两阶段问题：

- 证据层：REUSE / VERIFY / REFRESH；
- 回答层：REUSE / REGENERATE；
- 依赖链：文档 D → 证据 R → 回答 A；
- 可选扩展：act → resp/plan 或 plan → act 的一条工具/计划链；
- ctx 只作为版本、权限和失效来源；
- KV/prefix cache、embedding/向量库、生产级多区域一致性明确排除。
- 投毒、侧效应工具和跨区域安全只做硬门/边界说明，不作为概率风险来交易。
- 第一版使用外生负载档位和实测单位成本，不在线求解跨章节 λ 的固定点。
- 本章固定缓存容量和后台预算；GPU 扩缩容、副本数和全局路由留给第二章/第三章。
- 前提：来源提供版本/摘要或条件 GET，且能在证据块级判断变化；否则 B 退化为全量重检索。

```callout info 运行示例
政策文档只改了一个段落。证据集合有 3 块，2 块仍支持当前问题，1 块失效。

独立层门控可能整层重检索；全有或全无的依赖门可能让整条回答失效。可修复复用只补检失效块，再决定回答复用还是重生成。

GroundedCache 式全量证据验证更安全，但作者报告在 document drift 下会把缓存命中压得很低。B 的问题就是：能否在风险约束下恢复部分可用命中。
```

### E.2 只保留三个核心 Claim

| 编号 | 主张 | 判定性证据 |
|---|---|---|
| C1 | 证据层风险不能替代最终答案风险 | q_total ≈ q_evid·τ + q_base·(1−q_evid) 的校准与对照。 |
| C2 | 联合选择证据与回答动作，优于两层独立门控 | 2×2 动作实验：独立层最优 vs 联合动作的 fresh-goodput。 |
| C3 | 在相同验证预算下，按最终答案边际风险分配验证，优于按层平均或按不确定性排序 | 固定预算、固定 δ 的预算分配实验；只在验证可能跨过联合动作边界时购买验证。 |

### E.3 数学骨架先修到能算

对请求 r 和当前缓存集合 M，先定义整条服务路径的成本：

$$
C_M(r)=\min_{\pi\in\Pi(M)} C_\pi(r)
$$

再用路径成本定义动作价值：

$$
\Delta_a(r)=C_M(r)-C_{M,a}(r)
$$

这比把每层内部节省相加更不容易重复计数。

对证据风险向最终答案的传播，保留设计稿中很有价值的方向：

$$
q_{\mathrm{total}}\approx q_{\mathrm{evid}}\tau+q_{\mathrm{base}}(1-q_{\mathrm{evid}})
$$

其中 q_evid 是相对于当前问题的证据失效概率，不是文档错误概率。τ 必须通过“同一请求分别使用缓存证据与 gold 证据生成”的对照来测，不能当作固定常数。

可做的理论内核是“决策边界价值信息”。若当前风险区间不跨过 REUSE / REGENERATE / REFRESH 的动作边界，额外验证就没有决策价值。这个引理比把“更不确定就多验证”写成启发式更有辨识度。

对刷新级联，把一次性重建和每请求重算分开：

$$
\Delta_k = \mathbb{E}\left[\sum_{r\in H}(C_{\mathrm{no-refresh}}(r)-C_{\mathrm{after-refresh}}(r))\right]
-C_{\mathrm{refresh}}(k)
-\sum_{j\in Desc(k)} \mathbf{1}[N_j(H)>0]\,C_{\mathrm{rebuild-once}}(j)
$$

这条式子比 m_j(H) × C_rebuild(j) 更不容易把一次性重建重复收费。

### E.4 三条路线的取舍

| 路线 | 创新上限 | 四个月可行性 | 判断 |
|---|---:|---:|---|
| A：四类对象统一准入 | 2.5/5 | 3/5 | 保留标签，但仍背四套数据；容易变成带四种特征模板的 U>0。 |
| B：证据—回答可修复复用 + 级联判定 | 3.5–4/5 | 4.5/5 | 推荐；主线窄，有交互实验，可接现有 Flink 工程。 |
| C：风险校准 + 决策边界价值信息 + 集合优化 | 4–4.5/5 | 2.5–3/5 | 上限最高，但理论风险高；适合导师明确要求理论贡献时。 |

当前方案更接近“A 加完整生命周期”。它保留了最多的对象，却没有给出一条足够尖锐的交互主张。

我的选择是 B。只有导师明确要求理论贡献时才选 C；只有导师坚持四类对象标签时才选 A，并把 A 的实证降到准入与接口层。

### E.5 状态与安全不变量

把生命周期拆成四个正交轴：

| 轴 | 取值 | 作用 |
|---|---|---|
| payload | PRESENT / ABSENT / TOMBSTONED | 物理副本是否存在。 |
| validity | CANDIDATE / VALID / SUSPECT / INVALID | 逻辑上能否复用。 |
| task | NONE / QUEUED / RUNNING / FAILED | 后台任务状态。 |
| policy | NORMAL / FROZEN | 业务策略，不得绕过硬门。 |

EVICT 只改变 payload；INVALIDATE 才改变 validity。

版本事件至少带 source_sequence、content_digest 和 event_id；同版本不同摘要必须 fail closed。

权限过滤要在 ANN 之前完成。读路径、版本失效和后台完成要么在同一 keyed operator 内串行，要么使用 entry_generation、base_dependency_snapshot 和 auth_epoch 做 CAS 发布。

checkpoint 只恢复元数据；外部索引和真实来源版本在恢复后必须重新校验，校验前禁止复用。

## F 最小研究范围：五个 P0 加一个条件性微基准

| P0-C | 跨层动作 2×2 | 独立层最优、联合动作、Oracle | 联合动作在 ≥10% 请求改变决策，且 fresh-goodput ≥8% | 跨层耦合不成立，收缩为单层风险门。 |
| P0-D | 刷新级联 | TTL、仅依赖失效、级联调度、合并刷新 | M(i) 中位数 ≥1.2，级联改变 ≥5% 的刷新决策 | 级联降级为负结果；保留失效不变量。 |

### F.1 对照与统计底线

强基线至少包括：no-cache、exact cache、GDSF、vCache、SafeCache 式答案路由、GroundedCache、FreshCache、FinCacheServe、Multi-Turn 式风险集合、StepCache 式和 Oracle。

所有策略固定同一 retriever、generator、judge、候选集和调参预算。没有官方实现时，明确写“按论文复现的近似版”，不要把论文数字当成自己的结果。

主数据优先选择 mtRAG/document-drift 或政策文档库，并接入 Wikipedia revision history。HotpotQA 只用于有标准答案的受控 QA 标签。

主实验还要做替换式因子：淘汰策略 ∈ {价值密度, LCFU} × 刷新策略 ∈ {TTL, 级联}，报告交互项和边际贡献。不能只做 on/off 消融。

在正式写方法前做 3–5 天 pilot：复用率、C_v/W、M(i) 三个数先落地。

建议起始规模：约 10^4 请求、10^2–10^3 文档、10^2 次版本更新、每请求 3–5 个证据块。用 2–4 张 GPU，不追求生产规模。

统计采用会话/租户 cluster bootstrap；稀有错误用 exact binomial CI；合成器至少 5 个种子；主门槛预注册。

标签审计报告 judge 与人工的 κ、误批准率、误拒绝率，以及 judge 噪声向 δ 的传播。不要让同一个 judge 既是策略组件，又是唯一测试真值。

### F.2 统一结果表

| 维度 | 必报指标 |
|---|---|
| 质量 | 最终答案正确率、证据支持率、人工接受率 |
| 新鲜度 | stale-served rate、文档变更后的答案错误率 |
| 安全 | unauthorized reuse = 0、权限撤销后的泄漏 = 0 |
| 收益 | GPU-ms、token、检索调用、工具调用、远端字节、总成本 |
| 成本 | 指纹、embedding、ANN、judge、回放、刷新、存储、探索、恢复 |
| 体验 | p50 / p95 / p99、goodput、恢复时间、churn |
| 行为 | 动作分布、决策翻转率、漏复用、无效重生成、刷新后未使用率 |

fresh-goodput 应是主指标：满足质量、新鲜度和 SLO 的任务数除以时间。它不是单纯的缓存命中率。
