## 1 参考论文在「问题背景」上的共同写法

### 1.1 总判断（分析稿开篇结论）

> 结论先行：这批论文**几乎没有人用「缓存很重要」开篇**。它们先给重复的证据，再把「朴素复用为什么会错」写成矛盾，最后把矛盾收束到某个中间结果层。

即：**证据 → 矛盾 → 收束到对象层**，而不是「价值 → 意义 → 重要性」的三段式。

### 1.2 七步共同骨架（分析稿 A 卡片）

| 步骤 | 论文在这里放什么 | 1.1 要准备什么 |
|:--|:--|:--|
| 场景定位 | 固定系统形态：Plan-Act、RAG、多轮会话、具身循环 | 流式 Agent 的事件流：请求、工具返回、证据更新 |
| 重复证据 | 比例、token、时间、金额 | 四类对象各自的重复形态与可测口径 |
| 成本测量 | 把重复换算成延迟、费用、显卡小时 | 统一口径：用户端时间、token、调用次数、后台工作量 |
| 朴素复用失效 | 精确匹配不中、语义匹配不等价、KV 依赖前缀 | 三类失效分别落在哪类对象上 |
| 局部性来源 | 需求头部集中、结构模板、DAG 依赖、工作流顺序 | 复用机会来自结构、版本还是权限 |
| 收益口径 | 命中率乘单次节省，再减开销 | 只把「通过有效性检查的复用」计入收益 |
| 难点收束 | 有效性、验证成本、失效传播、非平稳 | 四个小点与两条路径 |

配套流程：`场景与事件流 → 重复现象 → 成本测量 → 朴素复用失效 → 中间结果可复用性与风险 → 收益口径 → 难点清单 → 四个子问题`。

**关键结构性认识**：链路稳定，各篇的差别只在「把哪一步当作主要矛盾」。

### 1.3 三条共同出发点（为什么值得缓存中间结果）

1. **成本位置。** 最贵的阶段在中间——规划、检索、工具调用，而不是最后的逐 token 解码。
2. **结构可复用。** 中间结果自带结构：计划模板、文档块、工具历史、DAG 子图；结构让匹配比「整句相似度」更准。
3. **风险可治理。** 中间结果可以绑定依赖、版本、权限与校验；最终答案很难这样做。

### 1.4 八种开场招式（分析稿 B 卡片）

| 招式 | 代表论文的开场动作 | 适用条件 | 风险 |
|:--|:--|:--|:--|
| 成本测量开场 | Continuum 先说明 end-of-turn 驱逐对工具型 Agent 失效 | 有真实负载统计 | 没有自己的数据会显得空泛 |
| 矛盾开场 | vCache 指出静态阈值无正确性保证；Krites 指出单阈值造成硬权衡 | 已有主流方案可攻击 | 需要准确复述他人做法 |
| 地图开场 | APC 列 context caching 与 semantic caching 都不适用；GenCache 列精确与语义都不适用 | 要引入第三类对象 | 地图画错会被审稿人抓住 |
| 局部性观察开场 | Cortex 引用远端检索占 40–50% 时间与热点集中；CachedAttention 统计 73% 多轮会话 | 有可引用的统计 | 统计口径必须注明 |
| 失败模式开场 | Continuum 用图 1 给出两种失败模式；CacheBlend 指出前缀缓存只覆盖 8% 请求 | 能画出示意图 | 图必须对应真实机制 |
| 风险与时效开场 | FreshCache 对比首都与比分；FinCacheServe 举财报修订 | 对象会过期 | 需要给出风险预算口径 |
| 结构定义开场 | GenCache 用结构化、受控变化、响应可预测三条性质定义新问题类 | 要造一个新对象类 | 定义要能落到匹配算法 |
| 评测缺口开场 | SCBench 指出多数方法只在单请求 benchmark 上评测 | 做评测贡献 | 需要先证明缺口影响结论 |

**选择结论**：要论证「缓存 Agent 中间结果」的必要性，最稳的是 **「地图开场 + 局部性观察」**——前者排除已有方案，后者给出自己的复用机会。

### 1.5 按缓存对象分层的四种范式

这批论文的写法可以按「缓存哪一层」分成四种，范式彼此不同：

**（1）resp 层（C 卡片，5 篇：vCache / Krites / MVR-cache / SISO / MeanCache）**
共同写法：**先承认语义缓存有效，再把「相似不等于正确」写成核心矛盾**。
- vCache：先承认可省高达 100 倍延迟，再指出工业界统一用静态阈值 0.8；45k 样本上正确命中与错误命中的相似度分布高度重叠。给用户错误率 δ 的统计意义保证，收益最高 12.5 倍命中率、26 倍更低错误率。
- Krites：先描述生产两层结构（离线静态层 + 在线动态层），两层都用单一阈值 → 收紧漏掉安全复用、放松返回语义错误。卖点是**「不改变关键路径，只提升覆盖」**（静态来源服务比例 8.2%→19.4%）。
- MVR-cache：承认 vCache 解决阈值，但输入仍是整句向量；反例是同一部剧两条评论主题词同、情绪反，整句余弦相似但回答不同。改为学习式分段 + 多向量匹配。
- SISO：把现有问题归三条（单条查询为单位、LRU/LFU 淘汰、所有请求都走缓存）；用质心代表查询簇、语义局部性替换时间局部性、只在 SLO 受压时启用。**「什么时候不该用缓存」写进背景**。
- MeanCache：以「问题清单」开场（服务端语义缓存五个问题，隐私与网络成本最突出），把缓存搬到用户侧。

**（2）plan / tool / reasoning 层（D 卡片，9 篇）——最直接对应本题**
共同写法只有两步：**先证明最终答案不能缓存，再证明中间结果可以**。
三句话论证（可直接改写）：
> 背景：Agent 的成本与延迟集中在规划、检索、工具三个阶段，这些阶段的输出依赖外部状态，不能像聊天回答那样直接复用。
> 收益：省下的是单次任务里最贵的一段工作，而且中间结果结构稳定，命中率可以很高。
> 难点：有效性由状态、版本、参数决定；从模板适配到当前任务需要校验；写入本身有成本，错误会沿执行链传播。

| 中间结果 | 论文 | 省下的工作 | 收益证据 | 主要难点 |
|:--|:--|:--|:--|:--|
| 计划模板 | APC | 大规划模型的 token | 成本降 50.31%，性能保留 96.61% | 适配失败、无 TTL 与版本 |
| 工作流记忆 | AWM | 逐步探索与试错 | 成功率 35.5%，基线 23.5% | 只覆盖网页导航，无成本数据 |
| 生成程序 | GenCache | 重复的 LLM 调用 | token 省 35%–73% | 程序生成成功率仅 10.4% |
| in-context 示例 | IC-Cache | 大模型调用 | 吞吐 1.4–5.9 倍 | 示例质量与隐私 |
| 工具调用历史 | TVCACHE | 工具调用与状态重建 | 需核对正式版 | 外部状态一致性 |
| 计划转移 | AgenticCache | 逐步 LLM 规划 | 时延降 65%，token 降 50% | 元数据范围设计 |
| 中间表示 IR | SemanticALLI | 重复推理步骤 | 可视化阶段命中 83.1%，省 4023 次调用 | 分解质量、适用面窄 |
| DAG 中间结果 | Workload-Aware | 重复子代理执行 | 时延降 64.7% | 依赖计数维护 |
| 缓存键 | Why Agent Caching Fails | 无效缓存与误命中 | 键一致 91.1%，GPTCache 37.9% | 意图规范化成本 |

可借用的三个具体写法：
- APC 用两个反例证明「语义相似不等于计划可复用」（同一「总结数据集统计量」请求计划结构相似但步骤取决于数据；同一句「删除顶部评论」坐标与滚动量不同）。
- GenCache 用**一句定义**把缓存对象从答案换成参数化产物：「缓存的是生成程序，不是答案」。
- Workload-Aware 的三项打分信号（重算成本、DAG 依赖数、代理调用频率）与价值模型里的「节省成本、依赖数、需求频率」几乎同构。

**（3）ctx / KV 层（E 卡片，8 篇 + 8 篇速查）**
共同写法：**收益与代价同源**——缓存确实省了重复预填充，但立刻制造新的容量、带宽与失效问题。
- CachedAttention：73% 多轮、30% 超 4K token；命中率 71%–90%、首 token 延迟降 61%–87%；但 KV 每 token 4.5MB，上下文溢出截断会让已存 KV 全部失效 → 「收益—代价同源」的最标准范式。
- Continuum：**「现有策略的错误假设」这种写法，比「现有方法效果不好」有力得多**（end-of-turn 驱逐适合多轮聊天却不适合 Agent；SWE-Bench 平均 10.9 轮、工具时间均值 925 ms）。
- KVFlow：一个时刻级反例（13 时刻淘汰 Expresser，14 时刻立刻 cache miss）胜过十行平均数据。
- Marconi：把「两难」写成显式结构（块大小 32 时 25.0% 的 KV 块被复用，但只有 0.4% 的 SSM 状态被复用，相差 65.3 倍）。
- AdaptCache：用容量缺口数字开场（两个 H100 节点加 150GB 内存只存约 50 万 token，而 Agent 一次运行可产生数百万 token、KV 约 3TB）。
- 速查 8 条：SmartCache / KVCacheCostModel / MemoryOS / Pie / KVShare / SCBench / PromptPeek / VaSE，各自给出一句背景写法与可用位置。

**（4）rag 层（F 卡片，8 篇）**
共同写法最统一：**先给重复证据，再说顺序或版本让复用不成立**。
- Cortex：外部检索占端到端 40%–50%，但现有缓存只加速推理、不在知识边界做校验。
- Cache-Craft：「前缀缓存只覆盖 8% 的请求与 18% 的预填充 token」——**「现有优化只覆盖 X%」是最锋利的缺口写法**。
- ContextPilot：精确前缀命中率仅 4.6%–5.5%，因为文档顺序常变 → 用机制解释「命中率为什么低」。
- FreshCache：固定 TTL 两难（首都可复用数月、比分几分钟过期）→ 把复用改写成**风险约束的时间推断**，而非相似度阈值。
- FinCacheServe：「回答说到底是一个带依赖的服务对象」（请求签名 + 源文档版本 + 证据指纹 + 工具指纹 + 反向索引）→ 依赖传播小点最好的引子。

### 1.6 中文参考毕业论文的 3.1 节范式（分析稿 G 卡片）

两篇都比英文论文更适合当结构模板。

| 维度 | 李宇航（KV Cache 分层管理） | 刘非凡（范围过滤器） |
|:--|:--|:--|
| 开场 | 先讲长上下文预填充与 KV 写入开销 | 先讲范围查询的应用价值与研究对象的切换 |
| 收益 | 前缀共享确实省重复计算 | 过滤器确实降低查询开销 |
| 转折 | 共享缓存持续累积、挤占显存 | 倾斜负载让误判集中到高频查询 |
| 现有做法 | LRU/LFU 不理解前缀树；全量卸载带来传输瓶颈 | 分类梳理代表方法，并指出各自负载短板 |
| 关键证据 | Llama-2 13B 上全量卸载总时延 2138 秒，卸载占 56.1% | 倾斜分布下误判数高一个数量级；误判率 50% 对 99% 的小例子 |
| 难点 | 节点价值受活跃度、频次、树深与重算量共同影响 | 现成数据结构没有留下自适应更新所需的信息或空间 |
| 收束 | 价值评估、显存驱逐、主存准入三个子问题 | 结构与轻量更新、构建访存优化两个子问题 |

**两条可迁移的论证手法：**
1. **先呈现收益，再揭示收益带来的管理负担。** 研究问题来自优化机制自身的资源后果，而不是孤立的容量不足。
2. **用「直觉方案的代价」把问题从扩容收束到选择机制。** 数字承担论证职责，而不是装饰。

**两篇的完整论证环节（可直接照抄结构）：**
- 李宇航七环节：发现问题 → 定义问题 → 分析现有做法 → 建立重要性 → 找出难点 → 拆分子问题 → 引出方案。一句话理解：从「前缀共享能否节省重复计算」推进到「共享产生的前缀 KV Cache 如何在有限显存、主存容量和传输带宽之间分层管理」。
- 刘非凡八步：任务价值与研究对象 → 现有方案建立地图（字典树/位图/哈希/混合，逐一点短板）→ 图 3-1 把负载假设失配变成可见现象 → 小例子解释因果机制 → 指出已有自适应工作的适用边界 → 难点落实到数据结构 → 收束成两个子问题 → 章节路线图逐项回答（3.2 Hourglass / 3.3 滑动窗口更新 / 3.4 构建访存优化 / 3.5 实验），对抗负载下误判率降低 9.8–35.4 倍。

**英文顶会与中文硕士论文 3.1 节的差别：**

| 维度 | 英文顶会论文 | 中文硕士论文 3.1 节 |
|:--|:--|:--|
| 长度 | 一到两页，压缩在引言 | 五到八页，独立成节 |
| 证据 | 一两个 headline 数字 | 多层证据：统计、图、小例子、量级测算 |
| 结构 | 矛盾式推进，快速收束 | 发现、定义、分析、难点、子问题、方案，逐段推进 |
| 相关工作 | 放在引言后段或独立节 | 融进背景，按方案分类建立比较对象 |
| 收尾 | 贡献列表 | 子问题与章节路线图对应 |

### 1.7 被明确列为「常见写法错误」的四条（分析稿 warn 卡 + warn 卡 + callout）

1. 只写「缓存能降本增效」，没有先证明重复发生在哪、省下的是哪一段工作、为什么会复用错。读者会追问：命中率从哪来，错误由谁承担。
2. 把数据集与环境类文献（AgentBench、WebArena、StreamRAG、RAGTruth、Apache Flink 等）当动机引用，审稿人会问它们与缓存决策有什么关系。
3. 把某篇论文的 headline 数字当成自己的前提，忽略它的负载与边界条件。
4. 只讲收益不讲验证成本，价值模型会被质疑为单一指标。

**非缓存类文献的正确摆放**（分析稿 §H 末表）：

| 文献 | 在第一章的角色 | 写法提醒 |
|:--|:--|:--|
| AgentBench、WebArena、WebShop | 任务与环境来源 | 只说明能采集哪些事件，不要写成「证明缓存有收益」 |
| ToolBench、StableToolBench | 工具 API 与可复现响应 | 模拟响应不等于真实在线工具成本 |
| StreamRAG | 流式场景背景 | 说明知识随流更新，它不研究缓存修复 |
| HoH | 过时信息评测 | 支撑「旧证据会过时」，使用前核验字段 |
| RARR | 事后修订方法 | 支撑「局部修复」，它不处理失效传播 |
| RAGTruth | 幻觉标注 | 支撑「逐主张核验」，它不提供缓存标签 |
| Apache Flink | 流式原型工具 | 只写在实现段，框架本身不是贡献 |

**边界与评测类文献的用法**：SCBench、PromptPeek、Pie、KVShare 适合放在「难点」段，而不是「动机」段——它们证明的是「这件事为什么难」，不是「这件事为什么值得做」。

### 2.1 改进/否决清单

### 2.2 例子降到什么位置（逻辑草稿 C/D 卡片）

例子从「开篇叙事」降级为**「业务现象 → 系统本质 → 缓存对象」的映射表**：

| 业务现象 | 系统中的本质 | 缓存对象 |
|:--|:--|:--|
| 履约政策变更 | RAG 材料或索引版本更新 | `rag` 证据 |
| 订单状态推进 | ACT 结果依赖的数据快照变化 | `act` 结果 |
| 事件重复或流程重试 | 同一任务上下文再次执行 | `plan`、`resp` |

并明确规定：**「例子只在需要解释机制时出现。正文可以直接谈 RAG 材料、数据快照、权限范围和依赖版本。」**

### 2.3 研究价值的新口径（逻辑草稿 A 卡片）

Agent 让业务处理变成一条持续运行的执行链：一次事件会触发检索、读状态、规划和生成；不同任务反复使用相同材料与步骤，缓存因此产生价值；版本、状态、权限与依赖变化也由此成为系统问题。

| 研究价值 | 具体表现 |
|:--|:--|
| 降低处理时延 | 减少重复检索、模型调用和只读接口访问，缓解事件积压 |
| 降低运行成本 | 减少重复推理、知识加工与后端查询 |
| 提高状态一致性 | 在版本变化后识别仍可复用的对象，避免旧结果进入后续计划与操作 |

### 2.4 「沿用参考论文第三章的组织方式」（逻辑草稿 ok 卡）

> 先说明优化收益，再指出它引出的资源与一致性问题。随后检查直觉方案，最后拆成可研究的决策问题。

对应到本课题：收益（复用省下生成/检索/工具/规划）→ 收益引出的问题（有效性、验证成本、依赖传播、容量）→ 检查直觉方案（TTL、LRU/LFU、语义相似、全量清理）→ 拆成可研究决策（准入、保留、刷新/局部修复、淘汰）。

## 3 结论性判断（观点先行）

> 每条标注来源：〔分析·X〕= 写法分析稿卡片；〔逻辑·X〕= 逻辑草稿卡片。

**关于参考论文的写法**

- **C1** 这批论文几乎不用「缓存很重要」开篇；它们先给重复证据，再把「朴素复用为什么会错」写成矛盾，最后收束到某个中间结果层。〔分析·开篇〕
- **C2** 问题背景有稳定七步骨架（场景定位→重复证据→成本测量→朴素复用失效→局部性来源→收益口径→难点收束），各篇差别只在「把哪一步当主要矛盾」。〔分析·A〕
- **C3** 「为什么缓存中间结果」由三条合一立住：最贵的阶段在中间、中间结果自带结构、中间结果可绑定依赖/版本/权限。〔分析·A〕
- **C4** 论证「缓存 Agent 中间结果」最稳的开场组合是「地图开场 + 局部性观察」：前者排除已有方案，后者给出自己的复用机会。〔分析·B〕
- **C5** 中间结果层只需两步论证：先证明最终答案不能缓存，再证明中间结果可以。〔分析·D〕
- **C6** KV/上下文层的通用范式是「收益与代价同源」：省下重复预填充，立刻制造容量、带宽、失效问题。〔分析·E〕
- **C7** RAG 层的通用范式是「先给重复证据，再说明顺序/版本/新鲜度让复用不成立」。〔分析·F〕
- **C8** 「现有优化只覆盖 X%」（Cache-Craft：8% 请求、18% 预填充 token）是最锋利的缺口写法。〔分析·F〕
- **C9** 主动把代价写出来会增强可信度（TurboRAG 承认 1M 个 512-token 块约需 28TB）。〔分析·F〕
- **C10** 「现有策略的错误假设」比「现有方法效果不好」有力得多（Continuum 的 end-of-turn 驱逐）。〔分析·E〕
- **C11** 把「什么时候不该用缓存」写进背景会显著提高论证可信度（SISO）。〔分析·C〕
- **C12** 数字承担论证职责而非装饰：李宇航的 2138 秒 / 56.1%、刘非凡的 50% 对 99%。〔分析·G〕
- **C13** 中文硕士 3.1 节与英文引言是两种文体：5–8 页独立成节、多层证据（统计+图+小例子+量级测算）、相关工作融进背景、收尾对应子问题与章节路线图。〔分析·G〕
- **C14** 边界与评测类文献（SCBench、PromptPeek、Pie、KVShare）属于「难点」段，不属于「动机」段。〔分析·E〕
- **C15** 非缓存类文献（benchmark、数据集、Flink）不能当动机引用；框架本身不是贡献，只写在实现段。〔分析·H〕

**关于 1.1 该怎么写**

- **C16** 业务例子退到后面；1.1 主线落在处理方式的演进与缓存决策。〔逻辑·副标题〕
- **C17** 背景按四阶段展开：传统处理 → Agent 处理 → 复用机会 → 系统问题。〔逻辑·B〕
- **C18** 缓存难点来自三组张力（稳定/变化、收益/验证成本、跨对象依赖/局部更新），不是能力清单。〔逻辑·E〕
- **C19** 现有做法不足要落成「做法 + 机制缺口」五行清单，每行可被反驳、可被实验检验。〔逻辑·F〕
- **C20** 研究问题用 `V_eff = 安全复用机会 × 单次净节省 − 验证与维护成本` 收束，再分到准入/保留/刷新/淘汰四条决策路径。〔逻辑·G〕
- **C21** 正文论证顺序固定六步：系统演进 → 执行链拆解 → 复用机会 → 失效边界 → 现有策略缺口 → 研究问题与挑战。〔逻辑·H〕
- **C22** 组织节奏沿用参考论文第三章：先收益，再收益引出的资源与一致性问题，再检查直觉方案，最后拆成决策问题。〔逻辑·ok 卡〕
- **C23** 订单履约场景不作为全文唯一场景；正文初稿在本次讨论时尚未修改，本页只定论证逻辑。〔逻辑·warn 卡〕

### 4.3 每类对象的难点句骨架（分析稿 H）

- **resp**：复用省下生成，但语义相近的回答可能不等价。质量控制要落到条目级，而不是全局阈值。
- **rag**：复用省下检索与回源，但证据有版本与新鲜度。复用前必须核对来源状态。
- **act**：复用省下工具调用，但结果依赖外部状态。工具历史或参数不一致时不能复用。
- **plan**：复用省下规划，但计划要与当前参数绑定。适配失败需要回退。

### 4.4 研究问题收束图（逻辑草稿 G）

```
请求流 & 更新事件 & 执行反馈 → 有效复用价值
有效复用价值 → 准入
有效复用价值 → 保留
有效复用价值 → 刷新 / 局部修复
有效复用价值 → 淘汰
依赖版本与状态检查 --> 有效复用价值
```

`V_eff = 安全复用机会 × 单次净节省 − 验证与维护成本`

### 4.5 可观测的落地结果（对照件）

`第一章_改后初稿.md` 的 1.1 已按此结构成文，可视为这套判断的验证样本：五段推进 + 四类对象表 + 两个核心问题，**开篇为运行形态而非业务例子**，且明确写出「以命中率、相似度、访问频率为主的传统策略，衡量不了复用相对重新执行的真实净收益，也处理不了对象间的依赖一致性」。其 1.2 进一步把 V_eff 落成可计算形式：

`V_base(i,H) = N̂_i(H)·Δ̄t_i − F̂_i(H)`（预计有效复用次数 × 单次复用净节省 − 失败尝试的额外开销），再对四类对象分别加类型专属修正项。

| H | 给第一章的落地写法（七段 + 引用摆放 + 难点句骨架） | 建议的正文论证顺序（六步 flow） |

**核心术语**

- 四类缓存对象：`resp`（回答）、`rag`（检索证据）、`act`（只读工具结果）、`plan`（计划模板/片段）；`ctx`（会话上下文）作为依赖与失效信息来源，不是被缓存对象。
- 四类复用动作：`reuse` / `verify then reuse` / `recompute`（初稿另列 `reuse`、`verify_then_reuse`、`recompute` 三动作表）。
- 四条决策路径：准入、保留、刷新/局部修复、淘汰。
- 四阶段叙事：传统处理 → Agent 处理 → 复用机会 → 系统问题。
- 三组张力：稳定与变化共存、收益与验证成本共存、跨对象依赖与局部更新共存。
- 收益口径：`V_eff = 安全复用机会 × 单次净节省 − 验证与维护成本`。
- 关键范式名：「收益与代价同源」「地图开场 + 局部性观察」「先证明最终答案不能缓存，再证明中间结果可以」「现有策略的错误假设」。

**引用纪律**

- 「通过有效性检查的复用」才计入收益。
- headline 数字不能直接当自己论文的前提；引用须带负载与边界条件。
- 预印本只支撑「问题存在」，不支撑「方法已成立」。
- 框架（Apache Flink）只出现在实现段，不作为贡献。
