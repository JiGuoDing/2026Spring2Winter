## 一、11-18「研究背景与问题重构」

### 1.1 主线

**建议把第一部分的主线定为：复用机会随请求出现，也随状态变化而失效。** 三句话展开：

- 当前请求来了，要判断哪些旧结果还能用（**选**）；
- 空间有限时，要决定哪些值得留（**留**）；
- 状态变化后，要决定哪些值得修（**修**）。

四类缓存是这两个问题的具体载体。这条主线把「缓存」重新定义为一个**决策问题**，而不是一种加速手段。

### 1.2 问题背景的层次（六节结构）

| 节 | 标题 | 承担的功能 |
| --- | --- | --- |
| 1 | 研究背景：重复的是需求，变化的是答案的依据 | 交代运行形态与现象 |
| 2 | 问题定义：现在复用什么，未来保存什么？ | 输入 / 决策与约束 / 目标 |
| 3 | 现有做法的缺口：把「哪一步答不上」说具体 | 规则层 + 代表工作层双重定位 |
| 4 | 研究价值：用三笔账说明值得做什么 | 微观经济性论证 |
| 5 | 技术挑战：判断正确、资源分配、更新一致性 | 三个研究点的难点分解 |
| 6 | §1.1 建议怎么落笔 | 写作执行方案 |

层次逻辑是：**现象 → 形式化 → 缺口 → 价值 → 难点 → 写法**，是一条完整的论证链，而非并列的背景介绍。

### 1.3 核心论点与支撑证据

**（1）「流式」的界定。** 把「请求持续到达、所依赖的状态按事件生效」的运行形态称为「流式」。这是自下而上的运行定义，不是引用某个框架的术语。

**（2）场景与时间线证据。** 以电商大促客服咨询为例（耳机能否满减、有没有货、能否退），用 19:50–20:05 六个时刻做时间线：

- 19:50 一次咨询产生四类可保存结果；
- 19:52 同一条规则服务不同问题（复用机会出现）；
- 19:54 库存先变、政策未变（同一答复内部分失效、部分仍可用）；
- 20:00 满减门槛 300→399（可只改门槛、保留有独立依据的退货期限）；
- 20:01 修复期间收到第二次更新（门槛再调 499，按 399 修出的答复不能写回）；
- 20:05 新增规则改变相关证据（白色预售版不参加满减，通用规则没变也要查例外）。

结论句：**同一份结果能用多久，取决于它依赖什么；复用范围与更新影响范围各自变化。**

**（3）四类缓存对象（按产物形态划分）。**

| 对象 | 例子 | 复用前要回答的问题 |
| --- | --- | --- |
| 完整回答 `resp` | 同一活动下「满多少减 30」与「减 30 的门槛是多少」 | 旧答复能否直接满足新请求？事实依据是否仍有效？通过则跳过整条后续路径 |
| 检索证据 `rag` | 「没拆封能退吗」与「退货期限从哪天算」沿用同一售后条款 | 证据是否可访问、仍有效且覆盖当前问题？缺哪块补哪块，覆盖不明则重检 |
| 只读工具结果 `act` | 同权限下再查 A 款黑色耳机同地区库存 | 工具、参数与相关状态是否相容？同规格同地区库存也会变 |
| 计划模板 `plan` | 「识别规格→查适用规则→查地区库存→汇总」 | 能否绑定新商品与收货地区？接口与前置条件是否齐备？ |

配套判断：完整回答失效时可回退正常执行，并在合适步骤复用仍有效的证据、工具结果或计划。

**（4）缺口证据——两层写法。**

- 规则层：精确键/固定相似度（黑白色不同规格、19:54 前后库存不同）、TTL（30 分钟 TTL 挡不住 19:54 过时，统一缩短 TTL 又会提前丢掉整天未变的售后证据）、LRU/LFU/成本感知淘汰（更新缩短收益窗口、完整回答覆盖时其内部工具结果当次不被访问）、更新后整答重生成（门槛变了退货期限可留，「459 元耳机能否减 30」还要重判门槛、价格与适用范围）。
- 代表工作层：vCache（在线学习逐条目阈值控制语义复用风险）；Cortex（远程知识访问的语义验证 + 成本感知淘汰）、SSC（生产 RAG 中证据权限与新鲜度验证 + 按效用选证据）；TVCACHE（按工具调用历史匹配环境状态）、Agentic Plan Caching（检索并适配结构化计划模板）；FinCacheServe（预印本，答案绑定意图/证据/工具输出/版本 + 反向依赖管理失效）。另用 HoH 说明陈旧证据影响动态 RAG 正确性。

**本章切入点：四类结果在同一服务中的相互影响**——同一请求有多条复用路径，状态更新会改变其中哪些路径可走；要回答如何据此算净收益、分配容量、更新后恢复可用结果。

**（5）研究价值的三笔账（均为演算示例）。**

- 第一笔（单次命中）：查地区库存 200 ms vs 读缓存并核验 30 ms，命中省 170 ms；发现过期再调工具共 230 ms，反而多等 30 ms；若与被加速的慢步骤并行，省下的工具时间未必改变用户等待。要求**同时记录端到端等待和实际省去的调用/计算**。
- 第二笔（容量只够留一个）：售后条款 50 次 × 8 ms = 400 ms；库存结果 5 次 × 170 ms = 850 ms，扣 3 次核验失败（3 × 30 ms）后净省 760 ms；若只剩 2 次有效复用则降为 250 ms。结论：**价值排序随复用窗口变化，最热条目和曾经最贵的条目都可能让位。**
- 第三笔（局部修复）：只改门槛 vs 重判「459 元耳机能否减 30」，门槛涨到 499 后原结论失效；要合计重检、生成、核验、回退的工作量，另测更新期请求 P95 与恢复复用时间；两组都做同样完整重检时检索单独计账，局部修复省的是重写成本，扣掉额外核验与回退才是净收益。

**（6）技术挑战三层。**

- 挑战一·判定：「相似、适用、值得用」是三次不同判断——语义与任务约束、状态与结构（工具依赖参数与所读状态，计划依赖可绑定参数/工具能力/前置条件，单一语义相似分无法表达）、验证成本（太重吞掉节省，太轻放过错用；查新版与再调一次工具一样贵时，工具缓存就缺时延收益）。
- 挑战二·估值：反馈稀疏且有选择性（被挡下的候选少有核验标签，版本刚更新时旧反馈参考价值变弱）；同一请求的收益不能加两遍（完整回答返回后当次检索/调用已被跳过，保留它们的收益来自其他请求或替代路径）；容量与时间尺度（逻辑单位计容量要与内存字节指标分开）。
- 挑战三·维护：影响发现三种形式（修改改变主张、删除使主张失去支撑、新增使旧答案遗漏条件；反向依赖能找到引用者，新证据却尚未被任何旧答案引用）；能否局部修复取决于推理结构；并发更新时提交比对绑定版本，过时任务不写回。
- 实验共同口径：同一时间点用已生效状态标注正确答案/证据/结果，避免用最新状态回评旧请求；回放隔离重复率、热点、更新强度，端到端测实际等待与后台开销；**§1.4.2 的提升幅度保留为待验假设。**

### 1.4 当时遗留的问题

1. **全部时延与收益数字是演算示例**，无实测；§1.4.2 提升幅度仍是待验假设——价值论证悬空。
2. **只有电商客服一个场景，「流式」为何成立未论证**：什么样的业务值得做成流式智能体、值得配缓存，缺适用边界与判据。
3. **价值论证停留在微观毫秒账**：缺业务量级（日请求/日案件、账单、QPS）来说明「不做会怎样」。
4. **分类维度是工程产物（resp/rag/act/plan），未回答「缓存的到底是什么性质的东西」**，也未给出价值上限这类可判断的命题。
5. **失效仍依赖「来源有可观测更新或可查询版本」的口径**，对不可观测、不可复现的外部系统没有交代。
6. **缺外部术语锚点**：「流式」是自定义，未挂到既有流处理/框架语境上。

## 二、11-20「流式 Agent 的缓存：场景、价值与本质」

### 2.1 讨论定位：是纠正，也是深化

主题句即为全文纲领：**「缓存不是提速开关。它是 Agent 与时间签的一份契约：记什么、记多久、何时忘。」**

它没有推翻 11-18，而是把讨论从「怎么算收益、怎么判定」拉到上一层：「**这件事在什么业务里才成立、价值上限在哪、本质是什么**」。副标题三问写得很直白——Flink Agents 适合什么、缓存值多少、问题真正难在哪。重点确实是**场景价值从哪来**与**缓存的本质是什么**。

### 2.2 适用边界：四条同时成立才值得用

把 Agent 看成流里的一个**有状态算子**，「不是给 Flink 加一个函数调用」。

| 要素 | 含义 | 不满足时 |
| --- | --- | --- |
| 事件驱动 | 没有人在提问，事件在推系统 | 退回单次问答 |
| 长时程 | 判断跨分钟到天 | 一次请求内出结果 |
| 有状态 | 按实体累积上下文 | 无状态工具 |
| 高并发 | 要背压、扩缩容、自愈 | 内部低 QPS 工具 |

**只中一两条时，普通服务更省事。**

### 2.3 场景匹配：对 11-18 场景选择的校准

| 形态 | 匹配度 | 原因 |
| --- | --- | --- |
| 人工审批回流 | 高 | 人也是事件源 |
| 系统主动对话 | 高 | 交互由事件触发 |
| 慢通道客服 | 中 | 秒到小时可接受 |
| 同步多轮聊天 | 低 | 缺 token 流与请求亲和 |

这条表实际上**把 11-18 的电商客服主场景降级为「中」**，并把「同步多轮聊天」判低，收窄了「流式智能体」的口径。

深例换成风控案件侦查的两层架构，关键判断是 **Agent 不进支付主链路**（授权有 100 ms 预算）：第一层毫秒级、确定性可回滚；第二层秒到小时级，负责侦查与跟踪。Agent 不阻塞等人——案件留在 keyed state，人批完，结论作为事件回流。

### 2.4 缓存分四层：风险完全不同

| 层 | 缓存什么 | 落在哪 | 风险 |
| --- | --- | --- | --- |
| 参考数据 | 名单、商户档案 | 广播状态 | 低 |
| 实体画像 | 设备与账户特征 | Flink State + TTL | 中 |
| 证据 | 图扩线结果 | 带版本的状态 | 中高 |
| 推理 | 前缀与分类结果 | 模型侧与应用侧 | 高 |

框架自带两层：短期记忆由 Flink State 支撑、可过期；Action State Store 只在恢复时复用。

**铁律：缓存事实，不缓存判断。** 落地为逐动作判断——名单筛查每案必查、改广播状态；商户档案重复度极高，长 TTL + CDC 失效；实体画像优先放 Flink State；图扩线键带版本号；相似案件属于长期记忆；处置动作绝不缓存。风险偏好也定了调：**漏放比误杀贵，「放行」类结论只能用短 TTL。**

### 2.5 价值分三层（对 11-18 三笔账的升维）

| 层 | 价值 | 度量 | 不做会怎样 |
| --- | --- | --- | --- |
| 省资源 | token、下游 QPS | 账单对比 | 贵，但能跑 |
| 撑形态 | 长时程与突发 | 峰值下的 P99 | 形态不成立 |
| 定语义 | 新鲜度与回放 | 回放一致性 | 不敢上线 |

即：第一层省钱，**第二层决定能不能做，第三层决定敢不敢上线**。案件跨 72 小时就要反复取证，事件越多成本越涨，缓存把它压成常数。

量级估计（明确标注「仅用于说明量级」）：日 3 万案件，中档模型 120→60 万元、高档 750→375 万元；ROI 中档约 2.4 倍「可做但要控人力」，高档约 15 倍「属于一期需求」。

### 2.6 本质三层与收尾

- **经济层**：缓存的本质是把成本单位从「事件」换成「变化」——同一商户被 2000 个案件查询，只算一次变化。
- **认识层**：**失效策略就是你对世界如何变化的建模**；TTL 假设世界按时钟均匀变化，这是最粗的假设。
- **系统层**：判断要可复现，但模型和外部系统都不可复现，**唯一出路是把观察记下来**。
- 一个反转：缓存与审计不是对立面——缓存是短命的记录，审计日志是长命的记录，真正对立的是「记录」与「不记录」。
- 一句话：**缓存的价值上限，等于业务里慢变量的占比。** 设计缓存只回答三个问题：记什么、记多久、何时忘；技术选型只是这三个答案的写法。
- 收尾判断：**真正的难点不是怎么缓存，是你敢在多长时间里相信一个旧事实；这个答案不在框架文档里，在业务对错误的容忍度里。**

### 2.7 它自身未解决的问题

- 量级与 ROI 同样是估算（日 3 万案件、2.4×/15×），性质与 11-18 的毫秒演算相同，仍是「说明量级」而非实测。
- 11-18 提出的判定、估值（反馈稀疏、收益重复计）、并发写回三大技术挑战在 11-20 未被处理——这是有意留到技术章节，不是已解决。
- 「慢变量占比」是个好命题，但没有给出可操作的度量方法；「业务容错度」如何映射为 TTL/版本判据也未展开。

**明确被否决或收窄的：**

- 「同步多轮聊天」作为流式缓存目标形态——判低（缺 token 流与请求亲和）。
- 电商客服作为唯一主场景——不再是主例，只在匹配表中占「中」。

**未被解决、跨两次遗留的：** 所有数字仍为估算；判定/估值/维护的算法问题仍开放；「慢变量占比」「业务容错度」尚无度量口径。

## 四、对 1.1 的贡献与落笔建议

### 4.1 各自贡献

- **11-18 给骨架**：1.1 的四步写法（先交代服务如何运行 → 给一次机会和一次冲突 → 用代表方法定位缺口 → 提出两问并落到指标），以及贯穿全章的两问分工（研究点一 §1.2 价值估计；研究点二 §1.3 容量分配与更新维护）。可直接沿用。
- **11-20 给地基**：补上 11-18 最虚的两块——① 适用边界（四要素 + 场景匹配表，回答「为什么必须是流式、什么业务才值得」）；② 价值上限（价值上限 = 慢变量占比；三层价值给出「不做会怎样」）；③ 本质表述（对时间的契约、失效即世界变化建模、记录 vs 不记录）。

### 4.2 建议的 1.1 合并结构

1. **形态成立条件**：事件驱动、长时程、有状态、高并发四条同时成立；Agent 是有状态算子，不是给流框架加函数调用。
2. **场景价值从哪来**：价值上限等于业务里慢变量的占比；三层价值——省资源（账单）、撑形态（峰值 P99）、定语义（回放一致性）；量级说明必要性（标注为估算）。
3. **缓存的本质**：与时间的契约，三参数「记什么、记多久、何时忘」；缓存事实不缓存判断；失效判据来自对状态变化方式的建模（TTL 是最粗假设，版本/CDC/事件驱动更细）。
4. **由此引出两问与指标**：当前怎么选、未来怎么留和修；质量约束下的累计净收益、用户等待、更新恢复代价、回放一致性。
5. **代表工作与缺口**：保留 11-18 的规则层 + 代表工作层双层写法（vCache、Cortex、SSC、TVCACHE、Agentic Plan Caching、FinCacheServe、HoH），缺口落在「四类结果在同一执行路径上相互影响」。

### 4.3 两处口径冲突需在成稿前统一

1. **场景口径**：11-18 以电商客服为主例，11-20 判其为「中」匹配。建议 1.1 用「四要素 + 匹配表」定边界，主例二选一（若保留客服，须说明它是「慢通道客服」而非同步聊天；若换风控，则 11-18 的满减/库存案例降为辅助例）。
2. **分类口径**：11-18 四类产物 vs 11-20 四层数据。建议 1.1 用四层数据作背景层分类（性质与风险），四类产物作为「复用粒度/执行路径」在 1.2–1.3 展开，避免两套分类并列造成读者负担。
