## A 核心结论 {span=3}
:::callout info Agent 让业务处理变成一条持续运行的执行链
一次事件会触发检索、读状态、规划和生成。不同任务反复使用相同材料与步骤，缓存因此产生价值。版本、状态、权限与依赖变化，也由此成为系统问题。
:::

| 研究价值 | 具体表现 |
|---|---|
| 降低处理时延 | 减少重复检索、模型调用和只读接口访问，缓解事件积压 |
| 降低运行成本 | 减少重复推理、知识加工与后端查询 |
| 提高状态一致性 | 在版本变化后识别仍可复用的对象，避免旧结果进入后续计划与操作 |

## B 背景按四个阶段展开 {span=3}
```timeline
1 | 传统处理 | 规则、状态机和工作流执行固定步骤，复杂例外交给人工核对
2 | Agent 处理 | 事件进入上下文，Agent 检索材料、读取状态、组织计划并生成结论
3 | 复用机会 | 相同材料、相同参数、重复事件与流程重试产生可复用中间结果
4 | 系统问题 | 文档、状态、权限和工具版本变化，使复用必须附带有效性与依赖判断
```

## C 例子的作用：把业务现象映射到系统机制 {span=2}
| 业务现象 | 系统中的本质 | 缓存对象 |
|---|---|---|
| 履约政策变更 | RAG 材料或索引版本更新 | `rag` 证据 |
| 订单状态推进 | ACT 结果依赖的数据快照变化 | `act` 结果 |
| 事件重复或流程重试 | 同一任务上下文再次执行 | `plan`、`resp` |

## D Agent 执行链中的缓存位置 {span=2}
```flow LR
事件到达 -> 上下文组装
上下文组装 -> RAG证据
上下文组装 -> ACT结果
RAG证据 -> PLAN计划
ACT结果 -> PLAN计划
PLAN计划 -> RESP结论
版本更新 -.-> RAG证据
状态更新 -.-> ACT结果
版本更新 -.-> PLAN计划
状态更新 -.-> RESP结论
```

例子只在需要解释机制时出现。正文可以直接谈 RAG 材料、数据快照、权限范围和依赖版本。

## E 缓存难点来自三组张力 {span=3}
| 张力 | 缓存要回答的问题 | 不能只看什么 |
|---|---|---|
| 稳定部分与变化部分共存 | 哪些中间结果仍然有效 | 创建时间、固定 TTL |
| 复用收益与验证成本共存 | 命中后是否真的更划算 | 命中率、语义相似度 |
| 跨对象依赖与局部更新共存 | 一个变化应影响哪些对象 | 全部清除或全部保留 |

## F 现有做法为何不足 {span=2}
| 做法 | 机制缺口 |
|---|---|
| 每次重新执行 | 稳定材料、规则解析和只读查询被反复计算 |
| 统一 TTL | 政策、配置、订单状态与权限的更新节奏不同 |
| LRU / LFU | 访问频率不能表示当前有效性和重算代价 |
| 语义相似命中 | 相似任务可能依赖不同版本、状态或权限 |
| 任意更新全量清理 | 有效对象被连带淘汰，刷新成本被放大 |

## G 研究问题如何收束 {span=2}
```flow
请求流 & 更新事件 & 执行反馈 -> 有效复用价值
有效复用价值 -> 准入
有效复用价值 -> 保留
有效复用价值 -> 刷新 / 局部修复
有效复用价值 -> 淘汰
依赖版本与状态检查 --> 有效复用价值
```

$$V_{\mathrm{eff}} = \text{安全复用机会} \times \text{单次净节省} - \text{验证与维护成本}$$

## H 建议的正文论证顺序 {span=3}
```flow LR
系统演进 -> 执行链拆解 -> 复用机会 -> 失效边界 -> 现有策略缺口 -> 研究问题与挑战
```
