1.1 研究背景与总体思路

1.1.1 研究场景与目标

流式 Agent 持续接收任务，并在处理任务时规划、检索知识、调用工具、生成回答。任务间可能出现相似的信息需求、相同的只读工具调用和可迁移的计划片段；与此同时，请求热点、知识来源和工具状态持续变化。系统因此需要边处理事件，边判断哪些历史结果适用于当前任务，以及哪些缓存值得继续保存或维护。

本章将 resp（回答）、rag（检索证据）、act（只读工具结果）和 plan（计划模板或片段）作为四类缓存对象。会话上下文、用户权限、外部数据与工具版本作为适用性和依赖状态的来源。系统接收请求与 Agent 执行事件、来源或工具状态更新事件、后台任务完成事件，在线更新缓存状态和统计信息。

研究目标： 在持续变化的请求与来源状态下，衡量四类对象的有效复用价值，选择当前请求的服务路径，并在有限缓存空间与后台预算下管理条目。评价同时报告任务质量、用户时延与资源开销。

1.1.2 两大研究点与四个问题

研究点 小点 关键问题 输出
一、价值建模与检索复用 ① 异质缓存对象的价值建模 缓存未来保留能带来多少收益？ 长期管理价值和有效性依据
一、价值建模与检索复用 ② 候选检索与有效性检查 怎样找到候选并判断是否可以复用？ 本次请求的服务路径及执行反馈
二、缓存生命周期管理 ③ 价值驱动的准入、淘汰与异步验证提升 有限空间和后台资源下，保存什么、如何改进回答缓存？ 新的缓存集合及回答提升任务
二、缓存生命周期管理 ④ 面向流式证据更新的依赖传播与自适应修复 证据更新后，哪些回答受影响，适合局部修复还是完整重生成？ 经过核验并绑定最新证据版本的缓存回答

四点依次形成“估值 → 在线复用 → 准入与提升 → 依赖传播与回答修复 → 反馈估值”的闭环。候选检索与有效性检查支持当前请求复用，未来管理价值支持跨请求的保留与维护决策；更新后的回答作为新版本重新进入价值评估。

1.1.3 流式处理边界与系统流程

以处理时间为本章原型的统计口径：同一测试序列中的请求、依赖更新及任务完成按控制器接收顺序处理；需求统计使用固定长度的滑动时间窗口。历史回放以实验调度的逻辑时间作为处理时间，真实系统记录实际处理时间。涉及乱序和事件时间的研究留作后续扩展。

读取路径使用当前已知的依赖版本和权限判定有效性；后台任务携带版本快照，提交前再次检查。外部状态更新被系统接收之前的可见性取决于数据源更新通知及其延迟，实验分别记录通知延迟和系统接收后的处理延迟；一致性保证以系统已接收的最新版本为边界。

1.2 面向异质缓存对象的价值建模与检索复用

1.2.1 异质缓存对象的未来管理价值建模

设计目标。 基于在线观测和成本统计估计条目未来管理价值，支持准入、保留和维护。

对象及其有效性条件。 四类对象纳入同一个条目接口，各自保留专属语义条件：

对象 缓存粒度 请求时的主要适用性检查 直接节省的工作
resp 完整回答或可参数化回答模板 权限、问题语义、模型/内容版本、时效、答案可接受性 回答生成与推理
rag 证据集合及集合内来源可追溯的证据块 权限、来源版本、新鲜度、当前问题证据覆盖 检索、回源和证据加工
act 一次只读工具调用结果 工具/算法版本、规范化参数、权限、依赖数据或环境状态 工具调用与远程交互
plan 参数化计划模板或计划片段 任务阶段、前置条件、工具/权限、参数绑定和可执行性 规划搜索与重规划

写入或重用时保存对象标识、内容引用、大小、来源和版本、创建/确认时间、访问时间、权限域、对象专属特征及依赖边。act 普通结果缓存限于只读操作；副作用工具调用不以缓存命中跳过一次新的业务动作。ctx 等会话信息作为依赖和失效来源记录，不额外扩展为本章核心实验对象。

成本记录。 分别记录用户端耗时、模型 token、远程调用次数或费用及后台工作时间。有效性检查与适配的时间计入其实际所在的前台或后台，实验主指标采用用户端耗时；token、调用次数与后台计算分项报告。

近期统计统一使用处理时间上的固定长度滑动窗口 T，到达事件更新窗口内计数与成本样本。窗口不混用“最近 N 次请求”口径；请求事件的到达时间、来源更新和任务完成时间由回放器明确排序。成本预测仅使用当前事件之前的历史观测。

条目未来管理价值。 在未来窗口 H 内，以近期窗口估计兼容请求的到达率、条目的可用机会以及每次实际可节省的用户端时间。单条目的近似价值可以写为：

V_hold(i, H) = 预计有效复用次数 × 每次预期用户端时间节省 − 持有开销

有效复用次数综合近期需求、权限、对象适用性、剩余有效期及依赖版本状态；每次节省按复用相对于正常执行的净成本估计。resp 进一步考虑当前缓存中已有的安全覆盖；rag 按实际使用的来源记录需求，来源更新时只折减受影响证据的机会；act 依据参数匹配和可观察的数据版本估算；plan 将计划适配、执行回退和重新规划成本纳入收益，任务完成率独立报告。重复候选的边际价值以缓存集合比较，避免重复计数。

在时间口径下，rag 可按来源分别估计：最近 T 内来源 s 对集合 i 分得的使用次数为 n(i,s)，未来时间 u 内来源当前版本仍有效的估计比例为 P(s,u)，h(i,s) 为未来窗口 H 与集合、来源剩余有效期的较小值，则 O(i,H) = Σ_s [n(i,s)/T × ∫₀ʰ⁽ⁱ,ˢ⁾ P(s,u) du]。一次请求使用多个来源时将一次机会分摊给相关来源；机会估计仍须通过在线证据充分性和实际选用情况校准。可用近期更新率构造 P(s,u) = exp(−λ(s) × u) 作为待验证的泊松假设，样本不足时使用同类来源的统计；版本刷新后重新估计。 对任一估计，保存样本量与置信区间；样本少时采用保守先验。预计收益用于决策，实验同时报告估值与实测收益的偏差和风险结果，不能仅凭公式声称预测有效。

1.2.2 候选检索与有效性检查

检索职责。 检索负责在对象专属索引中提出少量候选，不负责证明可复用。比较不同缓存策略时固定请求规范化方法、索引、候选数和相似度排序，避免将检索质量变化误认为价值模型收益。四类对象共享“检索—有效性检查—复用或执行—反馈”接口，采用各自匹配特征：

  • resp：按请求意图、实体、时间范围及权限/版本等字段检索完整答案；语义向量用于候选召回，权限与时间条件用于过滤或检查。
  • rag：按当前问题或子需求检索证据块，回溯其证据集合与来源版本；检查证据覆盖，对有效部分复用，对缺失部分补检，无法确认时完整检索。
  • act：以工具标识、版本和规范化参数作精确或结构匹配；动态结果还需比较当前依赖状态，状态检查开销纳入复用成本。
  • plan：按任务目标、阶段和工具需求找参数化模板；检查前置条件，记录参数绑定、局部修复及失败回退成本，不能仅凭文本相似直接执行。

当前请求的复用流程。 检索候选后，检查权限、版本、时效及对象适用性；通过检查的候选可供复用。rag 证据部分覆盖时，复用有效证据并对缺失部分补检。没有可用候选时，正常执行相应的检索、工具调用、规划或回答生成。执行结果及实际使用的证据、计划、工具结果和回答写入反馈日志。

对同一请求中多个缓存阶段的收益，记录各阶段实际避免的工作，并避免把下游生成已包含的上游成本再次计入。plan、act、rag 与 resp 的组合收益在端到端实验中衡量，单对象实验用于区分各机制贡献。

1.3 价值驱动与依赖感知的缓存生命周期管理

1.3.1 价值驱动的准入、保留、淘汰与回答异步验证提升

管理目标。 生命周期控制使用第一小点的未来管理价值，并以第二小点的安全门和执行反馈为输入。在固定缓存容量和后台预算下，决定候选是否准入、已有条目是否保留，以及有限后台验证资源优先用于何处。

准入、保留与淘汰。 新结果经过对象专属有效性检查后成为候选。若有空间且预期未来价值为正，则准入；容量不足时，评估候选加入并移除条目集合后的整体价值变化：

ΔV(M → M′) = V(M′, H) − V(M, H)

其中 M′ 满足容量约束；V(M,H) 是未来窗口内缓存集合相对于相同请求全部重算的预计用户端累计时间节省，计入候选之间的覆盖重叠和回退开销。集合差值体现被替换条目的空间机会成本，准入和保留时的未来维护开销纳入比较；质量约束与后台资源分别记录。只有预计价值增量为正且硬约束满足时才执行替换。先移除已确认失效且无刷新计划的条目；其余淘汰选择依据“移除造成的未来服务损失/占用空间”比较。定期重估使用当前窗口统计，记录反复准入淘汰作为抖动成本。候选冷启动只使用有限探索预算，且所有方法使用相同的探索机会。

resp 静态层后台验证与提升。 该机制参考 Krites 的双层回答缓存和异步验证思路，扩展为按预计增量价值选择提升任务。静态层存放经过离线精选的回答条目，动态层存放在线生成回答及已验证的静态回答映射。请求先检查静态层：候选满足较高适用性阈值与所有硬条件时可直接返回；处于预设灰区且权限、版本和时效可预先检查时，当前请求沿动态层或后端完成服务，再提交独立后台验证任务。后台任务验证静态答案对原请求的适用性，并在有可靠基线时比较回答质量；通过后按 ΔT_post + λ_Q × ΔQ_post 重新计算提升后的增量价值，并扣除尚未发生的维护开销；只有预计增量价值为正且容量约束满足，才写入动态层映射。已发生的验证成本用于任务选择和实验记账，准入比较不再重复扣除。验证结论绑定请求条件、权限、静态内容和依赖版本，后续请求仍须经过在线有效性检查。提升不重置源内容年龄，存储指针和元数据计入动态层容量。

后台任务优先级按单位后台时间的预期收益排序：

P_verify(j) = [p_pass(j) × (ΔT_post(j) + λ_Q × ΔQ_post(j)) − λ_B × C_verify(j)] / max(T_verify(j), ε)

其中 ΔT_post 是提升成功后相对未提升的预计未来用户端累计时间节省，单位为秒；ΔQ_post 是相同未来请求上预计累计回答质量分之差，λ_Q 的单位为秒／质量分。两者采用相同未来窗口、相同请求样本估计，质量评分及 λ_Q 在验证集确定并做敏感性分析；缺少可比评分时质量增益按零处理。因而即使已有安全动态命中、时间节省接近零，只要通过概率加权后的预计质量收益足以覆盖后台成本和其他增量开销，仍可安排验证并在通过后决定提升。C_verify 是该次验证消耗的后台计算工作量（以单工作槽秒计，含并行工作槽之和），T_verify 是任务对调度槽的预计占用时长；当每次任务固定占用一个槽时二者数值相同，分子反映成本、分母反映有限时间内的任务排序。λ_B 将后台工作秒折算为用户端时间收益，采用验证集选定的无量纲权重并做敏感性分析；队列等待另行记录。通过概率和成本使用此前同类观测。排队任务去重、限长、限并发；执行前重新检查需求、依赖版本和剩余有效期。任务过期或候选状态改变时取消/合并或丢弃结果，避免无用工作；失败、超时后有限重试，随后交由在线请求按需验证或重算。后台验证时间、判官 token、队列等待和实际后续命中均进入评估。

rag、act、plan 不使用回答静态层提升机制，但都按同一管理价值口径做在线准入/替换；其验证工作针对证据支持和来源状态、工具结果状态、计划前置条件与执行反馈分别设计。

1.3.2 面向流式证据更新的缓存依赖传播与自适应修复

细粒度依赖记录。 首版聚焦单轮 rag → resp，记录“来源版本 → 检索证据块 → 回答事实表述”的依赖关系。生成回答时拆分可核验的事实表述，保存每条表述对应的证据 ID、内容版本或摘要；无法清晰对应的跨句推理或无引用表述标记为不可局部修复。反向索引支持从来源更新快速定位受影响证据与回答表述。

更新事件与影响定位。 生成回答时同时保存原查询、检索器配置、索引版本和旧 Top-k 证据。来源新增、修改或删除都可能使旧 Top-k 外的新证据进入结果，因此首版在每次更新后对全部缓存查询使用固定确定性检索器重检，并与记录的旧 Top-k 比较证据 ID、内容版本或哈希及排序；同一证据 ID 的内容变化也触发处理。完成影响判断前，相关回答保持待确认且不可服务。删除后无替代证据的事实表述不再作为事实服务。只有检索结果变化会改变回答依据或覆盖时才触发修复；重检成本计入实验。

修复或重生成决策。 将原问题、旧回答、变更前后的相关证据和更新后的完整相关证据上下文交给轻量 LLM，要求返回受影响表述、修复候选和结构化依据。影响局部、替代证据充分且未修改部分仍有有效支撑时，只修复相关表述；溯源不足、更新改变多条主张之间的推理、影响范围不清或证据不足时完整重生成。重生成仍缺少证据时，明确表达不确定性或证据不足，不补造事实。

核验与版本条件写回。 逐条检查修改及保留的事实表述是否得到当前证据支持，并检查其证据版本。通过后写入新 resp 版本及依赖映射；失败则完整重生成。任务携带检索索引与来源版本快照，提交前再次检查；若处理中又到达更新，丢弃旧候选并基于最新版本重新定位和处理。正确性评估使用人工、程序化真值或独立标注，不以修复模型自身判断作为真值。

流式执行与研究边界。 请求、证据更新和修复完成按控制器接收顺序处理；版本条件提交保证结果对应系统当前已知版本，更新事件被系统接收前的可见性受通知延迟影响。首版将实现和实验限定为单轮 rag → resp、短回答、可追溯证据和固定确定性检索器；act 与 plan 保留各自的状态检查与按需重算流程。

与流处理实现的关系。 事件回放验证依赖传播、修复决策和版本一致性；后续 Flink 原型维护来源版本、证据—主张反向索引、缓存状态和修复任务。checkpoint 与恢复用于检查状态和任务结果一致性。研究重点是更新后回答质量、过期结果控制和修复总成本；吞吐与恢复性能只在原型实际测量后报告。

四点之间的接口与因果关系

  1. 第一小点定义条目管理价值的估计量，并使用按时间更新的请求、成本及依赖状态。
  2. 第二小点执行候选检索与有效性检查，复用有效缓存或正常执行，并输出真实结果及成本反馈。
  3. 第三小点消费条目管理价值和反馈，控制准入、保留、淘汰；resp 灰区验证通过后再评估动态层提升。
  4. 第四小点消费证据更新事件，定位受影响的 rag 和 resp，选择局部修复或完整重生成；核验、版本冲突与修复成本反馈再进入第一小点估值。

请求路径通过有效性检查确定是否复用；生命周期路径决定缓存条目是否保留，以及证据更新后如何恢复回答有效性。两者共享观测和对象状态，收益与修复成本在对应路径记账一次。

1.4 实验设计与评估

本节按“先确认缓存机会，再验证价值模型与生命周期策略，最后验证流式原型”的顺序开展。实验目标是检验：在相同请求轨迹、缓存容量、有效性规则与后台预算下，所提出的在线价值估计与生命周期决策能否提高安全复用所带来的累计收益，并在请求需求或依赖状态变化时保持服务质量。

1.4.1 研究问题与实验边界

实验围绕四个问题组织：

  1. RQ1：四类 Agent 对象分别有多少可利用的复用机会？ 测量 resp、rag、act、plan 的精确重复与语义近邻分布、结果可验证比例、复用所需成本，以及缓存查找和有效性检查的管理开销。先确认每类对象的净收益空间，再进入策略比较。
  2. RQ2：候选检索与有效性检查能否支持可靠复用？ 测量四类对象的候选检索效果、检查开销和错误复用情况，评价复用路径的成本与质量。
  3. RQ3：价值驱动的生命周期策略能否更有效地使用有限缓存与后台资源？ 比较准入、保留、淘汰和回答异步提升，检验单位缓存空间和后台工作量带来的服务收益。
  4. RQ4：证据更新与 Agent 请求、回答修复交错时，依赖传播和自适应修复能否保持回答有效？ 比较受影响回答定位、局部修复或完整重生成、版本条件写回的质量、陈旧结果暴露和总成本；随后用 Flink 原型验证事件处理与恢复行为。

四类对象均进入实验范围，但采用共同的实验协议和对象专属的真值定义：resp 评价答案适用性与回答质量；rag 评价证据支持、来源权限和版本；act 评价工具、参数、权限及外部状态；plan 评价前置条件、适配成本、执行完成情况和回退。四者不共用一个未经校准的质量分数；时间、费用、质量、错误复用分别报告。静态层异步验证与提升仅针对 resp，其他对象的后台工作以可定义的状态检查或依赖刷新为主。

1.4.2 数据集、运行环境与事件构造

任务来源

采用“公开基准任务／环境 + 自建运行日志 + 可控流事件”的组合。候选来源为：

  • AgentBench ：覆盖多种交互环境，可用于采集请求、计划、工具调用、工具结果和最终回答。官方仓库说明与运行入口见 THUDM/AgentBench。选择具体子环境后再锁定依赖与许可；仓库许可不能替代对环境镜像、底层数据或外部服务条款的核验。
  • WebArena ：自托管网页任务与可程序化评估，适合采集浏览器工具动作、页面状态、计划和执行结果，也可构造页面内容版本变化。官方实现见 web-arena-x/webarena。它提供的是任务与环境，不应描述为天然具有长期请求到达流或真实更新日志。
  • ToolBench / StableToolBench ：可作为工具 API 与可复现响应模拟的补充来源，重点用于 act 的输入、输出和状态变化实验。官方项目见 OpenBMB/ToolBench。模拟响应和静态轨迹不能直接当作真实在线工具调用成本或生产到达流。
  • HoH ：动态知识更新与过时回答的候选任务／数据来源。使用前核验当前发布版本、许可、字段及其与证据版本和回答主张映射的适配性；若字段不足，则借鉴其更新事件设计，以自建可控文档版本构造主实验数据。论文见 ACL 2025。

具体起步顺序采用 AgentBench 的 DBBench 与 WebShop 子环境：前者优先用于可重置的只读数据操作与计划执行，后者用于购物交互、回答和多步计划；为两者增加带来源 ID 和版本的可检索文档、证据引用记录及更新事件，以形成 rag 样本。四类对象均使用同一个仪表化 Agent 记录，必要时用 WebArena 作为独立环境复核。执行前核对各环境硬件要求，固定仓库提交及各环境版本。

上述基准均需在开工时确认当前版本、可下载性、执行依赖和许可证；只将核验过的任务子集纳入正式实验。可用 API 模型或本地模型驱动 Agent，记录模型版本、提示词、参数、调用价格口径和硬件环境。对需要判定答案或计划质量的场景，优先使用环境自带程序化评估；LLM 判官用于辅助标注时，固定模型和评分规程，并抽样人工复核，判官调用成本计入资源账本。

运行日志与事件流

每次运行按统一日志记录任务 ID、事件序号、到达时间、会话／租户、请求、对象类型和 ID、候选检索结果、依赖版本、所选动作、实际路径、工具参数与结果、回答／任务评分、延迟、token 或外部费用、缓存大小、后台任务及完成状态。不可观测字段保留缺失标记，不从测试集反推。

公开任务通常不提供流式服务所需的真实到达时间、热点漂移、连续来源版本和缓存决策反事实。对这些变量，先从任务内容和环境状态生成带固定种子的事件序列，并在结果中标为 实验构造 ：

  • 请求到达时间及并发负载；
  • 热点阶段及迁移时刻；
  • 知识文档、网页、工具数据的更新事件和版本号；
  • 处理、验证、刷新和重算的成本参数（若无直接观测，则通过实际运行测量或明确的负载模型取得）；
  • 后台服务速率及预算。

事件回放按序推进；任一决策只能使用此前已经处理的请求、更新和任务完成反馈。先按原始任务族或会话划分历史构建、验证和测试数据，再在各自内部构造重复或相近请求流；静态库使用历史部分，但不得引入测试请求的答案或测试期间后续版本。参数只在验证集确定，测试轨迹用于最终报告。至少保存原始数据版本、环境配置、模型设置、事件生成代码版本和随机种子。

每类缓存的实验样本构造

  • resp： 用问题及上下文检索历史回答候选；通过基准标签、环境状态或人工复核建立“适用于当前请求”的标注。测语义近邻误复用风险、完整回答质量、动态层命中和静态层灰区候选。静态回答库从训练部分构建，测试请求不参与构建。
  • rag： 对可访问文档或页面切分证据块，保留文档 ID、版本、权限和生成回答时实际采用的证据引用。构造可控文档修订，检查旧证据及其下游回答的失效传播；采用答案支持标注或环境真值判断证据覆盖与补检效果。
  • act： 记录工具名、规范化参数、权限、工具版本、输入状态版本和输出。先覆盖确定性计算及可重放只读工具，再加入外部状态发生变化的情形。新业务操作不作为缓存命中；副作用工具不允许通过普通结果复用跳过执行。
  • plan： 从可重复执行的任务轨迹提取计划模板和参数槽位，记录工具依赖、前置条件、适配／验证／修复步骤、执行结果、回退和重规划。通过环境重复运行同一任务族来比较复用计划与直接重规划；只基于任务文本相似度不能标为可安全复用。

1.4.3 对照策略与公平性控制

所有策略共享同一事件序列、候选检索器、候选生成规则、权限与版本安全底线、离线独立质量评估规程和执行环境；各策略自行决定缓存内容。实验 D 中双层回答缓存对照与本文方法使用相同在线验证器；实验 E 的在线核验属于本文修复方案的一部分，三组均以统一离线独立评估比较正确性。改变候选检索算法时另设检索实验，不与价值和生命周期策略同时变动。对比方法包括：

  1. 无缓存： 每次完整检索、调用工具、重新规划或生成回答，建立成本和质量基线。
  2. 精确匹配缓存： 只在键和依赖条件完全匹配时复用，用于测量仅使用精确匹配时的收益。
  3. LRU/TTL： 固定容量下的通用近期使用和年龄管理基线。
  4. LFU／近期频率策略： 使用同一窗口统计频率决定准入或淘汰，用于比较动态价值估计的作用。
  5. 成本感知策略： 按单次重算成本及大小排序；维护相同硬有效性门，不加入质量收益或依赖机会估计。
  6. 依赖失效 + 按需重生成： 更新时传播失效，后续请求到达后按最新证据完整生成回答，作为维护基线。
  7. 直接轻量 LLM 修复： 将证据变更和旧回答直接交给轻量模型修订，不提供主张级影响定位，检验依赖信息的作用。
  8. 依赖定位的自适应修复： 本文方案；按主张—证据依赖定位、局部修复或完整重生成，再进行证据核验和版本条件写回。
  9. 双层 resp 基线： 相同静态回答库、灰区阈值、验证器及后台预算下，按到达顺序处理验证任务，成功后使用 LRU/TTL 管理动态提升项。
  10. 本文策略及消融： 长期管理价值、依赖状态、质量收益和后台任务优先级按设计逐项启用或移除。

若按论文描述自行实现对照方法，记录实现假设和与原论文的差异，不标注为官方复现。所有方法使用相同的缓存容量（按对象字节数计）、模型调用预算、请求与更新轨迹、验证器和后台工作预算。权重或阈值用验证集确定；报告敏感性曲线，避免只选择有利工作点。质量约束通过独立质量指标和约束线报告，除非单位和转换依据明确，不把质量分与毫秒直接相加。

1.4.4 分层实验步骤

实验 A：缓存机会与管理税预实验

对四类对象分别统计精确重复率、候选近邻率、通过硬有效性检查的比例，以及“潜在节省 − 检索／验证／适配开销”的净收益分布。随机抽取分层样本，人工或程序化检查真值。对复用路径和正常执行路径重复执行并测量成本，固定 API 模型或本地环境及缓存热身条件。

产出： 每类对象的可复用样本规模、风险标签覆盖率、平均及分位成本、缓存空间分布和管理税。若某类样本或真值不足，在章节中报告限制，并扩大可控环境样本；不据候选清单推定该类已经有足够复用机会。

实验 B：候选检索与有效性检查

固定候选检索方法和排序，对四类对象分别检查候选的权限、版本、时效与适用性，并测量查找、检查和复用开销；没有可用候选时正常执行。以标注或环境真值评估候选检索及有效性判断。

报告候选召回、有效性判别 precision/recall、错误复用率及其质量损失，以及检索和检查耗时。对 plan，另报任务成功率、额外重规划次数及完成耗时；对 rag，另报证据覆盖率和支持正确率。

实验 C：长期价值与准入／保留／淘汰

在固定容量下按时间回放请求，比较 LRU、LFU、成本感知和本文长期价值策略。使用相同的候选生成规则、初始状态及估值预算，允许各策略产生不同缓存集合，测量不同对象的累计安全服务收益、被淘汰后重建成本、命中质量、缓存空间和条目 churn。对 act 与 plan，分别在环境执行或重规划成本可重复测量的任务族中运行；用价值因素消融区分需求估计、内容年龄、依赖稳定性、对象大小及质量反馈。

容量建议先按统一对象字节数设定多个归一化档位（如工作集大小的 25%、50%、75%），并在预实验后锁定范围；此为实验设计默认扫描档，不是既有实测参数。每个条件使用相同测试序列和多组事件随机种子，报告均值及置信区间。

实验 D：resp 静态回答后台验证与提升

用训练轨迹构造静态答案库，验证集确定候选相似度灰区和质量比较规则，测试流中遇到灰区候选后先完成当前请求服务路径，再创建后台验证任务。任务确认静态回答适用性和与当前回答的质量差；通过后才计算提升的增量价值并写入动态层。比较双层到达顺序任务处理与价值排序／执行前重估策略，并设置“不提升”对照。

改变请求热点迁移、灰区到达率、验证成本及后台服务预算，统计后续新增安全覆盖、用户端累计时延变化、回答质量变化、验证调用/token、任务等待时间、队列积压和提升后未使用比例。增设动态回答已安全命中、提升前后时间差接近零而质量提高的样本，检验质量收益驱动的验证与提升；单独报告这些样本的质量变化，避免重复计作新增命中。后台任务若因来源版本变化或需求消退而作废，计入后台开销。

实验 E：流式证据更新与缓存回答自适应修复

首版使用单轮 rag → resp 问答、固定确定性检索器和同一索引版本，保存查询、检索器配置、索引版本、旧 Top-k 证据和回答主张—证据版本映射。构造证据新增、修改、删除和连续更新事件；每次更新后对全部缓存查询重检，与旧 Top-k 比较证据 ID、内容版本或哈希及排序，同一 ID 内容更正也触发处理，定位潜在影响，重检成本计入评估。比较三组：①依赖失效后完整重生成；②直接轻量 LLM 修复，输入原问题、旧回答、证据变更和更新后的完整相关证据；③本文依赖定位方案，根据影响范围局部修复或完整重生成。三组统一在更新事件到达时触发维护，共享权限、版本等安全基线；回答正确性使用统一的离线独立标注或程序化真值评估，不假设三组共用在线核验器。

测量主张定位 precision/recall、陈旧回答暴露次数与时长、修复后事实正确率和证据支持率、局部修复比例、失败后完整重生成比例、端到端时延和总成本。所有策略均计入查询重检、影响判定、修复及失败回退的模型调用、token、费用和时间。设置无关更新、证据替换、删除无替代、新证据改变 Top-k、证据不足及修复期间连续更新；检查版本冲突时过期候选是否被丢弃。

实验 F：组合策略与流式原型

将 A–E 中通过验证的动作组合，运行稳定到达、突发到达、热点迁移、来源更新与混合事件工作负载。扫描缓存容量、来源更新率和后台服务预算，比较同等资源限制下的累计收益、质量、前台 P95/P99 时延、请求吞吐、队列长度和过期复用。以时间曲线展示变化发生前后策略响应，而不是只报告全程平均值。

事件回放完成后，再把请求、来源更新和后台任务完成事件接入 Flink 状态处理原型。验证状态更新、反向依赖查询、任务幂等和 checkpoint 恢复；报告吞吐、处理延迟、队列积压及恢复前后重复／遗漏任务数。若只完成离线回放，则不报告 Flink 系统性能结论。

1.4.5 指标与统计报告

维度 指标 解释
复用与收益 有效复用率、安全覆盖率、累计节省时间／费用、管理税后净收益 将命中收益与检索、验证、补检、回退开销合并核算
质量与风险 任务成功率、回答质量、证据支持率、错误复用率、陈旧复用率 按对象报告，不以命中率代替正确性
价值估计 管理价值估计误差、准入后收益 衡量预计价值与后续实际收益的差异
缓存控制 占用字节、有效条目数、淘汰 churn、重建开销 解释固定空间下的收益来源
后台管理 验证／刷新任务数与成功率、后台 CPU／时间、API/token、积压及未使用率 核算为未来请求准备缓存的真实代价
流式响应 热点迁移适应时间、更新标记延迟、前台 P95/P99、吞吐 直接检验动态流负载下的响应能力

成本优先分别报告毫秒、token、API 费用与 CPU 时间；如需合并为净收益，明确单价与转换来源，并提供分项结果。质量优先报告原始任务指标；若设置质量门槛，门槛由验证集和研究目标预先确定，测试集不调参。随机种子、任务拆分和缓存初始状态保持配对；对配对测试轨迹报告置信区间，统计检验结合效应量，不只报告显著性。

1.4.6 实施顺序与阶段交付

  1. 数据适配盘点： 下载并核验具体基准子集、许可证、运行条件和对象覆盖；完成日志 schema 与原始／构造字段清单。
  2. 单对象端到端打通： 先选择环境支持最完整的一类对象，跑通候选检索、硬有效性检查、复用与正常执行路径测量和回放；随后将相同协议扩展到另外三类。
  3. 价值与生命周期策略： 完成固定检索器条件下的有效性检查、准入淘汰、resp 提升，以及单轮 rag → resp 证据更新修复实验。
  4. 动态流和预算扫描： 固定验证集选出的参数，运行测试事件流，完成热点变化、来源更新、缓存容量和后台预算实验。
  5. Flink 原型验证： 将已通过回放验证的状态转移接入 Flink；只评估实现过的吞吐、延迟和恢复能力。

每阶段先检查样本量、可重复运行性和对应真值是否可得，再扩大实验规模。数据集实际字段、估值参数、事件生成规则和系统结果均在实施后填入；本设计不预设数据集提供了真实流时间戳、更新事件或缓存反事实，也不预设任一策略已取得优势。

1.4.7 分支重放与成本测量约定

日志中的历史时延不能直接当作缓存策略的端到端收益：缓存会改变后续 Agent 轨迹、工具调用数量和回答内容。可重放性按对象区分：

  • 对确定性只读工具和自托管环境，保存环境快照或可恢复状态，在同一初始状态分别运行候选缓存动作与完整执行分支；以实际观测到的两分支差值估计节省。
  • 对外部 API 工具，只有在响应可回放且状态条件一致时才可做分支配对；否则使用受控模拟响应评价策略，并把模拟环境结果与真实 API 的单次成本测量分开报告。
  • 对回答生成、证据检索及计划执行，缓存命中与重算分支应使用相同模型／提示词／检索版本和任务初始状态；质量由基准评分、环境成功条件或经复核的标注测量。缓存导致的后续调用变化也计入整条任务的端到端成本。
  • 对具有副作用的工具，不通过重放已执行动作来推断收益；在隔离环境中重置状态后重跑，或仅报告安全只读动作的结果。

若无法重跑反事实分支，该样本只用于估值输入或描述性统计，不用于宣称实际节省。离线策略回放报告“由模型／代价表推算的估计值”；真实环境重跑报告“实测端到端差值”，两者分开列出。API 费用按调用账单或明确的公开单价记录，本地模型同时记录墙钟时延、设备和 token 数；相同硬件、并发度与模型配置下做配对运行，并在报告中说明缓存热身和计时边界。

定义每条测试任务轨迹的实测净时间收益为：

G_time = T_base − T_cache

其中 T_base 与 T_cache 分别是同一初始任务状态下无缓存基线和缓存策略完整执行至任务结束的墙钟时间。费用收益同理为 G_cost = C_base − C_cache。回答质量、任务完成率和错误复用独立报告；不将它们与时间合成单一分数，除非预先给出可解释的折算单位和验证集确定过程。

1.5 本章小结与实施顺序

本章以四类 Agent 缓存对象为研究对象，先建立未来管理价值，并通过候选检索与有效性检查支持复用，再将价值估计用于准入、保留与淘汰。面对流式证据更新，系统沿证据—回答主张依赖定位影响，选择局部修复或完整重生成，经证据核验和版本检查后更新缓存；请求、更新与修复事件的交错由版本条件提交保持一致。

建议先确定可运行任务和事件字段，再建立四类对象的复用机会与开销基线；随后实现价值决策、生命周期控制、resp 异步提升，以及固定检索器下的证据更新修复；最后组合动态事件流与 Flink 原型开展评估。
