## 3. 计时口径

- 计时器一律 `time.perf_counter()`，只包住被测操作，不含线程池排队等待。
- 每个 (路径, 并发) 单元开测前先**预热 5 次**，冷启动不计入。
- 每道题重复 **30 次**；200 道题 = 6000 个样本，1360 个更新事件 × 30 = 40800 个样本。
- 每个单元报 4 个量，`n` 列是样本数：
  - `p50` / `p95` / `mean`：**请求视角**，在 worker 内计时，并发下含等待 GIL 的时间；
  - `wall_ms_per_item`：**系统视角**，单元墙钟 ÷ 执行次数（= 吞吐的倒数）。
- 分位数：线性插值（type-7）；`mean`：算术平均。
- 并发 1 / 8 / 32 用 `ThreadPoolExecutor` 模拟，工作项集合与串行完全一致。

**边界（必须写进论文的说明）**

1. 不含冷启动：预热 5 次之后才开始计时；索引构建与快照首读都在计时之外。
2. 不含评测器成本：本表不调用 `compare.py`，因此不含判分、结果比对与正确性校验的时间。
3. 不含模型推理：`local-small-7b` 与 `api-large-placeholder` 是**占位标识**，不是真实模型。
4. 不含网络与排队：`act` 只计时本地 SQLite 只读查询；没有远端服务、没有队列等待。
5. 单机单次运行：数值依赖本机 CPU、页缓存与 Python 版本，换机器需重跑，不能跨机比较。

**并发怎么读**：本机是单进程 CPython，线程池里跑的都是本地计算与 SQLite 只读。

- 线程池每项派发本身有约 7 µs 的固定开销（可由 `locate` 档反推：c=1 约 1.2 µs、
  c=32 约 8.2 µs，差值即派发与调度）。
- 这个开销对毫秒级路径可忽略：`semantic_hit` / `full_regen` 三档摊薄墙钟基本持平，
  CSV 的 `note` 记为「无显著差异（无吞吐收益）」；`act` 8 并发还略快（SQLite 执行期释放 GIL），
  32 并发明显变慢（线程数远超有效并行度）。
- 对微秒级路径（`validity_check` / `exact_hit` / `partial_repair/*`），派发开销与操作本身同量级甚至更大，
  并发档的绝对值失真。**这几条路径的结论只看 c=1**，并发档保留只为说明派发开销的量级。

请求视角的 `p50` / `p95` 在并发档上升，因为排队等 GIL 的时间算进了单次操作；
`p95` 出现几十到几百毫秒的尾部也来自线程切换与争用，不是检索或 SQL 本身变慢。
两种视角不矛盾：吞吐没变，排队变长。该结论只适用于单进程线程池。

## 4. 实测与待回填怎么区分

CSV 用两列做互斥标记，**同一行只允许一列有值**：

| 列 | 取值 | 含义 |
|---|---|---|
| `measured` | `1` | 本次运行真实计时得到的值 |
| `measured` | `backfill` | 作者用自己的模型实测后回填的值（见第 5 节） |
| `mock` | `pending` | `value_ms` 留空，等作者实测；当前仓库状态 |
| 两列 | 空 | 不允许；`check_separation()` 会直接报错 |

`runner.py` 在写盘前逐行断言：`measured` 与 `mock` 不同时有值、标 `measured` 必须有数值、
标 `mock` 必须没有数值。验收器 `verify.py` 另有一次裸切检查，两者互为兜底。

当前待回填的只有 4 个单元格：`partial_repair/rewrite` 与 `full_regen/generate` × 2 个模型占位。

## 5. 回填步骤（作者自己做）

1. 打开 `path_costs.backfill.template.csv`（runner 每次生成，只含 `mock=pending` 的行）。
2. 用你自己的模型跑对应阶段，测**端到端墙钟时间**：从收到请求到拿到最终文本，
   含 tokenize、prefill、decode，不含网络重试与排队。每道题 30 次，取 p50 / p95 / mean。
3. 把数值填进模板的 `value_ms`；两行别互相顶替。
4. 合并：`python dataset/costs/runner.py --backfill dataset/costs/path_costs.backfill.template.csv`
   - 只覆盖 `mock=pending` 的单元格，本地已实测的行拒绝外部数值（写错位置会直接报错）；
   - 合并后该行变成 `measured=backfill`、`mock` 清空，`note` 记录来源文件名。
5. 重跑会重新测本地路径并覆盖 `path_costs.csv`，所以回填值只存在模板/合并这一步；
   想保留本地旧测量请加 `--out` 另存。
6. 重跑后 `MANIFEST.json` 自动重算哈希；`measured=backfill` 的行数与来源写进 `stats`。

## 6. 测量效度自检（口径）

这一节回答一个会被答辩追问的问题：**微秒级的数字，计时窗口里到底有没有真活？**

**6.1 判定标准。** 一条「非空」的测量必须同时满足三条，缺一条就不采信：

1. **有遍历**：每个样本实际访问的对象数可数、且与实现一致（第 7 节的效度表）；
2. **有判别力**：同一函数在输入变化时必须给不同结论，不能是常量（6.3）；
3. **尺度可解释**：成本能对上「访问了多少对象 × 每对象的工作量」，不是凭空一个数（6.4）。

**6.2 遍历计数怎么得到的。** 不是估算：`validity_check` 与 `locate` 系列函数带一个可选
`trace` 参数，runner 在诊断阶段打开计数、用同一批输入再跑一遍，把累计计数除以样本数。
计时阶段传 `None`，只多一次 `is not None` 判断。

**6.3 判别力检验。** 200 条请求在 `as_of=v0` 下全部通过（v1 文档就是这个时刻的现行版本）；
把同一条检查的 `as_of` 换成 `v2`（12:00Z）后 200 条全部判为失效，因为引用的 v1 块已被
v2 改过、TTL 也已过期。同一段代码两种结论，说明它在读版本序列和块哈希，而不是返回常量。

**6.4 为什么本地检查是十微秒而不是毫秒。** 有效性检查访问的是内存里的版本索引：
每条请求 4.2 篇文档、8.4 条版本记录、6.7 个证据块、6.7 次 sha256 重算，
按每次字典查找 + 短字符串 sha256 约 1 µs 计，落在 9 µs 是合理的。
把同样的判定放到持久层（每次请求读一次 SQLite）就会跳到毫秒：同机一次 SQLite 只读查询
实测 1.4 ms（见 `act` 行）。所以 µs 与 ms 的差别来自**存储选择**，不是测量缺陷。
若把审计深度加大（`check_full`：全版本全部块复核）成本升到几十微秒，
不用索引做全库扫描（`locate_full_scan`）升到约 58 µs——三个数一起看，成本随对象数单调变化，
符合第 6.1 条第 3 款。

因此论文里写 `partial_repair` 的本地成本时，用 `locate_hit` 那一档（真正发生修复的事件），
并注明：本地定位相对模型改写可忽略，修复的收益来自**模型调用变短**，不是来自定位免费。

**6.5 本次修订记录（P5a 复测）。** 首版把两个阶段测成了近乎空转的循环：
`validity_check` 只做一次布尔缓存判断（p50≈0.4 µs）、`partial_repair/locate` 只做一次索引键查找
（p50≈0.2 µs）。两者都低于一次完整函数调用的合理量级，属于测量错误。
现改为：检查逐文档逐块走完整判定并重算哈希；定位从变更块反查 claim 并逐条物化。
复测后 p50 从 0.4 µs 升到约 8 µs（约 18 倍）、定位从 0.2 µs 升到约 1 µs（命中事件约 2 µs），
并保留 `locate`（全部事件）/`locate_hit`（命中事件）/`locate_full_scan`（无索引基线）三档口径。
具体数字以第 7 节为准。

## 10. 工具成本构成模型（`tool_cost_model.json`，v0.3.0 新增）

`path_costs.csv` 记的是「每请求 1 次成功调用」的单次成本。真实智能体一次查询会调用多次工具：
数据集里 plan 平均 4.42 步、act 下游工具均值 2.42 个；工具调用还会失败并重试。
`tool_cost_model.json` 把这层结构显式化，**用于敏感性分析，不是测量结果**。

字段分两类，引用时不得混淆：

| 类别 | 内容 |
|---|---|
| `measured` | 单次延迟（v0.3.0 标定：rag 6.2 ms / act 1.1 ms）、act 下游均值 2.42、plan 步数 4.42 |
| `assumed` | 远程单次延迟、失败率 `p_fail`、最大重试 2 次 |

| 画像 | 模型段 | 工具段 | 工具占比 |
|---|---|---|---|
| P1 当前部署（实测） | 198.87 s | 0.010 s | 0.005% |
| P2 慢模型 + 远程工具（假设） | 198.87 s | 2.115 s | 1.05% |
| P3 快模型 + 远程工具（假设） | 4.00 s | 2.115 s | 34.6% |
| P4 快模型 + 数仓（假设） | 4.00 s | 8.036 s | 66.8% |

若按「各 1 次、无重试」的旧口径计，P4 的工具段只有 2.4 s，**低估 3.35 倍**。
产生脚本：`exp_motivation/scripts/tool_cost_sensitivity.py`；结果：
`exp_motivation/results/m3_tool_cost_sensitivity.csv`。

**可靠性边界**：数据集目前没有工具失败与重试事件（`events/` 下无 `tool_failures.jsonl`），
所以重试相关的成本只能按 `assumed` 参数估算。要支撑「失败结果不应缓存」这类论点，
需新增构造的失败事件与每请求 `attempts` 字段（计划为 v0.4.0）。
