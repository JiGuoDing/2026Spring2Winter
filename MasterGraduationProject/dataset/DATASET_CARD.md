# 数据集卡片：流式智能体缓存实验数据系统 v0.6.0

> 完整说明（数据模型、构造方法、已完成实验与结果、未完成实验清单）见 **`REPORT.md`**。
> 本卡片只给摘要与边界。`v0.6.0` 延续冻结 `v0.3.0` 主干数据，完成现代六阶段重排 RAG 与生产级百万行 HTTP 工具网关 `act` 双真机标定。

## 一、这是什么

一个面向"缓存价值建模与生命周期控制"的可复现实验数据系统，覆盖智能取数场景下的四类缓存对象
（`resp` / `rag` / `act` / `plan`）、三类证据（文本知识、语义层口径、血缘边）、五类失效事件，
以及"同题不同问法"的语义簇结构。

**这不是**真实企业数据平台的镜像，也**不包含**真实用户请求或真实业务文档。除明确标注为
`measured` 的项之外，所有内容由本仓库脚本按固定种子确定性构造。v0.2.0 的构造改动依据是
`dataset/audit_v010_report.json`（体检报告），不是主观判断。

## 三、双时间戳与版本语义

v0.2.0 起，文档版本有两个时刻，**不能混用**：

| 字段 | 含义 | 用途 |
|---|---|---|
| `docs_versioned.updated_at` / `update_events.effective_at` | 新版本在底层**生效**的时刻 | 判定"真值上是否已过期" |
| `update_events.timestamp` | 系统**收到通知**的时刻 | 判定"系统当时知道什么" |
| `update_events.notification_delay_s` | 两者之差，实测 0.03–3.0 小时（中位 1.6） | 通知延迟统计 |

由此产生两个标签视角：

- `safe`（真值视角）：证据版本在两次请求之间按 `effective_at` 是否变化。
- `safe_system`（系统视角）：按 `notified_at` 是否变化。规则：若某版本由更新事件引入，`notified_at`
  取事件 `timestamp`；否则取 `updated_at`。

恒有 `safe_system ⇒ safe`。反方向（真值过期但系统不知情）在本数据中**结构上为 0**：2,000 篇文档在
06:00/12:00 批量升版且即时通知，跨版本的请求对必然让系统同时看到变化。因此可观测的分歧只有
10 条"系统保守误失效"（`safe=True, safe_system=False`）：条目事实上仍正确，系统因刚收到通知而误判过期。
这是可测量的管理成本，不是数据缺陷。

**判据**：`measured` 列非空即实测；留空并标 `pending` 即未测。任何估算值都不得写入 `measured`。

**测量效度**：纯内存检查在微秒量级是物理事实，不是空计时。成本表给出"每条请求实际遍历的对象数"
与 `check_full`（36.6 µs）、`locate_full_scan`（63.1 µs）两个上限对照；换算到毫秒的杠杆见 `costs/README.md` §6。

## 五、真值定义

1. **数值层**：`gold_sql` 在指定快照上的执行结果，规范化后比对（列序无关、行序无关、浮点 6 位）。
2. **口径层**：指标卡证据，指向 `metric_XXX` 的具体块与版本。
3. **主张层**：每题 1–5 条事实表述，每条挂 1–2 个证据块；块 ID 跨版本稳定，内容变则 hash 变。
4. **安全复用**：五条件同时成立——同题 ∧ 答案仍正确 ∧ 证据块版本相容 ∧ 权限域相容 ∧ 时间窗覆盖；
   并且区分真值视角与系统视角（见第三节）。

## 七、许可与可获取性

- 本数据集**未使用任何第三方数据集**，无外部许可证约束。
- 建议对数据本体采用 CC BY 4.0、对生成脚本采用 MIT，并在论文附录给出版本号与哈希。
- 句向量依赖的模型权重（`Xenova/bge-small-zh-v1.5`，Apache-2.0）缓存在 `embeddings/cache/`，可删可重下，不计入 MANIFEST。
- 数据不含真实个人信息；文档与请求均为合成文本。

## 八、已知局限

1. **规模与外推**：60 表、约 5 万行，远小于真实企业仓库；延迟只能做相对比较。
2. **文本区分度**：知识文档由模板生成，检索难度偏易；未加干扰块（需先测 Top-K 召回再决定）。
3. **到达过程未与真实 trace 对齐**：热点迁移与突发是构造的。
4. **无副作用工具**：`act` 全只读，"副作用不可跳过"未检验，属明确范围外。
5. **模型耗时只有单一部署**：生成与改写阶段已在 `qwen3.8-27b`（单卡、串行、无截断）上标定，但无第二模型、无并发档位；`ΔT` 的模型分量只代表该部署。
6. **人工标注未做**：300 条标签来自规则谓词，60 条复核清单未标，无一致性系数。
7. **单业务域**：零售/供应链/财务的合成域，跨域迁移未验证。
8. **无静默过期窗口**：如第三节所述，`(F,T)` 结构上为 0；若论文需要"系统不知情"的过期样本，需给文档设置互相独立的生效时刻（未做）。
9. **论文数字需改**：1.4.5 写"约 1,600 条受影响回答"，实测为 874（主张级去重）/1,102（对数）/1,795（文档级），三口径都不是 1,600。

### v0.3.0 补充：思考量（20 条，辅助口径）

- 思考占 completion token 的 **p50 87% / p95 92%**；思考字数与 resp 时长 Spearman ρ=0.988。
- 这 20 条用独立进度文件（`requests_progress_supp.jsonl`）测量，不计入 300 条主标定。
- 主标定的 300 条记录**没有** reasoning 字段（采集代码在跑批中途才修好），所以思考占比只有这 20 条样本；
  主标定的 token 与时长数据仍然完整（`completion_tokens` 已包含思考 token）。
10. **rag/act 的耗时为本地实现值**：BM25 检索 6.2 ms、只读 SQLite 执行 1.1 ms。
    生产环境的检索（向量库 + 重排 + 多路召回）与 SQL（跨库/分布式/大表）通常高出数个量级。
    因此「模型段占端到端 99.99%」与「缓存收益主要在模型段」只对本部署成立；
    act/rag 的缓存收益须按目标部署重新标定，不能直接用本地数字外推。
    数据集在 `costs/path_costs.csv` 保留了相对成本字段（`act_cost` 0.02–0.77）供缩放。

11. **工具调用次数与失败重试未建模**：标定管线按「每请求 1 次 rag + 1 次 act、均成功」执行，
    而数据集结构显示 plan 平均 4.42 步、act 下游工具均值 2.42 个，且没有失败/重试字段。
    按 `costs/tool_cost_model.json` 折算，快模型 + 数仓画像下工具段占比可达 67%，
    旧口径会低估工具成本约 3.35 倍。该模型中的远程延迟与失败率均为 **assumed**，不得当实测引用。
