收束价值评估、显存驱逐、主存准入三个子问题结构与轻量更新、构建访存优化两个子问题

2.2 三个手法

  1. 先收益后代价（同源）。 优化的收益与它带来的管理负担出自同一机制，研究问题因此来自机制自身的资源后果。
  2. 用直觉方案的代价收束。 用数字否定“扩容/全量缓存/全量重算”这类直觉方案，把问题从容量收束到选择机制。
  3. 证据分层落位。 图用来看现象，小例子用来讲因果，分类用来看边界，量级用来立约束。

2.3 三条纪律

  • 一段只推进一个判断，段末留一个未答问题让下一段接手。
  • 文献只在断言处出现，一句话带引用；不写“某某提出……某某提出……”的综述段。
  • 数字三原则：带条件、一段最多两个、不跨论文比命中率。自己的数据用占位符留白。

3 四条见解的评估

每条先给原始表述（用户原话），再给判断、理由、需要拆分的概念、风险与落位。第 6 节给出可直接粘贴的正文。

3.1 见解一：集中管理缓存，因为存在状态联动

原始表述：为什么集中管理缓存：因为存在缓存状态联动，一次部署或文档更新会改变相关条目的有效性，也会改变其他条目的边际价值。例如一个 rag 缓存的更新会导致 resp 缓存的同步更新。

合理 且是“为什么要统一管理”的核心论据，但论证里混了两个不同机制，写的时候必须拆开。

机制含义文献依据写作要点
有效性传播（二值） 一次来源更新会作废由它派生的全部条目；模型升级会同时改变一类条目的有效性 FinCacheServe 把答案绑定文档版本、证据指纹与反向索引；FreshCache 分 L1/L2/L3 三层各带错误预算；CachedAttention 说明上下文截断会让已存 KV 整体失效 写成依赖关系与方向：文档→rag→resp；模型→resp/plan；工具状态→act
集合级边际价值（连续） 条目增删会改变其余条目的覆盖贡献；已有条目能提供同等服务时，新条目增量为零 语义缓存的最优集合问题（INFOCOM 2026，文献 [5]）直接把它写成集合优化；RAGCache 的 PGDSF 用大小、频率、重算成本共同决定淘汰 只在集合层面成立，不能写成单条目属性；可与 1.2.1 的“边际覆盖价值”对应
风险与限定。 集中管理本身有成本（耦合、协调、复杂度），文献也没有证明分布式的按对象管理一定更差。合理写法是“当更新频繁、派生关系密集时，统一管理更有利”，把前提说清。另外“一次部署”与“文档更新”影响的对象集合不同，不能混成一句。

落位：1.1 第 3 段之前新增一段（第 6 节插入 3）；1.3.2 开头补两句（插入 6）。

3.2 见解二：不同粒度对象为不同请求节省不同工作

原始表述：不同粒度的对象，能为不同的请求节省不同工作。相似的两个请求，未必可以共用完整回答；同类任务可能采用相同的处理计划。

合理 但前半句已写在对象表里，重复写没有增量；真正有价值的是后半句：相似性是多维的，不同对象对应不同的复用判据。

对象可复用的判定维度不能直接复用的情形文献依据
resp问题语义、关键实体、时间范围、权限语义相近但回答依赖不同证据或上下文vCache、MVR-cache、SISO、IC-Cache

3.3 见解三：上下文与缓存的区别

原始表述：上下文和缓存的区别：会话上下文中已有的工具结果或证据，可以由 Agent 在正常执行时继续使用，而外部缓存的研究重点是跨请求、跨会话以及上下文不再携带相关结果时的增量复用。

合理，是必要的研究边界，也解释现有稿里“ctx 只作证据、不作复用对象”的原因。但措辞必须精确，否则会被“KV cache 就是上下文缓存”直接反驳。

  • 同一执行内：工具结果与证据仍在上下文，Agent 直接读取，不需要查找、准入、失效判断，也没有命中与未命中。
  • 跨请求 / 跨会话 / 上下文被裁剪压缩后：才需要显式判断哪些历史结果仍适用于当前任务。
  • 同会话跨轮次也算跨请求复用，不要漏掉多轮对话这一类。

文献依据：CachedAttention（上下文溢出后截断会让已存 KV 失效）、MemoryOS（截断丢失早期事实）、Continuum（工具调用间隔中上下文状态仍有效、值得保留）。

落位：1.1 示例段之后（插入 2）；也可在 3.1.5 的子问题边界处呼应。

3.4 见解四：把 resp 缓存视为底层知识库上的物化视图

原始表述：将缓存的 resp 视为底层知识库上的物化视图。

有价值，但不能当严格结论。物化视图的四个特征（派生、需要维护、可能过期、物化选择是优化问题）几乎逐条对得上缓存；但它有两个前提在这里不成立，必须加限定。

物化视图前提本场景的实际情形写法
派生确定：同一基表得到同一结果resp 依赖模型版本与采样，同一输入可能不同输出写“近似物化视图 / 派生对象”，不写“就是物化视图”
基表更新可见：能拿到更新事件外部世界状态变化往往不可直接观测写“依赖外部事件感知的视图维护问题”

推广后可以统一四类对象，这是它最大的价值：

对象基表派生关系维护动作
resp模型版本 + 证据 + 对话生成重生成或局部修复
rag语料与索引版本检索与重排重检或补检
act外部状态 + 工具版本调用重调用或状态校验

4 智能取数助手案例

原始表述：是否可以添加一个和 oncall 助手并列的例子：智能取数助手，用 agent 完成数据查询或者数据分析，例如对于一个 T+1 的离线表，用 agent 对这个表的查询结果是可以缓存下来的；另一方面，对于一些定时任务，其执行的计划是可以复用的，不需要每次执行任务时都去重新推理一个计划出来。

4.1 判断

成立，建议加入，作为与 OnCall 并列的第二场景。它比 OnCall 更好地补上了两件事：版本化的有效期与计划复用；同时让四类对象的分类看起来不是硬凑的。

4.2 为什么好

  1. T+1 表提供“有效性边界可观测”的最干净样本。 分区回刷时 TTL 未到期也会失效；分区未变时 TTL 过期仍有效。可直接支撑“有效性由外部状态决定，时间只是粗糙代理”。
  2. 查询结果对应 act 对象，键可写实。 键 = 规范化查询/意图签名 + 参数（时间窗口、过滤）+ 分区版本 + schema 版本 + 权限域；对应 1.2.2 的 act 精确匹配条款。
  3. 定时任务对应 plan 对象，到达可预测。 重复性强、执行时间已知，式 (1) 中的复用机会估计在这一类对象上最容易做；计划复用文献证据最充分（APC 成本降 50.31%、保留 96.61% 性能）。
  4. 与 OnCall 互补。 OnCall 偏处置与回答（resp/act/plan），取数偏查询与分析（act/plan/rag），合起来覆盖四类对象。

4.3 必须加的限定

  1. 容易被看成“SQL 结果缓存 / 物化视图”的老问题。 需写清 Agent 侧的新问题：自然语言到查询的语义等价、schema 与上下文依赖、表面形式键造成的复用碎片化。硬数据：按 SQL 文本或 AST 做键，命中率 28% 与 56%；改用统一意图签名后 82% 且零误命中（TPC-DS、SSB、NYC TLC，共 1,395 条查询）。
  2. T+1 是最干净的特例，不代表全部。 还有小时级表、流式表、回刷与口径变更；写作时标成“版本边界最清晰的一类”，不要外推成“离线表都可缓存”。
  3. 权限域必须进键。 同一条 SQL 在不同行级权限下返回不同结果，跨用户复用不安全。对应 act 有效性条件里的“权限”。
  4. 查询结果与最终分析结论要分开。 缓存查询结果（act）风险低；缓存分析结论（resp）还含解释与叙述，质量风险高。建议例子里只把查询结果作为缓存对象。
  5. 计划复用不是免费的。 参数、工具版本、权限、依赖表 schema 变化都会让计划失效；APC 的“保留 96.61% 性能”是经验结果；GenCache 在真实云运维场景里程序生成成功率仅 10.4%，还有 1% 的失败来自错误缓存。

6.2 插入 1：取数助手示例

企业内部的智能取数助手是这类场景的具体形态：它由定时任务或自然语言请求触发，经规划、生成查询、执行与校验后产出分析结果。它的重复分为两类。其一，对 T+1 分区表的查询在分区未更新前结果保持有效，同一意图的查询可以直接复用结果；分区回刷、口径变更或权限范围变化后，旧结果随即失效。其二，同类定时任务在参数、工具版本与执行时间不变时可以复用执行计划，不必每次重新推理。已有报告显示，结构化查询生成可以利用结构相近的查询与槽位填充提高命中率[31]；分析负载若按统一意图签名而不是 SQL 文本或语法树作键，命中率可由 28% 与 56% 提升到 82%，且不产生误命中[32]。工作流级缓存在生产负载中可承担过半查询、避免大量工具执行[33]，说明计划与工具结果的复用空间在真实系统中确实存在。

6.3 插入 2：上下文与缓存的边界

需要区分两类复用。执行过程中仍在上下文里的证据与工具结果，由 Agent 直接读取使用，不涉及查找、准入与失效判断；跨请求、跨会话，或上下文因裁剪、压缩不再携带这些结果时，才需要判断哪些历史结果仍适用于当前任务。本章研究后一类复用，并把上下文中的状态作为依赖与失效的证据来源。

6.4 插入 3：状态联动与统一管理

四类对象不是彼此独立的缓存。一次来源更新会作废由它派生的全部条目，一次模型或口径升级会同时改变一类条目的有效性；条目之间的覆盖关系还会改变彼此的边际价值——已有条目能提供同等服务时，新条目的增量为零。前一类问题由依赖关系决定，后一类只在集合层面存在。两者共同说明缓存需要统一管理，策略按对象各自维护会同时出现陈旧复用与重复占用。

6.5 插入 4：粒度与相似性维度（含表）

四类对象服务于不同的复用需求，可复用的粒度也不同：相似请求未必能共用完整回答，但可能共用检索证据；同类任务未必得到相同答案，但可能共用计划模板。因此每类对象按各自的相似性维度判定。

6.6 插入 5：1.2.1 开头的概念框架

从数据管理的角度看，四类对象都是底层数据与模型状态的派生结果：resp 派生自模型版本、证据与对话，rag 派生自语料与索引版本，act 派生自外部状态与工具版本，plan 派生自任务目标与可用工具集。它们的有效期由基表版本决定，维护方式可以是重算，也可以是局部修复。与数据库物化视图相比，这里有两处不同：派生结果不唯一，受模型版本与采样影响；基表更新也未必直接可见。价值估计因此要同时处理版本依赖与证据缺口。

6.7 插入 6：1.3.2 开头

一次来源更新不仅作废直接依赖它的条目，还会改变其他条目的边际价值：覆盖关系重叠的条目在新版本下可能从互补变为冗余，原本不必保留的条目反而值得保留。失效定位与价值重估需要一起执行，只做单条目的失效标记会留下新的错误决策。

7.4 可直接引用的结论与不建议的说法

四组可引用结论：

  1. 重复普遍且成本集中在中间阶段（CachedAttention、Cache-Craft、Cortex、APC、LMCache）。
  2. 现有信号不足以判断复用（vCache、Krites、SISO、KVFlow、Continuum、FreshCache、FinCacheServe、APC、Why Agent Caching Fails）。
