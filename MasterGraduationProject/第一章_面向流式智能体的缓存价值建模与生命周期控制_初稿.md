# 第一章 面向流式智能体的缓存价值建模与生命周期控制

本章围绕流式智能体场景下缓存复用价值难以准确衡量、缓存生命周期缺乏统一控制的问题展开研究。针对缓存对象异质性、复用动作差异性、系统状态动态性以及对象间依赖关系带来的挑战，本章研究动作条件的缓存价值与有效性建模方法，以及依赖感知的缓存生命周期联合控制方法，并通过分层次实验评估二者的独立作用与协同效果。

## 1.1 问题背景与分析

介绍流式智能体场景下缓存复用的研究背景，分析以命中率、相似度、访问频率等指标为主要依据的传统缓存管理方法在收益衡量、质量风险、资源约束与依赖一致性等方面存在的局限。在此基础上，界定本章的研究对象、应用边界与约束条件，明确缓存价值建模与生命周期控制两个核心研究问题，并阐述二者之间的内在联系。

**本节参考文献：** [1]、[2]、[3]、[4]、[5]、[6]、[7]。

## 1.2 异质缓存对象的缓存价值与有效性建模

面向不同类型的缓存对象，研究缓存价值随请求特征、复用动作、系统负载及依赖状态变化的建模方法。综合刻画复用、验证与重算等动作的成本收益关系，分析错误复用、内容陈旧等风险及其不确定性，建立具有可解释性的动作价值与有效性评估机制，为缓存复用决策及后续生命周期控制提供统一的价值与风险依据。

- 该研究的意义在于对 Agent 的各个中间结果都纳入缓存对象范围内，形成了一个完整的 Agent 缓存系统

- 缓存价值是对象、请求、动作、依赖、负载五个因素的的函数，目的是计算一次复用动作相对于“重新计算”的增量净收益

  - 需要区分当前请求的动作价值与缓存条目的长期管理价值：前者比较本次复用、验证和重新计算的成本及风险；后者可结合近期需求、覆盖范围和资源占用，为 1.3 的准入与淘汰提供参考。近期访问频率不必作为每类对象单次复用价值的必选因素。

- 缓存对象包括四类，不同的缓存对象采取不同的复用粒度与机制

  | 缓存对象 | 复用粒度                   | 必须检查的条件                                     | 首选策略                                                   | 降级动作                   |
  | -------- | -------------------------- | -------------------------------------------------- | ---------------------------------------------------------- | -------------------------- |
  | resp     | 最终回答、模板、程序       | 模型版本、权限、语义有效性、最终答案可接受度       | 高风险时先验证答案，再返回；低风险时根据情况复用           | 重新生成回答               |
  | rag      | 文档块、数据表、检索证据   | 文档版本、访问权限、证据是否支持当前问题           | 复用有效证据；缺失部分补检，再生成回答                     | 重新检索或补充检索         |
  | act      | 只读工具调用结果           | 工具和参数、权限、结果依赖的数据状态               | 满足有效性条件时复用结果，必要时先检查外部状态             | 重新调用只读工具           |
  | plan     | 计划模板、计划片段         | 任务阶段、前置条件、工具和权限、计划可执行性       | 适配计划模板；必要时验证并局部修复                         | 重新规划                   |

  - resp，节省回答生成和模型推理
  - rag，节省检索与知识加工
  - act，节省工具调用与环境交互
  - plan，节省规划推理与搜索

  - 以下三类对象的动作价值均以本次请求中“直接重算的预计成本减去选择复用的预计总成本”衡量，实验中可先统一采用端到端耗时。在权限、时效等必要条件满足的前提下，依据近期同类请求的观测，在执行高开销验证或适配之前比较预计成本；样本不足时保守回退。动作选择前已发生的共同开销不重复计入动作间比较。

    - 复用粒度：一次检索获得的证据集合，集合中的每个文档块或数据记录保留来源、版本、权限范围和获取时间。复用的是证据内容，仍需根据当前问题生成回答。

    - 缓存价值：

      - 判断证据是否仍然有效：检查当前请求的访问权限，以及来源版本、更新时间等依赖信息。版本变化或权限不满足时，对应证据不能直接复用；无法确认新鲜度时，按数据源的时效要求重新检索。

      - 判断证据能覆盖当前问题的哪些信息：将问题按固定规则或轻量模型拆成少量信息项，由规则或语义判官判断各信息项是否有证据支持。语义判官只提供辅助判断，不能把相似度或模型结论直接当作充分性的保证；无法可靠判断时走完整检索。

      - 估计补检后能节省的成本：比较完整检索的历史平均开销，与候选检索、权限和版本检查、证据判断及缺失信息补检的总开销。仅有部分证据有效时，只计算复用这部分证据实际避免的开销；还需将判断失败后完整检索的可能开销计入估计。

      - 参考 Cortex [3] 对候选知识的语义验证和 FreshCache [11] 对内容时效风险的处理，在本研究中进一步结合当前问题的证据覆盖与补检成本选择动作。上述覆盖判断和成本比较是本文拟设计的方法，需要通过实验检验，而非两篇文献原有的完整机制。

    - 复用机制

      - 检索候选证据 -> 基于历史成本决定是否尝试验证和补检 -> 检查权限、来源状态及证据覆盖 -> 满足要求时复用；仅部分覆盖且预计补检有收益时补充检索；无有效候选或无法确认时完整检索 -> 使用最终证据生成回答 -> 记录验证、补检及检索耗时。

  - act

    - 复用粒度：一次只读工具调用的结果，记录工具标识和版本、规范化输入参数、输出、权限范围及可获取的数据版本或更新时间。`act` 按工具调用匹配结果；`rag` 按问题组织供生成使用的知识证据，同一数据可由二者引用，但各自复用条件不同。

    - 缓存价值：

      - 判断结果是否适用于当前调用：工具、关键参数、权限及工具版本必须兼容。对于确定性计算工具，检查输入和算法版本；对于依赖动态数据的只读工具，还要检查结果对应的数据版本或外部状态。

      - 比较状态验证和重新调用的成本：记录同类工具的调用耗时、缓存读取耗时和状态检查耗时，以及历史验证中发现数据已变化的比例。验证后复用的预期成本包括检查和读取成本，以及发现变化后重新调用的预期开销；当其不低于直接调用时，选择重新调用。

      - 对没有可靠版本或状态检查接口的数据，只有在业务允许且满足预先设定的新鲜度要求时才考虑复用；否则重新调用。历史变化比例用于成本估计，不能代替有效性检查，也不能单独证明结果仍然正确。

      - TVCACHE [16] 通过工具调用历史复用工具结果，但面向后训练中可复现的环境轨迹；在线服务中的外部状态可能独立变化，不能直接套用其一致性前提。本文借鉴其状态依赖意识，并结合 Cortex [3] 的远程结果复用，研究在线场景下的状态检查与成本比较。

    - 复用机制

      - 按工具标识和输入参数查找候选 -> 检查权限与工具版本 -> 对动态数据比较状态检查与重新调用的预计成本 -> 满足有效条件或业务明确允许的时效要求时复用；需要且值得验证时先验证，验证失败或不具备可接受的有效性依据时重新调用 -> 记录调用、验证耗时和结果变化情况。

      - 有副作用操作不纳入普通工具结果复用。对同一业务操作的重试，应根据业务操作 ID 和外部执行记录确认是否已完成；幂等性本身不能证明可以跳过一次新的业务操作。

  - plan

    - 复用粒度：一个参数化计划模板或子目标计划片段，记录步骤及依赖、所需工具、参数槽位和适用前置条件。模板不直接复用历史任务中的实体、参数和执行结果。

    - 缓存价值：

      - 判断计划是否适用：根据当前任务目标、执行阶段、工具和权限查找候选，检查前置条件以及需要替换的参数。关键词或任务相似只能用于候选检索，不能单独证明计划可执行。

      - 估计适配与修复成本：结合近期同类任务的日志，统计模板检索、参数绑定、验证和局部修复的耗时或 token 成本；分别记录重新规划的成本。结构相近且只需填参的计划通常比需要修改多个步骤的计划更容易复用，但具体收益以观测值为准。

      - 估计适配失败的回退开销：根据近期适配和验证结果估计失败比例，将失败后重新规划的预期成本计入复用成本，再与直接重新规划比较。样本不足时不假定低失败率：需要额外验证，无法确认时重新规划；计划执行中出现状态变化也应重新检查或规划。

      - APC [15] 从历史执行中提取计划模板，按关键词检索并用轻量模型适配当前任务。本文在此基础上结合前置条件、适配成本和失败回退成本选择动作，作为待验证的扩展，而不是声称 APC 已实现该价值模型。

    - 复用机制

      - 提取任务目标和当前阶段 -> 检索候选模板 -> 检查前置条件、工具和权限，并比较适配与重新规划的预计成本 -> 预计复用有收益时绑定当前参数，必要时验证并局部修复 -> 验证通过后使用，否则重新规划 -> 根据适配和执行结果更新统计。

## 1.3 依赖感知的缓存生命周期联合控制

基于缓存对象的价值与风险评估结果，研究容量、质量风险、新鲜度、权限及验证资源等约束条件下的缓存生命周期联合控制方法，统一协调准入、复用、验证、刷新、降级、失效与淘汰等控制动作。重点刻画缓存对象之间的依赖关系以及刷新与失效操作的级联影响，并建立价值估计、控制执行与结果反馈之间的闭环机制，利用实际执行结果持续校准价值模型，实现面向动态系统状态的缓存生命周期管理。

### 1.3.1 设计目标与整体思路

缓存条目的生命周期管理需要回答三个问题：新结果是否值得保存；面对无法立即复用的候选，是否值得投入后台资源验证；依赖变化后，受影响条目应当立即刷新、暂时失效还是直接淘汰。原因不仅是缓存数量增大会占用存储并可能增加检索成本，还包括不同条目的复用收益、验证成本和更新频率不同，且陈旧结果可能沿证据与回答之间的依赖传播。

本节拟采用**价值驱动的后台验证与依赖感知维护**：1.2 负责评估当前请求的复用、验证和重算动作；1.3 利用近期需求及成本观测，决定条目的准入和保留，并在有限后台资源下选择验证、刷新任务。缓存命中时的权限、版本、时效和对象特定有效性检查仍由 1.2 的复用机制执行，管理价值高不能代替这些检查。

Krites [17] 对未直接命中静态缓存的候选进行异步验证，将通过验证的静态回答提升到动态缓存，主要改善未来请求的静态来源回答覆盖。本文借鉴其将部分验证移出关键路径的思路，进一步研究多类对象下验证任务的选择，以及依赖变化后的维护；不要求为所有对象构建 Krites 式静态层。FinCacheServe [6] 已研究文档到回答的依赖索引、失效与效用驱动管理，Cortex [3] 已研究成本感知淘汰与语义验证。因此，本节不能把后台验证、反向索引或价值排序各自作为独立首创，而应验证**有限后台资源下验证选择与依赖感知刷新的联合效果**。

研究对象沿用 1.2 的 `resp`、`rag`、`act`、`plan` 四类，以 `resp` 和 `rag` 及其依赖关系作为主要实现与实验对象；`act` 和 `plan` 接入统一条目接口，并验证基本有效性及生命周期流程。该范围不代表四类对象都采用相同的检索、验证或刷新方式。

### 1.3.2 缓存条目、状态与管理价值

统一元数据包括：对象标识与类型、内容或存储引用、大小、权限范围、创建与最近访问时间、近期需求统计、验证状态、依赖标识及其版本。`rag` 记录来源文档或数据记录的版本；`resp` 记录生成时使用的证据及其来源版本；`act` 记录只读工具、参数和可获得的数据版本；`plan` 记录工具版本和可表达的前置条件。反向索引用于从发生变化的依赖找到受影响条目。这里记录的是实际可获取的依赖，而非假定系统能够自动发现所有隐含依赖。

为说明状态变化，条目采用以下逻辑状态；具体实现可以用状态字段与队列任务表示，不要求为每个动作单独建立复杂状态机。

| 状态 | 含义与处理 |
| --- | --- |
| 候选 | 新生成或检索到的结果，尚未通过准入和必要的有效性检查，不能作为已验证条目直接复用。 |
| 可用 | 已满足入库条件；每次复用时仍按当前请求检查权限、版本、时效和适用性。 |
| 待确认 | 验证尚未完成、依赖发生变化或有效性无法确认；不能直接复用，必要时走验证或重算。 |
| 已淘汰 | 缓存副本被删除；后续请求按未命中处理，可重新生成候选。 |

后台验证或刷新是作用于候选或待确认条目的任务，而不是保证成功的状态转换。只有任务完成且必要检查通过，条目才可进入可用状态；失败、超时或版本冲突时保持不可直接复用，或按策略淘汰。

**管理价值与单次动作价值的区别。** 单次动作价值比较当前请求的不同动作；管理价值估计条目在未来观察窗口内是否值得占用缓存和后台资源。令未来窗口为 \(H\)，对条目 \(i\) 使用以下可解释的启发式估计：

\[
V_i(H)=\widehat N_i(H)\,\widehat S_i-\widehat C_i^{maint}(H),
\qquad D_i=V_i(H)/s_i.
\]

其中，\(\widehat N_i(H)\) 为预计可由条目有效服务的请求次数，\(\widehat S_i\) 为一次有效复用相对重算的平均节省耗时，\(\widehat C_i^{maint}(H)\) 为窗口内预计验证、刷新等维护开销，\(s_i\) 为条目的存储大小，\(D_i\) 为单位空间价值。估计以近期日志为基础，证据不足时使用同类对象的保守统计或暂不主动投入后台资源。回答候选的需求估计优先使用 1.2 中的**新增安全覆盖**，避免将已被现有缓存安全服务的请求再次计为新增收益；计算覆盖的回放及判官开销也须计入测量。

该公式是可比较的工程估计，不是质量风险的概率保证，也不把不同单位的风险和时延直接相加。检索、判官、后台模型调用与回源成本应分别记录；首版以耗时为主要成本，并额外报告调用数和 token。条目大小为零或未知时使用实际序列化大小或预设的非零下限。

### 1.3.3 价值驱动的准入、保留与淘汰

在线请求产生的新结果先经过对象类型所需的权限、版本及内容检查，再估计其管理价值。预计窗口内能产生正收益且满足准入条件时，条目可进入缓存；样本不足时可在有限试验预算下采用小规模、短期的试探性准入，不能因此降低有效性要求。对仍需较高成本判断的候选，进入后台验证流程。

容量充足时保留可用条目；空间不足时，先移除已失效且不准备刷新的条目，再依据单位空间价值从低到高选择淘汰对象，直到满足容量约束。候选条目应与现有可用条目的最低价值进行比较，避免仅因新条目收益为正就驱逐更有价值的条目；条目过大或候选价值不足时拒绝准入。周期性重估近期需求，避免旧热点长期占用空间，并记录淘汰与重新写入次数以观察抖动。

淘汰只是删除缓存副本，不表示底层事实已经改变。删除 `rag` 缓存项不会自动证明依赖同一文档版本生成的 `resp` 已失效；但 `resp` 必须保留独立的来源版本信息，不能把被淘汰的缓存副本作为唯一有效性证据。

### 1.3.4 面向有限资源的后台验证

当前请求按 1.2 的规则处理：可以安全直接复用则复用；值得同步验证且通过时复用；否则重算。无法直接使用、但具有潜在复用价值的候选可以产生后台验证任务。后台结果用于**未来请求**，不改变已返回的当前请求结果。

例如，`resp` 的候选回答与新请求语义接近，但尚不满足直接复用条件；`rag` 的候选证据可能覆盖新问题，但需要检查支持关系。对象类型决定验证方式，权限不满足、依赖已知失效或明显不适配的候选不进入普通验证提升流程。队列按候选与请求条件、权限范围及依赖版本去重，并限制长度和并发；队列满时舍弃或延后低优先级任务，在线请求不等待后台结果。

对验证任务 \(j\)，以通过验证后可能带来的**新增**未来收益估计优先级：

\[
P_j^{verify}=\frac{\widehat p_j^{pass}\,\widehat N_j^{new}\,\widehat S_j-\widehat C_j^{verify}}{\widehat T_j^{verify}}.
\]

其中，\(\widehat p_j^{pass}\) 是同类任务的历史通过比例，仅用于成本收益估计；\(\widehat N_j^{new}\) 是验证通过后未来窗口内预计新增的有效服务次数，\(\widehat S_j\) 是每次预计节省，\(\widehat C_j^{verify}\) 和 \(\widehat T_j^{verify}\) 分别是验证成本与占用后台资源的时间估计。按正优先级从高到低执行；估计不足时采用保守先验和受限探索，验证时间使用非零下限。收益中应排除原缓存已能安全服务的请求，避免把一次复用收益重复分配给多个候选；实验需统计估算与实际之间的偏差。

验证通过后，将结论绑定被验证的请求条件、对象内容、权限范围及依赖版本，再执行准入检查。若写入前发现依赖版本已变化，则丢弃该验证结果或重新排队；验证失败、超时或结果不明确时不提升。历史判官通过率不是正确率保证：对未来请求仍需检查当前权限、版本和具体适用性，不能因为某个相似请求通过验证就对任意近邻无条件复用。

### 1.3.5 依赖感知失效与选择性刷新

实验中假设数据源可提供版本和更新事件。数据源更新时，系统更新已知版本，通过反向索引找到受影响的证据和回答，将它们标记为待确认；处理尚未完成期间，读取路径以当前已知版本检查为准，不直接返回旧版本结果。依赖链可以表示为：

```text
文档 D（版本变化） → 证据 R（待确认） → 回答 A（待确认）
                                  ↓
                   依据需求与成本选择后台刷新或按需重算
```

例如，客服政策文档更新后，引用该文档的证据和由其生成的回答均不能直接复用。如果相关问题近期需求较高，可优先刷新证据，再按回答的预计需求决定是否重新生成回答；如果需求很低，则暂不主动刷新，等后续请求到达时重新检索或生成。刷新证据不会自动证明旧回答仍然正确，回答必须经过重新生成或适当验证。

对刷新任务 \(k\)，比较不主动刷新时未来请求的预计成本与主动刷新后的预计成本：

\[
P_k^{refresh}=\frac{\widehat C_k^{on\text{-}demand}-\widehat C_k^{after\text{-}refresh}-\widehat C_k^{refresh}}{\widehat T_k^{refresh}}.
\]

三项成本使用同一观察窗口和耗时口径；后一项包含刷新后仍需发生的查找与复用成本，分母是预计后台占用时间。仅对预计净收益为正的任务安排主动刷新，并按优先级与验证任务竞争共享后台预算。证据与回答顺序刷新时，上游刷新成本只计一次；已被其他缓存覆盖的请求不重复计为收益。两类任务的优先级都是单位后台占用时间的预计净节省，但参数估计误差及队列等待仍须在实验中评估。

刷新任务生成后保存所读依赖的版本快照；提交结果前再次比较系统已知版本，一旦发生变化便丢弃旧结果或重新执行。更新事件与读取存在并发时，原型须使版本检查与条目发布具有可验证的先后关系；实际保证仅针对**系统已接收的更新事件和已记录的依赖**，不等同于对外部世界实时一致。无法获取可靠版本或变化信息时，只有满足业务明确允许的时效要求才考虑复用，否则重新检索或调用。

### 1.3.6 流式实现与反馈闭环

原型以请求、数据更新和后台任务完成作为事件，使用 Flink 状态记录条目元数据、近期统计、已知版本和待处理任务；外部工作池执行模型判断或回源刷新。任务携带唯一标识和版本快照，完成事件进行去重和版本检查；失败或超时可有限重试，超过预算则回退为按需重算。checkpoint 与恢复需要验证状态和待处理任务可恢复，但外部判官、缓存及索引的端到端 exactly-once 不作为预设结论。

记录请求匹配、验证和刷新耗时、命中与失败、依赖更新、失效传播、淘汰与重复任务等数据，周期性更新需求、节省成本和任务耗时估计。后台资源不足、判官不可靠或依赖不完整时，系统应退化为保守复用与按需重算，而不是以未经验证的结果维持命中率。

## 1.4 实验评估与分析

围绕缓存价值建模、生命周期联合控制及二者协同机制开展分层次实验评估。首先，从风险校准与复用决策等方面验证动作条件价值模型的有效性；其次，从缓存净收益、风险约束满足与依赖一致性等方面评估生命周期联合控制方法；最后，通过端到端对比实验分析完整机制的综合效果，并考察流式实现的运行开销与故障恢复一致性。结合实验结果总结方法的作用机制、适用条件与局限性。

生命周期实验以 `resp`、`rag` 为重点，构造可控版本更新及带热点变化的请求流，记录证据与回答的真实来源。固定请求、更新序列、缓存容量、在线检索器和后台资源预算，比较 LRU、TTL、参考 Cortex 的成本感知淘汰、参考 Krites 的简单后台验证队列、参考 FinCacheServe 的依赖失效与按需重算，以及本文方案；没有公开实现时明确说明是根据论文复现的近似基线，不称为原系统结果。

分别关闭价值驱动的验证排序和刷新排序，并将主动刷新与只在请求到来时重算比较；改变后台预算、缓存大小、文档更新频率及请求热点变化速度，观察两项机制是否各自有效以及组合是否带来额外收益。以端到端平均和尾部时延、有效复用节省的重算时间、过期复用次数、缓存占用、后台调用与 token 开销、队列积压和刷新后未使用比例为主要指标，分对象报告 `resp` 与 `rag` 的结果。后台成本与为构建候选、判断覆盖而执行的工作均计入总成本，避免将工作从在线转移到后台后只报告时延改善。

先用可控真值测试版本变化、验证和刷新逻辑，再对实际判官输出进行人工或可信标注的抽样比较，报告误批准和漏批准；验证依赖更新与后台任务完成并发、重复事件、故障恢复以及缓存副本淘汰等情形。无论模拟还是实际判官，实验结果都只能支持所测负载和依赖可观测范围内的结论。
