# 第一章 面向流式智能体的缓存价值建模与生命周期控制

本章围绕流式智能体场景下缓存复用价值难以准确衡量、缓存生命周期缺乏统一控制的问题展开研究。针对缓存对象异质性、复用动作差异性、系统状态动态性以及对象间依赖关系带来的挑战，本章研究动作条件的缓存价值与有效性建模方法，以及依赖感知的缓存生命周期联合控制方法，并通过分层次实验评估二者的独立作用与协同效果。

## 1.1 问题背景与分析

介绍流式智能体场景下缓存复用的研究背景，分析以命中率、相似度、访问频率等指标为主要依据的传统缓存管理方法在收益衡量、质量风险、资源约束与依赖一致性等方面存在的局限。在此基础上，界定本章的研究对象、应用边界与约束条件，明确缓存价值建模与生命周期控制两个核心研究问题，并阐述二者之间的内在联系。

## 1.2 异质缓存对象的价值建模与检索机制

面向不同类型的缓存对象，研究缓存价值随请求特征、复用动作、系统负载及依赖状态变化的建模方法。综合刻画复用、验证与重算等动作的成本收益关系，分析错误复用、内容陈旧等风险及其不确定性，建立具有可解释性的动作价值与有效性评估机制，为缓存复用决策及后续生命周期控制提供统一的价值与风险依据。

- 该研究的意义在于两点

  - 对 Agent 的各个中间结果都纳入缓存对象范围内，形成了一个完整的 Agent 缓存系统

  - 缓存价值不是对象的静态属性，而是对象、请求、动作、依赖状态和系统负载的函数

- 缓存价值是对象、请求、动作、依赖、负载五个因素的的函数，目的是计算一次复用动作相对于“重新计算”的增量净收益

  - 当前请求的动作价值比较本次复用、验证和重新计算的成本及风险；缓存条目的长期管理价值结合近期需求、覆盖范围、剩余有效期、质量改善与资源占用，为 1.3 的准入、提升和淘汰提供依据。近期访问频率用于估计未来需求，不必作为每类对象单次复用价值的必选因素。

  - resp

    - 复用粒度：一个完整的回答条目

    - 缓存价值：

      - 用固定的 LLM 把请求归一化为签名

        - 对请求使用固定的 LLM 提取结构化签名

          - 意图

          - 实体

          - 时间范围

          - 主题

          - 权限范围

          - 版本

        - 签名对应一个请求簇，包括多个相近的请求

        - 检索器如何实现？怎么去检索呢？检索成本怎么算？

      - 用近期滑动窗口估计访问频率

        - 最近 N 条请求作为窗口

        - 这个统计量用于衡量近期需求。它会随请求流滚动更新，能反映热点变化

      - 回放请求，估计候选回答的新增覆盖比例

        - 假设当前缓存集合为 \(M\)，候选回答为 \(c\)，请求日志中保存了近期请求、签名和向量。对每条与 \(c\) 相关的请求 \(q\)，做两次检索比较

        - 1. 在当前缓存 \(M\) 中检索，记录结果。
          2. 假设把 \(c\) 加入缓存，在 \(M\cup\{c\}\) 中检索，记录结果。
          3. 如果原缓存已经能安全命中，这条请求不算 \(c\) 的新增覆盖。
          4. 如果原缓存没有安全命中，而加入 \(c\) 后会选中 \(c\)，再检查 \(c\) 是否通过安全门。
          5. 只有“原来不能安全命中、现在由 \(c\) 安全服务”的请求，才算新增安全命中。

      - 用历史反馈估计回答的复用安全性

        - 借鉴 vCache 的风险控制思路，但采用更轻量的历史安全率估计

      - 估计缓存命中时能节省的推理与时延成本

        - 生成成本可以用 GPU 推理时间、输入输出 token 对应的服务成本，或 API 费用衡量

        - 缓存命中时没有实际生成开销，可以用同签名历史未命中请求的平均值估计

    - 复用机制

      - 检索候选回答 -> 判断能否复用 -> 选择回答或重新生成 -> 更新统计信息

      （outdated）把请求归一化到一个请求签名，使用 LLM，同一签名代表一类可能由相同回答服务的请求，签名可能包含查询意图、实体和时间范围；权限范围、模型版本等信息用于判断请求与缓存回答是否兼容。实验中固定签名生成方式和检索器，保证不同缓存策略使用相同的请求分组和候选检索结果。

      - 查询意图

      - 实体或主题

      - 时间范围

      - 权限范围

      - 模型版本

      - 系统统计最近一个固定窗口内每种查询签名的请求数，每隔一段时间滚动更新统计，使频率估计反映近期请求变化

      - 估计候选回答新增覆盖的请求比例，设当前缓存集合为 \(M\)，待评估的缓存回答为 \(c\)，对近期请求进行回放，分别使用 \(M\) 和 \(M\cup\{c\}\) 检索。如果加入 \(c\) 后，检索器会选中它，而原缓存集合不能安全服务该请求，就记为 \(c\) 新增覆盖了一次请求

      - 估计每次复用能省多少成本：比较重新生成回答的开销（通过历史类似的请求的推理时间来计算）和查找、验证缓存的开销（权限、版本检查，语义检查，可以交给 LLM 判官进行裁决）。生成越贵、复用越便宜，这条缓存的价值越高

  - rag

    - 复用粒度：一次检索获得的证据集合，集合中的每个文档块或数据记录保留来源、版本、权限范围和获取时间。复用的是证据内容，仍需根据当前问题生成回答。

    - 缓存价值：

      - 判断该资料或证据是否能用

        - 权限是否允许

        - 来源是否有效

        - 时效是否满足

      - 依赖感知的证据复用机会估计

        - 统计窗口内证据或资料的使用频率

        - 统计窗口内证据或资料来源的稳定性

      - 估计复用资料或证据所能节省的成本（时延、api 调用成本）

        - 完整检索成本可用基于历史记录得到的统计值，包括检索的时延、检索涉及的 api 调用费用（如有）

      - （In detail）判断证据是否仍然有效：检查当前请求的访问权限，以及来源版本、更新时间等依赖信息。版本变化或权限不满足时，对应证据不能直接复用；无法确认新鲜度时，按数据源的时效要求重新检索。

      - 估计证据集合的依赖感知复用机会：根据证据块的来源及版本建立“来源版本—证据块—证据集合”的显式依赖关系。系统在流式运行中记录请求最终采用的证据块，无论该块来自缓存还是本次检索；将一次请求关联到集合内被实际使用的来源，得到各来源对该集合近期需求的贡献。第二点只估计未来可能的复用机会，单次复用成本由第三点计算。

        对集合 \(i\)，设近期观察窗口长度为 \(T\)，集合涉及的来源版本为 \(s\)。当某次请求使用该集合中来自 \(k\) 个不同来源的证据时，将该请求的一个机会平均分给这 \(k\) 个来源，令 \(n_{is}\) 为窗口内来源 \(s\) 分得的机会数，\(\widehat P_s(t)\) 为来源版本在未来时刻 \(t\) 仍可用的估计比例，则未来窗口 \(H\) 内的依赖感知机会数估计为：

        \[
        \widehat O_i(H)=\sum_{s\in Dep(i)}\frac{n_{is}}{T}\int_0^H\widehat P_s(t)\,dt.
        \]

        来源按可观测的文档或数据记录版本分组，同一来源下的多个块共享版本变化信号，避免将同一次来源更新重复当作多个独立事件。首版可依据近期来源更新频率估计 \(\widehat P_s(t)=e^{-\widehat\lambda_s t}\)，其中 \(\widehat\lambda_s\) 为来源版本变化率；样本不足时采用同类来源的保守先验。该公式估计当前版本在未主动刷新的条件下能带来的机会；发生刷新后更新依赖版本和统计，再重新估计。一个来源失效只折减其分得的机会，其他有效来源的证据仍可参与复用，具体证据是否充分由在线检查和补检决定。

        同一请求使用集合内多个块时只计一个机会；若多个集合共享被使用的块，按在线策略确定的唯一归属记录需求，避免同次需求在多个集合中重复累计。机会统计通过在线使用记录更新，无需重新执行历史请求。该估计受现有检索和归属策略影响，可对少量请求抽样完整检索并校准；新集合使用相同来源和证据块的已有统计作为初始参考。

      - 估计补检后能节省的成本：比较完整检索的历史平均开销，与候选检索、权限和版本检查、证据判断及缺失信息补检的总开销。仅有部分证据有效时，只计算复用这部分证据实际避免的开销；还需将判断失败后完整检索的可能开销计入估计。

      - Cortex [3] 按有效命中频次、数据稳定性和获取成本管理语义缓存；RAGCache [5] 利用文档顺序造成的 KV 前缀依赖组织缓存，并结合频次、重算成本和空间进行管理。SSC [18] 针对证据块结合权限、新鲜度、历史效用和服务成本进行管理。本文借鉴频次与稳定性联合衡量、依赖结构感知的思路，将证据与来源版本之间的依赖用于估计集合的未来复用机会，再结合补检后的单次收益管理集合。

    - 复用机制

      - 检索候选证据 -> 基于历史成本决定是否尝试验证和补检 -> 检查权限、来源状态及证据覆盖 -> 满足要求时复用；仅部分覆盖且预计补检有收益时补充检索；无有效候选或无法确认时完整检索 -> 使用最终证据生成回答 -> 记录验证、补检及检索耗时。 对当前问题的证据覆盖，可将问题按固定规则或轻量模型拆成少量信息项，再由规则或语义判官辅助判断各信息项是否有证据支持；无法可靠判断时进行完整检索。

  - act

    - 复用粒度：一次只读工具（搜索、解析、计算和只读）调用的结果，记录工具标识和版本、规范化输入参数、输出、权限范围及可获取的数据版本或更新时间。`act` 按工具调用匹配结果；`rag` 按问题组织供生成使用的知识证据，同一数据可由二者引用，但各自复用条件不同。

    - 缓存价值：

      - 计算本次复用工具结果能节省多少成本（时延成本），工具调用是有一定概率出错的

      - 自启动以来、最近时间窗口内该工具的使用频率及变化幅度

      - 把工具调用结果所在的后续调用结构，作为长期保留价值的依据。一次工具调用的结果如果曾经支撑多种后续工具调用（这个怎么去验证？通过调用工具时传递的参数，例如字段值），它可能是一个具有共享价值的中间结果

      - 不同任务可能调用相同的工具和参数，随着未来任务类型的比例变化，各工具结果的复用机会也会变化，用任务类型的近期需求，估计每条 `act` 缓存在未来能服务多少次调用

      - （In detail）判断结果是否适用于当前调用：工具、关键参数、权限及工具版本必须兼容。对于确定性计算工具，检查输入和算法版本；对于依赖动态数据的只读工具，还要检查结果对应的数据版本或外部状态。

      - 记录工具的历史使用频次并用时间窗口统计过去一段时间内工具的调用频率以及和前一个窗口的频率增幅

      - 比较状态验证和重新调用的成本：记录同类工具的调用耗时、缓存读取耗时和状态检查耗时，以及历史验证中发现数据已变化的比例。验证后复用的预期成本包括检查和读取成本，以及发现变化后重新调用的预期开销；当其不低于直接调用时，选择重新调用。

      - 对没有可靠版本或状态检查接口的数据，只有在业务允许且满足预先设定的新鲜度要求时才考虑复用；否则重新调用。历史变化比例用于成本估计，不能代替有效性检查，也不能单独证明结果仍然正确。

      - TVCACHE [16] 通过工具调用历史复用工具结果，但面向后训练中可复现的环境轨迹；在线服务中的外部状态可能独立变化，不能直接套用其一致性前提。本文借鉴其状态依赖意识，并结合 Cortex [3] 的远程结果复用，研究在线场景下的状态检查与成本比较。Hierarchical Caching for Agentic Workflows 关注工作流和工具层的缓存，并利用工具依赖关系处理缓存一致性

    - 复用机制

      - 按工具标识和输入参数查找候选 -> 检查权限与工具版本 -> 对动态数据比较状态检查与重新调用的预计成本 -> 满足有效条件或业务明确允许的时效要求时复用；需要且值得验证时先验证，验证失败或不具备可接受的有效性依据时重新调用 -> 记录调用、验证耗时和结果变化情况。

      - 有副作用操作不纳入普通工具结果复用。对同一业务操作的重试，应根据业务操作 ID 和外部执行记录确认是否已完成；幂等性本身不能证明可以跳过一次新的业务操作。

  - plan

    - 复用粒度：一个参数化计划模板或子目标计划片段，记录步骤及依赖、所需工具、参数槽位和适用前置条件。模板不直接复用历史任务中的实体、参数和执行结果。

    - 缓存价值：

      - 未来复用机会有多少？

        - 看近期有多少任务可能使用该计划，以及这些任务的需求是否正在变化。例如，退款咨询计划每小时都可能用到；某个特殊故障排查计划可能一个月才遇到一次

      - 遇到机会时，平均能省多少？

        - 适配成功：节省重新规划的成本，但要支付参数绑定、验证、修复等成本

        - 适配失败：尝试适配的成本已经花掉，随后还要重新规划

      - 计划稳定性带来的长期价值

        - 复用一个 plan 之后，智能体能否沿着这套步骤顺利完成任务，以及执行过程中需要多少次返工、回退或重新规划。执行越稳定的 plan 质量越高，也就越具有缓存价值

        - 这一点可以通过真实执行日志观察，可以把日志交给 LLM 判官进行判定（Generalizing Experience for Language Agents NIPS '25，Agentic Plan Caching NIPS '25）

      - 计划执行稳定性价值：计划决定后续步骤及其依赖，适配通过后仍需观察实际执行结果。针对同类任务，记录使用该计划后的任务完成情况、执行中重新规划或回退的次数，以及执行阶段的端到端耗时；与同类任务直接重新规划的基线比较，估计该计划对后续执行成本及任务完成率的影响。未来窗口内的执行收益可由预计尝试次数与单次尝试的平均执行成本差相乘；完整统计适配失败后回退及执行中重新规划的情况，并将适配阶段开销与执行阶段开销分别计入一次。任务完成率作为独立质量指标或约束，避免直接与耗时相加。统计按任务条件、工具版本等分组，优先通过可复现任务或随机分组建立基线；样本不足时使用同类计划的统计并持续积累数据。MetaFlowLLM [19] 从历史任务构建可复用工作流，并评估任务成功率和执行成本；基于计划执行反馈估计长期价值是本文提出的建模思路。

      - （In detail）判断计划是否适用：根据当前任务目标、执行阶段、工具和权限查找候选，检查前置条件以及需要替换的参数。关键词或任务相似只能用于候选检索，不能单独证明计划可执行。

      - 估计适配与修复成本：结合近期同类任务的日志，统计模板检索、参数绑定、验证和局部修复的耗时或 token 成本；分别记录重新规划的成本。结构相近且只需填参的计划通常比需要修改多个步骤的计划更容易复用，但具体收益以观测值为准。

      - 估计适配失败的回退开销：根据近期适配和验证结果估计失败比例，将失败后重新规划的预期成本计入复用成本，再与直接重新规划比较。样本不足时不假定低失败率：需要额外验证，无法确认时重新规划；计划执行中出现状态变化也应重新检查或规划。

      - APC [15] 从历史执行中提取计划模板，按关键词检索并用轻量模型适配当前任务。本文在此基础上结合前置条件、适配成本和失败回退成本选择动作，作为待验证的扩展，而不是声称 APC 已实现该价值模型。

    - 复用机制

      - 提取任务目标和当前阶段 -> 检索候选模板 -> 检查前置条件、工具和权限，并比较适配与重新规划的预计成本 -> 预计复用有收益时绑定当前参数，必要时验证并局部修复 -> 验证通过后使用，否则重新规划 -> 根据适配和执行结果更新统计。

  - 检索采用通用框架与对象专属策略

  - resp

      - 精确键索引

      - 关键词索引

      - 语义向量索引，拆成多个语义片段，使用多向量匹配捕捉更细的差异（MVR-cache ICML '26）

      - 读取用户身份与权限

  - rag

      - 同时记录反向索引，系统找到某个证据块后，也知道它属于哪个证据集合

        - 块级关键词索引：查找包含关键实体或术语的证据块

## 1.3 依赖感知的缓存生命周期联合控制

基于 1.2 的缓存价值与有效性评估，结合近期需求、缓存年龄、依赖状态及资源约束，研究缓存条目的准入、异步验证与提升、保留、失效、刷新和淘汰。通过价值估计、控制执行与反馈更新形成生命周期管理闭环。

  - 已验证

  - 已失效

- 新鲜度

  - 版本落后还是最新

- 需求

  - 热

  - 温

  - 冷

### 1.3.1 设计目标与整体思路

- （outdated）缓存准入与淘汰

  - 基于缓存价值建模、有效性、新鲜度和热度

  - 缓存失效与刷新

    - resp 的依赖项变更后需要失效（反向索引）

- 缓存分层与提升

  - 静态层与动态层

    - 先查静态层

  - 灰度区域先查动态层再考虑是否需要推理或提升

- （current）面向流式运行的价值驱动缓存准入与淘汰：让缓存内容随流式运行中的需求和有效期变化而调整

  - 准入：对新结果检查其有效性，结合第一点的价值评估、近期需求和剩余有效期，判断是否值得缓存

  - 保留：随着请求、缓存年龄和依赖状态变化，持续更新条目的管理价值

  - 淘汰：空间不足时，综合条目价值与占用空间，优先淘汰保留收益较低的条目

  - 静态回答提升：沿用现有静态层、动态层设计；对需要进一步确认的静态候选进行异步验证，通过后结合价值决定是否提升到动态层

- 面向流式证据更新的缓存依赖传播与自适应修复：让缓存随外部知识变化及时维护，并处理更新与 Agent 执行交错带来的一致性问题

  - 记录依赖：记录来源、检索证据与缓存回答之间的关系；对回答中的事实表述记录对应证据和版本

  - 传播影响：收到证据更新事件后，定位受影响的 `rag` 和 `resp`，将受影响的旧条目标记为暂不可复用。新增证据先判断是否改变原检索结果

  - 选择处理方式：基于更新后的证据，由轻量 LLM 判断影响范围；范围清晰且证据充分时局部修复，否则重新生成

  - 核验并写回：检查新回答的证据支持情况和版本；处理期间证据再次更新时，基于最新版本重新处理

1.2 评估当前请求下复用、验证和重算的成本与有效性；本节在此基础上估计条目在未来一段时间内带来的增量收益，用于决定哪些结果值得保存、哪些候选值得投入后台资源，以及依赖变化后如何维护。整体流程为：**估计未来价值 → 价值驱动准入 → 异步验证与提升 → 依赖感知维护 → 反馈更新**。

`resp` 参考 Krites [17] 采用静态层与动态层：静态层保存离线精选的回答，动态层保存在线生成结果及经验证提升的静态回答。请求优先检查静态层；静态候选处于相似度灰区时，当前请求继续通过动态层或后端处理，同时为静态候选创建后台验证机会。验证通过后，系统依据增量价值决定是否将静态回答提升到动态层，供未来请求使用。

在 Krites 的双层结构和异步验证基础上，本节进一步结合 1.2 的动作价值、缓存年龄及依赖状态，研究质量与成本共同驱动的准入和提升，以及来源变化后的选择性维护。研究对象沿用 `resp`、`rag`、`act` 和 `plan`，以 `resp`、`rag` 及其依赖关系为主要实现与实验对象；`act` 和 `plan` 接入统一条目接口并验证基本生命周期流程。FinCacheServe [6] 和 FreshCache [11] 等工作提供依赖管理和新鲜度建模的相关基础，本节通过对照与消融评估各因素联合控制的效果。

### 1.3.2 缓存状态、年龄与管理价值

统一元数据包括对象标识与类型、内容或存储引用、大小、权限范围、内容生成或新鲜度确认时间、最近访问时间、近期需求统计、验证状态，以及依赖标识和版本。`rag` 记录来源文档或数据记录的版本；`resp` 记录使用的证据及其来源版本；`act` 记录只读工具、参数和可获得的数据版本；`plan` 记录工具版本和可表达的前置条件。静态回答及其动态层提升项还记录静态条目标识与版本，反向索引用于定位受影响条目。

| 状态   | 含义与处理                                                             |
| ------ | ---------------------------------------------------------------------- |
| 候选   | 新生成或检索到的结果，等待必要检查与准入决策。                         |
| 可用   | 已满足准入条件；复用时检查当前请求的权限、版本、时效和适用性。         |
| 待确认 | 验证尚未完成、依赖发生变化或有效性无法确认；等待验证、刷新或按需重算。 |
| 已淘汰 | 缓存副本被删除；后续请求按未命中处理。                                 |

**缓存年龄与剩余有效期。** 令 \(a_i(t)\) 表示从条目内容生成或最近一次实际确认内容及来源新鲜度有效到当前时刻的时间，\(L_i\) 为对象类型或业务设定的允许内容年龄，\(H\) 为未来观察窗口。在当前依赖有效时，条目自身时效约束下的剩余窗口为：

\[
h_i(H,t)=\max\{0,\min(H,L_i-a_i(t))\}.
\]

涉及外部来源时，还需结合来源自身的时效期限和版本变化情况估计有效机会。静态回答提升到动态层时，沿用源内容及其依赖的时间和版本，提升操作与普通访问均不重置内容年龄；最近访问时间用于估计近期需求。时效期限按对象和来源配置，实际确认来源新鲜度或生成新内容后更新相应时间。

对 `rag`，沿用 1.2 已包含来源稳定性的复用机会估计，将各来源的剩余有效期直接作为积分上界。设来源 \(s\) 及集合 \(i\) 的允许年龄分别为 \(L_s\)、\(L_i\)，当前年龄分别为 \(a_s\)、\(a_i\)，则：

\[
h_{is}=\max\{0,\min(H,L_i-a_i,L_s-a_s)\},\qquad
\widehat O_i^{age}(H)=\sum_{s\in Dep(i)}\frac{n_{is}}{T}\int_0^{h_{is}}\widehat P_s(u)\,du.
\]

其中，\(n_{is}/T\) 和 \(\widehat P_s\) 沿用 1.2 的近期需求及来源版本稳定性估计。结合权限、证据覆盖和实际选用情况，将潜在机会转化为有效复用次数；部分来源失效时，其余有效证据仍可按 1.2 的复用与补检机制处理。对依赖多个来源的完整 `resp`，结合必要来源中最先到期的时效和版本变化估计剩余服务机会。上述估计以当前版本未主动刷新为前提，刷新后的新内容按其依赖和有效期重新估计。

**增量管理价值。** 设当前缓存集合为 \(M\)，准入、提升、淘汰或刷新后的集合为 \(M'\)，以相同未来请求和观察窗口比较两种状态：

\[
\Delta V(M\!\to\!M')=
\Delta\widehat T(H)
+\lambda_Q\Delta\widehat Q(H)
-\lambda_B\Delta\widehat C^{bg}(H).
\]

其中，\(\Delta\widehat T\) 是预计用户端总耗时的减少量，依据 1.2 的单次复用净节省、近期需求及有效复用机会估计；\(\Delta\widehat Q\) 是预计回答质量总分的变化量；\(\Delta\widehat C^{bg}\) 是预计未来后台维护工作量的变化量，以工作线程占用时间计量。\(\lambda_Q\) 和 \(\lambda_B\) 将质量变化和后台工作量折算到统一价值口径，使用验证集确定，并在实验中分析权重变化的影响。

估计时对近期请求样本比较 \(M\) 与 \(M'\) 下实际可能选择的回答或重算路径，并按预计请求量加权。新条目带来的新增安全覆盖可使用 1.2 的覆盖估计和单次复用收益；原来已经安全命中的请求只计入加入条目前后的实际耗时差和质量差。容量不足时，比较同时计入被替换条目造成的覆盖和收益变化。`rag` 的版本稳定性已包含在上述机会数中，维护、补检及失败回退开销分别按实际发生的位置计入一次。

为控制估值开销，系统使用数量受限的近期代表性请求样本、分组统计和已获得的判官结果，对新候选进行异步或批量估值。容量不足时，先根据近期贡献和大小筛选少量潜在淘汰项，再评估候选与拟淘汰集合的整体影响。估值期间新条目保持候选状态，估值占用及模型调用纳入后台开销。

回答质量采用统一标准，对同一请求的候选回答与当前方案回答按相关性、正确性和完整性评分，并归一化至 \([0,1]\)。近期同类请求的评分差用于预测未来质量变化；静态来源作为可追溯属性记录，质量收益依据比较结果估计。样本不足时使用同类历史统计或零质量增益作为初始估计，并通过受限探索补充观测。`rag`、`act` 和 `plan` 以 1.2 的复用收益及对象有效性为基础，具有可测量的下游回答质量变化时再计入质量项。`plan` 的执行稳定性沿用 1.2 的执行耗时、回退和任务完成情况：执行成本差计入时间收益，任务完成率作为独立质量指标或约束。

### 1.3.3 价值驱动的准入、保留与淘汰

在线生成结果先按对象类型检查权限、版本、时效和内容有效性，再结合剩余有效期估计增量管理价值。容量充足时，预计增量价值为正的候选可准入；估计数据不足时使用有限预算进行短期试探，并遵循相同的有效性条件。需要较高成本确认的候选进入后台验证流程。

容量不足时，先处理已失效且无刷新计划的条目，再估计移除每个可用条目对整体价值造成的损失，并按单位空间损失从低到高选择拟淘汰集合。系统将“准入候选并移除拟淘汰集合”后的状态与当前集合进行整体比较，预计增量价值为正且满足容量约束时执行替换。周期性更新需求、年龄与依赖状态，重新评估条目价值并观察淘汰和重复写入。

静态 `resp` 由离线流程精选和更新；动态 `resp` 使用在线准入与淘汰策略。静态回答的提升项按动态层实际占用的指针和元数据空间计费，并保留对静态来源的引用。淘汰 `rag` 缓存副本后，`resp` 保留独立的来源版本信息，继续依据实际来源状态判断有效性。

### 1.3.4 价值驱动的异步验证与提升

对 `resp` 请求，先检索静态层；候选达到静态命中阈值 \(\tau_{static}\) 并满足 1.2 的权限、版本、时效及复用条件时直接返回。否则继续检索动态层，必要时调用后端生成回答。静态候选与请求的相似度落入灰区 \([\tau_{min},\tau_{static})\) 且通过可预先检查的权限、版本和时效条件时，系统在确定当前请求的服务路径后创建后台任务；后台处理不增加该请求对验证结果的等待。

对后台任务 \(j\)，先根据近期同类任务估计验证通过概率、通过后的增量管理价值及验证成本，以单位后台占用时间的预期净收益排序：

\[
P_j^{verify}=
\frac{\widehat p_j^{pass}\,\widehat{\Delta V}_j^{post}
-\lambda_B\widehat C_j^{verify}}
{\widehat T_j^{verify}}.
\]

其中，\(\widehat{\Delta V}_j^{post}\) 比较提升后的动态层与当前动态层，包含未来时间收益、质量变化及后续维护开销；\(\widehat C_j^{verify}\) 包含语义验证和质量比较所需的后台工作量，\(\widehat T_j^{verify}\) 为预计占用时间，并设置非零下限。通过率及质量改善优先使用同类请求和候选的近期观测；缺少样本时采用保守初值，初始预留最多 5% 的后台预算开展受限探索，比例通过验证集调整。正常任务按正优先级执行，队列进行去重、限长和并发控制。

后台判官先验证静态回答对当前请求的适用性，再依据统一标准比较静态回答与当前实际返回的动态或后端回答。通过验证后，系统结合比较结果、当前缓存状态和剩余有效期重新计算准入价值；若当前基线回答已变化且缺少相应质量评分，质量项使用保守估计或重新评分。已发生的验证成本用于此前的任务选择，后续准入比较计入尚未发生的成本。新键以当前请求为索引，指向相应静态回答及版本；提升覆盖已有动态项时，价值计算包含被覆盖回答的影响。验证结论绑定请求条件、权限范围、静态内容及依赖版本，后续近邻请求仍按 1.2 执行有效性检查。验证失败、超时或写入前发现来源版本变化时，候选保持不可直接复用或重新验证。

例如，某类请求已经由动态回答安全服务，静态回答提升后的额外时间节省接近零；若同一请求的质量比较显示静态回答更好，系统仍可结合未来需求和后台开销选择提升。若静态内容的允许年龄为 10 天，当前年龄为 8 天，提升后的价值按剩余 2 天内的机会估计。

`rag` 按证据支持和来源状态构造适合自身的后台验证任务，并使用相同的增量价值口径选择任务；`act` 和 `plan` 保留各自的有效性检查与按需处理流程。

### 1.3.5 依赖感知失效与选择性刷新

实验假设数据源可提供版本和更新事件。数据源更新时，系统更新已知版本，通过反向索引找到受影响的证据、回答及静态回答提升项，标记为待确认；读取路径依据当前已知版本检查条目。依赖链可以表示为：

```text
文档 D（版本变化） → 证据 R（待确认） → 回答 A（待确认）
                                  ↓
                   按增量价值选择后台刷新或按需重算
```

例如，客服政策文档更新后，系统可优先刷新近期需求高、预计收益为正的证据，再根据回答的需求和重生成成本决定是否刷新回答；需求较低时由后续请求触发检索或重算。更新静态精选回答时，由离线流程重新确认或替换其内容，并更新静态条目版本；关联的动态提升项需依据新版本重新确认。

对刷新任务 \(k\)，以按需重算为比较基线，估计刷新成功后的增量管理价值、成功概率和执行成本：

\[
P_k^{refresh}=
\frac{\widehat p_k^{success}\,\widehat{\Delta V}_k^{post}
-\lambda_B\widehat C_k^{refresh}}
{\widehat T_k^{refresh}}.
\]

其中，\(\widehat{\Delta V}_k^{post}\) 包含刷新后预计带来的时间及可测质量变化，并扣除未来维护开销；\(\widehat C_k^{refresh}\) 为本次刷新工作量。刷新任务与验证任务按同一价值口径竞争后台预算。顺序刷新证据与回答时，以已完成的上游状态重新估计下游收益，同一请求的收益和同一任务的成本各计一次。

后台任务保存依赖版本快照；提交前再次检查来源版本、权限及剩余时效。版本冲突时丢弃结果或重新排队。同一状态域使用版本条件提交；涉及外部缓存写入时保留版本标记，并在读取路径复核，以处理更新事件与提交并发。对无法获得可靠版本的来源，按业务明确允许的时效要求处理。

### 1.3.6 流式实现与反馈闭环

原型以请求、数据更新和后台任务完成作为事件，使用 Flink 状态记录条目元数据、内容年龄、近期需求、静态来源版本、依赖索引和待处理任务；外部工作池执行模型判断或回源刷新。任务携带唯一标识和版本快照，完成事件进行去重与版本检查；失败或超时后有限重试，超出预算时转为按需重算。通过 checkpoint 与恢复验证状态和待处理任务的可恢复性。

持续记录请求命中、实际复用耗时、回答质量比较、验证通过情况、来源更新、刷新与淘汰，以及后台线程占用和 token 开销，周期性更新需求、通过率、质量差和任务成本估计。在线请求始终按照 1.2 的权限、时效、版本及对象有效性条件选择复用、验证或重算。

## 1.4 实验评估与分析

围绕缓存价值建模、生命周期联合控制及二者协同机制开展分层次实验。首先评估动作条件价值与有效性判断；其次评估基于年龄、质量与依赖状态的准入、提升和维护；最后通过端到端实验分析整体收益及流式实现开销。

生命周期实验以 `resp`、`rag` 为重点，构造包含热点变化、来源版本更新和时效要求的请求流，记录证据与回答的来源。按时间划分历史、验证和测试数据：历史数据用于构建静态精选层和初始统计，验证集用于确定价值权重及策略参数，测试集用于报告最终结果。各方法使用相同的请求与更新序列、在线检索器、缓存容量、时效规则和后台资源预算，采用双层结构的方法使用相同的静态候选。

对照方法包括双层结构下的 LRU/TTL 动态管理、参考 Cortex 的成本感知淘汰、Krites 式静态与动态双层及异步验证提升、参考 FinCacheServe 的依赖失效与按需重算，以及本文方案。Krites 式对照采用相同静态层、灰区和语义判官，按到达顺序在后台资源预算内处理灰区任务，验证通过后使用 LRU/TTL 管理动态层；本文方案的额外质量比较开销计入资源统计。没有公开实现时，基于论文描述构建近似对照并标明实现方式。

消融实验分别考察价值驱动准入与任务排序、质量收益项、年龄进入未来机会估计，以及依赖感知的选择性刷新；将主动刷新与按需重算比较。年龄消融保留一致的在线时效检查，仅移除价值估计中的剩余有效期因素；各组保持相同权限和版本有效性条件。改变后台预算、缓存大小、来源更新频率和请求热点变化速度，评估各机制的独立作用与组合效果。

指标包括回答质量、静态来源回答覆盖比例、有效命中率、端到端平均及尾部时延、缓存占用、过期复用次数、后台线程占用、模型调用与 token 开销、队列积压和刷新后未使用比例。回答质量由统一标准评分，并对实际判官结果进行人工或可信标注抽样比较；静态来源覆盖与质量分开报告。记录新增节省及提升前后的质量差，后台验证、评分、候选构建和回放开销均计入资源统计。

使用可控真值检验灰区验证、缓存已命中时的质量提升、年龄与剩余有效期、依赖更新、异步任务提交时的版本冲突和失败恢复；特别检查静态回答提升后沿用源内容年龄、近邻请求执行在线有效性检查，以及淘汰缓存副本后来源版本记录仍可用于有效性判断。报告质量权重和后台成本权重的敏感性，并比较预计收益与实际收益。
