## 思路记录

- 小红书的流式推理系统是针对单轮对话的，考虑将场景迁移至多轮 Agent 会话，就有会话结果 & 知识库复用
- 把 Flink 状态用作 Agent 多轮会话/跨会话的知识库的缓存，缓存最近最常访问的知识资料，拼接上下文时直接从状态中获取，而不需要从远端知识库拉取
- 受启明师兄论文中的短路读思路启发，考虑复用到 LLM 推理场景 (参考论文 vCache)

## 整体框架

面向 SLO 与知识库缓存优化的流式 Agent 推理系统

### 点 1：面向多轮上下文的推理时延预测

目标：尽量高效、准确地预测推理长度与端到端时延

端到端时延 = 排队时延 + 推理时延

- 推理长度预测
  - 根据当前 prompt、会话上下文长度、RAG 文档长度，预测输出 token 数的区间
  - 使用轻量机器学习算法 (同小红书项目)
- 端到端时延预测
  - 结合输出 token 数区间、批次大小、并行度、队列长度（新增）预测 TTFT、端到端时延 P50 / P95
  - 使用轻量机器学习算法预测推理时延（同小红书项目）
  - 排队时延：当前请求在队列中所处位置及前序请求的预测时延，是端到端时延中的排队时延

### 点 2：面向 SLO 的推理短路与语义库 & 推理参数调优

目标：保证满足 SLO 的情况下最小化语义库缓存容量以及推理并行度 ( Flink 算子并行度)，尽可能降低成本；负载上升时提升语义库缓存容量与推理并行度，尽可能满足 SLO；对于相似度达到阈值的请求，复用请求回复从而节省 GPU

- 推理短路（推理缓存复用）
  - 计算两个 prompt 的相似度（embedding 相似度 + TODO 另一个相似度）
  - 相似度达到阈值则该 prompt 直接短路到专门的对话明细存储算子，拿到会话结果后直接返回给用户，节省一次拼接上下文和推理的过程
  - 借鉴 vCache 算法，根据历史探索结果估计候选响应的正确复用概率（简版实现，且要贴合流处理系统场景）
    - vCache 解决的问题：两个问题语义相似时，系统怎样在“尽量复用历史回答”的同时，把返回错误回答的概率控制在用户指定范围内。

```
Source → StateFetcher → Batcher → Inferencer → Sink
            ↑ 升级为「语义记忆算子」（embedding 索引 + 语义检索）
            ↑ 语义命中 → 短路 Batcher+Inferencer（省 GPU）
```

  - Flink 状态语义库缓存容量调优（基于小红书缓存替换算法改进）
    - 从当前配置开始扩/缩容，直到能满足/不再能满足 SLO
  - 推理并行度及批次大小调优 （利用推理时间）
    - 从当前配置开始扩/缩容，直到能满足/不再能满足 SLO

### 点 3：面向语义命中的语义缓存淘汰算法（基于中移动项目研究）

目标：基于集成学习/高效数据结构对 Flink 状态语义缓存进行淘汰，在 2 给定的缓存容量下，优先预取哪些语义资料、优先保留已有的哪些语义资料能最大化语义缓存的命中率，从而减少语义资料检索召回时间，降低端到端时延

- 基于集成学习与高效数据结构的语义库缓存项替换算法
  - 基于集成学习 LightGBM GPU (可替换其他算法)
    - 根据 prompt、访问间隔等属性为语义资料预测访问概率，并归一化得到得分
  - 基于高效数据结构 Count-Min Sketch / Cuckoo filter (可替换其他数据结构)
    - 根据缓存项的事实访问频次、访问波动按规则得到访问趋势，并归一化得到得分
  - 两种方向的得分以权重相加，归一化后保留最后得分最高的 n 个语义资料（语义容量内）
  - 每次最多替换缓存中已有语义资料的 25%，防止抖动
