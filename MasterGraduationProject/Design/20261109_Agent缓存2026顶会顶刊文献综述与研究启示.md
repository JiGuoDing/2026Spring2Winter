> 文档性质：独立文献调研与新研究建议。  
> 检索与核验日期：2026-11-09。  
> CCF 等级依据：CCF 2022 推荐目录。  
> 研究边界：只讨论 Agent 执行过程中的逻辑缓存对象，包括语义回答、RAG 证据、工具结果、计划模板、会话摘要和事实记忆；不把 KV、prefix KV、attention cache 或 prefill 加速作为核心研究对象。

## 0. 结论摘要

2026 年与 Agent 缓存相关的研究已经从“相同请求复用”明显转向四类问题：

1. **语义命中是否可信**：vCache、MVR-cache、LaCache、缓存投毒研究分别从逐条目错误率保证、多向量匹配、响应侧验证和对抗攻击角度处理正确性。
2. **缓存集合如何优化**：INFOCOM 2026 与 MobiHoc 2026 的工作把语义缓存从阈值问题推进到带失配成本、未知分布、连续查询空间和切换成本的优化问题。
3. **缓存生命周期如何管理**：Cortex、RAG-Cache、TVCACHE、C-DIC 以及一批 Agent memory 工作分别覆盖知识缓存、工具结果、上下文压缩、记忆合并和失效更新。
4. **缓存如何评测与治理**：Closing the Operational Gap、NDSS、LDPCache 等工作说明命中率、准确率和原始成本都不够，还要看可用命中、陈旧风险、安全风险和隐私预算。

对当前毕业设计第一章最有利的定位不是“再做一个多层缓存”，而是：

> **面向流式 Agent 的依赖感知缓存价值建模与生命周期控制。**

核心问题应从“相似度阈值是多少”推进为：

- 这个缓存对象的未来复用概率有多大？
- 命中它能节省多少真实工作，在动态负载下这些工作值多少钱？
- 它的语义、来源、会话状态和工具环境是否仍然有效？
- 验证、刷新、迁移和错误复用分别引入多少管理税与风险？
- 在容量和质量预算约束下，什么时候准入、复用、刷新、降级和淘汰？

## 1. 收录与分类口径

### 1.1 缓存对象

本文使用以下五类逻辑对象描述 Agent 缓存：

| 类型 | 典型对象 | 主要收益 | 主要风险 |
|:--|:--|:--|:--|
| `resp` | 最终回答、回答模板、生成程序 | 短路完整推理或降低模型档位 | 语义误命中、答案过时、缓存投毒 |
| `rag` | 文档块、检索结果、知识子图、远端查询结果 | 避免重复检索、远端 I/O 和上下文拼装 | 来源版本变化、权限越界、证据不足 |
| `act` | 工具调用结果、执行观察、API 返回 | 避免重复调用和等待 | 环境状态不同导致相同调用产生不同结果 |
| `ctx` | 会话摘要、事实/约束、工作记忆、计划草案 | 减少上下文长度和重复压缩 | 摘要失真、事实冲突、旧状态未失效 |
| `control` | 准入、验证、刷新、淘汰、分层和路由决策 | 把缓存价值转化为系统动作 | 管理税、策略抖动、负载变化下失效 |

## 7. 现有第一章设计的主要缺口

### 7.1 从“命中价值”转向“净复用价值”

vCache 和 MVR-cache 解决的是“是否应当命中”，INFOCOM/MobiHoc 解决的是“缓存集合如何优化”，但它们大多把回源成本视为相对稳定的参数。第一章可以把计算资源稀缺性显式引入：

- 低负载时，一次命中主要节省时延，GPU 影子价格较低。
- 高负载时，同样的命中节省的是稀缺 GPU 时间，价值上升。
- 但高负载也会提高刷新和重算成本，不能简单使用“越忙越激进复用”的一条规则。

这使缓存价值成为系统状态 `c` 的函数，而不是对象的静态属性。

### 7.2 从“语义相似”转向“依赖有效”

2026 年文献已经给出三个不同层次的有效性信号：

- `resp`：LaCache 和缓存投毒研究表明，相似查询可能对应恶意或不可复用响应。
- `rag`：Cortex 和 RAG-Cache 证明需要知识检索索引和成本感知淘汰，但来源版本仍是弱项。
- `act`：TVCACHE 证明相同工具调用只有在完整执行历史一致时才能复用结果。

第一章应把缓存 key 从 `semantic_key` 扩展为 `semantic_key + scope + version_vector + dependency_closure`。

### 7.3 从“固定淘汰”转向“风险预算下的生命周期”

现有工作分别覆盖：

- 淘汰：LCFU、HARF、prefix/LRU 类替换。
- 刷新：C-DIC 的 revise/write-back。
- 验证：vCache、Cortex、LaCache。
- 压缩：MemForest、MemCoRe、ACON、COMI。
- 恢复：MemCoRe、Sculptor。

但几乎没有工作统一回答“准入、复用、验证、刷新、降级、淘汰”六个动作之间的资源竞争关系。

### 7.4 从“单对象”转向“依赖闭包和失效传播”

建议把刷新成本写成：

```text
C_refresh_total(i) =
  重算(i) 的成本
  + 因 i 变化而失效的下游对象期望重建成本
  + 刷新期间的短期质量损失
```

否则模型会系统性低估热对象刷新成本，也会忽略“刷新一个摘要会杀死多个回答缓存命中”的耦合。

### 7.5 从“离线命中率”转向“流式有效 goodput”

Closing the Operational Gap 和 ChurnBench 说明，离线排序好并不等于在线可用。第一章至少需要同时观察：

- 有效命中率：通过验证且没有过期/越权的命中比例。
- 质量违约率：错误复用和陈旧复用占总请求比例。
- 净节省：节省的 GPU/检索资源减去验证、刷新、迁移和存储成本。
- 决策后悔：相对知道未来复用结果的 Oracle 的损失。
- 负载扰动下的恢复时间：扩缩容或路由变化后，命中率和 goodput 的恢复速度。

## 8. 建议的研究框架

### 8.1 建议标题

**面向流式 Agent 的依赖感知缓存价值建模与生命周期控制**

该标题比“Agent 多级缓存管理”更聚焦：核心不是堆叠缓存层，而是研究日志状态、版本依赖、质量风险与资源约束如何共同决定缓存价值。

### 8.2 三个研究问题

1. **净价值估计**：如何为一个带依赖闭包和版本状态的 Agent 缓存对象估计未来复用概率、工作节省、验证成本、陈旧风险和安全风险？
2. **生命周期控制**：在容量、质量、隐私和新鲜度约束下，如何联合决定准入、复用、验证、刷新、降级和淘汰？
3. **流式状态落地**：如何用 Flink keyed state、timer、broadcast dependency index、checkpoint 和 rescale 实现上述策略，并量化缓存迁移与冷启动代价？

### 8.3 统一的缓存对象接口

建议在第一章内部约定如下逻辑结构，具体实现可映射到 Flink state：

```text
CacheItem {
  id,
  layer,                    // resp | rag | act | ctx
  artifact_type,
  tenant_id,
  session_id,
  semantic_scope,           // 会话、租户、知识域或全局
  content_hash,
  version_vector,
  source_refs[],            // 文档、工具、上游缓存项
  dependency_refs[],        // 失效传播依赖
  created_at,
  last_access_at,
  ttl,
  fidelity,                 // full | compact | summary | trace
  size_bytes,
  recompute_cost,
  verify_cost,
  access_stats,
  risk_state,
  provenance
}
```

```text
CacheAction = ADMIT | REUSE | VERIFY_THEN_REUSE
            | REFRESH | DEMOTE | EVICT | RECOMPUTE
```

```text
ValueEstimate {
  p_use_now,
  p_use_horizon,
  saved_work,
  shadow_price,
  risk: {q_wrong, q_stale, q_security, q_privacy},
  cost: {verify, hold, refresh, churn},
  net_value: {p10, p50, p90},
  action_hint,
  reason_codes[]
}
```

### 8.4 扩展价值函数

```text
V_i(t, c) =
    p_use · [ λ(ρ) · W_saved + β · latency_saved ]
  − C_verify
  − C_hold
  − C_refresh_total
  − C_churn
  − q_wrong · L_answer
  − q_stale · L_stale
  − q_security · L_security
  − q_privacy · L_privacy
```

其中：

- `λ(ρ)` 是随系统利用率和容量约束变化的资源影子价格。
- `C_refresh_total` 包含下游失效和重建成本。
- `q_security/q_privacy` 不是一般准确率风险，而是租户隔离、投毒和隐私预算风险。
- 所有成本最终统一到 GPU-ms、检索调用、token 或可比较的归一化成本。

### 8.5 建议的 MVP

第一阶段不要同时铺开所有缓存对象：

1. **主对象 `resp`**：复用 vCache/MVR/INFOCOM 的强基线，研究风险预算、容量和负载价格联合决策。
2. **第二对象 `rag`**：复用 Cortex/RAG-Cache 的结构，引入文档版本、来源和刷新。
3. **`ctx` 作为依赖源**：记录会话摘要、事实和版本的变更，不先做完整通用记忆系统。
4. **`act` 作为扩展实验**：用 TVCACHE 式执行历史前缀验证工具结果复用。
5. **计划缓存作为后续扩展**：参考 AgenticCache 和 SemanticALLI，不进入第一版 MVP。

## 9. 实验与验证建议

### 9.1 预实验

| 预实验 | 问题 | 不通过时的处理 |
|:--|:--|:--|
| P1 复用机会 | 三类对象的语义/结构重复率是否足以产生收益 | 若回答复用低于 5%，重心转向 RAG/上下文状态 |
| P2 验证税 | judger、verifier 或 ACL 检查是否低于命中收益 | 对低价值对象只启用精确匹配或跳过验证 |
| P3 价值淘汰 | 净价值策略是否显著优于 LRU/LFU/LCFU/HARF | 降低淘汰策略权重，把贡献收缩到价值建模和刷新 |
| P4 负载价格 | 负载变化是否改变最优缓存动作 | 若不变，删除显式 λ，退化为固定容量策略 |
| P5 失效传播 | 刷新连带损失是否足以改变刷新时机 | 若很小，可将依赖闭包限制在 `rag → resp` |

### 9.2 对比基线

- 无缓存与精确匹配缓存。
- LRU、LFU、GDSF、LCFU、HARF。
- vCache 式逐条目阈值。
- INFOCOM 式带失配成本的缓存集合优化。
- Cortex 式语义验证 + 成本感知淘汰。
- TVCACHE 式执行前缀匹配。

### 9.3 核心指标

- 有效命中率与命中精度。
- 净 GPU-ms、检索调用和 token 节省。
- 质量违约率、陈旧复用率和安全违规率。
- 相对 Oracle 的决策后悔。
- p50/p95 时延和单位资源 goodput。
- checkpoint/rescale 后的命中率与 goodput 恢复时间。

### 9.4 消融

至少做以下消融：

- 去掉负载影子价格 `λ(ρ)`。
- 去掉依赖闭包和版本向量。
- 固定 TTL 替代刷新策略。
- 去掉质量风险预算。
- 去掉安全/隐私风险项。
- 去掉跨层容量分配。

## 10. 与现有项目材料的关系

### 10.1 保留的部分

现有材料中以下判断仍然成立：

- 命中率不是最终目标，应使用净收益和有效复用率。
- `ctx/rag/resp` 三层可以作为分析框架。
- 价值建模与生命周期控制应组成一个闭环。
- 影子价格、质量预算、指纹稳定性和刷新—命中耦合具有辨识度。
- MVP 应先度量复用机会，再决定是否实现复杂模型。

### 10.2 需要调整的部分

- 把 KV/prefix cache 文献集中放入边界小节，不与逻辑缓存主表混排。
- 把 `resp` 研究从“相似度阈值”扩展到“验证、风险、集合优化和负载价格”。
- 把 `rag` 的风险从“知识过期”细化为来源版本、依赖传播、权限和刷新成本。
- 把 `act` 独立视为依赖完整执行历史的状态对象，不把它简单归入普通 RAG 文档。
- 把 `ctx` 的压缩、降级和恢复纳入生命周期动作，而不是只作为 prompt 工程。
- 在评测中增加 Operational Retention、stale error、security violation 和 rescale recovery。

## 11. 证据边界与后续核验

1. 本文主表按 2026 年会议/期刊版本统计，不把 arXiv 首发时间当作正式发表时间。
2. NeurIPS 2026 和 MobiHoc 2026 的若干论文在本文截止日期前已录用，但会议尚未召开；正式引用时应再次核对 camera-ready 版本。
3. EMNLP 2026 非主会论文单独标注 Industry/Findings，不用它们替代 CCF-B 主会证据。
4. TVCACHE 的完整工具历史匹配解决的是“相同环境状态”问题，不证明所有工具结果都可跨用户、跨租户复用。
5. vCache 和 MVR-cache 的错误率/正确性保证依赖各自的任务定义和评估集；不能直接外推到 RAG 事实正确性、工具副作用或安全攻击。
6. Cortex 的 LCFU 是启发式价值密度，不是经过在线价格校准的最优决策；这正好给第一章留下“负载影子价格”的研究空间。
7. 预印本中的 FreshCache、FinCacheServe、ChurnBench 和 Workload-Aware Caching 应继续跟踪正式版本；在正式录用前不应作为已有顶会结论引用。

---

**一句话总结：**

2026 年文献已经分别证明“语义缓存需要质量控制”“RAG/工具缓存需要依赖验证”“Agent 记忆需要生命周期管理”，但还没有把它们统一成一个面向流式 Agent 的净价值与依赖感知控制框架。这正是第一章可以继续深化、且与后续算力配置和路由章节自然衔接的位置。
