# 毕业论文设计简洁版

## 1. 研究题目

面向地球物理数据的流式 RAG 推理系统设计与优化

## 2. 研究背景

地球物理领域的数据具有来源多样、空间分布广泛、数据规模大、实时性要求高等特点。传统离线式数据处理与问答系统难以及时吸收新采集或新计算的数据，也难以在高并发场景下稳定支撑大模型推理服务。

因此，本文设计一个基于 Apache Flink 的流式智能处理框架，将实时数据接入、地球物理知识库更新、RAG 检索增强生成、大模型推理、系统负载监控与自适应重配置等能力统一到流式计算体系中。

## 3. 总体设计思路

系统整体由两个 Flink 任务组成：

1. **第一个 Flink 任务：数据接入、知识更新与 Prompt 构造**
   - 接收用户输入；
   - 接收来自多个 Kafka 的地球物理采集数据或计算数据；
   - 对多源地球物理数据进行清洗、关联和状态管理；
   - 将新数据整理后写入地球物理知识库；
   - 根据用户问题从知识库中检索相关资料，构造 RAG Prompt；
   - 对 Prompt 请求进行攒批后写入下游 Kafka。

2. **第二个 Flink 任务：批量推理、结果输出与系统自适应调度**
   - 从 Kafka 接收上游批量请求；
   - 调用推理框架执行大模型推理；
   - 将推理结果写入下游 Kafka；
   - 持续监控系统负载指标；
   - 使用轻量级 Agent 分析系统状态，并在必要时触发系统重配置。

## 4. 第一个 Flink 任务设计

### 4.1 输入数据

第一个 Flink 任务包含两类输入：

- **用户输入流**
  - 用户提出的自然语言问题；
  - 用于触发 RAG 检索与 Prompt 构造。

- **地球物理数据流**
  - 新采集数据；
  - 新计算数据；
  - 可来自多个 Kafka Topic；
  - 数据可能包含时间、空间位置、测线、测点、深度、物性参数、计算结果等信息。

### 4.2 多源地球物理数据 Join 优化

当多个数据源之间存在关联需求时，系统采用双流 Join 模板进行数据拼接。

针对地球物理数据空间分布广泛的特点，本文考虑在 Join 过程中引入空间分区与状态访问优化，例如：

- 基于空间网格、GeoHash 或 Hilbert 曲线进行空间编码；
- 将空间位置相近的数据分配到相同或相邻 Key 中；
- 减少无效 Join 搜索范围；
- 优化 Flink 状态访问路径；
- 提高 Join 吞吐率，降低端到端时延。

该部分可结合已有项目中的状态存取优化方法，重点说明其对 Join 性能的提升作用。

### 4.3 RAG 算子设计

系统中设置专门的 RAG 算子，承担两类功能：

1. **面向用户问题的检索增强**
   - 接收用户输入；
   - 从地球物理知识库中检索相关资料；
   - 将检索结果作为上下文与用户问题拼接；
   - 输出完整 Prompt 给下游推理任务。

2. **面向新数据的知识库更新**
   - 接收实时地球物理数据；
   - 对数据进行清洗、结构化、切分和向量化；
   - 将处理后的数据写入地球物理知识库。

### 4.4 多级缓存机制

为提高 RAG 检索效率，RAG 算子中设计多级缓存机制：

- 一级缓存：Flink 算子本地缓存；
- 二级缓存：外部高速缓存；
- 三级存储：向量数据库或长期知识库。

缓存替换策略可借鉴已有项目中的基于预测的缓存替换与扩缩容策略，根据访问频率、访问趋势、语义相似请求等信息预测数据未来被访问的概率，从而提高缓存命中率。

### 4.5 可选：在线微调算子

系统可进一步设计模型微调算子，用于接收高质量增量样本，对模型进行实时或准实时微调。

该部分作为扩展模块，需要重点考虑：

- 微调数据筛选；
- 训练稳定性；
- 推理服务与训练服务的资源隔离；
- 模型版本管理与回滚机制。

### 4.6 批量输出

在第一个 Flink 任务的 Sink 算子中，对构造好的 Prompt 请求进行攒批，并将批次请求写入下游 Kafka 队列，供第二个 Flink 任务进行推理。

## 5. 第二个 Flink 任务设计

### 5.1 输入

第二个 Flink 任务从上游 Kafka 队列读取批次 Prompt 请求。

### 5.2 推理算子

Source 将批次请求发送到推理算子，推理算子内部启动或调用大模型推理框架完成推理。

推理算子主要负责：

- 批次请求解析；
- 调用推理引擎；
- 获取生成结果；
- 将结果发送给下游 Sink。

### 5.3 输出与监控

Sink 算子接收推理结果并写入下游 Kafka 队列。

同时，Sink 算子持续监控系统指标，例如：

- 请求吞吐率；
- 推理时延；
- GPU 利用率；
- 显存占用；
- Kafka 堆积量；
- Flink 反压情况；
- 算子处理速率。

这些指标会被记录为系统负载日志，并持久化到状态或外部存储中。

### 5.4 Agent 自适应重配置

在 Sink 算子中部署一个轻量级 Agent 服务，用于分析当前系统负载情况。

Agent 的输入包括：

- 实时系统指标；
- 历史负载日志；
- 当前资源配置；
- 请求队列状态。

Agent 的输出包括：

- 是否需要重配置；
- 推荐的 batch size；
- 推荐的并行度；
- 推荐的缓存容量；
- 推荐的推理实例数量；
- 是否需要扩缩容。

当 Agent 判断系统需要调整时，系统基于已有项目中的联调方法触发配置更新，以实现自适应调度。

## 6. 预期研究内容

本文主要研究以下内容：

1. 面向地球物理多源数据的 Flink 实时处理框架；
2. 面向空间分布数据的双流 Join 状态访问优化；
3. 面向地球物理知识更新的流式 RAG 算子设计；
4. 基于预测的多级缓存替换与扩缩容机制；
5. 面向大模型推理服务的批处理与吞吐优化；
6. 基于 Agent 的系统负载分析与自适应重配置。

## 7. 预期创新点

1. 将地球物理实时数据接入、知识库更新和 RAG 推理统一到 Flink 流式计算框架中；
2. 针对地球物理数据空间分布广泛的特点，设计空间感知的 Join 与状态访问优化方法；
3. 在 RAG 算子中引入基于预测的多级缓存机制，提高检索效率；
4. 在推理任务中结合批处理和系统负载监控，提高推理吞吐率；
5. 使用轻量级 Agent 分析系统负载并触发自适应重配置。

## 8. 系统流程总结

整体流程如下：

1. 用户输入和实时地球物理数据进入第一个 Flink 任务；
2. 多源数据经过清洗、Join 和状态优化后进入知识库更新流程；
3. 用户问题经过 RAG 检索后构造完整 Prompt；
4. Prompt 在 Sink 中被攒批并写入 Kafka；
5. 第二个 Flink 任务读取批次请求并调用推理框架；
6. 推理结果写入下游 Kafka；
7. 系统持续监控负载；
8. Agent 根据负载情况触发系统重配置。
