# ABCD-Cache：基于 ABCD 的流式缓存实验数据集改造方案

> 定位：ABCD 原始数据**不改动**；在其上叠加派生数据包（事件流 + 状态/政策版本 + 账本 + 模拟器），形成第一章的主实验基准 StreamCache-Bench T1。
> 依据：ABCD v1.1 全量（10,042 通对话）本地实测统计；2026-11-18。

---

## 0. 结论

**能改，而且改造后能覆盖 E1–E6 的主体。** 关键是四个判断：

1. **不重写内容，只加壳**：ABCD 提供"人话 + 场景真值 + 政策文档 + 动作真值"；缺的是时间、版本、权限、账本、模拟器——全部以**派生层**形式加，原始数据保持可追溯。
2. **请求单位要重定义**：ABCD 是"轮次级"语料，不是请求流。应定义为 **request = 一次 agent 处理步**（由客户发言触发），每个请求可含 0–3 次对象 lookup。这样 10,042 会话 → 约 9.5 万请求、约 15.5 万次 lookup。
3. **在线可见性要分离**：`scenario` 是上帝视角真值，不能直接暴露给缓存策略；在线只能看到对话历史与已执行动作的返回，`scenario` 只进模拟器与评测。否则 `act` 缓存变成"直接查答案"，实验失效。
4. **改造必须可复现、可审计**：builder + 固定 seed + append-only ledger + 统计校验报告；论文里把每个构造字段标出来。

## 1. 目标数据包

```text
abcd-cache/
├── raw/abcd_v1.1.json            # 原始数据，只读
├── state/
│   ├── scenario_states.jsonl     # 每会话的状态快照 + 版本
│   ├── state_events.jsonl        # 订单/会员/ACL 变化事件
├── policy/
│   ├── policy_docs.jsonl         # 条款级文档（doc_id/version/effective_from/acl）
│   ├── policy_versions/          # v1..v5 内容
│   └── policy_rules.yaml         # 规则引擎可执行版本
├── stream/
│   ├── request_stream.parquet    # 请求事件（ts/session/tenant/role/regime）
│   └── session_index.parquet
├── objects/
│   ├── resp.jsonl / rag.jsonl / act.jsonl / plan.jsonl
├── labels/
│   ├── ledger.parquet            # (req, object) → safe/reason/gold/quality/age
│   └── split.json                # 历史/验证/测试切分
├── sim/
│   └── simulator.py              # 状态→动作返回；政策→合法性；分支重放
├── cost/cost_profile.json        # 实测或标定的每操作成本
└── build/                        # 全部构造脚本 + seed + 统计校验
```

## 2. 请求流的定义与规模（本地实测）

| 指标 | 实测值 | 说明 |
|---|---|---|
| 会话数 | 10,042（8,034/1,004/1,004） | 按会话切分，避免答案泄漏 |
| 客户发言轮 | 89,372 | 可作为"原始请求"，但上下文相关 |
| **agent 处理步（建议的 request 单位）** | **95,129** | 每步触发一次 resp lookup，可能还有 act/rag/plan |
| 动作调用（act lookup） | **36,482**（16.5% 的轮次，3.63/会话） | 其中**无参数调用 11,327 次（31.0%）**，全局可复用 |
| 政策/检索动作（rag lookup） | **12,924** | search-faq、select-faq、ask-the-oracle、validate-purchase、membership 等 |
| 计划选择（plan lookup） | **10,042**（每会话一次 + 重规划） | 55 个意图、2,438 个 (intent, action-sequence) 组合 |
| 合计 lookup | **约 154,577** | 对 E2 容量实验足够 |
| 对话长度 | 均值 22.0 轮（中位 21，p90 32，最大 75） | 单会话长，LLM 实验需抽样 |
| 客户/客服发言长度 | 6.1 / 10.1 词 | 短文本，适合固定模型与低成本标定 |

**时间线构造**：会话到达用 Chutes inter-arrival 缩放；会话内轮间隔从"客户思考时间"分布抽样（对数正态，中位 6–10 s）；10,042 会话铺到 4–8 周逻辑时间；3 个热点 regime（常态/促销/政策变更期）按子流程需求切换。

## 3. 四类对象抽取

| 对象 | 来源 | 规模 | key | value | 依赖 | 真值 |
|---|---|---|---|---|---|---|
| `resp` | agent 去词化发言（95,129 轮） | 58,657 个不同模板文本（38% 有重复） | 意图簇 + 下一步 + 状态指纹 | 模板文本 + 槽值 | 政策版本、订单状态 | CDS 目标句 + 动作一致性 |
| `rag` | guidelines.json（55 子流程 × 4.64 动作 = **255 条动作条款** + **48 条 FAQ** ≈ 303 条，扩展到 400–600 块） | 303→600 | 查询意图 + 会员等级 + 动作 | 政策条款 | 文档版本 + 权限 | 金标条款 ID + 动作合法性 |
| `act` | 动作轮（36,482 次） | 8,734 个唯一 (动作, 槽值) | 动作按钮 + 规范化槽值 + 状态版本 | 系统返回文本 | 状态版本、工具版本 | AST 动作/槽值 + 状态一致性 |
| `plan` | 动作序列 | 55 意图；2,438 个 (意图,序列) 对；2-gram 片段 515 个、3-gram 1,754 个 | 意图 + 状态类 | 动作序列/模板 | 政策版本、前置条件 | 金标动作序列 |

**注意三个容易踩的坑：**

1. **在线不准用 gold intent 当 key**。意图标签只能用于评测；在线 key 必须由请求文本/embedding 生成（否则缓存命中率被人为抬高）。
2. **`scenario` 不能直接给策略**。策略只能看到对话历史与已执行动作的返回，状态由模拟器逐步揭示。
3. **96 vs 55**：`scenario.subflow` 有 96 个题面变体（如 `timing_4`），`targets[0]` 才是 55 个粗意图。plan 用 55，FAQ 题面用 96。

## 4. 状态模型与模拟器

- 状态 = {会员等级, 订单状态, 购买时间, 商品, 退货资格, ACL 角色} 的快照，带 `state_version`。
- **可见性**：客户说的话、agent 说过的、已执行动作的返回可见；`scenario` 全集不可见。
- 模拟器接口：
  - `do(action, params, state) -> output`（act 的 value + 副作用校验）
  - `legal(action_sequence, policy_version, state) -> bool`（政策合法性）
  - `score(action_sequence, gold) -> quality`（AST/CDS 兼容）
  - `snapshot()/restore()`（分支配对重放）
- **分支重放**：同一 request 的初始状态可分别跑 reuse 分支与 recompute 分支，测真实差值。这是 1.4.7 的硬要求，也是把静态语料变成可实验数据的关键。

## 5. 政策版本与规则引擎

`guidelines.json` 拆成条款级文档（`doc_id = flow/subflow/action`），原始为 v1；每轮编辑生成 v2–v5，带 `effective_from`。编辑类型与实测 fan-out：

| 编辑类型 | 例子 | 受影响会话（实测口径） | 适用实验 |
|---|---|---|---|
| 阈值型 | bronze 退货窗口 90→60 天 | 单个意图 30–361 会话 | E5 细粒度失效 |
| 流程型 | 退款流程新增/删除/重排一个必需动作 | 单个子流程全部（最多 361）或整个 flow（713–1,094） | **E5 主实验（样本量最够）** |
| 权限型 | 某等级/角色不再允许延期 | membership 动作 1,434 次；政策敏感会话 4,463（44%） | 权限检查 + 失效 |
| 文档型 | FAQ 答案从 7 天改为 14 天 | FAQ 检索动作约 4,100 次 | rag 缓存更新 |
| 参数型 | 默认退款额 $50→$40 | offer-refund 826 次 | act/rag 值变化 |

**规则引擎**：每个子流程实现"政策版本 × 状态 → 允许动作序列/槽值"；对 55 个子流程逐一实现工作量大，建议先覆盖 `product_defect`（1,070）、`shipping_issue`（1,020）、`order_issue`（1,040）= 3,130 会话（31%），再扩展。**必须审计**：抽 200 条双人标注，报与规则引擎一致率/κ。原来的 policy 文本存在"或"条件（如 receipt/packaging 可替代期限），规则化时会出现歧义——这正是最需要审计的地方。

**防"送分"设计**：更新事件对**所有方法可见**（同一硬有效性门），账本标签只用于评测；不同方法只在"价值估计/刷新调度/准入淘汰"上不同。否则数据集会把本文方法的优势编码进去。

## 6. 权限与租户（合成）

- 10 个虚构客户 → 20 个租户（每个客户两个角色）；角色 = {一线, 资深, 主管}；
- 文档与动作加 `acl_scope`；注入 2 轮 ACL 变更（角色撤销/租户迁移）；
- 标签原因增加 `acl_denied`；论文明确"权限为合成"。
- 公开数据里权限维度基本为空（SSC 的 InternalQA 不公开），这是必须声明的边界。

---

## 7. 重复与近重复注入

**ABCD 的天然重复（实测）**：

- 动作调用：36,482 次 → 8,734 个唯一 (动作, 槽值)，唯一率 23.9%；
- 动作序列：1,712 个不同序列 / 10,042 会话（83% 落在已有序列上）；
- 客户发言精确重复 45.6%，但**由去词化占位符主导**（"order id: <order_id>" 1,445 次、"yes" 1,147 次），通用寒暄仅 7.9%；
- agent 回复模板：58,657 / 95,129（38% 有重复），头部是"还有别的可以帮您吗"这类。

**结论**：raw repeat 不能直接当语义缓存命中率。必须做三档：

- **R0 天然**：仅用非占位符、非通用寒暄的重复；
- **R1 簇内重采样**：只改重复次数；
- **R2 受控改写**：客户问题用 LLM 改写（记录模型/prompt），按 λ∈{0,10,25,50}% 注入；报告注入对相似度不高于天然对、换生成器重跑、λ=0 臂。

**计划模板复用**用 n-gram 片段而不是整段序列：2-gram 有 515 个不同片段、总频次 26,440；3-gram 1,754 个/16,573 次。片段级复用的样本量和真实性都更好。

## 8. 标签与账本

每个 `(request, candidate_object)` 一条：

```json
{"req_id":"r000001","object_id":"act_000123","type":"act",
 "safe":0,"reason":"stale_state","detail":"order_status: delivered->refunded",
 "gold_action":"offer-refund","gold_values":["50"],"gold_evidence":["policy_pd_07_v3"],
 "quality":1,"age_s":86400,"state_version":3,"policy_version":4}
```

- `reason`：`safe / entity_mismatch / policy_superseded / stale_state / acl_denied / insufficient_evidence / irrelevant`；
- **三层分离**：动作级（AST）、证据级（条款）、新鲜度级（政策/状态版本）；`resp` 质量另用动作一致性 + judge，不与动作真值混报；
- **change ≠ harm**：政策文本变了不等于答案/动作变了；两列都报（变更率、影响率）；
- 账本只追加，任何时刻 T 的真值由账本 + 版本区间重算。

---

## 9. 成本模型

ABCD 没有时延。做法：
1. 用本地固定模型（如 Qwen2.5-7B/14B）+ 固定 prompt，实测 200–500 条请求的生成/检索/判断耗时，得到 `cost_profile`（p50/p95、token 数、GPU 秒）；
2. 其余请求用查表模拟，并在论文里分开报"实测子集"与"模拟全集"；
3. 缓存命中分支不真实生成，用"历史 gold + 查表成本"近似——这是构造偏差，必须声明。

## 10. 统计校验（构造完必须做）

| 校验项 | 目标 | 方法 |
|---|---|---|
| 会话长度分布 | 与 ABCD 原始一致（构造不应改变它） | KS 检验 |
| 到达 CV / 周期性 | 接近 Chutes 子集 | 与源对比 |
| 意图热度 / 热点漂移 | 可控 | 报告 regime 参数与 JS 散度 |
| 有效重复率 | 三档分别报告 | 去除占位符/寒暄后的重复率 |
| 政策变更→影响率 | 可分 | 双参考标签 |
| 标签一致性 | κ ≥ 0.8 | 200 条双人审计 |
| 泄漏检查 | 测试答案不进历史 | 会话切分 + 静态库来源审计 |

## 11. 规模估算与可行性

- 数据包：原始 JSON 116 MB + 派生 parquet/jsonl，估计 < 1 GB；
- 请求 95,129、lookup 154,577、账本行数约 30–50 万（每请求 1–3 候选）；
- 规则引擎：先 3 个 flow（3,130 会话）打通，再扩到 10 个 flow；
- 工程：MVP 2–3 周（事件化 + 状态 + 3 flow 规则 + 账本 + 统计校验），全量再 2 周。

**为什么不是"从零合成"**：ABCD 提供真人语言、真实政策复杂度、动作级真值；从零合成这些要贵得多，而且不可信。**为什么不是"直接用 ABCD"**：它没有时间、版本、权限、可见性控制与账本，无法支撑生命周期与依赖更新实验。

## 12. 风险与论文写法

| 风险 | 处理 |
|---|---|
| 自造数据外部效度 | 用 ChurnBench（受控版本）+ FiscalQA Pro（真实版本）做外部效度；SemCache 做 resp 轨 |
| 规则引擎歧义/错误 | 200 条审计 + κ；规则与人工双参考 |
| 闭环实体空间放大重复 | 报"有效重复率"并标注为受控上界；R0/R1/R2 三档 |
| 构造送分 | 更新事件对所有方法可见；标签只评测；冻结协议 |
| 规模小（10k 会话） | 用于 E1/E2/E5 足够；E3 到达用 Chutes 放大 |
| 许可 | ABCD MIT，可再分发；派生标签与脚本随论文开源 |

**论文定位**：不写"新数据集"，写"面向流式缓存实验的构造协议与账本"，把 ABCD 作为语言与真值来源，把构造偏差量化并消融。这样评审可以质疑数据，但无法质疑你没测量它。

## 13. MVP 路线

1. **W1**：事件化（request/lookup/session）+ 状态快照 + 时间线；先在 `product_defect` 上跑通。
2. **W2**：政策条款化 + v1/v2 两版规则引擎 + 标签账本；审计 100 条。
3. **W3**：接入 `shipping_issue`、`order_issue`；构造 3 类更新事件 + 2 类 ACL 事件；统计校验报告。
4. **W4**：扩到 10 个 flow；冻结 v0.1，跑 E1/E2/E5 的 pilot（各 1–2 个 RQ）。
5. 之后：与 Chutes 到达层拼接、接入 SemCache 轨、Flink 回放。
