# Agent 执行会话中可缓存内容的深度探索

> 日期：2026-09-23
> 背景：导师反馈当前缓存内容单薄（只有"上下文/RAG知识/历史回答"三类），需深度探索 Agent 执行会话中还有哪些值得缓存的内容。
> 硬约束：①不能涉及工具调用（推理时延预测要求）；②缓存对象必须具体到表示与复用边界；③推理时延可预测性须说明省略/新增哪个阶段及可观测特征；④Flink 控制面可管理（不改 vLLM 内核）。
> 证据标记：【论文实测】= 已核验原文的论文数据；【推导】= 基于论文结论的逻辑推导；【假设】= 待实验验证。

---

## 1. 分析框架：Agent 执行管线分解

当前设计的三类缓存（上下文/RAG知识/历史回答）只覆盖了管线的输入侧和输出侧，**中间推理阶段的计算产物和辅助推理调用完全没有被当作缓存对象**。将一次 Agent 轮次的执行管线展开：

```
用户输入
  → [意图分类/路由]          ← 辅助推理调用（LLM或轻量模型）
  → [任务规划/分解]          ← 辅助推理调用（LLM）
  → [上下文组装]
      ├─ 系统提示词          ← 静态，跨会话共享
      ├─ 对话历史            ← 会话内累积，可能被压缩
      ├─ RAG 检索文档        ← 外部知识
      └─ Few-shot 示例       ← 同类任务共享
  → [Prefill: 计算 K/V]      ← 推理计算，与输入长度近线性
  → [Decode: 逐 token 生成]  ← 推理计算，与输出长度线性
  → [输出解析/结构化]        ← 可能是LLM调用
  → 工具调用（排除）
```

方括号内的每个环节都可能产生可复用的中间产物。以下按优先级逐一分析。

## 2. 新增缓存对象（按优先级排序）

### 2.1 分层前缀 KV 缓存（最高优先级）

#### 缓存对象定义

缓存的不是"对话历史文本"，而是对话历史在 **prefill 阶段计算出来的 K/V 张量**。按复用范围和变化频率拆成四层：

| 层 | 表示 | 粒度 | 复用范围 | 变化频率 |
|---|---|---|---|---|
| L0 系统提示词 | 系统提示 token 序列 → KV blocks | 0.5k–4k token | 全集群跨会话共享 | 几乎不变 |
| L1 Few-shot 模板 | 同类任务示例 → KV blocks | 1k–8k token | 同类任务跨会话共享 | 低频 |
| L2 RAG 文档段 | (系统提示+文档) → KV blob，key=文档内容哈希 | 单段 256–1k token | 相似查询近似共享 | 中频 |
| L3 会话历史 | (L0+L1+L2+既往轮次) → KV blocks | 随轮增长，长会话 50k–200k token | 仅同一会话跨轮共享 | 每轮增长 |

**关键区分**：缓存文本只省 token 费用，prefill 照跑；缓存 K/V 张量直接跳过对应长度的 prefill 计算。vLLM×Mooncake 实测 agentic trace 上缓存命中从 1.7%→92.2%，P50 TTFT 降低 **46×**【论文实测，vLLM blog 2026-05-06】。

#### 复用边界与失效机制

- **L0/L1**：精确复用，要求 token 级完全一致（含模型版本、tokenizer revision）。失效条件：prompt 模板改版、模型换版。用内容哈希+模型版本号管理。
- **L3**：会话内精确复用。第 k+1 轮 prompt = 第 k 轮完整 transcript + 新用户轮。失效条件：会话关闭/空闲超时（TTL）。
- **L2**：精确 blob 复用（按文档内容哈希），近似复用需引擎内核改动（SparseX/Irminsul），本课题显式排除近似复用。
- 不需要逐 token 比对——前缀哈希树（vLLM-APC 的 radix 树已提供）定位最长匹配前缀。

#### 时延可预测性分析

- **命中后省略阶段**：prefill。命中长度 L 的前缀即跳过 L 个 token 的 prefill 计算。
- **可观测特征**：命中前缀长度（token 数/block 数）。prefill 在长上下文下是 memory-bandwidth bound，经验上与输入 token 数近线性【Orca/DistServe 结论；PrefixPlace 实测近线性】。
- **部分命中**：前缀长到 L 就停，只重算 L 之后的 delta——增量可预测。
- **缓存查找开销**：radix 树最长前缀匹配 O(prefix_len)，微秒级；Flink keyed state 元数据查表 O(1)。相对 prefill 的毫秒~百毫秒级可忽略。
- **诚实边界**：llm-d 实测对 decode-bound 的推理负载，前缀路由几乎无收益【arXiv 2609.23130 转述】。本维度收益在 prefill-bound 的长上下文/agentic 负载上成立。

#### Flink 层可行性

- **控制面存什么**：按 prefix_key 作 keyed state → `{内容哈希, token_length, num_blocks, 持有worker, 所在层级(HBM/DRAM/SSD), 最近使用watermark, TTL截止时间}`。KB 级元数据，可 exactly-once checkpoint。
- **数据面存什么**：vLLM-APC/SGLang RadixAttention 已提供 radix 前缀缓存，FP16 K/V blocks，易失可重建。
- **是否需改 vLLM**：精确前缀复用**不需要**。Flink 只做"驻留哪些前缀+亲和路由"策略。
- **checkpoint/恢复语义（最硬增量）**：Flink checkpoint 的是"前缀复用意图日志"（"存在前缀P，长L，属会话S，应驻留worker m"），不 checkpoint 张量。故障恢复时 exactly-once 重放意图，指示 vLLM 从 token transcript 重算或从 Mooncake 层取回 KV。这是"控制面持久容错/数据面易失可重建"的干净落地。

#### 与现有三类缓存的区别

| 现有缓存 | 缓存什么 | 本候选 | 本质区别 |
|---|---|---|---|
| 上下文 | 对话历史**文本** | 历史的 **K/V 计算结果** | 文本省 token 费但 prefill 照跑；KV 直接跳过 prefill |
| RAG知识 | 检索文档**文本/embedding** | (系统提示+文档)的 **KV blob**，按内容哈希 key | 文本缓存不省 prefill；KV blob 省 prefill 且跨会话路由 |
| 历史回答 | 最终输出**文本**，命中跳过整段推理 | 前缀 KV，命中只跳过 prefill，仍生成新回答 | 粒度不同：答案 vs 张量 |

#### 文献证据

| 来源 | 数字 | 性质 |
|---|---|---|
| vLLM×Mooncake | 命中 1.7%→92.2%，吞吐 3.8×，P50 TTFT ↓46×，E2E ↓8.6× | 【论文实测】 |
| llm-d GLM-5.2 研究 | 96% 主轮复用≥90% 输入，缓存轮 TTFT 快 2.8× | 【论文实测】 |
| PrefixPlace | RAG replay materialization-cost 比 vLLM-APC 省 40.3% | 【论文实测】 |
| HotPrefix (SIGMOD'26) | 前缀热度动态追踪优于纯 LRU | 【论文实测】 |
| 【假设】 | 分层差异化管理优于 vLLM 单层 LRU | 待验证 |

#### 研究价值

**研究问题**：在多轮 agentic 负载上，把前缀按"会话生命周期"分层、由 Flink 控制面以可恢复元数据管理、与在线路由联合优化，能否在 cache-goodput 与故障恢复上优于"全局 LRU + 离线放置"？

**创新点（诚实定位）**：
1. 会话级、事件时间的前缀生命周期模型（L0 跨会话钉住/L3 随轮单调增长+会话TTL/L2 内容哈希 blob），论证 vLLM 单层 LRU 对"会话长前缀+全局系统前缀"混合场景次优。
2. 控制面元数据 exactly-once 恢复 vs 数据面 KV 易失可重建的故障容错叙事。
3. 在线/流式的前缀-路由 crossover 预测器，对标 PrefixPlace 的离线 epoch 规划——增量是连续、会话增长感知、带恢复语义。

**必须避开的已有工作**：vLLM-APC（引擎内前缀缓存）、Continuum（工具等待TTL）、IntentKV（引擎内剪枝）、PrefixPlace（离线放置）、llm-d（无状态路由）。

### 2.2 对话历史摘要文本块缓存（高优先级）

#### 缓存对象定义

当对话历史 chunk 因超出上下文窗口被驱逐时，对该 chunk 做一次 LLM 压缩调用，产出的**摘要文本块（summary segment）**。

```
SummaryBlock {
  session_id, chunk_id, chunk_token_count,
  summary_text, summary_token_count,    // 通常固定在预算内
  content_hash, model_version,
  fidelity_level,  // full/compressed/skeletal/trace（借鉴 CrystalMem）
  created_at
}
```

大小量级：0.3k–3.5k token/块（AgentMemBench 实测 CBS 平均 footprint 3,478 tokens【论文实测】），远小于原始 chunk（DPM 中 82–96 事件/轨迹 ~26k 字符【论文实测】）。

#### 复用边界与失效机制

- **精确复用**：同一会话内，被驱逐 chunk 已生成过 summary block；后续轮次拼接 prompt 时直接用缓存 summary。对话历史 append-only，chunk 内容不变，content_hash 可校验。
- **近似复用（有损）**：summary 保留语义但丢弃精确 token。文献明确三类信息丢失【Beyond Context Window, arXiv 2603.04814 Table 6】：① temporal marker（日期/时序）；② implicit coreference（职位名等）；③ ephemeral update（"每周两次"→"三次"的更新未传播）。
- **失效检测**：content_hash 不匹配→重新压缩；模型版本升级→全部失效；CrystalMem 的 recrystallization（从 residue 重建，p50 586ms/p95 2.0s【论文实测】）；StateMem 式 supersession 信号标记旧事实为 stale。
- **关键工程机制**：CrystalMem 的四档 fidelity 状态机（full→compressed→skeletal→trace）+ verified recrystallization，证明"降级不是删除，而是可逆的"【论文 2608.00303】。

#### 时延可预测性分析

- **命中后省略阶段**：一次 LLM 压缩调用（compression call）。
- **可观测特征**：输入长度=原始 chunk token 数（可观测），输出长度=摘要 token 数（由预算固定，可观测）。因此 compression call 的时延=排队时延+推理时延，**正好落在现有预测模型覆盖范围内**，不需要补全新维度。
- **DPM 直接对比数字**【论文 2604.20158】：增量滚动摘要需 82–96 次 call；DPM 延迟投影只需 1 次 call，快 **7–15×**，且 tight budget（20×压缩）下事实精度 0.907 vs 0.392（+0.515, p=0.0014）。
- **缓存查找开销**：Flink keyed state 按 session_id+chunk_id 查找 O(1)，亚毫秒。若需语义检索决定用哪个 summary，则引入 embedding 检索开销（不在现有模型内）——但 DPM 式做法避免了检索（decision time 一次 projection，不做在线检索）。

#### Flink 层可行性

- 控制面：Operator State by session_id → ListState<SummaryBlock>。维护摘要块生命周期（生成、fidelity 降级、失效标记、checkpoint）。
- 数据面：无变化。vLLM 只看到拼接后的 prompt 文本，不知道 summary 是缓存的。
- 不需要改 vLLM。checkpoint 后 SummaryBlock 随 keyed state 持久化，故障恢复后不需重新压缩。

#### 与现有三类缓存的区别

- **vs 上下文（KV prefix cache）**：本候选缓存的是 LLM 压缩产出的**文本块**，不是 KV tensor；生命周期独立于具体 prompt prefix；由 Flink 控制面管理。两者可叠加。
- **vs RAG 知识**：来源是**本会话的对话历史**，不是外部文档；经过 LLM 语义压缩，不是原文 embedding。
- **vs 历史回答（语义缓存）**：历史回答是请求级 question→answer 映射，命中后短路整个推理；本候选是**会话级中间表示**（chunk→summary），不短路推理（仍需基于 summary+当前 query 生成回答）。

**一句话区分**：历史回答缓存="跳过这次推理"；摘要块缓存="省略一次中间压缩调用，并缩短后续 prompt"。

#### 文献证据

| 来源 | 数字 | 性质 |
|---|---|---|
| DPM (2604.20158) | tight budget FRP 0.907 vs 增量摘要 0.392（+0.515）；快 7–15× | 【论文实测】 |
| CrystalMem (2608.00303) | 50% byte budget 匹配 full provision；recrystallization p50 586ms | 【论文实测】 |
| AgentMemBench (2608.00009) | CBS Recall@5 0.556, footprint 3,478 tok；LoCoMo 长程 CBS Recall@5 仅 0.005 | 【论文实测】 |
| Beyond Context Window (2603.04814) | ~10 turns 后 memory cheaper，20 turns 省 26%；压缩丢失三类信息 | 【论文实测/成本模型】 |

#### 研究价值

**研究问题**：在 Flink 控制面，对话历史 chunk 的压缩调用何时触发、压缩到什么 fidelity、何时复用缓存 summary vs 重新压缩，才能在满足推理 SLO 的前提下最小化压缩调用的累计开销？

**创新点**：
1. 把"压缩决策"从规则驱动（"超窗口就压"）变为**时延预测驱动**：用已有推理时延预测模型在每个 chunk 驱逐点做收益-成本核算（成本=预测的 compression call 时延；收益=缓存 summary 后缩短后续 prompt 的 prefill 节省+省略未来重压缩）。这与项目已有的"驻留门控"框架同构。
2. fidelity 分级与 SLO 联动：CrystalMem 的降级由 byte-budget 驱动，本课题改为**推理时延 SLO 驱动**——预测排队时延超阈值时，主动把更多 chunk 降级到 skeletal/trace 级以缩短 prompt。
3. DPM 式延迟投影 vs 增量摘要的在线切换：按会话剩余轮数预测（已有 RP1）动态选择。

### 2.3 任务规划/分解结果缓存（中高优先级，条件性）

#### 缓存对象定义

Agent 对用户请求执行任务规划（task decomposition）的结构化结果——将任务分解为子步骤的 DAG 或有序步骤列表。

```
PlanTemplate {
  intent_id, template_embedding,
  steps: [{step_type, tool_name, parameters_schema, dependencies}],
  estimated_tokens, complexity_tier, model_used
}
```

大小量级：每个计划模板 1–5KB。百级任务类型×10 模板/类型 = 5–50MB，极轻量。

#### 复用边界与失效机制

- **精确复用**：意图类目相同 + 请求去除参数后的语义相似度 > γ（AgentReuse 用 γ=0.75【论文实测】）。直接复用计划模板，仅替换参数槽位。
- **部分复用**：前 N 步相同，后续不同。HeraSys 的拓扑融合处理并发查询中的冗余子图【论文 2607.22578】。
- **失效条件**：任务需要多步动态规划（如开放式代码调试），每步依赖前一步工具输出——这种规划不是一次性的，而是 ReAct 循环中的逐步规划，不适合缓存。
- **失效处理**：AgenticCache 的后台异步更新（Cache Updater 异步调 LLM 验证修正）+ 即时替换（LLM 返回计划与缓存不一致时立即替换）【论文 2604.24039】。

#### 时延可预测性分析

- **命中后省略阶段**：一次任务规划 LLM 调用。
- **可观测特征**：规划调用输出长度可变但有范围（简单任务~200 tokens，复杂任务~1000 tokens），可通过输入特征（任务复杂度分类）预测输出 token 范围。AgentReuse 实测规划生成时延与计划文本长度成正比【论文实测】。
- **净节省**：AgentReuse 实测平均规划生成时延 **31.8s**（GPT-4+AutoGen），命中时省略整个阶段，缓存查找+参数注入 <10ms。节省比 >2500:1。
- **对时延预测模型的影响**：缓存命中/未命中导致服务时间分布发生**结构性跳变**（常数 vs 31.8s）。这在传统排队论中没有现成解——需要建模一个"缓存命中概率依赖于请求到达模式"的 M/G/1 分支队列。这本身是一个研究问题。

#### Flink 层可行性

- 控制面：计划模板缓存表 + 语义签名索引（HeraSys 方式）+ 计划复杂度统计。
- 不需要改推理引擎，但需要 Agent 框架配合：收到请求后先查 Flink 控制面的计划缓存，命中则实例化模板跳过规划 LLM 调用。
- 后台 PlanUpdater 算子异步验证缓存计划。

#### 与现有三类缓存的区别

- **vs 历史回答**：核心区别——计划是**中间决策结构**，不是最终回答。两个请求可能得到完全不同的最终回答（参数不同），但共享同一个计划模板。AgentReuse 消融证明：不提取参数直接做相似度，F1 从 0.9718 降到 0.9035【论文实测】。
- **vs 上下文**：上下文是 token 级，计划是操作级。
- **vs RAG**：RAG 是内容复用，计划是控制流复用。

#### 文献证据

| 来源 | 数字 | 性质 |
|---|---|---|
| AgentReuse (2512.21309) | 有效计划复用率 93%；F1=0.9718；延迟降低 93.12%；规划生成平均 31.8s | 【论文实测】 |
| AgenticCache (2604.24039) | 延迟降低 65%，token 使用降低 50%，命中率 39–73%；TDW-COOK 上 GPT-5 延迟 12.86h→1.75h（7.4×） | 【论文实测】 |
| HeraSys (2607.22578) | P99 延迟降低最高 2.17×；吞吐提升最高 1.85× | 【论文实测】 |
| SAGA (2605.00528) | 工作流感知 KV 缓存达 Bélady 最优 1.31×；TCT 降低 1.73× | 【论文实测】 |

**条件性说明**：AgentReuse 的 93% 复用率基于 SMP 数据集（23 个意图类目），在更开放的 Agent 场景（如 SWE-bench 编程任务）中复用率可能显著下降【假设】。

#### 研究价值

**研究问题**：在多轮 Agent 推理流中，如何将一次性的任务规划结果转化为可复用的结构化模板，在 Flink 控制面实现"计划级缓存+参数级实例化"，同时处理动态环境中的计划失效？

**创新点**：
1. 参数槽位的语义级提取在 Flink 流处理中的实时实现。
2. 计划级缓存的时延预测分支——缓存命中 vs 未命中是两种完全不同的时延分布，如何在排队时延预测模型中建模这个二元分支。
3. 与 SAGA AEG 的结合：计划缓存产生的 DAG 可直接作为 SAGA 工作流感知 KV 缓存的输入，同时优化控制面（计划缓存）和数据面（KV 缓存）。

### 2.4 结构化状态变量缓存（中优先级，补充性）

#### 缓存对象定义

从对话历史中提取的**结构化状态变量 / typed facts**，带 supersession 跟踪（旧值→新值的替代关系）。

```
StateVariable {
  session_id, variable_name, current_value,
  value_history: [{value, valid_from, valid_to}],  // supersession 链
  confidence, source_turn_id
}
```

大小量级：每条 <100 token；活跃会话 10–50 个变量 = 1–5k token。

#### 复用边界与失效

- **有效场景**：事实型/persona 型查询（"我住哪个城市？"）。
- **失效场景**：需要精确时序计算、隐式指代消解、叙事连贯性推理（LoCoMo 上 memory system 57.68% vs long-context 92.85%【论文实测】）。
- **失效机制**：Supersession（新轮次提供新值→旧值移入 value_history）；Memanto 的 automated conflict resolution【论文 2604.22085】。

#### 时延可预测性

- 生成成本：用 LLM 提取（Mem0/ENGRAM 式）= 一次 LLM call，输入=turn 长度，输出=facts 固定长度，在现有预测模型内。ENGRAM 报告端到端 median 1.487s【论文 2511.12960】。
- 检索成本：Memanto 无索引语义检索 sub-90ms【论文实测】——CPU 侧，不在现有预测模型内，需补全。
- 命中后省略：省略"从对话历史中重新提取状态变量"的 LLM call。

#### 与摘要块缓存的关系

互补而非替代：摘要保留**叙事**（"之前聊了什么"），状态变量保留**事实**（"当前事实是什么"）。AgentMemBench 已证明朴素 GEM（知识图谱）在长程上崩溃（Recall@5 0.361【论文实测】），必须用 LLM 级提取而非规则 NER。

#### 研究价值

把对话状态维护建模为流处理的**物化视图**：每轮对话增量更新相关 state variables（类似 CDC→materialized view），而非每轮重读全部历史。与 Flink keyed state + process function 范式天然契合。

### 2.5 意图分类/路由决策缓存（低优先级，前置层）

- 缓存对象：意图分类的结构化决策结果 `(intent_label, route_target, confidence)`。
- 节省：一次分类调用（BERT/SetFit 2–10ms，LLM 分类 50–100ms）。绝对节省量小。
- 时延可预测性：输入极短（10–50 tokens）、输出极短（1–3 tokens），时延近乎常数，是所有候选中最可预测的。
- 价值：作为任务规划缓存的**前置层**——意图分类缩小检索空间，使计划模板的相似度搜索更快更准。AgentReuse 消融证明不先做意图分类就跨类目检索，F1 显著下降【论文实测】。
- 不建议独立深化，建议作为 2.3 的配套机制。

## 3. 不建议独立深化的方向

| 方向 | 排除理由 |
|---|---|
| **跨会话摘要** | AgentMemBench 实测 LoCoMo 长程 CBS Recall@5 仅 0.005（vs dense retrieval 0.573）【论文实测】。摘要在超长程上信息损失不可补救。更适合作为 2.2 的终态产物（会话结束时的 digest），而非独立维度。 |
| **CoT 推理前缀缓存** | ReasonCache (arXiv 2507.21433) 已做跨生成相似推理步 KV 块复用，吞吐 +89.2%【论文实测】。且推理负载是 decode-bound，前缀复用收益有限。建议并入 2.1 的 L1/L2 知识层（worked-example 前缀放置），不单独立机制。 |
| **推测性预解码下一轮** | 开放对话中下一条用户输入未知，无法准确预解码。要么退化成 speculative decoding（需 draft 模型，引擎内），要么预测工具调用（SPORK，属约束①排除区）。 |
| **Few-shot 示例选择缓存** | 选择本身只需 embedding+向量检索（~5ms），已很便宜。更大价值在 KV 缓存复用（AdapShot），属数据面优化。 |
| **Prompt 模板实例化缓存** | 确定性操作（字符串填充），不需要 LLM 调用，不存在"省略推理阶段"。与"上下文"高度重叠。 |
| **安全审核/内容过滤缓存** | 每个输入内容不同，复用价值低；审核模型轻量（<50ms），即使不缓存开销也小。 |
| **KV 级压缩（LiveMem/KV Compaction/SeDeM）** | 需改 vLLM 内核或模型结构，违反"不改引擎"约束；且 2608.00902 明确压缩 tool response 段，违反约束①。只能作对比基线。 |

## 4. 关键纠偏与诚实定位

在文献核验中发现以下容易误引的点，必须在论文中诚实处理：

1. **SPORK (arXiv 2607.03333) 不是"推理 KV 缓存"，而是"推测工具调用"**——它分叉 probe 预测下一个 tool 名（74.6–99.6% 准确率）并提前派发工具执行。属约束①要排除的工具调用范畴，不能写进推理中间状态缓存的贡献。
2. **PrefixPlace (arXiv 2608.01655) 已离线、可证明地解决了"哪些前缀放哪个 worker"**（设施选址问题，RAG replay 上比 vLLM-APC 省 40.3% materialization cost）。本课题不能再 claim"决定前缀放置"，增量必须在 Flink 的**在线/会话生命周期/checkpoint 语义**。
3. **llm-d / NVIDIA Dynamo 已经是控制面**（prefix-aware、token-aware、learned-predicted-latency 路由），vLLM×Mooncake 已实现命中 1.7%→92.2%。本课题的增量不在"做控制面路由"，而在"把多轮会话生命周期当一等 keyed state + exactly-once 恢复"。
4. **Continuum 的 KV TTL 是为"等待工具结果"设计的**（arXiv 2511.02230），不是通用的前缀驻留策略。本课题的前缀驻留不应照搬其 TTL 逻辑。
5. **ReasonCache 已做跨生成推理 KV 复用**（吞吐 +89.2%），CoT 推理前缀不能当新发现。

## 5. 时延可预测性统一分析

| 缓存对象 | 省略的阶段 | 该阶段时延的可观测特征 | 缓存查找开销 | 与现有预测模型的契合度 |
|---|---|---|---|---|
| **分层前缀 KV** | prefill | 命中前缀长度（token 数），近线性 | radix 树 O(L)，微秒级 | **完全契合**——prefill 时延已有模型 |
| **摘要文本块** | LLM 压缩调用 | 输入=chunk 长度，输出=固定摘要长度 | Flink state O(1)，亚毫秒 | **完全契合**——标准 LLM call |
| **任务规划** | LLM 规划调用 | 输入=查询长度，输出=复杂度分档→token 范围 | 模板查找+参数注入 <10ms | **需扩展**——二元分支（命中=常数，未命中=f(输入,输出估计)） |
| **结构化状态变量** | LLM 提取调用 | 输入=turn 长度，输出=facts 固定长度 | embedding 检索 sub-90ms（需补全） | 基本契合，检索成本需补全 |
| **意图分类** | 分类调用 | 输入/输出极短，近常数 | 模板hash查找 <1ms | **最契合**——近乎常数 |

**核心结论**：分层前缀 KV 和摘要块缓存的时延可预测性最好，完全落在现有"排队+推理"模型内。任务规划缓存需要扩展模型以处理二元分支，但这本身是一个有价值的研究问题。

## 6. 推荐的深化组合与优先级

### 核心组合（推荐）：分层前缀 KV 缓存 + 对话历史摘要块缓存

**为什么是这两个**：

1. **管线位置互补**：前缀 KV 在 prefill 计算侧，摘要块在上下文组装侧。一个省"算 KV 的时间"，一个省"压缩历史的时间+缩短 prompt"。
2. **正向循环**：摘要块缩短上下文 → 更小的 KV → 更多会话前缀能驻留 HBM → 前缀命中率上升。两者形成正反馈。
3. **证据最强**：前缀 KV 有 Mooncake 46× TTFT、llm-d 96% 复用的实测；摘要块有 DPM 7–15× 加速、+0.515 精度的实测。
4. **时延可预测性最好**：两者都完全落在现有"排队+推理"预测模型内，不需要补全新维度。
5. **Flink 控制面定位最清晰**：前缀 KV 的元数据 + 摘要块的文本都在 Flink Operator State，实际 KV 张量在 vLLM，控制面/数据面分离干净。
6. **与现有三类缓存边界最清晰**：前缀 KV 不是"上下文文本"（是 KV 计算结果）；摘要块不是"历史回答"（是中间压缩产物）。

**统一叙事**：Flink 控制面管理多轮 Agent 的两类会话状态——**前缀计算状态**（KV，省 prefill）和**上下文压缩状态**（summary block，省压缩调用+缩短 prompt），共用一套 keyed state 元数据模型和 exactly-once 恢复语义。

### 增强组合（如果论文需要更多深度）：+ 任务规划结果缓存

- 任务规划缓存是与现有三类缓存区别最大的新维度（中间决策 vs 最终回答），绝对节省量最大（31.8s/次）。
- 但其适用性依赖 Agent 架构有显式规划阶段，且开放场景复用率可能下降。
- 二元分支时延预测（常数 vs 31.8s）是一个有深度的研究问题，可以作为论文的一个理论亮点。
- 与前缀 KV 的结合：计划缓存产生的 DAG 可直接作为工作流感知 KV 缓存（SAGA 式）的输入，同时优化控制面和数据面。

### 补充层（不独立成章）：

- 意图分类缓存：作为任务规划缓存的前置层，不独立深化。
- 结构化状态变量：作为摘要块缓存的补充（事实 vs 叙事），可在实验中作为消融项。
- 空闲时段会话预热：作为前缀 KV 缓存的"when"维度（what/where/when 三位一体），不独立成章。

## 7. 对现有设计的具体修改建议

当前 prototype.md 中"缓存管理"部分写的是：
- Agent 上下文：不仅是复用推理结果，也要考虑复用其他上下文信息
- RAG 知识/语义库
- 缓存汰换策略

建议将"Agent 上下文"细化为两个独立的缓存维度：

1. **前缀 KV 计算状态缓存**（新增，最高优先级）：明确缓存的是 prefill 的 K/V 计算结果而非文本，按 L0/L1/L2/L3 分层管理，Flink 控制面存元数据、vLLM 数据面存张量。
2. **上下文压缩状态缓存**（新增，高优先级）：明确缓存的是 LLM 压缩产出的摘要文本块，带 fidelity 分级，由时延预测驱动压缩决策。

原有的"RAG 知识/语义库"和"历史回答（语义缓存短路）"保留不变。

这样缓存维度从笼统的三类变为具体的四类：
| 维度 | 缓存对象 | 省略的阶段 | 层次 |
|---|---|---|---|
| 前缀 KV 计算状态 | 系统提示/历史/RAG的 K/V 张量 | prefill | 数据面+控制面元数据 |
| 上下文压缩状态 | 对话历史 chunk 的摘要文本块 | LLM 压缩调用 | 控制面 |
| RAG 知识 | 检索文档片段 | 远端检索 | 控制面 |
| 历史回答 | 语义相似请求的完整响应 | 整次推理 | 控制面 |
