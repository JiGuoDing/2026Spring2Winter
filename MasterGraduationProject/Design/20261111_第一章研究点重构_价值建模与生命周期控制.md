## 0. 一页式决策摘要

### 0.1 推荐结论

| 决策项     | 推荐                                                                                            | 一句话理由                                                                                         |
|:---------- |:----------------------------------------------------------------------------------------------- |:-------------------------------------------------------------------------------------------------- |
| 第一章结构 | 只保留两个研究点：**估值**与**控制**                                                            | 两个问题可以各自独立证伪，又必须通过价格与日志闭环，而不是两个松散模块                             |
| 研究点一   | **异质缓存对象的动作条件价值与有效性建模**                                                      | 缓存价值不是对象的静态属性，而是“对哪个请求、采取哪个动作、在什么负载与依赖状态下”的函数           |
| 研究点二   | **依赖感知的缓存生命周期联合控制**                                                              | 准入、复用、验证、刷新、降级、失效、淘汰必须共享同一组资源价格；刷新必须按级联计价                 |
| 连接方式   | **双向价格接口 + 反事实账本**                                                                   | 研究点一给动作价值、风险与敏感性；研究点二给约束价格、实际动作与结果；不是“拿研究点一的分数做排序” |
| 核心对象   | `resp + rag`；`ctx` 只作为版本、依赖、权限与失效传播源                                          | 同时覆盖“短路推理”和“省检索”两类收益，且两者风险语义不同，足以支撑统一模型                         |
| 评测主轴   | 决策后悔、风险预算兑现、净收益、约束满足率                                                      | 命中率、MAE、AUC 只能作为辅助指标，不能作为贡献的主证据                                            |
| 最小可交付 | 两对象 × 六类核心动作（准入/复用/验证/刷新/降级/淘汰）+ 失效/冻结 + 离线回放 + Flink 元数据原型 | 16 周内可完成，且足以支撑三组判定性实验                                                            |

### 0.2 两个研究点的一句话

**研究点一（RP1）：动作条件价值与有效性建模。**
给定缓存项 `i`、请求 `r`、依赖状态 `D` 与系统负载 `S`，估计三个动作——`REUSE`、`VERIFY_THEN_REUSE`、`RECOMPUTE`——各自的净价值分布、风险上界与置信区间，并给出一个在风险预算内可辩护的动作。

**研究点二（RP2）：依赖感知的生命周期联合控制。**
在容量、质量风险、新鲜度、权限与验证吞吐约束下，利用 RP1 的动作价值及其对价格/版本/负载的敏感性，联合决定准入、复用、验证、刷新、降级、失效与淘汰，并对“刷新一个 `ctx`/`rag` 项会杀死哪些下游 `resp` 命中”进行级联计价与调度。

### 0.3 最终章节故事

```text
命中率不是目标
  → 因为一次命中可能省很多工作，也可能制造一次错误复用
  → 所以先定义“复用相对于重算的净价值”，并让它依赖负载、依赖状态与请求
  → 但价值估计有不确定性，所以要把风险校准成可约束的预算，而不是一个分数
  → 有了价值与风险，仍不知道“何时准入、何时刷新、何时淘汰”
  → 因为生命周期动作竞争容量、验证吞吐与风险预算，而且刷新会杀死下游命中
  → 所以需要依赖感知的联合控制，并把控制结果反哺估值
  → 最后落到 Flink 的 keyed state、timer、checkpoint 与 rescale
```

这条链条的每一环都有一个可证伪的实验；任何一环不成立，都有明确的裁剪方案（见 §9.4）。

### 0.4 最关键的三个可行性判断

1. **复用机会与验证经济学是否成立（P0 / G1）。**
   如果语义/结构复用率过低，或验证成本长期高于命中收益，则第一章的收益前提不成立。此时应把主对象从 `resp` 转向 `rag + 文档更新`，或把 `resp` 降为精确匹配。这个判断必须在第 3 周前完成，不能等到模型写完。

2. **反事实是否可识别（E1.6 / OPE）。**
   复用决策是策略选择的，未采取动作的结果不可观测。若不能通过随机留出、倾向加权或双稳健估计给出可信的反事实，RP1 的“净价值”就只是相关性叙事。必须在系统里预留探索与倾向日志，而不是事后补救。

3. **刷新级联是否足够大（E2.3 / G3）。**
   如果刷新一个 `ctx`/`rag` 项造成的下游命中损失只占刷新成本的很小一部分，那么“刷新—命中耦合”不值得作为 RP2 的核心机制，应降级为工程细节，把 RP2 收缩为“风险预算下的准入/淘汰 + 惰性失效”。

**对应的三个最大风险**：复用机会不足；反事实不可识别；范围/工程量与新颖性碰撞。详见 §11.1。

### 0.5 相对旧设计的三个最大变化

| 变化                                                 | 旧设计                                                 | 新设计                                                                | 为什么必须改                                                                         |
|:---------------------------------------------------- |:------------------------------------------------------ |:--------------------------------------------------------------------- |:------------------------------------------------------------------------------------ |
| 价值从“标量”变为“动作条件分布”                       | `V = p_use·B − C_verify − q·L − ...`，一个对象一个分数 | 对每个 `(item, request, action)` 给净价值、风险上界、置信区间与敏感性 | 旧式标量无法区分“直接复用”和“先验证再复用”；RP2 拿到一个分数只能排序，无法做动作选择 |
| 生命周期从“三个问题的三种用法”变为“约束下的联合控制” | 建不建、新不新、留不留；声称 1.2 不需要新模型          | 共享价格向量 + 依赖闭包 + 刷新级联 + 失效域风险预算                   | 旧设计把资源竞争与刷新级联藏起来了；RP2 会退化成“价值版 LRU”                         |
| 闭环从“日志回灌”变为“价格—账本—校准”                 | 1.1 出分数，1.2 用分数，日志再训练                     | RP1 给动作价值与敏感性；RP2 给约束价格与反事实日志；双方各自更新      | 旧闭环只有一条边；新闭环有两条边，且每条边都有明确的数据契约                         |

### 0.6 本文明确不做的事

- 不设计新的 embedding、相似度函数或向量数据库；匹配器是外生组件，可用 vCache/MVR-cache 式方法作基线。
- 不研究 KV/prefix/attention cache 的驱逐、压缩、传输、量化或融合；这些只作为推理引擎背景与“收益上界”的边界说明。
- 不研究第二章的算力扩缩容；只保留 `λ(ρ)`、容量 `B`、副本状态三个接口。
- 不研究第三章的完整多租户调度与路由；只保留租户权重、SLO、迁移事件三个接口。
- 不把工具结果、计划片段、skill 复用作为第一版 MVP 主体；它们是 `act`/`plan` 扩展验证（见 §4.6）。
- 不声称“首次研究 Agent 缓存”；本文的新颖性只在 §3.5 列出的四个具体条件上主张。

### 1.1 研究边界

#### 1.1.1 在范围内

| 类别         | 内容                                                                                        | 本章位置                           |
|:------------ |:------------------------------------------------------------------------------------------- |:---------------------------------- |
| 逻辑缓存对象 | `resp`：最终回答、答案模板、生成程序；`rag`：检索证据、文档块、表格、工具查询返回的知识结果 | RP1 的估值对象；RP2 的生命周期对象 |

| 排除项                    | 原因                                           | 保留的接口                                                                 |

## 2. 现状诊断：保留什么、删除什么、为什么重构

### 2.1 现有设计真正有价值、必须保留的部分

| 现有要素            | 判断                                     | 在新设计中的位置                                            |
|:------------------- |:---------------------------------------- |:----------------------------------------------------------- |
| 净收益而非命中率    | **保留为核心**                           | RP1 的目标函数与 RP2 的评价主轴                             |
| 反事实基线          | **保留并强化**                           | RP1 的 `NV(a) = U(a) − U(RECOMPUTE)`；§5.4、§8.3            |
| 质量预算            | **保留，但改为“失效域/曝光”口径**        | RP2 的风险约束；§6.8                                        |
| 依赖闭包与版本向量  | **保留并结构化**                         | `CacheItem.dependency_closure`、`VersionVector`；§5.9、§6.6 |
| 刷新—命中耦合       | **保留并升级为级联计价与调度**           | RP2 的核心机制；§6.7                                        |
| 影子价格            | **保留，但改为“可估计、可检验、可删除”** | RP1 的 `λ(ρ)` 与决策翻转实验；§5.4、§8.3                    |
| 四类管理税          | **保留，但合并为三类**                   | 在线税、条件税、后台/恢复税；§5.5                           |
| 最小实现/MVP        | **保留**                                 | §9.4 的裁剪顺序与 §8.6 的原型范围                           |
| “冻结稳定前缀/指纹” | **保留为依赖源机制**                     | `ctx` 版本作为 `resp` 的依赖；§6.6                          |

### 2.2 必须删除、降级或改写的部分

| 旧设计要素                                               | 处理                       | 理由                                                                                         | 替代                                                      |
|:-------------------------------------------------------- |:-------------------------- |:-------------------------------------------------------------------------------------------- |:--------------------------------------------------------- |
| `V = p_use·B − C_verify − q·L − C_hold − C_churn` 单标量 | **改写**                   | 它把“直接复用”和“验证后复用”混成一个分数；也无法表达“同一对象对 A 请求值钱、对 B 请求不值钱” | 动作条件净价值 `NV_i(a; r, S)`；§5.4                      |
| “1.2 不需要新模型，只是 1.1 的三种用法”                  | **删除**                   | 这是旧设计最危险的简化。生命周期是容量、风险、验证吞吐、依赖闭包与刷新级联的联合约束问题     | RP2 的约束优化 + 对偶价格；§6.4–6.5                       |
| 三层 × 七动作 = 21 个组合                                | **收缩**                   | 16 周做不完；`ctx` 不作为主缓存对象                                                          | `resp + rag` × 六类核心动作 + 失效/冻结；`ctx` 只作依赖源 |

### 2.3 为什么必须重构：五个具体理由

1. **两个研究点目前不是两个问题，而是一个问题的两半。**
   旧设计中 RP2 的三个规则都直接复用 RP1 的 `V̄`，没有自己的状态、约束与失败模式。这会导致评审问：“如果 RP2 只是把分数拿去排序，它为什么是独立研究点？”新设计让 RP2 拥有独立的约束（容量、风险预算、验证吞吐、依赖一致性）与独立的机制（刷新级联、失效域风险、联合价格），RP1 只提供“动作价值”，不提供“全局分配”。

2. **旧价值函数无法支持动作选择。**
   `V` 是一个标量，无法回答“直接复用”与“先验证再复用”哪个更好。更严重的是，验证成本、验证通过率、验证后的残余风险三者没有被显式建模，导致 `VERIFY` 要么被忽略，要么被当成免费动作。新设计把 `VERIFY` 作为一等动作，并给出其占优/被占优的条件（§5.4 命题 1）。

3. **旧生命周期忽略了刷新级联。**
   “刷新成本 = 重算成本 + 被杀死的下游重建成本”只被写成一句备注，没有进入决策。实际上，刷新一个高扇出的 `ctx`/`rag` 节点，可能一次性杀死大量 `resp` 命中；如果控制器按单对象 TTL 刷新，会系统性低估热对象的刷新成本。新设计把级联成本写进 `REFRESH` 的价值，并给出“立即刷新 / 惰性失效 / 冻结 / 增量更新”的选择条件（§6.7）。

4. **旧设计没有反事实识别策略。**
   “日志回灌”默认日志能告诉我们未采取动作的结果，但缓存命中后我们看不到重算的质量，强制重算又会影响用户体验。没有探索、倾向记录与 OPE，RP1 的“净价值”无法被可信地验证。新设计把倾向日志、随机留出与双稳健估计作为接口的一部分（§5.7、§8.3 E1.6）。

5. **旧设计没有流式语义。**
   “Flink 映射”只列了 state 类型，没有回答：timer 如何恢复、rescale 后依赖索引如何重分配、失效事件与读路径如何保证不出现“旧版本被复用”、checkpoint 是否包含价值参数。新设计把这些问题变成 RP2 的一等公民（§6.10、§7.5、§8.6）。

### 2.4 重构后的因果链

```text
问题：命中率/相似度不能告诉我该不该复用
  → 洞察 1：价值是动作条件、请求条件、负载条件与依赖条件的函数
  → 方法 1：动作条件净价值 + 校准风险 + 置信下界决策
  → 接口 1：ValueEstimate（含敏感性、依赖元数据、建议动作）

问题：有了价值，仍不知道该准入/刷新/淘汰谁
  → 洞察 2：生命周期动作竞争容量、风险预算与验证吞吐；刷新会杀死下游命中
  → 方法 2：共享价格 + 依赖闭包 + 刷新级联 + 失效域风险预算
  → 接口 2：LifecycleDecision（含级联影响、资源占用、风险记账）

闭环：RP1 的价值 → RP2 的分配 → RP2 的价格与结果 → RP1 的再校准
```

这条链条的每一环都对应一个实验编号，见 §10 的 Claim–Evidence Matrix。

### 3.3 关键工作的“能与不能”逐条说明

#### 3.3.1 vCache：逐条目错误率保证，但不回答“值不值得”

- **解决什么**：全局静态相似度阈值没有错误率保证；不同条目的安全阈值差异很大。vCache 为每个条目在线学习 `(t, γ)`，用悲观置信带把“探索多少次”折算成错误率约束。
- **核心机制**：`Pr(c=1|s)=sigmoid(γ(s−t))`；由 δ 反解最小探索概率；随机化决策；在 i.i.d. 与 sigmoid 族假设下给出边缘正确率保证。
- **不能外推**：保证是“每条请求的边缘概率”，不是“某个租户/某个语义簇的尾部风险”；没有容量、TTL、淘汰、多租户、依赖版本；长回答的等价性依赖 LLM judge，成本非零。
- **本文区别**：vCache 是 `resp` 的**门控器**；本文把门控输出当作 RP1 的一个风险特征，并在其上研究动作价值、负载价格、依赖条件与生命周期。本文不重复其阈值学习，也不继承其分布假设下的理论保证。

#### 3.3.2 MVR-cache：更好的相似度，但不是更好的决策

- **解决什么**：单向量余弦把“主题相似”误判为“回答等价”；用学习式分段 + 对称 MaxSim 提高匹配精度。
- **核心机制**：pointer network 选择标点切分；每段独立嵌入；对称 MaxSim；复用 vCache 门控；用 RL 训练分段策略。
- **不能外推**：只改匹配器；无容量/淘汰/TTL/多租户；在线开销约为 vCache 的 2–3 倍；理论依赖高斯、均衡等额外假设。
- **本文区别**：MVR-cache 是**匹配器**，本文是**决策器与控制器**。本文把 `SMaxSim` 作为 `e_{i,r}` 的一个特征，不训练新的分段器；若匹配器足够好，本文的增量应依然存在（实验 E1.5 固定匹配器，只换决策规则）。

#### 3.3.3 Cortex：RAG 生命周期最完整，但没有质量预算与依赖失效

- **解决什么**：Agent 的远端检索/工具查询在关键路径上；同一知识结果会被反复请求。
- **核心机制**：Semantic Element + ANN 召回 + 0.6B judger + LCFU 淘汰 + TTL + Markov 预取 + 周期阈值重校准。
- **不能外推**：无形式化质量保证；`staticity→TTL` 无公式；无文档版本失效；负载是构造的 Zipf/Trends；只测读取型 search/RAG。
- **本文区别**：Cortex 的 LCFU 是**静态价值密度启发式**；本文把 `REUSE/VERIFY/REFRESH/EVICT` 放在同一组约束价格下，并把文档版本、权限、下游失效纳入。Cortex 是 `rag` 的强基线，不是本文的“已解决问题”。

#### 3.3.4 INFOCOM 2026：集合优化，但没有负载价格与生命周期

- **解决什么**：语义缓存不是“相似就命中”，而是在容量 k 下选一组查询，使“回源成本 vs 失配代价”的期望损失最小。
- **核心机制**：`ℓ(M)=Σ p(q)·min{c(q), d(q,M)}`；Reverse Greedy；未知参数下的 CUCB/CLCB；低切换在线更新。
- **不能外推**：查询空间有限且平稳；距离即失配损失；只约束基数 k；无 TTL/刷新/多租户；实验为 m=20 合成查询。
- **本文区别**：INFOCOM 把“失配代价”当作外生距离；本文把风险校准成 `q·L`，并让 `L` 与任务质量挂钩；更重要的是，本文研究**异构对象**与**动作条件价值**，而 INFOCOM 研究同质 `resp` 集合。

#### 3.3.5 FreshCache / FinCacheServe：新鲜度与依赖一致，但没有“控制”

- **FreshCache 解决什么**：开放网页 RAG 的缓存复用应按“过期概率 ≤ 分层预算”决策，而不是只看相似度或固定 TTL。
- **FreshCache 不能外推**：无容量/驱逐；ε 固定；依赖主要是时间与 URL；MLP 特征在跨域迁移时命中率下降；预印本。
- **FinCacheServe 解决什么**：企业文档会变；答案复用必须是带签名、证据指纹、工具指纹、模型配置、文档版本与反向索引的 serving 对象。
- **FinCacheServe 不能外推**：单一金融域；`U` 的权重离线固定；对象只有 `resp`；无流式状态、无刷新调度、无动作条件价值；预印本。
- **本文区别**：
  - 对 FreshCache：本文不把“新鲜度”当作唯一风险，而是把 `q_sem × q_stale × q_auth × q_model` 分解后用端到端标签校准；并且把新鲜度放进 RP2 的刷新调度与失效域预算。
  - 对 FinCacheServe：本文承认它是最接近的工作。区别在四点：(i) 对象异构 `resp+rag`，不是单一答案；(ii) 价值是动作条件、带不确定性与敏感性，不是固定权重 `U`；(iii) 生命周期是联合控制 + 刷新级联，不是“准入/驱逐 + 反向索引”；(iv) 价值参数由 RP2 的日志与价格反馈更新，不是离线一次设定。

#### 3.3.6 AgenticCache：计划转移缓存与异步纠错，但不是本章对象

- **解决什么**：具身 Agent 每步都调用 LLM；计划转移有强局部性。
- **核心机制**：缓存 `⟨P_i→P_j⟩`；状态元数据范围过滤；`C×I` 评分；后台 LLM 异步确认/纠错；查询抑制。
- **不能外推**：2-gram；状态用 min–max 范围；计数无衰减；无容量/淘汰实验；每 Agent 独立缓存；无形式化保证。
- **本文区别**：AgenticCache 是 `plan` 层的扩展证据；本文只在 §4.6 讨论其接口（状态范围 → 版本向量、异步纠错 → `REFRESH`），不把它写进 MVP 或核心对比。

## 4. 统一问题设定

### 4.1 系统模型：事件驱动的流式 Agent

系统接收一条持续到达的请求流 `{(r_t, t)}`，并同时接收版本事件、权限事件、容量事件与扩缩容事件。决策不是按固定窗口批量做的，而是由事件触发：

```text
事件类型 E = {
  REQUEST_ARRIVAL,      // 请求到达，可能命中候选
  VERSION_CHANGE,       // 文档/摘要/事实/模板/模型/权限版本变化
  TIMER_EXPIRE,         // TTL、复审期、风险窗口到期
  CAPACITY_PRESSURE,    // 容量超过软/硬阈值
  AUTH_CHANGE,          // 租户权限、隔离域变化
  LOAD_REGIME_CHANGE,   // 负载档位变化，λ(ρ) 改变
  RESCALE,              // Flink 并行度/资源变化
  FEEDBACK              // 观测到质量、延迟、成本、违约
}
```

系统状态：

```text
S_t = (I_t, G_t, B_t, P_t, Q_t)
I_t : 缓存项集合与其生命周期状态
G_t : 依赖图（节点、版本、边、失效域）
B_t : 容量/风险/验证吞吐预算与当前占用
P_t : 价格向量（λ, λ_B, λ_R, λ_V）
Q_t : 队列、在途请求、副本状态
```

**设计原则**：读路径只做 O(1) 的版本与权限检查；重决策（刷新、淘汰、校准）异步或批量执行，不阻塞首 token。

### 4.2 缓存对象、依赖节点与版本向量

```text
CacheItem {
  item_id            // 全局唯一
  layer              // resp | rag（MVP）；act | plan（扩展）
  artifact_type       // answer | template | program | doc_chunk | table | tool_result
  tenant_id, scope    // tenant | session | global
  semantic_key        // 规范化 query/intent 指纹
  content_hash        // 负载内容哈希
  version_vector      // Map<DepNodeId, Version>
  dependency_closure  // Set<DepNodeId>，包含传递依赖
  provenance {        // 可审计来源
    source_refs[], tool_refs[], prompt_fingerprint,
    model_id, model_revision, decode_config, template_version
  }
  size_bytes
  fidelity            // full | compact | summary | trace
  created_at, last_access_at, ttl_hint
  recompute_profile { gpu_ms, tokens_in, tokens_out, retrieval_calls, remote_bytes }
  verify_profile    { judge_ms, judge_tokens, acl_ms, ann_ms }
  stats             { hits, verifies, refreshes, invalidations, evictions, exposures }
  risk_state        { q_mean, q_ucb, cluster_id, domain_id, violations }
  lifecycle_state    // ACTIVE | SUSPECT | INVALID | REFRESHING | FROZEN | EVICTED
}
```

```text
DependencyNode {
  node_id            // doc:<id> | ctx:<session>:<fact> | template:<id> | model:<id> | acl:<tenant>
  kind               // document | summary | fact | template | model | permission | tool
  current_version
  last_change_ts
  volatility_class   // static | slow | medium | fast | realtime
  change_magnitude   // 0..1，版本变化的语义幅度（可由 diff/摘要/人工规则估计）
  affected_domains   // 失效域
}
```

**版本向量的语义**：

- `vv_i[d]` 是 `i` 在被构建时看到的依赖 `d` 的版本。
- 请求 `r` 携带 `required[r]`：它要求的最低版本（例如用户刚上传的文档、刚更新的权限）。
- `i` 对 `r` **版本兼容**当且仅当：对所有 `d ∈ D_i ∩ required[r]`，`vv_i[d] >= required[d]`。
- 版本兼容不等于内容仍然正确：依赖可能发生了变化但 `r` 没有显式要求；这时进入“软陈旧”分支（`VERIFY` 或 `REFRESH`），而不是直接复用。

**依赖闭包必须传递**：`D_i` 包含直接依赖与传递依赖（例如 `resp → ctx summary → raw conversation`）。登记不完整是危险方向：它会漏掉失效，产生错误复用。因此“依赖登记完整”是 `ADMIT` 的硬条件（§6.8），并把“未登记依赖导致的错误命中率”作为单独指标报告。

### 4.3 生命周期动作与触发事件

| 动作                   | 触发                           | 语义                                  | 主要资源       | 主要风险         |
|:---------------------- |:------------------------------ |:------------------------------------- |:-------------- |:---------------- |
| `ADMIT`                | 重算完成、外部导入             | 写入缓存，登记依赖与来源              | 容量、元数据   | 未来失效、越权   |
| `REUSE`                | 请求到达且候选有效             | 直接返回缓存负载                      | 读带宽         | 语义误命中、陈旧 |
| `VERIFY`（验证后复用） | 请求到达且候选可疑             | 先判官/ACL/证据检查，再决定复用或重算 | 验证吞吐、延迟 | 判官误判、验证税 |
| `REFRESH`              | 版本变化、定时复审、风险超预算 | 重算/增量更新缓存负载，重置版本       | GPU/检索、容量 | 级联失效、刷新税 |
| `DEMOTE`               | 容量压力、价值下降             | 降低保真度（full→compact→summary）    | 存储、质量     | 保真度损失       |
| `INVALIDATE`           | 权限/模型/硬版本变化           | 标记不可复用，等待重建或淘汰          | 元数据         | 读路径漏检       |
| `EVICT`                | 容量压力、价值为负             | 删除负载与元数据                      | 容量释放       | 未来重建成本     |
| `FREEZE`               | 高扇出/高价值/高刷新成本       | 固定版本，只对版本兼容请求开放复用    | 容量、风险     | 陈旧但可控       |

**动作之间的竞争**：`ADMIT` 占用容量与风险预算；`REFRESH` 占用 GPU/检索并可能触发级联；`VERIFY` 占用判官吞吐；`EVICT` 释放容量但增加未来重建。它们不能各自用一套启发式，否则会在同一资源上互相拆台。

### 4.4 约束分层

| 层级         | 约束                                             | 处理方式                        | 违反后果               |
|:------------ |:------------------------------------------------ |:------------------------------- |:---------------------- |
| **硬约束**   | 租户隔离、权限、模型 revision、依赖登记完整      | 门控，直接禁止 `REUSE`          | 安全/合规事故，零容忍  |
| **预算约束** | 质量风险 `δ`、新鲜度 `ε`、容量 `B`、验证吞吐 `V` | 对偶价格 + 预算记账             | 质量违约/性能退化      |
| **软约束**   | 延迟 SLO、租户公平、churn                        | 目标函数中的惩罚/权重，报告分布 | 体验下降，不阻塞正确性 |

**原则**：硬约束不进入标量目标；预算约束用价格而不是硬编码阈值；软约束只报告，不偷偷变成硬约束。

### 4.5 目标函数与评价

系统目标是带约束的净收益最大化：

```text
max_{π}  E[ Σ_t ( λ(ρ_t) · W_saved(π) + β · latency_saved(π) − C_mgmt(π) ) ]
s.t.     hard constraints,
         E[errors in window] ≤ δ · N_window,
         E[stale in window] ≤ ε · N_window,
         Σ size ≤ B,
         verify throughput ≤ V
```

其中 `C_mgmt` 包括在线税、条件税、后台/恢复税（§5.5）。`β` 是延迟的权重，默认只作为约束/报告，不参与主目标，避免把毫秒与 GPU-ms 混加。

评价不只看目标值，还看：

- **决策后悔**：相对知道结果的 Oracle，策略损失了多少净价值；
- **风险预算兑现**：违约率是否 ≤ δ，预算利用率是否合理（不能只花掉 Surplus 报告的 12–55% 的 δ，也不能超支）；
- **约束满足率**：质量、新鲜度、权限、SLO；
- **净收益**：扣除验证、刷新、失效、存储、重建后的收益；
- **稳定性**：负载/版本扰动下的决策翻转率与 churn。

### 4.6 扩展对象：`act` 与 `plan` 的接口

MVP 不实现，但 schema 必须留位：

- `act`（工具结果）：`dependency_closure` 是工具调用历史前缀（TVCACHE 式最长前缀匹配），`version_vector` 包含工具版本、环境快照、权限。风险是“环境状态不同导致相同调用不同结果”，因此 `q_stale` 的判定不是文档版本，而是执行历史一致性。
- `plan`（计划片段）：`dependency_closure` 是任务阶段、状态范围、数据/工具版本、权限（AgenticCache 式状态过滤）。风险是“状态范围外推导致计划不适用”，因此 `q_sem` 需要包含状态覆盖度。

扩展对象的接口与 `resp/rag` 相同，只是 `CacheItem.layer` 与风险特征不同；这保证本章的模型不是“只为回答缓存设计的一次性方案”。

## 5. 研究点一：异质缓存对象的动作条件价值与有效性建模

### 5.1 标题、一句话与职责边界

**中文标题：异质缓存对象的动作条件价值与有效性建模。**

**英文标题：Action-Conditional Value and Validity Modeling for Heterogeneous Agent Cache Objects.**

**一句话：** 对每个 `(缓存项, 请求, 动作)`，估计“复用相对于重算”的净价值、风险上界与不确定性，并给出一个在风险预算内可辩护的动作。

**职责边界：**

- RP1 负责**估值**：`CacheItem × Request × Action × DependencyState × SystemState → ValueEstimate`。
- RP1 不负责**全局分配**：它不决定“总容量给谁”“刷新谁”“淘汰谁”，只给出每个动作的价值、风险、敏感性与建议。
- RP1 不训练新的匹配器：`sim`、`entity_overlap`、`structural_match` 是输入特征。
- RP1 的输出必须能被 RP2 用作“动作菜单 + 价格响应曲线”，而不是一个不可解释的分数。

**结构对照：**

```text
问题：命中率/相似度/频率/大小，为什么不能决定该不该复用？
洞察：价值是动作条件、请求条件、负载条件、依赖条件的函数；风险必须校准，而不是打分。
方法：动作条件净价值 + 因子化估计 + 依赖条件风险 + 置信下界决策。
接口：ValueEstimate（动作、净价值分布、风险上界、敏感性、依赖元数据）。
实验：校准、决策后悔、稳定性、因子消融、基线对比、OPE、预算兑现。
结论（待验证）：在至少一个负载区间，动作条件价值比分数排序产生更低的决策后悔与更少的违约。
边界：不解决容量分配、刷新调度、失效传播；这些交给 RP2。
```

### 5.2 研究问题与可证伪假设

**核心研究问题：**

> 给定一个 `resp` 或 `rag` 缓存项、当前请求、依赖状态与系统负载，如何估计“复用相对于重算”的净价值、错误风险、陈旧风险和不确定性，并使该估计改善**决策**而不是只改善**预测**？

**子问题：**

1. 为什么缓存价值不能由命中率、相似度、访问频率或对象大小单独决定？
2. 如何统一建模回答缓存与 RAG 知识缓存的收益与风险，而不把两者混成一个命中率？
3. 如何表示依赖闭包、版本向量、来源、租户范围与权限？
4. 如何估计未来复用概率、命中可节省工作、验证成本、持有成本、错误损失与刷新损失？
5. 显式负载影子价格是否真的会改变复用决策？
6. 如何校准 `q_wrong`、`q_stale`、`q_unauthorized`，并报告不确定性？
7. 相对 vCache、MVR-cache、Cortex、RAGCache、Semantic Caching INFOCOM 2026 与 AgenticCache 的明确增量是什么？

**可证伪假设：**

| 编号 | 假设                                                                                            | 可观测预测                                                      | 否定条件                                 | 对应实验   |
|:---- |:----------------------------------------------------------------------------------------------- |:--------------------------------------------------------------- |:---------------------------------------- |:---------- |

| H1.5 | `VERIFY` 只在可测区域最优；区域外被 `REUSE` 或 `RECOMPUTE` 支配                                 | 实验中的动作分布与命题 1 的区域一致                             | 实验中最优动作与区域预测系统性矛盾       | E1.4、E1.5 |

### 5.3 研究动机：五个反例

**反例 1：高命中率不等于高价值。**
Cortex 的实验里，LCFU 的命中率 0.86 低于 LFU 的 0.89，但吞吐 2.35 req/s 高于 LFU 的 2.16（NSDI 2026，Table 6）。原因是命中率不区分“省下的是远端 300–500 ms 调用”还是“省下的是本地小计算”。这说明价值必须按“避免的工作”计价，而不是按命中次数。

**反例 2：高相似度不等于可复用。**
MVR-cache 给出的例子是同一部犯罪剧的两条评论：主题词高度重叠，整句余弦相似度高，但情绪相反，回答不同（ICML 2026）。这说明 `sim` 只能是风险特征，不能是价值本身。

**反例 3：新鲜不等于有用，陈旧不等于错误。**
FreshCache 在 396 个确认变化对上用 LLM judge 评估，只有 34.3% 的内容变化实际影响答案正确性；其报告的答案级真实过期约 0.034%，远低于哈希过期率（arXiv:2607.04281v1）。这说明“版本变了”与“答案错了”之间有一个可校准的传播概率，不能一律硬失效，也不能一律忽略。

**反例 4：验证不是免费的。**
Cortex 的单请求拆解显示，判官本地开销约 0.05 s（缓存查询 0.02 s + 判官 0.03 s），相对省掉的远端 0.48 s 很小；但这是在其特定负载下。对短回答、便宜回源、低相似度候选，验证成本可能高于命中收益。MVR-cache 的在线开销实验显示，其非 LLM 开销约为 vCache 的 2–3 倍（55–60 ms vs 20–25 ms），说明“更好的匹配”本身也有税。这要求 `VERIFY` 作为一等动作被显式建模，而不是默认开启。

**反例 5：预算可能花不完，也可能被热对象击穿。**
Surplus 报告 vCache 在三条公开查询流上只实现 12–55% 的 δ（arXiv:2611.02498v1）。这说明“保守”本身有成本：过度保守会浪费质量预算。另一方面，如果一个错误对象被同一租户反复复用，错误会在一个失效域内集中，边缘概率保证不能防止“某个租户连续看到错误”。这两点共同要求：风险预算要按**曝光/失效域**核算，而不是只按请求平均。

### 5.4 形式化：动作条件净价值

#### 5.4.1 基线

对缓存项 `i` 与请求 `r`，定义**重算基线** `a0 = RECOMPUTE`：

```text
C_0 = λ · w_i + η · E[latency_0] + μ · L_0
```

其中 `λ` 是资源价格向量，`λ_gpu` 是每 GPU-ms 的影子价格（锚），其余分量按部署单价换算；`λ · w_i` 是点积。`η` 是延迟价格（默认只作约束），`μ` 是质量损失价格（默认只作约束），`L_0` 是重算本身的期望质量损失。为了不把“重算也会错”重复计算，后文的 `L` 定义为**相对于重算的增量损失**。

#### 5.4.2 三个动作的净价值

记 `W = λ · w_i`（点积）为命中避免的工作价值，`C_l` 为缓存查询/组装成本，`C_v` 为验证成本，`q` 为不验证直接复用的错误概率，`p` 为验证通过概率，`q'` 为验证通过后的残余错误概率，`L` 为一次错误复用的增量损失。

```text
NV_i(REUSE | r, S)    = W − C_l − q · L
NV_i(VERIFY | r, S)   = p · (W − q' · L) − C_l − C_v
NV_i(RECOMPUTE | r, S)= 0
```

推导（相对重算）：

- `REUSE`：省掉 `W`，支付查询 `C_l` 与风险 `qL` → `W − C_l − qL`。
- `VERIFY`：支付 `C_l + C_v`；以 `p` 通过并复用，残余风险 `q'L`；以 `1−p` 失败并重算（相对基线为 0）→ `p(W − q'L) − C_l − C_v`。
- `RECOMPUTE`：定义为 0。

**两种口径**：上面的 `NV` 是“损失可货币化”口径；若 `L` 不可标定，采用“约束口径”：`NV(REUSE)=W−C_l`、`NV(VERIFY)=pW−C_l−C_v`，并用 `q^UCB≤δ` 控制风险。两种口径不能混用；论文主表用约束口径，附录给损失敏感性。

**命名约定**：动作名 `VERIFY` 表示“先验证，通过则复用，不通过则重算”；输出决策中写作 `VERIFY_THEN_REUSE`。二者同义。

**注意**：`W` 是“避免的工作”，不是“省下的钱”。它必须用资源向量 `w_i` 与价格 `λ` 计算；当价格未知时，保留向量并报告敏感性，不强行合成标量。延迟与质量损失默认作为约束（`η/μ`）；若需要货币化，在 `NV` 中显式加 `η·Δlatency` 与 `μ·Δquality`，并报告敏感性。

#### 5.4.3 命题 1：验证的占优区域

由上式：

```text
NV(REUSE) − NV(VERIFY) = (1−p)·W − (q − p·q')·L + C_v
NV(VERIFY) − 0        = p·(W − q'·L) − C_l − C_v
```

因此：

1. **`VERIFY` 优于 `RECOMPUTE`** 当且仅当 `p(W − q'L) > C_l + C_v`。
2. **`REUSE` 优于 `VERIFY`** 当且仅当 `(1−p)W + C_v > (q − p q')L`。
3. 若 `q' ≈ q`（弱验证器），条件 2 变为 `C_v > (1−p)(qL − W)`。若 `qL ≤ W`（风险损失不超过节省的工作），则 `VERIFY` **永远不优于** `REUSE`；若 `p ≈ 1`（验证几乎总通过），`VERIFY` 只是在支付 `C_v`。
4. 若风险预算要求 `q' ≤ δ < q`，则 `REUSE` 不可行，`VERIFY` 可能成为唯一可行的复用动作——这时它的价值不是“比 REUSE 更好”，而是“让复用进入可行域”。

**含义**：验证不是“更安全的默认动作”，而是一个有明确占优区域的决策。实验必须报告这个区域的经验版本；如果验证器很弱或验证很贵，就应该删除 `VERIFY`，而不是把它做成默认。

#### 5.4.4 命题 2：负载影子价格产生阈值策略

在风险约束不绑定时，固定 `q, q', p, L, C_l, C_v`，令 `W = λ·w_i`。两个差值都是 `λ` 的线性函数：

```text
D_RV(λ) = NV(REUSE) − NV(VERIFY) = (1−p)·w_i·λ − (q − p q')·L + C_v
D_VR(λ) = NV(VERIFY) − 0        = p·w_i·λ − p·q'·L − C_l − C_v
```

因此最优动作在 `λ` 上单调：

```text
λ 低：RECOMPUTE
λ 中：VERIFY（仅当 λ 落在 [λ_VR, λ_RV] 且该区间非空）
λ 高：REUSE
```

阈值：

```text
λ_VR = (p·q'·L + C_l + C_v) / (p·w_i)
λ_RV = ((q − p·q')·L − C_v) / ((1−p)·w_i)
```

若 `p = 1`，`λ_RV` 的分母为 0；此时 `REUSE` 与 `VERIFY` 的比较退化为 `C_v` 与 `(q − q')L` 的比较，不随 `λ` 变化。这是命题 2 的边界情形，实验里应单独标注。

**推论 2.1**：若 `λ_RV ≤ λ_VR`，`VERIFY` 区间为空，策略退化为 `RECOMPUTE → REUSE` 的两段式。此时“验证”机制在本负载/本任务上不成立，应删除或只保留给风险预算强制的场景。

**推论 2.2**：若实验中的 `λ` 范围没有跨过 `λ_VR` 或 `λ_RV`，则“负载影子价格改变决策”的假设在本实验里不可观测。此时不能声称机制有效，只能报告“在本负载区间内未触发”，并扩大负载范围或删除 `λ`。

**推论 2.3**：固定相似度阈值等价于固定 `q` 与固定动作；当 `λ` 或依赖状态变化时，它无法移动到新的最优动作。这是“状态盲策略在高负载区间后悔更大”的形式来源（H1.1）。

#### 5.4.5 风险约束下的决策

对每个动作 `a`，除了净价值，还要给出风险上界 `q_a^UCB`。可行集：

```text
F(r) = { RECOMPUTE } ∪ {
         a ∈ {REUSE, VERIFY} :
         auth_ok(i, r) ∧ version_ok(i, r, a) ∧ q_a^UCB ≤ δ_remaining(r)
       }
```

决策：

```text
a* = argmax_{a ∈ F(r)} LCB(NV_i(a | r, S))
```

`RECOMPUTE` 始终在可行集中；风险预算只约束增量复用风险，不约束重算基线。`F(r)` 不会为空。

这是“先约束、后优化”的字典序：硬约束与风险预算优先，净价值只在可行集内比较。这样不会为了收益突破质量底线，也不会把质量损失随意货币化。

**Oracle 定义**：对每个请求，若知道真实结果（复用是否正确、真实成本、真实延迟），可以选择使实际净价值最大的动作。这个 Oracle 是**事后逐请求 Oracle**，不是可部署策略；它给出后悔的下界。另一定义是**因果可实现 Oracle**：只使用请求时刻可得的信息，但知道真实模型参数；它给出更紧的上界。两者都报告，避免用不可实现的 Oracle 夸大差距。

### 5.5 因子分解与估计职责

**原则：能算的不要学，能卡的不要校准，能作为约束的不要货币化。**

| 因子        | 定义                            | 估计方式                                                                      | 职责          | 数据来源                         | 主要失败模式                    |
|:----------- |:------------------------------- |:----------------------------------------------------------------------------- |:------------- |:-------------------------------- |:------------------------------- |
| `p_use`     | 未来窗口内被再次使用的概率      | 生存分析/风险模型；按层、租户、会话剩余轮数、对象年龄、访问频次、簇热度       | **学习**      | trace、访问日志                  | 长尾、非平稳、会话结束即失效    |
| `W`         | 命中避免的工作向量              | profiler + 成本模型（token→GPU-ms、检索调用、远端字节）；前缀感知插值         | **计算**      | 离线 profile、在线计量           | 模型/硬件/batch 变化导致漂移    |
| `C_l`       | 查询/组装成本                   | 直接测量                                                                      | **计算**      | 在线计量                         | 忽略缓存查询本身的 ANN/组装成本 |
| `C_v`       | 验证成本                        | 直接测量（judge/ACL/ANN）                                                     | **计算**      | profile                          | judge 排队、token 成本被低估    |
| `p`, `q'`   | 验证通过率与残余风险            | 校准分类器 + 验证日志                                                         | **学习+校准** | 验证结果、抽样审计               | 验证器自身漂移、标签噪声        |
| `q_sem`     | 语义误命中概率                  | 校准分类器（相似度、实体重叠、结构匹配、查询类型）                            | **学习+校准** | 复用结果、judge                  | 分布漂移、近邻对抗              |
| `q_stale`   | 依赖变化导致过期的概率          | 风险模型（版本差、变化幅度、依赖类型、年龄、来源波动）                        | **学习+校准** | 版本事件、重算标签               | 变化幅度不可观测、标签稀疏      |
| `q_model`   | 模型/配置漂移导致不可复用的概率 | 硬门 + 少量校准                                                               | **规则**      | 模型 revision                    | 同 revision 但行为变化          |
| `L`         | 一次错误的增量损失              | 任务基准 + 敏感性分析；不强行跨任务统一                                       | **标定**      | QA/对话/RAG 指标、人工/LLM judge | 任务异质、损失不可货币化        |
| `λ`         | 计算影子价格                    | 系统负载模型/第二章对偶；或外生档位                                           | **估计/外生** | 利用率、队列、容量               | 价格不可观测、估计噪声          |
| `C_hold`    | 持有成本                        | 存储单价 × 字节 × 时间 + 机会成本                                             | **计算**      | 存储计量                         | 机会成本与容量价格重复计算      |
| `C_refresh` | 刷新成本（含级联）              | RP2 提供；RP1 不输出 `REFRESH` 动作，只用它估计 `refresh_benefit` 供 RP2 参考 | **RP2 计算**  | 依赖图、重建 profile             | 级联低估（见 §6.7）             |
| `C_churn`   | 迁移/恢复/冷启动成本            | RP2/第三章反馈                                                                | **反馈**      | rescale/迁移事件                 | 与 `C_hold` 重复                |

**三类管理税（与旧设计“四类”的对应）：**

| 税种        | 何时发生            | 包含                                             | 对应因子                                      | 计入方式                        |
|:----------- |:------------------- |:------------------------------------------------ |:--------------------------------------------- |:------------------------------- |
| 在线税      | 每次请求            | 缓存查询/组装、embedding/ANN、指纹计算、决策开销 | `C_l`、部分 `C_v`                             | 每请求扣一次                    |
| 条件税      | 命中/未命中后触发   | judge、ACL、证据校验、错误回源                   | `C_v`、`qL` 中的回源部分                      | 只在实际触发时扣                |
| 后台/恢复税 | 刷新/失效/迁移/恢复 | 刷新、重建、失效传播、checkpoint、冷启动         | `C_refresh`、`C_churn`、`C_create` 的后台部分 | 按窗口摊销                      |
| 容量持有    | 持续                | 存储字节、机会成本                               | `C_hold` / `λ_B·b_i`                          | 按字节×时间；不重复计入上面三桶 |

每笔费用只进一个桶；`C_hold` 不与管理税混算。这样“净收益”不会因为重复记账而被低估。

**三个关键取舍：**

1. **`W` 与 `C_v` 是“算”出来的，不是“学”出来的。** 把可核算的成本交给回归模型，是这类论文最常见的失败原因；模型误差会污染价值，且无法审计。
2. **`q` 是“校准”出来的，不是“训练到高 AUC”就够。** 决策用的是上界/分位数，不是均值；AUC 高但校准差的模型会让风险预算失效。
3. **`L` 是“标定 + 敏感性”出来的，不是拍一个权重。** 不同任务的一次错误代价不同；本文报告 `L ∈ {1×, 10×, 100×} C_r` 的决策曲线，而不是假装存在一个通用常数。

### 5.6 有效性代数与风险分解

#### 5.6.1 四类有效性

| 有效性       | 判定                                     | 失败后果  | 处理              |
|:------------ |:---------------------------------------- |:--------- |:----------------- |
| **语义有效** | 缓存负载能回答当前请求                   | 答非所问  | `q_sem`，可验证   |
| **依赖有效** | 依赖版本满足请求要求，且内容未被语义改变 | 过期/错误 | `q_stale`，可刷新 |
| **权限有效** | 租户/会话/角色允许访问                   | 越权/泄漏 | 硬门，零容忍      |
| **模型有效** | 模型 revision、解码配置、模板兼容        | 行为漂移  | 硬门，必要时重算  |

**门序**：`auth → model → version → semantic`。前两道是硬门，不通过直接 `RECOMPUTE`；后两道是软门，进入 `q` 估计。门序不能反：先做语义匹配再做权限检查，会把越权候选暴露给匹配器，增加侧信道与计算浪费。

#### 5.6.2 风险分解与端到端校准

不要假设四类风险独立。做法是：

1. **分解用于特征与归因**：`q_sem`、`q_stale`、`q_model` 分别建模，便于消融与解释。
2. **合成用于决策**：`q_total` 直接在端到端标签上校准（复用后最终答案是否可接受），不把分解概率相乘。相乘只在“条件独立”时成立，而缓存复用恰恰不独立（同一对象、同一来源、同一租户）。
3. **报告分解与合成的差距**：如果 `Π(1−q_k)` 与 `q_total` 差距很大，说明存在相关性/交互，必须在论文中报告，而不是隐藏。

对 `rag`，端到端风险要经过“证据 → 生成”的传播：

```text
q_total^resp(rag reuse) = P(最终答案不可接受 | 复用 rag 证据)
```

它不等于 `P(证据错误)`。生成模型可能纠正坏证据，也可能被好证据误导。本文用一个**传播因子** `τ` 描述：

```text
q_total ≈ q_evid · τ + q_base · (1 − q_evid)
```

其中 `q_evid` 是证据缺陷概率，`τ` 是“坏证据导致坏答案”的概率，`q_base` 是“好证据下仍答错”的概率。`τ` 不是假设，而是通过“同一请求分别用缓存证据与 gold 证据生成”对照实验测量（E1.1b）。这是 `rag` 与 `resp` 风险语义不同的核心，也是相对 Cortex（只验证检索结果）的增量。

#### 5.6.3 依赖元数据

每个 `ValueEstimate` 附带：

```text
dependence {
  cluster_id          // 语义簇，用于错误相关性
  domain_id           // 失效域：tenant × cluster × source_doc × model_revision
  shared_deps[]       // 与其他项共享的依赖节点
  version_gap         // 当前版本与构建版本的差异摘要
  unregistered_deps   // 未登记依赖计数（应为 0）
}
```

RP1 只输出依赖元数据，不做全局风险聚合；聚合是 RP2 的职责（§6.8）。这样两个研究点的边界清晰：RP1 对“这一项、这一请求”负责，RP2 对“这一组项、这一预算”负责。

### 5.7 校准、不确定性与曝光核算

#### 5.7.1 校准方法

- **概率校准**：温度缩放 / isotonic regression；按层（`resp/rag`）、按租户档位、按版本变化与否做分组校准（Mondrian）。
- **不确定性**：split conformal 给出 `q^UCB`；按 `layer × change_flag × cluster` 分层，保证条件覆盖。
- **依赖数据**：请求不是 i.i.d.，同一会话/同一对象连续出现。使用**块 conformal**（按会话/时间块）或**聚类 bootstrap**，避免把相关样本当独立样本。
- **漂移**：监控 ECE、覆盖率、分数分布 PSI；超过阈值触发再校准，而不是等季度重训。

#### 5.7.2 报告指标

| 指标       | 定义                              | 用途                                |
|:---------- |:--------------------------------- |:----------------------------------- |
| ECE        | 分箱后“准确率 − 置信度”的加权平均 | 概率是否可信                        |
| Brier      | `E[(q − y)^2]`                    | 概率预测的整体质量                  |
| 覆盖率     | conformal 区间包含真实值的比例    | 上界是否可靠                        |
| 锐度       | 区间宽度                          | 上界是否过保守                      |
| 条件覆盖   | 按层/租户/版本变化分组的覆盖率    | 是否在某些子群失效                  |
| 预算利用率 | `E[errors]/δN`                    | 是否浪费预算（对照 Surplus 的批评） |
| 尾部违约   | 每租户/每失效域的最大违约率       | 是否集中击穿                        |

#### 5.7.3 曝光与相关性

定义对象 `i` 在窗口内的曝光 `M_i`（被复用的次数）。单请求风险 `q_i` 与曝光风险不同：

- 期望错误数：`E[errors] = Σ_i q_i M_i`（线性，仍成立）。
- 尾部/集中风险：同一对象被复用 `M_i` 次时，`P(至少一次错误) = 1 − (1−q_i)^{M_i}`；同一失效域内的错误还可能相关。
- 因此，质量预算不能只写“每请求 δ”，还要写“每失效域每窗口的违约率 ≤ δ(1+κ)”；RP1 输出 `q_i` 与 `domain_id`，RP2 做聚合（§6.8）。

这不是说 vCache 的期望保证错了；而是说：**期望保证不等于租户级/簇级尾部保证**，而后者才是产品与公平性关心的。本文把这一点作为 RP1 的风险口径，而不是重复 vCache 的定理。

#### 5.7.4 反事实与 OPE

反事实问题：我们只观测到被采取动作的结果，未采取动作的结果不可见。三种处理：

| 方法            | 做法                                            | 优点         | 缺点                       | 本文用法                             |
|:--------------- |:----------------------------------------------- |:------------ |:-------------------------- |:------------------------------------ |
| 随机留出        | 以 `ε_explore` 概率强制 `RECOMPUTE` 或 `VERIFY` | 无偏、简单   | 有质量/成本代价；样本少    | 原型期 1–5% 流量；离线期按会话块随机 |
| 倾向加权（IPS） | 用行为策略的倾向 `π_b(a; x)` 加权               | 无需额外探索 | 方差大；倾向重叠差时偏差大 | 主估计；报告有效样本量与权重截断     |
| 双稳健（DR）    | 结合结果模型与倾向                              | 偏差更小     | 需要结果模型正确           | 主报告；与 IPS 对照                  |
| 回放/仿真       | 用日志重放候选动作                              | 便宜         | 依赖仿真假设               | 辅助；只用于机制排序                 |

**必须报告**：倾向分布、权重截断、有效样本量、IPS/DR 与随机留出的差异、未观测混淆的敏感性（例如 E-value 或 Rosenbaum 界）。如果 OPE 与随机留出差异超过阈值，结论降级为“相对排序”，不报绝对收益。

### 5.8 决策规则与算法

#### 5.8.1 决策规则

```text
输入：请求 r，候选集 C(r)，系统状态 S，剩余风险预算 δ_rem
输出：动作 a*，ValueEstimate

for i in C(r):
    e = match(r, i)                       // sim, entity, structure, version gap
    if not auth_ok(i, r): continue
    if not model_ok(i, r): continue
    for a in {REUSE, VERIFY, RECOMPUTE}:
        ve[i][a] = estimate_value(i, a, e, S)
    feasible[i] = {RECOMPUTE}
    for a in {REUSE, VERIFY}:
        if version_ok(i, r, a) and q_ucb(i, a) <= δ_rem:
            feasible[i].add(a)
    a_i = argmax_{a in feasible[i]} LCB(ve[i][a].net_value)
return best (i, a_i) by LCB, or RECOMPUTE
```

#### 5.8.2 `estimate_value` 的内部顺序

```text
estimate_value(i, a, e, S):
    p_use   = survival_model(i, r, S)          // 学习；供 RP2 的 ADMIT/REFRESH 使用
    W       = dot(price(S.lambda), profile(i)) // 计算
    C_l     = lookup_cost(i)                   // 测量
    if a == REUSE:
        q   = calibrate_q(i, e, "reuse")       // 校准
        return W - C_l - q * L(i, r)
    if a == VERIFY:
        C_v, p, q_post = verify_model(i, e)    // 测量 + 校准
        return p * (W - q_post * L(i, r)) - C_l - C_v
    return 0
```

#### 5.8.3 复杂度与降级

- 每个请求对每个候选做 O(1) 特征 + O(1) 校准查表；候选数由 ANN top-k 控制（k ≤ 20）。
- 若校准服务不可用：降级为“精确匹配 + 版本/权限硬门 + 保守风险上界”，并记录降级事件。
- 若 `λ` 不可用：用固定档位价格，报告敏感性；不能假装价格已知。
- 若 `L` 不可标定：把风险作为约束（`q^UCB ≤ δ`），不做损失货币化；决策规则退化为“可行集内最大化 `W − C_l − C_v`”。

### 5.9 数据模型与接口

RP1 的核心输出（完整 schema 见附录 A）：

```text
ValueEstimate {
  item_id, request_id, action
  avoided_work { gpu_ms, tokens_in, tokens_out, retrieval_calls, remote_bytes }
  priced_benefit { mean, lcb, ucb }
  costs { lookup, verify, hold_alloc, refresh_alloc, churn_alloc }
  risk { q_sem, q_stale, q_model, q_total, q_ucb }
  loss { answer, stale, auth, security }
  net_value { mean, lcb, ucb }
  decision                  // REUSE | VERIFY_THEN_REUSE | RECOMPUTE
  binding_constraint        // auth | version | risk | capacity | verify_throughput | none
  reason_codes[]
  sensitivities { dNV_dlambda, dNV_drisk_budget, dNV_dcapacity,
                  dNV_dverify_throughput, dNV_dversion, dNV_ddependency }
  dependence { cluster_id, domain_id, shared_deps[], version_gap, unregistered_deps }
  model_version, calibration_version
}
```

**为什么需要 `sensitivities`**：RP2 不只要“这个动作值多少”，还要知道“价格/预算变化时它会怎么变”。没有敏感性，RP2 只能重新调用 RP1，无法做对偶更新或快速重排。

**为什么需要 `binding_constraint`**：它让 RP2 知道该调哪个价格。如果大多数决策被 `risk` 绑定，应提高风险价格/收紧预算；如果被 `verify_throughput` 绑定，应扩容判官或降低验证频率。

1. **问题形式化**：把“缓存价值”从对象属性改写为 `(item, request, action, dependency, load)` 的函数，并给出可检验的阈值结构（命题 1–2）。
2. **风险口径**：把 `q_sem/q_stale/q_model` 分解用于归因，把 `q_total` 端到端校准用于决策；把曝光/失效域引入质量预算，区分“期望正确”与“租户级尾部正确”。
3. **验证动作的价值理论**：给出 `VERIFY` 的占优/被占优条件，避免把验证当默认。
4. **评估协议**：用决策后悔、风险预算兑现、决策翻转率替代单纯 MAE/AUC；用 OPE + 随机留出验证反事实。
5. **接口**：`ValueEstimate` 的敏感性、绑定约束与依赖元数据，使 RP2 能做价格分配而不是排序。

**不主张**：新的相似度模型、新的向量索引、新的 KV 机制、新的质量保证定理。RP1 的贡献是决策层，不是匹配层。

### 5.13 失败条件

| 失败条件         | 判定                                                | 处理                                             |
|:---------------- |:--------------------------------------------------- |:------------------------------------------------ |
| 复用机会不足     | P0 中语义/结构复用率 < 5%，或可避免工作 < 管理税    | 主对象转向 `rag + 文档更新`；`resp` 降为精确匹配 |
| 验证经济学不成立 | `C_v` 高于命中收益，或 `p` 很低导致 `VERIFY` 被支配 | 删除 `VERIFY`；只对高风险高价值对象保留          |
| 校准失败         | ECE > 0.10、覆盖率 < 0.85、版本变化子集条件覆盖崩溃 | 退化为保守硬门 + 精确匹配；不报“风险预算”结论    |
| 影子价格无效     | `λ` 扫描不跨阈值，翻转率 < 5%                       | 删除 `λ`，退化为固定档位；在论文中写负结果       |
| OPE 偏差过大     | IPS/DR 与随机留出差异超过阈值                       | 只报相对排序；增加探索比例；缩小结论范围         |
| `rag` 传播不可测 | 无法分离 `q_evid` 与 `q_prop`                       | 只做 `resp`，`rag` 降为“证据新鲜度门”            |

### 5.14 风险与裁剪

**风险：**

1. **标签稀疏**：错误复用是稀有事件；校准需要足够正例。缓解：主动采样、分层抽样、合成近邻对抗样本、用 judge 而不是人工全标。
2. **judge 成本/漂移**：把 judge 成本计入 `C_v`，抽样人工校验；judge 版本变化触发再校准。
3. **特征泄漏**：`sim` 与标签可能来自同一匹配器，导致“校准”其实是“匹配器的后处理”。缓解：固定匹配器、跨匹配器验证、留出匹配器版本。
4. **租户异质性**：一个全局校准器可能在某些租户失效。缓解：分层校准 + 最少样本阈值 + 回退到全局。
5. **价格不可观测**：`λ` 是估计值。缓解：报告敏感性、用档位而非连续值、与第二章对偶对照。

**裁剪顺序（从后往前删）：**

```text
1. 删除 q_model 的细粒度校准（保留硬门）
2. 删除 q_sem 的学习，改用相似度阈值 + 保守上界
3. 删除 λ 的连续估计，改用 3 档价格
4. 删除 rag 的传播因子，改为证据新鲜度门
5. 删除 VERIFY，只保留 REUSE/RECOMPUTE
6. 删除 resp，只保留 rag
7. 删除整个 RP1 的动作价值，退回“精确匹配 + 版本门”
```

最后一级是保底方案：即使 RP1 全部降级，系统仍能靠“精确匹配 + 依赖版本 + 权限”提供正确但收益较小的缓存。这保证论文不会因为一个机制失败而没有可交付物。

## 6. 研究点二：依赖感知的缓存生命周期联合控制

### 6.1 标题、一句话与职责边界

**中文标题：依赖感知的缓存生命周期联合控制。**

**英文标题：Dependency-Aware Joint Lifecycle Control for Agent Caches.**

**一句话：** 在容量、质量风险、新鲜度、权限与验证吞吐约束下，利用 RP1 的动作价值及其敏感性，联合决定准入、复用、验证、刷新、降级、失效与淘汰，并对刷新造成的下游失效进行级联计价与调度。

**职责边界：**

- RP2 负责**控制**：`(所有 CacheItem, 依赖图, 预算, 价格) → 动作集合 + 资源分配`。
- RP2 不重新定义价值：它消费 RP1 的 `ValueEstimate`，但**不把 RP1 的分数当作唯一排序键**；它有自己的约束价格、依赖闭包、刷新级联与失效域风险。
- RP2 不研究匹配器，也不研究 KV：它只操作逻辑对象的元数据与负载。
- RP2 必须能独立回答一个问题：**“在没有 RP1 的精确价值时，仅靠依赖感知与风险预算，生命周期控制是否仍然优于 LRU/TTL/LCFU？”** 这是它作为独立研究点的底线。

**结构对照：**

```text
问题：有了价值，仍不知道何时准入、刷新、降级、失效、淘汰。
洞察：生命周期动作竞争容量、风险预算与验证吞吐；刷新会杀死下游命中；失效会沿依赖图传播。
方法：共享价格 + 依赖闭包 + 刷新级联 + 失效域风险预算 + 事件驱动控制。
接口：LifecycleDecision（动作、资源、风险记账、级联影响、幂等键）。
实验：淘汰、准入、刷新、失效、联合控制、风险组合、Flink 恢复。
结论（待验证）：联合控制优于任何单动作启发式；刷新级联值得建模；依赖失效能减少陈旧/越权复用而不显著损伤性能。
边界：不解决匹配质量、KV 驻留、算力扩缩容、全局调度。
```

### 6.2 研究问题与可证伪假设

**核心研究问题：**

> 在容量、质量、新鲜度和权限约束下，如何利用 RP1 的价值输出，联合决定缓存项的准入、复用、验证、刷新、降级和淘汰，并处理刷新造成的下游失效？

**子问题：**

1. 生命周期动作有哪些？每个动作由什么事件触发？
2. 准入、刷新和淘汰如何共享同一价值信号，而不是各用一套启发式？
3. 如何限制质量风险预算和无效复用频率？
4. 如何表示和传播依赖失效？
5. 刷新一个 `ctx` 或 `rag` 项会杀死哪些 `resp` 命中，如何计算刷新总成本？
6. 热对象应冻结、增量更新、主动刷新还是惰性失效？
7. 多租户、权限变化和版本变化如何影响生命周期？
8. 如何映射到 Flink keyed state、timer、依赖索引、checkpoint 和 rescale？
9. 相对 LRU、LFU、LCFU、HARF、固定 TTL、vCache 式门控和成本感知淘汰，独立贡献是什么？

**可证伪假设：**

| 编号 | 假设                                                                                    | 可观测预测                                                             | 否定条件                                         | 对应实验   |
|:---- |:--------------------------------------------------------------------------------------- |:---------------------------------------------------------------------- |:------------------------------------------------ |:---------- |
| H2.1 | 刷新级联成本足够大，忽略它会导致刷新时机系统性偏早/偏晚                                 | `M(i)=C_refresh_now/C_r` 的分布右偏；计入级联后刷新次数/净收益显著变化 | `M(i)` 中位数 <1.2 且决策变化 <5%                | E2.3       |
| H2.2 | 共享价格下的联合控制优于任何单动作启发式                                                | 净收益/违约率至少一项显著优于“最佳单动作 + 价值排序”                   | 与最佳单动作差异在噪声内                         | E2.5       |
| H2.3 | 失效域风险预算比逐项风险阈值更能防止集中违约                                            | 在相同总违约率下，最大租户/域违约率更低                                | 逐项阈值已达到同等尾部控制                       | E2.6       |
| H2.4 | 依赖闭包失效比“全局即时失效”或“无依赖图”更优                                            | 陈旧复用率更低，且性能损失更小                                         | 闭包失效的陈旧率与全局失效无差异，或性能损失更大 | E2.4       |
| H2.5 | 依赖感知淘汰（考虑扇出/子树）优于只看对象自身的价值密度                                 | 在相同容量下，重建成本/净收益更好                                      | 与价值密度/LRU 无显著差异                        | E2.1、E2.7 |
| H2.6 | Flink keyed state/timer/checkpoint/rescale 能以可接受开销实现上述控制，并保持失效一致性 | 开销 <10%，rescale 后零陈旧复用，恢复时间在门槛内                      | 开销 >20% 或出现陈旧复用                         | E4.1、E4.2 |

### 6.3 研究动机：单动作启发式的四个失效

**失效 1：淘汰策略看不到刷新级联。**
Cortex 的 LCFU 用 `log(Freq)·log(Cost)·log(Latency)·log(Staticity)/Size` 排序，命中率 0.86 低于 LFU 的 0.89，但吞吐更高（NSDI 2026）。这说明“淘汰分数”可以不是命中率导向。但它仍然只看对象自身：淘汰一个 `rag` 文档块，可能让依赖它的多个 `resp` 答案失效；淘汰一个 `ctx` 摘要，可能让整条会话的回答缓存失效。LCFU/LRU/LFU 都没有“子树/扇出”的概念。

**失效 2：固定 TTL 看不到版本事件与刷新调度。**
ChurnBench 用四源企业数据时间线证明：在按计划刷新时，缓存年龄不预测陈旧；关闭分层刷新后，28 天窗口的新鲜度错误从 4 升到 45（arXiv:2609.11515v2）。这说明“TTL 长度”不是核心，**刷新调度与版本事件**才是。固定 TTL 会把所有对象当成同质，忽略文档波动率、下游扇出与刷新成本。

**失效 3：价值排序退化。**
如果 RP2 只是“按 RP1 的 `NV` 从大到小淘汰”，它等价于一个加权 LRU/GDSF；它无法回答：

- 一个高价值但高扇出的 `ctx` 要不要刷新？
- 一个低价值但被多个 `resp` 依赖的 `rag` 块要不要保留？
- 验证吞吐被谁占用？准入是否值得花风险预算？
- 权限变化时，是全局失效还是只失效相关子树？
  这些都需要**动作集合 + 约束 + 依赖图**，而不是一个排序键。

**失效 4：风险预算被热对象击穿。**
如果同一错误对象被同一租户反复复用，逐请求的 δ 约束不能防止该租户连续看到错误；需要失效域/曝光预算（§6.8）。这是 RP2 独立于 RP1 的风险控制职责。

### 6.4 形式化：约束、动作与目标

#### 6.4.1 决策变量

在一个决策 epoch（事件触发，不是固定窗口），对每个 `i` 选择至多一个动作 `a ∈ A_RP2`：

```text
A_RP2 = { ADMIT, REUSE, VERIFY, REFRESH, DEMOTE, INVALIDATE, EVICT, FREEZE }
```

`REUSE` 与 `VERIFY` 是读路径动作；`ADMIT/REFRESH/DEMOTE/INVALIDATE/EVICT/FREEZE` 是状态动作。一次请求可能同时触发“读动作 + 后续状态动作”（例如 `VERIFY` 失败后 `REFRESH`），但主决策仍可分解为“当前请求的动作”与“后台状态动作”。

#### 6.4.2 约束

```text
(C1) 容量：      Σ_i b_i · 1[resident(i)] ≤ B
(C2) 风险预算：  Σ_g q_g^UCB · M_g(H) ≤ δ · N(H)
(C3) 新鲜度：    ∀i, P(stale served | i) ≤ ε(layer(i))
(C4) 权限：      ∀i, scope(i) ⊆ scope(r)   （硬约束，零容忍）
(C5) 验证吞吐：  Σ_i v_i · 1[verify(i)] ≤ V
(C6) 依赖一致：  ∀i, REUSE(i) ⇒ ∀d∈D_i, vv_i[d] ≥ required_r[d]
                 且 i 的所有祖先均非 INVALID
(C7) 动作优先：  INVALID 不得 REUSE；REFRESH 后必须重新 ADMIT 或标记 ACTIVE
(C8) 登记完整：  ADMIT(i) ⇒ D_i 已登记且 provenance 完整
```

#### 6.4.3 目标

```text
max_{x} Σ_i Σ_a x_{i,a} · [ NV_i(a) − λ_B·b_i(a) − λ_R·ρ_i(a) − λ_V·v_i(a) ]
s.t. (C1)–(C8)
```

其中：

- `NV_i(a)` 来自 RP1；对 `ADMIT/REFRESH/EVICT` 等状态动作，`NV` 是“相对不做的**毛**期望净价值”（尚未扣容量/风险/验证价格），由 RP1 的价值函数在相应状态上求值或由 RP2 用同一接口近似。
- `b_i(a)` 是动作占用的容量（`EVICT` 为负）。
- `ρ_i(a)` 是动作的**质量风险**记账（`REUSE/ADMIT` 为 `q_i^UCB·E[M_i]`；`REFRESH` 为刷新窗口内的残余风险；`EVICT/INVALIDATE` 为 0，重建成本已计入 `NV`）。
- `v_i(a)` 是验证吞吐占用。
- `λ_B, λ_R, λ_V` 是约束的对偶价格，由 RP2 在线更新。

**状态动作的 `NV` 如何得到**（单位统一：读动作是每请求，状态动作是每窗口；比较时统一乘/除 `E[M_i]`）：

```text
NV_i(ADMIT)      = E[M_i]·LCB(NV_i(REUSE)) − C_create(i)
NV_i(REFRESH)    = −C_refresh_total(i) + (q_stale_before − q_stale_after)·L·E[M_i]
NV_i(EVICT)      = −E[future rebuild cost(i)]
NV_i(DEMOTE)     = −Δquality_loss(i)
NV_i(FREEZE)     = −q_stale·L·E[M_i] + avoided_refresh_cost(i)
NV_i(INVALIDATE) = −C_inv(i) + avoided_stale_or_unauthorized_loss(i)
```

其中 `ADMIT` 是“未来复用价值的期望减去创建成本”；`REFRESH` 是“负的级联刷新成本加上避免的陈旧损失”；`EVICT` 是“负的未来重建期望”。这些都是近似，但都由 RP1 的同一组量（`p_use`、`NV(REUSE)`、`q_stale`、`L`）拼成，不引入第二套价值定义。容量、风险与验证价格只在 `I_i(a)` 中扣一次，不在 `NV` 中重复扣；硬约束动作（权限/模型失效）不参与打分，直接执行。

**关键区别**：RP1 的 `λ` 是**计算资源价格向量**（GPU-ms 为锚）；RP2 的 `λ_B/λ_R/λ_V` 是**缓存资源价格**（每字节、每单位风险、每毫秒验证）。两组价格不能混为一个。RP2 通过调整后者来分配缓存资源，通过消费前者来给 `NV` 定价。

#### 6.4.4 与“价值排序”的区别

如果令 `λ_B=λ_R=λ_V=0`，且只允许 `EVICT`，上面的目标退化为“按 `NV` 排序淘汰”——这正是我们要避免的退化。RP2 的独立性来自：

1. **动作集合**：不是只排序，而是选择动作；`REFRESH/INVALIDATE/FREEZE/DEMOTE` 不在排序键的空间里。
2. **约束**：容量、风险、验证吞吐、依赖一致性共同决定可行集；排序键无法表达“这个对象不能淘汰，因为它的子对象还在”。
3. **级联**：`REFRESH/EVICT` 的成本包含下游；排序键只看自身。
4. **价格**：`λ_B/λ_R/λ_V` 是状态相关的，不是静态权重；它们把“现在缺什么”编码进决策。

### 6.5 共享价格与联合索引

#### 6.5.1 拉格朗日索引

对约束 (C1)(C2)(C5) 引入价格，得到每个 `(i,a)` 的索引：

```text
I_i(a) = NV_i(a)
         − λ_B · b_i(a)
         − λ_R · ρ_i(a)
         − λ_V · v_i(a)
```

在每个 epoch：

1. 对每个 `i`，在局部可行动作集中选 `a_i = argmax_a I_i(a)`；
2. 全局检查容量/风险/验证吞吐；若超限，按 `I_i` 最低的动作回退（`EVICT`/`DEMOTE`/`RECOMPUTE`）；
3. 用对偶上升更新价格。

这是一个**贪心 + 对偶**的近似，不保证全局最优；本文用离线 ILP/动态规划在小子例上量化贪心 gap（E2.5），并报告 gap 随规模的变化。对硕士论文，这比声称“最优”更可信。

#### 6.5.2 对偶更新

```text
λ_B ← max(0, λ_B + η_B · (usage_B − B) / B)
λ_R ← max(0, λ_R + η_R · (usage_R − δN) / (δN))
λ_V ← max(0, λ_V + η_V · (usage_V − V) / V)
```

工程约束：

- **平滑**：`λ ← (1−α)λ_old + αλ_new`，`α ∈ [0.1, 0.3]`，避免价格抖动。
- **钳制**：设置上下界，防止一个约束把价格推到无穷。
- **滞后**：价格更新有冷却窗口；窗口内不重复调价。
- **可观测**：每个价格都记录“当前绑定约束”和“利用率”，便于调试。

#### 6.5.3 价格的含义与可解释性

| 价格     | 高值意味着   | 控制器行为                                            | 对应实验   |
|:-------- |:------------ |:----------------------------------------------------- |:---------- |
| `λ_B` 高 | 容量稀缺     | 更激进地淘汰/降级；提高准入门槛                       | E2.1、E2.2 |
| `λ_R` 高 | 风险预算紧张 | 更少 `REUSE`；更多 `VERIFY`/`RECOMPUTE`；按失效域分配 | E2.6       |
| `λ_V` 高 | 验证吞吐稀缺 | 只对高价值对象验证；其余走保守门                      | E2.2、E2.5 |

这张表也是论文中“为什么不是加权求和”的回答：价格不是拍定的权重，而是约束的对偶，随系统状态变化，并且可以被实验单独操纵。

### 6.6 依赖闭包、版本向量与失效代数

#### 6.6.1 依赖图

```text
G = (V_dep, E_dep)
V_dep = 文档、摘要、事实、模板、模型、权限、工具
E_dep: d → i 表示 i 依赖 d
D_i = ancestors(i)          // 传递闭包
Desc(d) = descendants(d)    // 反向闭包
```

依赖图必须支持：

- `add_edge(d, i)`：登记依赖；
- `descendants(d)`：失效传播；
- `ancestors(i)`：读路径版本检查；
- `topological_order()`：刷新调度按拓扑序，先刷新上游再刷新下游；
- `subtree(d)`：级联计价与合并刷新。

#### 6.6.2 失效代数

| 事件                          | 判定               | 传播                                               | 允许的动作                          |
|:----------------------------- |:------------------ |:-------------------------------------------------- |:----------------------------------- |
| 权限变化                      | 硬失效             | `Desc(acl_node)` 全部 `INVALID`                    | `INVALIDATE`、`EVICT`；禁止 `REUSE` |
| 模型 revision 变化            | 硬失效             | 所有 `model` 依赖的项 `INVALID`                    | `INVALIDATE`、`REFRESH`             |
| 请求要求的最低版本高于 `vv_i` | 硬失效（对该请求） | 只影响该请求                                       | `RECOMPUTE`/`REFRESH`               |
| 文档内容变化                  | 软失效             | `Desc(doc)` 标记 `SUSPECT`                         | `VERIFY`、`REFRESH`、`FREEZE`       |
| 摘要/事实重写                 | 软失效（可能硬）   | `Desc(ctx)` 标记 `SUSPECT`；若指纹变化则 `INVALID` | `VERIFY`、`REFRESH`、`INVALIDATE`   |
| 模板版本变化                  | 硬失效             | `Desc(template)` 全部 `INVALID`                    | `INVALIDATE`、`REFRESH`             |
| 工具指纹变化                  | 硬失效（`act`）    | `Desc(tool)` 全部 `INVALID`                        | `INVALIDATE`、`REFRESH`             |

**软失效的读路径**：`SUSPECT` 项不能直接 `REUSE`，但可以 `VERIFY`；验证通过后临时放行，并把结果写回风险状态。这样避免“一有版本变化就全量重算”的抖动，也避免“忽略版本变化”的错误复用。

#### 6.6.3 一致性不变量

**不变量 INV-1（无陈旧复用）**：
对任意被 `REUSE` 的项 `i` 和请求 `r`，若 `d ∈ D_i ∩ required[r]`，则 `vv_i[d] ≥ required_r[d]`；且 `i` 的祖先中没有 `INVALID`。

**不变量 INV-2（失效单调）**：
依赖 `d` 的版本单调递增；`i` 的 `vv_i[d]` 不会在没有 `REFRESH` 的情况下被“伪造”为更高版本。

**不变量 INV-3（幂等失效）**：
对同一个 `(item_id, dep_node, version)` 的失效通知，重复执行不改变状态；用 `(item_id, dep_node, version)` 做去重键。

**不变量 INV-4（rescale 后仍成立）**：
rescale 后，`dep_epoch` 与 `vv` 从 checkpoint/状态后端恢复；任何在途失效事件在恢复后重放；不允许因分区重分配而出现“旧版本被当作新版本”。

这些不变量是 §8.6 的验收条件，也是 RP2 相对“启发式 TTL”的硬区别：TTL 无法保证 INV-1。

### 6.7 刷新级联与刷新调度

#### 6.7.1 刷新不是单对象操作

刷新一个 `ctx` 摘要或 `rag` 文档块，会改变依赖它的 `resp` 答案的 `vv`；如果 `resp` 的 `prompt_fingerprint` 包含该摘要，则 `resp` 直接失效。设 `Desc(i)` 为依赖 `i` 的下游项，`m_j(H)` 为下游 `j` 在窗口 `H` 内的期望命中次数（由 RP1 的 `p_use` 给出），`C_rebuild(j)` 为重建成本，`L_gap(j)` 为不可用期间的质量/延迟损失，`C_inv(j)` 为失效元数据成本。

**立即刷新：**

```text
C_now(i) = C_r(i) + Σ_{j∈Desc(i)} [ m_j(H)·(C_rebuild(j) + L_gap(j)) + C_inv(j) ]
```

**惰性失效：**

```text
C_lazy(i) = Σ_{j∈Desc(i)} [ 1[j 在窗口内被请求]·(C_rebuild(j) + L_gap(j)) + C_inv(j) ]
```

惰性失效只在下游真的被请求时重建；如果下游很冷，它更便宜。但它有一个风险：在重建之前，必须确保读路径不会把 `SUSPECT` 当 `VALID`；否则会陈旧复用。

**冻结：**

```text
C_freeze(i) = q_stale(i,H)·L·M_i(H) + C_hold(i,H)
```

冻结不重算，只对版本兼容的请求开放复用；它适合“高扇出、低波动、重建昂贵”的对象。但冻结必须配合版本检查，否则会变成“永久陈旧”。

**增量更新：**

```text
C_inc(i) = C_r_inc(i) + residual_risk(i) + partial_cascade(i)
```

增量更新只重算变化部分（例如摘要的局部修订、文档的 diff），成本低于全量刷新，但可能留下残余不一致；需要 `q_stale` 校准。

**决策**：

```text
a_refresh(i) = argmin { C_now, C_lazy, C_freeze, C_inc }
s.t. 新鲜度/风险约束
```

#### 6.7.2 命题 3：级联乘数

定义：

```text
M(i) = C_now(i) / C_r(i)
     = 1 + [ Σ_{j∈Desc(i)} m_j(H)·(C_rebuild(j)+L_gap(j)) + C_inv(j) ] / C_r(i)
```

- 若 `M(i) ≈ 1`，刷新近似单对象，固定 TTL/立即刷新足够。
- 若 `M(i) ≫ 1`，刷新成本由下游主导；此时应立即刷新只在“陈旧损失 > 级联成本”时成立，否则惰性/冻结更优。
- `M(i)` 的分布是 RP2 是否存在独立贡献的**判定性证据**（E2.3 / G3）。如果中位数 <1.2，级联建模不值得作为核心机制。

**推论 3.1**：高扇出（`|Desc(i)|` 大）、高下游命中（`m_j` 大）、高重建成本（`C_rebuild` 大）的对象，应优先考虑 `FREEZE` 或 `LAZY`；低扇出、高陈旧损失的对象，应优先 `REFRESH_NOW`。这给出了一个可执行的启发式，但它仍然由统一的价值比较产生，不是硬编码规则。

#### 6.7.3 刷新合并

如果多个待刷新项共享下游子树，逐个刷新会重复重建同一批下游项。定义刷新集合 `S`：

```text
C_set(S) = Σ_{i∈S} C_r(i) + Σ_{j∈Desc(S)} [ m_j(H)·(C_rebuild(j)+L_gap(j)) + C_inv(j) ]
```

其中 `Desc(S) = ∪_{i∈S} Desc(i)`。按“边际成本/边际收益”贪心选择 `S`，并受刷新吞吐约束。这就是**子树合并刷新**（subtree-coalesced refresh）。

它与“逐对象 TTL”的区别：

- TTL 不知道下游共享，可能在同一分钟内刷新多个上游，重复重建同一批下游；
- 合并刷新按依赖子树调度，减少重复重建与抖动；
- 合并刷新需要拓扑序与依赖图，是 RP2 的独立机制。

#### 6.7.4 刷新调度

刷新不是“到期就做”，而是按优先级排队：

```text
priority(i) = [q_stale(i)·L·M_i(H) − C_refresh(i)] / C_refresh(i)
```

- 分子是“不刷新的期望损失 − 刷新成本”，分母是成本（单位成本的净收益）。
- 高优先级先刷新；低优先级进入惰性失效或冻结。
- 刷新任务异步执行，不阻塞读路径；刷新期间对象标记 `REFRESHING`，读路径可选择旧版本（带风险）或重算。

### 6.8 风险组合、失效域与曝光预算

#### 6.8.1 为什么逐项阈值不够

逐项阈值 `q_i ≤ δ` 控制的是“每个请求/每个对象的边缘风险”。它不能控制：

- **集中风险**：同一租户/同一语义簇的多个对象同时失效，导致连续错误；
- **曝光放大**：一个错误对象被复用 `M` 次，用户看到 `M` 次错误；
- **相关性**：同一源文档、同一模型 revision、同一模板的多个对象可能一起错。

#### 6.8.2 失效域

定义失效域：

```text
g = (tenant_id, semantic_cluster, source_doc, model_revision)
```

同一 `g` 内的对象被视为“可能相关失败”。域风险用 Beta-Binomial 估计：

```text
q_g = (errors_g + α0) / (exposures_g + α0 + β0)
```

小样本时向全局均值收缩（层次贝叶斯/经验贝叶斯）；`q_g^UCB` 用 Beta 后验分位数。这样避免“某个域只出现 1 次错误就被判死”，也避免“某个域样本少就被低估”。

#### 6.8.3 预算约束

```text
Σ_g q_g^UCB · M_g(H) ≤ δ · N(H)
```

并对每个租户加一条公平上限：

```text
q_g^UCB · M_g(H) ≤ δ_tenant · N_tenant(H)   ∀g with tenant(g)=t
```

`δ_tenant` 默认等于 δ；若租户有更严格 SLA，取更小值。

如果全局预算与租户上限冲突，优先满足租户上限（公平/合规优先），再在剩余预算内分配。

#### 6.8.4 风险分配

把风险预算视为一种资源，用价格 `λ_R` 分配：

- 每个域 `g` 的“风险价格”可以统一，也可以按租户公平做域特定价格；
- 高 `NV per unit risk` 的域获得更多预算；
- 低价值/高风险域被限制复用，转为 `VERIFY` 或 `RECOMPUTE`。

这与“逐项阈值”的区别：逐项阈值是局部的、无预算的；域预算把“总风险”当作全局约束，能防止热对象/热租户击穿。

#### 6.8.5 准入与淘汰的风险记账

**准入**：

```text
ADMIT(i) iff
  LCB(NV_i(REUSE))·E[M_i]
    > C_create(i) + λ_B·b_i + λ_R·q_i^UCB·E[M_i] + λ_V·E[v_i]
  ∧ dependency_registered(i)
  ∧ provenance_complete(i)
  ∧ auth_scope_known(i)
```

**淘汰**：

```text
I_i = [LCB(NV_i(REUSE))·E[M_i] − λ_R·q_i^UCB·E[M_i]] / b_i − λ_B
```

淘汰 `I_i` 最低的项；但必须做依赖检查：

- 若 `i` 有下游 `j`，淘汰 `i` 会让 `j` 失效；需要把 `j` 的重建成本计入 `i` 的淘汰成本；
- 或者优先淘汰叶子（无下游）项；
- 或者整棵子树一起淘汰（如果下游也低价值）。

这就是**依赖感知淘汰**：它不是“按对象自身价值密度排序”，而是“按对象 + 子树的净价值排序”。

### 6.9 算法与伪代码

#### 6.9.1 主事件循环

```text
on_event(e):
    update_state(e)
    switch e.type:
        case VERSION_CHANGE:  propagate_invalidation(e)
        case REQUEST_ARRIVAL: handle_request(e)
        case TIMER_EXPIRE:    handle_timer(e)
        case CAPACITY_PRESSURE: handle_capacity(e)
        case AUTH_CHANGE:     hard_invalidate(e)
        case RESCALE:         restore_and_validate(e)
    update_prices()
    emit_metrics_and_logs()
```

#### 6.9.2 失效传播

```text
propagate_invalidation(e):
    closure = descendants(e.node)
    for i in topological_order(closure):
        if e.kind in {AUTH, MODEL, TEMPLATE, TOOL}:
            state[i] = INVALID
        else:
            state[i] = SUSPECT
        add_pending_invalidation(i, e.node, e.new_version)
        schedule_review(i, now + review_delay(i))
```

#### 6.9.3 请求处理

```text
handle_request(r):
    candidates = ann_lookup(r, top_k=20)
    best = (None, RECOMPUTE, -inf)
    for i in candidates:
        if not auth_ok(i, r) or not model_ok(i, r): continue
        if state[i] == INVALID: continue
        ve = RP1.estimate(i, r, S, remaining_budget)
        for a in {REUSE, VERIFY}:
            if not dependency_ok(i, r, a): continue
            if ve[a].risk.ucb > remaining_budget(r): continue
            idx = I_i(a)          // shared price index
            if idx > best.score: best = (i, a, idx)
    if best.item is None: return RECOMPUTE
    return execute(best)
```

#### 6.9.4 容量压力

```text
handle_capacity():
    while usage_B > B:
        candidates = resident_items()
        // 先尝试降级，再淘汰；按“子树净价值/字节”升序
        i = argmin_{i in candidates} subtree_value(i) / b_i
        if can_demote(i) and demote_gain(i) > evict_gain(i):
            DEMOTE(i)
        else:
            EVICT(subtree_or_item(i))
```

#### 6.9.5 刷新决策

```text
handle_timer(i):
    if state[i] == SUSPECT or due(i):
        c_now  = C_r(i) + cascade_cost(i, H)
        c_lazy = lazy_cost(i, H)
        c_frz  = freeze_cost(i, H)
        c_inc  = incremental_cost(i, H)
        a = argmin({c_now, c_lazy, c_frz, c_inc}) subject to freshness
        if a == REFRESH:
            enqueue_refresh(i, priority(i))
        elif a == FREEZE:
            state[i] = FROZEN
        else:
            state[i] = SUSPECT   // lazy
```

#### 6.9.6 价格更新

```text
update_prices():
    if now < next_price_update: return
    usage_B, usage_R, usage_V = window_usage()
    λ_B = clamp(smooth(λ_B, λ_B + η_B*(usage_B-B)/B), 0, λ_B_max)
    λ_R = clamp(smooth(λ_R, λ_R + η_R*(usage_R-δN)/(δN)), 0, λ_R_max)
    λ_V = clamp(smooth(λ_V, λ_V + η_V*(usage_V-V)/V), 0, λ_V_max)
    next_price_update = now + cooldown
```

#### 6.9.7 复杂度

- 请求路径：ANN top-k + 每候选 O(1) 检查；依赖检查 O(|D_i|)，`|D_i|` 通常 ≤ 10。
- 失效传播：O(|Desc(d)|)；高扇出节点用批量/异步处理。
- 容量压力：堆/排序 O(n log n)，可增量维护。
- 价格更新：O(1)，按窗口。
- 刷新调度：优先队列 O(log n)。

### 6.10 Flink 状态与事件流程

#### 6.10.1 拓扑

```text
RequestSource
  → keyBy(tenant_id)
  → ReuseGate (broadcast dependency index, price vector)
  → Sink / Response

VersionSource
  → keyBy(dep_node_id)
  → ReverseIndex (dep → items)
  → keyBy(item_id)
  → Invalidator / LifecycleController
  → Sink (invalidation notifications, refresh jobs)

TimerService
  → keyBy(item_id)
  → LifecycleController

MetricsSource
  → keyBy(tenant_id)
  → PriceUpdater
  → Broadcast price vector
```

**为什么两段式**：`VersionSource` 按依赖节点分区，`RequestSource` 按租户分区；失效事件需要先查反向索引得到 `item_id`，再路由到 item 分区。这样避免“每个版本事件广播给所有 item 分区”的 O(N) 扫描。

#### 6.10.2 状态

| 状态           | 类型                               | 键             | 内容                       | 是否进 checkpoint                      |
|:-------------- |:---------------------------------- |:-------------- |:-------------------------- |:-------------------------------------- |
| `ItemMeta`     | `MapState<ItemId, CacheItemMeta>`  | tenant/item    | 生命周期、版本、风险、统计 | 是                                     |
| `DepMeta`      | `MapState<DepNodeId, DepMeta>`     | dep_node       | 当前版本、波动率、失效域   | 是                                     |
| `ReverseIndex` | `MapState<DepNodeId, Set<ItemId>>` | dep_node       | 依赖 → 下游项              | 是（可重建，但进 checkpoint 更快恢复） |
| `DomainRisk`   | `MapState<DomainId, DomainRisk>`   | domain         | 曝光、错误、后验           | 是                                     |
| `Budget`       | `ValueState<Budget>`               | tenant         | 容量/风险/验证预算         | 是                                     |
| `Prices`       | `ValueState<PriceVector>`          | 全局 broadcast | `λ_B, λ_R, λ_V`            | 是                                     |
| `Timers`       | `ValueState<Long>`                 | item/domain    | 复审、过期、刷新重试       | 由 Flink timer 恢复                    |
| `Outbox`       | `ListState<PendingInvalidation>`   | item           | 待发送失效通知             | 是（幂等）                             |
| `ModelParams`  | `ValueState<CalibrationParams>`    | 全局           | 校准版本、阈值             | 是                                     |

#### 6.10.3 事件时间与水位线

- 版本事件使用事件时间；读路径使用处理时间做快速检查。
- 失效事件允许延迟到达：用 `version` 比较而不是“到达顺序”，保证晚到的旧版本不会覆盖新版本。
- 水位线用于风险窗口与价格窗口；窗口结束时触发一次预算结算。

#### 6.10.4 checkpoint 与恢复

- **checkpoint 内容**：上表所有“是”；外部 ANN/负载存储不进 checkpoint，但记录 `index_generation` 与可重建指针。
- **恢复**：先从 checkpoint 恢复元数据与价格；再校验外部索引 generation；若不一致，触发重建/降级。
- **exactly-once 边界**：元数据状态 exactly-once；外部失效通知 at-least-once + 幂等键；不声称端到端 exactly-once。
- **恢复后的读路径**：在 `index_generation` 未校验前，禁止 `REUSE`，只允许 `RECOMPUTE`/`VERIFY`；避免“状态恢复了但索引没恢复”导致的错误命中。

#### 6.10.5 rescale

- **key group 重分配**：item 状态随 key 迁移；依赖索引按 `dep_node` 重新分区；反向索引可能需要重建（或从 checkpoint 恢复后重算）。
- **timer 恢复**：Flink 会恢复 registered timers；需要去重，避免重复刷新。
- **in-flight 事件**：版本事件可能跨 rescale；用 `version` 与 `event_id` 去重。
- **验收**：rescale 后 5 分钟内命中率恢复至基线 ±5%；零陈旧复用；状态一致性校验通过；重建成本在预算内。

| 工作/策略        | 决策对象       | 共享价值信号 | 依赖感知       | 刷新级联 | 风险预算     | 流式状态 | RP2 的区别                     |
|:---------------- |:-------------- |:------------:|:--------------:|:--------:|:------------:|:--------:|:------------------------------ |
| LRU              | 淘汰           | 否           | 否             | 否       | 否           | 否       | RP2 不是时间排序               |
| LFU              | 淘汰           | 否           | 否             | 否       | 否           | 否       | RP2 不是频率排序               |
| LCFU (Cortex)    | 淘汰           | 静态分数     | 否             | 否       | 否           | 否       | RP2 用在线价格 + 依赖 + 级联   |
| HARF (RAG-Cache) | 淘汰           | 否           | 否             | 否       | 否           | 否       | RP2 不依赖引用计数启发式       |
| GDSF/PGDSF       | 淘汰           | 成本/大小    | 否             | 否       | 否           | 否       | RP2 加入风险/验证/级联         |
| 固定 TTL         | 刷新           | 否           | 否             | 否       | 否           | 部分     | RP2 用版本事件 + 级联调度      |

| Cortex           | 复用/淘汰/预取 | 静态分数     | 否             | 否       | 否           | 否       | RP2 统一价格 + 依赖 + 刷新     |
| FinCacheServe    | 复用/准入/驱逐 | `U` 固定权重 | 是（反向索引） | 否       | 部分（硬门） | 否       | RP2 在线价格 + 刷新级联 + 流式 |
| Workload-Aware   | 淘汰           | DAG 计数     | 部分           | 否       | 否           | 否       | RP2 级联 + 风险预算 + 联合动作 |
| ChurnBench       | 评测           | —            | 部分           | 否       | 否           | 否       | RP2 是控制器，不是 benchmark   |

**RP2 的独立贡献（必须由实验支撑）：**

1. **共享价格**：准入、复用、验证、刷新、淘汰用同一组 `I_i(a)`，而不是五套阈值。
2. **刷新级联**：`C_now` 包含下游重建与命中损失；合并刷新减少重复重建。
3. **失效域预算**：把风险从“每请求”提升到“每域/每租户”，防止集中违约。
4. **依赖闭包失效**：软/硬失效代数 + 版本向量 + 幂等传播，保证 INV-1。
5. **流式落地**：checkpoint/rescale 后仍满足失效一致性。

### 6.13 预期贡献

1. **联合控制形式化**：把准入、复用、验证、刷新、降级、失效、淘汰写成一个带约束的随机控制问题，并给出可执行的对偶价格算法。
2. **刷新级联**：给出 `C_now/C_lazy/C_freeze/C_inc` 的计价与合并刷新，证明/量化“刷新会杀死下游命中”这一耦合。
3. **失效域风险预算**：把质量预算从“每请求”提升到“每域/每租户”，处理曝光放大与相关性。
4. **依赖闭包失效代数**：软/硬失效、版本向量、幂等传播、rescale 不变量。
5. **Flink 落地**：keyed state/timer/checkpoint/rescale 的具体映射与验收条件。

### 6.14 失败条件

| 失败条件             | 判定                                         | 处理                                                                |
|:-------------------- |:-------------------------------------------- |:------------------------------------------------------------------- |
| 级联不显著           | `M(i)` 中位数 <1.2，或计入级联后决策变化 <5% | 删除级联计价，RP2 收缩为“风险预算 + 依赖失效 + 淘汰”                |
| 联合控制不优于单动作 | E2.5 中与最佳单动作差异在噪声内              | 把 RP2 降为“执行模块”，不作为独立研究点；或只保留失效域预算作为贡献 |
| 域预算无优势         | E2.6 中尾部违约无改善                        | 退回逐项阈值 + 全局预算；删除域模型                                 |
| 依赖图不可维护       | 依赖登记缺失率高、传播延迟大                 | 只做 `rag → resp` 一层依赖；放弃深层闭包                            |
| Flink 开销过高       | 读路径开销 >20% 或恢复时间超门槛             | 控制面异步化；只保留元数据状态；读路径本地缓存                      |
| 陈旧复用无法消除     | E2.4 中出现 INV-1 违反                       | 硬门优先；宁可多 miss，不可错误复用                                 |

### 6.15 风险与裁剪

**风险：**

1. **依赖图爆炸**：每个 `resp` 依赖多个 `rag`/`ctx` 节点，闭包可能很大。缓解：限制闭包深度（≤3）、按域聚合、只登记“可能影响语义”的依赖。
2. **刷新抖动**：频繁版本变化导致反复刷新。缓解：合并刷新、冷却窗口、冻结策略、按波动率分级。
3. **价格震荡**：对偶更新可能振荡。缓解：平滑、钳制、冷却、滞后；报告价格轨迹。
4. **风险预算不可行**：δ 太严时无动作可行。缓解：优先 `RECOMPUTE`；报告“不可行窗口”；不偷偷放宽 δ。
5. **Flink 状态过大**：反向索引与依赖闭包占内存。缓解：分片、压缩、只保留热项、冷项落外部存储。
6. **多租户公平**：全局预算可能被大租户吃掉。缓解：租户上限、加权分配、报告分租户违约。

**裁剪顺序：**

```text
1. 删除 DEMOTE（降级），只保留 full fidelity
2. 删除 FREEZE，只保留 REFRESH/LAZY
3. 删除增量更新，只保留全量刷新
4. 删除失效域预算，退回全局预算 + 逐项阈值
5. 删除子树合并刷新，只保留单对象刷新
6. 删除依赖感知淘汰，只保留价值密度
7. 删除刷新级联，只保留 TTL + 惰性失效
8. 删除 RP2 的独立控制，退化为“RP1 价值 + LRU 排序”
```

第 8 级是 RP2 的“死亡线”：如果退化到这一步，RP2 不再是一个独立研究点，必须把第一章收缩为“RP1 + 简单生命周期”，并在论文中明确说明。

```text
│  共享价格索引 → 容量/风险/验证约束 → 动作选择 → 刷新级联 → 失效传播    │
│  输出：LifecycleDecision（动作、资源、风险记账、级联影响、幂等键）      │
└──────────┬──────────────────────────────────────────────────────────┘
           │  执行结果 + 反事实日志 + 价格
           ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 执行与反馈层                                                         │
│  LLM / Retriever / Judge / Cache Store / Invalidation Notifier       │
│  FeedbackLog（propensity, outcome, cascade, violation）              │
└──────────┬──────────────────────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 校准层（离线/近线）                                                   │
│  q 校准 / p_use 更新 / L 标定 / 价格回放 / OPE / 漂移检测              │
│  输出：新的 CalibrationParams → broadcast 回 RP1                     │
└─────────────────────────────────────────────────────────────────────┘
```

**一句话**：RP1 把“对象”变成“动作价值”，RP2 把“动作价值”变成“资源分配”，反馈层把“分配结果”变成“下一次估值的参数”。

### 7.2 双向接口

#### 7.2.1 RP1 → RP2：`ValueEstimate`

```text
ValueEstimate {
  item_id, request_id, action
  avoided_work { gpu_ms, tokens_in, tokens_out, retrieval_calls, remote_bytes }
  priced_benefit { mean, lcb, ucb }
  costs { lookup, verify, hold_alloc, refresh_alloc, churn_alloc }
  risk { q_sem, q_stale, q_model, q_total, q_ucb }
  loss { answer, stale, auth, security }
  net_value { mean, lcb, ucb }
  decision                  // REUSE | VERIFY_THEN_REUSE | RECOMPUTE
  binding_constraint        // auth | version | risk | capacity | verify_throughput | none
  reason_codes[]
  sensitivities {
    dNV_dlambda            // 对计算影子价格
    dNV_drisk_budget       // 对风险预算
    dNV_dcapacity          // 对容量价格
    dNV_dverify_throughput // 对验证吞吐
    dNV_dversion           // 对依赖版本变化
    dNV_ddependency        // 对依赖闭包/失效状态变化
  }
  dependence { cluster_id, domain_id, shared_deps[], version_gap, unregistered_deps }
  model_version, calibration_version
}
```

**RP2 使用方式**：

1. **动作菜单**：对每个候选，RP2 看到的是 `REUSE/VERIFY/RECOMPUTE` 三个 `ValueEstimate`，不是单条 `NV`。
2. **索引**：`I_i(a) = NV_i(a) − λ_B b_i(a) − λ_R ρ_i(a) − λ_V v_i(a)`；`NV_i(a)` 用 LCB，风险用 UCB。
3. **敏感性**：当 `λ_B/λ_R/λ_V` 改变时，用 `dNV/d...` 做一阶重排，避免每次价格更新都重跑 RP1。
4. **绑定约束**：如果 `binding_constraint` 集中在 `risk`，RP2 应提高 `λ_R` 或收紧预算；如果集中在 `verify_throughput`，应扩容判官或降低验证频率。
5. **依赖元数据**：`domain_id`、`shared_deps` 用于失效域风险聚合与子树淘汰。

#### 7.2.2 RP2 → RP1：`FeedbackRecord` 与 `PriceUpdate`

```text
FeedbackRecord {
  decision_id, request_id, item_id, action
  override_reason?           // RP2 覆盖 RP1 局部建议的原因
  propensity                 // 行为策略选择该动作的概率
  context_snapshot           // 决策时刻的特征摘要
  value_snapshot             // 决策时刻的 ValueEstimate[] 快照（按动作）
  prices_snapshot            // λ_B, λ_R, λ_V, λ
  outcome {
    correct, stale, unauthorized,
    latency_ms, gpu_ms, recompute_cost,
    tokens_in, tokens_out,
    retrieval_calls, remote_bytes, verify_ms
  }
  alternatives {
    action, estimated_nv, realized_nv_if_replayable, replayable
  }
  forced_exploration         // 是否随机留出
  cascade {
    refreshed_items, invalidated_items,
    rebuild_cost, hit_loss, cascade_multiplier
  }
  migration {
    migrated, from_worker, to_worker,
    cold_start_cost, hit_rate_drop
  }
  quality_violation, budget_charge
  timestamp, policy_version, calibration_version
}
```

```text
PriceUpdate {
  window_start, window_end
  lambda_B, lambda_R, lambda_V
  usage_B, usage_R, usage_V
  binding_constraint_share   // 各约束被绑定的比例
  price_trajectory           // 用于稳定性分析
}
```

**RP1 使用方式**：

1. **再校准 `q`**：用 `outcome.correct/stale/unauthorized` 作为标签；用 `propensity` 做 IPS/DR 加权，避免“只有被复用的样本才有标签”的选择偏差。
2. **更新 `p_use`**：用请求序列与会话结束事件做生存分析；`cascade.hit_loss` 提供“刷新导致的需求转移”信号。
3. **更新 `L`**：用 `quality_violation` 与任务指标校准损失；不直接用 `budget_charge` 反推。
4. **更新价格敏感性**：用 `PriceUpdate` 与决策变化做回归，校准 `dNV/dλ`。
5. **检测漂移**：用 `calibration_version` 与 `outcome` 的时间序列监控 ECE/覆盖；触发再校准。
6. **更新 `C_churn`**：用 `migration` 字段校准迁移/冷启动成本，避免第二章扩缩容时把缓存收益算高。

#### 7.2.3 接口契约

| 契约           | 内容                                                                                                         | 违反后果          |
|:-------------- |:------------------------------------------------------------------------------------------------------------ |:----------------- |
| **动作一致性** | RP1 的 `decision` 必须在 RP2 的可行动作集内；若不在，RP2 记录 `interface_violation` 并回退 `RECOMPUTE`       | 决策不可执行      |
| **版本一致性** | `ValueEstimate` 必须带 `calibration_version`；RP2 不接受过期版本用于高风险决策                               | 用旧校准做新决策  |
| **风险上界**   | RP1 必须给 `q_ucb`，不能只给均值；RP2 用 `q_ucb` 做预算                                                      | 预算被低估        |
| **敏感性**     | RP1 必须给至少 `dNV_dlambda`、`dNV_drisk_budget`、`dNV_dversion` 与 `dNV_ddependency`；缺失时 RP2 退化为重算 | 价格/版本更新失效 |
| **反事实**     | RP2 必须记录 `propensity` 与 `forced_exploration`；缺失时 RP1 不能做无偏校准                                 | 选择偏差          |
| **幂等**       | `decision_id` 与 `(item_id, dep_node, version)` 全局唯一                                                     | 重复刷新/失效     |

**覆盖规则**：RP1 的 `decision` 是局部建议（只考虑该候选与当前请求）；RP2 可以在容量/风险/验证吞吐约束下选择不同的动作。覆盖时必须记录 `override_reason`（如 `risk_budget`、`capacity`、`verify_throughput`），并进入 `FeedbackRecord`，用于校准 RP1 的敏感性。这样 RP2 不是执行器，而是全局分配器；RP1 不是策略，而是估值器。

### 7.3 状态与事件模型

#### 7.3.1 状态分层

| 层       | 状态                                   | 更新频率      | 存储                         | 一致性要求                       |
|:-------- |:-------------------------------------- |:------------- |:---------------------------- |:-------------------------------- |
| 对象状态 | `CacheItem` 生命周期、版本、风险、统计 | 每请求/每事件 | Flink keyed state            | 强一致（单 key）                 |
| 依赖状态 | `DependencyNode` 版本、波动率、失效域  | 版本事件      | Flink keyed state            | 单调版本                         |
| 索引状态 | 反向索引 `dep → items`                 | 版本事件/准入 | Flink keyed state 或外部索引 | 最终一致，读路径校验 generation  |
| 预算状态 | 容量/风险/验证吞吐                     | 窗口          | Flink keyed state            | 近似一致（允许短暂超支，需回退） |
| 价格状态 | `λ_B/λ_R/λ_V`                          | 分钟级        | broadcast state              | 最终一致                         |
| 校准状态 | `q/p_use/L` 参数                       | 小时/天级     | 外部模型库 + broadcast       | 版本化，可回滚                   |
| 负载状态 | LLM/检索/判官延迟与成本                | 秒级          | 外部 metrics                 | 最终一致                         |

#### 7.3.2 事件顺序

- **版本事件**：以 `version` 为准，不以到达顺序为准；晚到的旧版本事件必须被忽略。
- **请求事件**：读路径先检查 `state` 与 `vv`；若 `SUSPECT`，进入 `VERIFY` 或 `RECOMPUTE`；若 `INVALID`，禁止 `REUSE`。
- **定时器**：Flink timer 可能重复触发；用 `decision_id` 去重。
- **rescale**：在途事件可能重放；用 `event_id` 去重；`dep_epoch` 单调。

#### 7.3.3 快照与重放

- 每次决策记录 `context_snapshot`、`value_snapshot`、`prices_snapshot`，用于离线重放与审计。
- 快照只存特征摘要，不存完整 prompt/答案，避免隐私与存储膨胀；完整负载在外部存储，用 `content_hash` 关联。
- 重放时，若外部负载已变化，标记 `replayable=false`，不强行回放。

### 7.4 价格与反馈闭环

#### 7.4.1 双时间尺度

闭环最容易犯的错误是“价格一更新就重训价值模型，价值一更新就重排所有动作”，导致系统追逐自己的尾巴。本文采用双时间尺度：

| 环路       | 周期      | 更新什么                          | 不更新什么           | 目的                     |
|:---------- |:--------- |:--------------------------------- |:-------------------- |:------------------------ |
| **快环**   | 事件/分钟 | `λ_B/λ_R/λ_V`；动作选择；刷新队列 | `q/p_use/L` 参数     | 在固定估值下做资源分配   |
| **慢环**   | 小时/天   | `q` 校准、`p_use`、`L`、敏感性    | 价格轨迹（作为输入） | 在固定分配策略下修正估值 |
| **超慢环** | 周        | 模型结构、特征、校准方法          | 在线决策             | 防止概念漂移             |

**稳定性条件**：快环的价格更新必须比慢环的参数更新快一个数量级；慢环更新后，快环用新参数重新计算索引，但不立即重置价格（价格有记忆）。

#### 7.4.2 避免循环依赖

RP1 的 `NV` 依赖 `λ`（计算价格）与 `C_refresh`（RP2 的级联成本）；RP2 的索引依赖 `NV`。这是一个双层结构。为避免不稳定：

- RP1 在决策时刻使用**当前**的 `λ` 与 `C_refresh` 估计，不预测 RP2 的未来分配；
- RP2 在决策时刻使用**当前**的 `NV`，不重新训练 RP1；
- 价格更新是慢变量，`NV` 是快变量；用时间尺度分离保证收敛（至少在实践中不振荡）。
- 如果观测到价格振荡（振幅 > 阈值），冻结价格，回退到固定档位，并记录事件。

#### 7.4.3 反馈的类型

| 反馈      | 来源                | 用途                  | 偏差风险             | 缓解              |
|:--------- |:------------------- |:--------------------- |:-------------------- |:----------------- |
| 正确/错误 | judge/人工/任务指标 | 校准 `q`              | judge 噪声、选择偏差 | 抽样人工、IPS/DR  |
| 陈旧/越权 | 版本检查/审计       | 校准 `q_stale/q_auth` | 越权样本稀少         | 主动探测、硬门    |
| 成本/延迟 | 计量                | 校准 `W/C_v`          | 计量口径不一致       | 统一 profiler     |
| 级联      | 刷新/失效日志       | 校准 `C_refresh`      | 低估下游             | 依赖图 + 重建日志 |
| 价格      | 预算使用            | 更新 `λ_B/λ_R/λ_V`    | 震荡                 | 平滑/钳制/冷却    |
| 决策      | 动作日志            | 校准 `dNV/d...`       | 内生性               | 探索、IV/断点     |

### 7.5 Flink 映射

#### 7.5.1 作业拓扑

MVP 建议一个 Flink 作业、两个核心算子：

```text
Source(Request, Version, Timer, Metrics)
  → KeyedProcessFunction<tenant, Request, ...>  // ReuseGate + ValueOperator
  → KeyedProcessFunction<item, Decision, ...>   // LifecycleOperator
  → Sink(Response, FeedbackLog, Invalidation, Metrics)
```

- `ValueOperator` 可以是 `ProcessFunction` 或 `AsyncFunction`（调用外部 judge/模型）；异步调用必须有超时与降级。
- `LifecycleOperator` 维护 item/dep/domain 状态与 timer；失效传播通过 `KeyedCoProcessFunction` 或两阶段拓扑。
- 价格与校准参数用 `BroadcastState` 下发；每个分区本地缓存，避免每请求远程调用。

#### 7.5.2 状态后端与序列化

- 状态后端：RocksDB（大状态）+ 增量 checkpoint；MVP 可用 HashMapStateBackend 做小规模。
- 序列化：Avro/Protobuf/JSON 均可；关键是 schema 演进（新增字段可选、版本号）。
- 大对象（prompt、答案、文档块）不放 Flink state；只放 `content_hash` 与指针。

#### 7.5.3 checkpoint / restore / rescale

| 阶段       | 动作                                                              | 验收                                   |
|:---------- |:----------------------------------------------------------------- |:-------------------------------------- |
| checkpoint | 保存 item/dep/domain/budget/price/outbox；记录 `index_generation` | checkpoint 大小、耗时在门槛内          |
| restore    | 恢复状态；校验外部索引 generation；未校验前禁止 `REUSE`           | 恢复后零陈旧复用                       |
| rescale    | key group 重分配；timer 恢复；反向索引重建/迁移                   | 命中率 5 分钟内恢复 ±5%；无 INV-1 违反 |
| failover   | 从最近 checkpoint 恢复；重放在途失效事件                          | 幂等；无重复刷新爆炸                   |

#### 7.5.4 与外部系统的边界

| 外部系统         | 交互        | 是否进 checkpoint          | 失败降级                    |
|:---------------- |:----------- |:-------------------------- |:--------------------------- |
| LLM 推理（vLLM） | 重算/生成   | 否                         | 超时→RECOMPUTE/排队         |
| 检索/ANN         | 候选召回    | 否（索引可重建）           | 超时→精确匹配/降级          |
| Judge            | 验证        | 否                         | 超时→保守拒绝（视为不通过） |
| 负载存储         | 答案/文档块 | 否                         | 不可用→miss                 |
| 失效通知         | 下游清理    | 否（outbox 进 checkpoint） | 至少一次 + 幂等             |

### 7.6 与第二章、第三章的接口

#### 7.6.1 与第二章（算力配置）

| 方向            | 内容                                                          | 频率   | 说明                                                            |
|:--------------- |:------------------------------------------------------------- |:------ |:--------------------------------------------------------------- |
| 第二章 → 第一章 | `λ(ρ)`、容量 `B`、副本 `generation`、负载预测                 | 分钟级 | `λ` 进入 RP1 的 `NV`；`B` 进入 RP2 的容量约束                   |
| 第一章 → 第二章 | 复用后的有效到达率、单位请求工作分布、缓存预算建议、`λ_B`     | 分钟级 | 帮助第二章判断“加算力”还是“加缓存”                              |
| 反馈            | rescale 导致会话迁移 → 缓存冷启动 → 命中率下降 → 有效负载上升 | 事件   | 必须在 `p_use`/`C_churn` 中显式表达（旧设计 §7 的“反身性”保留） |

**边界**：第一章不决定副本数、batch size、GPU 型号；只提供“缓存侧的工作节省与有效负载”。

#### 7.6.2 与第三章（调度与路由）

| 方向            | 内容                                           | 频率          | 说明                                          |
|:--------------- |:---------------------------------------------- |:------------- |:--------------------------------------------- |
| 第三章 → 第一章 | 租户权重、SLO class、会话迁移事件、路由决策    | 请求级        | 迁移视为“局部性版本事件”；缓存可能失效/冷启动 |
| 第一章 → 第三章 | 对象价值排序、会话粘性需求、失效事件、风险预算 | 请求级/分钟级 | 帮助第三章判断“粘性 vs 最短队列”              |
| 反馈            | 路由导致的命中/未命中、迁移后的重建成本        | 事件          | 进入 `C_churn` 与 `p_use`                     |

**边界**：第一章不做全局调度、不做租户公平分配；只提供“缓存亲和”的输入与“失效”的输出。

### 7.7 一致性与正确性论证

#### 7.7.1 不变量

- **INV-1（无陈旧复用）**：见 §6.6.3。
- **INV-2（版本单调）**：依赖版本只增不减；`vv_i` 只能通过 `REFRESH/ADMIT` 更新。
- **INV-3（幂等失效）**：同一 `(item, dep, version)` 重复通知不改变状态。
- **INV-4（rescale 一致）**：恢复后 `dep_epoch` 与 `vv` 不倒退；在途事件重放不产生旧版本覆盖。

#### 7.7.2 论证思路

1. **读路径**：`REUSE` 前检查 `auth/model/version/state`；`SUSPECT` 必须 `VERIFY`；`INVALID` 禁止。因此任何 `REUSE` 都满足 INV-1 的前件。
2. **失效传播**：版本事件按 `descendants` 传播；晚到旧版本被 `version` 比较丢弃；因此 INV-2 成立。
3. **幂等**：outbox 以 `(item, dep, version)` 为键；重复消费不改变状态；因此 INV-3 成立。
4. **rescale**：Flink keyed state 与 timer 随 key group 迁移；`dep_epoch` 从 checkpoint 恢复；在途事件重放时用 `event_id` 去重；因此 INV-4 成立。

**边界**：这些是**相对已记录依赖**的一致性，不是事实正确性。若依赖登记遗漏，INV-1 仍可能被违反；因此“依赖登记完整”是 `ADMIT` 的硬条件，并单独报告未登记依赖率。

#### 7.7.3 控制器不是最优的

RP2 的贪心 + 对偶是近似算法；不声称全局最优。本文用：

- 小规模 ILP/动态规划 Oracle 量化 greedy gap；
- 大规模用 Belady 式离线 Oracle 作上界；
- 报告 gap 随容量/对象数/负载的变化。

这比“声称最优但无法验证”更可信。

### 7.8 失败模式与降级

| 失败模式       | 检测                                | 降级                                                   |
|:-------------- |:----------------------------------- |:------------------------------------------------------ |
| RP1 校准不可用 | `calibration_version` 过期/服务超时 | 保守门：精确匹配 + 版本/权限 + 固定阈值；记录降级      |
| 价格震荡       | `λ` 轨迹振幅 > 阈值                 | 冻结价格；回退固定档位；告警                           |
| 依赖索引延迟   | `index_generation` 落后             | 禁止 `REUSE`，只允许 `RECOMPUTE`；异步追平             |
| 判官过载       | 队列长度/超时率                     | 降低验证比例；只对高价值对象验证；其余保守拒绝         |
| 容量超限       | `usage_B > B`                       | 优先 `DEMOTE`，再 `EVICT` 低子树价值项；不突破风险约束 |
| 风险预算不可行 | 可行动作集为空                      | 全部 `RECOMPUTE`；报告不可行窗口；不偷偷放宽 δ         |
| 反馈偏差       | IPS/DR 与留出差异大                 | 增加探索；只报相对排序；缩小结论                       |
| Flink 反压     | checkpoint 时长/队列                | 异步化控制面；降级刷新；限流                           |

### 8.1 工作负载与 Trace

#### 8.1.1 三类必做负载

| 编号       | 负载                    | 主要对象                | 关键现象                         | 主要风险               | 对应研究点             |
|:---------- |:----------------------- |:----------------------- |:-------------------------------- |:---------------------- |:---------------------- |
| W1         | 多轮问答 / 语义回答缓存 | `resp`                  | 释义重复、会话内复用、跨会话复用 | 语义误命中、答案过时   | RP1 为主               |
| W2         | RAG 知识复用与文档更新  | `rag` + `resp`          | 文档块重复、版本变化、证据传播   | 证据陈旧、下游答案错误 | RP1 + RP2              |
| W3         | 长会话上下文与版本失效  | `ctx`（依赖源）+ `resp` | 摘要重写、事实更新、指纹失效     | 指纹不稳定、级联失效   | RP2 为主               |
| W4（扩展） | 工具/计划复用           | `act`/`plan`            | 执行历史一致、状态范围           | 环境状态不同           | 只做边界验证，不进 MVP |

**为什么是这三类**：它们分别覆盖“回答短路”“知识复用”“上下文版本”三种收益/风险结构，且都能产生版本事件与依赖关系；只做 W1 会把论文做成“语义缓存阈值研究”，只做 W3 会丢掉 `rag` 的远端收益。

#### 8.1.3 合成器设计

合成器不是“随机生成命中/未命中”，而是生成**因果一致的会话、版本与请求事件**，再让缓存机制去处理。

**生成顺序：**

```text
1. 生成租户（权重、SLO、权限域）
2. 生成会话（到达时间、轮数、话题）
3. 生成意图簇与 query（Zipf 热度、释义、漂移）
4. 生成文档/事实/摘要及其版本时间线（更新过程）
5. 由会话与版本派生 prompt、指纹、依赖闭包
6. 由任务与证据派生“真实答案/质量标签”
7. 注入负载曲线、权限变化、故障/迁移
8. 回放：请求到达 → 缓存决策 → 结果记录
```

**统计规律（每一项都要在论文中写明依据）：**

| 维度     | 生成规律                                               | 依据/校准                                                      | 只对合成负载成立的结论 |
|:-------- |:------------------------------------------------------ |:-------------------------------------------------------------- |:---------------------- |
| 会话到达 | 非齐次 Poisson；租户特定速率；日周期                   | 公开对话数据的轮次间隔统计；Cortex/Pensieve 的 Poisson 假设    | 绝对吞吐、峰值倍数     |
| 意图热度 | Zipf(α) over clusters；α 可调                          | Cortex 的 Zipf-0.99 设置；Web 查询长尾                         | 命中率绝对值           |
| 释义     | 每个意图生成 `k` 个释义；语义漂移参数 `σ`              | vCache/MVR 的 paraphrase benchmark                             | 语义复用率             |
| 文档更新 | 每文档独立 Poisson；波动率分档；版本跳变               | Wikipedia revision history / SEC filing 节奏                   | 陈旧率、刷新次数       |
| 变化影响 | 只有一部分版本变化影响答案（`p_affect`）               | FreshCache 报告 34.3% 的变化影响答案；作为先验，不当作固定事实 | 答案级过期率           |
| 权限变化 | 稀有 Poisson；跨租户探测                               | 企业租户生命周期                                               | 越权率（应保持 0）     |
| 负载     | 正弦 + 突发 + 阶跃；ρ ∈ [0.2, 0.95]                    | 排队系统常用；第二章接口                                       | 负载敏感性的形状       |
| 质量     | 由构造保证“同意图 + 同证据版本 → 同答案”；加入近邻对抗 | 任务标签 + 人工抽查                                            | 绝对质量分数           |

**避免“先假设机制一定有效”的做法：**

1. **零假设控制**：打乱意图簇、删除版本更新、让所有 query 唯一、令验证免费/极贵；如果机制在这些控制下仍然“显著更好”，说明评估有漏洞。
2. **对抗区间**：高更新率、低复用、严格 δ、低负载、验证极贵；机制应在这些区间失败或退化，论文要报告。
3. **基线同等调参**：所有基线在同一预算/同一匹配器/同一校准集上调参；不允许“基线用默认值、方法精调”。
4. **预注册门槛**：在跑实验前写下“多大算有效”（见 §8.8 的判定门槛），避免事后挑结果。
5. **双轨报告**：机制分轨（单独验证每个机制）与端到端（整体效果）分开；端到端不能替代机制证据。

**合成器的边界**：

- 只能证明“在给定统计规律下，机制有效/无效”；
- 不能证明“真实生产流量下一定有效”；
- 论文必须有一节“外部有效性”，列出哪些结论依赖合成器、哪些有公开数据支撑。

#### 8.1.5 真实 trace 的替代方案

如果 W1 找不到真实 Agent trace：

1. **公开数据 + 合成会话结构**：用公开 QA/对话数据做“内容”，用合成器做“到达/版本/租户结构”。
2. **半真实回放**：用 Wikipedia revision history 提供真实版本时间线，用 QA 数据提供真实问题与证据。
3. **在线微原型**：2–4 GPU、10–30 req/s、1–2 小时，产生自己的 trace；只用于验证机制方向，不作为外部有效性证据。
4. **明确降级**：所有“绝对收益/倍数”结论标注“合成负载”；只保留“相对排序/机制方向”作为可迁移结论。

### 8.2 测量研究 P0

#### 8.2.1 目标

在写模型之前，先回答“这个机制有没有价值”。P0 不做完整控制，只测量分布与经济学。

#### 8.2.2 测量项

| 编号 | 问题                                  | 指标                                                      | 输出                                         |
|:---- |:------------------------------------- |:--------------------------------------------------------- |:-------------------------------------------- |
| P0.1 | 语义/结构复用机会有多少？             | 候选相似度分布、同意图率、跨会话/跨租户复用率、精确匹配率 | 复用机会分布；按 W1/W2/W3 分层               |
| P0.2 | 对象的大小/生命周期/复用分布？        | `size_b`、age、hit count、reuse interval、存活曲线        | 分布拟合（对数正态/幂律）；用于 `p_use` 先验 |
| P0.3 | 验证成本是否低于命中收益？            | `C_v/W`、`p_pass`、`q'`、验证延迟                         | 验证经济学表；按对象价值分层                 |
| P0.4 | 知识与上下文的更新频率？              | 文档/摘要更新率、半衰期、变化幅度、`p_affect`             | 更新过程参数；用于合成器与 `q_stale`         |
| P0.5 | 生命周期动作是否造成 churn？          | 每 item-hour 的 evict/refresh/invalidate 次数、抖动率     | churn 基线；用于 RP2 的稳定性指标            |
| P0.6 | 缓存收益是否随 load/tenant/任务变化？ | 命中率、净收益、违约率 vs ρ、租户、任务                   | 负载敏感性曲线；用于 `λ` 区间                |
| P0.7 | 依赖扇出与级联乘数？                  | `Desc(i)` 的规模分布、`M(i)` 分布                         | 级联是否值得建模（G3）                       |

**P0 的 8 项说明（按 §7 的统一模板）：**

1. **假设**：三类负载中存在足以覆盖管理税的语义/结构复用，且至少部分对象的验证成本低于命中收益。
2. **自变量/混淆**：负载类型（W1/W2/W3）、对象层（`resp/rag`）、租户、更新率；混淆包括匹配器质量、数据难度、会话长度。
3. **数据**：W1–W3 的公开数据 + 合成器；若获得真实 trace，作为外部验证而非调参数据。
4. **对照**：无缓存、精确匹配、固定相似度阈值（作为收益下界与参照，不作为“方法”）。
5. **指标**：复用率、`C_v/W`、`p_pass`、更新率、`M(i)`、churn、负载敏感性。
6. **预期趋势**：复用率随任务/对象层变化；`C_v/W` 在短回答/便宜回源上更高；`M(i)` 右偏。
7. **否定条件**：G1a–G1c 任一不通过。
8. **结论范围**：只描述测量分布与经济学；不把相关性写成因果，不外推为“所有 Agent 负载”。

#### 8.2.3 P0 的判定门槛（G1）

| 门槛           | 通过条件                                                                     | 不通过的处理                                   |
|:-------------- |:---------------------------------------------------------------------------- |:---------------------------------------------- |
| G1a 复用机会   | 至少一个负载的语义/结构复用率 ≥10%，或复用率 ≥5% 但单次可避免工作 ≥3× 管理税 | 主对象转向 W2/W3；`resp` 降为精确匹配          |
| G1b 验证经济学 | 高价值对象的 `C_v / W` ≤0.3，且 `p_pass` 不是极低                            | 删除 `VERIFY`；只对高风险对象保留              |
| G1c 版本事件   | W2/W3 中每 100 请求至少 1 次版本事件；`M(i)` 有右尾                          | 合成器提高更新率；或把 RP2 收缩为“失效 + 淘汰” |

**G1 是 Go/No-Go 的第一道门**：不通过就调整研究对象，而不是硬写模型。

### 8.3 研究点一实验

#### E1.1 风险校准（含 `rag` 传播）

1. **假设**：依赖条件化 + 端到端校准的风险模型，在版本变化子集上比“相似度 + 年龄”模型有更好的条件覆盖与更低的 ECE。
2. **自变量/混淆**：风险模型（相似度、+年龄、+版本、+全部）；校准方法（无、Platt、isotonic、conformal）；层（`resp/rag`）。混淆：匹配器质量、标签噪声、类别不平衡、租户混合。
3. **数据**：W1（`resp`）、W2（`rag` + `resp`）、W3（`ctx` 版本）；标签来自 judge + 10% 人工抽查。
4. **对照**：固定相似度阈值、vCache 式逐条目门控、FreshCache 式时间风险、Cortex 式 judge、`Π(1−q_k)` 独立相乘。
5. **指标**：ECE、Brier、覆盖率、锐度、条件覆盖（按层/租户/版本变化）、risk–coverage 曲线、预算利用率。
6. **预期趋势**：加入版本特征后，版本变化子集的条件覆盖提升；端到端校准优于独立相乘；`rag` 的 `q_total` 明显低于/高于 `q_evid`（取决于 `τ`）。
7. **否定条件**：ECE >0.10，或版本变化子集覆盖率 <0.85，或端到端校准与分解模型无差异。
8. **结论范围**：只对测试任务/租户/δ 区间成立；不外推为“通用校准器”。

**E1.1b `rag` 传播因子**

1. **假设**：`q_total^resp(rag reuse)` 不能由 `q_evid` 代替；传播因子 `τ` 可测且在不同任务间有稳定区间。
2. **自变量/混淆**：证据质量（缓存证据 vs gold 证据）；任务类型（多跳/单跳/表格）；生成模型。混淆：证据覆盖度、问题难度。
3. **数据**：W2 的 QA 子集；同一请求分别用缓存证据与 gold 证据生成。
4. **对照**：`q_evid` 单独、`q_total` 端到端、独立相乘。
5. **指标**：`q_evid`、`τ`、`q_total`、校准误差、按任务分组。
6. **预期趋势**：`τ` 显著大于 0 且小于 1；多跳任务 `τ` 更高；`q_total` 与 `q_evid` 排序不完全一致。
7. **否定条件**：`τ` 的置信区间跨 0/1，或按任务分组不可比。
8. **结论范围**：只对测试任务/模型；若不稳定，`rag` 只做硬新鲜度门，不做风险校准。

#### E1.2 决策后悔（判定性）

1. **假设**：动作条件 + LCB 的决策比点估计/分数排序有更低后悔，且违约率不升。
2. **自变量/混淆**：决策规则（固定阈值、点估计 NV、LCB NV、全分布）；匹配器固定为 vCache/MVR 式。混淆：候选集大小、风险预算、负载。
3. **数据**：W1–W3 的离线回放；合成数据提供 oracle 标签，真实数据用随机留出 + judge。
4. **对照**：固定阈值、vCache、INFOCOM Reverse Greedy（小 k）、Cortex 式 judge+LCFU、GPU-only、size/hit-rate。
5. **指标**：归一化后悔 `Regret/C_r`、违约率、净收益、动作分布、预算利用率。
6. **预期趋势**：LCB 在不确定性高的区间优于点估计；点估计在风险预算紧时超支；固定阈值在高负载/版本变化时后悔更大。
7. **否定条件**：相对最佳分数基线后悔降低 <10%，或违约率上升。
8. **结论范围**：离线回放；在线确认见 E3.1；不外推为“所有负载”。

#### E1.3 决策稳定性

1. **假设**：决策在阈值附近翻转；翻转率随 `λ` 与版本扰动上升；LCB 减少“有害翻转”。
2. **自变量/混淆**：扰动类型（embedding 噪声、版本抖动、`λ` 偏移、负载噪声）；决策规则。混淆：候选相似度分布、校准误差。
3. **数据**：W1–W3 的重复回放；对同一请求注入扰动。
4. **对照**：点估计、LCB、固定阈值。
5. **指标**：翻转率、翻转后的后悔增量、翻转方向（保守/激进）、按 `λ` 分档。
6. **预期趋势**：`λ` 跨阈值时翻转率上升；LCB 的翻转更偏保守；固定阈值在版本扰动下翻转更“盲目”。
7. **否定条件**：翻转导致的后悔增量 > 收益的 50%，或 `λ` 扫描无翻转（机制惰性）。
8. **结论范围**：扰动范围要对应实测噪声；不把人工扰动当真实漂移。

#### E1.4 因子消融

1. **假设**：`λ`、`q_stale`、`C_v`、依赖状态、相关性/曝光各自对决策有贡献；去掉任一项会恶化后悔或违约。
2. **自变量/混淆**：消融项（−λ、−q_stale、−C_v、−依赖、−相关性、−LCB）；其余固定。
3. **数据**：W1–W3；重点看高负载/高更新/严格 δ 区间。
4. **对照**：完整模型、各消融、Oracle。
5. **指标**：后悔、违约、预算利用率、动作分布。
6. **预期趋势**：`q_stale` 在高更新区间重要；`λ` 在高负载区间重要；`C_v` 在验证贵时重要；相关性在热对象区间重要。
7. **否定条件**：某因子在所有区间都不改变主指标 → 从模型中删除，并写成负结果。
8. **结论范围**：因子的重要性是区间依赖的；不外推为“永远重要”。

#### E1.5 基线对比（固定匹配器）

1. **假设**：在固定匹配器下，RP1 的决策层仍优于分数排序，说明增量来自决策而不是匹配。
2. **自变量/混淆**：决策层（固定阈值、vCache、频率、GPU-only、size/hit-rate、RP1）；匹配器固定（同一 embedding/ANN/rerank）。混淆：阈值调参、候选数。
3. **数据**：W1–W3。
4. **对照**：上述基线 + Oracle。
5. **指标**：后悔、净收益、违约、预算利用率、命中精度。
6. **预期趋势**：RP1 在风险预算紧/负载变化时优势更明显；在低负载/低风险时与固定阈值接近。
7. **否定条件**：固定匹配器下无显著优势 → RP1 的增量不成立，需重新定位。
8. **结论范围**：只证明“决策层”增量；不证明“匹配器”增量。

#### E1.6 OPE 验证

1. **假设**：IPS/DR 能在随机留出预算有限时，给出与留出实验一致的估计；倾向日志足够。
2. **自变量/混淆**：估计器（IPS、DR、direct method）；探索率（1%、5%、10%）；权重截断。混淆：行为策略、样本量、非平稳。
3. **数据**：W1–W3 的随机留出实验；同一策略对不同动作的倾向。
4. **对照**：随机留出真值、IPS、DR、direct method。
5. **指标**：偏差、RMSE、95% CI 覆盖、有效样本量、权重分布。
6. **预期趋势**：DR 偏差更小；IPS 方差更大；探索率越低，方差越大。
7. **否定条件**：偏差 > 预设阈值，或 CI 覆盖 <80%。
8. **结论范围**：只对记录的策略对成立；跨策略外推需重新验证。

#### E1.7 风险预算兑现

1. **假设**：校准 UCB 能把违约控制在 δ 内，并比保守门控花掉更多预算；失效域核算降低尾部。
2. **自变量/混淆**：风险控制（固定阈值、vCache、FreshCache、Surplus 式分箱、逐项 cap、域预算）；δ 档位（1%、5%、10%）。混淆：对象热度、租户混合。
3. **数据**：W1–W3；合成热对象区间。
4. **对照**：上述 + Oracle 分配。
5. **指标**：违约率、预算利用率、最大租户/域违约、覆盖率、净收益。
6. **预期趋势**：逐项阈值保守、预算利用率低；域预算在相同总违约下尾部更低；校准 UCB 接近 δ 但不超。
7. **否定条件**：违约 > δ + 2SE，或预算利用率无改善，或尾部无改善。
8. **结论范围**：δ 的测试区间；不外推到极端 δ。

### 8.4 研究点二实验

#### E2.1 淘汰

1. **假设**：依赖感知价值密度淘汰在相同容量下比 LRU/LFU/LCFU/HARF/GDSF 有更高净收益/更低重建成本。
2. **自变量/混淆**：淘汰策略；容量（对象数/字节）；负载。混淆：对象大小分布、复用分布。
3. **数据**：W1–W3；容量扫描。
4. **对照**：LRU、LFU、LCFU、HARF、GDSF、价值密度、Belady Oracle。
5. **指标**：净收益、重建成本、churn、命中精度、p95。
6. **预期趋势**：容量越紧，依赖感知优势越明显；低负载时差异缩小。
7. **否定条件**：相对最佳基线 <5%，或 churn 过高。
8. **结论范围**：容量/负载区间；不外推为“所有容量”。

#### E2.2 准入

1. **假设**：风险预算准入比全缓存/固定阈值有更高净收益、更低违约。
2. **自变量/混淆**：准入策略（全缓存、固定阈值、价值准入、风险预算准入、Oracle）；容量。混淆：候选质量、租户。
3. **数据**：W1–W3。
4. **对照**：上述 + Oracle。
5. **指标**：净收益、违约、预算利用率、命中精度、churn。
6. **预期趋势**：全缓存在风险预算紧时违约高；固定阈值在负载变化时收益低；风险预算准入更稳。
7. **否定条件**：无显著差异。
8. **结论范围**：准入密集区间；不证明“所有对象都该准入”。

#### E2.3 刷新级联（判定性）

1. **假设**：`M(i)` 足够大，忽略级联会改变刷新决策；级联感知 + 合并刷新提升净收益、降低 churn。
2. **自变量/混淆**：刷新策略（不刷新、固定 TTL、启发式 TTL、依赖感知、合并刷新）；级联计价开/关；更新率。混淆：扇出、下游命中率、重建成本。
3. **数据**：W2（文档更新）、W3（摘要/事实更新）；合成更新率扫描。
4. **对照**：不刷新、固定 TTL、启发式 TTL、依赖感知、合并刷新、Oracle。
5. **指标**：`M(i)` 分布、刷新次数、下游命中损失、重建成本、净收益、陈旧率、churn。
6. **预期趋势**：`M(i)` 右偏；合并刷新减少重复重建；高扇出对象更倾向 `FREEZE/LAZY`。
7. **否定条件**：`M(i)` 中位数 <1.2，或净收益提升 <5%，或陈旧率上升。
8. **结论范围**：更新率区间；若更新稀少，级联不重要。

#### E2.4 失效传播

1. **假设**：依赖闭包失效比无图/全局即时/惰性更能降低陈旧/越权复用，且性能损失小于全局失效。
2. **自变量/混淆**：失效策略（无图、全局即时、惰性 epoch、闭包、闭包 + auth 即时）；版本/权限事件率。混淆：依赖深度、扇出。
3. **数据**：W2/W3；注入版本/权限事件。
4. **对照**：上述 + 无失效（下界）。
5. **指标**：陈旧复用率、越权率（必须 0）、命中率、p95、重建成本、失效延迟。
6. **预期趋势**：无图/惰性漏失效；全局即时性能损失大；闭包折中最好。
7. **否定条件**：闭包无陈旧率优势，或性能损失 > 阈值。
8. **结论范围**：事件率/深度区间；权限事件稀少但必须硬门。

#### E2.5 联合控制（判定性）

1. **假设**：共享价格的联合控制优于“最佳单动作 + 价值排序”，且优于任何单动作启发式。
2. **自变量/混淆**：控制器（最佳单动作、价值排序、联合、ILP Oracle）；负载/更新率。混淆：容量、对象异质性。
3. **数据**：W1–W3；小规模 ILP 实例。
4. **对照**：最佳单动作、价值排序、联合、Oracle。
5. **指标**：净收益、违约、动作分布、churn、p95、greedy gap。
6. **预期趋势**：联合在高负载/高更新/多对象时优势明显；低负载时接近。
7. **否定条件**：与最佳单动作差异在噪声内 → RP2 不独立。
8. **结论范围**：测试区间；不外推为“联合永远更好”。

#### E2.6 风险组合

1. **假设**：失效域预算在相同总违约下降低最大租户/域违约（尾部）。
2. **自变量/混淆**：风险分配（逐项阈值、全局预算、域预算、Oracle）；相关性强度。混淆：域大小、热度。
3. **数据**：W1–W3；合成相关失败区间。
4. **对照**：上述 + Oracle。
5. **指标**：最大域违约、p95/p99 违约、总违约、预算利用率、公平。
6. **预期趋势**：相关性越强，域预算优势越大；无相关时接近。
7. **否定条件**：尾部无改善。
8. **结论范围**：相关失败区间；不证明“域预算总是更好”。

#### E2.7 依赖感知淘汰

1. **假设**：子树感知淘汰比只看对象自身价值密度/叶子优先更低重建成本。
2. **自变量/混淆**：淘汰策略（价值密度、叶子优先、子树、Oracle）；扇出。混淆：容量、复用。
3. **数据**：W2/W3；高扇出合成。
4. **对照**：上述 + Oracle。
5. **指标**：重建成本、净收益、churn。
6. **预期趋势**：扇出越高，子树感知优势越大。
7. **否定条件**：无差异。
8. **结论范围**：高扇出区间。

#### E2.8 Flink 开销与恢复

1. **假设**：控制器开销 <10%，rescale/恢复后保持 INV-1，命中率 5 分钟内恢复 ±5%。
2. **自变量/混淆**：并行度、状态大小、checkpoint 间隔、故障注入。混淆：外部服务延迟。
3. **数据**：W1–W3 的回放；2–4 GPU；10^4–10^6 对象。
4. **对照**：无状态基线、不同并行度、不同 checkpoint 间隔。
5. **指标**：吞吐、p95/p99、checkpoint 大小/耗时、恢复时间、陈旧复用、命中率恢复、重建成本。
6. **预期趋势**：开销随状态/并行度上升；checkpoint 间隔影响恢复时间；异步化降低读路径开销。
7. **否定条件**：开销 >20%，或任何 INV-1 违反，或恢复超门槛。
8. **结论范围**：原型规模；不外推为生产级。

### 8.5 集成实验

#### E3.1 端到端对照（判定性）

1. **假设**：完整系统（RP1 + RP2）在净收益、质量/新鲜度约束满足率上优于任何单组件与所有基线；增益在扣除验证、刷新、失效、存储后仍存在。
2. **自变量/混淆**：系统配置（见下）；负载（低/中/高）；更新率（低/高）；租户混合（单/多）。混淆：匹配器、数据分布、judge 成本。
3. **数据**：W1–W3；真实/半真实 trace 优先；合成器做压力测试。
4. **对照（必须全部出现）**：

```text
无缓存
精确匹配
LRU
固定 TTL
vCache 式质量门控
成本感知淘汰（Cortex LCFU 式）
研究点一单独使用（RP1 + 简单 LRU）
研究点二使用启发式价值（RP2 + 固定价值）
完整系统：RP1 + RP2
Oracle 上界
```

5. **指标**：
   - 节省的 LLM token、GPU-ms、检索调用、远端字节；
   - 扣除验证、刷新、失效、存储、重建后的净收益；
   - 质量违约率、陈旧复用率、越权率（必须 0）、新鲜度满足率；
   - 决策后悔、命中精度、churn、refresh 次数；
   - p50/p95 时延、单位资源 goodput；
   - 负载/知识更新/权限变化下的恢复时间。
6. **预期趋势**：低负载时缓存收益小、差异不显著；高负载/高更新时完整系统优势最大；只用 RP1 时刷新/淘汰仍弱；只用 RP2 时价值粗糙、违约可能更高。
7. **否定条件**：完整系统相对最佳单组件在净收益上提升 <5%，或在扣除管理税后优势消失；或任何越权复用。
8. **结论范围**：端到端只证明“在该负载/该数据上有效”；机制归因必须回到 E1.x/E2.x。

#### E3.2 负载/版本/权限变化下的鲁棒性

1. **假设**：完整系统在阶跃负载、更新突发、权限变化下比固定策略恢复更快、违约更少。
2. **自变量/混淆**：扰动类型（负载阶跃、更新突发、权限撤销、租户混合变化）；策略（固定 TTL、vCache、完整系统）。混淆：扰动幅度、检测延迟。
3. **数据**：W1–W3 的扰动回放；合成阶跃。
4. **对照**：固定 TTL、vCache、成本感知淘汰、完整系统。
5. **指标**：恢复时间（回到基线 ±5%）、扰动期间违约、净收益损失、churn、价格轨迹。
6. **预期趋势**：固定策略在扰动后长时间偏离；完整系统通过价格/风险预算更快适应；但价格震荡可能带来短期过冲。
7. **否定条件**：无恢复优势，或扰动期间违约显著上升。
8. **结论范围**：扰动类型/幅度；不证明“任意漂移”。

#### 8.6.3 验收实验

**E4.1 开销**

1. **假设**：控制面开销 <10% 吞吐，p95 增加 <20 ms。
2. **自变量/混淆**：并行度（2/4/8）、状态大小（10^4/10^5/10^6）、checkpoint 间隔。混淆：外部 LLM 延迟。
3. **数据**：W1–W3 回放；合成请求率 10–50 req/s。
4. **对照**：无状态基线（只做精确匹配）。
5. **指标**：吞吐、p50/p95/p99、CPU/内存、checkpoint 大小/耗时、反压。
6. **预期趋势**：开销随状态/并行度上升；异步化后读路径开销下降。
7. **否定条件**：开销 >20%，或 p95 增加 >50 ms。
8. **结论范围**：原型规模；不外推生产。

**E4.2 恢复与 rescale 一致性**

1. **假设**：checkpoint/restore/rescale 后 INV-1 不被违反；命中率 5 分钟内恢复 ±5%；重建成本在预算内。
2. **自变量/混淆**：故障类型（TaskManager kill、JobManager failover、rescale up/down）；checkpoint 间隔；在途事件量。混淆：外部索引恢复时间。
3. **数据**：W1–W3 回放；注入版本/权限事件。
4. **对照**：无 checkpoint、不同 checkpoint 间隔、不同并行度。
5. **指标**：恢复时间、陈旧复用、越权、命中率恢复、重建成本、重复刷新次数、状态一致性校验。
6. **预期趋势**：checkpoint 越频繁，恢复越快但开销越大；在途事件重放不产生旧版本覆盖；命中率有短暂下降后恢复。
7. **否定条件**：任何 INV-1 违反，或恢复 > 门槛，或重复刷新爆炸。
8. **结论范围**：原型规模/故障类型；不证明跨区域/多集群。

#### 8.6.4 原型能证明与不能证明什么

| 能证明                                      | 不能证明                         |
|:------------------------------------------- |:-------------------------------- |
| 依赖闭包/版本向量可在 keyed state 中维护    | 生产级多区域一致性               |
| timer 可驱动 TTL/复审/刷新                  | 亚秒级实时性                     |
| checkpoint 可保存价值参数/依赖/生命周期状态 | 外部 ANN/负载存储的 exactly-once |
| rescale 后失效一致性可保持                  | 大规模（>10^6 对象）性能         |
| 控制器开销在可接受范围                      | 真实生产流量的外部有效性         |
| 失效传播的幂等/去重可实现                   | 跨租户安全审计的完整性           |

### 8.7 消融与负结果

> E5 是消融集合，不是单一实验；每个消融沿用 §8.3/§8.4 的数据、对照与指标，表中只列增量假设、预期影响与否定条件。

#### 8.7.1 必做消融

| 消融 | 去掉什么                         | 预期影响                                     | 否定条件                       |
|:---- |:-------------------------------- |:-------------------------------------------- |:------------------------------ |
| A1   | 负载影子价格 `λ`                 | 高负载区间后悔上升；决策不再随负载移动       | 无变化 → 删除 `λ`              |
| A2   | 依赖闭包/版本向量                | 陈旧复用上升；刷新决策变差                   | 无变化 → 依赖图可简化          |
| A3   | 固定 TTL 替代刷新策略            | 高更新区间陈旧率上升；churn 可能下降         | 固定 TTL 不差 → 刷新机制不成立 |
| A4   | 去掉质量风险预算                 | 违约上升；短期净收益可能更高                 | 违约不升 → 预算不约束          |
| A5   | 去掉刷新下游损失                 | 刷新过度；净收益下降                         | 无变化 → 级联可删              |
| A6   | 只保留精确匹配                   | 收益大幅下降；质量最高                       | —（下界）                      |
| A7   | 去掉 `VERIFY`                    | 高风险区间违约上升；低风险区间净收益可能上升 | 无变化 → 验证不必要            |
| A8   | 去掉失效域预算                   | 尾部违约上升                                 | 无变化 → 逐项阈值足够          |
| A9   | 去掉共享价格（每个动作单独阈值） | 资源竞争失控；净收益下降                     | 无变化 → 联合控制不成立        |
| A10  | 去掉 LCB（用均值）               | 不确定性高时违约/后悔上升                    | 无变化 → 不确定性建模不必要    |

#### 8.7.2 必报负结果区间

| 区间                           | 预期结果                   | 解释           | 论文写法              |
|:------------------------------ |:-------------------------- |:-------------- |:--------------------- |
| 复用率低（<5%）                | 缓存收益 <管理税           | 机制前提不成立 | 明确写“不推荐启用”    |
| 重算成本低（小模型/短 prompt） | `W` 小，`C_v` 占比高       | 验证不划算     | 只对高价值对象启用    |
| 知识更新频繁（半衰期 < 窗口）  | 陈旧率高，刷新成本高       | 缓存生命周期短 | 退化为精确匹配/短 TTL |
| 质量约束极严（δ < 1%）         | 可复用对象少，预算利用率低 | 风险预算主导   | 报告“安全但收益低”    |
| 低负载（ρ < 0.3）              | `λ` 小，缓存只买延迟       | 价值主要是时延 | 不以吞吐/成本主张     |
| 多租户权限高度异构             | 跨租户复用少，隔离成本高   | 复用机会被切碎 | 分租户报告            |
| 验证成本高（`C_v/W` >0.5）     | `VERIFY` 被支配            | 验证税过高     | 删除 `VERIFY`         |
| 精确匹配局部性强               | 语义缓存增量小             | 匹配器已足够   | 把语义缓存降为可选    |
| 引擎 APC 已覆盖大部分 prefill  | 逻辑缓存收益被高估         | 收益边界       | 明确扣除/说明         |

#### 8.7.3 负结果的写法

负结果不是“实验失败”，而是论文的一部分。每个负结果必须写：

1. 在什么条件下发生；
2. 机制为什么失效（是前提不成立、成本太高、还是风险不可控）；
3. 对实践的启示（何时不该启用）；
4. 对后续章节的接口影响（例如第二章是否需要重新算有效负载）。

### 8.9 统计、可复现性与成本

#### 8.9.1 统计单位

- **分析单位是会话/租户，不是单请求**：同一会话的请求相关，同一对象的复用也相关。用 cluster bootstrap（按会话/租户重采样）计算置信区间。
- **配对比较**：同一 trace 上跑不同策略，用配对 bootstrap 比较差异，降低方差。
- **多种子**：合成器至少 5 个种子；真实回放按时间切分训练/测试，避免未来信息泄漏。
- **多重比较**：对主指标做 Holm/BH 校正；报告效应量与 CI，不只报 p 值。
- **预注册**：在跑主实验前写下判定门槛（本文 §8.8 即预注册草案）。

#### 8.9.2 可复现性

| 项     | 要求                                                             |
|:------ |:---------------------------------------------------------------- |
| 代码   | 控制器、合成器、回放脚本开源（或附附录）                         |
| 配置   | 所有超参、价格、δ、容量、种子写入配置文件                        |
| 数据   | 公开数据给下载脚本；合成数据给生成器与种子；不能公开的给统计摘要 |
| 日志   | trace schema（附录 B）+ 决策日志 + 价格轨迹                      |
| 环境   | Flink/vLLM/模型 revision、GPU 型号、驱动版本                     |
| 成本   | judge/LLM 调用次数与费用单独报告                                 |
| 负结果 | 所有区间都报告，不只报最好的                                     |

#### 8.9.3 成本控制

- P0/E1.x 以离线回放为主，LLM 调用按需；judge 抽样而非全量。
- E2.x/E3.x 用 profiled 模拟 + 小规模真实跑；真实跑只覆盖关键配置。
- E4.x 用 2–4 GPU、短时间窗口；故障注入用受控脚本。
- 预算上限：总 GPU 时间与 API 费用在 W1 估算，超出则按 §9.4 裁剪。

#### 8.9.4 伦理与隐私

- 不使用真实用户对话/企业文档的未脱敏数据；公开数据按许可使用。
- 租户 ID 匿名化；日志只存 `content_hash` 与特征摘要，不存完整 prompt/答案。
- 越权测试只在合成租户/受控环境进行，不触碰真实权限边界。
- 投毒/对抗测试只在隔离环境进行，不针对生产系统。

### 8.10 三个判定性实验（一页版）

| 实验            | 判定什么                                              | 通过意味着         | 不通过意味着                                 |
|:--------------- |:----------------------------------------------------- |:------------------ |:-------------------------------------------- |
| **E1.2**        | 动作条件价值 + LCB 是否降低决策后悔，而不只是降低 MAE | RP1 的核心成立     | RP1 退回“风险校准 + 保守门”；不主张动作价值  |
| **E2.3**        | 刷新级联是否值得作为独立机制                          | RP2 的核心机制成立 | 删除级联；RP2 收缩为“风险预算 + 失效 + 淘汰” |
| **E3.1 + E4.2** | 两个研究点闭环是否优于单组件，且 Flink 恢复后仍一致   | 第一章故事成立     | 收缩为“RP1 + 简单生命周期”；或只做离线回放   |

**为什么是这三个：**

- E1.2 直接检验“估值是否改善决策”，而不是预测误差；它决定 RP1 是不是一个独立研究点。
- E2.3 直接检验“刷新—命中耦合”是否值得成为独立机制；它决定 RP2 是不是“价值版 LRU”。
- E3.1 + E4.2 直接检验“两个研究点闭环 + 流式落地”是否成立；它决定整章故事是否自洽。

## 11. 风险、负结果与边界

### 11.1 当前最大的三个风险

**风险 1：复用机会与验证经济学不成立。**
这是最便宜排除、也最致命的风险。如果语义复用率只有 3%，或验证成本长期高于命中收益，整章的收益前提不成立。缓解：P0/G1 前置；主对象可切换；保底方案是“精确匹配 + 依赖版本 + 权限”，仍能提供正确性价值，但故事会缩水。

**风险 2：反事实不可观测，校准与收益被高估。**
缓存命中后看不到重算的质量；强制重算又有成本。若没有探索/倾向日志/OPE，RP1 的“净价值”无法被可信验证，评审会质疑“省下的就是赚到的”。缓解：从 W1 就在系统里预留 1–5% 探索与倾向记录；E1.6 专门验证 OPE；所有绝对收益都标注估计方法与偏差。

**风险 3：范围与工程量；新颖性碰撞。**
16 周内同时做动作价值、风险校准、依赖图、刷新级联、Flink 原型，任何一个环节都可能拖垮进度。与此同时，FinCacheServe（依赖一致复用）、Surplus（错误预算利用）、Workload-Aware Caching（DAG 淘汰）、ChurnBench（刷新调度）已经覆盖了相邻问题。缓解：按 §9.4 裁剪；把贡献定位在“动作条件 + 风险校准 + 级联 + 流式”的交集，而不是“首次”；用 E1.5/E2.5 的隔离实验证明增量。

### 11.2 其他风险

| 风险           | 表现                         | 缓解                                      |
|:-------------- |:---------------------------- |:----------------------------------------- |
| judge 成本过高 | 验证税吃掉收益               | 抽样、缓存 judge 结果、只对高价值对象验证 |
| judge 不可靠   | 标签噪声导致校准失败         | 人工抽查、置信度过滤、保守上界            |
| trace 不真实   | 合成负载上有效，真实流量无效 | 公开数据 + 半真实版本流 + 外部有效性小节  |
| 依赖元数据缺失 | 漏失效、错误复用             | 依赖登记作为准入条件；单独报告未登记率    |
| 价格震荡       | 决策抖动、churn 上升         | 平滑/钳制/冷却；冻结回退                  |
| 校准漂移       | ECE 随时间上升               | 在线监控、再校准、版本回滚                |
| Flink 状态膨胀 | checkpoint 慢、恢复慢        | 只存元数据；冷项落外部；分片/压缩         |
| 越权/安全      | 跨租户命中                   | 硬门 + 隔离域 + 安全审计；不把安全概率化  |
| 论文故事散     | 两个研究点像两个模块         | 用 §0.3 的因果链与 §7 的价格闭环统一叙事  |

### 11.3 负结果区间（必报）

| 区间                           | 预期                       | 结论              |
|:------------------------------ |:-------------------------- |:----------------- |
| 复用率 <5%                     | 收益 <管理税               | 机制不推荐启用    |
| 重算成本低（小模型/短 prompt） | `W` 小、验证税占比高       | 只用精确匹配      |
| 知识更新频繁（半衰期 < 窗口）  | 陈旧率高、刷新成本高       | 短 TTL/精确匹配   |
| 质量约束极严（δ <1%）          | 可复用对象少、预算利用率低 | 安全但收益低      |
| 低负载（ρ <0.3）               | `λ` 小、缓存只买延迟       | 不以吞吐/成本主张 |
| 多租户权限高度异构             | 跨租户复用少               | 分租户报告        |
| 验证成本高（`C_v/W` >0.5）     | `VERIFY` 被支配            | 删除验证          |
| 精确匹配局部性强               | 语义缓存增量小             | 语义缓存可选      |
| 引擎 APC 已覆盖 prefill        | 逻辑缓存收益被高估         | 明确扣除          |

### 11.4 边界声明

**本文计划主张（需实验支持）：**

- 在测试负载/数据/δ 区间内，动作条件价值比分数排序有更低后悔；
- 在测试条件下，依赖条件风险校准能把违约控制在预算内；
- 在测试条件下，刷新级联/失效域预算/联合控制有可测收益；
- 在原型规模内，Flink 状态/定时/恢复能实现上述机制；
- 机制在哪些区间失效（负结果）。

**本文不能声称：**

- 生产级多区域一致性；
- 任意 Agent 负载的普适收益；
- KV/prefix cache 层面的改进；
- “首个”或“最优”；
- 质量损失的通用货币化；
- 跨租户安全的完全保证（只能做到硬门 + 审计）。

### 11.5 如果机制失败，论文怎么写

| 失败           | 论文写法                                                             |
|:-------------- |:-------------------------------------------------------------------- |
| 复用机会不足   | 写成“语义回答缓存的收益边界”测量研究；主贡献转为 `rag`/上下文失效    |
| 校准失败       | 写成“语义缓存风险校准的困难与边界”；给出失败原因（标签/漂移/相关性） |
| 级联小         | 写成“刷新级联在何种扇出/命中率下才重要”的负结果                      |
| 联合控制无优势 | 写成“生命周期动作的耦合在本规模不显著”；RP2 降为执行模块             |
| Flink 太重     | 写成“最小流式原型的开销边界”；保留离线回放结论                       |

**原则**：负结果不是失败，而是“机制何时有效、何时不值得启用”的答案。论文的可信度来自边界，而不是只挑有利结果。

## 附录 F：一页式答辩口径（备用）

如果只有 3 分钟陈述，按以下顺序讲：

1. **问题**：Agent 缓存复用不是“相似就命中”；命中可能省很多，也可能错得很贵。
2. **两个研究点**：
   - RP1：给每个 `(对象, 请求, 动作)` 算净价值、风险上界与不确定性；
   - RP2：在容量/风险/验证/依赖约束下，联合决定准入、刷新、失效、淘汰。
3. **闭环**：RP1 给动作价值与敏感性；RP2 给约束价格与反事实日志；两边互相校准。
4. **最硬的证据**：
   - E1.2：动作条件价值降低决策后悔；
   - E2.3：刷新级联改变刷新时机；
   - E3.1/E4.2：端到端 + Flink 恢复一致性。
5. **边界**：不碰 KV、不做新匹配器、不做算力扩缩容；负结果区间明确。
6. **失败时**：保底方案是“精确匹配 + 依赖版本 + 权限”，仍能交付正确性价值。
