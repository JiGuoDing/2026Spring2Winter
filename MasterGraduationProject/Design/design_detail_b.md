# 毕业论文设计详细版

## 1. 研究题目

面向地球物理数据的流式 RAG 大模型推理系统设计与优化

## 2. 研究背景与问题分析

### 2.1 研究背景

随着地球物理勘探、反演计算、数值模拟和地质解释等任务的发展，地球物理领域产生了大量多源异构数据。这些数据可能来自野外采集设备、传感器网络、历史数据库、反演计算任务、模拟任务以及人工解释结果。

与此同时，大语言模型在知识问答、辅助解释、报告生成和智能决策支持等方面展现出较强能力。为了让大模型能够利用最新的地球物理资料，需要构建一个能够实时接入新数据、动态更新知识库并支持检索增强生成的系统。

传统离线式 RAG 系统通常存在以下问题：

1. 新数据进入知识库的延迟较高；
2. 多源地球物理数据之间的关联处理效率不足；
3. 面向大规模知识库的检索开销较大；
4. 大模型推理吞吐率受限；
5. 系统在负载变化时缺乏自适应调整能力。

因此，本文提出一个基于 Apache Flink 的流式 RAG 推理系统，将数据接入、数据关联、知识库更新、Prompt 构造、批量推理、指标监控和自适应调度统一起来。

### 2.2 地球物理数据特点

地球物理数据通常具有以下特点：

1. **多源性**
   - 可能来自不同采集设备、不同计算程序、不同数据库或不同 Kafka Topic。

2. **时空属性明显**
   - 数据通常包含采集时间、测线、测点、经纬度、深度、空间网格编号等信息。

3. **空间分布广泛**
   - 勘探区域可能覆盖大范围空间，不同区域数据密度差异明显。

4. **数据类型复杂**
   - 包括结构化表格数据、曲线数据、剖面数据、体数据、文本解释资料、反演结果等。

5. **实时性和增量更新需求**
   - 新数据采集或计算完成后，需要尽快进入知识库并被大模型使用。

### 2.3 核心问题

本文关注以下核心问题：

1. 如何基于 Flink 构建面向地球物理数据的实时处理框架；
2. 如何高效完成多源地球物理数据的流式 Join；
3. 如何将实时地球物理数据转化为可被 RAG 使用的知识；
4. 如何提高 RAG 检索效率并降低端到端时延；
5. 如何提高大模型推理服务的吞吐率；
6. 如何根据系统负载变化自动调整配置。

## 3. 总体架构设计

### 3.1 总体架构

系统整体由两个 Flink 任务组成：

- **Flink 任务一：数据处理与 RAG Prompt 构造任务**
  - 负责接收用户输入和实时地球物理数据；
  - 负责多源数据 Join、清洗和知识库更新；
  - 负责 RAG 检索与 Prompt 构造；
  - 负责将 Prompt 请求攒批写入 Kafka。

- **Flink 任务二：批量推理与系统自适应调度任务**
  - 负责读取上游 Kafka 中的批量请求；
  - 负责调用推理框架进行大模型推理；
  - 负责输出推理结果；
  - 负责监控系统负载并触发自适应重配置。

## 4. Flink 任务一：数据处理与 RAG Prompt 构造

## 4.1 任务一的功能定位

第一个 Flink 任务位于系统前半部分，主要目标是将实时输入转换为可供大模型推理的 Prompt 请求。

该任务承担两条逻辑链路：

1. **用户请求链路**
   - 接收用户问题；
   - 检索地球物理相关知识；
   - 拼接上下文；
   - 构造 Prompt；
   - 将请求发送给下游推理任务。

2. **地球物理数据更新链路**
   - 接收新采集或新计算的地球物理数据；
   - 进行清洗、标准化、关联和结构化处理；
   - 将结果写入地球物理知识库；
   - 为后续 RAG 检索提供增量知识。

## 4.2 输入数据设计

### 4.2.1 用户输入流

用户输入流主要包含用户自然语言问题，字段可设计如下：

| 字段          | 含义                                     |

| request_id    | 请求唯一标识                             |
| user_id       | 用户标识                                 |

| domain_hint   | 可选领域提示，如重力、磁法、地震、电法等 |
| location_hint | 可选空间范围，如区块、测线、经纬度范围   |
| task_type     | 可选任务类型，如问答、解释、报告生成等   |

### 4.2.2 地球物理数据流

地球物理数据流可来自多个 Kafka Topic。不同 Topic 对应不同来源或不同类型的数据，例如：

- 采集设备数据；
- 反演计算结果；
- 正演模拟结果；
- 历史解释资料；
- 空间网格数据；

## 4.3 数据清洗与标准化

由于地球物理数据来源复杂，需要在进入 Join 和知识库前进行统一处理。

主要清洗步骤包括：

1. 字段名称统一；
2. 时间格式统一；
3. 空间坐标系统一；
4. 异常值过滤；
5. 缺失值处理；
6. 单位转换；
7. 元数据补全；
8. 数据质量评分。

清洗后的数据被转换为统一内部格式，便于后续状态存储、Join 处理和知识库写入。

## 4.4 多源地球物理数据 Join 设计

### 4.4.1 Join 需求

在地球物理场景中，不同来源的数据往往需要根据时间、空间和业务字段进行关联。例如：

- 将同一区域的采集数据与反演结果关联；
- 将测线测点数据与地质解释文本关联；
- 将不同方法得到的物性参数进行联合分析；
- 将实时采集结果与历史模型进行对比。

因此，当多个数据源之间存在关联需求时，系统采用 Flink 双流 Join 模板实现实时拼接。

### 4.4.2 基础 Join 方式

可使用以下 Flink 算子或编程模型：

1. `intervalJoin`
   - 适用于按照事件时间窗口进行关联的双流数据；
   - 例如将时间差在一定范围内的两类数据进行 Join。

2. `KeyedCoProcessFunction`
   - 适用于自定义 Join 逻辑；
   - 可对两条流分别维护状态；
   - 根据空间、时间和业务规则触发匹配。

3. `Broadcast State`
   - 适用于一条流为主数据流，另一条流为维表或规则流的场景；
   - 可用于动态更新 Join 规则或空间索引规则。

### 4.4.3 空间感知 Join 优化

地球物理数据具有空间分布广泛的特点。如果仅使用普通 Key 进行 Join，可能导致状态访问范围大、匹配效率低或数据倾斜。

因此，本文设计空间感知的 Join 优化方法。

核心思路如下：

1. **空间编码**
   - 将经纬度、测区、网格或三维坐标转换为空间编码；
   - 可选方法包括 GeoHash、网格编号、Z-order 曲线、Hilbert 曲线等。

2. **空间分区**
   - 将空间相近的数据划分到相同或相邻分区；
   - 减少跨分区 Join 开销。

3. **邻域扩展查询**
   - 对于边界区域的数据，不仅查询当前空间单元，还查询相邻空间单元；
   - 保证 Join 结果完整性。

4. **状态局部化**
   - 将同一区域的数据尽量维护在相同 Keyed State 中；
   - 减少状态随机访问和无效扫描。

5. **状态 TTL 控制**
   - 对时效性较强的数据设置状态过期时间；
   - 减少状态膨胀。

6. **热点区域识别**
   - 对数据密度较高的区域进行热点检测；
   - 必要时进一步细分空间网格或增加并行度。

### 4.4.4 状态存取优化

该部分可结合已有项目中的状态访问优化经验，针对 Flink 状态后端进行优化。

可考虑的优化方向包括：

1. **状态 Key 设计优化**
   - 使用 `spatial_key + time_bucket + business_key` 作为组合 Key；
   - 提高状态访问的局部性。

2. **状态分层存储**
   - 高频访问数据保存在更快的状态结构中；
   - 低频或历史数据保存在 RocksDB State Backend 或外部存储中。

3. **状态索引优化**
   - 为时间范围、空间范围和业务字段建立辅助索引；
   - 减少 Join 匹配时的扫描范围。

4. **状态压缩与序列化优化**
   - 使用高效序列化格式；
   - 减少状态读写开销。

5. **异步访问**
   - 对外部存储或远程索引访问使用异步 I/O；
   - 降低算子阻塞时间。

### 4.4.5 预期优化效果

通过空间感知 Join 和状态访问优化，预期可以实现：

1. 提高 Join 吞吐率；
2. 降低 Join 端到端时延；
3. 减少状态访问次数；
4. 减少无效匹配；
5. 缓解空间热点导致的数据倾斜；
6. 提高系统整体稳定性。

## 4.5 RAG 算子设计

## 4.5.1 RAG 算子的功能定位

RAG 算子是第一个 Flink 任务的核心算子，负责连接实时数据流、知识库和大模型推理请求。

该算子承担两个方向的功能：

1. **查询方向**
   - 用户输入进入 RAG 算子；
   - RAG 算子从地球物理知识库中检索相关资料；
   - 将检索结果作为上下文；
   - 构造完整 Prompt。

2. **更新方向**
   - 新的地球物理数据进入 RAG 算子；
   - RAG 算子对数据进行清洗、切分、向量化和写入；
   - 将其更新到知识库或向量数据库中。

## 4.5.2 知识库结构

地球物理知识库可分为三部分：

1. **原始数据存储**
   - 保存原始文件、曲线、剖面、体数据或计算结果文件。

2. **结构化元数据存储**
   - 保存数据来源、时间、空间位置、测线测点、数据类型等信息。

3. **向量数据库**
   - 保存文本块、数据摘要、解释资料等内容的向量表示；
   - 支持语义检索。

## 4.5.3 数据写入流程

实时地球物理数据进入 RAG 算子后，按照以下流程处理：

1. 数据清洗；
2. 结构化转换；
3. 元数据提取；
4. 文本化或摘要化；
5. 文档切分；
6. Embedding 向量生成；
7. 写入向量数据库；
8. 写入元数据索引；
9. 更新缓存。

## 4.5.4 用户查询流程

用户问题进入 RAG 算子后，按照以下流程处理：

1. 解析用户问题；
2. 提取领域关键词、空间范围和时间范围；
3. 查询缓存；
4. 如果缓存命中，直接返回相关上下文；
5. 如果缓存未命中，访问向量数据库和元数据索引；
6. 对检索结果进行排序；
7. 根据 token 限制选择 Top-K 资料；
8. 拼接系统提示词、用户问题和检索上下文；
9. 输出完整 Prompt。

## 4.6 多级缓存机制设计

### 4.6.1 缓存设计目标

RAG 检索通常涉及向量检索、元数据过滤和上下文拼接，开销较大。为了降低查询延迟，本文在 RAG 算子中设计多级缓存机制。

缓存的目标包括：

1. 提高高频问题的响应速度；
2. 减少向量数据库访问次数；
3. 降低端到端时延；
4. 缓解知识库访问压力；
5. 支持系统根据负载动态扩缩容。

### 4.6.2 缓存层次

缓存可设计为三级结构：

| 缓存层级 | 位置                   | 内容                                    | 特点                   |
| -------- | ---------------------- | --------------------------------------- | ---------------------- |
| L1 缓存  | Flink 算子本地内存     | 高频 Query 的检索结果、Prompt 片段      | 速度最快，容量有限     |
| L2 缓存  | 外部高速缓存，如 Redis | 跨算子共享的检索结果、Embedding、元数据 | 容量较大，可共享       |
| L3 存储  | 向量数据库和长期知识库 | 完整知识数据                            | 容量最大，访问成本最高 |

### 4.6.3 基于预测的缓存替换策略

传统 LRU 或 LFU 只考虑历史访问情况，而地球物理任务中查询可能具有明显的区域性和阶段性。例如，在某个测区作业时，相关区域的数据会被频繁访问。

因此，本文考虑引入基于预测的缓存替换策略。

预测特征可包括：

1. 历史访问频率；
2. 最近访问时间；
3. 查询语义相似度；
4. 空间区域热度；
5. 用户任务类型；
6. 当前作业阶段；
7. 知识更新时间；
8. 缓存对象大小；
9. 缓存命中收益。

缓存对象的保留价值可定义为：

```text
CacheScore = f(访问频率, 最近访问时间, 空间热度, 语义相似度, 对象大小, 命中收益)
