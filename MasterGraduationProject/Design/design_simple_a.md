# 基于 Flink 的地球物理流式 RAG 推理系统设计简述

## 1. 研究背景

地球物理数据通常具有多源异构、规模大、实时性强、空间分布广泛等特点。传统离线式数据处理方式难以及时融合多源数据，也难以支持知识库的持续更新和大模型的实时推理。

本文拟设计一个基于 Apache Flink 的地球物理流式 RAG 推理系统，将实时数据处理、知识库更新、RAG 检索增强、大模型推理和系统自适应调控集成在统一的流式计算架构中。

系统整体由两个 Flink 任务组成：

1. 第一个 Flink 任务负责用户输入和地球物理数据的接入、处理、RAG 检索增强、Prompt 构造以及推理请求攒批。
2. 第二个 Flink 任务负责从 Kafka 中读取批量推理请求，调用大模型推理框架完成推理，并进行结果输出、系统监控和负载自适应调控。

---

## 2. 系统总体架构

系统采用如下架构：

```text
用户输入流
    |
    v
第一个 Flink 任务：数据处理与 RAG Prompt 构造
    |
    v
Kafka 推理请求队列
    |
    v
第二个 Flink 任务：批量推理与自适应调控
    |
    v
Kafka 推理结果队列
```

其中，第一个 Flink 任务还与地球物理知识库、向量数据库和多级缓存模块交互；第二个 Flink 任务还负责采集系统指标，并通过轻量级 Agent 判断是否需要进行系统重配置。

---

## 3. 第一个 Flink 任务：数据处理与 RAG Prompt 构造

第一个 Flink 任务接收两类输入：

1. 用户输入，例如自然语言问题、分析请求等；
2. 地球物理数据，例如来自多个 Kafka Topic 的采集数据或计算结果。

### 3.1 多源地球物理数据处理

对于来自不同 Kafka Topic 的地球物理数据，系统首先进行清洗和标准化处理，包括时间戳对齐、空间坐标统一、异常值过滤、字段格式规范化等。

如果不同数据源之间存在关联关系，则采用 Flink 双流 Join 或多流 Join 进行融合。例如，可以按照时间窗口、空间区域、测线编号、任务编号等条件进行关联。

### 3.2 面向地球物理数据的 Join 状态优化

地球物理数据具有明显的空间分布特征。为了提高 Join 效率，系统在 Flink Join 算子中引入空间感知的状态管理优化方法，包括：

1. 按空间网格、Geohash、区域编号或台站编号进行 `keyBy`；
2. 在状态中维护空间索引，减少无效匹配；
3. 为 Join 状态设置合理的 TTL，及时清理过期数据；
4. 对热点区域的数据进行缓存或分区细化；
5. 优化状态访问路径，降低 RocksDB 状态后端的随机读写开销。

该部分的目标是提高 Join 吞吐率，降低状态访问开销和端到端处理延迟。

### 3.3 RAG 算子设计

系统设计一个 RAG 算子，用于处理用户问题和地球物理数据。

对于用户输入，RAG 算子执行如下流程：

```text
用户问题
  -> 问题预处理
  -> 向量化
  -> 从知识库或向量数据库中检索相关资料
  -> 检索结果重排序
  -> 拼接上下文和用户问题
  -> 生成完整 Prompt
  -> 发送给下游攒批 Sink
```

对于地球物理数据输入，RAG 算子执行如下流程：

```text
新地球物理数据
  -> 数据清洗
  -> 结构化整理
  -> 文档切分
  -> 元数据标注
  -> 向量化
  -> 写入地球物理知识库和向量数据库
```

通过该设计，系统可以实现知识库的持续更新，并利用 RAG 提高大模型回答的领域准确性。

### 3.4 多级缓存机制

为了降低 RAG 检索延迟，RAG 算子中引入多级缓存机制：

1. L1 缓存：算子本地内存缓存，用于存储近期热点查询结果；
2. L2 缓存：Flink State，用于存储可恢复的热点知识片段或查询结果；
3. L3 存储：外部向量数据库和文档库，用于存储完整知识数据。

缓存查询顺序为：

```text
L1 本地缓存 -> L2 Flink 状态缓存 -> L3 外部知识库/向量数据库
```

缓存替换策略采用基于访问预测的方法，根据访问频率、最近访问时间、空间区域热度、任务类型和系统负载等因素计算缓存项价值，并优先淘汰低价值缓存项。

同时，系统根据缓存命中率、检索延迟和内存压力动态调整缓存容量，实现缓存扩缩容。

### 3.5 模型微调算子

系统可选设计模型微调算子，用于收集用户反馈、高质量问答样本和新增领域数据，并以异步方式对模型进行 SFT、LoRA 或其他轻量化微调。

为了避免影响在线推理链路，模型微调算子不直接位于主推理路径中，而是作为异步增强模块运行。

### 3.6 请求攒批 Sink

第一个 Flink 任务的 Sink 算子负责将生成的 Prompt 请求进行攒批，并写入下游 Kafka 推理请求队列。

攒批策略可以基于：

1. 批大小阈值；
2. 最大等待时间；
3. 请求优先级；
4. Prompt 长度相似性；
5. 下游推理服务负载。

通过请求攒批，可以提升下游 GPU 推理吞吐率，减少单请求推理带来的资源浪费。

---

## 4. 第二个 Flink 任务：批量推理与自适应调控

第二个 Flink 任务从 Kafka 推理请求队列中读取批量 Prompt 请求，并调用大模型推理框架完成推理。

### 4.1 推理算子

推理算子负责解析批量请求，并调用推理框架进行模型推理。推理框架可以是 vLLM、TensorRT-LLM、HuggingFace TGI 或其他大模型推理服务。

推理流程为：

```text
Kafka 批量请求
  -> Flink Source
  -> 推理算子
  -> 大模型推理框架
  -> 推理结果
  -> Sink 输出
```

### 4.2 结果输出与指标采集

Sink 算子接收推理结果，并写入下游 Kafka 推理结果队列。

同时，Sink 算子持续采集系统运行指标，包括：

1. Kafka 队列积压；
2. 端到端延迟；
3. 推理吞吐率；
4. GPU 利用率；
5. RAG 检索延迟；
6. 缓存命中率；
7. Flink 反压情况；
8. Join 状态大小；
9. 状态访问延迟。

这些指标会被记录为系统负载日志，并持久化到 Flink State 或外部监控系统中。

### 4.3 负载分析 Agent 与系统重配置

在第二个 Flink 任务的 Sink 算子中部署轻量级 Agent 服务。该 Agent 经过 SFT 训练后，能够根据系统运行指标判断当前负载状态，并给出是否需要重配置的决策。

Agent 的输入包括：

```text
Kafka 积压、端到端延迟、GPU 利用率、缓存命中率、RAG 检索延迟、Flink 反压比例等
```

Agent 的输出包括：

```text
是否需要重配置、重配置原因、推荐调整参数
```

可调控对象包括：

1. Flink 算子并行度；
2. Join 状态 TTL；
3. RAG 缓存容量；
4. RAG 检索 Top-K；
5. 请求攒批大小；
6. 推理批大小；
7. 模型推理实例数量；
8. Kafka 消费速率。

通过该机制，系统能够根据负载变化动态调整运行参数，提高系统稳定性和资源利用率。

额外想法：把触发重配置操作做成一个 tool，Agent 可以根据需要调用该 tool 来触发重配置，并根据 tool response 来判断重配置结果。

---

## 5. 主要研究内容

本文的主要研究内容包括：

1. 设计基于 Flink 的地球物理流式 RAG 推理系统架构；
2. 研究面向地球物理时空数据的多源 Join 与状态存取优化方法；
3. 设计面向 RAG 检索的多级缓存机制和预测式缓存替换策略；
4. 构建基于 Kafka 解耦的请求攒批与批量推理链路；
5. 设计基于轻量级 Agent 的系统负载分析与自适应重配置机制。

---

## 6. 预期效果

系统预期达到以下效果：

1. 支持多源地球物理数据的实时接入和融合；
2. 支持地球物理知识库的持续更新；
3. 通过 RAG 提高大模型回答的专业性和准确性；
4. 通过 Join 状态优化提高多源数据融合效率；
5. 通过多级缓存降低 RAG 检索延迟；
6. 通过请求攒批和批量推理提高推理吞吐率；
7. 通过 Agent 自适应调控提高系统在动态负载下的稳定性。
