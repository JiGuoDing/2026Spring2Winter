# 自跑 Trace 生成数据集的可行性方案

> 背景：v0.2 审计发现 ABCD 改造有三处硬伤（act 无真实工具结果、日期/版本脱钩、静态库泄漏），用户提出"自行部署服务、自己跑 trace 生成数据集"。
> 结论：**可行，而且在你这个选题下很可能优于继续改造 ABCD**；但要把它定位为"可控测试台轨迹"，不是"生产 trace"，并复用现有可执行环境，避免把论文时间耗在造世界上。

---

## 0. 结论

1. **可以自己做**：所需服务全部可开源部署（LLM 推理、embedding、向量库、模拟工具、数据库、编排、日志），不需要任何专有服务。
2. **你缺的不是服务，是 GPU**：当前工作站无独显、16 GB 内存，不能本地跑 7B+ 模型。三条路：API 模型（最省事）、按小时租 GPU、实验室 GPU。
3. **不要从零造世界**：优先用 τ²-bench（客服/工具/数据库/可验证奖励）、AgentBench DBBench（确定性 SQL 工具）、StableToolBench（虚拟 API）作为环境壳；把工作集中在"缓存相关埋点 + 版本/权限事件 + 请求流标定"。
4. **生成的是"基础执行轨迹"**：先跑无缓存的全量 agent 轨迹（含工具调用、检索、回答、时延、token），再离线回放缓存策略；这与 v0.2 的事件契约完全兼容。
5. **规模建议 2–5 万请求**（不是百万）：足够支撑 E1/E2/E5 的统计功效，API 成本约几十到几百美元，租 GPU 约 10–30 美元量级。
6. **最大风险不是技术，是"自造负载偏置"**：请求到达/重复分布必须对齐真实 trace（Chutes/FreeInference/DRGym），并把构造偏差量化、冻结。

---

## 1. 你要生成的是哪种 trace

| 类型 | 内容 | 能否自己生成 | 对你的用途 |
|---|---|---|---|
| A. 服务到达 trace | 请求时间、token 数、模型 | 容易，但没有内容 | 只补"到达形状"，已有 Chutes |
| B. **Agent 执行轨迹** | 请求、计划、检索、工具调用（参数/输出/时延）、LLM 调用、回答 | **这是你要的**，需要环境+agent+日志 | 四类缓存对象的全部内容与真值 |
| C. 缓存决策轨迹 | 命中/验证/重算、成本、质量 | 由 B 离线回放产生，不需要"跑" | E1–E5 的实验数据 |

**目标 = B 为基础轨迹 + C 为回放产物。** 不要试图生成"生产级 C"（那需要真实业务）。

---

## 2. 与继续改造 ABCD 的对比

| 维度 | ABCD-Cache v0.2 | 自跑 trace |
|---|---|---|
| act 真实性 | 只能构造"策略/状态谓词查询" | **真实工具输出**（数据库/模拟 API） |
| 时间戳 | 合成 | **真实运行时间**（含排队/推理/工具时延） |
| 版本事件 | 合成政策 v2–v5 | **可控且真实生效**（状态/政策/工具版本） |
| 权限 | 合成 ACL | 可在服务层真实执行 |
| 依赖/claim | 规则+人工 | 生成时可同步记录（模板/引用/槽位） |
| 静态库泄漏 | 需重映射+过滤 | **天然因果**（只允许历史服务过的对象） |
| 内容语言 | 真人客服对话（ABCD） | LLM/模板生成，需质量控制 |
| 外部效度 | 真人数据但场景小 | 更"系统真实"，但负载仍是自造 |
| 工程量 | 6–7 周 | 5–8 周（复用环境壳可压到 4–6 周） |
| 算力 | 几乎不需要 GPU（离线） | 需要 LLM 推理（API 或 GPU） |

**建议：两条腿走路**——自跑 trace 作为主实验台（解决 act/时间/版本），ABCD 作为内容种子（政策文本、意图、对话语言）与外部效度参照。不是二选一。

## 3. 技术栈与部署清单

| 组件 | 选型 | 资源 | 备注 |
|---|---|---|---|
| LLM 推理 | vLLM（本地 GPU）或 OpenAI 兼容 API（DeepSeek/Qwen/GLM） | GPU 或 API | 固定模型 digest、temperature=0 |
| Embedding | BGE-M3 / gte-large（TEI 或 API） | 小 GPU 或 CPU | 语料小，CPU 也能跑但慢 |
| 向量索引 | FAISS / Qdrant | CPU/内存 | 语料 1k–1M 块 |
| 关系库 | SQLite / Postgres | CPU | 订单/会员/政策状态 |
| 模拟工具 | FastAPI（查询订单、退款、物流、会员、政策检索） | CPU | 只读工具 + 少量写工具（写工具不缓存） |
| 政策引擎 | Python 规则/DSL | CPU | 生成 gold、判定合法性 |
| Agent 编排 | Python asyncio（或 Ray） | CPU | 支持并发请求、重试、分支 |
| 日志/追踪 | JSONL/Parquet + OpenTelemetry（可选） | 磁盘 | 统一 event envelope（复用 v0.2） |
| 容器化 | Docker Compose | CPU | 一键起服务 |
| 回放/评测 | Python + DuckDB | CPU | 离线策略回放、指标 |

**当前机器评估**：i7-13700 / 16 GB RAM / 无独显 / Q 盘约 954 GB。
- 编排、DB、模拟工具、向量库、日志：**完全够**；
- 7B 模型本地推理：**不够**（16 GB RAM 无 GPU，vLLM 跑不动；CPU 推理慢到不可用）；
- Embedding：CPU 可跑小模型，但建议用 API 或与 LLM 同机 GPU；
- 磁盘：足够存 2–5 万条完整轨迹（约 1–5 GB）。

---

## 4. 三种资源方案与成本

### 方案 A：全 API（最快上手）
- 模型：DeepSeek-V3 / Qwen-Plus / GLM-4 等，价格约 $0.3–1.5 / 百万 token（输入），$1–3 / 百万（输出）。
- 规模 3 万请求 × 2.2 次 LLM 调用 × 平均 1.4k token ≈ **9,000 万 token**。
- 成本粗算：**$50–200**（mid-tier）；用 GPT-4o 级别约 $300–800。
- 优点：无需 GPU、当天可开工；缺点：模型版本会变，必须锁定 API 快照/版本号，长期复现有风险。

### 方案 B：租 GPU（推荐，最平衡）
- 1×RTX 4090（24 GB）按小时约 $0.3–0.6；vLLM 跑 7B AWQ/FP8。
- 9,000 万 token 在 2,000 tok/s 批处理下约 **12–15 GPU 小时**；算上并发/重试约 20–40 小时 → **$10–25**。
- 14B 需 2×4090 或 A100；32B 需 A100 80GB。
- 优点：模型固定、可复现、成本低；缺点：要运维 vLLM。

### 方案 C：实验室 GPU
- 最佳；需确认卡型/显存/可用时长。A100/H100 可跑 32B，20–40 小时即可完成 3 万请求。
- 注意：不同 GPU 的 batch/量化会影响时延绝对值，必须记录硬件与配置。

**结论**：算力不是瓶颈；**2–5 万请求的量级，API 或租一张 4090 都够**。真正成本是 4–8 周工程时间。

## 5. 推荐架构

```text
请求流生成器（Poisson/regime + 会话模板）
        ↓
Agent 执行器（脚本策略 + LLM 生成语言）
   ├─ Plan 选择/适配（规则+模板）
   ├─ 检索（政策/文档）→ rag 对象
   ├─ 只读工具调用（订单/物流/会员/退款）→ act 对象
   ├─ 回答生成（模板+LLM）→ resp 对象
   └─ 版本/权限检查
        ↓
日志与真值（统一 event envelope）
   ├─ request/lookup/decision
   ├─ tool_call（参数/输出/时延）
   ├─ cache_object（内容/依赖/版本/size）
   ├─ update（政策/状态/ACL）
   └─ label（safe/reason/gold/quality）
        ↓
离线回放（DuckDB/Python）→ 缓存策略实验
```

### 关键设计选择

1. **环境壳优先复用**：
   - τ²-bench（retail/airline/telecom，客服+工具+DB+可验证奖励）最贴近你的场景；
   - AgentBench DBBench（确定性 SQL 工具）最简单；
   - StableToolBench（虚拟 API + 缓存）适合 act 工具轨；
   - WebShop（购物，reward）适合电商场景。
   自建"客服政策世界"只在需要 ABCD 政策文本/权限模型时才做，工作量约多 2–3 周。
2. **Agent 策略用"脚本执行 + LLM 生成"**：工具/计划由规则驱动，保证可复现和真值；LLM 只负责自然语言回答，降低轨迹噪声。
3. **写工具不缓存**：只读工具结果才进入 act 缓存；写操作记录但不复用。
4. **版本事件真实注入**：政策库 v1→vN、订单状态事件、ACL 事件都走同一事件总线；所有策略共享同一硬有效性门。
5. **日志 schema 直接复用 v0.2 契约**（event envelope、对象元数据、标签、成本），不要再另造一套。
6. **基础轨迹一次生成、多策略回放**：不要为每个策略重跑 agent；只有需要真实时延的分支做小规模实测。

---

## 6. 生成协议（七步）

1. **Pilot（1,000 请求）**：跑通环境+agent+日志；检查成功率、平均 token/请求、工具时延、回答质量。
2. **标定（1 周）**：把请求流统计对齐真实 trace——到达 CV、会话长度、重复率、热点漂移、前缀共享；报告偏差。
3. **生成基础轨迹（2–5 万请求）**：无缓存；记录全部对象、工具 I/O、检索结果、回答、时延、token、seed。
4. **注入事件**：6 个主版本事件 + 阈值/连续/无效果/ACL 事件；事件时间独立 seed、±2h 抖动。
5. **派生缓存流**：按 v0.2 的 KeySpec 与候选冻结规则，从基础轨迹派生候选/静态库/标签。
6. **分支实测（小样本）**：200–500 条任务，同初始状态跑 reuse 与 recompute 两分支，测真实墙钟/token；其余用查表成本。
7. **冻结 v1.0**：manifest、seed、模型 digest、成本表、数据卡、复现脚本。

## 7. 规模与算力估算（按 3 万请求）

| 项 | 估算 |
|---|---|
| 会话数 | 3,000–5,000 会话（每会话 6–10 请求） |
| LLM 调用 | 约 6.6 万次（2.2/请求） |
| token 总量 | 约 0.9 亿（输入 0.8 亿 + 输出 0.13 亿） |
| API 成本 | $50–200（mid-tier）；$300–800（GPT-4o 级） |
| 本地 7B GPU | 12–40 GPU 小时；租 4090 约 $10–25 |
| 存储 | 基础轨迹 1–5 GB（含完整 prompt/response） |
| 工程时间 | 4–8 周（复用环境壳取低值） |
| Flink 回放事件量 | 约 10–20 万事件（3 万请求 × 4–6 事件） |

若做 10 万请求：token 约 3 亿，API 成本 $200–700，GPU 40–130 小时；仍可承受，但工程与校验时间增加。

## 8. 风险与论文写法

| 风险 | 表现 | 控制 |
|---|---|---|
| **自造负载偏置** | 重复率/到达/热点是你定的，方法天然占优 | 对齐 Chutes/FreeInference/DRGym；报告偏差统计；λ=0 臂；冻结生成器 |
| 合成内容质量 | LLM 回答差/不一致 | 规则执行 + LLM 生成；固定 judge；人工抽检；质量门槛 |
| Agent 失败率高 | 轨迹大量失败，样本浪费 | 脚本策略保证任务完成；失败重试；成功率报告 |
| 模型漂移 | API 模型升级导致不可复现 | 锁定版本/快照；记录 digest；本地模型优先 |
| 硬件差异 | 时延绝对值随 GPU 变 | 报相对收益；同机同配置；硬件表 |
| 工程吞时间 | 2 个月都在搭环境 | 复用 τ²-bench/DBBench；MVP 先 5k 请求；砍掉浏览器环境 |
| 审稿人质疑"自造数据" | "这不是真实 trace" | 定位为"可控测试台"；外部效度用真实 trace 校准；代码/数据/种子全公开 |
| 成本失控 | agent 循环调用过多 | 预算上限；小模型；限制重试；批量并发 |

**论文定位建议**：
> "我们不是采集生产 trace，而是构建一个可复现的缓存实验测试台：用可执行环境生成带工具调用、版本事件与真值的 agent 执行轨迹，并用真实服务 trace 标定其到达与重复统计。"

这样审稿人质疑的是"标定是否充分"，而不是"你凭空造数据"。

## 9. 与 v0.2 的关系

- **自跑 trace 取代 T1 中"从 ABCD 抽 act/时间/版本"的部分**；
- ABCD 保留为：政策文本与意图/对话语言的种子、外部效度参照、resp/rag 内容源；
- T2–T5（SemCache/ToolBench/ChurnBench/FiscalQA/Chutes）仍作为外部效度轨；
- v0.2 的契约层（事件信封、对象元数据、标签、成本、冻结门）**原样复用**，不重新设计；
- 数据包从"ABCD 派生"变成"测试台生成"，但对外接口（事件流+账本+manifest）不变，后续实验无需改代码。

## 10. 分阶段计划

| 阶段 | 内容 | 时间 | 产出 |
|---|---|---|---|
| W0 | 选环境壳（τ²-bench/DBBench）、定模型与算力、定日志 schema | 3–5 天 | 技术选型单页 |
| W1 | Docker Compose：LLM/embedding/向量库/DB/模拟工具/编排 | 1 周 | 可一键起的环境 |
| W2 | Agent 执行器 + 日志 + 单请求端到端 | 1 周 | 1k 请求 pilot |
| W3 | 请求生成器 + 标定真实 trace + 事件注入 | 1 周 | 标定报告 |
| W4 | 生成 2–5 万请求基础轨迹 | 3–5 天 | 基础轨迹包 |
| W5 | 派生候选/静态库/标签 + 分支实测 | 1 周 | 缓存实验数据包 v0.9 |
| W6 | 冻结 v1.0 + 数据卡 + 复现脚本 | 1 周 | 交付包 |

## 11. 需要确认的资源问题

1. 有没有可用的 GPU（实验室/云）？卡型与可用时长？
2. 若只能 API，月度预算上限多少？能否接受模型版本锁定？
3. 是否接受以 τ²-bench/DBBench 作为环境壳（而不是自建客服世界）？
4. 目标规模是 2–3 万还是 5–10 万请求？
