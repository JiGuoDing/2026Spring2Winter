# 第二章重构讨论：从"推理时延预测"转向"容量控制"

> 文档性质：选题讨论稿，回答"Agent 算子一次输入包含多次推理、时延不可预测，第二章还能怎么做"。
> 结论先行，供导师讨论与后续改写 `20261102大论文讨论.md` §2 使用。
> 事实边界：Flink Agents 的旋钮与指标均取自官方文档 1.0-SNAPSHOT（要求 Flink ≥ 1.20.3），见文末来源；未实测，量级待预实验确认。

---

## 0. 一句话结论

**逐请求时延预测既不可行，也不必要。** 配置调优是一个控制问题，只需要三个可测量：
**排队量（现在有多堵）、服务需求分布（每个请求要多少活）、容量包络（这个配置能扛多少）**。
把"预测时延"换成"归因时延 + 维持达成率"，第二章不仅成立，而且比原方案更容易做实验、更容易证伪。

推荐的新定位：

> **面向内生负载的流式 Agent 算子容量控制：从时延预测到瓶颈归因与分层调参**

## 1. 卡点的真正来源：三个错配

### 1.1 目标错配：把"手段"当成了"目标"

原文 §2 写的是"给定推理时延 SLA，调整推理配置"。
但预测只是控制回路里的一个可选环节。控制回路可以是纯反馈的：

```text
         ┌──────────────────────────────────────────┐
         │  观测（队列/需求/达成率/成本/失败）        │
         ▼                                          │
   决策（选哪个旋钮、加到多少） ──► 执行（调参/扩缩容） ┘
```

预测只在"前馈"分支里出现，而前馈是可选的。没有预测，反馈仍然闭环。

### 1.2 对象错配：Agent 算子的"一次输入"不是"一次推理"

`inputRunProcessingLatencyMs` 的定义就是"从一次输入 run 开始到完成"，
它内部是 `Agent Loop × (LLM 调用 + 工具调用 + 记忆读写)`。设第 i 次输入有 N_i 步、第 j 步耗时 T_j，
则处理时延是**复合随机变量**：

```text
T_proc(i) = Σ_{j=1..N_i} (T_llm,j + T_tool,j + T_mem,j),   N_i 也是随机变量
```

对复合随机变量做点预测，误差必然被 N_i 的方差主导。但这只说明**不该预测单请求**，
不说明**不该控制系统**：`inputRunLatencyMs` 是官方直方图指标，P95 直接可读。

### 1.3 资源错配：两个不同的旋钮被写成了一个

原文 §2 同时说"推理实例数量和批次大小"（vLLM 侧）和"Agent 算子并行度"（Flink 侧）。
这是两个资源池、两种瓶颈、两套代价：

| 旋钮 | 资源 | 扩容代价 | 主要影响 |
| --- | --- | --- | --- |
| Flink 算子并行度 `p` | CPU slot / 网络 / 状态 | savepoint + 重启 + key 迁移 | 排队与并发，**不直接增加 GPU 算力** |
| vLLM 实例数 / 批大小 | GPU / 显存 | 模型加载（分钟级） | 真正的推理吞吐 |

**加 Flink 并行度不等于加算力**，它只是把更多请求同时压到 vLLM 门口。
这一点如果不在第二章说清，实验会得到互相矛盾的结果。

## 2. 参考系：Flink Agents 实际给了哪些旋钮与传感器

这一节决定"能做什么"，不是设想。

### 2.1 可用旋钮（官方配置项）

| 层级 | 旋钮 | 默认 | 作用与代价 |
| --- | --- | --- | --- |
| Flink | 算子并行度、slot、chain 策略、网络 buffer、checkpoint 间隔 | — | 最贵：savepoint + 重启 + key 重分配 |
| Agent 算子 | `max-in-flight-input-records` | 100 | 每 subtask 在途输入上限；到顶即反压。**便宜的"虚拟扩容"** |
| Agent 算子 | `num-async-threads` | CPU×2 | 每 subtask 异步工作线程；**池耗尽会让作业卡到 checkpoint 超时失败** |
| Agent 算子 | `async.batch.parallelism` | CPU 数 | 单次 `ctx.gather` 批内并发 |
| Agent 算子 | `chat.async` / `tool-call.async` / `rag.async` | true | 同步 vs 异步；同步会把等待时间算进占用 |
| Agent 算子 | `max-retries` / `retry-wait-interval` | 0 / 1s | 重试放大在途量，直接推高尾延迟 |
| 状态 | `short-term-memory.state-ttl.ms` | 0 | 与第一章的缓存生命周期共用 |
| 模型 | Model Routing / Decision Model / max tokens | — | **降级式调参**：少推理、换小模型（接第一章） |

### 2.2 可用传感器（官方指标，直接对应控制量）

| 控制量 | 指标 | 为什么关键 |
| --- | --- | --- |
| 排队时延 | `inputRunQueueLatencyMs` | **把"排队"从"处理"里拆出来了**，这是全文的支点 |
| 处理时延 | `inputRunProcessingLatencyMs` | 服务需求，测出来即可，无需预测 |
| 端到端 | `inputRunLatencyMs` | 达成率直接从直方图算 |
| 排队长度 | `numOfPendingInputEvents` | 队列长度 L，配 Little 定律 |
| 并发 | `numOfActiveInputRuns` | 在途量，判断是否打满 |
| 阶段归因 | `action.*.actionSchedulingLatencyMs`、`.actionExecutionLatencyMs`、`numOfPendingActionTasks` | 哪一段在吃时间 |
| 下游归因 | `llmCallLatencyMs`、`toolCallLatencyMs`、`subagentCallLatencyMs` | 区分 GPU 排队 / 工具慢 / 子 Agent |
| 吞吐 | `numOfInputRunsSucceeded`、`promptTokens`/`completionTokens` | 用 token/s 而不是 req/s 衡量负载 |
| 稳定性 | `numOfInputRunsFailed`、`retryCount`、checkpoint 对齐时间 | 调参可能把系统调崩 |

### 2.3 一个必须修掉的前提

`20261102_与导师讨论初稿版本三.md` 写的是 **Flink 1.17**；Flink Agents 要求 **Flink ≥ 1.20.3**，
且不支持 BATCH 模式的 keyed-state backend（`execution.batch-state-backend.enabled` 必须关闭）。
这会影响路由、状态后端与 checkpoint 的实验设计，需在开题前定版。

## 3. 六个替代信号：不预测时延，靠什么决策

### 3.1 信号一：排队量与反压（最便宜的闭环）

不需要知道"这个请求要多久"，只需要知道"现在排队在变长还是变短"。
Flink 原生有 `outPoolUsage`/`inPoolUsage` 反压指标，Flink Agents 又直接给了队列时延与 pending 数。
控制器就是：队列时延 P95 超过阈值 → 加 `max-in-flight` 或并行度；低于某值 → 减。

**优点**：零预测、可解释、工程成熟。
**风险**：这就是 K8s HPA / Flink Autoscaler 的思路，单独用没有学术新意，只能当基线。

### 3.2 信号二：服务需求分布（测，不预测）

从 Trace Log（`entityType=llm/tool/action`，带 `timestamp` 与 `executionId`）离线统计：
每个"任务类型 × 第几步"的 LLM 调用耗时分布、token 数分布、工具耗时分布。
用途不是预测某请求，而是算**聚合需求**：

```text
λ_eff  = λ_req × E[N_step]              （步/秒，而不是请求/秒）
G_eff  = λ_req × E[Σ tokens]            （token/秒）
ρ(c)   = λ_eff × E[S_step] / μ_step(c)  （利用率，必须 < 1）
```

只要 ρ < 1 且 E[S] 与 C_s² 可测，排队时延就有解析近似：

```text
E[W_q] ≈ (ρ / (1-ρ)) · ((C_a² + C_s²)/2) · E[S]
```

这不是"预测时延"，是**用测得的分布算系统的稳态行为**，可以用实测 P95 校验覆盖率。

### 3.3 信号三：容量包络（configuration → sustainable throughput）

对每个配置 `c=(p, in-flight, async-threads, batch, cache budget)`，
在给定达成率目标 A* 下测出**可持续到达率** μ_A*(c)。做一张表/热力图，控制器只做查表 + 保守插值。

这是本方案的核心资产：它把"时延预测"替换成"容量标定"，而容量是**配置的属性**，不是请求的属性，
因此可以离线测、可以复用、可以对不同负载族分别测。

### 3.4 信号四：瓶颈归因（本文最推荐的"替代预测"）

不问"要多久"，问"时间花在哪"。一次输入的时延可分解为：

```text
T = T_queue(算子) + T_hol(同 key 队头阻塞) + Σ_steps (T_llm_queue + T_llm + T_tool + T_mem)
```

Flink Agents 的指标已经按这个粒度切好。控制器规则：
**只调"占比最大且边际收益为正"的那一段对应的旋钮**。

- 若 `T_llm_queue` 占主导 → 瓶颈在 GPU，加 Flink 并行度无用，应加 vLLM 实例或降级。
- 若 `T_queue` 占主导且 `numOfActiveInputRuns` 已接近 `max-in-flight` → 加 in-flight。
- 若 `T_tool` 占主导 → 调并行度无用，应限制工具并发或改异步。
- 若 `T_hol` 占主导 → 这是**同 key 串行**，加并行度无用（见 §4.2）。

归因是**可观测的因果**，预测是**不可靠的推断**。用前者替后者，是这一章最干净的立论。

### 3.5 信号五：边际成本效益（每 GPU-小时的达成率增量）

```text
ΔA / Δcost  对每个旋钮分别估计
```

决策 = 选单位成本增益最大的旋钮。这让"并行度 vs 批大小 vs 降级"变成可比较的量，
而不是凭直觉设定。代价是需要小步试探（probe），但配置空间只有十几个离散点，试探成本可控。

### 3.6 信号六：稳定性与失败（SLA 的硬边界）

官方文档明写：异步池耗尽会"stall the job until Flink's checkpoint timeout fails it"。
这意味着**调参有崩溃模式**。因此第二章的约束不只是时延，还包括：

- `numOfInputRunsFailed` 不上升
- checkpoint 对齐时间不超阈值
- 重试率不上升
- 不出现"扩缩容震荡"（单位时间 rescale 次数上限）

把"调参把系统调崩"写成显式的失效分析，比多一个时延模型更有工程说服力。

## 4. 五个结构性洞察：这一章真正的"新东西"

### 4.1 负载是内生的（Agent Amplification）

Agent 的自适应计算让"一个请求要多少活"由模型自己决定，且**取决于系统当前状态**
（上下文越长、工具越慢、失败越多，步数越多）。所以：

```text
请求到达率 λ_req  ≠  负载
真实负载 = (步/秒, token/秒, 工具调用/秒)
```

**推论**：基于 req/s 的 autoscaling 在 Agent 场景会系统性错配——同样 10 req/s，
简单问答是 10 次推理，深度调研是 100 次推理。这条可以做成一个非常干净的对照实验，
也是"为什么现有流式 autoscaling 不适用"的核心论据。

### 4.2 并行度的单位是"会话"，不是"请求"

`fromDataStream(input, keySelector).apply(agent)` 是 keyed 算子，同 key 串行
（官方对 `inputRunQueueLatencyMs` 的说明明确包含 "time queued behind an earlier input with the same key"）。
于是有效并发有一个天花板：

```text
有效并行度 ≈ min(p, S_active),   S_active = 当前活跃会话数
```

**推论**：
1. 活跃会话数 < 并行度时，加并行度是纯浪费——这解释了容量曲线的"膝点"。
2. 热会话（一个大客户反复对话）是天然串行瓶颈，加并行度救不了，只能靠会话内并发或拆分算子。
3. 负载生成器必须控制"不同会话数"，只调 req/s 会得到不可解释的结果。

这是一条**可证伪的定量规律**，两小时实验就能验证，且是 Flink 场景特有的。

### 4.3 扩缩容的反身性：扩容动作会制造它要解决的问题

rescale → key 重新分配 → 会话迁移 → 短期记忆/缓存冷启动 + 状态恢复 →
单位请求的工作量上升 → 有效负载上升。

设扩容前后缓存命中率为 h、h'（h' < h），则净容量增益必须满足：

```text
(μ(c') / μ(c)) × (E[S(h)] / E[S(h')]) > 1
```

否则"扩容"反而更慢。这条把第一章（缓存）和第二章（算力）真正缝在一起，
也是很好的"反直觉结论"：**在高复用负载下，最优策略可能是"不扩容 + 保局部性"**。

### 4.4 两个串联队列：加并行度可能只是把排队搬了个地方

```text
Flink 算子队列  ──►  vLLM 连续批处理队列  ──►  GPU
   （可调 p）           （不可调，只能靠实例数）
```

GPU 是瓶颈时，提高 p 只会让更多请求同时进入 vLLM，抬高 TTFT 与显存压力，端到端不变甚至更差。
所以"并行度是否单调有益"本身就是一个应该被实验回答的问题，而不是假设。

### 4.5 旋钮有"快慢"和"贵贱"，必须分层

| 环 | 时间尺度 | 旋钮 | 代价 |
| --- | --- | --- | --- |
| 快环 | 秒 | 准入、排队、`max-in-flight`、重试开关 | ~0 |
| 中环 | 十秒~分钟 | `num-async-threads`、`async.batch.parallelism`、批大小、模型路由 | 低 |
| 慢环 | 分钟~十分钟 | 并行度、vLLM 实例数、缓存预算 | 高（savepoint/迁移/冷启动） |

**分层本身就是对"时延不可预测"的回答**：不确定性由快环吸收，慢环只需要粗粒度的容量判断。
这也解释了为什么"预测"在这套设计里变得不必要——快环不需要预测。

## 5. 目标函数的五种改写（SLA 不必是时延）

原文场景明确写"没有非常严格的 SLA 限制，更注重体验、质量与成本"。
那么"给定推理时延 SLA"这个前提和场景是矛盾的。可选的替代形式：

| 形式 | 定义 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. 达成率约束 | `P(T ≤ D) ≥ A*`，最小化成本 | 只需实测分位数，无需预测 | D 的选取需论证 |
| B. 软效用 | `U(T)=1 (T≤D)`，之后指数衰减 | 不会因"晚 1ms"全盘归零；贴近体验 | 效用函数需标定 |
| C. 相对 slowdown | `T / T_solo` ≤ k | 尺度无关，直接反映"争抢"，与配置强相关 | 需离线测 T_solo |
| D. 进度型 SLA | 每 X 秒必须有一步进展 | 执行中可观测，能抓 stall/池耗尽 | 不约束总时长 |
| E. 成本归一 goodput | 每 GPU-小时完成的任务数（质量达标） | 直接对齐"降本"目标 | 需统一成本口径 |

**建议**：主用 A（好实现、好报告），辅用 B（解释体验），C 作为诊断指标，E 作为最终汇报口径。
**D 特别值得写进论文**：它是唯一能在 Agent 运行过程中判断"卡住了"的 SLA 形式，
正好对应"工具时延不可预测"这个原始痛点——不去预测工具多久返回，而是约束"不许长时间没有进展"。

## 6. 方法路线：三档，按四个月的工作量选

### 路线 A（推荐）：测量驱动的分层控制 + 容量包络

1. **标定**：离线扫配置 × 负载，测容量包络与膝点；用 Trace Log 统计阶段服务分布。
2. **归因**：在线计算各阶段时延占比（滑动窗口）。
3. **控制**：规则 + 迟滞 + 冷却；快环优先，慢环仅在"预计增益 > 迁移代价"时触发。
4. **验证**：真实集群回放 + 校准后的离散事件仿真（解决 2–4 卡样本不足）。

贡献落点：负载度量（4.1）、会话并行度规律（4.2）、反身性（4.3）、分层与失效模式（4.5）。

### 路线 B（增强）：排队论/鲁棒模型 + MPC-lite

用 §3.2 的近似 + 实测校准，做 2–3 步预测视界的滚动优化；用 conformal 分位数给"未知分布"上界。
贡献更"理论"，但标定工作量大，且很容易退化成"用复杂模型拟合噪声"。

### 路线 C（不建议作为主线）：在线学习（bandit / BO）

配置空间小，但每次试验要跑分钟级、集群噪声大、非平稳。
2–4 卡上样本量根本不够收敛。可做成"仿真里验证 + 真机小规模佐证"，写进讨论与局限。

### 路线 D（被否掉的"修复预测"方案）

把点预测换成"步级分布 + 循环次数生存模型"再做卷积。技术上成立，但：
需要大量带标注轨迹、分布漂移严重、**而且即使预测完全准确，也不能回答"该调哪个旋钮、值不值"**。
预测既不充分也不必要，故不作为主线，只作为相关工作里的一个对照。

## 7. 第二章重构草案

### 7.1 标题与两节

- **2.1 面向流式 Agent 算子的负载与容量刻画**（替代"推理时延预测"）
  - 负载的度量：请求率 → 步率/token 率；Agent Amplification 的测量与分布
  - 阶段服务需求：LLM / 工具 / 记忆的耗时与 token 分布（Trace Log）
  - 容量包络：配置 → 可持续吞吐 @ 目标达成率；膝点与瓶颈迁移
  - 会话并行度规律：`有效并行度 ≈ min(p, S_active)` 的验证与偏差分析
- **2.2 面向负载变化的容量控制策略**（替代"基于时延预测的调优"）
  - 分层控制：快环（准入/in-flight）、中环（异步池/批）、慢环（并行度/实例）
  - 归因驱动的旋钮选择；边际收益决策
  - 迁移代价与缓存局部性的联合判断（反身性）
  - 稳定性：迟滞、冷却、震荡抑制、失败模式与回退

### 7.2 实验矩阵

| 实验 | 问题 | 对照 | 指标 |
| --- | --- | --- | --- |
| E2-1 并行度饱和 | 加并行度何时不再有用？ | p = 1/2/4/8 | 吞吐、排队时延、vLLM 队列、达成率 |
| E2-2 会话并行度 | `min(p, S_active)` 是否成立？ | 均匀 key vs 热 key | 有效并发、队头阻塞占比 |
| E2-3 负载度量错配 | req/s 控制 vs 步率控制 | 两种 autoscaling | 震荡次数、超额配置率、达成率 |
| E2-4 旋钮替代性 | 多 subtask×少 in-flight vs 少 subtask×多 in-flight | 等总量并发 | 单位成本达成率 |
| E2-5 迁移反身性 | 扩容是否反而变慢？ | 扩容 vs 不扩容 | 冷启动 miss、恢复期达成率、净增益 |
| E2-6 闭环 | 完整控制 vs 固定/阈值/Oracle | 4 类 | 达成率-成本 Pareto、rescale 次数、失败率 |

**评价口径**：达成率-成本 Pareto 前沿 + 相对 Oracle 的 regret + 震荡/迁移次数。
不报"预测精度"，因为没有预测器。

### 7.3 与第 1、3 章的接口

```text
第一章：复用决策 ──► 输出"有效到达率 + 单位请求工作量分布" ──► 第二章定容量
第二章：容量与迁移 ──► 输出"副本数/路由约束/迁移时机" ──► 第三章定路由
第三章：路由结果 ──► 改变缓存局部性 ──► 反馈回第一章、第二章
```

三者构成一个真实的反馈环，而不是三个并列模块。**反身性（4.3）就是这个环的数学表达。**

## 8. 四个判定性预实验（1–2 周内可出结果，决定路线）

| 预实验 | 怎么做 | 若成立 | 若不成立 |
| --- | --- | --- | --- |
| P1 并行度膝点 | 固定负载，p=1/2/4 扫描，同时看 vLLM 队列 | 存在膝点且由下游造成 → 立论成立 | 并行度线性有效 → 第二章退化为经典 autoscaling，需换角度 |
| P2 热 key | 100 会话均匀 vs 10 会话热点，同 req/s | `min(p,S_active)` 明显 → 有独家结论 | 无差异 → 删除该主张 |
| P3 迁移代价 | 强制 rescale 一次，测前后 10 分钟 | 恢复期达成率显著下降 → 反身性成立 | 代价可忽略 → 简化控制器 |
| P4 旋钮等价 | 等并发下比较 in-flight vs 并行度 | 便宜旋钮可替代昂贵旋钮 → 分层有据 | 不可替代 → 保留并行度为主旋钮 |

四个实验都不需要新写系统，只需要改配置 + 读官方指标。**这是本方案相对原方案最大的优势：先有证据，再定模型。**

## 9. 风险与边界

1. **新颖性风险**：单看"按队列扩容"，HPA/KEDA/Flink Autoscaler 已覆盖。必须靠 §4 的四条 Agent/Flink 特有规律立住。
2. **版本风险**：Flink Agents 需 Flink ≥ 1.20.3，与现有 1.17 设计冲突；BATCH 模式不可用。
3. **测量开销**：Trace Log 是 best-effort，可能丢记录；指标是 task-attempt 局部，恢复后样本缺失。需在论文中声明。
4. **规模风险**：2–4 卡上"扩容"空间有限（p 只有几个整数点），所以主线必须是"分层 + 归因"，而不是"大规模弹性"。
5. **负结果风险**：P1/P3 很可能给出"并行度无用/迁移代价可忽略"，这时应把结论写成边界条件，而不是硬凑收益。

## 10. 需要向导师确认的三件事

1. 第二章是否可以从"时延 SLA 驱动的调优"改写为"达成率约束下的容量控制"（目标函数换口径）。
2. 是否接受"不做时延预测"作为明确的方法论选择，并把理由写成贡献的一部分。
3. Flink 版本是否可以从 1.17 升到 1.20.3+（否则 Flink Agents 这条技术路线不成立）。
