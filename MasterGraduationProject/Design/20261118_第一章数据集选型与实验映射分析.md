# 第一章数据集选型与实验映射分析

> 调研日期：2026-11-18。对象：《第一章_面向流式智能体的缓存价值建模与生命周期控制_初稿.md》1.4 节列出的 22 个数据集。
> 方法：5 个并行调研（resp/服务流、act/工具轨迹、rag/版本化语料、新兴业务 trace、相关工作 workload 方法学），逐条核对论文、官方仓库、HF 数据卡与许可证。文中"已核实/部分核实/未找到公开证据"为本次核对的边界，开工前仍需按第 9 节清单复核。

## 0. 一页结论

**你这 22 个候选里，真正适合作为毕业设计实验主干的只有 3 个：ABCD、ToolBench（建议配 StableToolBench）、Chutes 一年生产 trace。** 另外有三类缺口必须补：

1. `resp` 语义缓存的"错误率—命中率"标准评测集：**vCache 的 SemCacheLMArena / SemCacheSearchQueries**（HF 公开，vCache/Krites 都用它）；
2. 带"文档版本更新 + 可验证真值"的受控平台：**ChurnBench**（开源、ledger 真值、你参考文献 [12] 已引用）；
3. 真实版本事件的外部效度数据：**FiscalQA Pro**（真实"条文—版本—生效区间"，与你的 1.3.2 最贴合）。

其余按三类处理：**补充**（Search Arena 24K、AgentSim ATC、FreeInference、Mooncake、DeepResearchGym、ASQ、AReaL-tau2/τ²-bench、ShoppingBench/SN15、WorkArena++/WebShop 作为受控环境）、**只作样本池/压测**（Nemotron、MiroVerse、Ko-Agent、AgentBank、ShareChat）、**不建议/须纠正**（AitW、UserSim 是工具不是数据、PasarBench 查无此物）。

**关键判断：没有任何一个公开数据集同时具备"真实到达时间 + 重复请求分布 + 四类对象结构 + 文档版本事件 + 可验证真值"。因此第一章的数据方案必须是"三层拼装"——到达层借 trace、内容/重复层借任务数据集、版本层借版本基准或受控注入——并把每一层"哪些字段是构造的、偏差多大"写进论文。这不是退而求其次，而是公开数据现状下唯一可辩护的做法（Cortex 论文自己就写明商业查询日志不可得，SSC 的真实企业数据 InternalQA 不公开）。**

## 1. 筛选标准

按本章实验需求，一个数据集要同时回答六个问题：

| 标准 | 具体含义 | 对应实验 |
|---|---|---|
| S1 能否形成请求流 | 有到达时间戳，或可按会话/事件顺序重放并赋逻辑时间 | E2/E3/F |
| S2 是否有可统计的重复 | 精确重复、等价类、模板重复、同一工具+参数重复，且不是自己硬造出来的 | E1/A |
| S3 是否覆盖四类对象 | `resp` 问答、`rag` 证据、`act` 工具结果、`plan` 计划片段 | E1–E3 |
| S4 是否有可验证真值 | 程序化 reward / 动作级标签 / qrels / 人类偏好 / ledger | A/B/D/E |
| S5 是否有时间演化与版本 | 来源更新时间、版本区间、TTL/新鲜度标签，或可受控注入 | E2/E5 |
| S6 许可与成本 | 公开可下载、许可清晰、规模可在单机/小集群容纳 | 全程 |

**没有数据集能全部满足**。所以正确做法不是"找一个完美的"，而是：**一个叙事主场景 + 一条真实流 + 一条语义缓存标准线 + 一个版本实验平台，各自承担不同实验层，最后在 E6 拼装。**

### 3.3 几个关键数据集为什么是这个定位

**ABCD（核心，E1 主场景）**
- 10,042 条真人 role-play 客服对话、55 个子流程、30 个动作、125 个槽值、逐轮可自动评分；政策文件 `guidelines.json` 可拆成文档并注入版本。
- 这是公开数据中**唯一同时具备"动作序列 + 政策约束 + 逐动作真值"**的客服数据，正好对应你 1.2 的四类对象（resp=客服回复，rag=政策条款，act=账户/订单查询，plan=多步处理流程）。
- 限制：众包 role-play 不是生产 trace；无时间戳/版本/ACL；政策库只有 ~95 KB，做 RAG 检索会饱和——需要展开成自然段、加干扰文档，或只用于"政策—动作"这一层。

**ToolBench + StableToolBench（核心，act）**
- 126,486 条实例、469,585 次调用，工具名/参数/返回齐全，`toolenv/*/api.py` 可本地起服务，StableToolBench 提供虚拟 API + 缓存 + 模拟器，能把"真实 API 已失效"的问题绕开。
- 可直接统计"工具名+规范化参数"的精确重复率，并把只读工具（列表查询、详情查询）与写操作分开——这正是你 1.2 对 `act` 的限定条件。
- 限制：2023 年 API 大量失效；无时间戳；工具版本需自建（schema 哈希/快照日期）；观测里混有错误串需过滤。

**Chutes 一年 trace（核心，E2/E3）**
- 6.12B 请求、314,970 用户、9,174 个模型、875,921 个实例，字段含 `started_at/completed_at/it/ot/ct(缓存命中 token)/ttft`；CC BY 4.0，91 GB parquet 可用 DuckDB 按列查询。
- 论文报告 prefix-cache 命中呈双峰、复用高度集中在短间隔（约 50% 在 0.1 s、80% 在 10 s、99% 在 15 min 内），这直接支撑你的"缓存年龄/保留窗口"建模。
- 关键限制：**无 prompt/response 文本**，只能做系统层（到达、容量、TTL、吞吐、TTFT）与成本层，不能做语义正确性。它必须与内容层数据集拼接使用。

**vCache SemCache（必补，resp）**
- SemCacheLMArena 约 6 万条（3,500 个语义类、每类 1–23 个变体，类 ID 即等价真值），SemCacheSearchQueries 约 15 万条，另有 Classification/Combo；HF 公开。
- Krites 正是用这两个基准做 trace-driven 模拟（前 20% 历史前缀、后 80% 在线流、等价类 oracle、100 对人工审计），你的 E1（动作价值）与 E4（静态层异步验证提升）可以直接复用这套口径，和 vCache/Krites 可比。
- 限制：无时间戳、无文档版本、无权限；代码仓库许可徽章偏严（非商用/禁演绎），论文里注明学术用途。

**ChurnBench（必补，E5 受控平台）**
- 合成企业数据织物（Postgres/MongoDB/限流 SaaS API/文档库），每次变更写 append-only ledger，任意时刻 T 的金标由 ledger 重算；`--days 180 --seed 42` 可复现；MIT。
- 它能区分 **freshness error（取回时对、评测时错）** 与 reasoning error，并给出关键结论：**是刷新调度而不是缓存年龄决定陈旧性**（TTL 1/14/28 天时错误 7/4/4；禁用分层刷新后 28 天从 4 涨到 45）。这正好是你 1.3 的实验假设来源与对照。
- 限制：合成环境（软件资产域）；无权限维度；任务量小需自行扩生成；要真跑 agent 才有 LLM 成本。

**FiscalQA Pro（建议补，E5 外部效度）**
- 32,436 个"条文—版本"（法国税法 1938–2031，93 年），69,208 条判决→条文版本链接；209 道专家题；nugget 确定性评分。
- 它是目前少见的**真实版本事件 + 生效区间 + 时间适用性**基准：静态 RAG 严格准确率 2.7%，版本化语料 + 金标条文 99.1%——把"版本选择"的危害量级说清楚了。
- 限制：法语法律域、仅 209 题、无请求流/重复查询/权限；端到端检索器闭源，可作为 oracle-retrieval 条件下的外部效度实验。

**Search Arena 24K（补充，resp/rag 质量）**
- 24,069 条多轮对话、12,652 张人类偏好票、带时间戳、带 web search trace；prompt CC-BY-4.0，输出受模型 ToS 约束。
- 适合做"近重复 prompt 复用后的质量损失"和"检索证据是否支持回答"的人工偏好对照；2 个月时间窗也够做话题热度演化。
- 限制：没有时延/token/实例；票只覆盖一半会话。

**AgentSim ATC（补充，rag）**
- 103,567 条 step 级 reason-ing trace，字段含 `goal/action/tool_input/tool_output/evidence_retrieved/timestamp/execution_time_ms/error`，固定 199,968 篇文档，grounding 真值 100%。
- 适合做 rag 证据集合复用（同一 query 重复检索是确定的），以及"固定语料 v0 → 重建索引 v1"的版本注入。
- 限制：gated；工具空间只有 search/synthesize；step 时间不是用户到达时间；源数据许可混合（MSMARCO 非商用）。

**FreeInference / Mooncake / DeepResearchGym（补充，真实流）**
- 三者都是真实日志但都有硬伤：FreeInference 有会话/工具参数/延迟/块 hash但无文本；Mooncake 只有 1 小时且无文本；DRGym 被打散、只有会话内相对时间、无文档/答案。用法必须写清楚：**只借到达/规模/结构，不借语义真值**。
- 若只能留一个：FreeInference（agent 形态最贴合"流式智能体"，16 周、120 万请求、121 万次工具调用）；Chutes 已经覆盖系统层，两者选一即可。

## 7. 三层拼装协议与效度威胁

### 7.1 三层拼装

- **到达层**：Chutes（1 年、毫秒/秒级、可缩放）或 FreeInference（16 周、agent 会话、工具调用间隔）或 Mooncake（1 小时、agent 形态）。只取 inter-arrival 形状与规模，不取语义。
- **内容/重复层**：ABCD/ToolBench/SemCache/AgentSim 提供请求内容、对象结构与天然重复；按目标 QPS 绑定到到达点。
- **版本层**：FiscalQA Pro（真实版本区间）、ChurnBench（可编程 UPDATE/SUPERSEDE/EXPIRE + ledger）、ABCD 政策编辑（规则重算动作）、StreamingQA（`index(T)` 时间切片）。

### 7.2 重复注入三档

- R0 有机重复：只保留数据集中天然存在的精确重复/等价类/同工具同参数/同任务多次 rollout；
- R1 簇内重采样：只改重复次数，不改相似度结构；
- R2 受控注入：显式比例 λ∈{0,10,25,50}%，并报告"注入对相似度不高于 R0 中位数"、换改写模型重跑、λ=0 臂作为下界。

### 7.3 版本注入四档

- U0 无更新（对照）；U1 真实快照（FiscalQA/StreamingQA/SEC filing/Wikipedia revision）；U2 合成 churn（按对象设更新率，区分 content-change 与 answer-affecting change）；U3 近似碰撞探针（同实体不同期，测失效 P/R）。
- 二维网格：`TTL × 每实体更新率`，并保留"固定刷新调度"臂——ChurnBench 的结论是调度而非年龄预测陈旧。

### 7.4 指标纪律

- 三个命中必须分开报：**相似命中 / 正确命中 / 新鲜命中**；错误命中率、陈旧命中率、无效复用率（越权/过期/supersede 后仍复用）。
- **change ≠ harm**：FreshCache 在 396 对确认变更中只有 34.3% 影响答案正确性——不区分会高估失效收益。
- 命中时年龄分布（p50/p95）+ "TTL 内已变更未过期"比例；失效精确率/召回率（对 ledger）；fan-out。
- 质量：固定 judge 模型/prompt/温度，报与人工的一致率/κ，人工抽样按灰区分层 ≥200 条；oracle-judge 只作上界。
- 成本：策略收益与实现开销分账（参考 APC 的 1.04% overhead、FinCacheServe 的 GPU-s/Wh）；≥3 seeds、Wilson/ bootstrap CI；丢弃 warm-up（≥600 请求）并单列冷启动。
- 所有"构造字段"（到达时间、热点、版本、成本参数、后台预算）在论文中显式标注为实验构造。

### 7.5 主要效度威胁

| 威胁 | 表现 | 控制 |
|---|---|---|
| 自造重复偏置 | 注入 paraphrase 天然更相似 | λ=0 臂、相似度分布对齐、换生成器 |
| 生成—标签同源 | 同一模型改写又当 judge | judge 与生成器分离、人工核对 |
| 变更≠危害 | 只改内容未改答案 | 双参考判分（ChurnBench/FreshCache） |
| oracle 过理想 | 等价类当判官 | 加真实 judge 臂 + 噪声模型 |
| 非平稳 | 违背 i.i.d. 假设 | 报漂移统计量 + stationary 对照 |
| 暖机/泄漏 | 空缓存虚高 miss、测试答案进静态库 | 丢弃 warm-up、按任务/簇切分 |
| 许可 | CRAG 非商用、RealTimeQA 无许可、TimelyQABench 无 LICENSE、vCache 代码 NC-ND、MiroVerse NC | 只用 MIT/CC-BY 作主数据，其余注明学术用途 |

## 8. 实施顺序与时间预算（建议）

1. **第 0 周：许可与可得性复核 + ledger/schema 设计**（0.5–1 周）。别急着下载 91 GB，先确认许可与门禁（AgentSim gated、MiroVerse gated、FiscalQA 的 canary 串）。
2. **第 1–3 周：ABCD + SemCache 打通**（E1/A/B/D）。离线、便宜、快出结果；同时把复现口径对齐 vCache/Krites。
3. **第 3–5 周：ToolBench/StableToolBench + DBBench**（act/plan，E1/C）。起虚拟 API，统计精确重复与只读分类，测重算/验证成本。
4. **第 5–7 周：Chutes 到达层 + 生命周期**（E2/C/F 前半）。DuckDB 抽 1–2 周子集，按容量/TTL/热点分段回放。
5. **第 6–9 周：版本更新与修复**（E5）。先 ChurnBench 受控，再 ABCD 政策注入，最后 FiscalQA 外部效度（时间不够就放附录）。
6. **第 9–11 周：组合 + Flink 原型**（E6）。只报实现过的吞吐/恢复；事件回放与真实运行分开写。
7. **并行**：所有阶段保留日志 schema、随机种子、成本单价表；judge 成本计入资源账本。

> 时间预算按"一名硕士生 + 单机/小集群 + 本地 7B–32B 模型 + 固定 API 判官"估算；若用大模型跑 agent，成本会成倍上升，建议 E1/E5 用本地模型、只对 200–500 条样本做人工/API 判官核对。
