# 上下文压缩与会话记忆缓存 —— 硕士毕设缓存维度探索分析

> 探索日期：2026-09-23
> 探索方向：多轮 Agent 会话中，对话历史与会话状态的**中间表示**可以缓存什么
> 硬约束：不涉及工具调用｜缓存对象必须具体到 representation + reuse boundary｜推理时延可预测｜Flink 控制面可管理（不改 vLLM 内核）
> 证据标记：【论文】= 已精读原文的论文事实；【核验】= 仅核验摘要/身份；【分析】= 本报告推导或建议，非论文结论；【假设】= 待实验验证

---

## 0. 先给结论

在"上下文压缩与会话记忆"这个方向里，2025–2026 年的文献实际上分成了**两条完全不同的技术路线**，它们对"Flink 控制面能不能管"的回答截然相反：

| 路线 | 代表工作 | 操作对象 | Flink 控制面可管？ |
|---|---|---|---|
| **数据面 / 内核层记忆** | LiveMem（2608.02515）、在线 KV Compaction（2608.00902）、SeDeM（2608.00311）、TF-Engram（2607.07388） | 模型内部 hidden state / KV tensor / engram table | **不可**——必须改 vLLM 推理内核或模型结构，违反"不改引擎"约束 |
| **控制面 / 文本级记忆** | CrystalMem（2608.00303）、DPM（2604.20158）、Memanto（2604.22085）、AgentMemBench 的 CBS（2608.00009） | LLM 产出的摘要文本块 / typed facts / event log | **可**——纯文本或结构化 JSON，可存入 Flink Operator State |

**核心判断：本课题应深耕第二条路线。** 第一条路线虽然数字亮眼（KV Compaction 把峰值 KV 降 3.5×、吞吐提 4.2×【论文 2608.00902】），但它操作的是 attention KV，需要改推理引擎，且 2608.00902 这篇明确压缩的是"tool response"段，直接违反"不涉及工具调用"约束。第二条路线的缓存对象是**对对话历史做一次 LLM 调用后产出的文本/结构化中间表示**，命中后省略的是这次 LLM 调用——而这次调用的时延（排队+推理）正好落在本课题已有预测模型的覆盖范围内。

**最值得深化的 2 个候选（详见 §5）：**
1. **对话历史 chunk 的摘要文本块缓存**（候选 1b）——DPM 提供了最强的时延/精度数字，CrystalMem 提供了 fidelity 降级工程框架；
2. **对话状态变量的结构化缓存**（候选 3）——StateMem 的 supersession tracking 与 Memanto 的 typed schema 提供了具体表示；朴素 GEM 已被证明在长程崩溃，必须带 supersession 语义才有价值。

## 2. 候选 1：上下文压缩/摘要结果缓存

> **注意**：这个候选在文献里有两种截然不同的"压缩"，必须先区分。

### 2.0 先排除：KV 级压缩（数据面，不可用于本课题）

LiveMem、2608.00902、SeDeM、TF-Engram 都属于"操作模型内部表示"的压缩：
- LiveMem：在每 decoder layer 挂 GDN2 recurrent side-path，维护每请求 `32×128×128` FP32 tensor，需 post-training 训练状态转移函数，并在推理引擎内维护独立的 recurrent slot【论文 2608.02515 §2.2, Appendix C】。
- 2608.00902：Token Eviction / Attention Matching 直接对 attention KV tensor 打分和改写。

**排除理由【分析】**：(1) 需改 vLLM 内核或模型结构，违反"不改引擎"约束；(2) 2608.00902 明确把 assistant generation 和 tool response 分开压缩【论文 §A.3】，直接违反"不涉及工具调用"约束；(3) 它们优化的是 KV 显存和 decode 带宽，不是"省略一次 LLM 推理调用"。本课题推理时延预测只覆盖排队+推理，不覆盖 KV kernel 内的压缩操作。

### 2.1 可用子候选：文本级摘要块缓存

**这是本课题应深耕的方向。** 下面按要求的 8 个维度展开。

---

#### 2.1.1 缓存对象定义

**缓存什么**：当对话历史 chunk 因超出上下文窗口被驱逐时，对该 chunk 做一次 LLM 压缩调用，产出的**摘要文本块（summary segment）**。

**数据结构**【分析】：
```
SummaryBlock {
  session_id: string
  chunk_id: int              // 第几个被驱逐的 chunk（按时间序）
  chunk_token_count: int     // 原始 chunk 的 token 数（prefill 成本依据）
  summary_text: string       // LLM 产出的摘要文本
  summary_token_count: int    // 摘要 token 数（decode 成本依据，通常固定在预算内）
  content_hash: string        // 原始 chunk 文本哈希
  model_version: string       // 生成摘要所用的模型版本
  fidelity_level: enum         // full/compressed/skeletal/trace（借鉴 CrystalMem）
  created_at: timestamp
}
```

**大小量级**【论文 2608.00009 + 2604.20158】：
- AgentMemBench 实测 CBS（compression-based summarisation）的平均 memory footprint ≈ **3,478 tokens**（macro avg across 3 datasets），对比 EKV 的 5,126 tokens、ICW 的 297 tokens。
- DPM 的预算三档：tight **1,338 字符**（20× 压缩）、moderate 5,352 字符（5×）、loose 13,381 字符（2×），对应轨迹长度 ~26,762 字符。
- 即：一个被驱逐 chunk 的摘要块通常在 **0.3k–3.5k token** 量级，远小于原始 chunk（DPM 中 82–96 事件/轨迹 ~26k 字符）。

---

#### 2.1.2 复用边界

**精确复用**：同一 session 内，被驱逐的 chunk 已生成过 summary block；后续轮次拼接 prompt 时，直接用缓存的 summary 替代重新压缩该 chunk。由于对话历史是 append-only，chunk 内容本身不变，summary 的输入内容哈希可校验。

**近似复用（条件性有效）**：summary 保留语义但**有损**地丢弃了精确 token。文献给出了明确的失效类型【论文 2603.04814 Table 6】：
1. **Temporal marker 丢失**："MoMA 参观和 Met 展览之间隔了几天"——摘要只存了"对艺术主题一日游感兴趣"，没存日期。
2. **Implicit coreference 丢失**："我之前的职业"——摘要存了"管理实习生团队"，没存职位名"Marketing specialist"。
3. **Ephemeral update 丢失**：用户先说"每周瑜伽两次"，后更新为"三次"——摘要/旧事实没传播更新。

**失效条件总结【分析】**：当后续轮次的问题需要被摘要丢弃的精确细节（日期、数字、职位名、时序关系）时，缓存的 summary 不足以支撑回答，需要回退到原始 chunk 或触发重新提取。这是**近似复用**而非精确复用。

---

#### 2.1.3 失效机制

| 失效类型 | 检测信号 | 处理方式 |
|---|---|---|
| 原始 chunk 内容变更 | content_hash 不匹配（对话 append-only，实际很少发生） | 重新生成 summary |
| 模型版本升级 | model_version 不匹配 | 全部失效，重新压缩（【分析】） |
| 摘要质量退化（信息丢失被命中） | 新一轮 query 的 embedding 与 summary 匹配度低，或 LLM judge 判定回答质量下降 | CrystalMem 的 **recrystallization**：从 residue 重新展开，p50 586ms / p95 2.0s（Orin 边缘设备），阻塞前台推理 2.9% 时间【论文 2608.00303 Fig.9】 |
| 时序事实被 supersede | StateMem 式 supersession 信号：新对话轮次明确否定旧摘要中的事实 | 标记旧 summary 中的对应条目为 stale，保留 trace 级【论文 2608.19652】 |
| 跨会话时间窗口过期 | TTL / 时间衰减（CrystalMem 的 expiry 基线 H̄=0.178 vs CrystalMem 0.015） | 降级或淘汰【论文 2608.00303 Table II】 |

**关键工程机制【论文 2608.00303】**：CrystalMem 的四档 fidelity 状态机（full → compressed → skeletal → trace）+ verified recrystallization。它证明了"降级不是删除，而是可逆的"——每个降级 entry 保留 residue + invariants，预算恢复时可重建。这对 Flink 状态管理是直接可借鉴的：**summary block 不应是二元的"存/不存"，而应有分级退化路径。**

---

#### 2.1.4 时延可预测性分析

**命中后省略了哪个阶段**：省略了对被驱逐 chunk 的**一次 LLM 压缩调用**（compression call）。

**该阶段的时延由什么可观测特征决定**【分析】：
- 这是一次标准的 prefill + decode 推理：
  - **输入长度** = 原始 chunk 的 token 数（`chunk_token_count`，可观测）
  - **输出长度** = 摘要 token 数（`summary_token_count`，由预算固定，可观测）
- 因此 compression call 的时延 = 排队时延 + 推理时延，**正好落在本课题已有预测模型覆盖范围内**（排队时延 = 队列长度/到达率预测；推理时延 = f(prefill 长度, decode 长度, batch)）。
- 这是本候选最大的优势：不需要补全新的时延模型维度。

**缓存查找本身的开销**【分析】：
- Flink keyed state 查找（按 session_id + chunk_id）= O(1) 哈希，亚毫秒级，相对 LLM 推理（秒级）可忽略。
- **注意**：如果需要做"query 是否与某个 summary 相关"的语义检索来决定用哪个 summary，那引入了 embedding 检索开销——**这部分不在现有预测模型内，需要补全**。但 DPM 式做法避免了检索：它不检索，而是在 decision time 把整个 event log 做一次 projection【论文 2604.20158 §4】。

**DPM 的直接对比数字【论文 2604.20158 Table 1, §6.1】**：
- 增量滚动摘要（Summ-only）：每个 event 后一次 summarization call，n=82–96 个 event = 82–96 次 call。
- DPM（延迟投影）：decision time **1 次** projection call。
- DPM 比 Summ-only **快 7–15×**，且 tight budget（20× 压缩）下事实精度 FRP 0.907 vs 0.392（+0.515，Cohen's h=1.17，p=0.0014）。
- **关键洞察【论文】**：增量摘要的信息丢弃会**compound（累积）**——每一步丢弃的内容在后续步骤无法恢复；延迟投影避免了这个累积。这直接论证了"缓存 summary block"的价值：一旦生成并缓存，后续轮次复用它就省略了反复重压缩的 compounding 损失。

**AgentMemBench 的 CBS 实测【论文 2608.00009 Table 5】**：
- CBS Recall@5 = 0.556（macro avg），是检索亚军（冠军 EKV 0.792）。
- CBS latency = 3,540ms（5 策略中最高），footprint = 3,478 tokens。
- **但在 LoCoMo 长程召回上，CBS Recall@5 仅 0.005**——摘要在跨多会话的超长程上几乎崩溃，只有 EKV（dense retrieval）达到 0.573。

#### 2.1.5 Flink 层可行性

| 层 | 存什么 | 做什么 |
|---|---|---|
| **Flink 控制面** | Operator State：KeyedState by session_id → ListState&lt;SummaryBlock&gt; | 维护摘要块生命周期（生成、fidelity 降级、失效标记、checkpoint）；决策当前轮次拼接哪些 summary + 哪些 recent full turns |
| **vLLM 数据面** | 无变化 | 只看到拼接后的 prompt 文本（summary text + recent turns + 当前 query），不知道 summary 是缓存的 |

**不需要改 vLLM**【分析】：summary block 就是普通文本，拼入 prompt 即可。vLLM 的 prefix cache 自然会复用不变的前缀部分。

**checkpoint/恢复语义**【分析】：SummaryBlock 是纯数据对象，随 Flink keyed state checkpoint 持久化。故障恢复后，Flink 重放 checkpoint 即可恢复所有 summary block，不需要重新压缩。这比 vLLM 的 KV cache（易失，故障后需重新 prefill）有更强的容错语义——正好契合本课题"控制面持久状态 vs 数据面易失加速"的设计原则。

**CrystalMem 的工程佐证【论文 2608.00303 §V-A】**：它明确在 vLLM 之上跑 sidecar，"All policies serve from vLLM on A100 and H100 GPUs, with a Qwen2.5-7B-Instruct host"——即记忆管理完全在 vLLM 外部，不侵入引擎内核。这与本课题的 Flink 控制面定位一致。

#### 2.1.6 与现有三类缓存的区别

| 现有缓存 | 它是什么 | 本候选为什么不是它 |
|---|---|---|
| **上下文（KV prefix cache）** | prompt 前缀的 KV tensor 复用，数据面/vLLM 管理 | 本候选缓存的是 LLM 压缩产出的**文本块**，不是 KV tensor；生命周期独立于具体 prompt prefix；由 Flink 控制面管理。两者可叠加：summary 文本拼入 prompt 后，其前缀仍可被 vLLM prefix cache 复用 |
| **RAG 知识** | 外部语料库的文档块检索 | 本候选的来源是**本会话的对话历史**，不是外部文档；经过了 LLM 语义压缩，不是原文 embedding；有时间衰减和 supersession 语义 |
| **历史回答（语义缓存）** | 请求级的 question→answer 映射，命中后短路整个推理 | 本候选是**会话级中间表示**（chunk→summary），不短路推理（仍需基于 summary + 当前 query 生成回答）；粒度是 chunk 而非完整问答对；生命周期是整个会话而非单轮 |

**一句话区分【分析】**：历史回答缓存 = "跳过这次推理"；摘要块缓存 = "省略一次中间压缩调用，并缩短后续 prompt"。前者是请求级短路，后者是会话级中间产物复用。

#### 2.1.8 研究价值评估

**如果作为论文的一个缓存维度，研究问题是什么【分析】**：

> 在 Flink 流处理控制面，对话历史 chunk 的压缩调用何时触发、压缩到什么 fidelity、何时复用缓存 summary vs 重新压缩，才能在满足推理 SLO（排队+推理时延）的前提下，最小化压缩调用的累计开销？

**创新点可能在哪【分析】**：
1. **把"压缩决策"从规则驱动变为时延预测驱动**：传统做法是"超窗口就压"（CBS 每 s 轮压一次）。本课题可以用已有推理时延预测模型，在每个 chunk 驱逐点做收益-成本核算：
   - 成本 = 预测的 compression call 时延（排队 + prefill(chunk_len) + decode(fixed_summary_len)）
   - 收益 = 缓存 summary 后缩短后续轮次 prompt 的 prefill 节省 + 省略未来重压缩
   - 这与项目已有的"驻留门控（逐轮收益-成本在线核算）"框架完全同构，可以直接复用 RP3/RP4 的决策逻辑。
2. **fidelity 分级与 SLO 联动**：CrystalMem 证明四档 fidelity 有效，但它的降级 schedule 是 byte-budget 驱动的。本课题可以把降级触发条件改为**推理时延 SLO 驱动**——当预测排队时延超阈值时，主动把更多 chunk 降级到 skeletal/trace 级以缩短 prompt。
3. **DPM 式延迟投影 vs 增量摘要的在线切换**：DPM 证明 tight budget 下延迟投影更优，宽松预算下两者无差异。本课题可以按会话剩余轮数预测（已有 RP1）动态选择：短期会话用 DPM（不增量压缩，结束时一次投影），长期会话用增量 summary block。

## 3. 候选 2：会话级长期记忆/跨会话摘要缓存

### 3.1 缓存对象定义

**缓存什么**：单个会话结束时，对整个会话做一次 LLM 调用生成的**会话摘要（session digest）**，作为该用户后续新会话的 system prompt 上下文。

**数据结构【分析】**：
```
SessionDigest {
  user_id: string
  session_id: string
  session_digest_text: string   // 会话级摘要
  typed_facts: List<TypedFact> // 可选，结构化提取的事实
  token_count: int
  time_range: [start, end]
}
```

**与候选 1 的区别【分析】**：候选 1 是**会话内** chunk 级摘要（chunk_id → summary），生命周期限定在单个会话内；候选 2 是**会话级**摘要（session_id → digest），跨会话复用。

---

### 3.2 复用边界与失效

**有效条件**：新会话的问题与历史会话摘要中的事实/偏好相关。

**关键失效证据【论文 2608.00009】**：在 LoCoMo（需要回溯到很多会话之前的 turn）上：
- CBS（摘要记忆）Recall@5 = **0.005**
- EKV（dense retrieval）Recall@5 = 0.573
- ICW/GEM/WAM 也都 ≤0.005

**这意味着【分析】**：会话摘要在跨多会话的超长程召回上**几乎失效**。摘要丢失了原始 turn 的精确 provenance，当问题需要"很多会话前说过的某句话"时，摘要无法定位。这不是工程优化能弥补的——是表示本身的信息损失。

**失效机制**：
- **Stale propagation**【论文 2606.24535】：旧会话摘要中的事实被新会话更新后，旧摘要仍可能被注入，导致矛盾。
- **Ephemeral update**【论文 2603.04814 Table 6】："瑜伽每周两次"→后来改成"三次"，旧摘要没传播更新。
- Governed Shared Memory（2606.24535）把这形式化为四种失败模式之一：stale propagation。

---

### 3.3 时延可预测性

- **写入**（会话结束时）：一次 LLM call，输入=完整会话历史，输出=session digest。时延 = 排队 + 推理（输入=会话长度，输出=digest 固定长度），可预测。
- **读取**（新会话开始时）：注入 digest 文本到 system prompt，**增加了 prompt 长度**，因此增加了新会话首轮的 prefill 时延。这部分成本在现有预测模型内（输入长度增加 → prefill 增加）。
- **跨会话检索开销**：Memanto 报告无索引语义检索 **sub-90ms** 确定性延迟【论文 2604.22085】。这是 CPU 侧检索成本，**不在现有排队+推理时延预测模型内**，需补全。

---

### 3.4 Flink 层可行性

- **控制面**：Operator State by user_id → ListState&lt;SessionDigest&gt;。会话结束时触发一次 projection 写入。
- **数据面**：新会话开始时，Flink 算子从 state 中取该用户最近 N 个 digest，拼入 prompt。
- **不需要改 vLLM**。

---

### 3.5 与现有三类缓存的区别

**这个候选与"RAG 知识缓存"的边界最模糊**，需要明确切割【分析】：
- RAG 知识缓存：检索的是**外部语料**（政策文档、产品手册、历史案例库），与本用户对话无关。
- 会话摘要缓存：来源是**本用户自己的对话流**，经过 LLM 压缩，有时间衰减和 supersession。
- 但 AgentMemBench 的证据表明【论文 2608.00009】：跨会话长程上，摘要方法远不如 dense retrieval。因此**纯文本会话摘要的独立价值有限**——它更适合作为候选 1（会话内压缩）的延伸，而非独立缓存维度。

---

### 3.6 研究价值评估

**作为独立缓存维度的价值：中等偏低【分析】**：
- 文献证据不支持它在长程上有效（CBS Recall@5 0.005）。
- 与 RAG 缓存边界模糊，导师可能质疑"这不就是另一种 RAG 吗"。
- 更适合作为候选 1 的补充：会话结束时的 digest 是候选 1 中最后一个 chunk 的"终态摘要"，不需要独立成维度。

**如果要做，研究问题【分析】**：跨会话 digest 的注入策略——注入多少历史会话的 digest（token 预算），在不显著增加首轮 prefill 的前提下，多大程度提升新会话的 persona 一致性？PersonaMem v2 上 memory system 62.48% vs long-context 69.75%【论文 2603.04814】，差距仅 7.3pp，说明 persona 类信息适合 typed extraction。

---

## 4. 候选 3：对话历史的结构化表示缓存

### 4.1 缓存对象定义

**缓存什么**：从对话历史中提取的**结构化状态变量 / typed facts / 实体关系**，而非纯文本摘要。

**具体表示**：

**方案 A：Typed Facts（Memanto 式）【论文 2604.22085】**
- 13 个预定义 memory categories（如用户偏好、事实、时间、关系等）
- 每条 fact 有类型标签 + 时间版本
- automated conflict resolution（新事实与旧事实冲突时自动处理）

**方案 B：State Variables with Supersession（StateMem 式）【论文 2608.19652】**
- 显式跟踪 supersession（旧值→新值的替代关系）和 relational dependencies
- StateMem 在 current-state accuracy 上比最强同骨干基线提升 **1.8×（0.205→0.363）**
- 关键：不是存"事实"，而是存"当前有效状态"+ "被替代的历史值链"

**方案 C：Entity-Relation Graph（GEM 式）【论文 2608.00009】**
- (subject, predicate, object) triples，构建知识图谱
- AgentMemBench 实测 GEM Recall@5 = 0.361（**5 策略中最弱**），原因是 "off-the-shelf spaCy NER on informal dialogue produces noisy graphs"。
- **结论：朴素 GEM 不可取**，需要 LLM 级别的提取（如 Mem0/A-MEM）而非规则 NER。

**数据结构【分析】**：
```
StateVariable {
  user_id / session_id: string
  variable_name: string       // e.g. "current_city", "yoga_frequency"
  current_value: string
  value_history: List[{value, valid_from, valid_to}]  // supersession 链
  confidence: float
  source_turn_id: int         // 来自哪个对话轮次（可追溯）
}
```

**大小量级【分析】**：每条 state variable 通常 < 100 token；一个活跃会话维护 10–50 个变量，总量 ~1–5k token。与 summary block（0.3–3.5k token）相当或更小。

---

### 4.2 复用边界

**有效场景**：
- 事实型 / persona 型查询（"我住哪个城市？""我每周瑜伽几次？"）——PersonaMem v2 上 memory system 接近 long-context【论文 2603.04814】。
- 需要状态更新一致性的场景——StateMem 的 supersession tracking 直接解决"旧事实覆盖"问题。

**失效场景**【论文 2603.04814 Table 6】：
- 需要精确时序计算（"隔了几天"）——结构化 fact 只存了当前值，没存两个事件的精确时间戳关系。
- 需要隐式指代消解（"我之前的职业"）——提取管线可能只存了行为描述，没存职位名。
- 需要叙事连贯性的推理（LoCoMo 上 memory system 57.68% vs long-context 92.85%）——结构化事实丢失了叙事上下文。

---

### 4.3 失效机制

- **Supersession**：新轮次明确提供新值 → 旧值移入 `value_history`，current_value 更新。StateMem 证明这是核心机制（+1.8×）。
- **Conflict resolution**：Memanto 的 automated conflict resolution 处理新事实与现有事实矛盾的情况【论文 2604.22085】。
- **Temporal versioning**：Memanto 的 temporal versioning 标记每条 fact 的有效期。

---

### 4.4 时延可预测性

**生成成本**：
- 如果用规则提取（GEM 式 spaCy）：CPU 计算，非 LLM call，时延可预测（毫秒级）但质量差【论文 2608.00009：GEM 最弱】。
- 如果用 LLM 提取（Mem0/ENGRAM 式）：一次 LLM call，输入=对话 turn，输出=typed facts。ENGRAM 报告端到端 median **1.487s**（含 typed extraction + routing + retrieval）【论文 2511.12960】。
  - 这是一次 LLM 推理调用，时延在现有预测模型覆盖内（输入=turn 长度，输出=facts 固定长度）。

**检索成本**：
- Memanto：无索引语义检索 **sub-90ms**【论文 2604.22085】——CPU 侧，不在现有预测模型内，需补全。
- GEM：2-hop graph walk，NetworkX 图操作——毫秒级。

**命中后省略**：省略了"从对话历史中重新提取状态变量"的 LLM call，直接用缓存的 current_value。

---

### 4.5 Flink 层可行性

- **控制面**：Operator State by session_id → MapState&lt;variable_name, StateVariable&gt;。checkpoint 友好（纯 JSON 可序列化）。
- **数据面**：当前轮次 prompt 拼接时，把相关 state variables 作为结构化上下文注入（如"当前已知事实：{city=杭州, yoga=3次/周}"）。
- **不需要改 vLLM**。
- **额外优势【分析】**：结构化状态变量比自然语言摘要更紧凑、更可控，且天然支持 Flink 的 queryable state——可以在控制面直接做条件路由（如"if city changed, trigger re-onboarding flow"），这是纯文本摘要做不到的。

---

### 4.6 与现有三类缓存的区别

- **vs 上下文**：上下文是 token 序列；这里是键值对/图结构，经过语义提取。
- **vs RAG 知识**：RAG 检索外部文档块；这里检索本会话提取的结构化事实。区别在于**信息已经过 LLM 压缩和结构化**，不是原文。
- **vs 历史回答**：历史回答是完整答案；这里是中间状态变量，不短路推理（仍需基于状态+当前 query 生成回答）。

**与候选 1 的区别【分析】**：候选 1 缓存"叙事级摘要"（保留对话的叙述流），候选 3 缓存"事实级状态变量"（保留可枚举、可 supersede 的离散事实）。两者信息互补：摘要回答"之前聊了什么"，状态变量回答"当前事实是什么"。

---

### 4.7 研究价值评估

**研究问题【分析】**：
> 在 Flink 控制面，如何从对话流中在线提取并维护一组 supersession-aware 的状态变量，使得每轮 prompt 只需注入紧凑的结构化事实而非全文历史，同时保证状态更新的一致性？

**创新点可能在哪【分析】**：
1. **把对话状态维护建模为流处理的物化视图**：每轮对话增量更新相关 state variables（类似数据库 CDC → materialized view），而非每轮重读全部历史。这与 Flink 的 keyed state + process function 范式天然契合。
2. **Supersession 感知的注入策略**：不是盲目注入所有 state variables，而是根据当前 query 的 embedding 匹配度选择相关变量注入，平衡 prompt 长度与召回率。
3. **与候选 1 的分层组合**：full turns（最近几轮）+ state variables（关键事实）+ summary blocks（叙事上下文）= 三级上下文组装，Flink 控制面决定每级注入多少 token。

**风险【论文 2608.00009】**：AgentMemBench 已证明朴素 GEM 在长程上崩溃（Recall@5 0.361）。如果结构化提取质量不够（用规则 NER 而非 LLM），效果会很差。必须用 LLM 级提取，但这又引入额外 LLM call 成本——需要量化权衡。

---

## 5. 总结：最值得深化的候选与组合建议

### 5.1 最值得深化：候选 1b（对话历史 chunk 的摘要文本块缓存）

**理由**：
1. **证据最强**：DPM 提供了直接的时延（7–15× 加速）和精度（+0.515 事实精度）对比数字，CrystalMem 提供了 fidelity 降级的工程实测（p50 586ms recrystallization），AgentMemBench 提供了 CBS 的 footprint 和 latency 锚点。
2. **Flink 控制面完全可管理**：纯文本 SummaryBlock，Operator State，不改 vLLM，checkpoint 语义清晰。
3. **时延预测可直接复用**：compression call 就是一次标准 LLM 推理（输入=chunk 长度，输出=固定摘要长度），落在现有排队+推理预测模型内，不需要补全新维度。
4. **与项目已有框架同构**：InferenceStateFetcherProcessor 的 keyed state + 驻留门控逻辑可以直接复用到 summary block 的生命周期管理。
5. **与现有三类缓存边界最清晰**：不是 KV prefix cache、不是 RAG、不是历史回答短路——它是会话级中间文本产物的复用。

### 5.2 第二深化：候选 3（supersession-aware 结构化状态变量缓存）

**理由**：
1. StateMem 的 +1.8× current-state accuracy 证明了 supersession 跟踪的价值。
2. 结构化变量在 Flink 控制面可 queryable，支持条件路由，是纯文本摘要做不到的。
3. 与候选 1 互补：摘要保留叙事，状态变量保留事实。

**但需控制风险**：必须用 LLM 级提取（非规则 NER），并量化提取调用的成本。

### 5.3 不建议独立深化：候选 2（跨会话摘要）

AgentMemBench 已证明摘要在跨多会话长程召回上崩溃（Recall@5 0.005）。它更适合作为候选 1 的终态产物（会话结束时的 digest），而非独立缓存维度。

### 5.4 组合建议：三级上下文组装

```
Flink 控制面每轮组装 prompt 时：
  Level 1: Recent full turns（最近 k 轮原文，ICW）
  Level 2: State variables（supersession-aware 结构化事实，候选 3）
  Level 3: Summary blocks（被驱逐 chunk 的缓存摘要，候选 1b）
                    ↓
          根据推理时延预测，动态调整各层 token 预算：
          - 低负载/短会话：多注入 Level 1（精确）
          - 高负载/长会话：多注入 Level 2+3（紧凑）
```

这个组合的统一框架可以借鉴 CrystalMem 的 fidelity 降级调度【论文 2608.00303】，但把降级触发条件从 byte-budget 改为**推理时延 SLO 驱动**。这是本课题相对于 CrystalMem 的差异化贡献：CrystalMem 在 byte budget 上做弹性，本课题在**推理时延 SLO** 上做弹性，且把决策层放在 Flink 流处理控制面而非模型侧 sidecar。

### 5.5 需要补全的时延模型维度（用户特别提醒）

现有推理时延预测只覆盖排队+推理。本方向引入的额外成本：

| 成本项 | 性质 | 是否在现有模型内 |
|---|---|---|
| Compression/projection LLM call | 一次标准 prefill+decode | **在现有模型内** |
| Summary block 拼接后的 prompt prefill | 输入长度 = 注入的 summary token 数 | **在现有模型内**（输入长度可观测） |
| Flink keyed state 查找 | O(1) 哈希，亚毫秒 | 可忽略 |
| Embedding 相似度检索（决定用哪个 summary） | CPU/GPU embedding + ANN | **不在现有模型内**，需补全；或用 DPM 式延迟投影避免检索 |
| LLM 结构化提取 state variables | 一次 LLM call | 在现有模型内 |
| Memanto 式无索引检索 | sub-90ms CPU | **不在现有模型内**，需补全 |

**建议【分析】**：优先采用 DPM 式做法（不做在线检索，decision time 一次 projection），避免引入 embedding 检索成本到 hot path。检索只在跨会话（候选 2）场景出现，且可以异步化。
