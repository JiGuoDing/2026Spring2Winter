A

共同骨架：从"重复"推到"中间结果"

这批论文的问题背景有一条稳定链路。区别只在各篇把哪一步当作主要矛盾。

步骤 论文在这里放什么 你第一章要准备什么
场景定位 固定系统形态：Plan-Act、RAG、多轮会话、具身循环 流式 Agent 的事件流：请求、工具返回、证据更新
重复证据 比例、token、时间、金额 四类对象各自的重复形态与可测口径
成本测量 把重复换算成延迟、费用、显卡小时 统一口径：用户端时间、token、调用次数、后台工作量
朴素复用失效 精确匹配不中、语义匹配不等价、KV 依赖前缀 三类失效分别落在哪类对象上
局部性来源 需求头部集中、结构模板、DAG 依赖、工作流顺序 你的复用机会来自结构、版本还是权限
收益口径 命中率乘单次节省，再减开销 只把"通过有效性检查的复用"计入收益
难点收束 有效性、验证成本、失效传播、非平稳 四个小点与两条路径

三条共同出发点。 它们合起来就是"为什么缓存中间结果"的完整论证。

  1. 成本位置。 最贵的阶段在中间：规划、检索、工具调用，而不是最后的逐 token 解码。
  2. 结构可复用。 中间结果自带结构：计划模板、文档块、工具历史、DAG 子图。结构让匹配比"整句相似度"更准。
  3. 风险可治理。 中间结果可以绑定依赖、版本、权限与校验。最终答案很难这样做。
常见写法错误

只写"缓存能降本增效"，没有先证明重复发生在哪、省下的是哪一段工作、为什么会复用错。 读者会追问：命中率从哪来，错误由谁承担。

怎么选。 你要论证"缓存 Agent 中间结果"的必要性，最稳的是"地图开场 + 局部性观察"。前者排除已有方案，后者给出你自己的复用机会。

C

C resp 层：把"相似"拆成"可安全复用"

这一层的共同写法是：先承认语义缓存有效，再把"相似不等于正确"写成核心矛盾。

vCache（ICLR 2026）

  • 开场：先承认语义缓存能省高达 100 倍延迟，再指出工业界统一用一个静态阈值，例如 0.8。
  • 矛盾：正确命中与错误命中的相似度分布高度重叠。45k 样本上，固定阈值要么错误率高，要么被迫设得极高。
  • 出发点：把全局阈值换成逐条目在线学习的阈值，用用户给定的错误率 δ 约束。
  • 收益：最高 12.5 倍命中率、26 倍更低错误率。作者明确这是统计意义的保证。
  • 难点：依赖 i.i.d. 请求与 sigmoid 曲线假设；负载漂移后没有重校准；不涉及容量与 TTL。
  • 可借用：三连问——有没有保证、分布是否重叠、条目是否同质。

Krites（EuroMLSys 2026 Workshop）

  • 开场：先描述生产实践的两层结构：离线精选的静态层，加在线写入的动态层。
  • 矛盾：两层都用单一阈值。收紧漏掉安全复用，放松则返回语义错误的结果。
  • 出发点：把"相似度略低于静态阈值"的灰区请求交给离路径判官验证，通过后提升到动态层。
  • 收益：静态来源服务比例从 8.2% 升到 19.4%，搜索流量从 2.2% 升到 8.6%；关键路径延迟不变。
  • 难点：判官假批准会直接变成质量事故；静态层本身陈旧时没有失效传播。
  • 可借用："不改变关键路径，只提升覆盖"这个卖点写法，适合你的异步验证提升机制。

MVR-cache（ICML 2026）

  • 开场：承认 vCache 已经解决阈值，但输入仍是整句一个向量。
  • 矛盾：同一部剧的两条评论主题词相同、情绪相反，整句余弦相似但回答不同。
  • 出发点：用学习式分段加多向量匹配，把决定等价性的局部片段单独嵌入。
  • 收益：同一 δ 下命中率高于 vCache，always-cache 协议下最高提升 37%。
  • 难点：非 LLM 开销是 vCache 的两到三倍；分段模型需要训练标签。
  • 可借用：把"相似度不够细"写成可测量的失败案例，再定义新的匹配粒度。

SISO（arXiv 2025）

  • 开场：把现有语义缓存的问题归为三条：单条查询为单位、LRU/LFU 淘汰、所有请求都走缓存。
  • 矛盾：语义相近的查询重复存储，而 LRU 会误删覆盖一大片查询空间的高价值条目。
  • 出发点：用质心代表查询簇，用语义局部性替换时间局部性，并只在 SLO 受压时启用缓存。
  • 收益：命中率平均为 GPTCache 的 1.71 倍；替换策略比次优 LFU 高 43%。
  • 难点：只支持单轮；高负载下仍有 6.9% 的边际准确率损失。
  • 可借用：把"什么时候不该用缓存"写进背景，这会显著提高论证可信度。

MeanCache（IPDPS 2025）

  • 开场：把服务端语义缓存的五个问题一次列出，其中隐私与网络成本最突出。
  • 矛盾：中心缓存越大越难扩展；用户查询即使命中也要过网络。
  • 出发点：把缓存搬到用户侧，用联邦学习共享嵌入与阈值，查询不出设备。
  • 收益：F 值 0.73 对 GPTCache 的 0.56；上下文链把假命中从 54 条压到 3 条。
  • 难点：无法利用跨用户复用；合成数据占比较高；没有形式化隐私保证。
  • 可借用：用"问题清单"开场的结构，适合写多约束场景。
D

D plan / tool / reasoning 层：为什么必须缓存中间结果

这一层最直接回答你的问题。共同写法是两步：先证明最终答案不能缓存，再证明中间结果可以。

先看收益与难点的对照。

这一层的三句话论证

背景：Agent 的成本与延迟集中在规划、检索、工具三个阶段，这些阶段的输出依赖外部状态，不能像聊天回答那样直接复用。 收益：省下的是单次任务里最贵的一段工作，而且中间结果结构稳定，命中率可以很高。 难点：有效性由状态、版本、参数决定；从模板适配到当前任务需要校验；写入本身有成本，错误会沿执行链传播。

Agentic Plan Caching（NeurIPS 2025）

  • 开场：Plan-Act 循环里，规划阶段用思维链或推理模型，消耗大量 token，是成本大头。
  • 矛盾：两类现成缓存都不适配。KV 缓存与模型绑定，不能跨模型迁移；语义缓存假设输出只由 prompt 决定。
  • 反例：同一个"总结数据集统计量"的请求，计划结构相似，具体步骤取决于数据；同一句"删除顶部评论"，坐标与滚动量不同。
  • 出发点：抽计划中可复用的结构，命中后用轻量模型适配，而不是复用旧输出。
  • 收益：平均成本降 50.31%，延迟降 27.28%，保留 96.61% 性能；写路径只占总成本 1.04%。
  • 难点：关键词精确匹配牺牲召回；模板可能过拟合；没有 TTL 与版本。
  • 可借用：用两个具体反例证明"语义相似不等于计划可复用"，这是最有说服力的段落。

AWM（ICML 2025）

  • 开场：现有 Agent 把固定示例放进上下文，任务或环境一变就缺乏鲁棒性。
  • 矛盾：Agent 逐个任务求解，不从过去成功与失败中学习，因此不会随时间适应。
  • 出发点：从轨迹归纳可复用的工作流，而不是塞完整示例。抽象的工作流更容易跨任务迁移。
  • 收益：WebArena 成功率 35.5%，基线 23.5%；平均步数从 7.9 降到 5.9。
  • 难点：只覆盖网页导航；没有 token、延迟、显存数据；记忆规模与冲突未分析。
  • 可借用："抽象层次越高，迁移性越好"这一句可以直接支撑你把 plan 独立成一类对象。

GenCache（NeurIPS 2025）

  • 开场：可重复工作流里，prompt 结构相同但有少量关键差异。
  • 矛盾：精确匹配不中；语义缓存忽略关键差异，返回错误答案。
  • 定义：用结构化、受控变化、响应模式可预测三条性质定义"结构相似"这一新问题类。
  • 出发点：缓存的是生成程序，不是答案。命中后本地执行程序，按参数产出新答案。
  • 收益：命中率 83%；token 省 35%–73%；SRE 场景执行时间 39.91 秒对 53.45 秒。
  • 难点：程序生成成功率在真实云运维只有 10.4%；不适用自由聊天与不可逆动作。
  • 可借用：把"缓存对象从答案换成参数化产物"写成一句定义，读者立刻明白你为什么要做中间结果。

IC-Cache（SOSP 2025）

  • 开场：对四个开源请求数据集的分析显示，超过 70% 的请求有语义相似的历史请求。
  • 矛盾：精确匹配命中率低；语义匹配又因上下文不匹配降低质量。
  • 出发点：复用示例而不是答案。用小模型加高质量历史问答对，模仿大模型能力。
  • 收益：吞吐 1.4–5.9 倍，延迟降 28%–71%；与语义缓存组合还能提升质量。
  • 难点：质量靠 LLM 判官；隐私只有访问控制；固定衰减因子是启发式。
  • 可借用："同样一次命中，可以复用答案，也可以复用示例"这个二选一，是 resp 与中间结果之间的桥梁。

TVCACHE（ICML 2026）

  • 开场：后训练 Agent 的工具调用可以复用，但前提是环境状态一致。
  • 矛盾：只看请求语义会命中"历史上对的、当前状态不对"的工具结果。
  • 出发点：用完整工具调用历史树做最长前缀匹配，只有工具历史一致才复用。
  • 收益与难点：本章参考文献汇总只收录了机制摘要，未见原文解读，引用前需要核对正式版数字。
  • 可借用：把"状态一致"作为复用的硬条件，可以直接对应你 act 对象的有效性检查。

AgenticCache（MLSys 2026）

  • 开场：具身 Agent 每一步都问 LLM。超过 70% 运行时间花在规划查询。
  • 矛盾：并行规划会因环境变化失效；推测规划回滚成本高；纯模式缓存忽略状态。
  • 观察：计划转移有强局部性，下一步通常只由少数常见转换决定。
  • 出发点：缓存计划转移，并用状态元数据范围过滤候选，用确认比例给可靠性打分。
  • 收益：跨 12 个配置平均时延降约 65%，token 降约 50%，成功率平均提升约 22 个百分点。
  • 难点：平均提升不是每个任务都提升；部分 benchmark 反而下降。
  • 可借用：用"平均值的边界"提醒自己，headline 数字不能写成普适结论。

SemanticALLI（arXiv 2026）

  • 开场：Agent 流水线会反复重建相同的中间逻辑，例如指标归一化与图表骨架，即使自然语言表述全新。
  • 矛盾：以整条请求为边界的缓存命中率只有 38.7%；瓶颈在黑箱式缓存看不到流水线内部。
  • 出发点：把结构化中间表示提升为一等可缓存工件，拆成意图解析与可视化合成两个阶段分别缓存。
  • 收益：可视化合成阶段命中 83.1%，跳过 4023 次 LLM 调用，中位延迟 2.66 毫秒。
  • 难点：依赖流水线可分解；分解质量决定命中与正确性。
  • 可借用：一句结论可以直接引用——即使用户很少重复自己，流水线也经常在稳定的结构化检查点重复。

Workload-Aware Caching（arXiv 2026）

  • 开场：多代理系统把任务分解成 DAG，中间结果天然有复用机会。
  • 矛盾：现有淘汰策略只看访问历史，忽略结构与负载信号。
  • 出发点：把重算成本、DAG 依赖数、代理调用频率合成一个打分函数。
  • 收益：相对无缓存时延降 64.7%，比次优有限容量基线平均低 31.1%。
  • 难点：依赖计数需要维护；与 plan 缓存、并行执行是互补关系，不是替代。
  • 可借用：这三项信号与你价值模型里的"节省成本、依赖数、需求频率"几乎同构。

Why Agent Caching Fails（arXiv 2026）

  • 开场：给出结论式证据。GPTCache 在实际基准上准确率 37.9%，APC 只有 0–12%。
  • 矛盾：现有方法优化的是分类准确率，而缓存真正需要的是键一致性与精确性。
  • 出发点：把缓存键评估退化为聚类评估，用 V-measure 分解两类错误，再用结构化意图分解做规范化。
  • 收益：SetFit 用每类 8 个示例达到 91.1%，约 2 毫秒；GPTCache 为 37.9%。
  • 难点：跨语言迁移仍有损耗；风险控制依赖 RCPS 假设。
  • 可借用：把"缓存失效首先是键失效"写进背景，能把你的候选检索小点顺势引出。
E

E ctx / KV 层：省下计算，把压力转移到容量与带宽

这一层的共同写法是"收益与代价同源"。缓存确实省了重复预填充，但立刻制造新的容量、带宽与失效问题。

CachedAttention（USENIX ATC 2024）

  • 开场：统计 ShareGPT 九万多条会话，73% 是多轮，30% 超过 4K token。
  • 矛盾：引擎在会话空闲后丢弃 KV，下一轮重算全部历史；新技术会话中历史 token 占比可超过 99%。
  • 收益：命中率 71%–90%，首 token 延迟降 61%–87%，预填充吞吐提升 2.6–7.8 倍。
  • 难点：KV 体积是硬约束，GPT-3 每 token 4.5MB；上下文溢出后的截断会让已存 KV 全部失效。
  • 可借用："收益—代价同源"的最标准范式：先证明复用，再证明复用的代价。

Pensieve（EuroSys 2025）

  • 开场：多轮对话每轮都要把变长的历史重新预填充。
  • 难点三条：放哪里（显存快但小）、如何复用（可能只覆盖部分上下文）、换入换出会让 KV 不连续。
  • 观察：因果注意力让前部 token 重算更便宜，因此从头部驱逐。
  • 收益：吞吐为 vLLM 的 1.36–3.0 倍。
  • 可借用：用"三个难点"开场的结构，读者能立刻看到设计空间。

Continuum（VLDB 2027，arXiv 2511.02230）

  • 开场：定义 end-of-turn 驱逐，指出它适合多轮聊天却不适合 Agent。
  • 证据：SWE-Bench 平均 10.9 轮，工具时间均值 925 毫秒；BFCL v4 为 6.3 轮与 1923 毫秒。
  • 矛盾：工具调用期间淘汰 KV，回来要么重算，要么加载，还要承受每轮排队延迟。
  • 出发点：给 KV 一个按重载成本与排队延迟决定的 TTL。
  • 收益：平均任务完成时间降 1.12–3.66 倍，生产环境最高 8.18 倍。
  • 难点：工具时长分布不均，最慢 10% 的 fetch_url 占该工具总延迟 52.5%。
  • 可借用："现有策略的错误假设"这种写法，比"现有方法效果不好"有力得多。

KVFlow（NeurIPS 2025）

  • 开场：多代理工作流里每个代理有固定 prompt，适合前缀缓存。
  • 矛盾：执行顺序不是到达顺序，LRU 会把马上要用的缓存误判为冷数据。
  • 反例：四代理循环里，13 时刻淘汰 Expresser，14 时刻立刻 cache miss。
  • 出发点：用工作流步距预测未来复用，做主动预取。
  • 收益：相对 SGLang 加 HiCache 提升 1.24 倍；固定前缀越长收益越大。
  • 可借用：一个时刻级的反例，比十行平均数据更能说明"顺序信息被忽略"。

LMCache（arXiv 2510.09665）

  • 开场：把 KV 缓存称为 LLM 原生知识表示，并给出线上统计。
  • 矛盾：用户存储的 KV 总量持续增长并远超 GPU 容量；超过 19% 的用户复用次数超过 1.5。
  • 出发点：把 KV 从 GPU 移出，做共享与复用，而不是只做单次查询优化。
  • 收益：首 token 延迟降 1.9–8.1 倍，同延迟下吞吐高 2.3–14 倍。
  • 难点：页太小打不满带宽；模型迭代导致布局频繁变化；缺统一接口。
  • 可借用：把"复用已经是既成事实，只是系统没有接口"写成出发点。

Marconi（MLSys 2025）

  • 开场：混合模型里 SSM 状态原地更新，不能像 KV 那样切片复用。
  • 两难：要复用就得细粒度检查点；细粒度检查点产生大而稀疏的条目。
  • 证据：块大小 32 时，25.0% 的 KV 块被复用，但只有 0.4% 的 SSM 状态被复用，相差 65.3 倍。
  • 收益：token 命中率提升 4.5–34.4 倍，P95 首 token 延迟降 36.9%–73.2%。
  • 可借用：把"两难"写成显式结构，是工程类论文最容易借用的段式。

Mooncake（FAST 2025）

  • 开场：面向上亿用户的聊天服务，负载在输入长度、到达分布、SLO 上高度多样。
  • 出发点：把预填充、解码、KV 池解耦成独立资源池。
  • 收益：有效请求容量提升 59%–498%；工具型负载下比 vLLM 前缀缓存高 42%。
  • 难点：全局池需要高带宽网络，100 Gbps 是论文建议的下限。
  • 可借用：给出一个带宽判据而不是口号，读者会相信"为什么必须全局池"。

AdaptCache（SOSP 2025 BigMem）

  • 开场：直接给容量缺口。两个 H100 节点加 150GB 内存只能存约 50 万 token；Agent 一次运行可产生数百万 token，对应 KV 约 3TB。
  • 矛盾：KV 超过显存与内存容量，只能放到 SSD，而 SSD 加载慢。
  • 出发点：压缩算法与放置位置都随内容与复用频率变化。
  • 收益：同质量下延迟降 1.43–2.4 倍。
  • 可借用：用容量缺口数字开场，是硬件类动机最直接的写法。

Cortex（USENIX NSDI 2026）

  • 开场：Agent 循环里远端检索在关键路径上，Search-R1-7B 上外部检索约占端到端时间 40%–50%。
  • 矛盾：现有缓存只加速推理，不解决外部数据访问；语义缓存比较 prompt，不在知识边界做校验。
  • 观察：搜索兴趣头部集中；代码 Agent 反复读同一批核心文件。
  • 出发点：在外部知识结果这一层做语义复用，用向量召回加小模型判官验证。
  • 收益：吞吐提升 3.6 倍，命中率超过 85%，正确性与无缓存基本一致。
  • 难点：负载是构造的；只测读取型检索；判官正确率没有完整曲线。
  • 可借用："缓存放在哪一层"这个问题，可以写成一句坐标式判断。

RAGCache（ACM TOCS 2026）

  • 开场：RAG 输入由检索文档与原问题拼接，100 token 的请求可变成 1000 token 以上。
  • 证据：文档平均 3718 token，MMLU 请求平均 348 token；输入超过 4000 token 时推理接近 1 秒。
  • 观察：同一文档跨请求重复；MMLU 中前 3% 的文档被 60% 的请求引用。
  • 难点：文档顺序敏感；CPU 检索与 GPU 生成串行会让 GPU 空转。
  • 收益：首 token 延迟比 vLLM 低 1.2–4 倍，替换策略优于 LRU 1.06–1.62 倍。
  • 可借用：先给"输入被放大"的比例，再给"热点集中"的分布，两段就能立住动机。

Cache-Craft（SIGMOD 2025）

  • 开场：RAG 输入以检索块为主、回答很短，因此预填充是主要成本。
  • 证据：LLaMA-3-70B 处理 32k token、batch 8 时预填充可达 76 秒；生产系统里预填充占推理时间最多 77%。
  • 矛盾：前缀缓存对 RAG 几乎无效，只覆盖 8% 的请求与 18% 的预填充 token。
  • 观察：75% 的检索块被重复处理，一个月超过 12B token。
  • 收益：比前缀缓存减少 51% 冗余计算；重算 20% token 时 ROUGE 0.87。
  • 难点：知识库相对静态的假设；没有评估文档更新后的失效。
  • 可借用："现有优化只覆盖 X%"是最锋利的缺口写法。

TurboRAG（EMNLP 2025）

  • 开场：传统 RAG 把 k 个块拼成长序列再预填充，带来三个问题。
  • 观察：跨块注意力稀疏；RoPE 只依赖相对位置。
  • 出发点：离线逐块预填充，在线拼接，位置重排。
  • 收益：首 token 延迟从 1165 毫秒降到 134 毫秒，约 8.6 倍。
  • 难点：存储代价被明确承认，1M 个 512 token 块约需 28TB；需要微调。
  • 可借用：把代价主动写出来，反而增强可信度。

CacheBlend（EuroSys 2025）

  • 开场：RAG 输入包含多个检索块，预填充要处理全部 token。
  • 矛盾：前缀缓存只能复用第一个块；全量 KV 复用忽略跨块注意力，F1 明显下降。
  • 出发点：问题不是要不要复用，而是如何补回跨块注意力。重算少量关键 token。
  • 收益：首 token 延迟比完整重算低 2.2–3.3 倍，质量下降不超过 0.02。
  • 难点：只适用 transformer；大模型上加载遮不住重算。
  • 可借用：把连续问题改写成"补回缺失信号"，是方法类动机的经典转法。

ContextPilot（MLSys 2026）

  • 开场：长上下文预填充瓶颈；引擎经常处理 20k–130k 个预填充 token。
  • 矛盾：精确前缀命中率只有 4.6%–5.5%，因为文档顺序常变。
  • 观察：MultihopRAG、NarrativeQA、QASPER 中分别有 79.2%、57.4%、49.6% 的问题来自前 20% 最常访问的文档。
  • 出发点：把部分重叠变成可命中前缀，靠对齐与去重。
  • 收益：最高比 LMCache 快 3.08 倍。
  • 可借用：用"命中率为什么低"的机制解释，比单纯抱怨命中率低更有力。

FreshCache（arXiv 2026）

  • 开场：开放网页 RAG 每条查询延迟常超过 3 秒，语义缓存可以跳过重复流程。
  • 矛盾：固定 TTL 两难。首都可复用数月，比分几分钟就过期。
  • 定义：把复用改写成风险约束的时间推断，而不是相似度阈值。
  • 收益：0.1% 过期率与 97% 搜索节省；基线 SemanticTTL 为 14.9% 与 72%。
  • 难点：真实条件 GET 只有 11.3% 返回 304；模型跨域迁移会掉点。
  • 可借用："问题不是是否相似，而是过期概率是否低于预算"这句话，直接适配你的有效期估计。

FinCacheServe（arXiv 2026）

  • 开场：企业 RAG 反复执行语义等价的分析请求，但文档会变。
  • 矛盾：基于相似度或固定 TTL 的命中可能返回过期证据。
  • 出发点：把答案缓存定义为 serving 对象，记录请求签名、源文档版本、证据指纹、工具指纹与反向索引。
  • 收益：跳过 53.27% 的模型调用且 0 条过期输出；强基线下跳过率只有 38.97%。
  • 难点：一致性承诺是相对已记录依赖，不是事实正确性；元数据持久化是瓶颈。
  • 可借用："回答说到底是一个带依赖的服务对象"这个定义，是你依赖传播小点最好的引子。

H

给第一章的落地写法

建议的段落序列。 每段只推进一个判断，段末留下一个未答问题。

  1. 固定场景：流式 Agent 的事件流，请求、工具返回、证据更新如何交错。
  2. 给出重复证据：四类对象各自的重复形态，加一个可核验的量级测算。
  3. 指出朴素复用失效：精确不中、语义不等价、依赖与版本不一致。
  4. 论证为什么缓存中间结果：成本位置、结构可复用、风险可治理。
  5. 给出收益口径：命中率乘单次节省，再减验证与维护开销。
  6. 列难点：非平稳需求、对象异质、依赖传播、在线估值开销。
  7. 收束到四个小点，并给出与后续章节的对应关系。

你要写的论断 放在哪一段 配哪几篇

每类对象的难点句骨架。

  • resp：复用省下生成，但语义相近的回答可能不等价。质量控制要落到条目级，而不是全局阈值。
  • rag：复用省下检索与回源，但证据有版本与新鲜度。复用前必须核对来源状态。
  • act：复用省下工具调用，但结果依赖外部状态。工具历史或参数不一致时不能复用。
  • plan：复用省下规划，但计划要与当前参数绑定。适配失败需要回退。
三个容易踩的坑

把数据集与环境类文献当动机引用，审稿人会问它们与缓存决策有什么关系。 把某篇论文的 headline 数字当成你的前提，忽略它的负载与边界条件。 只讲收益不讲验证成本，价值模型会被质疑为单一指标。

非缓存类参考文献怎么用。 第一章的 32 条文献里，有一半不是缓存机制论文。写背景时不要把它们的结论当动机，而要把它们放到实验与评测段。

文献 它在第一章的角色 写法提醒
AgentBench、WebArena、WebShop 任务与环境来源 只说明能采集哪些事件，不要写成"证明缓存有收益"
ToolBench、StableToolBench 工具 API 与可复现响应 模拟响应不等于真实在线工具成本
StreamRAG 流式场景背景 说明知识随流更新，它不研究缓存修复
HoH 过时信息评测 支撑"旧证据会过时"，使用前核验字段
